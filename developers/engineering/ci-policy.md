# CI and merge policy

English | [简体中文](../zh-CN/engineering/ci-policy.md)

## Routine checks

[CI](../../.github/workflows/docs.yml) runs one Linux job on pushes to main, pull requests, and manual dispatch. It checks documentation links and JSON, versions and UI text, generated-resource consistency, window/shared-control contracts, Rust and native source formatting, workflow structure, and whitespace errors. Rust input changes run the same strict workspace Clippy command as release validation and check production dependency boundaries for Linux. CI compares the full push or pull request difference and runs both checks on manual dispatch or when the comparison base is unavailable. It does not build the desktop product or run complete Rust, three-platform Qt, archive-format interoperability, packaging, or installation lifecycle checks. The target is usually under five minutes, with queue and download times in the run records.

Routine CI and Foundation use `scripts/check-native-format.py` with clang-format 18.1.8. The check covers tracked handwritten C, C++, Objective-C, and Objective-C++ sources. The format registry generator checks its generated native header, and the archived preferences compatibility fixture keeps its original source.

Each PR update can cancel older runs for the same PR; main and manual runs use independent run identities. Failures and cancellations do not count as passes. Workflows use read-only repository permissions and pinned dependencies, without release keys. Routine CI does not start Playwright, Chromium, or another web browser.

### Change classification and fallback

[ci-plan.py](../../scripts/ci-plan.py) classifies the full Git tree difference against a verified base using [the committed policy](../../scripts/ci-plan-policy.json). The current allowlist admits only an in-place UTF-8 change to `docs/README.md`, subject to the file and diff budgets. Other paths, adds, deletes, renames, mode changes, unverifiable Git history, and manual dispatch produce `classification=full`. The current `shadow` mode keeps `run_heavy=true` even when it classifies a change as `plain-docs`.

Foundation and Qt record separate `build/ci-plans/*-plan.json` artifacts. A missing or failed plan falls back to the full checks for a non-cancelled ordinary run. The explicit Foundation diagnostic inputs select their own jobs. Routine CI runs its lightweight job independently of the plan. For classifier or workflow changes, run `python3 scripts/test-ci-plan.py` and `python3 scripts/test-ci-workflows.py` locally.

## Local verification before commit

Before committing and pushing, complete the build or verification appropriate to the proposed changes locally and record what actually ran. Git hooks are not required. Reverify after source or configuration changes that affect results; do not describe tests including other uncommitted changes as results for a clean commit.

| Change | Local verification |
| --- | --- |
| Documentation and static assets | Check links, JSON, and affected generated outputs. |
| Rust core and formats | Check formatting; build or test affected crates and business paths. Changes to secure I/O, formats, or task semantics cover relevant failure, cancellation, and protection behavior. |
| C++, Qt, and bridge | Build affected targets; run relevant model, bridge, and interaction tests. |
| QML windows | Check window contracts, shared controls, and bilingual multi-font-size layouts. For radio or checkbox behavior changes, exercise actual accessibility actions and inspect the selection model. |
| Packaging, installation, and updates | Run affected local tests; use appropriate workflows as needed for isolated systems, other platforms, or real installations. |

For native bridge build changes, check the desktop and isolated worker targets. Each tracks the local normal and build dependencies resolved by Cargo for its native target. Verify that a shared source change reaches the appropriate bridges and that unrelated crate sources leave them up to date. For incremental CLI staging, rebuild with the same inputs and check that staged binaries, identity and desktop context retain their timestamps. Then check that changed input bytes propagate even when size and timestamp match.

Native sidecars are declared build outputs. Verify that a missing installed copy is restored, a sidecar-only change updates its copy, and neither operation relinks the desktop executable. The worker, bridge, bundled CLI and update helper use the same CMake profile mapping. Debug uses Cargo dev, Release uses Cargo release, and RelWithDebInfo uses an optimized Cargo profile with debug information. The supported desktop and CLI build entry points share source provenance. A direct Cargo build without that provenance reports an unknown revision.

The desktop product and its browser, shell and update checks link the shared session target and its `Xdzip.Native` QML registration. Keep target-specific fixtures and definitions on the executable that uses them. For changes to this target, check that its common sources compile once and verify QML loading in the product and affected test entry points.

See the [developer build guide](../../docs/engineering/developer-build.md) for commands and toolchain prerequisites. Prefer the environment available on the current machine. When required tools are missing, report unexecuted checks; do not report preflight or another platform's results as a local pass. Routine checks do not require a full IDE installed locally and do not automatically install the product or change file associations.

## Full checks on demand

[MSIX shell integration](../../.github/workflows/windows-msix-shell.yml) builds the production menu DLL and a small, independent activation fixture without Qt. Run it directly or select `shell_only` in [MSIX lifecycle](../../.github/workflows/windows-msix.yml). The default host is Windows 11 ARM using x64 emulation; `windows-2025` provides a native x64 COM diagnostic, without establishing Windows 11 desktop acceptance. Reports record the actual OS and architecture.

The probe checks package registration, bilingual classic menus, enablement changes, refusal to invoke a disabled menu, package activation, modern-menu signature rejection, unregistered targets and default choices. It activates the installed fixture by its AUMID under a disposable standard account and rejects elevation. Loading its WindowsApps DLL requires the fixture package identity; an unpackaged copy is not a valid substitute. Each invocation removes an old receipt before checking a fresh package activation. Hosted session restrictions and activation through alternate credentials can prevent these checks from completing. A failed probe provides no menu-activation pass and must remain recorded as unresolved. Fixture certificates, package registrations, development-policy values and temporary accounts are cleaned up or restored. Self-signed fixtures do not establish real Store signature acceptance or Explorer display.

[Foundation probes](../../.github/workflows/foundation.yml) and [Qt components](../../.github/workflows/qt-components.yml) run manually across Windows, Linux, and Apple Silicon macOS. Foundation covers the Rust workspace, Clippy, bridge probes, isolated workers, and format interoperability. Qt covers product builds, component and session tests, native platform checks, deployment, and applicable installation lifecycles. Qt components and Release each run the complete browser suite once. Run [Browser stability](../../.github/workflows/browser-stability.yml) on the candidate commit when archive browsing, session timing, or Qt changes require repeated verification. It checks ten complete rounds against that commit and retains their logs.

Qt on-demand `test --skip-rust` marks the Rust workspace as not executed. When a Foundation conclusion is needed, run and verify it separately for the same commit; Qt results alone do not establish a Foundation pass. Running failures, cancellation, missing platforms, or missing original logs still fail the corresponding full check. Use only runs and artifacts actually executed for this work.

Foundation and Qt use pinned-input caches containing only Cargo downloads, pip downloads, pinned Qt corresponding-source archives and (for Qt) the hash-verified upstream UI font, not compiled products, generated font subsets, installed Qt SDKs, test conclusions, or credentials. Trusted manual main runs may save hash-sealed caches; other branches only restore and verify them. Cache hits do not replace rerunning checks.

[UI font generation](../../.github/workflows/ui-fonts.yml) is a lightweight manual three-platform check for automatic glyph coverage, offline cache failures, concurrent generation and identical TTF/WOFF2 output hashes. It uploads JSON only, without building or deploying Qt applications. Routine CI runs the font regressions on Linux. See the [font guide](../../design/assets/fonts/README.en.md) for preparation and preview commands.

Foundation natively builds and runs CLI regressions without Qt on all three platforms, clearing display-session and Qt search paths and retaining JSON receipts. Qt builds also verify private CLI layout and same-user update handoff. Standalone package generation requires passing receipts bound to the same executable, worker hash, and build identity. Three-platform CLI release packages and independent signing manifests are produced only by an authorized Release workflow. Ordinary macOS CI still uploads only logs and JSON.

Foundation CLI checks use the unified build entry point and real binaries and also verify creating, running, overwrite protection, and removal of user-level command entry points. Installation fixtures copy only project-owned test binaries, do not generate release archives or deploy the desktop application, and upload only JSON receipts. Private update fixtures are also exercised.

Manual Qt runs on Windows and Linux upload experimental development packages and verification artifacts, normally retained for 14 days. Ordinary macOS checks retain only logs and JSON and do not deploy, sign, or upload app packages. Routine CI does not produce these development packages. See [Mac deployment](../../docs/engineering/macos-deployment.md) and [release protocol](../../docs/engineering/release-protocol.md) for on-demand development DMG and dedicated Release exceptions.

Ordinary development and release acceptance do not automatically generate project-source archives or invoke the corresponding-source collector. Source collection requires a separate explicit owner request. GitHub's tag-provided source snapshots are described separately from project pipeline attachments.

[SDK trial](../../.github/workflows/sdk-trial.yml) is also manual only. It first runs independent read-only protocol and native-kernel gates without downloading Qt or deploying the application and uploads only logs and JSON. Foundation's manual `sdk_only=true` option invokes the same SDK workflow and skips the full Foundation jobs and gate; it cannot establish a full Foundation pass. Use this entry point first to narrow SDK platform failures. Reuse other still-applicable Foundation and Qt evidence according to the verification method.

Foundation `image_only=true` uses system sips/ImageIO on native macOS to convert a fixed project-owned HEIC, installs pinned Qt through the same shared toolchain preparation method, and separately builds the real image worker and test controls. It compares an unrestricted Qt reader and real worker code with one limit omitted at a time to distinguish system/plugin capabilities from resource budgets; test interceptors do not enter product builds. `--verify-worker` additionally requires correct dimensions/pixels for two inputs through the real parent and default worker, growth within the runtime file budget, and EFBIG beyond it; otherwise this check fails. This entry point does not build the desktop application, deploy, or sign, and saves only JSON and logs. Observed success or affected-component regression does not establish a full product/Foundation pass. The two preflight options are mutually exclusive.

### Update-specific verification

[Native update regression](../../.github/workflows/update-regression.yml) uses isolated fixtures and offers one platform for diagnosis or `platform=all` for its full matrix. [Production update acceptance](../../.github/workflows/production-update-acceptance.yml) is a separate manual workflow. It checks the production trust roots through the protected `release-signing` environment on `main` and exercises signed fixtures. Publish decisions still use the dedicated release workflow and the actual candidate. Identify the run, platform, and scope in the issue. For long native jobs, normally check at least five minutes apart and read relevant log excerpts only.

## Visual, desktop, and release

Run automation appropriate to the change first, and inspect the actual application or screenshots where practical. Check input methods, real screen readers, system dialogs, window decorations, physical multiple displays, and real GPUs as needed. Record limitations when checks or environments are unavailable. Maintainers need not complete a fixed manual checklist every time, and offscreen, synthetic-input, or virtual-display results are not recorded as human or physical-device passes. See [desktop verification](../qa/private-test-manual.md).

[Windows native visual diagnostics](../../.github/workflows/windows-native-visual.yml) can manually capture project-owned windows and menus. It is a one-off hosted-runner automated diagnostic, not human clicking or physical-display acceptance. [Qt source verification](../../.github/workflows/qt-source.yml) and update-specific workflows likewise use their respective manual entry points.

The Windows visual entry first runs `test-windows-capture.ps1` to check the [reusable screenshot tools](windows-screenshots.md), including PNG pixel fidelity, receipt rejection and reproducible demo inputs. This self-test does not operate the desktop and does not add a Windows job to ordinary CI.

[Windows MSIX lifecycle](../../.github/workflows/windows-msix.yml) builds an experimental package on a disposable GitHub-hosted Windows Server, signs a test copy with a temporary self-signed certificate, checks sideload installation, default associations, channel-specific update controls in the Chinese and English About pages, settings retention, portable coexistence, file activation, rejection of the ordinary installer's shell-registration command under MSIX identity, and uninstallation, then removes the certificate. The upgrade fixture increments only the MSIX manifest version for a dedicated CI identity and verifies every other product file remains unchanged, then checks upgraded settings, update-entry isolation, and default associations. It is not a new product version or Store update acceptance. This workflow is manual only and does not use actual Store signing or modify the developer's computer. Server sideload results do not establish Windows 11 desktop, Store provenance, ordinary installed-edition coexistence, or manual visual acceptance.

[Windows Store MSIX](../../.github/workflows/windows-store-msix.yml) is the manual packaging entry point for the Store identity. It builds a commit reachable from the `main` revision at dispatch, runs the desktop and CLI checks, verifies the deployed runtime and unsigned MSIX, and preserves the package and receipts as an Actions artifact. The desktop test step skips the Rust workspace and worker test inventory. Store submission, certification, signing and publication take place in Partner Center. See the [Store packaging instructions](../../docs/engineering/developer-build.md#microsoft-store-msix).

When only test scripts or the lifecycle workflow change, [MSIX lifecycle recheck](../../.github/workflows/windows-msix-recheck.yml) can be run manually with the original build run ID and complete commit. It checks package digests, production receipts, and commit ancestry and permits only explicitly listed test and documentation changes. Product or packaging-input changes require rebuilding. Results identify build and test commits separately; the old package is not called a new product build.

The recheck can optionally use GitHub-hosted `windows-11-arm` to run the same x64 package under Windows 11 x64 emulation. Results must identify system and architecture; this is not native x64, a native ARM64 build, or an expanded support commitment.

[MSIX and installed-edition coexistence](../../.github/workflows/windows-msix-coexistence.yml) reuses builds and runtime audits subject to the same provenance constraints, generates a per-user installer on a disposable hosted machine, and checks concurrent operation, mutual uninstallation, and default associations. It can use Windows Server or Windows 11 ARM with x64 emulation. It does not modify the maintainer's computer or replace Windows 11 x64 native and Store acceptance.

The [Release workflow](../../.github/workflows/release.yml) separately handles three-platform release builds, package verification, signing, and immutable assets under the [release protocol](../../docs/engineering/release-protocol.md). A release requires owner authorization for the specific result; unexecuted checks and license-review limitations are recorded accurately. Routine CI success, manual workflow success, and formal release approval are distinct conclusions.

For an authorized ordinary release, dispatch the formal Release once after the applicable local preflight. Do not run an equivalent full candidate rehearsal or three-platform packaging workflow first unless the user explicitly requests it, an applicable specification requires it, or a concrete risk cannot be resolved by targeted checks. Before any exception, record its necessity and recognize that the current formal workflow cannot promote artifacts from another run. Preserve applicable evidence and retry the affected job in the original run when valid; the decision rules and same-run boundaries are mandatory in the [release runbook](release-runbook.md#choose-the-minimum-release-runs).

Logs, screenshots, copies of test inputs, and generated reports remain only in `build/`, `dist/`, or Actions artifacts. Project source, design specifications, and test code remain versioned; actual work progress and results are recorded in GitHub issues.
