# 파일 관리자 작업과 독립 작업 호스트

[English](../../engineering/shell-actions.md) | [简体中文](../../zh-CN/engineering/shell-actions.md) | [繁體中文](../../zh-TW/engineering/shell-actions.md) | [日本語](../../ja-JP/engineering/shell-actions.md) | 한국어 | [Français](../../fr-FR/engineering/shell-actions.md) | [Deutsch](../../de-DE/engineering/shell-actions.md) | [Español](../../es-ES/engineering/shell-actions.md) | [Português (Brasil)](../../pt-BR/engineering/shell-actions.md) | [Русский](../../ru-RU/engineering/shell-actions.md)

시스템 진입점은 선택 항목과 작업을 같은 로그인 세션의 데스크톱 프로세스에 전달합니다. Windows 11에서 일반 설치 확장은 ‘추가 옵션 표시’ 아래에 나타납니다. 이 COM 클래스는 `IContextMenu`와 `IExplorerCommand`를 모두 제공합니다. MSIX는 별도의 클래식 처리기를 선언하며 Store 빌드는 아래 설명하는 최신 메뉴 처리기도 추가합니다. Ubuntu 24.04의 파일 관리자는 Nautilus 4.0 확장을 사용합니다. macOS는 Finder Sync 하위 메뉴, 서비스 명령과 독립 작업 패널을 제공합니다.

실제 플랫폼 검증과 남은 작업은 [#270](https://github.com/xiaodaozhi/xdzip/issues/270)에서 추적합니다. 소스의 기능이 이미 출시된 파일에 소급 적용되지는 않습니다.

유료 계정이 필요 없는 Finder Sync 구현과 로컬 검증은 [#273](https://github.com/xiaodaozhi/xdzip/issues/273)에서 추적합니다. Apple은 Finder Sync를 동기화 앱에 사용하도록 안내합니다. 이 프로젝트는 일반 압축 메뉴에 적용할 때의 제약을 받아들이며 App Store 심사 승인을 주장하지 않습니다. 로컬 ad-hoc 무결성 서명에는 유료 계정, Developer ID, App Groups 또는 공증이 필요하지 않으며 Gatekeeper의 게시자 신뢰를 제공하지 않습니다. [Apple Finder Sync 문서](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Finder.html)를 참조하세요.

## macOS Finder Sync

`Contents/PlugIns/xdzip-finder-sync.appex`는 Qt, Rust 또는 형식 라이브러리에 연결하지 않는 네이티브 확장입니다. `/`를 감시 루트로 모든 로컬 Finder 디렉터리를 대상으로 하며 Finder의 선택만 처리하고 디렉터리를 순회하지 않습니다. 도구 모음, 배지 또는 동기화 작업도 추가하지 않습니다. 일반 항목 하나에는 세 가지 생성 작업을 제공하고 여러 항목을 선택하면 항목별 ZIP 생성이 추가됩니다. 모든 항목이 압축 파일 후보이면 네 가지 압축 풀기 작업을 추가합니다. 빈 선택, 로컬이 아닌 URL 또는 128개를 넘는 선택에는 메뉴를 만들지 않습니다. 네이티브 메뉴의 크기는 시스템이 정하고 독립 작업은 공유 일반 밀도 창을 사용합니다.

확장은 사용자 Application Support의 자체 JSON 설정 `xdzip/finder-sync.json`만 읽습니다. 여기에는 현재 앱 위치, 활성화 상태, 언어, 등록 리비전과 로컬에서 무작위로 생성한 전달 토큰이 들어 있습니다. 파일은 8 KiB 이하이며 현재 사용자가 소유한 0600 일반 파일이어야 합니다. 쓰기는 원자적 교체를 사용하며 링크나 타인의 설정은 거부합니다. CFPreferences 파일은 아닙니다. 샌드박스는 이 정확한 파일에 대해서만 임시 읽기 전용 예외를 부여하며 사용자 디렉터리, App Groups 또는 네트워크 리스너를 공유하지 않습니다. 권한 경로는 `/`로 시작해야 합니다. [Apple의 임시 예외 명세](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/AppSandboxTemporaryExceptionEntitlements.html)를 참조하세요.

Finder가 메뉴 항목의 `representedObject`를 유지하지 않으므로 확장은 단조 증가 태그를 이용해 제한된 선택 스냅샷을 유지합니다. 만료된 태그는 새 선택을 가리킬 수 없습니다. 명시적인 `NSWorkspace` 대상을 통해 확장은 `xdzip-shell://v1/`의 base64url JSON 이벤트를 `Contents/Helpers/xdzip-shell-relay.app`으로 보냅니다. 샌드박스 호출자의 실행 인수는 신뢰할 수 없습니다. relay는 Qt에 연결하지 않는 별도 네이티브 앱입니다. 현재 사용자 비공개 설정의 무작위 토큰을 인증하고 URL, UUID, 작업, 경로와 JSON 한도를 검증하며 UUID를 유지한 채 기존 비공개 요청 파일 및 단일 인스턴스 진입점을 호출합니다. 승인 실패는 네이티브 오류로 표시합니다. 토큰은 요청 파일, 데스크톱 프로토콜 또는 제품 로그에 포함하지 않습니다. 올바른 토큰 없이 외부에서 만든 URL은 파일 작업을 수행하지 않습니다. URL은 로컬 전달에만 사용합니다.

확장은 고정된 번들 구조로 자신을 포함한 앱을 찾으며 샌드박스에서 외부 앱 메타데이터를 읽지 않습니다. relay는 호출할 때마다 외부 `Info.plist`를 다시 읽고 제품 ID, `XdzipShellProtocol=1`, `XdzipFinderSyncProtocol=1` 및 유효한 실행 파일 이름을 요구합니다. 롤백되거나 호환되지 않는 대상은 거부합니다. 로드된 이전 확장이 일시적으로 메뉴를 유지할 수 있지만 relay는 클릭을 거부해야 합니다. 서비스는 자체 기존 프로토콜을 별도로 검증합니다.

설치된 앱은 최초 실행 시 자체 appex와 서비스를 등록하지만 사용자가 시스템 설정에서 Finder 확장을 활성화해야 합니다. 설정의 토글은 두 진입점을 모두 관리합니다. 앱의 언어 변경은 확장 메뉴에만 적용되고 서비스 이름은 시스템 언어를 따릅니다. 설정을 반복 저장해도 변경 없는 appex를 다시 추가해 Finder 연결을 끊지 않습니다. 콘텐츠 다이제스트가 바뀌거나 등록이 없을 때만 재등록합니다. 비활성화는 이 앱의 정확한 경로에 대한 등록만 제거하고 비활성 설정을 유지합니다. 이전 복사본을 제거해도 더 새 앱의 설정은 비활성화하지 않습니다. 명시적으로 등록한 개발용 복사본은 비활성화 후 설정에서 다시 활성화할 수 있으며 등록되지 않은 개발용 복사본은 자동 활성화하지 않습니다.

업데이트할 때 Finder가 이전 확장 인스턴스를 유지할 수 있습니다. 필요하면 시스템 설정에서 소유한 확장을 껐다가 다시 켭니다. Finder를 강제 종료하지 않습니다. 롤백과 제거는 소유한 등록과 파일만 다루며 기본 파일 연결을 바꾸지 않습니다. 서비스 위치는 시스템이 정하며 컨텍스트 메뉴 최상위에 표시될 수 있습니다.

## Windows 패키지 경계

MSIX 빌드는 Windows 11의 ‘추가 옵션 표시’용 클래식 `IContextMenu` 처리기를 `desktop9:Extension`으로 선언합니다. Store 빌드는 최신 메뉴를 위해 별도의 `IExplorerCommand` 클래스와 `windows.fileExplorerContextMenus`도 선언합니다. 클래스는 서로 다른 ID를 가지며 각자의 메뉴 인터페이스만 제공합니다. 사이드로드 빌드는 클래식 클래스만 선언합니다. 일반 설치 프로그램은 기존 클래식 메뉴를 유지합니다. 파일 작업과 비공개 요청 검증은 두 메뉴 방식에서 공유합니다.

`--msix-channel store|sideload`는 변경 불가능한 패키지 표식과 일치하는 매니페스트 선언을 선택하며 기본값은 `sideload`입니다. 최신 명령에는 Windows 11에 등록된 Store 빌드와 해당 패키지 자체의 시스템 서명 종류 `Store`가 필요합니다. 서명 조회 실패 또는 Developer, Enterprise, None 서명이면 최신 항목을 숨깁니다. Store 서명된 Store 빌드의 복사본은 사이드로드로 설치해도 Store 빌드입니다. 이는 빌드 채널 정책이며 동일한 서명 바이트의 설치 경로를 알아낸다는 뜻이 아닙니다. [이 제약에 관한 Microsoft 논의](https://github.com/microsoft/WindowsAppSDK/issues/4993)를 참조하세요.

확장은 Explorer 프로세스 ID 대신 자체 DLL의 패키지 디렉터리와 현재 사용자 등록을 확인합니다. 호출할 때마다 등록과 실행 파일의 셸 프로토콜을 다시 검사한 다음 해당 패키지의 AUMID를 활성화합니다. 등록이 없거나 대체되었으면 실행을 거부합니다. 패키지 메뉴 언어와 활성 상태는 일반 설치 메타데이터와 별도의 패밀리 전용 키를 사용합니다. 앱은 패키지 ID로 일반 COM 등록을 쓰지 않습니다. 매니페스트 등록과 제거는 Windows가 관리합니다. 실제 Store 서명, Explorer 표시, 업데이트와 공존의 승인은 자체 서명 테스트 패키지 검사와 별개입니다. Windows 10에는 Windows 11 최신 메뉴가 없으며 현재 지원 범위 밖입니다.

[GetStagedPackageOrigin](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getstagedpackageorigin)은 준비된 패키지의 출처를 보고하며 검증된 사용자별 설치 경로는 아닙니다. 진단용으로 유지하며 최신 메뉴 승인에 사용하지 않습니다.

출처를 비교하려면 현재 사용자에게 대상 패키지가 등록된 Windows에서 아래 읽기 전용 진단을 실행합니다. 패키지 이름은 예시이며 출력은 `build/` 아래 새 JSON 파일이어야 합니다. 진단은 시스템 서명 종류, 준비된 패키지 출처와 전체 패키지 이름의 익명화 다이제스트를 기록하고 등록 버전이 유일하지 않은 결과를 거부합니다. 시나리오는 작업자 라벨이며 설치 채널의 증거가 아닙니다. 조회 실패, 알 수 없는 값 또는 동일한 결과만으로 메뉴를 허용할 수 없습니다. 인증서, 설치 또는 시스템 설정을 변경할 필요는 없습니다.

```powershell
python scripts/msix-origin-probe.py --name xdzip.Example --scenario store-install --output build/store-origin-observation.json
```

## 선택과 출력

파일 관리자에서 생성할 때의 확인은 기본 다운로드 디렉터리를 먼저 검사하지 않고 미리 채워진 원본 디렉터리 또는 선택한 대상을 직접 검사합니다. 관련 없는 macOS 개인정보 접근 지연을 피하기 위함입니다. 일반 메인 창 생성은 기본 대상을 유지합니다.

생성 메뉴는 빠른 ZIP, 7z, 확인 후 생성과 여러 항목 선택 시 항목별 ZIP을 제공합니다. 일반 파일 하나는 `a.txt.zip`처럼 전체 이름을 유지하고 폴더는 `foo.zip`을 사용하며 같은 디렉터리의 통합 선택은 해당 디렉터리 이름을 사용합니다. 서로 다른 디렉터리의 통합 선택은 대상 확인을 위해 독립 생성 창을 엽니다. 빠른 생성은 암호화나 분할 없이 보통 수준을 사용하며 대상 이름 충돌은 기존 충돌 확인으로 처리합니다.

압축 풀기 작업은 모든 선택 항목이 지원 확장자 또는 분할 파일 이름에 따라 압축 파일 후보일 때 나타납니다. 메뉴는 파일 내용을 검사하지 않습니다. 실제로 열 때 Rust가 전체 분할 그룹을 찾고 내용, 원본과 형식의 기능을 검증합니다. 동일한 완전한 원본 그룹은 압축 풀기 배치에서 한 번 실행됩니다. 프로세스 내부의 불투명한 원본 그룹 표식은 파일 ID를 보유하지만 쓰기 권한은 아닙니다.

- 현재 디렉터리: 각 압축 파일을 각각의 상위 디렉터리에 직접 풉니다.
- 스마트 디렉터리: 완전히 검증된 출력 그래프에 암묵적 최상위 디렉터리를 포함해 최상위 디렉터리가 하나뿐일 때만 바깥 폴더를 추가하지 않습니다. 루트 파일이나 여러 최상위 항목은 압축 파일 이름의 폴더가 필요합니다. 내부 디렉터리는 제거하거나 이름을 바꾸지 않습니다.
- 압축 파일별 디렉터리: 항상 압축 파일 이름의 바깥 폴더를 추가합니다. 보유한 대상 권한을 사용해 독점적으로 예약하며 기존 파일, 디렉터리와 링크는 재사용하지 않습니다. `name (2)`와 같은 새 번호 이름을 최대 만 번 시도해 선택합니다.
- 선택한 디렉터리: 독립 압축 풀기 창에서 공통 대상을 선택합니다. 기본값은 압축 파일별 디렉터리이며 스마트 또는 직접 병합도 선택할 수 있습니다.

디렉터리 이름은 [안전한 압축 풀기](zip-safe-extraction.md)의 이식 가능한 이름과 `.app` 접미사 규칙을 따릅니다. 스마트 판정은 출력을 승인하지 않습니다. 각 작업은 대상, 원본, CRC 또는 인증, 충돌과 게시 권한을 다시 검증해야 합니다. 개별 압축 파일 실패는 기존의 전체 파일 중단 정책을 따르며 배치 조정자는 다음 파일로 진행합니다.

## 프로세스, 요청과 창

비공개 데스크톱 진입점은 `--shell-request <request.json>`이며 독립 CLI의 스크립트 인터페이스가 아닙니다. 네이티브 확장은 선택 매니페스트만 만들고 데스크톱 진입점을 실행하며 Qt나 형식 라이브러리를 로드하지 않습니다. 매니페스트는 시스템 임시 루트 아래 독점 생성한 비공개 `xdzip-shell-<무작위 16진수 32자리>` 디렉터리에 고정 파일 이름 `request.json`으로 저장합니다. Windows는 쓰기 전에 현재 사용자와 SYSTEM을 위한 보호된 DACL을 설정하며 POSIX는 0700 디렉터리와 0600 파일을 사용합니다. 데스크톱은 링크를 따르지 않는 공유 Rust 기능과 디렉터리 권한으로 루트, 소유자와 권한을 검증하고 최대 256 KiB를 읽으며 링크, 상대 경로, 잘못된 Unicode, 알 수 없는 작업과 128개가 넘는 선택을 거부합니다.

요청에는 스키마 1, UUID, 작업과 절대 경로가 들어 있습니다. 선택적 불리언 `archive_candidates`는 파일 관리자가 이미 알고 있는 MIME 또는 UTI 힌트만 전달합니다. 공유 확장자 및 분할 규칙과 함께 메뉴 표시 여부를 결정하지만 I/O를 승인하거나 Rust의 내용 검증을 우회하지 않습니다. Windows는 확장의 등록된 Content Type을, Nautilus는 FileInfo MIME을, macOS 도우미는 URL Content Type을 읽습니다. 파일 관리자에서 압축 파일을 구문 분석하지 않습니다. 단일 인스턴스 프로토콜은 기존 열기 및 CLI 작업을 유지하고 구조화된 `shell_action`을 추가합니다. 승인과 실행 성공은 별도로 판단합니다. 앱은 승인된 요청 ID를 최대 128개 유지합니다. ID와 내용이 같으면 한 번만 승인하고 ID는 같지만 내용이 다르면 거부합니다. 승인 후 고정 파일과 빈 디렉터리만 제거하며 외부 입력을 재귀적으로 정리하지 않습니다.

셸 콜드 시작은 숨겨진 메인 창이 아닌 `ShellHost`만 만듭니다. 파일을 일반적으로 열거나 메인 창을 명시적으로 표시하면 필요할 때 브라우저 창을 만듭니다. 기존 인스턴스가 셸 작업을 받아도 브라우저 탭을 바꾸거나 숨겨진 메인 창을 복원하지 않습니다. 작업 세션은 기존의 제한된 세션 슬롯을 사용하며 배치는 압축 파일마다 브라우저 페이지를 만들지 않고 컨트롤러를 순서대로 재사용합니다.

`OperationTasks`는 브라우저와 독립 진입점에서 진행, 결과, 암호와 충돌 창을 공유합니다. 최상위 `OperationWindow`는 소유자가 없을 수 있습니다. 소유자가 있으면 호출 창을 따르고 없으면 선택 화면 안으로 제한합니다. 모달 요청은 실제 작업 창에 속하며 종료 확인은 `OperationConfirmationWindow`를 재사용합니다. 레이아웃, 공유 컨트롤, 이중 언어 및 접근성 요구 사항은 [시각적 작업 흐름](../visual/design-workflow.md)을 따릅니다.

macOS의 단일 인스턴스 ID는 현재 사용자와 Security 프레임워크의 실제 로그인 세션 ID를 사용합니다. 조회가 실패하면 도우미에 없을 수 있는 환경 변수에 의존하지 않고 선출을 거부합니다. 따라서 일반 시작, Finder relay와 서비스가 같은 로그인 세션 인스턴스에 도달합니다. [SessionGetInfo](https://developer.apple.com/documentation/security/sessions)를 참조하세요.

셸 생성과 압축 풀기는 `TaskWindow`의 진행 및 결과 보기를 재사용합니다. 배치는 실제 상태와 오류를 같은 레이아웃에 표시합니다. 작업 접수증 없이 제출 전 실패하면 결과 보기만 만들고 가짜 작업은 만들지 않습니다. 셸 창은 현재 화면의 사용 가능한 영역 가운데에 놓이며 요청은 실제 호출 창을 유지합니다. Windows 클래식 진입점은 시스템이 지원하는 `Position=Top`을 요청하여 Explorer가 동적 메뉴 조회 후 ‘연결 프로그램’을 추가해도 그 앞에 표시됩니다. 루트와 열거된 작업에는 앱, 형식과 시스템 폴더 아이콘을 사용하며 네이티브 크기는 Windows가 정합니다.

## 배치 완료와 종료

각 배치는 실제 성공, 실패, 취소, 미실행 항목과 분할 그룹 중복 제거를 기록합니다. 개별 실패는 나머지 항목을 중단하지 않습니다. 취소는 후속 항목을 중단하고 준비 중 또는 실행 중인 작업에 기존 취소 의도를 보냅니다. 이미 확정된 출력은 남으며 배치 전체의 롤백을 보장하지 않습니다. 준비, 암호 대기, 충돌, 취소와 정리는 전역 활동 및 종료 장벽에 포함됩니다.

독립 생성 창이 아직 작업 접수증을 받지 않았다면 제출 거부 시 입력, 매개변수와 오류를 보존하여 수정하고 재시도할 수 있습니다. 작업 종결 상태를 만들거나 배치 인덱스를 소비하지 않습니다. 빠른 작업에는 설정 창이 없으며 제출 실패를 기록하고 배치를 계속합니다.

성공한 셸 생성은 앱 내 열기 의도를 제출하지 않으며 압축 풀기의 ‘완료 후 폴더 열기’는 기본적으로 꺼져 있습니다. 성공한 독립 결과는 사용자가 대상을 열 수 있도록 유지됩니다. 완료가 포커스를 빼앗지 않습니다. 의도적으로 닫은 창은 작업 진입점에서 배치 결과를 다시 열 수 있습니다. 트레이를 끄거나 호스트를 잃으면 닫힌 결과는 숨겨진 상태를 유지합니다. 보이거나 최소화된 메인 창은 작업 진입점을 제공하며, 메인 창이 없으면 숨겨진 활성 작업만 복원합니다. 트레이 또는 접근 가능한 메인 창이 있으면 작업을 계속하면서 진행 창을 닫을 수 있습니다. 둘 다 없으면 먼저 대기 또는 취소를 선택해야 합니다. 접근 가능한 창, 트레이와 활성 작업이 모두 없으면 종료 전에 모든 Rust 연결이 끝날 때까지 기다립니다. 열린 설정 창은 사용자가 닫을 때까지 사용할 수 있습니다.

## 설치와 호환성

설치된 버전은 기본적으로 통합을 켜며 일반 설정에서 끌 수 있습니다. 등록은 소유한 항목만 관리하고 기본 파일 연결을 바꾸지 않습니다. 포터블 및 개발용 복사본은 자동으로 등록되지 않습니다. 명시적 데스크톱 진입점 `--register-shell-integration`과 `--remove-shell-integration`은 메인 창을 표시하지 않고 제어된 등록과 제거를 수행합니다.

설치 프로그램은 단일 인수의 정확한 동기화 또는 제거 명령을 사용하며 설치 트랜잭션 시작 잠금을 해제하기 전에 소유한 통합 메타데이터만 갱신합니다. 일반 파일, 셸 작업과 메인 창 시작에는 여전히 런타임 승인이 필요합니다. Windows 설치 ID는 현재 사용자의 등록된 제품 ID, 설치 위치와 파일 매니페스트를 확인합니다. 포터블 디렉터리는 배포 매니페스트가 있더라도 자동 등록되지 않습니다.

전달 전 데스크톱 프로토콜 1을 확인하여 롤백 후에도 로드된 확장이 이전 앱에 요청을 넘기지 못하게 합니다. Windows는 GUI 실행 파일 버전 리소스 `XdzipShellProtocol`을 읽고 소유한 `Applications/xdzip.exe` 등록 명령이 같은 실제 파일을 가리키는지 확인합니다. 연결 실행기는 프로토콜 기능을 주장하지 않습니다. 이전 버전별 구조로 롤백한 뒤 루트에 남은 새 실행 파일은 더 이상 셸 대상이 아니며 기본 파일 연결은 읽거나 바꾸지 않습니다. macOS 도우미는 캐시된 NSBundle 상태 대신 대상 Info.plist의 제품 ID, 프로토콜과 단일 실행 파일 이름을 매번 다시 읽습니다. Ubuntu 패키지는 `/usr/share/xdzip/shell-protocol`을 소유하며 이전 패키지로 롤백하거나 제거하면 표식이 삭제됩니다. 대상이 없거나 알 수 없거나 호환되지 않거나 더 이상 등록되지 않았으면 실행을 거부합니다. 기능 표식은 전달 호환성만 관리하며 요청, Rust 내용 또는 대상 검증을 대신하지 않습니다.

Windows는 자체 CLSID와 클래식 명령을 HKCU에 저장합니다. 명령은 별도 클래스 ID를 사용해 Explorer에 캐시된 이전 클래스 팩터리가 업데이트 중 명령을 억제하지 못하게 합니다. 통합을 켜거나 끄면 일치하는 이전 메뉴 처리기와 소유한 이전 클래스만 제거합니다. 이전 처리기를 복원한 과거 롤백 후에는 남아 있는 새 명령이 중복을 피하도록 자신을 숨깁니다. 설치 프로그램은 롤백을 거쳐도 명령과 클래스의 제거 소유 기록을 유지합니다. 런타임 디렉터리에는 콘텐츠 다이제스트로 이름 붙인 확장 DLL과 검증 매니페스트가 있어 업데이트 중 Explorer가 로드한 같은 이름의 DLL을 덮어쓰지 않습니다. 이전 파일 정리는 Explorer를 강제 종료하지 않고 설치 프로그램의 소유 및 사용 중 정책을 따릅니다. 설치된 macOS 앱은 첫 일반 시작 시 사용자의 Library/Services에 자체 서비스를 설치합니다. 도우미는 선택을 수집해 전달만 하며 통합을 끌 때 검증된 자체 파일만 제거하고 추가 내용, 링크 또는 소유 불일치는 보존하고 보고합니다. 서비스의 표시와 활성화는 시스템이 관리합니다.

Ubuntu 네이티브 확장은 설치 패키지가 Nautilus 4.0 확장 디렉터리에 등록하며 같은 사용자의 설정을 읽습니다. 실행 중인 파일 관리자는 이전 모듈을 유지할 수 있으므로 자동으로 종료하지 않고 파일 관리자를 다시 열어 업데이트합니다. 독립 런타임 디렉터리는 시스템 확장 디렉터리에 자동으로 쓰지 않습니다. 통합 구성 요소를 명시적으로 설치하세요.

Ubuntu 24.04 amd64의 XDZip strict Snap에서는 별도의 `xdzip-nautilus-snap` DEB 패키지가 파일 앱의 확장을 등록합니다. 메뉴 프로토콜 1을 지원하는 Snap과 함께 설치한 뒤 파일 앱을 다시 엽니다. 확장은 크기가 제한된 선택 정보를 표준 입력으로 전달합니다. 런처는 Snap 내부에 비공개 요청 파일을 만들고 기존 검증과 작업 창을 사용합니다. 보조 패키지와 네이티브 DEB는 같은 확장 경로를 사용하므로 함께 설치할 수 없습니다.
