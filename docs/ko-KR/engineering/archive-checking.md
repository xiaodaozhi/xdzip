# 압축 파일 무결성 검사

[English](../../engineering/archive-checking.md) | [简体中文](../../zh-CN/engineering/archive-checking.md) | [繁體中文](../../zh-TW/engineering/archive-checking.md) | [日本語](../../ja-JP/engineering/archive-checking.md) | 한국어 | [Français](../../fr-FR/engineering/archive-checking.md) | [Deutsch](../../de-DE/engineering/archive-checking.md) | [Español](../../es-ES/engineering/archive-checking.md) | [Português (Brasil)](../../pt-BR/engineering/archive-checking.md) | [Русский](../../ru-RU/engineering/archive-checking.md)

도구 모음의 ‘Test’ 동작은 조건에 맞는 현재 압축 파일을 실제 백그라운드 작업으로 한 번 검사합니다. 현재 디렉터리, 검색 또는 선택과 관계없이 중복 이름, 디렉터리와 빈 파일을 포함한 모든 물리 레코드를 다룹니다. 디스크 인덱스를 사용하는 압축 파일의 전체 검사는 현재 지원하지 않습니다. [대용량 압축 파일 인덱싱](large-index.md)을 참고하세요. 검사는 고정된 입력 원본과 메타데이터만 보유하며 대상 권한을 얻지 않고 준비 또는 출력 파일을 만들지 않으며 추출 경로 매핑이나 링크 게시를 사용하지 않습니다.

UU/UUE와 XXE는 빈 파일과 중복 이름을 포함한 텍스트 봉투의 모든 물리 멤버를 검사하고 개수가 있는 줄 또는 허용된 Base64 패딩과 정확한 종료 마커를 검증합니다. 체크섬이나 인증이 없으므로 유효한 알파벳 문자를 바꾸면 실패 없이 바이트가 달라질 수 있습니다. 헤더의 경로와 모드는 출력이나 실행 권한을 부여하지 않습니다. [텍스트 봉투 계약](text-envelopes.md)을 참고하세요.

Z와 TAR.Z는 Unix compress LZW 코드, 사전 경계, CLEAR/너비 정렬과 물리 EOF를 검증하며 TAR.Z는 전체 TAR 레코드와 꼬리도 검사합니다. 콘텐츠 체크섬, 디코딩 크기 필드나 인증이 없으므로 구조 검사가 성공해도 콘텐츠를 보존하는 모든 치환이나 유효 코드 꼬리를 감지할 수 없습니다. 같은 제어된 원본과 작업 제한이 적용됩니다. [compress 계약](compress-streams.md)을 참고하세요.

<a name="xdzip-formats-and-results"></a>

## 형식과 결과

일반 GZIP, BZip2, LZMA Alone과 Lzip v1은 같은 제한된 폐기 싱크로 디코딩해 정확한 스트림 종료와 관찰된 크기를 검증합니다. GZIP은 각 멤버의 CRC/ISIZE, BZip2는 블록 및 결합 CRC, Lzip은 CRC, 데이터 크기와 멤버 크기를 검사합니다. LZMA Alone에는 콘텐츠 체크섬이 없으므로 성공은 구조와 읽기 가능성을 확인합니다. 필터링된 TAR 조합은 압축 EOF를 포함한 전체 컨테이너를 다시 스캔하며 페이로드를 두 번째로 처리하지 않습니다. 검사 강도는 [내장 레지스트리](format-registry.md), 제한과 프로필은 [스트림 계약](single-file-streams.md)을 따릅니다.

ZIP은 지원되는 번호 및 PKZIP 볼륨을 포함해 조건에 맞는 ZIP/ZIP64를 검사합니다. 디코더는 제한된 폐기 싱크로 지원되는 멤버 페이로드를 검사하고 중앙 디렉터리와 로컬 헤더, 디스크립터, 정확한 스트림 종료, 선언된 크기, CRC와 승인된 AES-256 인증을 검증합니다. 암호화되지 않은 Deflate64, BZip2, LZMA, XZ 항목은 아래의 추가 방식 제한도 따릅니다. 안전한 이름의 ZIP 심볼릭 링크는 대상을 해석하거나 링크를 만들지 않고 페이로드를 검사합니다. 알 수 없는 방식, 미지원 암호화, 안전하지 않은 이름과 그 밖의 미승인 레코드는 검사를 실패시킵니다.

7z와 RAR은 격리된 작업 프로세스의 독립 Rust 백엔드를 사용하고 각 물리 항목을 같은 제한된 폐기 싱크로 디코딩해 종료, 선언 크기와 컨테이너가 실제 제공하는 검사를 검증합니다. 현재 선택에 도달하려고 솔리드 블록에서 디코딩한 다른 데이터는 작업량으로만 계산하며 현재 파일의 검증 수를 늘리지 않습니다. 디렉터리, 빈 파일과 암호화 항목을 건너뛰고 전체 성공을 보고할 수 없습니다. 이전 RAR, RAR5와 새 RAR 7 알고리즘은 내용이 알려진 독립 샘플로 승인하며 같은 매직만으로 버전 호환성을 입증하지 않습니다.

CAB는 격리 작업 프로세스에서 자체 Rust 컨테이너와 공유 알고리즘을 사용해 볼륨 집합, 실제 디코딩 크기와 완전한 데이터 프레임이 제공하는 검사를 검증합니다. ISO/UDF는 디스크립터, 디렉터리, 데이터 범위와 선언 크기를 검사하고 지원되는 모든 일반 파일을 실제로 읽습니다. 일반적으로 파일별 콘텐츠 체크섬이 없어 구조를 유지하는 임의의 변조를 감지할 수 없습니다. 이미지 링크, 장치와 다른 미지원 레코드를 건너뛰고 전체 성공을 주장할 수 없습니다. 하이브리드 이미지는 고정된 UDF 네임스페이스를 사용하고 실패 후 ISO로 대체하지 않습니다.

TAR와 TAR.GZ는 검사 작업 안에서 전체 스트림을 순차적으로 다시 스캔해 고정된 물리 레코드 메타데이터와 대조하고 헤더 체크섬, 길이, 두 종료 블록과 꼬리를 검사합니다. TAR.GZ는 EOF까지 진행해 GZIP CRC/ISIZE를 검증하며 전체 스캔 후 콘텐츠를 두 번째로 모두 추출하지 않습니다. TAR에는 파일 콘텐츠 체크섬이 없어 형식 구조와 읽기 가능성만 확인하며 구조를 유지하는 임의의 콘텐츠 변조는 확인하지 못합니다. TAR 링크, 특수 객체와 희소 파일은 계속 미지원입니다. 이 기능은 원본 신뢰를 입증하거나 악성코드를 검사하지 않습니다.

Compound File (MSI)은 콘텐츠 체크섬 없이 컨테이너 구조와 원시 스트림의 읽기 가능성을 검사합니다. NSIS는 정적 설치 프로그램 메타데이터만 제공합니다. 제한은 [MSI 및 NSIS 형식 지원](wim-msi-installer-format-sources.md)을 참고하세요.

첫 구조, 페이로드, 원본, 자원 또는 미지원 항목 오류가 작업을 끝냅니다. 결과는 성공, 실패와 취소를 구분하고 검증 및 미검사 파일 수를 표시하며 실패 항목과 안정적 오류 코드를 보존합니다. 모든 물리 레코드를 검사하지만 `files`/`verified_files`는 빈 파일을 포함한 디렉터리가 아닌 파일만 셉니다. 디렉터리와 디렉터리만 있는 압축 파일도 성공 전에 구조 검증을 완료해야 합니다. 검사 중이나 그 전에 읽기가 완료되어도 전체 압축 파일이 통과한 것은 아닙니다.

<a name="xdzip-scheduling-source-and-resources"></a>

## 스케줄링, 원본과 자원

`Check { session }`은 `Source::fork()`로 원본과 형식, 메타데이터, 원래 세션 식별 정보를 고정하고 생성 및 추출과 같은 제한된 무거운 작업 큐와 앱 수준 순차 승인에 들어갑니다. 시작 시, 읽은 뒤, 성공 종료 상태 전에 원본 핸들과 각 볼륨 경로의 식별 정보, 크기와 시각을 다시 검사합니다. 원본 변경은 `source_changed`를 반환하고 해당 원래 세션만 무효화합니다. 이는 최선의 감지이며 입력 콘텐츠의 원자적 스냅샷이 아니므로 식별 정보와 타임스탬프를 유지하는 동시 제자리 변경의 감지를 보장하지 않습니다.

실제 디코딩은 파일당 8 GiB, 작업당 20 GiB로 제한하며 잘못된 암호 재시도는 누적 작업량을 초기화하지 않습니다. ZIP은 위치 메타데이터용 별도 64 MiB 예산과 실제 입력 읽기용 공유 20 GiB 예산을 유지합니다. TAR/GZIP은 기존 전체 스트림 읽기 제한 24 GiB를 유지합니다. 7z/RAR/CAB/ISO/UDF는 추가로 네이티브 작업 프로세스 메모리 1 GiB를 제한합니다. 입력 읽기와 솔리드 건너뛰기도 제한되며 초과는 자원 실패이지 무결성 통과가 아닙니다. 작업/이벤트 수, 스냅샷 세부 정보와 유지 메모리는 기존 큐 제한을 따릅니다. 성공 종료 상태는 쓰기, 확정, 저장 디렉터리 또는 출력 경로 수를 설정하지 않습니다.

작업 종류는 `kind=check`로 Qt에 명시적으로 전달됩니다. `read_bytes`는 헤더와 재시도를 포함한 실제 원본 읽기, `decoded_bytes`는 실제 디코딩 작업이며 `verified_bytes`/`verified_files`는 필요한 검사를 완료한 뒤에만 증가합니다. TAR/GZIP 전체 스캔 중 파일별 백분율을 만들어 내지 않으며 실제 읽은 바이트와 속도는 표시합니다. 전체 스트림 파일은 성공 후에만 검증된 것으로 셉니다.

AES 암호는 [암호 프로토콜](password-extraction.md)을 재사용합니다. 독립 제어 슬롯, 일회용 프롬프트 식별 정보, 작업 로컬 캐시, 항목당 최대 열 번의 잘못된 검증값 응답, 인증 손상 시 즉시 실패와 비밀 정보 제로화가 포함됩니다. 취소와 종료는 일반 명령 큐 용량과 관계없이 암호 대기를 깨웁니다. 탐색 페이지나 진행 창을 닫아도 승인된 작업은 취소되지 않으며 전역 작업 진입점에서 결과를 다시 엽니다. 명시적 종료는 여전히 취소와 비동기 스레드 종료 대기를 기다립니다.

<a name="xdzip-verification-boundaries"></a>

## 검증 경계

핵심 회귀는 지원 형식, 빈 파일, 디렉터리, 중복 이름, ZIP 링크 페이로드, 암호 재시도/취소, 손상된 페이로드, 원본 변경, 실제 수와 출력 없음을 다룹니다. 브리지와 Qt는 도구 모음에서 백그라운드 작업과 결과까지의 실제 흐름을 검사하며 암호 라우팅, 과거 작업, 세션 간 승인과 종료는 별도로 검사합니다. 두 언어 여러 글꼴 크기, 밝은/어두운 테마와 네이티브 데스크톱 시각 검수는 issue에 별도 기록합니다. 생성된 증거는 build/ 또는 CI 산출물에만 둡니다.

오래된 암호화 RAR 항목에는 잘못된 암호와 손상된 콘텐츠를 확실하게 구별하는 검증자가 없습니다. 암호화 항목을 각각 디코딩하기 전에 별도로 암호를 요청하며 다른 비밀을 사용할 수 있는 다음 항목에 이전 항목의 암호를 자동 적용하지 않습니다. RAR5와 다른 지원 형식은 작업 로컬 재사용을 계속합니다. 신뢰할 수 있는 암호 검증자가 없는 암호화 디코딩 또는 암호화 헤더 무결성 실패는 `password_or_integrity`를 보고해 잘못된 암호와 손상의 모호성을 유지합니다. 평문 헤더 검사, 원본 변경, 취소, 제한과 출력 I/O를 암호 문제로 잘못 분류하지 않습니다.

비압축 크기가 알려지지 않은 압축 파일도 탐색할 수 있습니다. 전체 검사는 합계를 알 수 없음으로 표시하고 페이로드를 열거나 암호를 요청하기 전에 `unsupported_feature`로 실패하며 실제 검증 및 디코딩 수를 유지합니다. 알 수 없는 크기를 빈 파일로 검사하지 않고 내부 센티널을 진행률 분모로 사용하지 않습니다.

XZ와 TAR.XZ는 `format_declared_checks`를 사용합니다. 선언된 CRC32/CRC64/SHA-256과 구조 필드를 모두 검증해야 하며 None을 선언한 스트림에는 콘텐츠 체크섬이 없습니다. 인터페이스는 모든 입력에 체크섬이 있다고 약속하지 않고 이 차이를 설명합니다. 새 암호화되지 않은 ZIP 방식 9/12/14/95도 정확한 디코딩 크기와 외부 ZIP CRC가 필요하며 LZMA 데이터 디스크립터에는 EOS가 필요합니다. 알 수 없는 방식은 보이지만 검증된 콘텐츠로 셀 수 없습니다.

AES Crypt는 `format_declared_checks`와 보유한 열기 암호를 사용합니다. 전체 암호문 HMAC은 메타데이터 승인 전과 실제 작업 디코딩 후에 통과해야 합니다. 버전 0–2는 끝 길이 나머지를 인증하지 않으며 확장도 인증되지 않습니다. 성공은 [AES Crypt 계약](aescrypt-envelopes.md)에 명시된 형식 선언 검사로 제한됩니다.

Brotli와 TAR.BR은 `structure_and_readability`를 사용합니다. 전체 스트림 종료, 선언된 메타블록 크기와 승인된 모든 사전/이력 변환이 통과해야 하지만 Brotli에는 콘텐츠 체크섬이 없습니다. [Brotli 계약](brotli-streams.md)을 참고하세요.

LHA/LZH는 `format_declared_checks`를 사용합니다. 지원되는 모든 일반 파일을 실제로 디코딩하고 정확한 길이와 존재하는 모든 헤더/페이로드 CRC-16을 검증합니다. 오래된 레벨 0 멤버는 CRC를 생략할 수 있으며 이 경우 구조, 크기, 읽기 가능성만 검사합니다. LH2는 CRC에 연결된 유한 변형 승인이 필요합니다. 알 수 없는 방식, 의심스러운 이름, 링크 또는 특수 객체는 전체 성공을 막습니다. [LHA 계약](lha-containers.md)을 참고하세요.

PMA는 `format_declared_checks`를 사용하며 승인된 PM0/PM1/PM2 멤버를 완전히 디코딩하고 정확한 크기와 존재하는 모든 페이로드 CRC-16을 검증합니다. CRC 없는 멤버는 구조, 크기와 읽기 가능성만 확인합니다. 알 수 없는 방식과 다른 미지원 항목은 전체 성공을 막습니다. CP/M 채우기는 압축된 멤버 범위 밖의 물리 컨테이너 구조로 검증합니다. [PMA 계약](pma-streams.md)을 참고하세요.

ARJ는 `supported_content`를 사용합니다. 완전한 메타데이터 승인은 주, 파일 및 확장 헤더 CRC-32를 검증합니다. 검사는 승인된 모든 일반 멤버를 Store 또는 방식 1–4로 완전히 디코딩하고 정확한 크기와 필수 페이로드 CRC-32를 검증하며 CRC가 적용된 이전 텍스트 바이트를 줄바꿈 변환 없이 보존합니다. 알 수 없거나 미지원 레코드는 전체 성공을 막습니다. [ARJ 계약](arj-streams.md)을 참고하세요.

ARC는 `supported_content`를 사용합니다. 완전한 물리 승인, 이전/새 Store 또는 방식 3–9를 통한 실제 디코딩, 정확한 디코딩 크기와 필수 CRC-16/IBM을 검증합니다. 알 수 없는 방식, 의심스러운 이름이나 미지원 프로필을 건너뛰고 전체 성공을 주장할 수 없습니다. 헤더 SHA 결합은 스냅샷 검사이지 인증이 아닙니다. [ARC 계약](arc-streams.md)을 참고하세요.

BH는 `supported_content`를 사용합니다. 완전한 `BH 05 07` 멤버 구조, 방식 8 원시 Deflate 종료, 정확한 디코딩 크기와 필수 CRC-32를 검증합니다. 알 수 없는 방식, 잘못된 상수, 의심스러운 이름과 미지원 프로필은 보이지만 전체 성공을 막습니다. [BH 계약](bh-containers.md)을 참고하세요.

ALZ는 `supported_content`를 사용합니다. 완전한 단일 볼륨 구조, Store 또는 원시 Deflate 페이로드 종료, 정확한 디코딩 크기와 필수 CRC-32를 검증합니다. 암호화, 디스크립터, 수정된 BZip2, 분할과 알 수 없는 방식의 레코드는 보이지만 전체 성공을 막습니다. [ACE, ALZ, EGG 소스 기준](ace-alz-egg-format-sources.md)을 참고하세요.

EGG는 `supported_content`를 사용합니다. 암호화되지 않고 솔리드가 아닌 완전한 단일 볼륨 구조, Store 또는 원시 Deflate 블록 종료, 정확한 블록 크기와 필수 CRC-32를 검증합니다. AZO, BZip2, LZMA, 암호화, 분할, 솔리드와 알 수 없는 방식은 보이지만 전체 성공을 막습니다. [ACE, ALZ, EGG 소스 기준](ace-alz-egg-format-sources.md)을 참고하세요.
