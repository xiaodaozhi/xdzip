# 압축 파일 암호와 암호화된 디렉터리 열기

[English](../../engineering/password-extraction.md) | [简体中文](../../zh-CN/engineering/password-extraction.md) | [繁體中文](../../zh-TW/engineering/password-extraction.md) | [日本語](../../ja-JP/engineering/password-extraction.md) | 한국어 | [Français](../../fr-FR/engineering/password-extraction.md) | [Deutsch](../../de-DE/engineering/password-extraction.md) | [Español](../../es-ES/engineering/password-extraction.md) | [Português (Brasil)](../../pt-BR/engineering/password-extraction.md) | [Русский](../../ru-RU/engineering/password-extraction.md)

이 계약은 [안전한 추출](zip-safe-extraction.md)을 보완하며 암호, 인증과 작업 상호작용을 정의합니다. 형식과 파일 보안 로직은 Qt와 독립적으로 유지되며 암호 창은 사용자 의도만 제출합니다. 실제 진행과 플랫폼 검증은 [issue #11](https://github.com/xiaodaozhi/xdzip/issues/11)을 참고하세요. 실행 보고서는 여기에 두지 않습니다.

## 기능과 형식 경계

ZIP/ZIP64 WinZip AES-256 AE-1과 AE-2는 실제 압축 방식이 Store 또는 Deflate일 때 지원됩니다. 평문, 암호화 및 혼합 항목을 선택할 수 있으며 빈 파일도 인증을 검증해야 합니다. 파일마다 암호가 다를 수 있습니다. AES-128/192, 기존 ZipCrypto와 다른 암호화는 계속 미지원입니다. 지원되는 분할 볼륨은 [통합 논리 입력](archive-opening.md)을 사용하며 암호 및 인증 규칙은 변하지 않습니다. 파일 이름, 디렉터리 구조와 일반 ZIP 메타데이터는 계속 보이며 암호 기능은 이를 암호화하거나 인증하지 않습니다.

AES 필드는 [WinZip 형식 사양](https://www.winzip.com/en/support/aes-encryption/)을 따릅니다. 표시 방식 99, 설정된 암호화 플래그, AE 공급자, 알려진 버전, 256비트 강도와 지원되는 실제 방식을 가진 AES extra 하나입니다. 현재 정의된 데이터 일곱 바이트만 허용하며 알 수 없는 확장은 계속 거부합니다. AE-1은 디코딩된 콘텐츠 CRC도 검증하고 AE-2의 저장 CRC는 0이어야 합니다. 중앙 디렉터리, 로컬 헤더와 데이터 디스크립터 선언은 독립적으로 검사하며 인증 코드가 구조 검증을 대체하지 않습니다.

어댑터는 먼저 고정된 스냅샷의 물리 레코드 식별 정보, 원시 이름, 유형, 크기, 방식, 암호화 플래그와 암호 지원 표시를 비교합니다. 이후 이 작업의 전체 플래그와 AES 프로필을 기록하고 로컬 헤더, 중앙 디렉터리, 디스크립터와 페이로드 범위의 일관성을 검증합니다. 초기 스냅샷은 전체 플래그와 프로필을 보유하지 않습니다. 원본 변경은 여전히 식별 정보/버전의 최선 감지에 의존하며 입력 콘텐츠의 원자적 스냅샷이 아닙니다. 로컬 또는 중앙 헤더의 ZIP64 크기 센티널이 디스크립터 너비를 결정합니다. 프로젝트는 [승인된 암호화 기본 요소](../engineering/dependencies.md)를 사용해 ZIP 컨테이너와 AES 래핑을 독립 구현하며 형식 라이브러리의 추출 함수를 호출하지 않습니다.

복호화기는 한 항목의 검증된 암호문 범위만 읽고 출력 경로를 받지 않습니다. Store 또는 공유 원시 Deflate는 정확한 압축 바이트 소비, 디코딩 크기와 AE-1 CRC를 검증합니다. 암호문을 모두 소비한 뒤 HMAC 인증 코드를 검증하며 모두 성공해야 성공을 반환합니다. 빈 파일도 인증을 완료합니다. 암호문과 디코딩 데이터는 제한된 버퍼를 사용해 파일 전체를 메모리에 쌓지 않으며 제3자 ZIP 라이브러리용 개인 압축 파일 뷰를 만들지 않습니다.

<a name="xdzip-7z-rar-and-encrypted-directories"></a>

## 7z, RAR과 암호화된 디렉터리

7z와 RAR은 같은 호스트 디코딩 싱크, 안전한 출력, 실제 할당량과 오류 분류를 유지합니다. 현재 제품 경로와 자체 후보 경계는 [격리 백엔드 계약](native-codecs.md)과 [독립 구현 계약](independent-rust-codecs.md)을 참고하세요. 7z AES-CBC에 독립 암호 검증자가 없으면 인식된 암호화 메타데이터의 디코딩/파싱 실패 또는 암호화 콘텐츠의 크기/스트림 종료/CRC 실패에 `password_or_integrity`를 사용합니다. 이는 암호 불일치 또는 암호화 데이터 손상을 뜻하며 `wrong_password`라고 안다고 가장하지 않습니다. 외부 평문 헤더 검증 실패는 컨테이너 손상으로 유지합니다. 원본 I/O, 원본 변경, 자원 제한, 취소, 미지원 기능과 출력 실패는 암호 오류로 재분류하지 않습니다. RAR은 과거와 현재 암호 경계를 유지하며 이전/현재 형식, 헤더 암호화, 솔리드 압축 파일과 분할 볼륨 조합을 각각 승인합니다.

암호화된 파일 이름이나 디렉터리는 메타데이터 스캔 전에 비밀이 필요합니다. OpenWithPassword는 이를 담는 유일한 열기 명령입니다. 암호 컨테이너는 큐에 넣기 전에 제한되고 해제 시 제로화되며 이벤트에는 비밀이 없습니다. 완전한 스캔 성공 전에는 부분적으로 탐색 가능한 인덱스를 게시하지 않습니다. 성공하면 세션이 제로화되는 컨테이너를 유지하고 승인된 작업은 페이지를 닫은 뒤에도 계속하도록 개인 사본을 복제할 수 있습니다. 사본은 스냅샷, 로그나 설정에 들어가지 않습니다. 작업 디코더가 다시 열릴 때 같은 암호를 사용하며 이후 항목 암호는 별도 프롬프트 제어 응답을 계속 사용합니다.

7z 생성은 콘텐츠 암호와 파일 이름 암호화를 함께 지원합니다. 파일 이름 암호화에는 비어 있지 않은 생성 암호가 필요하며 7z에서만 사용할 수 있습니다. ZIP은 콘텐츠만 암호화하고 TAR/TAR.GZ는 암호화 인자를 거부합니다. 암호화된 7z와 모든 RAR은 수정을 거부합니다.

## 비밀과 제어 프로토콜

`extraction::Password`는 생성 암호와 분리됩니다. 추출은 입력한 그대로의 UTF-8을 최대 1,024바이트까지 허용하며 빈 값, 공백과 제어 문자도 포함합니다. 공백을 잘라내지 않고 생성의 1–128바이트 규칙도 적용하지 않습니다. 현재 텍스트 UI는 UTF-8이 아닌 원시 암호를 표현할 수 없습니다. 입력 할당 용량도 제한됩니다. Rust 소유 컨테이너는 Debug 출력을 항상 가리고 거부, 교체, 취소 또는 범위 종료 시 제로화합니다.

`Client::respond_password(task, prompt, Password)`는 일반 명령 큐가 아닌 독립 제어 슬롯으로 비밀을 전달합니다. 각 프롬프트는 작업 로컬 일회용 ID를 사용해 이름 충돌과 암호 프롬프트를 구분합니다. 오래된 ID, 유형이 다른 응답, 중복 및 종료 상태나 취소 후 응답은 거부합니다. 스냅샷에는 `PasswordPrompt { id, name, retry }`와 `waiting_password`만 있고 암호나 다이제스트는 없습니다. GUI 메일박스 바이트 제한에는 프롬프트 이름도 포함됩니다.

처음 암호가 필요하면 작업은 명시적 응답을 기다립니다. 작업 안에서 성공적으로 사용한 암호는 이후 암호화 항목에 재사용할 수 있습니다. 검증값 불일치 또는 명시적 `password_or_integrity`는 이전 캐시를 지우고 다시 요청하며 물리 항목당 최대 열 번 실패할 수 있습니다. 한도에서는 실제 종료 오류 분류를 유지하며 불확실한 실패를 `wrong_password`로 강제할 수 없습니다. 암호화된 7z 디렉터리 열기도 암호 창과 열기 요청 식별 정보를 재사용하며 사용자는 열기를 취소할 수 있습니다. 독립 인증자가 있는 형식에서는 인증자 불일치가 무결성 실패로 남아 중지되며 암호 재시도로 들어가지 않습니다. 2바이트 검증값은 모든 잘못된 암호를 배제하지 못하므로 최종 인증이 필요합니다.

취소와 종료는 일반 큐 용량과 무관하게 암호 대기를 깨우고 소비하지 않은 비밀을 지웁니다. 콘텐츠 암호는 작업 동안만 유지하고 암호화 디렉터리 암호는 열린 세션과 승인된 작업으로 제한합니다. 어느 것도 설정, 이벤트, 로그, 명령줄, 복구 기록 또는 테스트 스크린샷에 들어가지 않습니다. 제출, 닫기, 취소, 프롬프트 변경과 종료 시 Qt 입력과 제어된 전송 버퍼를 지웁니다. Qt, 시스템 입력기와 의존성 내부의 모든 과거 사본 삭제는 보장할 수 없으며 Rust 컨테이너 제로화가 프로세스 전체의 삭제를 보장하지 않습니다.

## 출력, 재시도와 링크

일반 파일의 각 시도는 새 개인 준비 파일을 사용합니다. 잘못된 암호, 인증 실패, 스트림 오류와 취소는 해당 준비 수명을 끝내고 식별 정보를 검사하여 삭제를 시도합니다. 삭제가 실패하면 최종 작업 공간 정리가 경고를 보고하고 복구 자료를 보유하므로 즉시 삭제를 약속할 수 없습니다. 완전한 검증, 동기화, 원본 재검증과 확정 권한을 모두 얻은 뒤에만 기존 정책에 따라 게시하거나 교체합니다. 인증되지 않은 준비 파일은 대상에 게시하지 않습니다. 인증 실패 시 기존 대상은 그대로입니다. 재시도의 실제 디코딩/쓰기 수는 유지되고 파일당 8 GiB, 작업당 20 GiB와 원본 읽기 제한을 따르며 재시도로 예산을 초기화할 수 없습니다.

ZIP 작업은 디코더를 만들 때 실제 메타데이터 읽기 예산 64 MiB를 사용하고 이후 공유 입력 읽기 예산 20 GiB로 전환합니다. 로컬 헤더, 디스크립터, 암호문과 모든 암호 재시도가 같은 수를 소비합니다. 입력 읽기는 원본 파일 길이나 저장된 출력과 다르며 초과 시 중지하고 재시도에서 초기화하지 않습니다.

이후 파일이 실패하기 전에 이전의 검증된 파일을 이미 확정했을 수 있으며 전체 압축 파일 롤백은 약속하지 않습니다. 충돌을 건너뛸 때 파일을 읽지 않을 수 있으므로 인증된 것으로 셀 수 없습니다. 확정 항목, 정리 경고와 취소 후 불확실한 수치는 안전한 추출 계약을 따릅니다.

암호화된 심볼릭 링크를 선택하면 출력 권한을 얻거나 파생 디렉터리를 만들기 전에 작업의 Preparing 단계에서 선택된 모든 링크 페이로드와 의존 그래프를 인증하고 검증합니다. 일반 파일을 먼저, 링크를 마지막에 게시합니다. 경로 규칙, 링크당 4,096바이트/총 4 MiB, 64회 추적, 닫힌 의존성, 쓰기 부모로 링크 사용 금지, 점유된 말단 거부는 완화하지 않습니다. POSIX는 승인된 안전 실행 비트만 복원하며 Windows ZIP 링크와 TAR 링크는 계속 미지원입니다.

<a name="xdzip-interface-and-verification"></a>

## 인터페이스와 검증

암호 창, HTML과 고충실도 원본은 [암호 상호작용](../ux/password-extraction.md)을 참고하세요. 애플리케이션 모달 창은 작업이 대기할 때 자동으로 나타나며 작업 창에서 다시 열 수 있습니다. 오류 응답은 새 토큰을 사용하고 이전 입력을 지우며 수락된 응답은 중복 제출을 막습니다. 시스템 닫기 또는 취소는 현재 작업을 취소합니다. Escape는 공유 규칙에 따라 먼저 컨트롤 포커스에서 벗어난 뒤 창을 닫습니다.

생성과 추출 암호 필드는 입력과 독립된 명시적 UI 레이블로 접근성 이름을 제공합니다. Qt 6.8.2는 암호 상태에서 첨부 이름을 억제하므로 데스크톱 앱은 두 필드에 전용 접근성 인터페이스를 설치하여 이름만 재정의하고 Qt 상태, 텍스트/값과 동작을 유지합니다. 암호 플래그와 마스킹은 바꾸지 않습니다. 이 인터페이스는 Qt Quick 비공개 클래스를 상속하며 빌드와 런타임 Qt Quick 버전이 일치해야 합니다. 라이브러리를 업그레이드하거나 교체할 때 다시 빌드하고 인터페이스, 암호 비밀성과 세 플랫폼 호환성을 재검증합니다. 자동 인터페이스 검사와 시스템 화면 판독기 수동 검수는 별도 기록합니다.

검수 범위는 원시 AES 필드/CRC/디스크립터/ZIP64, 중복 이름 물리 레코드, 올바른 암호와 틀린 암호, 인증 손상, 혼합 파일, 서로 다른 암호, 빈 암호/제어 문자, 재시도 누적 자원, 가득 찬 큐, 취소/종료 깨우기, 원본 변경, 이전 대상 보호, 링크와 실행 권한, 독립 양방향 7-Zip 바이트 검사를 포함합니다. 인터페이스 검사는 실제 컨트롤러 흐름, 접근성 동작, 두 언어 여러 글꼴 크기 레이아웃, 밝은/어두운 테마, DPR과 네이티브 창을 별도로 다룹니다. 자동화는 시스템 화면 판독기 수동 검수가 아닙니다.

신뢰할 수 있는 암호 검증자가 없는 RAR에서도 암호화 헤더 또는 콘텐츠 디코딩 무결성 실패에 `password_or_integrity`를 사용합니다. 이미 일치한 신뢰할 수 있는 검증자, 평문 헤더 검사와 암호 외 실패는 각각의 분류를 유지합니다. 과거 항목별 암호와 플랫폼 문자 투영은 [RAR 구현 근거](../../engineering/rar-format-sources.md)를 참고하세요. 알 수 없는 크기는 디코딩이나 암호 상호작용 전에 거부하며 출력할 수 없는 항목에 비밀을 요청하지 않습니다.

오래된 암호화 RAR 레코드에는 잘못된 암호와 손상된 콘텐츠를 확실하게 구별할 검증자가 없으므로 각 암호화 항목을 디코딩하기 전에 별도로 암호를 요청합니다. 다른 비밀을 사용할 수 있는 다음 항목에 이전 암호를 직접 적용하지 않습니다. RAR5와 다른 지원 형식은 작업 로컬 재사용을 계속합니다. 이전 RAR CRC나 헤더 손상은 무결성 실패로 남으며 확인된 잘못된 암호가 아닙니다.

AES Crypt v0–3은 파일 이름이 암호화되지 않아도 열기 자격 증명이 필요합니다. 전체 암호문 인증이 어떤 행을 게시하기 전에 정확한 크기 메타데이터를 승인합니다. 검사/미리 보기/내보내기는 기존 비밀 슬롯으로 세션 자격 증명을 유지하고 항목별로 다시 묻지 않습니다. v0 검증자의 모호성, v1–3 래핑 키 검증과 이전의 인증되지 않은 길이/확장 필드는 [AES Crypt 계약](aescrypt-envelopes.md)을 따릅니다.
