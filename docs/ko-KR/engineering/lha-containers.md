# LHA 와이어 형식과 알고리즘 계약

[English](../../engineering/lha-containers.md) | [简体中文](../../zh-CN/engineering/lha-containers.md) | [繁體中文](../../zh-TW/engineering/lha-containers.md) | [日本語](../../ja-JP/engineering/lha-containers.md) | 한국어 | [Français](../../fr-FR/engineering/lha-containers.md)

LHA/LZH와 역사적인 LArc는 멤버를 순차적으로 저장하는 컨테이너 계열입니다. 파일 확장자, 알아볼 수 있는 방식 문자열 또는 Store 멤버의 성공만으로 다른 방식의 디코딩 지원을 증명하지 않습니다. `xdzip-compression`의 원시 프리미티브는 허용된 압축 범위와 독립적으로 검증된 디코딩 크기를 받으며 파일 시스템, 프로세스, 파일 이름 또는 게시 권한이 없습니다. 제품 등록과 컨테이너 수용에는 아래의 별도 검수가 필요합니다.

## 출처와 참조 경계

Masaru Oki의 1992년 3월 2일 원본 [LHa for Unix 헤더 문서](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/header.doc.md)는 Yoshizaki의 `lhx.doc`를 인용하여 레벨 0–2, 방식 마커, OS 식별자와 확장 범주를 정의합니다. 고정된 Git blob은 `b09a87759e4cee9c99f69616b2e975493253d412`, 저장소 커밋은 `16619b066b189ef289bb8b07b37d1c38d550da99`입니다.

이 문서는 압축 비트스트림의 완전한 명세가 아닙니다. 같은 원저자의 소스를 제한적으로 관찰해 필드 너비와 역사적 동작을 보완합니다. 정적 트리 알파벳의 [huf.c](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/huf.c), blob `15f90e1bb3079f6c11d852b9cb8a86fc7f240c35`, 공백으로 채운 기본 이력과 별도의 손상 아카이브 복구 모드에 관한 [slide.c](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/slide.c), blob `5dd5f9863993a6f4eda7398ecf4fe6f4ad7a711b`, LArc 필드와 절대 참조 원점의 [larc.c](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/larc.c), blob `c6f8f1ca111705a11dd744ac01e458e95377366d` 및 [lha_macro.h](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/lha_macro.h), blob `5c207426d0450468857187f5d74a675d695e3cc2`를 참조합니다. 엄격한 클린룸을 주장하지 않습니다. Rust 상태, 제한된 공유 접두사 디코딩, 오류 처리와 리소스 수용은 독립적으로 표현하며 참조 소스를 제품에 복사, 번역 또는 컴파일하지 않습니다.

[jLHA](https://github.com/umjammer/jlha/tree/0a6348d96e9bbb1ac5ee8b3f6ff1c2c75b17d0d9) 0.0.11, [Lhasa](https://github.com/fragglet/lhasa/releases/tag/v0.6.0) 0.6.0과 7-Zip 26.06은 독립 테스트 참조입니다. 고정된 ID와 공개 API 하네스는 [자체 픽스처](../../../tests/fixtures/lha/README.md)에 기록합니다. Java 알고리즘 소스는 제품 코드로 사용하지 않습니다. 참조 방식 범위와 기본 이력의 차이는 성공한 바이트 비교와 별도로 다룹니다. 참조 라이브러리와 도구는 `build/toolchain/`에 두고 제품 의존성 집합에는 포함하지 않습니다.

## 컨테이너 프레이밍 요구 사항

`xdzip-codec-lha::inspect`는 아래 레벨 0/1/2/3 프레이밍을 구현하고 `LhaCodec`은 물리 항목을 노출하며 `Reader`는 Qt와 독립적으로 제한된 페이로드를 디코딩합니다. 런타임, CLI와 Qt는 `LZH` 형식을 노출하며 `.lha`와 `.lzh`를 열기 및 연결 후보로 사용합니다. 접미사나 계열 마커는 제안일 뿐이며 게시 전 완전한 메타데이터가 검증을 통과해야 합니다. 강한 증거가 있는 유효 TAR, ZIP, 광학 및 SFX 발견은 우선권을 유지하며 원시 TAR 마커만 있는 경우 완전한 LHA 검증으로 구분할 수 있습니다. 생성은 레벨 2 헤더와 LH5 레벨 1/6/9를 수용하며 적격 레벨 2 아카이브는 다시 쓸 수 있습니다. 메타데이터 읽기는 64 MiB, 물리 레코드는 100,000개, 연쇄 확장은 멤버당 256개, 레벨 1과 레벨 3 헤더 누적은 1 MiB로 제한합니다. 호출자의 이름과 항목 제한도 적용됩니다. 레벨 0 CRC 생략은 명시적으로 표현하며 알 수 없는 OS별 기본 끝부분, 미지원 확장 종류와 헤더 레벨을 일반적인 지원 데이터로 해석하지 않습니다.

각 물리 멤버는 헤더와 정확한 압축 범위로 구성됩니다. 0 종료자가 아카이브를 끝냅니다. 후행 데이터, 종료 누락, 불가능한 범위와 이후 멤버의 오류로 부분 인덱스를 게시할 수 없습니다. 레벨 0과 1은 바이트 크기의 기본 헤더 합과 DOS 형태 타임스탬프를 유지합니다. 레벨 1 건너뛰기 크기는 연쇄 확장 헤더를 포함하므로 페이로드 범위를 수용하기 전에 정확한 합계를 빼야 합니다. 레벨 2의 리틀엔디언 전체 헤더 길이는 모든 확장을 제한하고 Unix 초를 사용합니다. 산술, 할당 또는 탐색 전에 필드와 확장 링크를 검사합니다. 선언된 확장 헤더 CRC는 자신의 CRC 필드를 0으로 하여 계산하며 페이로드 CRC와 별개입니다. 헤더 확장과 주석은 인접 파일, 권한 또는 실행 권한을 부여하지 않습니다.

레벨 3은 오프셋 0의 고정 리틀엔디언 크기 필드 너비 4, 32바이트 기본부, 오프셋 24의 전체 헤더 크기와 오프셋 28의 첫 32비트 확장 크기를 사용합니다. 각 확장은 32비트 다음 크기 필드로 끝납니다. 압축/원본 크기는 32비트, 시간은 Unix 초로 유지됩니다. 더 넓은 헤더가 자동으로 64비트 파일 크기를 허용하지 않습니다. 전체 헤더 길이는 할당 전에 1 MiB에 대해 수용하고 확장은 최대 256개입니다. 잘못된 최소 크기, 오버플로 또는 헤더 밖 링크와 추가 꼬리는 실패합니다. 필드는 원저자의 [레벨 3 헤더 주석](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/header.c), Git blob `df8ae5e3f9dece45325d499cf63c34fc2bb0ec99`에 기반합니다. 해당 README는 역사적인 레벨 3 명세가 확정되지 않았다고 경고합니다. 수용된 공통 확장은 jLHA와 Lhasa에서 별도로 입증하며 모든 역사적 확장을 주장하지 않습니다.

정확히 256바이트 경계에 정렬된 레벨 2 헤더는 첫 바이트가 0이 되어 종료자와 충돌합니다. 원저자가 문서화한 우회 방법은 이 경우 정확히 한 개의 0 패딩 바이트를 허용하고 전체 크기와 헤더 CRC에 포함합니다. 다른 헤더 꼬리와 0이 아닌 패딩은 거부합니다. 참조 도구의 레거시 경로 제한에 맞추기 위해 이름을 자르지 않고 독립적으로 인코딩한 222바이트 파일 이름으로 검증했습니다.

아카이브 이름 해석은 출력 승인과 독립적입니다. 물리 순서, 중복과 원시 이름을 보존합니다. 멀티바이트 후행 바이트가 디렉터리를 만들어 내지 않도록 백슬래시를 구분자로 해석하기 전에 레거시 인코딩을 해결합니다. 확장 파일 이름과 디렉터리 이름 필드는 명시적인 유일성 및 결합 규칙을 가지며 모호한 중복 선언은 편리한 표기를 선택하지 않고 실패합니다. 디렉터리와 특수/링크 레코드는 일반 파일로 취급할 수 없습니다. 원시 Unix 모드는 메타데이터이며 권한을 복원하지 않습니다. 기존 소스 고정, 이식 가능한 경로 사전 검사, 선택 항목 ID, 비공개 준비 영역과 최종 게시는 호스트의 책임으로 남습니다.

원시 이름은 디렉터리 이름 바이트, `0xff` 구분자, 파일 이름 바이트와 이 필드 사이의 정확한 경계를 보존합니다. 공유 제한 레거시 탐지기로 완전한 디렉터리 이름 구성 요소와 파일 이름을 독립적으로 샘플링합니다. 구분자 바이트가 인코딩 탐지를 오염시키거나 필드 사이에서 멀티바이트 문자를 완성할 수 없습니다. 각 필드를 엄격하게 디코딩한 뒤 실제 디코딩된 백슬래시를 정규화하고 `/` 구분자로 결합합니다. 각 구성 요소와 최종 이름에 의심스러운 경로 검사를 적용합니다. 원시 이름, 유효 이름과 이스케이프 표시는 공통 제한과 취소를 유지합니다. 같은 고정 유효 이름을 디렉터리 확장, 선택 압축 풀기, 미리 보기와 내보내기에 사용합니다. 알 수 없는 방식, 디코딩할 수 없거나 의심스러운 이름, 링크, 특수 유형과 모순된 디렉터리 선언은 경고와 함께 계속 보이지만 페이로드를 출력할 수 없습니다. Unix 모드는 권한 복원을 허용하지 않습니다.

제품은 Store (`-lh0-`, `-lz4-`), LH1–LH7, LZS와 LZ5를 수용하며 PMA 방식은 제품 수용 범위 밖입니다. 항목 방식 ID는 LZH에 한정되며 ZIP 방식 번호가 아닙니다. 검사는 `format_declared_checks`를 사용합니다. 존재하는 헤더/페이로드 CRC는 통과해야 하지만 CRC가 없는 오래된 레벨 0 멤버는 구조, 크기와 읽기 가능성만 제공합니다. LH2의 유한 변형 수용에는 페이로드 CRC가 필요합니다. 비밀번호, 볼륨과 복구 프로필은 지원하지 않습니다. 값이 0인 바이트 하나는 빈 아카이브이고 나중 레코드가 잘못되면 성공한 부분 목록을 만들 수 없습니다. 열기는 이름과 프레이밍을 스캔하고 검사나 압축 풀기는 실제로 콘텐츠를 디코딩해 선언된 검사를 검증합니다.

Store 마커 `-lh0-`와 `-lz4-`는 압축 및 디코딩 크기가 같아야 합니다. 역사적인 `-lz4-`는 현대 LZ4와 관계없습니다. `-lhd-`는 디렉터리를 선언합니다. LH1–LH3, PMarc, 확장 헤더, 비밀번호와 볼륨은 각각 독자적인 검증 프로필과 독립 샘플이 필요합니다. 확장자나 일반 Huffman/LZW 구현만으로 이러한 기능이 자동 제공되지 않습니다. 알 수 없는 방식은 디코딩된 일반 파일과 구별 가능해야 합니다. 프레이밍 검증은 페이로드 콘텐츠를 검증하지 않습니다.

## 정적 LH4–LH7 프리미티브

`LzhReader`는 1–65535개의 리터럴/일치 명령으로 된 MSB 우선 블록을 구현합니다. LH4와 LH5는 위치 알파벳 14와 4비트 트리 개수, LH6은 16과 5비트, LH7은 17과 5비트를 사용합니다. 사전 주소 비트는 각각 12, 13, 15, 16입니다. 이는 사전 용량과 더 넓은 인코딩 위치 알파벳을 구분하며 사전 밖 거리는 실패합니다.

19개 기호의 코드 길이 트리가 510개 기호의 리터럴/길이 트리를 설명합니다. 개수 필드는 각각 5비트와 9비트입니다. 짧은 트리 길이는 3비트와 제한된 단항 확장을 사용하고 길이 트리는 지정된 세 가지 0 연속을 지원합니다. 개수 0은 기호 비트를 소비하지 않고 명시적으로 제한된 단일 기호를 선택합니다. 일반 정준 트리는 완전하고 비어 있지 않으며 과잉 할당되지 않고 깊이가 16비트 이하여야 합니다. 기호 0–255는 리터럴, 256–509는 길이 3–256을 의미합니다. 위치 0은 거리 1이고 다른 위치는 선행 2의 거듭제곱과 하위 비트를 사용합니다. 겹치는 복사는 블록 간 이력을 유지합니다.

초기 사전은 일반 원본 LHa 동작에 따라 공백을 포함합니다. 0으로 채우는 손상 아카이브 복구 폴백은 시도하지 않습니다. 알려진 디코딩 크기는 명령과 블록 경계에서 정확히 끝나야 하며 리더는 허용된 전체 바이트 범위를 소비해야 합니다. 마지막 바이트의 미사용 비트는 무시하지만 추가 전체 바이트, 잘림, 명령 개수 0과 출력 초과는 실패합니다. 빈 디코딩 멤버에는 빈 압축 범위가 필요합니다. CRC-16 검증은 컨테이너의 책임입니다.

## LH1–LH3 프리미티브와 LH2 변형

`LhDynamicReader`는 LH1의 314기호 적응 모델, 4096바이트 사전, 길이 3–60과 거리에서 1을 뺀 값의 고정 정준 상위 비트를 구현합니다. 하위 6비트는 명시적입니다. LH2는 초기 기호 286개, 더 긴 길이를 위한 기호 285와 8비트 확장, 8192바이트 사전, 출력이 64바이트 경계를 지날 때마다 커지는 위치 알파벳을 사용합니다. 범위를 벗어난 확장 길이는 실패합니다. 둘 다 공백 이력과 정확한 크기/범위를 유지합니다. `LzhReader`는 추가로 LH3의 블록별 286기호 트리, 전송 또는 고정 128기호 위치 트리, 세 길이 단일 기호 센티널과 같은 8비트 길이 확장을 수용합니다. 0 블록, 잘못된 센티널과 불완전하거나 과잉 할당된 트리는 실패합니다.

일반 형제 속성 업데이트는 안정적 노드 ID, 명시적 순위와 부분 트리 교환을 사용하여 독립적으로 표현합니다. 재구축은 양수 잎 가중치를 위쪽으로 절반으로 줄이고 현재 순위를 유지하며 두 정렬 큐를 병합합니다. 재구축된 루트는 성장 전의 루트 ID와 독립적으로 완료된 병합에서 얻습니다. 실제 비교, 교환, 재구축과 초기화를 작업량으로 계산합니다. 이론적 근거는 [Vitter의 FGK 분석](https://www.ittc.ku.edu/~jsv/Papers/Vit87.jacm.pdf) 2절입니다. 와이어별 알파벳, 고정 위치와 임계값은 고정된 [dhuf.c](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/dhuf.c), Git blob `bcb08bdccf6c6396938e3b2d9b6b032a991aa26e` 및 [shuf.c](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/shuf.c), blob `2c18ed6a909cfa7fd1d591af1e7f0bd90e269fd7`에서 관찰했습니다. 이는 위 소스 관찰 공개를 확장하며 해당 구현 구조를 번역하지 않습니다.

원본 Unix LH2는 초기 단일 위치 가중치를 바꾸지 않고 위치 업데이트를 별도로 셉니다. jLHA는 일반 모델을 통해 단일 위치를 업데이트합니다. 같은 `-lh2-` 마커에서 호환되지 않는 실제 비트스트림이 생성됩니다. 원시 API는 명시적인 `Lh2Variant` 선택자를 제공하고 일반 방식 2 생성자는 jLHA 카운터 규칙을 사용합니다. 컨테이너는 LH2에 선언된 CRC를 요구하고 두 유한 변형을 출력하지 않는 싱크에 완전히 검증합니다. 잘못된 구조나 CRC는 변형을 제외할 수 있지만 소스, 취소, 할당량과 호스트 실패는 즉시 종료합니다. 모든 탐색은 실제 입력, 디코딩과 보조 작업량을 계산합니다. 성공한 변형은 디코딩 크기와 SHA-256 다이제스트가 같아야 하며 그렇지 않으면 모호하고 미지원입니다. 유일하게 유효하거나 동일한 결과는 출력용으로 다시 디코딩해 선택한 다이제스트와 CRC에 일치해야 합니다. 이 해시는 탐색과 제공 바이트를 결합할 뿐 아카이브의 진위성을 뜻하지 않습니다. 후보 바이트를 게시하거나 출력 작업량으로 재사용하지 않습니다.

원본 C 파일은 수정하지 않고 해시를 고정하며 자체 제한 호스트 하네스와 함께 `build/toolchain/`에서 테스트 오라클로만 컴파일합니다. 스트레스 생성은 해당 참조 빌드에서 원본의 테스트 전용 인코더/성장 상태를 호출하며 제품에 이식하지 않습니다. 거리를 바꾼 샘플은 각 변형의 문자와 위치 재조정 임계값을 모두 넘습니다. 자체 LH2 스트림 하나는 원본 단일 기호 규칙을 사용해 공개 일반 트리 API로 생성하고 원저자 디코더로 전체를 독립적으로 읽습니다. 원본 Unix가 jLHA의 긴/공백 프로필에 실패하는 경우를 포함한 참조 차이는 복구하거나 통과로 세지 않고 그대로 기록합니다.

## 컨테이너 생성과 게시

생성은 `.lzh` 또는 `.lha`에 방식 `lh5`, 레벨 1/6/9와 레벨 2 헤더를 사용하며 데스크톱 기본 접미사는 `.lzh`입니다. 호스트 생성 방식 ID는 259로 LZH 항목 범위의 방식 ID 5와 다릅니다. 생성은 Store, 비밀번호, 솔리드 그룹과 볼륨을 지원하지 않습니다. 입력은 고정된 최대 100,000 레코드, 이름 16 MiB, 실제 읽기 24 GiB이며 헤더 합계는 최대 64 MiB입니다. 각 멤버의 원본 및 압축 길이는 각각 부호 없는 32비트에 들어가야 하고 Unix 수정 초도 잘림 없이 부호 없는 32비트에 들어가야 합니다. 출력은 24 GiB로 제한되며 일반 파일은 멤버에 걸쳐 누적 원시 인코더 작업 대장을 유지합니다. CRC 처리는 실제 수용된 소스 바이트를 한 번만 다루고 입력 및 헤더 제한에 의해 제한됩니다. 읽기 예산을 완전히 소진하면 마지막 EOF 확인 전에 보수적으로 실패할 수 있습니다.

이식 가능한 일반 파일과 디렉터리만 수용합니다. 디렉터리는 `-lhd-`, 크기 0과 페이로드 CRC 0을 사용하며 일반 파일은 작은 입력이나 압축이 안 되어 크기가 늘어도 LH5를 사용합니다. 이름은 별도의 파일 이름 확장과 `0xff` 구분 디렉터리 이름 확장에 UTF-8로 저장합니다. 공통 헤더 CRC와 파일별 CRC-16을 항상 출력합니다. 정확히 정렬된 레벨 2 헤더는 필요한 단일 패딩 바이트를 유지합니다. 검증 중 검증된 디렉터리를 읽으면 바이트를 출력하거나 디렉터리 생성이나 권한 복원 권한을 부여하지 않고 성공합니다.

여기서 UTF-8은 선언되지 않은 이름 관례이며 보편적인 Unicode 플래그가 아닙니다. 자체 jLHA 공개 API 하네스는 UTF-8을 명시적으로 선택하고 페이로드와 독립적으로 전체 경로를 검사합니다. 레거시 Windows 리더는 대신 OEM 코드 페이지를 사용하여 모든 바이트와 CRC가 통과해도 다른 이름을 표시할 수 있습니다. 조사한 원본 7-Zip의 [LZH 이름 투영](https://github.com/ip7z/7zip/blob/main/CPP/7zip/Archive/LzhHandler.cpp), Git blob `1b6e3b9d9905abe28b53e39b1267465fe2fc7f03`는 `CP_OEMCP`를 선택합니다. 이 소스 관찰은 구현을 제품에 추가하지 않고 참조 한계를 설명합니다. 보편적인 파일 이름 상호 운용성은 주장하지 않습니다.

코덱은 고정된 소스 인덱스와 비어 있는 비공개 탐색 가능 준비 출력을 받습니다. 먼저 모든 레코드 경계를 검증하고 콘텐츠와 CRC를 스트리밍한 뒤 원시 인코더를 종료하고 압축 크기와 CRC를 수정하며 다음 멤버 전에 순차 끝 위치를 복원합니다. 임의 쓰기 미지원 또는 소스/출력/제한/취소 실패는 성공 종료자를 내보내지 않고 중단합니다. 최종 경로나 커밋 권한은 코덱에 들어가지 않습니다. 호스트 검증은 LHA의 고정된 유효 이름을 입력 이름과 비교하고 다른 컨테이너는 원래 원시 이름 비교를 유지합니다. 기존 고정 소스 재검사와 원자적 게시 전에 전체 콘텐츠를 실제로 디코딩합니다. 검증 실패, 소스 변경 또는 취소는 기존 대상을 유지하고 비공개 준비 영역을 정리합니다.

`scripts/check-lzh-creation.py`는 생성된 레벨 2 필드, 경계, UTF-8 이름, 타임스탬프와 두 CRC를 독립적으로 분석 및 검사하고 고정된 jLHA, Lhasa와 7-Zip으로 다중 멤버의 전체 콘텐츠를 비교합니다. 디렉터리/이름 결과와 페이로드 결과를 별도로 기록합니다. 런타임, CLI와 Qt 생성, 재열기, 검사와 압축 풀기는 각각 별도로 자동화되어 있으며 원시 작성기 왕복이 이 진입점들을 대체하지 않습니다.

기존 레벨 2 LHA/LZH 아카이브는 모든 멤버에 선언된 콘텐츠 CRC가 있고 이름, 레코드와 페이로드 수용을 통과하면 편집할 수 있습니다. 유지된 데이터는 압축된 형태로 복사합니다. 경로가 바뀌면 원래 방식, 크기, 타임스탬프, 속성과 허용된 비이름 확장을 유지하고 UTF-8 이름 확장을 재생성하여 공통 헤더 CRC를 갱신합니다. 새 파일은 LH5 작성기를 사용합니다. 레벨 0, 1, 3 헤더는 읽기 프로필에 따라 탐색할 수 있습니다. [아카이브 수정 계약](archive-transfers.md)을 참조하세요.

## 원시 LH5 작성기

`LzhWriter`는 제품 생성 수용과 별개인 제한된 원시 인코더입니다. 32768바이트 입력 블록에 걸쳐 8192바이트 이력을 유지하고 공유 4바이트 해시 체인을 통해 실제 길이 4–256 일치를 출력합니다. 레벨 1/6/9는 각각 1/16/64 후보를 검색하며 거리는 일치 탐색기의 더 넓은 용량이 아닌 LH5 사전으로 제한합니다. 완전한 정준 트리를 출력합니다. C 기호 0/1은 길이 8, 나머지 508개는 길이 9, 사용되는 두 길이 기호는 각각 길이 1, 위치 기호 0/1은 길이 3, 나머지 12개는 길이 4입니다. 의도적으로 제한된 이 고정 트리 전략은 최적 엔트로피 코딩이나 Store 폴백을 주장하지 않습니다. 명령 개수는 실제 개수이고 중간 블록은 바이트 정렬하지 않으며 마지막 부분 바이트만 0으로 채웁니다. 빈 입력은 압축 바이트를 출력하지 않습니다.

실제 해시 체인, 제한된 입력/이력, 최대 32768개의 4바이트 명령, 출력 버퍼와 제어 상태의 수용량은 1 MiB입니다. 실제 해시 초기화, 시드/조회, 후보 비교, 복사, 비트와 출력 시도는 누적 96 GiB 작업 대장을 소비하며 입력과 압축 바이트도 각각 24 GiB로 제한합니다. 콜백은 최대 8192 작업 단위를 다루고 쓰기는 최대 8192 입력 바이트를 받습니다. `finish_with_work()`는 멤버 사이에 남은 대장을 유지합니다. 짧은 쓰기와 타입 없는 중단은 바이트를 중복하지 않고 재시도합니다. 타입 있는 중단, 취소, 출력 및 리소스 실패는 인스턴스를 종료합니다. 싱크 경로나 게시 권한은 노출하지 않습니다. 마지막이 아닌 `flush()`는 연속된 하나의 비트스트림을 유지하며 성공 완료에는 `finish()`가 필요합니다.

명시적으로 실행하는 `scripts/check-lzh-writer.py`는 독립적으로 구성한 테스트 전용 레벨 0 프레이밍과 자체 원시 작성기 출력을 내보내고 7-Zip CRC 테스트를 포함해 고정된 jLHA, Lhasa와 7-Zip으로 모든 바이트를 비교합니다. 빈 입력, 1바이트, 모든 바이트, 공백, 결정적 난수, 긴 반복과 정확한 윈도 반복이 각 레벨을 다룹니다. 이는 원시 상호 운용성을 입증합니다. 제품 컨테이너 쓰기, 이름 메타데이터와 원자적 호스트 게시에는 별도 테스트가 필요합니다.

## LArc 프리미티브

`LarcReader`는 LZS 또는 LZ5를 별도로 선택합니다. LZS는 공백으로 채운 2048바이트 링, 초기 쓰기 인덱스 2031, MSB 우선 리터럴 플래그, 8비트 리터럴 또는 11비트 절대 참조 뒤에 2를 뺀 4비트 길이를 사용합니다. 일치 길이는 2–17입니다. LZ5는 4096바이트 링, 초기 쓰기 인덱스 4078, 바이트당 LSB 우선 플래그 8개, 바이트 정렬된 리터럴 또는 길이 3–18의 2바이트 절대 참조를 사용합니다. 절대 인덱스는 상대 거리가 아니며 두 방식 모두 Stac LZS 프레이밍을 재사용하지 않습니다.

LZ5 초기 링은 각 바이트의 13회 반복, 오름차순 바이트, 내림차순 바이트, 0 128개와 공백 110개를 포함합니다. 남은 미기록 슬롯 18개는 서로 호환되지 않는 역사적 기본값을 가지므로 실제로 쓰기 전에 읽으면 거부합니다. 이는 복구 변형을 선택하지 않고 수용 결과를 명확하게 만듭니다. 소스/대상 겹침과 링 순환은 일반적인 바이트별 의미를 유지합니다. 마지막 플래그 또는 바이트 미만 채움은 정확히 마지막으로 소비한 바이트 안에서만 무시하며 추가 전체 바이트는 거부합니다. 알려진 출력 크기와 CRC 검사는 컨테이너 수준에서 필수입니다.

## 리소스, 실패와 검수

모든 원시 리더는 압축 및 디코딩 크기를 각각 24 GiB, 누적 작업을 96 GiB 단위로 제한합니다. LH4–LH7은 사전 크기와 64 KiB, LArc는 사전 크기와 32 KiB를 수용하며 이력 초기화 플래그, 입력 버퍼와 제어 상태를 포함합니다. 더 작은 호출자 제한도 적용됩니다. 비트 필드, 트리 구성, 반복 확장, 사전 초기화와 출력은 사용 전에 작업량을 소비합니다. `work_remaining()`은 컨테이너가 멤버와 실패에 걸쳐 하나의 실제 작업 대장을 유지하게 합니다. 메모리와 필드 개수는 할당 전에 수용 여부를 판단하며 읽기는 최대 8192바이트를 반환합니다.

LH3는 사전과 64 KiB, 동적 LH1/LH2는 보수적으로 192 KiB를 수용합니다. 페이로드 인스턴스는 멤버, 반복 요청과 LH2 탐색에 걸쳐 실제 입력과 디코딩 작업 각각 24 GiB의 엄격한 대장과 알고리즘 작업 96 GiB 대장을 공유합니다. 메타데이터 재스캔은 입력 대장에 포함됩니다. LH2는 추가로 최종 패딩을 포함해 실제 SHA 압축 블록 바이트를 최대 24 GiB 수용하고 보조 작업 수용을 통해 보고합니다. 버린 후보는 `charge_skipped`로 디코딩 작업을 소비하며 최종 제공은 일반 쓰기를 사용하고 선불 크레딧을 얻지 않습니다. 페이로드 전에 소스와 스캔 스냅샷을 비교하며 최종 오류가 발생하면 해당 페이로드 인스턴스는 이후 사용할 수 없습니다.

협력 콜백은 새 소스 읽기가 없어도 제한된 작업을 다룹니다. 타입 없는 `Interrupted` I/O만 재시도하며 타입 있는 중단은 오류 객체를 유지하고 종료합니다. 소스, 작업량, 취소, 잘못된 데이터와 싱크 실패는 폴백이나 부분적으로 갱신된 상태의 재사용을 허용하지 않습니다. 호출자는 EOF까지 모두 읽고 선언된 페이로드 CRC를 검증하며 성공할 때까지 출력을 비공개로 유지해야 합니다. 이 CRC-16 값은 우발적 손상을 탐지할 뿐 진위성이나 비밀번호 검증에는 사용하지 않습니다. 공유 반사 다항식은 `0xa001`, 초기값 0이며 최종 xor는 없습니다.

[검수 요구 사항](../../../developers/qa/acceptance.md)의 `FORMAT-LHA`는 원시 상호 운용성, 컨테이너 검증과 실제 런타임/CLI/Qt 통합을 구분합니다. 프리미티브 테스트만으로 제품 진입점, 쓰기 지원, 비밀번호, 볼륨, 다른 플랫폼 또는 출시 승인을 입증할 수 없습니다. 참조 결과와 작업 패키지 진행 상황은 이슈에, 생성된 증거는 `build/` 또는 CI에 둡니다.
