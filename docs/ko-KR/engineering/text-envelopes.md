# UU, UUE 및 XXE 텍스트 봉투

[English](../../engineering/text-envelopes.md) | [简体中文](../../zh-CN/engineering/text-envelopes.md) | [繁體中文](../../zh-TW/engineering/text-envelopes.md) | [日本語](../../ja-JP/engineering/text-envelopes.md) | 한국어 | [Français](../../fr-FR/engineering/text-envelopes.md) | [Deutsch](../../de-DE/engineering/text-envelopes.md) | [Español](../../es-ES/engineering/text-envelopes.md) | [Português (Brasil)](../../pt-BR/engineering/text-envelopes.md) | [Русский](../../ru-RU/engineering/text-envelopes.md)

전통적인 UU 필드와 비트 순서는 [NetBSD uuencode(5)](https://man.netbsd.org/uuencode.5)를 따릅니다. Base64 모드는 [uuencode(1)](https://man.netbsd.org/uuencode.1)과 [GNU Sharutils](https://www.gnu.org/software/sharutils/manual/sharutils.html)에 설명되어 있습니다. XX 문자표는 `+-0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz`이며 [UUDeview](https://github.com/hannob/uudeview)의 공개 인코더와 대조했습니다. Rust 판독기는 이 필드와 비트 규칙을 바탕으로 독립적으로 작성되었습니다. 참조 C 구현은 테스트 도구일 뿐이며 런타임 의존성이 아닙니다.

<a name="xdzip-admitted-profiles-and-boundaries"></a>

## 허용 프로필과 경계

`begin`, 공백 하나, 8진 모드 숫자 한 자리에서 네 자리, 공백 하나, 비어 있지 않은 원시 파일 이름을 허용합니다. 헤더 모드는 구문만 검증하고 복원하지 않습니다. UU와 XX는 이 헤더를 공유합니다. 빈 멤버의 0개수 행을 포함해 완전히 유효한 개수 지정 본문 행으로 실제 문자표를 식별합니다. 각 행의 첫 6비트 값은 디코딩된 0–63바이트를 선언하며 행은 정확히 `1 + 4 * ceil(count / 3)`개의 문자여야 합니다. UU는 0에 공백과 백쿼트를 허용합니다. 상위 비트부터 6비트 값 네 개를 세 바이트로 디코딩하고 마지막 그룹의 사용하지 않는 바이트는 버립니다. 과거 패딩 비트가 0이어야 한다고 요구하지 않습니다. 0개수 행 바로 다음에는 정확한 `end` 행이 와야 합니다. 짧아지거나 손상된 행은 복구하지 않습니다.

`begin-base64` 변형은 각각 네 글자의 배수이며 정규 패딩 비트가 0인 4–76자 일반 Base64 행을 허용합니다. 패딩된 행은 본문을 닫고 그 뒤에는 정확한 `====` 종료 표시만 올 수 있습니다. 빈 본문도 허용합니다. 단독 Base64, MIME 조합, GNU `begin-encoded` 파일 이름 확장, 여러 부분 복구, yEnc와 BinHex는 이 프로필의 범위 밖입니다. `.uu`와 `.uue`는 UU 후보이고 `.xxe`는 XXE 후보입니다. 후보가 실제 문자표를 결정하지는 않습니다.

LF 또는 CRLF와 마지막 줄 바꿈 없는 완전한 종료 표시를 허용합니다. 길이가 제한된 전송 텍스트가 멤버 앞, 사이 또는 뒤에 올 수 있습니다. 헤더처럼 보이지만 잘못되었거나 지원하지 않는 행은 오류이며 멤버를 숨기기 위해 무시하지 않습니다. 첫 헤더는 64 KiB 이내에서 시작해야 하며 각 전송 또는 헤더 행은 최대 8192바이트입니다. 강한 컨테이너 서명, 광학 디스크 디스크립터와 유효한 TAR 헤더가 텍스트 후보 검색보다 우선합니다. 접미사나 `begin`이라는 단어가 아닌 완전한 검증으로 형식을 허용합니다. 모든 멤버가 XX인 아카이브는 XXE로, 일반 UU, Base64와 혼합 멤버 봉투는 UU로 표시합니다. 중복 이름을 포함하여 각 물리적 멤버는 직렬화 순서 식별자, 원래 이름과 실제 인코딩을 유지합니다.

## 호스트 권한, 할당량과 검사

백엔드는 승인된 위치 이동 가능 원본과 호스트 소유 출력 대상만 받습니다. 헤더 파일 이름은 공통 아카이브 수준 이름 해석, 표시 이스케이프와 안전하지 않은 경로 검사를 거칩니다. 이름이 입력을 열거나 출력 경로 권한을 부여하지는 않습니다. 판독기는 권한을 복원하거나 외부 파일을 따르거나 명령을 실행하거나 디렉터리를 만들지 않습니다. 작성기, 다시 쓰기, 암호화 또는 분할 볼륨 권한도 제공하지 않습니다. 인코딩된 본문과 종료 표시 구간은 알려진 압축 크기이며 데이터 크기는 검증된 행에서 계산합니다.

메타데이터 검증은 공통 검색 제한 안에서 봉투 전체를 읽습니다. 일반적인 제한은 실제 원본 읽기 64 MiB, 항목 100,000개, 파일 이름당 원시 4096바이트, 원시 이름과 표시 이름의 누적 예산 16 MiB입니다. 디코딩된 내용 대신 제한된 멤버 구간을 보관합니다. 데이터 전달 전에 다시 검색하여 완전한 투영 인덱스를 불변 호스트 스냅숏과 비교한 뒤 위치 정보를 보관하므로 이전 멤버를 매번 다시 검색하지 않고 임의의 물리적 선택을 할 수 있습니다. 메타데이터와 반복 본문 읽기는 전용 24 GiB 누적 입력 상한에 포함되고 전달된 바이트에는 별도의 24 GiB 상한이 있습니다. 호스트의 더 엄격한 작업 및 파일 제한도 적용됩니다. 읽기, 행 처리, 출력 대상 전달과 별도 취소 토큰을 협조적으로 확인합니다. 형식이 구분된 원본 실패를 보존하고 종료된 `Interrupted` 실패는 재시도하지 않습니다. 원본, 구조, 할당량, 취소 또는 출력 대상 오류가 발생하면 열린 판독기는 무효화되며 재시도해도 작업량은 반환되지 않습니다.

검사는 구조와 읽기 가능성을 검증하며 **체크섬이나 인증은 제공하지 않습니다**. 유효한 6비트 값을 바꾸면 검사 실패 없이 출력이 달라질 수 있습니다. 임시 준비와 최종 게시는 계속 호스트의 책임입니다. 원본 식별 검사는 변경을 가능한 범위에서 감지할 뿐 인증된 스냅숏이 아닙니다. 선택한 멤버만 추출해도 봉투 전체를 검증하며 지원하지 않는 헤더 확장이나 뒤에 있는 잘못된 멤버를 조용히 건너뛸 수 없습니다.

## 자동화된 수락 검증

프로젝트 소유 참조 입력은 모든 바이트 값, 빈 파일, 행 끝의 나머지, UU 0 별칭, CRLF, XX와 Base64, 전송 텍스트와 중복 이름을 가진 혼합 멤버를 다룹니다. 독립 소스 리비전을 고정하고 공개 인코더만 호출합니다. UU는 Python `binascii`로, Base64는 독립 표준 디코더로 검증합니다. 0–63의 모든 개수 길이, 안전하지 않은 이름과 Unicode 이름, 정확한 입력 및 이름 및 디코딩 제한, 짧은 읽기, 형식이 구분된 실패, 스냅숏 불일치, 취소, 종료 후 무효화와 기존 출력 불변성도 시험합니다. 실제 런타임, CLI와 Qt 작업은 탐색, 검사, 추출, 물리적 선택, 읽기 전용 설명, 검사 강도 안내와 등록된 후보를 다룹니다. 영향받은 이중 언어 및 테마 및 글자 크기 레이아웃과 기본 창 및 메뉴 비율은 자동화로 검증합니다. 참조 바이너리와 생성된 증거는 `build/`에 보관하며 진행 상황과 실제 결과는 전달 이슈에 기록합니다.
