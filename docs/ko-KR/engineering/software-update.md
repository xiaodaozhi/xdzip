# 사용자가 시작하는 업데이트 계약

[English](../../engineering/software-update.md) | [简体中文](../../zh-CN/engineering/software-update.md) | [繁體中文](../../zh-TW/engineering/software-update.md) | [日本語](../../ja-JP/engineering/software-update.md) | 한국어 | [Français](../../fr-FR/engineering/software-update.md) | [Deutsch](../../de-DE/engineering/software-update.md) | [Español](../../es-ES/engineering/software-update.md) | [Português (Brasil)](../../pt-BR/engineering/software-update.md) | [Русский](../../ru-RU/engineering/software-update.md)

Windows MSIX 패키지 ID가 있으면 정보 창에 앱 내 업데이트가 표시되지 않으며 업데이트 컨트롤러는 기존 GitHub 업데이트 확인을 거부합니다. Store 버전의 업데이트는 Microsoft Store가 관리하며 사이드로드한 패키지에는 앱 내 자동 업데이트를 보장하지 않습니다. ID 조회 오류는 설치 프로그램 업데이트의 오용을 방지하기 위해 패키지 ID로 취급합니다. 일반 설치와 다른 플랫폼은 그대로 유지됩니다.

독립 실행형 CLI와 데스크톱 패키지에 포함된 CLI는 [명령줄 계약](command-line.md)에 따라 각각의 설치를 업데이트합니다. 독립 실행형 CLI는 별도의 서명된 매니페스트와 관리 버전 디렉터리를 사용합니다. 포함된 CLI는 같은 사용자의 단일 인스턴스 IPC로 후보 의도를 전달하고 데스크톱 컨트롤러가 이를 독립적으로 검증합니다. 수락은 handed_off만 의미하며 실제 성공에는 영수증과 실행 중인 ID가 필요합니다. Windows/Linux 설치 사용 중 보호에는 CLI 작업도 포함됩니다. macOS는 공유 사용 잠금, 커밋 게이트와 영구 상태로 CLI를 보호합니다. 기존 작업은 암묵적으로 취소되지 않습니다. 헤드리스 CLI의 ID 조회는 QApplication을 생성하거나 설치 영수증을 읽고 지우지 않습니다.

앱의 `UpdateController`는 정보 창에서 공개 릴리스를 확인합니다. 정보 창을 닫아도 확인이나 다운로드는 취소되지 않으며 다시 열면 같은 상태를 표시합니다. 확인은 사용자가 시작하며 시작 시 폴링이나 자동 설치는 하지 않습니다. 제품 창은 정보 창과 공유 작업 컨트롤을 계속 재사용합니다.

## 선택, 네트워크와 개인정보

Qt 업데이트 클라이언트는 메타데이터, 체크섬과 패키지 다운로드에 HTTP/1.1을 사용합니다. 이는 고정된 Qt 릴리스에 대해 공개된 완화 조치를 적용합니다. macOS Sparkle 업데이트 전송은 별도입니다. [Qt 보안 권고](https://www.qt.io/blog/security-advisory-cve-2026-96432)

클라이언트는 고정 저장소 `xiaodaozhi/xdzip`의 공개 [Releases API](https://docs.github.com/en/rest/releases/releases)만 읽고 자격 증명을 사용하지 않으며 파일 이름, 아카이브 내용, 비밀번호, 최근 기록 또는 설정을 전송하지 않습니다. GitHub와 다운로드 CDN은 연결 정보와 앱 버전이 포함된 User-Agent를 받습니다. 릴리스 페이지와 다운로드 폴더는 시스템 인터페이스로 엽니다.

페이지당 최대 100개 항목, 최대 10페이지이며 각 응답은 최대 8 MiB, 매니페스트는 256 KiB, 서명은 4 KiB입니다. 원본 요청은 HTTPS와 명시적으로 등록된 GitHub/CDN 호스트만 허용합니다. 사용자가 미러를 설정하면 해당 HTTPS 사이트를 전송 주소로 허용하며 리디렉션은 최대 5회입니다. 메타데이터는 유휴 15초와 전체 30초, 다운로드는 유휴 30초와 전체 1시간으로 제한합니다. 메모리 ETag 캐시는 최대 24개 항목을 보유하며 304는 이전에 성공한 응답만 재사용합니다. 오프라인, TLS, 시간 초과, 속도 제한, 잘림, 패키지 누락과 매니페스트 오류는 ‘이미 최신’이 아니라 실패입니다. 반복 클릭으로 병렬 업데이트를 시작하지 않습니다.

업데이트는 설정된 시스템, 직접 연결 또는 자격 증명 없는 사용자 지정 HTTP/SOCKS5 프록시를 사용합니다. 선택적 미러는 HTTPS를 사용하고 자격 증명, 쿼리 또는 프래그먼트를 포함하지 않아야 하며, 미러 기본 주소 뒤에 원본 GitHub HTTPS URL 전체를 붙입니다. 원본 URL도 고정 호스트 허용 목록을 통과해야 합니다. 미러와 리디렉션은 서명된 매니페스트 내용, 검증, 후보 ID 또는 설치 게이트를 바꾸지 않습니다. 설정 변경은 현재 업데이트가 끝난 뒤 다음 업데이트에 적용합니다. macOS 네이티브 Sparkle은 시스템, 직접 연결과 자격 증명 없는 사용자 지정 HTTP CONNECT/SOCKS5 모드를 지원합니다. 각 네이티브 인스턴스는 시작 전에 검증된 모드와 프록시 주소를 복사하고 피드와 아카이브에 같은 세션 정책을 사용합니다. 사용자 지정 프록시 실패 시 직접 연결로 폴백하면 안 됩니다. 직접 모드는 URLSession 프록시 사전의 HTTP, HTTPS, SOCKS, FTP, PAC와 검색 플래그를 명시적으로 숫자 0으로 설정합니다. nil 사전이나 빈 최신 프록시 배열은 여전히 시스템 기본값을 뜻합니다. TLS 신뢰, 릴리스 서명과 독립 설치 게이트는 그대로 유지됩니다.

HTTP 429는 속도 제한입니다. HTTP 403은 남은 할당량이 0이거나 유효한 초 단위 Retry-After가 있거나 GitHub JSON 메시지가 속도 제한을 명시한 경우에만 속도 제한으로 분류합니다. 다른 403은 네트워크 실패로 남으며 할당량 소진을 추정하지 않습니다. 제품은 자동 재시도하거나 GitHub 자격 증명을 읽지 않습니다. 익명 할당량은 출발 IP별로 공유되며 CI 저장소 권한으로 늘릴 수 없습니다.

Qt가 없는 Rust 코어는 시맨틱 버전, 채널과 단조 증가하는 빌드 번호로 선택하고 고정 저장소, 전체 6개 패키지 클래스, 아키텍처, 패키지 유형, 최소 시스템 계약과 동일한 후보 ID를 검증합니다. stable은 stable만, alpha는 alpha, beta, rc와 stable을, beta는 alpha를 제외하고, rc는 rc와 stable을 수락합니다. dev는 공개 릴리스를 확인할 수 있습니다. 시맨틱 버전과 빌드 번호가 모두 증가해야 하며 게시 시각으로 대신하지 않습니다. 클라이언트는 현재 시스템 지원 여부와 Releases 에셋의 바이트 수도 확인합니다.

## 신뢰와 다운로드

`release.json.sig`는 매니페스트의 정확한 바이트를 검증합니다. 신뢰 루트는 클라이언트와 설치 도우미에 컴파일되어 있으며 다운로드나 요청으로 추가할 수 없습니다. JSON 메타데이터는 문자열 FFI 전에 UTF-8로 검증합니다. 잘못된 인코딩은 대체 문자로 인증된 바이트를 바꾸지 않고 명시적으로 실패합니다. 서명 형식, 독립 Sparkle 키, 전달 순서와 불변 에셋은 [릴리스 프로토콜](release-protocol.md)을 참조하세요. 서명이 없거나 공개 키를 알 수 없으면 공식 릴리스 페이지의 수동 다운로드만 제공하며, 잘못된 서명은 명시적으로 실패합니다. 프로덕션 공개 키를 설정하기 전에는 자동 교체가 비활성화됩니다.

Windows/Linux는 최대 2 GiB 패키지를 비공개 업데이트 캐시에 스트리밍하면서 길이와 SHA-256을 확인합니다. 성공적으로 게시된 경우에만 도우미에 전달할 수 있습니다. 취소나 검증 실패는 설치 가능한 상태를 만들지 않습니다. 포터블, 수정된 빌드, 개발·소스 빌드 또는 ID를 알 수 없는 빌드는 확인과 다운로드만 제공합니다. 자동 교체에는 Release 구성과 유효한 커밋 ID도 필요합니다. Git ID가 없는 소스 아카이브 빌드는 설치된 것으로 취급하지 않습니다. 설치 ID는 시스템 설치 기록, 실행 경로와 패키지 마커에 일치해야 합니다.

macOS는 고정된 Sparkle 2.10.0과 제한된 `xdzip-proxy.2` 프록시 확장을 사용하며 얇은 Objective-C++ 사용자 드라이버가 통합 정보 창에 상태를 전달합니다. 프레임워크 라이브러리와 Ed25519는 고정 소스 및 패치로 Apple Silicon에서 네이티브 빌드하고, 리소스, 설치 도우미와 서명 도구는 고정된 공식 SDK의 출처를 유지합니다. 파생 프레임워크가 업스트림 SDK와 바이트 단위로 같다고 주장하지 않습니다. Sparkle은 피드와 아카이브를 네이티브 검증하며 피드에는 같은 선택 후보만 포함합니다. Sparkle이 추가 SHA-256 검사를 수행한다고 주장하지 않습니다. 읽기 전용 DMG, App Translocation, 등록되지 않은 .app 또는 업데이트 공개 키 누락 시 수동 설치를 안내합니다. 일반 CI는 Sparkle을 사용한다는 이유만으로 Mac 앱 패키지를 배포, 서명 또는 업로드하지 않습니다.

수동 폴백은 설치 ID, 세션, 자동 업데이트 피드 누락, 잘못된 네트워크 구성 중 처음 충족되지 않은 조건을 표시합니다. ID 실패는 검사 그룹이 실패했다는 뜻일 뿐 어느 항목인지 추측하지 않으며, 여러 미충족 조건은 순서대로 해결해야 할 수 있습니다. 정보 창은 해당 릴리스와 DMG 안내에 연결하고 app.zip 압축 해제, 이전 버전 종료 및 앱 교체를 설명합니다. 다운로드 성공은 설치 성공이 아닙니다.

## 설치 전달과 복구

다운로드 중에도 기존 작업은 계속됩니다. 다운로드와 설치를 선택한 후 작업이 활성 상태면 기다립니다. 사용자는 대기를 취소하고 업데이트를 미룰 수 있으며 작업이나 비밀번호 요청은 암묵적으로 취소되지 않습니다. 도우미 준비 후 `prepareForUpdate`는 활성 작업, 작업 시작과 모달 상호작용을 거부합니다. 전달이 시작되면 새 세션이나 작업을 허용하지 않으며 설치 커밋을 보내기 전에 모든 Rust 연결을 정리하고 종료를 기다려야 합니다. 전달은 ‘이전 프로그램 즉시 재시작’ 경로를 사용하지 않습니다.

Windows는 현재 사용자에게 등록된 설치 루트에서만 Qt 없는 독립 도우미를 비공개 캐시에 복사합니다. 도우미는 서명, 크기와 해시를 독립적으로 다시 검증하고 포착된 메인 프로세스의 종료를 기다린 뒤 대화형 라이선스 동의가 있는 기존 Inno 설치 프로그램을 실행합니다. 설치 게이트는 교체 중 재시작을 차단합니다.

설치 루트가 안전 검사를 통과하지 못하면 정보 창은 네트워크 실패로 분류하지 않고 설치 폴더 권한이나 릴리스 페이지의 수동 설치를 안내합니다. 기존 디렉터리와 ID 검사는 완화하지 않습니다.

Ubuntu 설치는 고정 경로 `/usr/libexec/xdzip-update-helper`를 사용하며 일반 사용자 코디네이터는 고정 인수로만 polkit을 호출합니다. root 도우미는 패키지를 비공개 root 준비 영역에 복사하고 서명, xdzip 패키지 이름, 아키텍처와 버전을 다시 검증하며 고정 APT 작업만 허용합니다. 명령, 임의 패키지 이름이나 대상 디렉터리를 받지 않고 sudo 셸을 사용하지 않습니다. 인증 취소와 인증 에이전트 누락은 별도 상태입니다. 구성되지 않은 dpkg를 성공으로 보고하지 않으며 자동 롤백이나 이전 프로그램 재시작도 하지 않습니다. 원래 사용자로 새 버전을 재시작할 때 허용 목록의 제한된 XDG 설정, 데이터, 캐시, 상태 디렉터리와 데스크톱 언어는 유지하지만 동적 로더, Qt SDK 또는 테스트 환경 재정의는 유지하지 않습니다. 해당 변수는 root 설치 명령에 전달하지 않습니다.

macOS에서는 모든 연결 종료를 기다린 후에만 Sparkle 설치 콜백을 해제합니다. 메인 프로그램은 공급자가 실제 설치를 커밋됨으로 표시한 뒤 SDK 설치 응답을 호출하기 전에 종료 인터셉터를 동기적으로 해제합니다. 종료 대기 장벽만으로 마지막 창의 조기 자동 종료를 허용하면 안 됩니다. 전달이 실패하거나 취소된 후의 일반 종료도 네이티브 도우미 관찰 게이트를 기다립니다. Sparkle이 실제 아카이브 교체와 재시작을 수행합니다. 취소 후 다음 종료 시 설치할 계획은 남지 않습니다. 프레임워크, XPC와 도우미는 각각 필요한 서명 매개변수와 엔타이틀먼트를 유지하므로 일반 재서명 규칙을 모두에 적용할 수 없습니다.

Sparkle 취소 응답은 비동기 업데이트 주기에서 처리되며 주기 완료는 별도 설치 프로세스의 종료를 뜻하지 않습니다. 커밋되지 않은 설치에서 일반 종료는 취소를 요청하고 주기를 기다린 다음, 시스템 `/bin/ps`를 읽기 전용으로 사용해 이 앱의 정확한 프레임워크 경로에 일치하는 Autoupdate 프로세스를 관찰합니다. 해당 프로세스가 종료된 후에만 종료 인터셉터를 해제합니다. 준비 시 일치하는 설치 프로그램을 기록합니다. 검사 실패는 종료 허가가 아니며 도우미를 강제 종료하거나 무관한 프로세스 정보를 기록하지 않습니다. 준비 실패 후 재시도도 업데이트 드라이버를 교체하기 전에 이전 도우미의 종료를 기다립니다. 커밋된 설치는 Sparkle 고유의 종료와 재시작을 사용합니다.

Windows/Linux 트랜잭션은 무작위 ID와 고정 ready/proceed/cancel/result 파일 이름을 사용합니다. 종료 전에 클라이언트는 트랜잭션, 대상 ID와 캐시 디렉터리를 설정 구성 내부가 아니라 설정 옆의 별도 `update-state.ini`에 저장합니다. 도우미는 게이트를 해제하고 재시작하기 전에 성공 결과를 원자적으로 기록합니다. 다음 시작 때 영수증 경로와 크기를 제한하고 트랜잭션과 현재 버전, 빌드, 설치 ID를 검증합니다. 실패, 영수증 누락 또는 불일치 시 설치를 자동 재시도하지 않고 복구를 표시합니다. 유효한 후보 URL이 없는 복구 기록도 고정된 공식 릴리스 목록을 열 수 있습니다. 캐시 자료는 사용자 수리를 위해 유지하며 공개 증거에 완전한 비공개 경로를 포함하지 않습니다.

Sparkle 설치를 해제하기 전에 macOS는 대상 버전과 빌드의 로컬 시도 기록을 저장합니다. 재시작 후 실제 실행 ID와 신뢰할 수 있는 설치 마커가 완료 또는 복구를 결정합니다. 이 기록은 설치 권한을 부여하지 않으며 Sparkle 서명 검증을 대체하지 않습니다.

## 검증 범위

Mac 전용 진단은 전체 제품 체인만 실행할 수 있습니다. 전체 플랫폼 검증은 6개 Sparkle 시나리오와 전체 제품 체인을 항상 실행하며 6개 시나리오를 건너뛰는 진단 옵션을 무시합니다.

네이티브 다운로더 시스템 충돌 검사는 명시적으로 격리된 일회용 호스팅 Apple Silicon 러너에서만 자체 정적 프록시와 PAC를 임시 활성화합니다. 먼저 시스템 모드 피드와 아카이브가 실제 프록시에 도달하고 직접 모드에서는 도달 횟수가 0인지 확인합니다. HTTPS 대조 검사는 연결 대상을 검증하고 신뢰할 수 없는 인증서 거부를 유지합니다. 제한된 도우미는 서비스의 전체 프록시 설정과 고정 테스트 도메인의 hosts 내용을 저장, 복원, 검증하며 EOF와 시간 초과에도 적용합니다. 로컬 실행은 프록시, DNS 또는 인증서 신뢰를 절대 변경하지 않습니다. 별도의 전체 제품 체인은 제어된 PAC에서 직접 설치, 일반 재시작과 활성 업데이트 구성 스냅샷을 검증합니다. 다운로더 검사는 설치 증거를 대체하지 않습니다.

Mac의 SDK 없는 HTTPS 수용은 동일한 배포 프로브와 익명의 실제 업데이트 요청을 사용합니다. 기록에는 상태 코드, Qt 오류와 허용 목록의 속도 제한 응답 헤더만 포함하며 원시 오류 본문, 출발 IP 또는 자격 증명은 포함하지 않습니다. 속도 제한 확인 후 수용 드라이버는 최대 3개 프로브를 시작하며 Retry-After와 할당량 재설정 중 더 늦은 시각까지 기다립니다. 사용할 수 있는 주 할당량 재설정 시각이 없으면 조기 재시도를 거부합니다. 다른 확인된 제한은 최소 60초부터 증가하는 대기 시간을 사용합니다. 총 대기는 최대 3700초이며 초과 시 각 결과와 실제 대기를 유지하면서 명시적으로 실패합니다. 기존 요청별 시간 초과, TLS, 응답 제한, 성공 상태와 SDK 격리는 계속 필요하며 재시도를 한 번의 통과로 합치지 않습니다. 이 대기는 전용 수용 드라이버에만 속하며 제품에 백그라운드 재시도를 추가하거나 마지막 전문 검사를 건너뛰게 하지 않습니다.

코어 픽스처는 채널, dev, 순서가 다른 페이지, 패키지 누락, 잘못된 서명, 최소 시스템과 ID 충돌을 포함합니다. 네트워크 픽스처는 취소, 반복 클릭, 속도 제한, TLS, 응답 제한, ETag와 손상된 다운로드를 포함합니다. 세션 회귀는 작업 유지와 모든 종료 대기 후 전달을 확인합니다. 실제 3개 플랫폼의 이전 버전에서 새 버전으로의 업데이트, 인증 취소, 재시작, 설치 실패·복구, 설정·연결 유지와 SDK 없는 HTTPS에는 격리된 플랫폼 증거가 필요합니다. 단위 테스트나 CI 컴파일은 이를 대체하지 않습니다. 전체 Mac 업데이트에는 네이티브 Apple Silicon이 필요합니다. 실제 완료와 증거는 이슈에서 추적합니다.

[전용 네이티브 업데이트 회귀](../../../.github/workflows/update-regression.yml)는 수동으로만 실행하며 프로덕션 비밀을 포함하거나 앱 패키지를 업로드하지 않습니다. 기본값은 모든 플랫폼이며 진단용으로 단일 플랫폼을 선택할 수 있고 각각 독립 큐를 가집니다. 최종 수용에는 여전히 같은 커밋의 모든 플랫폼 결과가 필요합니다. 일회용 GitHub 러너의 Windows와 전용 컨테이너의 Linux는 먼저 자체 C 프로토콜 제품과 실제 Inno/APT로 도우미 취소, 실패와 복구를 검증합니다. 별도의 비공개 Qt 업그레이드 체인은 두 실제 `browser_main`/QML 버전을 빌드하고 정보 창에서 실제 마우스 입력을 사용하며 매니페스트와 패키지, 종료 대기, Inno/APT, 일반 사용자의 단일 인스턴스 재시작과 영수증 복구를 검증합니다. 설정, 알 수 없는 설정 키, 기존 기본값과 무관한 설치 디렉터리 파일의 유지도 확인합니다. Linux는 빌드 SDK와 런타임 컨테이너를 분리하며 런타임에는 컴파일러나 Qt SDK가 없고 사용자 지정 XDG 디렉터리를 사용합니다. Windows Server CI는 비공개 매크로 아래에서만 최소 시스템 감지를 대체하며 네이티브 Windows 11 수용을 대체하지 않습니다. 이 체인은 공개 GitHub URL의 네트워크 전송을 대체하며 프로덕션 HTTPS/TLS는 SDK 없이 별도 검증합니다.

별도로 승인된 [프로덕션 서명 수용](../../../.github/workflows/production-update-acceptance.yml)은 커밋된 프로덕션 공개 루트를 유지하면서 기존 보호 환경 키를 사용하고 실제 Qt 업그레이드 및 복구 체인을 따릅니다. 준비 단계에서는 서명하지 않습니다. 독립 서명 단계가 먼저 공개 신뢰 루트의 정확한 일치를 확인한 다음 이 고정 후보를 검증하며, 실행은 비밀이 있는 환경을 거부합니다. 임의 에셋 서명이나 게시 인터페이스는 제공하지 않습니다. 서명된 후보는 일회용 러너에 남고 공개 아티팩트에는 제한된 진단과 요약만 포함합니다. 테스트 키 회귀와 별도로 기록하며 실제 실행만 통과이고 키 일치는 설치 성공이 아닙니다. [릴리스 프로토콜](release-protocol.md)을 참조하세요.

확장 시나리오는 패키지 다운로드 완료를 지연하고 실제 AES 검사를 비밀번호 대기까지 시작한 뒤 업데이트가 해당 작업을 기다리는지 검증합니다. 비밀번호 대화 상자는 네이티브 앱 모달로 유지되며 픽스처는 컨트롤러로 업데이트 대기를 취소하고 해당 단계에서 정보 창 마우스 입력을 사용하지 않았음을 명시적으로 기록합니다. 취소 후 같은 작업과 비밀번호 토큰이 남고 입력기 확정 이벤트와 비밀번호 확인 버튼으로 검사를 완료한 다음 정보 창에서 설치를 다시 시작합니다. 다른 실행은 업데이트와 비밀번호 대기가 공존하는 동안 실제 메인 프로그램에 시스템 종료를 보내고 실제 돌아가기 및 취소 후 종료 컨트롤을 클릭하여 같은 작업과 토큰, 모든 종료 대기, 설치 전달 0회와 업그레이드 전 동일한 이전 설치에서의 일반 재시작을 확인합니다. 물리 데스크톱과 사람의 입력은 필요에 따라 별도 확인·기록하며 라이선스 검토와 릴리스 승인도 분리합니다.

두 세션 컴포넌트 회귀는 AppQuitGuard, DesktopIntegration과 전체 세션 라우팅을 통해 같은 종료 창으로 들어가 대기 중인 AES 작업의 돌아가기·취소와 종료 대기를 확인합니다. 관리 세션 자신의 비밀번호 또는 충돌 모달만 종료 확인에 의해 가려질 수 있으며 네이티브 QWidget 모달은 계속 종료를 차단합니다. 이 컴포넌트 검사는 업데이트 대기 중 전체 메인 프로그램의 시스템 종료 및 네이티브 설치 회귀와 별도로 기록합니다.

전체 Mac 제품 픽스처는 첫 시스템 종료 전에 같은 작업 세션의 비밀번호 창이 보이고 노출되어 있으며 해당 메인 창 소유이고 현재 앱 모달이며 작업과 비밀번호 토큰이 변하지 않았음을 실제로 관찰해야 합니다. Rust 비밀번호 요청만으로 지연 표시가 준비되었음을 증명하지 못합니다. 이 전제 충족 후 종료를 한 번만 보내고 실제 돌아가기, 모달 복원, 취소와 모든 종료 대기를 검증합니다. 시간 초과 시 정리 전에 진행을 고정하며 이후 정리 중 생성된 종료 결과가 실패를 덮어쓸 수 없습니다.

비공개 Windows 설치 회귀는 실제 Inno가 새 `xdzip.exe`를 복사한 뒤 다른 파일을 복사하기 전에 일시 중지하고 새 ID를 확인한 다음 실제 Qt 프로그램을 다시 실행합니다. 보이는 창이나 새 세션 없이 시작 게이트 종료 코드 11을 요구한 뒤 복사를 재개하고 기존 업그레이드 수용을 완료합니다. 관찰 핸들은 즉시 닫아 테스트가 설치 프로그램 게이트를 연장하지 않도록 합니다. 이전 버전과 새 버전은 모두 Qt 6.8.2를 사용하며 앱 패키지의 원자적 교체나 Qt 버전 간 마이그레이션을 입증하지 않습니다. 프로덕션 설치 프로그램 템플릿에는 일시 중지가 없습니다.

별도 이름의 비공개 Mac Qt 앱은 실제 정보 창, 두 세션 종료 대기, Sparkle, 서명된 app.zip과 새 빌드로의 재시작을 사용하며 피드·아카이브 변조와 취소를 다룹니다. 후보 발견에만 루프백 대체를 사용하고 공개 GitHub 매니페스트와 채널은 업데이트 코어 및 네트워크 회귀에서 별도 확인합니다. 테스트 키는 비공개 복사본에만 주입하며 프로덕션 리소스는 바뀌지 않습니다. 실제 실행의 증거만 통과로 기록할 수 있습니다.

Windows 도우미 전문 테스트는 실제 Inno 라이선스 페이지의 취소 버튼과 비공개 InitializeSetup 실패 주입도 실행합니다. 설치 로그로 해당 경로를 입증하고 이전 ID가 유지되며 재시작이 없고 설치 게이트가 해제되어야 합니다. Linux는 실제 pkexec로 정책 거부, 인증 에이전트 부재와 Cancelled를 반환하는 표준 D-Bus 에이전트를 각각 검증합니다. 취소 에이전트는 고정 테스트 UID, 작업과 요청만 처리하고 비밀번호를 받거나 권한을 부여하지 않습니다. 성공적 업그레이드는 기존 ZIP, TAR, GZip 기본 연결을 별도 확인합니다. 라이선스 버튼 자동 조작과 테스트 에이전트는 수동 라이선스 확인이나 시스템 데스크톱 인증 에이전트 수용을 의미하지 않습니다.

전체 Windows/Linux Qt 회귀는 실제로 Inno 초기화에 실패하는 패키지 또는 한 번 실패하는 postinst를 제출하여 실제 요청, 트랜잭션, 실패 영수증과 게이트 해제를 기록하고 실패 후 자동 재시작을 금지합니다. 복구는 일반 메인 프로그램을 시작합니다. 비공개 네트워크 팩터리가 null을 반환하여 기본 컨트롤러 생성자가 실제 기본 캐시에서 영수증을 읽도록 합니다. 복구 상태, 동일한 실제 설치 ID, 새 작업·설치 전달·자동 재시도가 없음, 설정과 ZIP/TAR/GZip 기본값 유지를 요구합니다. Linux postinst가 실패해도 새 파일이 이미 설치되었을 수 있으므로 이전 버전 유지라고 하지 않고 실제 새 버전과 dpkg 반구성 상태를 확인합니다. 픽스처만 APT 구성을 명시적으로 복구하고 별도 성공 시나리오를 재설정하며 이 테스트 작업을 제품 롤백으로 설명하지 않습니다.

전체 Mac 제품 회귀는 테스트 소유의 이전 앱 루트에 되돌릴 수 있는 UF_IMMUTABLE을 적용하여 종료 대기·커밋 경계의 취소와 실제 커밋 후 파일 시스템 거부를 구분합니다. 후자는 실제 설치 커밋, 스스로 종료한 정확한 도우미 PID와 해당 도우미의 권한 실패 로그를 기록해야 합니다. 전달 취소는 설치 실패를 대체할 수 없습니다. 소유 범위, UID, dev/inode와 원래 플래그를 확인한 후에만 플래그를 복원합니다. sudo를 사용하거나 설치 프로그램을 강제 종료하거나 결과를 조작하지 않습니다. 두 복구 사례 모두 이전 버전을 정상 시작해 영구 시도 기록을 읽습니다. 실제 Apple Silicon 아티팩트가 통과 여부를 입증합니다.

또 다른 전체 Mac 제품 체인은 두 개의 깨끗한 Release 소스 ID에서 실제 메인 프로그램을 빌드하고 정식 번들 ID, 설치 마커와 Alternate 문서 유형을 유지하여 일회용 러너의 자체 Applications 경로에 설치합니다. 이전 버전은 실제 정보 창과 UpdateController를 사용해 매니페스트 인증, Sparkle 설치와 종료 대기 후 전달을 수행합니다. 새 버전의 일반 시작은 설치 ID, 업데이트 영수증, 기본 구성 디렉터리, 설정과 알 수 없는 키, 단일 인스턴스 동작과 LaunchServices ZIP 기본 핸들러를 검증합니다. 비공개 전송은 고정 메타데이터 URL, 인증된 피드 URL과 정확한 아카이브 URL만 매핑하며 서명은 실제로 검증하고 SDK 없는 HTTPS는 별도입니다. 회귀는 원래 사용자의 HOME과 기본 구성 경로를 사용하며 재시작 복구를 테스트 경로 주입으로 대체하지 않습니다.
