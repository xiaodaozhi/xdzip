# 성능 설계와 측정

[English](../../design/performance.md) | [简体中文](../../zh-CN/design/performance.md) | [繁體中文](../../zh-TW/design/performance.md) | [日本語](../../ja-JP/design/performance.md) | 한국어 | [Français](../../fr-FR/design/performance.md) | [Deutsch](../../de-DE/design/performance.md) | [Español](../../es-ES/design/performance.md) | [Português (Brasil)](../../pt-BR/design/performance.md) | [Русский](../../ru-RU/design/performance.md)

XDZip은 인덱싱, 전송, 작업 실행과 이미지 미리 보기의 메모리 및 작업량을 각각 제한합니다. 아래 코드 한도는 구현 규칙입니다. 시간, 메모리 측정값과 처리량은 빌드와 작업 부하에 따라 달라집니다. 아래 참조 목표는 엔지니어링 목표입니다.

<a name="xdzip-limits-and-mechanisms-in-the-current-code"></a>

## 현재 코드의 한도와 메커니즘

| 영역 | 현재 동작과 비용 |
| --- | --- |
| 일반 단일 파일 ZIP/ZIP64 | 스트리밍 스캐너는 이름, 디렉터리와 읽기 예산 범위에서 최대 100만 개 물리 레코드를 허용한다. 활성 메타데이터가 64 MiB를 초과하거나 새 레코드로 상주 항목이 100,000개를 넘으면 레코드를 비공개 디스크 저장소로 옮긴다. 메타데이터 파일은 512 MiB로 제한되며 위치 표는 별도다. 탐색은 모든 데이터를 디코딩하는 대신 메타데이터를 검사한다. |
| 메모리와 디스크 쿼리 | 런타임은 현재 불변 결과 순서를 한 번 만든다. 디스크 경로는 최대 8 MiB의 정렬 런을 디스크에 저장한 후 토큰 순서로 병합한다. 이름과 정렬 저장은 제한된다. 캐시는 완전히 렌더링된 뷰나 무기한 쿼리 기록이 아니라 현재 쿼리를 담는다. |
| 탐색과 Qt 전송 | 디렉터리 트리는 32,768개 노드, 64개 깊이, 이름 4 MiB 예산을 가진다. 예산을 넘겨도 루트 탐색과 검색은 유지할 수 있다. 브리지는 페이지당 최대 128행과 이름 64 KiB를 보낸다. 큰 뷰는 최대 1,024행을 상주시키며 논리 행 수는 전체 결과를 포함한다. |
| 명령, 작업과 쓰기 | 메타데이터 스레드와 작업 스레드는 별도의 제한된 대기열을 사용한다. 무거운 데스크톱 작업은 한 번에 하나씩 허용한다. 디코딩 작업, 출력 바이트, 파일 확정과 워커 리소스는 각각 다르게 계산한다. 솔리드 및 스트리밍 형식은 선택 항목에 도달하기 전에 앞선 데이터를 읽거나 디코딩할 수 있다. |
| 미리 보기와 네이티브 워커 | 텍스트와 인코딩 이미지는 별도의 바이트 한도가 있다. 이미지 크기와 픽셀 수, 워커 실행과 썸네일 크기는 독립적으로 제한된다. 형식 워커는 자체 프로토콜 및 프로세스 한도를 사용한다. |

[디스크 인덱스 구현](../../../crates/xdzip-runtime/src/disk_index.rs), [대형 압축 파일 인덱싱](../engineering/large-index.md), [Qt/Rust 브리지 한도](qt-rust-bridge.md), [작업 허용](task-scheduling.md), [출력 예산](file-security.md), [미리 보기 예산](../engineering/content-preview.md)

메모리 비용에는 Qt, 글꼴, 렌더링과 모델, 압축 파일 메타데이터, 위치 표와 쿼리 버퍼, 디코더 상태, 자식 프로세스와 I/O 버퍼가 포함됩니다. 64 MiB 마이그레이션 기준은 메타데이터 임계값입니다. 프로세스 트리 메모리에는 그 인덱스 밖의 모든 것도 포함됩니다. 메타데이터 허용량이 커져도 추출 할당량이 늘어나거나 디스크 기반 세션에서 전체 압축 파일 검사와 편집이 가능해지지는 않습니다. 비공개 인덱스 쓰기와 추출 임시 준비는 별도의 디스크 비용입니다.

<a name="xdzip-measuring-the-current-implementation"></a>

## 현재 구현 측정

| 진입점 | 측정 또는 검증 내용 |
| --- | --- |
| `scripts/probe-large-index.py`와 `xdzip-m2-probe` | 자체 ZIP64를 생성하고 실제 스캐너, 정렬과 페이지 쿼리를 실행하며 단계와 저장량을 별도로 보고한다. 중복, 긴 이름과 디렉터리 구조를 포함하고 디스크 경로 도달 여부를 식별한다. |
| `scripts/measure-desktop.py`와 `xdzip-process-metrics` | 데스크톱 프로세스 트리, 시작과 탐색을 측정한다. 추출 옵션을 사용하면 실제 추출을 수행하고 출력 바이트를 독립적으로 검증한다. 렌더러, 빌드 식별 정보와 정확한 부하를 기록한다. |
| `scripts/run-performance-suite.py` | 시작, 안정적 유휴 상태와 탐색의 Release 관찰을 수집하고 자체 테스트 데이터에서 고정된 코어 프로브와 추출을 비교한다. 보고서는 빌드와 테스트 데이터 식별 정보를 기록한다. 비교는 관찰용이며 참조 기기 승인은 별도 조건이다. |
| `scripts/check-runtime-resources.py` | 프로브의 런타임 리소스와 글꼴 확인 기록을 검사한다. 해당 프로브의 리소스 식별과 범위를 입증하지만 상호작용 지연을 측정하지 않는다. |

[대형 인덱스 프로브](../../../scripts/probe-large-index.py), [데스크톱 측정](../../../scripts/measure-desktop.py), [성능 모음](../../../scripts/run-performance-suite.py), [리소스 프로브](../../../scripts/check-runtime-resources.py), [증거 수집](../../../developers/engineering/candidate-verification.md#performance-and-resource-evidence)

비교 시 커밋과 구성, 운영체제와 아키텍처, 렌더러, 하드웨어, 실행 횟수, 테스트 데이터, 장치 및 캐시 조건을 기록합니다. 콜드 시작과 반복 시작을 구분합니다. 측정이 지원하면 첫 상호작용, 압축 파일 검사, 쿼리 순서 지정, 페이지 전송과 화면 렌더링을 별도 단계로 보고합니다. 취소 응답과 실제 중단 및 정리를 구분합니다. 처리량 보고에서 입력, 디코딩 및 확정 바이트를 분리합니다.

프로세스 트리 도구는 Linux PSS, macOS 물리 점유량과 Windows 전용 커밋을 구분하여 표시하고 가능한 경우 RSS 또는 작업 집합도 보고합니다. 비슷한 조건에서 같은 지표를 비교합니다. 실제 패키지의 다운로드 크기와 설치 크기는 별도로 보고합니다. 오프스크린 시간과 프로토타입 실행은 각각의 조건만 설명합니다.

## 비교 테스트용 부하

| 부하 | 측정 내용 |
| --- | --- |
| B01/B08 빈 창, 유휴 상태와 테마 변경 | 시작과 프레임 시간, 유휴 CPU, 유지 메모리와 렌더러. |
| B02 100,000개 및 100만 개 ZIP 레코드 | 메타데이터 검사, 마이그레이션, 정렬, 페이지 조회와 별도의 메모리 및 디스크 비용. |
| B03/B04 큰 일반 파일 하나 또는 작은 파일 다수 | 처리량, 취소, 대상 작업, 동기화와 정리. 작은 파일은 파일 작업이 지배적일 수 있다. |
| B05/B06 고압축 또는 스트림 깊숙한 항목 | 할당량 처리와 선택 항목에 도달하기 전 추가 디코딩 작업. |
| B07 무거운 작업이 대기하는 동안 탐색 | 무거운 작업 하나가 실행되고 다른 하나가 대기할 때 검색 및 페이지 지연. |
| B09 포함된 워커와 전체 패키지 | 프로세스 트리 사용량, 프로토콜 비용, 다운로드 및 설치 크기. |

이들은 비교 시나리오입니다. 변경에 맞는 부하를 선택하고 크기와 해시가 기록된 프로젝트 소유 테스트 데이터를 사용합니다.

## 참조 목표와 예정 연구

기존 설계는 16 GiB 메모리, 로컬 SSD, 60 Hz 디스플레이, 시스템 글꼴, 실제 GPU와 Release 빌드를 갖춘 Apple Silicon을 참조합니다. 이 목표들은 비교 가능한 측정 후보이며 최신 릴리스나 다른 플랫폼의 결과를 주장하지 않습니다.

| 시나리오 | 설계 목표 |
| --- | --- |
| 빈 창 반복 시작 | 최소 30회 실행에서 상호작용 가능한 프레임까지 P95 최대 500 ms |
| 캐시된 ZIP 레코드 100,000개 열기 및 조회 | 메타데이터 준비 P95 최대 1 s, 인덱싱된 쿼리부터 표시까지 최대 80 ms |
| 웜 페이지 이동과 GUI 스케줄링 | 표시되는 페이지 이동 P95 최대 50 ms, GUI 스레드 연속 차단 최대 8 ms |
| 메모리 | 프로세스 트리 목표는 빈 상태 최대 150 MiB, 미리 보기와 디코딩 사전 없이 100,000개 항목 탐색 시 최대 256 MiB |
| 유휴 CPU | 안정화 후 논리 코어 하나의 평균 최대 0.5% |
| 취소 | 응답 P95 최대 50 ms, 로컬 협력 스트리밍 중단 최대 250 ms를 별도로 측정 |
| 추출과 배포 | 같은 부하와 I/O 설정에서 GUI와 코어를 비교하며 처리량 손실 설계 목표는 최대 10%. 단일 아키텍처 Mac 목표는 다운로드 최대 100 MiB, 설치 후 최대 250 MiB. |

블록 단위 병렬 추출, 지속적인 인덱스 재사용과 공유 CPU 토큰 스케줄러는 설계안으로 남아 있습니다. 동시성이나 저장 방식을 바꾸기 전에 현재 직렬 작업 경로와 메모리 및 디스크 경로를 프로파일링합니다. 어떤 비교에서도 동등한 바이트 검증, 취소와 안전한 게시를 유지합니다. [아키텍처 변화](architecture-evolution.md), [파일 게시](file-security.md)
