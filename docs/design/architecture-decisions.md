# xdzip: Architecture decision records

The initial records are dated 2026-10-11; later records state their own dates. Accepted means adopted by the design, not that implementation has been verified. When superseding a record, retain the original and append a new record.

## ADR-001: Qt Quick as the sole product interface

**Status: Accepted.**

Context: The product requires a modern desktop UI, consistent experience, and low resource use. Same-core prototypes for Slint, Tauri, and Qt Quick have been completed. Considering interface capabilities, consistency, and existing Linux software-rendering data, the project selected Qt Quick for the product stage; other platforms still require verification.

Decision: Qt Quick/QML + Qt Quick Controls 2 with thin C++ adaptation. Slint/Tauri remain historical experiments and are not packaged into the product.

Costs: Qt runtime, QML modules, cross-language builds, and licensing work. Mac/Windows input, accessibility, GPU, and deployment need additional tests. The 0.80 MiB prototype executable is not a complete Qt installer.

Reevaluation trigger: Qt cannot satisfy necessary functionality/licensing/security maintenance on target platforms and still misses core product budgets after actual optimization. Ordinary performance fluctuations do not trigger repeated framework selection.

## ADR-002: Rust owns all archive business logic

**Status: Accepted.**

Decision: Domain, index, plans, tasks, quotas, path policies, and format registry live in Rust. Qt represents state, authorizes system file selection, and conveys user decisions. Business tests require no Qt.

Alternatives: Connect libarchive/7zip directly to C++/QML or repeat control logic in each UI. This couples the core to platform UIs and prevents consistent security/cancellation verification. Rust does not eliminate native library security risks; relevant libraries may be isolated in workers.

Reevaluation trigger: If a platform API cannot be implemented reliably in Rust, allow a small platform C++ port without changing business ownership.

## ADR-003: Build-time cxx bridge

**Status: Accepted; integration requires M1 verification.**

Decision: Use a type-safe bridge generated by cxx inside the product and built from the same commit. Do not maintain a long-term handwritten C ABI or serialize JSON on hot paths. The bridge contains no Qt business logic.

Alternatives: Retain the experimental C ABI, generate QObjects with CXX-Qt, or connect the GUI and entire core over local IPC. cxx preserves explicit Qt model and thread boundaries without adding a QObject-generation framework in the first stage. The cost is maintaining the thin QObject layer and CMake/Cargo orchestration.

Non-promises: cxx does not provide dynamic binary compatibility across arbitrary Rust/Qt versions and does not generate a third-party format protocol.

Reevaluation trigger: M1 three-platform build/lifecycle verification fails or the adapter layer grows substantially. Evaluate CXX-Qt or an explicitly versioned C ABI through an ADR rather than switching silently.

## ADR-004: Separate built-in source SDK from external process protocol

**Status: Accepted; wire protocol is a draft.**

Decision: Built-in formats use Rust traits and Cargo features; external plugins use bounded CBOR IPC. The host unifies capabilities and I/O ports for both.

Rationale: The Rust dynamic-library ABI is unstable, and arbitrary in-process native plugins undermine crash isolation and resource governance. Wasm is not currently prioritized as a general format runtime because of migration, threading, seek, and performance-verification costs for existing native codecs; future use is not ruled out.

Costs: Protocol, broker, sandbox, and IPC overhead. Freeze the protocol only after two independent implementations interoperate.

## ADR-005: Host centrally controls actual file writes

**Status: Accepted.**

Decision: Backends write only to approved OutputSinks. The host controls actual paths, conflicts, staging, and commits. Do not directly invoke a library's general unpack into arbitrary directories unless its ports are fully verified as host-constrained.

Rationale: Independently implementing path protection per format easily produces inconsistencies; string checks alone cannot prevent links/races. The cost is implementing and fault-testing secure file layers on three platforms.

Non-promises: The host cannot prove malicious plugin output semantically correct or stop a malicious process already controlling the same user. Plugin trust and permissions must remain explicit.

## ADR-006: Commit extraction per file and new archives as a whole

**Status: Accepted.**

Decision: Each extracted file is staged and verified before publication; failed tasks may retain partial completion. New archives are written completely before publication. Do not overwrite by default.

Rationale: Merging into an existing directory cannot simply provide a truly atomic whole-directory transaction across platforms. Pretending to roll back the whole task could delete later user changes. Costs include detailed results and recovery logs, with cancellation semantics explained clearly.

Reevaluation trigger: A new “publish a wholly new directory” mode may be implemented separately under restricted conditions without changing existing-directory merge semantics.

## ADR-007: Bounded actors/worker pools and pushed events

**Status: Accepted.**

Decision: A lightweight scheduler decides state, bounded pools execute work, and Qt has a separate event receiver thread. Coalesce progress, deliver terminal states, and provide independent control admission for cancellation and shutdown.

Alternatives: Synchronous GUI calls, one thread per file, unlimited Tokio/spawn_blocking, or continuous polling. Archive work is primarily synchronous CPU/I/O; do not introduce unbounded tasks merely because something is called asynchronous. Actual future network I/O may use an asynchronous runtime locally.

Costs: Explicit backpressure, shutdown, and resource leases. Benefits: low idle overhead and a GUI that tasks cannot overwhelm.

## ADR-008: Capability-driven, limited first-version formats

**Status: Accepted.**

Decision: v0.1 uses ZIP Store/Deflate and TAR/GZIP; encryption, split volumes, RAR, 7z, and additional algorithms are verified individually. The UI does not infer full support from extensions.

Rationale: A format name cannot describe all actual features. The initial format table is shorter, but honest and verifiable for users.

## ADR-009: Separate small product data from user content

**Status: Accepted.**

Decision: Settings, temporary indexes, transaction logs, and extension manifests have separate lifecycles. No telemetry by default, no persistent passwords, and no archive-index caching across launches.

Costs: Multiple schemas and cleanup rules. Reconsidering cross-launch indexes requires new source identity, invalidation, privacy, and capacity design.

## ADR-010: Full distribution and licensing are architecture gates

**Status: Accepted.**

Decision: Deploy Qt dynamically by default and review actual module licenses. Installation size includes runtimes. Signing, SBOM, and replacement/source obligations enter release checks.

Alternatives: Compare only executables or add LICENSE just before release. Neither proves the product is small or legally distributable.

Costs: Ongoing deployment and license maintenance. Static Qt builds or store distribution require a separate ADR and license review; a size optimization PR cannot change them incidentally.

## ADR-011: Initial support scope and personal-project maintenance policy

**Status: Accepted on 2026-10-19, explicitly approved by the project owner.**

Decision: Initially support macOS 14 and later on Apple Silicon arm64, maintained Windows 11 x86_64, and Ubuntu 24.04 LTS x86_64 with X11 and glibc 2.39 or later. Prioritize only the latest public version, handle feedback on a best-effort basis without a fixed response-time commitment, use manual updates for v0.1, and keep development previews experimental. See the [support policy](../engineering/support-policy.md).

Rationale: Existing native builds, installers, and runtime dependencies bound the scope, narrowing unverified OS and architecture promises from older designs to match a personal open-source project's maintenance capacity. The cost is no promise for Intel Mac, Windows 10, ARM64 Windows/Linux, other distributions, or Wayland. Expanding scope requires implementation and actual verification first.

Boundary: Personal GitHub open-source distribution does not require paid developer accounts, signing certificates, Developer ID, or notarization. macOS retains necessary ad-hoc integrity. This policy does not replace license provenance and package verification or imply compatibility with every future OS version.

## ADR-012: Migrate each format to independent Rust format and compression algorithms

**Status: Accepted on 2026-10-25, explicitly approved for implementation by the project owner. Supersedes the long-term choice of third-party format engines; does not mean migration is complete.**

Decision: Use independent Rust implementations for format parsing and compression/decompression algorithms; general cryptography, character encoding, and system foundation libraries are allowed. Define behavior specifications from official specifications first, then implement independently; do not translate reference source line by line or copy it with renamed identifiers. Developers who have seen source do not claim strict clean-room development. Insufficient sources and licensing restrictions require separate review, particularly no RAR encoder development.

Accept and replace ZIP, TAR, TAR.GZ, 7z, RAR, CAB, ISO, and UDF individually according to existing capabilities. Retain the current implementation for formats that have not passed; do not silently fall back or expand read-only RAR/CAB/ISO/UDF scope. Reuse shared compression algorithms. Names, identities, authorized I/O, resources, cancellation, and commits remain under the Rust host; worker isolation does not disappear because the implementation changes to Rust.

Costs: Independently maintaining compatibility, security, performance, fuzzing, and algorithms over the long term. Third-party references may be used in tests, but migrated formats must remove the corresponding engines from product dependencies and delivery files. See the [in-house backend contract](../engineering/independent-rust-codecs.md) for sources and interface rules; progress and actual acceptance are tracked in [#45](https://github.com/xiaodaozhi/xdzip/issues/45).
