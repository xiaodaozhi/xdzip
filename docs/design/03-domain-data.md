# xdzip: 03 Domain model and data design

## 1. Identity and versioning

| Type | Meaning | Rules |
|---|---|---|
| `SessionId` | Archive session in the current runtime | Generated by the runtime, not derived from the path |
| `SourceRevision` | Version of an opened source | Bound to the open handle, file identity, size, modification information, and available change indicators |
| `EntryId` | One physical archive record | Stable within a session; duplicate paths still have different IDs |
| `QueryId` / `QueryGeneration` | Query snapshot and UI request generation | The generation discards stale responses; QueryId is bound to the actual result version |
| `PlanId` / `PlanRevision` | Prepared operation plan | A changed destination, policy, or source requires a new revision; an old plan cannot start |
| `TaskId` / `RequestId` | Background task and call correlation | Not reused; logs may refer to them anonymously |
| `ConflictId` / `PromptId` | Pending user decision | Applies only to the task's current decision point and can time out or expire |

IDs are non-interpretable integers or opaque values passed as 64-bit numbers across the bridge. QML does not represent 64-bit IDs directly as floating-point numbers; C++ provides opaque string/value wrappers to avoid JavaScript precision loss. A row number is a view position, not an identity.

Source version detection is a best-effort consistency guard; holding a file handle does not provide a static snapshot. Check for changes before reading, at key points during reading, and before committing. If reliable change detection is unavailable or the user requires strong consistency, first make a quota-limited source snapshot. On detecting a change, stop the task, retain committed items, and require reopening and replanning.

## 2. Entry model

`ArchiveEntry` contains an ID, parent ID, archive record ordinal, raw path bytes, display path, type, known/unknown compressed and uncompressed sizes, time and precision, checksum type, encryption flag, attributes, scan ordinal, and safety flags. A symbolic-link target is stored separately and must not be automatically restored as regular file content.

Sizes use `Option<u64>` for unknown values; zero does not mean unknown. Times include their source and time zone/precision; display “Unknown” when they cannot be determined. Regular files, explicit directories, synthetic directories, symbolic links, and special records are represented. The MVP outputs only regular files and directories; for the rest, it displays the reason and refuses restoration.

Preserve raw path bytes. Display follows format encoding rules where possible; UTF-8 flags, Unicode extensions, and encoding selection are handled according to backend capabilities. Invalid bytes are safely replaced/escaped in the UI. Do not write using the replacement name directly, since two different raw names could collide. Users may select a legacy encoding for the session, regenerating display/output candidates and invalidating old plans.

Records with the same name are not deduplicated. A synthetic directory has its own identity and contains the set of actual descendants. Archive safety flags such as `absolute_path`, `parent_escape`, and `unsupported_special` do not disappear when the display is normalized. The core retains the `EntryId -> raw_record` mapping; extensions must use that ID/record token to read content.

## 3. Index state

States are `Detecting -> Scanning -> Ready`, with `Failed` or `Closed` reachable from any stage. Scanning may produce incremental batches and `ScanProgress`; the number of discovered rows is not the total. Query results have `complete: bool` and `indexed_count`; until completion, the total match count is a lower bound.

Partial results default to discovery/path order, and scanned content can be queried. Final ordering and complete counts create a new snapshot after scanning finishes. The UI explicitly identifies “scanned content”; partial results cannot be used for the default “Extract all.” Streaming backends must preserve the location of scan errors and must not mark an early EOF as Ready.

Index fields are divided into common columns and details. The list page does not copy raw paths, comments, or every extended attribute; full records are read when details are opened. Long names, large entry counts, comments, and extra fields have separate budgets; see [constants](glossary.md).

## 4. Queries and pagination

`QuerySpec` includes directory scope, plain-text search, sort field, direction, and hidden-item options. The first version has no regular expressions to avoid unexpected complexity. Search uses the display path by default; size/type filters are separate explicit fields. Matching uses a Unicode-normalized, case-folded copy without changing the original name. Local sorting uses a deterministic comparator with EntryId as the final tie-breaker.

Creating a query snapshot can take time and therefore returns asynchronously. In `PageRequest {query_id, generation, offset, limit}`, offset is 64-bit and limit is at most 256. A page contains QueryId, generation, snapshot revision, row data, and completeness. A single Qt model's row count is limited by `int`; use segmented views above that limit. Do not narrow values or overflow the total.

Data updates do not change the row identities of an existing QuerySnapshot in place. A new scan batch, encoding change, filter, or sort creates a new version. Identical queries may share a read-only index. Retain at most the current version and old versions still in use; reclaim old snapshots after their references are released. The page-cache key is QueryId+revision+offset, not offset alone.

## 5. Selection

`SelectionState` belongs to a session. The core stores a selection expression instead of downloading every row each time. It supports explicit ID sets, QuerySnapshot ranges, and “all results minus exclusions.” Large ranges use intervals/bitmaps and provide counts, so the UI need not hold a million IDs.

Ctrl/⌘ toggles one item; a Shift range uses an anchor in the current QueryId. A query change clears the anchor but retains selected identities. The toolbar reports filtered-out selections as “N selected, M in the current view.” Directory selections expand descendants when a plan is built and deduplicate physical EntryIds to avoid extracting twice.

The UI may initially show a lightweight local selection state and confirm it when the core returns SelectionRevision. Every selection command carries the current QueryId. A stale range command returns `stale_query`; it must not select the wrong entries using new row numbers.

## 6. Operation plans

`OperationPlan` fixes the operation type, source version, selection snapshot, backend version/capabilities, authorized destination reference, output mapping, conflict policy, quotas, compression parameters, estimated work, and risk summary. Plans do not store plaintext passwords; secrets are passed through separate short-lived tokens.

Plan construction may defer storing large numbers of entries, but the input set must not change with UI selection after the task starts. Starting checks the source, destination authorization, plan revision, and backend version; an expired plan returns `stale_plan`. By default, only one task may start for a PlanRevision. A duplicate RequestId returns the already created TaskId instead of writing again.

“Compression inputs” are not archive entries: use `InputSourceId` and a prescanned tree, recording handle authorization and file versions. Scanning the input tree does not follow links; it detects input changes and excludes output and staging directories. Permission restoration allows only ordinary read/write bits; it does not restore setuid, setgid, device nodes, or untrusted extended attributes.

## 7. Results and persistence

`TaskResult` contains the state, completed/skipped/failed counts, actual bytes, a committed-item list or paged result handle, cleanup status, integrity status, and a bounded sample of errors. Success means every required item completed and passed the declared checks. A policy that permits skipping yields success with skips shown in the summary. Any failure not permitted by user policy makes the task Failed, although the summary may still contain completed files.

Transaction logs record only relative mappings needed for recovery, the random working directory, file identities, temporary-file states, and commit states. The log format is versioned, length-bounded, and treated as untrusted input. Restarting does not automatically resume writing or delete unfamiliar files; see [07](07-file-security.md) for recovery.

User settings, archive indexes, transaction logs, and extension manifests have different schemas; one SQLite database must not carry all their lifetimes. Passwords never enter them.

By default, keep at most eight unstarted plans and release the old plan when replanning. Plan mappings and paged results share a separate 64 MiB hot-data budget. In v0.1, exceeding it returns an explicit resource error; M6 moves large mappings/results to a disk backend. By default, task history keeps the latest 100 lightweight summaries; complete results are reclaimed when closed by the user or expired. Data referenced by active tasks cannot be cleaned up early. All caches include selection ranges and query snapshots; accounting must not count only list pages while omitting plan memory.
