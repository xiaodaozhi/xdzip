# Instaladores e associações de arquivos

No Windows 11 x64, procure **XDZip** na Microsoft Store para instalar ou atualizar a edição Store. Baixe o EXE ou ZIP portátil do Windows, os pacotes macOS e os pacotes Linux na [versão mais recente do GitHub](https://github.com/xiaodaozhi/xdzip/releases/latest). Os dois canais publicam independentemente. Consulte a página ou as notas da versão que está instalando.

O Windows MSIX declara as mesmas extensões como candidatas a Abrir com no manifesto do pacote, sem tomar a escolha padrão do usuário. Sua página de associações lista todos os tipos elegíveis com controles desabilitados. Os padrões atuais aparecem nas configurações do Windows. «Abrir configurações de aplicativos padrão» navega ao pacote atual usando seu `registeredAUMID`. Se a consulta de identidade falhar, abre o seletor geral de padrões. O pacote não lê os registros da edição instalada comum como estado do pacote nem grava valores UserChoice. Ativação real de arquivos, ícones, coexistência e desinstalação exigem aceitação no sistema de destino. Consulte [builds MSIX](../../engineering/developer-build.md#windows-msix-实验构建).

Consulte a [especificação de ícones de associação](../visual/file-association-icons.md) para imagens por formato e mapeamentos por plataforma. O Linux mantém os ícones MIME do sistema. A instalação não altera padrões nem o escopo de registro existente.

As associações MSIX referenciam recursos PNG por formato extraídos dos mesmos quadros ICO canônicos usados pelo instalador comum do Windows. ZIP, 7z, RAR e demais formatos mapeados mantêm as imagens de documento, perfis de tamanho e margens transparentes. O ícone do aplicativo tem recursos separados de tamanho de destino sem placa. Ambos os conjuntos são indexados no `resources.pri` do pacote; alterar a imagem da página da Store não substitui esses ícones instalados. O Windows controla o cache de ícones e a seleção do manipulador padrão, e a instalação nunca altera essa seleção automaticamente.

Pacotes de desktop desde `v0.2.0` e builds atuais de fonte colocam a CLI em um diretório `cli/` separado, ou `Contents/Helpers/cli/` no macOS, preservando pontos de entrada existentes da GUI e de associação. Assets de versões anteriores não recebem esse recurso retroativamente. O instalador Windows oferece uma opção PATH por usuário de adesão voluntária e detecta conflitos de comandos de mesmo nome; a desinstalação revoga apenas seu diretório de instalação. Mac/Linux executam explicitamente `setup` da CLI privada. Pacotes CLI independentes também usam `setup` para instalar diretórios de versão em nível de usuário e um lançador estável, sem alterar a configuração do shell. `setup --remove` revoga o registro e mantém os diretórios de versão para inspeção. Consulte o [contrato de instalação da CLI](command-line.md#xdzip-build-and-command-installation).

Os comandos de empacotamento abaixo produzem artefatos experimentais de desenvolvimento. Os pacotes oficiais do GitHub seguem o [protocolo de lançamento](release-protocol.md), e os pacotes da Store usam o [workflow MSIX](../../engineering/developer-build.md#microsoft-store-msix). Downloads diretos para macOS usam assinatura ad-hoc de integridade sem Developer ID ou notarização. Consulte a [política de suporte](support-policy.md) para os sistemas suportados.

Builds atuais de fonte usam `xiaodaozhi` como publicador do instalador Windows, mantenedor do pacote Linux e fornecedor da política de atualização. Esses metadados não substituem assinatura com certificado de publicador; lançamentos existentes mantêm os metadados originais.

Para atualizações manuais no macOS, prefira o DMG correspondente do Release. Com app.zip, primeiro extraia e mova xdzip.app para fora de Downloads, encerre a versão antiga em execução e depois substitua a cópia em Aplicativos. Baixar não é instalar; um pacote não notarizado pode gerar avisos do sistema. Consulte o [contrato de atualização](software-update.md) para as condições de fallback.

Consulte o [contrato de ações do gerenciador de arquivos](shell-actions.md) para menus de contexto, host independente de operações e ciclo de vida dos registros próprios. As ações de contexto não abrem a janela principal de navegação nem abrem por padrão a pasta de destino ao concluir.

## Ponto de entrada compartilhado de build

Consulte o [guia de build para desenvolvedores](../../engineering/developer-build.md) para preparar o ambiente e seguir a ordem. Após build limpo e teste do mesmo commit, use `python3 scripts/desktop.py prepare --packaging` para preparar materiais fixados e execute package e verify. Não use o script completo de CI diretamente no desenvolvimento rotineiro.

`package --kind runtime|installer|all` de Windows/Linux compartilha uma cadeia de implantação e auditoria, com `all` como padrão. runtime primeiro gera o diretório implantado; installer é criado a partir do runtime verificado no mesmo output-dir e o Linux também cria tar.gz. O macOS suporta apenas DMG de desenvolvimento local `all`. Artefatos e recibos ficam no output-dir informado, por padrão build/package. A preparação pode baixar ferramentas e materiais de empacotamento fixados, mas não instala xdzip nem instala automaticamente compiladores ou SDKs do sistema. Windows prepara CRT/Inno Setup, Linux exige patchelf e ferramentas Debian preinstalados e Mac usa ferramentas de implantação do sistema e integridade ad-hoc.

O `verify` comum verifica runtimes e pacotes existentes. Windows limpa caminhos de busca do SDK em cópia isolada, Linux usa contêiner isolado de runtime e Mac verifica realocação DMG e Cocoa/Metal. Por padrão não executa ciclos de instalação, upgrade/rollback ou associação nem grava padrões do usuário. Os mecanismos de instalação e verificações de CI descartável abaixo são barreiras separadas; o sucesso do runtime não os substitui.

## Windows

O instalador apresenta o contrato original do runtime Microsoft VC++ incluído no pacote. A página de licença identifica os componentes aplicáveis e exige aceitação, depois exibe Windows-runtime-NOTICE.txt em chinês e inglês. Pacotes portáteis incluem o mesmo texto original e explicação. O código original do projeto continua sob Apache-2.0; as licenças originais e direitos de substituição do Qt e demais componentes não mudam. Verifique hashes e descrições completas antes de compilar; anexos de materiais mantêm o mesmo texto. Consulte [licenciamento Windows](windows-licensing.md).

Pacotes portáteis e instaladores usam o mesmo diretório implantado. [deploy_windows.py](../../../scripts/deploy_windows.py) chama windeployqt e segue a política fixada de Qt Quick Basic para remover FluentWinUI3, Fusion, Imagine, Material, Universal, Windows, NativeStyle/Effects referenciados somente por estilos, qmltooling e .qmltypes. Basic, Controls impl, Templates, QML de runtime e qmldir permanecem; Qt Widgets qmodernwindowsstyle continua atendendo controles nativos. Novos diretórios de implantação não contêm DXC, DXIL ou D3DCompiler; a implantação falha se esses nomes aparecerem em qualquer local. `opengl32sw.dll` não é incluído em novas implantações. Uma cópia existente na raiz é removida em preparação controlada; resíduos de mesmo nome em outros locais fazem a implantação falhar. Adicionar novo estilo ou funcionalidade Effects exige atualizar a política e verificar novamente.

Qt Quick usa Direct3D 11 por padrão no Windows. Com hardware ou drivers insuficientes, o Qt pode recorrer ao Direct3D WARP; isso é distinto de OpenGL por software. Novos pacotes não prometem fallback Mesa por software via `QT_OPENGL=software` ou backend OpenGL. Pacotes históricos e seus materiais de licença permanecem inalterados. A [documentação de gráficos Windows do Qt](https://doc.qt.io/qt-6.8/windows-graphics.html) descreve dispositivos padrão e dispositivos de software solicitados explicitamente.

O VC++ é implantado junto ao aplicativo usando o runtime oficial Microsoft x64 14.44.35211 das [fontes e hashes fixados](../../../scripts/windows-runtime.json). O [script de preparação](../../../scripts/prepare-windows-runtime.py) extrai com ferramentas WiX fixadas e verifica cada DLL e texto de licença sem executar instaladores EXE/MSI nem copiar de System32. São entregues DLLs MSVCP/VCRUNTIME necessárias, licenças e proveniência; ferramentas, CAB, MSI e o instalador vc_redist não executado não entram no produto. Windows 10/11 fornece UCRT. Runtimes locais ao aplicativo devem ser mantidos com atualizações do produto; não se pode depender de atualizações de runtime do sistema para substituí-los. Consulte os [métodos de implantação Microsoft](https://learn.microsoft.com/en-us/cpp/windows/choosing-a-deployment-method).

A [regressão de implantação](../../../scripts/test-windows-deployment.py) verifica limites de remoção e runtime ausente. A [verificação real do runtime](../../../scripts/verify_windows_runtime.py) rejeita DLLs de OpenGL por software, adiciona DLLs de teste a uma cópia isolada, limpa caminhos de busca do SDK e verifica traduções do sistema, reinício de configurações, barra de título nativa e inicialização bilíngue. Após limpar substituições de renderização, verifica a inicialização padrão do grafo de cena D3D11 e solicita WARP explicitamente, verificando o dispositivo de software Microsoft realmente selecionado. Solicitações explícitas não estabelecem fallback automático em falhas nem substituem aceitação visual manual. Arquivos de teste não entram no diretório do produto; isso não substitui aceitação de instalação, upgrade e desinstalação em Windows limpo.

build-windows-installer.py aceita apenas auditoria deployed de build limpo e verifica novamente o SHA-256 de cada arquivo. Consulte a [configuração da cadeia de ferramentas](../../../scripts/installer-toolchain.json) para Inno Setup 6.7.3 fixado, hash do instalador oficial, commit de fonte, recursos de chinês simplificado e tradicional e texto de licença. O compilador não entra no produto; avisos incluem o texto de licença. O assistente suporta os dez idiomas do registro compartilhado.

O instalador usa AppId fixo e PrivilegesRequired=lowest e instala por padrão em LocalAppData/Programs/xdzip do usuário atual sem direitos de administrador. O executável principal é xdzip.exe na raiz de instalação, com bibliotecas Qt ao lado; plugins, QML, traduções e avisos mantêm os subdiretórios necessários. Atalhos, associações e ícones de desinstalação apontam para a raiz, sem hierarquia de produto versions/hash de commit. Hashes de commit e binários permanecem nos recibos de build e instalação, não nos caminhos de instalação. O [log cumulativo de desinstalação](https://jrsoftware.org/ishelp/topic_appendnotes.htm) do Inno Setup registra arquivos pertencentes a cada instalação sem excluir extras recursivamente. Configurações e itens recentes permanecem nos diretórios existentes do usuário e não são removidos pelo instalador.

A nova estrutura grava um install-manifest.txt limitado com caminhos relativos auditados e SHA-256. Antes do upgrade, valide caminhos, duplicatas e tamanhos do manifesto antigo; rejeite escapes de caminho, aliases de dispositivo e pontos de reanálise nos caminhos de limpeza. Se arquivos a retirar foram modificados ou não podem ser verificados, interrompa a instalação antes de gravar. Após instalação bem-sucedida, limpe apenas arquivos listados no manifesto antigo que não são mais entregues e ainda correspondem ao hash; remova apenas diretórios vazios e preserve extras. Mesmo eventos repetidos de conclusão na mesma instalação acionam a limpeza uma vez. Arquivos alterados ou mantidos em uso durante a limpeza permanecem com registro de nova tentativa e código de saída não zero 20. Falha ao gravar esse registro exige reparo manual; não se alega recuperação transacional ou segurança contra perda de energia. A instalação por usuário pressupõe que processos externos não modifiquem o diretório simultaneamente; reverificações de caminho e hash não são isolamento contra corridas maliciosas baseado em handles.

Estruturas existentes com diretórios de versão recebem upgrade direto. Comandos de inicialização e atalhos passam à raiz enquanto locais de configurações e itens recentes permanecem. O instalador antigo não entregava manifesto de propriedade separado, portanto diretórios históricos versions/ permanecem até a desinstalação comum; o log cumulativo do Inno limpa arquivos originalmente registrados sem excluir diretórios recursivamente. Arquivos adicionados pelo usuário permanecem. O rollback pode reinstalar uma versão anterior escolhida; fixtures QA antigos mantêm estruturas históricas e depois podem receber upgrade novamente para a estrutura de raiz. Instalação nova não cria versions/. Isso não inclui eliminação completa automática do diretório de instalação antigo.

O produto mantém o mutex nomeado `Local\xdzip.desktop.running` durante todo seu ciclo de vida. [AppMutex](https://jrsoftware.org/ishelp/topic_setup_appmutex.htm) bloqueia instalação/desinstalação, com CloseApplications=no e sem encerrar o aplicativo à força. Falha na criação do handle FFI impede a inicialização; o fechamento do processo o libera. A saída de tarefas continua usando a decisão existente e a barreira de finalização Rust.

O instalador comum do Windows registra candidatos de arquivo em HKCU. Ele grava ProgIDs próprios, duas entradas Applications próprias, Capabilities, RegisteredApplications e valores OpenWithProgids próprios. Não altera HKLM, padrões de extensão, UserChoice/UserChoiceLatest protegidos ou candidatos de outros aplicativos. Cada sufixo registrado tem um ProgID como `xdzip.Archive.ZIP` e um ICO atribuído. O antigo `xdzip.Archive` mantém seu comando de abertura direta e fica oculto em Abrir com junto a `Applications/xdzip.exe`. O upgrade remove suas recomendações antigas preservando compatibilidade com um padrão existente. O Windows mapeia um nome composto como `.tar.gz` pela extensão final para escolher o ícone.

Na inicialização e após uma mudança de idioma bem-sucedida, o aplicativo instalado comum sincroniza descrições de nove ProgIDs principais: ZIP, TAR, TGZ, GZ, 7Z, RAR, CAB, ISO e UDF. O instalador escolhe descrições usando o idioma salvo do aplicativo ou, em modo automático, o idioma de exibição do sistema. O idioma do assistente é independente. Antes da sincronização ao vivo, o aplicativo verifica identidade de instalação, localização do executável, manifesto, lançador de associação e os nove comandos de abertura existentes. Registros ausentes ou divergentes não são alterados. Gravações parciais podem ser repetidas no próximo início normal. Processos portáteis, de desenvolvimento e de teste com configurações isoladas não executam essa sincronização. Outros sufixos registrados mantêm descrições fornecidas pelo instalador. O cache do Explorer e o padrão escolhido podem afetar a exibição.

A CI Windows descartável verifica a sincronização de descrições na inicialização do produto instalado e a troca em execução entre chinês simplificado e inglês. Usa cópia portátil e processo com configurações isoladas para verificar que não há gravações e confere que os nove ícones, comandos, outros candidatos e padrões permanecem inalterados. Essa verificação automática não substitui a aceitação manual de exibição no Explorer ou nas Configurações.

Comandos entre aspas de todos os ProgIDs de formato iniciam `xdzip-association.exe -- "%1"`; seu registro Applications contém SupportedTypes completo para que Abrir com mostre uma única entrada xdzip. O lançador incorpora o mesmo ICO de aplicativo da marca e recursos distintos OriginalFilename e versão do produto. Verifique ícones do aplicativo separadamente dos ícones de documento por formato; DefaultIcon do documento não substitui recursos de aplicativo do executável. O pequeno lançador GUI aceita um argumento de arquivo, inicializa COM em apartamento de thread única em sua própria thread e delega o comando de abertura existente por ShellExecuteEx com classe explícita `xdzip.Archive` sem interpretador de comandos; libera COM após a chamada. Rollback antigo atualiza a entrada compartilhada, portanto candidatos por formato continuam apontando para o programa restaurado. Falha de inicialização COM, ponto de entrada ausente, argumentos inválidos ou rejeição do sistema retornam valor não zero sem tentar outro aplicativo ou mudar padrões. Isso depende de a instalação de rollback manter o lançador no diretório atual; instalação/rollback e desinstalação cumulativa exigem testes reais.

O instalador define `AllowSilentDefaultTakeOver` como REG_NONE no ProgID compartilhado e nos ProgIDs específicos de formato registrados. O Windows ainda pode oferecê-los como candidatos explícitos de Abrir com. O instalador usa uma chamada nativa limitada ao registro para definir o valor em chaves próprias já criadas. Falha interrompe a instalação e libera os handles. Consulte as [convenções ProgID do Windows](https://learn.microsoft.com/en-us/windows/win32/shell/fa-progids).

O instalador comum e o MSIX geram seus candidatos Windows de Abrir com a partir do [registro de formatos](format-registry.md). Esse mapeamento cobre ZIP, TAR, TGZ, GZ, 7z, RAR, CAB, ISO e UDF principais e sufixos registrados adicionais. `.gz` pode ser encaminhado para GZIP independente ou TAR.GZ conforme o conteúdo. Os genéricos `.img`, `.001` e `.rNN` ficam reservados à abertura explícita ou a pontos de entrada suportados. A associação oferece ao sistema uma rota para xdzip. O leitor continua examinando o arquivo e aplicando os requisitos de formato e origem da operação.

## Ubuntu 24.04

build-linux-installer.py cria .deb a partir do mesmo diretório verificado. Diretórios privados de preparação são diferenciados pelo caminho de saída, permitindo reconstruir o mesmo nome de pacote em diferentes diretórios candidatos sem sobrescrever preparações existentes. O pacote se chama xdzip, a versão vincula canal e commit do produto e a arquitetura é amd64. Dependências do sistema vêm dos manifestos reais de implantação mais ferramentas desktop-database e de bloqueio; glibc é no mínimo 2.39. Qt/QML/plugins e avisos ficam em /opt/xdzip/versions/; /usr/bin/xdzip é uma entrada de encaminhamento com destino fixo entre aspas. dpkg substitui e remove arquivos de pacotes antigos; rollback exige manter o .deb original.

O [xdzip.desktop](../../../apps/desktop/packaging/linux/xdzip.desktop) instalado declara os candidatos MIME do pacote. Incluem ZIP e aliases selecionados, TAR e TAR filtrado, fluxos de compressão independentes, formatos de arquivo como 7z, RAR e CAB e imagens ISO/UDF. `%f` solicita inicialização de um arquivo e `--` marca o limite de argumentos. O pacote fornece declaração MIME para `*.udf` e não altera tipos genéricos de imagem e binário. Instalação e remoção atualizam bancos MIME e de desktop sem reescrever `mimeapps.list`, mudar padrões do usuário ou substituir ícones MIME do sistema. A desinstalação remove lançadores, ícones e arquivos de runtime próprios e preserva configurações do usuário.

O DEB instala sua [entrada de catálogo AppStream](../../../apps/desktop/packaging/linux/xdzip-local.yml) em `/var/lib/swcatalog/yaml/xdzip-local.yml`, caminho legível pelo Ubuntu App Center. A entrada associa o nome do pacote `xdzip` a `xdzip.desktop` para que o pacote instalado possa aparecer na lista de aplicativos. O dpkg remove o arquivo de catálogo ao desinstalar XDZip.

O produto instalado mantém um flock compartilhado em /run/xdzip/usage.lock. Scripts de manutenção primeiro obtêm bloqueio exclusivo sem espera e falham se houver processo ativo. Os scripts definem uma barreira de instalação em /run/xdzip de propriedade do root; o produto verifica novamente após adquirir seu bloqueio para evitar iniciar entre hooks do dpkg. Links simbólicos ou proprietário/permissões incorretos são rejeitados; fechar QFile libera o bloqueio. tmpfiles.d prepara o bloqueio de runtime na inicialização do sistema. Isso não afeta aplicativos de desenvolvimento SDK.

Caminhos de sucesso e de aborto do dpkg limpam a barreira. Interrupção ou perda de energia pode deixar uma transação inacabada; execute sudo dpkg --configure -a e corrija o erro real. Não conseguir iniciar não é sucesso de instalação. Scripts não limpam diretórios de usuário recursivamente; artefatos são gerados apenas em build/ ou CI.

## macOS e abertura de arquivos

O aplicativo principal e o pacote entregue declaram documentos e ICNS como Viewer/Alternate no Info.plist, [sem reivindicar propriedade padrão](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html). Builds de desenvolvimento e teste usam Viewer/None por padrão e não entram nos candidatos Abrir com do sistema. Pacotes principais de desenvolvimento ou builds de entrega devem definir explicitamente `-DXDZIP_MACOS_HANDLER_RANK=Alternate`. Usuários e Launch Services determinam padrões; o aplicativo não os altera ativamente. Limpe registros temporários de cópias de verificação de desenvolvimento conforme o [método de manutenção Mac](macos-deployment.md), preservando aplicativos e padrões existentes.

CAB, ISO e UDF usam o mesmo papel Viewer. ISO usa `public.iso-image`. O aplicativo não reivindica `.img` nem o genérico `public.disk-image`. Viewer descreve a associação Launch Services, enquanto o [backend de formatos](native-codecs.md) determina as operações disponíveis. O [perfil de criação ISO](iso-creation.md) separado pode gravar novas imagens.

As declarações de documentos cobrem as extensões finais de todos os candidatos de shell no [registro de formatos](format-registry.md) e usam o ICNS correspondente do bundle. Sufixos compostos compartilham o tipo da extensão final. Por exemplo, `.tar.gz` e `.gz` compartilham o padrão GZIP, enquanto `.tgz` usa o tipo TAR compactado do sistema. Cache do Finder, padrão escolhido e reconhecimento de tipos do sistema afetam a exibição real.

Os tipos importados RAR, CAB e UDF do macOS devem estar em conformidade com `public.data` para identificar arquivos reais. CAB declara tanto o tipo de sistema `com.microsoft.cab` quanto o de compatibilidade `com.microsoft.cab-archive`; Configurações consulta e altera o tipo preferido real quando for um deles, caso contrário usa o identificador de compatibilidade. O Viewer UDF declara a extensão `.udf` sem `LSItemContentTypes` para que arquivos reais encontrem um candidato mesmo se uma declaração UTI inválida de instalação antiga ainda for usada. A Apple descontinuou essa [chave de declaração de extensão](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html); continue verificando-a nas versões macOS suportadas. Configurações consulta e altera o tipo `.udf` realmente reconhecido, usando o identificador existente quando indisponível. Instalação ou registro não substitui ativamente padrões existentes. Quando não havia manipulador, o Launch Services pode resolver um novo candidato como manipulador atual por [regras implícitas](https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/LaunchServicesConcepts/LSCGlossary/LSCGlossary.html). A remoção do registro temporário deve restaurar o estado original; essa resolução não significa que o aplicativo gravou preferências do usuário.

FileOpenRouter recebe [QFileOpenEvent](https://doc.qt.io/qt-6.8/qfileopenevent.html) antes do QML, aceita apenas arquivos locais e reutiliza o roteamento existente de abertura e ativação. Argumentos de linha de comando da GUI após `--` são caminhos de arquivo, evitando confusão com flags de diagnóstico. Até 128 intenções pendentes entram em fila sem interromper tarefas ativas. Processos normais do produto em uma sessão de login compartilham uma instância; solicitações com vários arquivos abrem em ordem e ativam o último. Consulte o [contrato de sessões](application-sessions.md) para abas e janelas.

Argumentos de inicialização entram em fila antes do carregamento do QML. A janela principal começa oculta e envia a primeira solicitação disponível imediatamente ao conectar o controlador, sem exigir visibilidade da janela. A janela é exibida na fila inicial de eventos para que eventos de inicialização da plataforma usem o mesmo caminho. Durante abertura externa, oculte a entrada de boas-vindas antes de alterar sessões para evitar um lampejo da página de boas-vindas no primeiro quadro ou na substituição de sessão. Cancelamento/falha restaura boas-vindas; sucesso mostra a lista real. Consulte [estado de carregamento](../ux/welcome-opening.md).

A inicialização nativa do macOS também espera NSApplicationDidFinishLaunchingNotification do AppKit, processa esse lote de eventos Qt de arquivos em fila enquanto oculta e depois mostra a janela. Notificações e callbacks em fila são limitados à vida da janela principal; não substituem o delegado de aplicativo Qt nem usam atrasos fixos em milissegundos. Uma regressão real do Launch Services encontrou antes um quadro de boas-vindas; o requisito corrigido é zero. check-macos-open.py executa caminhos argv e de abertura nativa localmente e na CI Mac, mantendo apenas JSON/logs e sem gerar ou enviar pacotes de aplicativo.

## Verificação automatizada e limites

CTest nas três plataformas verifica eventos de arquivo anteriores à inicialização, rejeição de URLs não locais e fila enquanto a leitura está ocupada. XDZIP_ASSOCIATION_PROBE explícito com configurações isoladas é apenas para CI: use o fluxo normal de abertura para ler um ZIP próprio de 100.000 entradas, mantenha contagem e identidade do build e encerre normalmente sem registrar caminhos de origem ou extrair.

A sondagem atual de associação espera ao menos uma apresentação real de quadro e registra a visibilidade do conteúdo de boas-vindas em cada quadro. Os requisitos atuais para Windows ShellExecuteEx e Linux GIO são presented_frames maior que 0 e welcome_frames igual a 0. Produtos antigos fixados são testados conforme a capacidade histórica de sua sondagem; não finja que binários antigos têm as novas contagens do primeiro quadro.

A CI nativa Windows instala a variante QA 1, atualiza para 2, reverte para 1 e então instala o pacote real de entrega. ShellExecuteEx abre classes de registro próprias com caminhos contendo chinês, espaços e e comercial, verificando que padrões e UserChoice não mudam, que a substituição ocupada é recusada e que a desinstalação preserva configurações, arquivos extras e outros candidatos. O Linux executa o mesmo ciclo dpkg em um contêiner sem rede, SDK, Qt de sistema ou compilador. O produto com UID 1000 abre de fato 100.000 entradas por um lançador desktop GIO; verificam-se MIME, padrões, bloqueios, desinstalação e purge.

A verificação de lançamento Linux também altera padrões MIME em um perfil de usuário isolado do contêiner e usa `gio open` quando o GIO resolve o tipo de conteúdo de uma amostra para xdzip. Verifica cada padrão MIME declarado, exercita outro manipulador e restaura os padrões originais. Verificações automáticas de abertura Linux e macOS usam amostras que podem ser abertas sem entrada. O teste de navegador AES Crypt verifica a solicitação de senha de abertura e leituras autenticadas. Configurações do sistema e outros ambientes de desktop precisam de verificação separada.

Variantes QA compartilham os binários atualmente verificados e alteram apenas versão e diretório do pacote de teste para testar mecanismos de instalação. Não são artefatos de lançamento e não se passam por migração real de dados entre versões diferentes do produto. O esquema de configurações é atualmente 1 e os metadados de instalação o registram em ambas as plataformas. Instaladores antigos recusam sobrescrever uma instalação que declare esquema mais novo; uma futura migração deve atualizar o contrato.

A injeção posterior de falhas é permitida apenas na variante QA 2, falhando uma vez durante a configuração postinst. A produção não deve conter esse ramo. O contêiner verifica de fato o estado semiconfigurado, inicialização bloqueada pela barreira e configurações preservadas, depois executa dpkg --configure -a para recuperar e abre um arquivo real via GIO. Trata-se de falha de configuração reproduzível, não perda de energia do dispositivo. Uma verificação separada de compatibilidade de configurações compila componentes originais preservados e atuais e faz ida e volta de configuração do mesmo esquema. Entradas originais são fixadas por hash de cada arquivo, independentemente do antigo histórico main, e não se passam por migração completa de dados do instalador.

A compatibilidade completa do produto é verificada separadamente por prepare-previous-product.py, que compila a fonte completa a partir de um snapshot de compatibilidade fixado (originalmente de 4cf0f8c) em hosts CI Windows/Linux descartáveis. Um worktree separado preserva a identidade limpa real; o SDK fixado atual compila instaladores QA do produto histórico sem baixar binários antigos de Actions sujeitos a expiração. Instale o produto histórico e abra-o de fato, depois instale o produto atual e verifique mudança de revisão e preservação dos bytes de configuração; então reverta, reabra o produto histórico e verifique os dados. Isso comprova compatibilidade de mesmo esquema entre dois commits completos de fonte, não um pacote original historicamente assinado, migração inexistente de esquema 2 ou reinicialização de dispositivo. Instaladores históricos são apenas QA e não são enviados como assets do produto; recibos vinculam os SHA-256 de ambos os binários e instaladores.

windows-install-lifecycle.json, linux-install-lifecycle.json e hashes de pacotes são evidência real. Cliques duplos reais no Explorer/Finder, interface de seleção padrão, serviços e caches após reinício, avisos por falta de assinatura formal e verificações de GPU e desktop seguem a lista manual. Scripts automatizados não devem marcar por si todos os INSTALL-01/ASSOC-01 como aprovados. Conclusões manuais existentes estão em [WP-12 #5](https://github.com/xiaodaozhi/xdzip/issues/5); regenerar um modelo pendente não reabre a aceitação. Migrações futuras de esquema exigem casos adicionais de compatibilidade real.

A sondagem Windows sem tarefas para proteção contra substituição ocupada usa configurações isoladas com bandeja desabilitada para que `CloseMainWindow` faça saída normal nessa configuração. Outras sondagens de abertura por associação mantêm configurações padrão da bandeja e terminam pela barreira explícita de encerramento. Sondagens de proteção de instalação não devem confundir janela oculta com falha de saída do processo nem contornar a verificação encerrando à força o caminho normal.

Fixtures de protocolo de atualização Windows e fixtures de atualização Qt real incluem o lançador de associação e todos os nove ICOs de documento; instaladores não podem passar nas verificações se uma carga obrigatória estiver ausente. O pequeno programa principal C e o comando de associação do fixture de protocolo verificam apenas a transferência de atualização. Recursos incorporados do aplicativo, candidatos nativos e janelas reais são verificados separadamente pelo produto Qt completo; as conclusões não são misturadas.

## Entradas da base de compatibilidade de longo prazo

Upgrade e rollback reais usam fonte completa antiga fixada do produto em vez do histórico main reescrito. `prepare-previous-product.py` fixa um snapshot de fonte de raiz única na branch independente `codex/installer-compat-baseline`. Essa branch contém apenas fontes e assets originais necessários a builds e regressão, sem pais do antigo main, relatórios de execução ou workflows. `COMPAT-BASELINE.json` no snapshot registra commit de fonte e identidade de árvore originais. Ela não deve ser mesclada de volta ao main nem tratada como pacote de lançamento ou conclusão de aceitação do produto atual.

Após o build, a identidade CLI deve corresponder ao SHA fixado do próprio snapshot; recibos registram separadamente a identidade da fonte original e não devem se passar pelo binário originalmente lançado. Os componentes de configuração também mantêm três pequenos arquivos-fonte originais como entradas duráveis de teste, fixadas por hash individual. Leituras e gravações bidirecionais e rejeição de esquemas futuros não dependem da rede ou de commits históricos. Não altere essas entradas de regressão junto com a implementação atual; revise uma nova base separadamente e mantenha a proveniência quando necessário.

O snapshot congelado é anterior ao auxiliar independente de atualização e não contém fonte ou binário desse auxiliar. Apenas `prepare-previous-product.py` passa `--qa-historical-revision` a ele. Scripts de implantação e empacotamento exigem simultaneamente CI descartável, SHA fixado completo e correspondência da identidade real limpa do produto. Linux também exige modo de versão histórica e proíbe mistura com a variante QA atual. Windows executa diretamente o comando de versão do produto antigo para identidade; Linux usa a identidade da auditoria independente de implantação e hashes completos de arquivos. Recibos informam explicitamente que a fonte histórica não contém o auxiliar, não injetam o auxiliar atual e não instalam autorização polkit para um auxiliar Linux inexistente. Produtos comuns e variantes QA atuais continuam obrigados a entregar e verificar o auxiliar independente; `--qa-legacy-version` sozinho não permite sua ausência.

## Migração de versão Debian

Desde o primeiro pré-lançamento público, usa-se epoch Debian 1: `1:<semantic-version mapping>+git<commit>`, por exemplo `1:0.1.0~alpha.1+git...`. O histórico `0.1.0~dev.9` é ordenado depois de alpha.1 sem epoch pelas regras dpkg, portanto o mapeamento antigo não pode simplesmente ser mantido. O epoch serve apenas à ordenação de pacotes do sistema; a interface do produto, tags de versão e release.json continuam usando a versão semântica original. Pacotes Debian posteriores mantêm epoch 1, com ordenação alpha, beta, rc e stable ainda expressa pelas versões upstream. Consulte [Debian Policy](https://www.debian.org/doc/debian-policy/ch-controlfields.html#version).

O fixture real do produto histórico usa `--qa-legacy-version` apenas em CI para manter sua identidade original sem epoch; não altere a ordenação do pacote antigo para ocultar problemas de upgrade. O pacote atual deve passar na aceitação real de upgrade, rollback e ciclo de instalação dpkg. Configurações do usuário e associações externas padrão mantêm seus contratos originais.

## Aplicativos padrão em Configurações

Configurações agrupa sufixos de associação usando dados de formato gerados. Controles editáveis dependem do serviço da plataforma e da identidade de instalação. O Windows delega alterações aos Aplicativos padrão do sistema e nunca grava UserChoice. O MSIX mantém os controles desabilitados e usa a entrada do pacote nas configurações do sistema. O Linux mapeia sufixos suportados a tipos MIME, usa `xdg-mime` para padrões do usuário e oferece uma substituição instalada ao remover um padrão.

No macOS, Configurações habilita cada controle cujo tipo de sistema é coberto pelas declarações Viewer/Alternate do bundle instalado. Um controle habilitado pode solicitar xdzip como padrão mesmo quando o tipo não tinha padrão anterior. O macOS pode pedir confirmação. Após um callback bem-sucedido, Configurações permite um curto intervalo para o Launch Services informar o novo padrão. Quando a consulta ao sistema confirma xdzip, o aplicativo registra localmente o bundle ID do aplicativo anterior por tipo de conteúdo do sistema. Ao desligar o controle, solicita primeiro o aplicativo anterior se o macOS ainda o listar como compatível. Se não houver aplicativo compatível salvo ou a restauração falhar, Configurações oferece alternativas compatíveis instaladas. Sem alternativa, explica isso ao lado do controle. O cancelamento preserva a seleção atual e o estado exibido segue nova consulta ao sistema. Builds Viewer/None desabilitam alterações.

No modo de idioma automático, o Windows Setup seleciona a descrição de associação usando o idioma atual da interface do sistema do usuário. Usa chinês tradicional para preferências de chinês tradicional e inglês dos EUA para idiomas não suportados. Uma escolha manual suportada tem prioridade. O Setup preserva o modo automático para que o aplicativo resolva o idioma do sistema e sincronize suas descrições próprias na inicialização.
