# Password extraction interaction

Supported ZIP, 7z and RAR tasks enter `waiting_password` upon an entry requiring a password. The runtime publishes a request with task ID and request ID; QML expresses input and cancellation intent only and does not decrypt, authenticate or publish files. Password requests and name conflicts are separate states; do not route password requests to the conflict window. Format, authentication, retry and output boundaries follow the [engineering contract](../engineering/password-extraction.md).

7z or RAR filename encryption requests a password during opening, reusing PasswordWindow. It shows “Open password” and “Continue opening”, explaining that closing cancels only this opening and creates no extraction or checking task. Opening uses a separate `open` identity and increasing request IDs; an old request cannot submit a password to a new open. No partial file list appears before complete scanning. Neither opening nor content passwords are persisted.

When 7z returns `password_or_integrity`, the same password window shows “密码不匹配或加密数据损坏，请重试。” in Chinese and “The password does not match or the encrypted data is damaged. Try again.” in English. This cannot establish that the password is wrong or promise that re-entry will repair corruption; the user may cancel. Task retries retain existing limits and keep this uncertain classification at the limit rather than showing confirmed password verification failure.

PasswordWindow is application-modal with the existing system title bar, client width 491 and maximum height 600, constrained by the current screen's available height. Title size is 20, body 13 and supporting text 12; the body grows or scrolls independently and the footer remains reachable. Dimensions come from [password-reference.json](../../specs/visual/password-reference.json); the high-fidelity basis is the [P02 standalone state design](../../design/hifi/sources/password-extraction.html). Chinese/English, light/dark and 100%/125%/150% font sizes use the same geometry policy.

The window shows the current encrypted entry's name, password field, show/hide action and task-scope explanation. The show action uses clear text and an accessible name, without a password-containing tooltip. Input is masked by default; submission, cancellation, window close or request ID change clears the field and restores masking. Passwords are not written to settings, clipboard, logs, task snapshots or reports. UI string cleanup does not claim to erase every historical Qt memory copy; the runtime contract governs the underlying secret container's lifetime.

Passwords for external archives can be empty or contain control characters; do not trim them or apply the 1–128 byte creation-password limit. Extraction passwords are limited to 1,024 UTF-8 bytes, with at most 1,024 UTF-16 units in the field and a UTF-8 byte check before submission; the backend checks again. Exceeding the limit shows the actual error and retains input for editing. A wrong-password request uses a new request ID, clears old input and displays “Incorrect password. Try again.”

Continue extraction submits the exact task ID, request ID and original password to the controller. Once accepted, immediately clear the field, restore masking and prevent duplicate submission; the window waits for the task snapshot to confirm departure from that request before closing. Expired, cancelled or duplicate requests cannot submit to another task. Immediate rejection retains the current valid request and input for retry. The controller presents parallel task requests sequentially; a later request cannot silently replace an unresolved task.

“Cancel task” or closing the native window cancels the current task associated with that window rather than leaving it in an undiscoverable wait. Escape follows shared application focus policy: first leave the current control's focus, then close the window and cancel the task. Return/Enter in the password field submits the current password under the same request identity, length and pending checks; buttons retain existing keyboard activation. The task window's “Waiting for password” state retains actual progress and offers to reopen the request; terminating a task clears its associated password request.

The design demo uses only empty fields and owned example filenames, does not read real archives and does not validate passwords. Automation must check masking, empty passwords, non-ASCII byte boundaries, rejected and duplicate submission, request replacement, cancellation and close, plus small-screen scrolling and a fixed footer. Functional success and native visual acceptance are recorded separately.
