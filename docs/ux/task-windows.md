# Task windows and integrity checks

The application task entry aggregates all sessions and routes progress, passwords, conflicts and results using session UUID and backend task ID. Closing a page retains its controller; explicit exit waits for all asynchronous joins. See the [application session contract](../engineering/application-sessions.md).

Task menu rows display operation icon, archive filename, sequence tag and status tag. Icons use shared assets for creation, extraction, checking, addition, movement and export without operation-type text prefixes. Both tags use the same component; sequence retains the backend number and cross-session internal identity is unchanged. Long filenames are elided while accessible names include operation, number, filename and state.

Extraction and creation confirmations are ExtractWindow and CreateWindow, owned by their respective main windows, with native decorations supplied by the system. Each main window has one TaskWindow; selecting an extraction or creation task binds its snapshot and shows its result in the same window after termination. Closing hides the view only; cancellation requires explicit action. Sessions share serial admission for heavy tasks rather than creating windows simultaneously for each task or state. Double-clicking a regular file reuses this window and automatically hides it after the system accepts the temporary file open; rejection shows an error and allows retry. Manually reopening historical results does not close them again due to unrelated progress updates; see the [temporary open contract](../engineering/archive-opening.md).

Creation formats are ZIP, TAR, TAR.GZ and 7z; RAR is read-only. 7z retains four levels, defaulting to normal LZMA2, non-solid, unencrypted and unsplit; level 0 stores only. Solid and filename encryption use shared OperationCheck. Filename encryption is available only with a password; removing the password or switching formats clears it and disables filename encryption. Format switches also reset solid and volume splitting. New options enter the scrolling body without widening the window or overriding footer appearance.

Integrity checking reuses the same TaskWindow layout. The real toolbar “Test” submits a whole-archive read-only background task, showing reading, password waiting, cancellation and terminal states as `kind=check`. It is independent of current selection, stops on first error and displays verified and unchecked counts separately. Extraction or creation commit counts are not checking counts. See the [checking contract](../engineering/archive-checking.md) for format and safety boundaries. Component development previews still offer a separate IntegrityWindow explicitly labeled “UI preview, no actual verification”.

The HTML check button runs an explicitly labeled UI demonstration. Close or return to browsing retains demo state and reopening shows current progress; cancellation ends the demo and terminal states must not keep advancing. Completion and cancellation use the same structure and footer. Object path, bytes read, file count, speed, remaining estimate, phase and current entry are data slots; the UI does not scan, read or extract files. Example numbers are not real check results.

Window width, density, fonts, radii, borders, progress bars, icon slots and explanation alignment come from the [visual standard](../visual/design-standard.md) and [frozen original](../../specs/visual/integrity-reference.json). Unknown totals show no definite percentage; large text allows body scrolling while keeping the footer reachable. Close emits no cancellation; Cancel explicitly requests it. A check terminal must not show saved files or open a destination folder.

The high-fidelity original is [integrity check progress](../../design/hifi/screens/integrity-progress.png); the runtime icon is document-check from shared assets. Original crops are references only; the dynamic UI uses shared components.

## Normal dimensions and task discovery

Creation, addition, extraction, task/result, conflict, settings and About windows with icon, title and subtitle share OperationHeader. The baseline is a 48-logical-unit icon slot, title 20, subtitle 13 and normal height 96. Long copy and larger fonts grow using shared font metrics; the body continues scrolling and footer does not move. Text-only password, preflight and exit/restart confirmations do not gain invented decorative icons. See the [visual standard](../visual/design-standard.md) for parameters, standalone states and registration.

The task button retains paired chevrons on its right. The in-app task menu is capped at 360 logical pixels and current available window height, with internally scrolling history and a fixed reachable clear button. Clear hides completed, failed or cancelled history only; running, queued, password/conflict-waiting, cancelling and cleaning tasks remain. Disable it when there is no clearable history. It does not cancel tasks, delete source archives or user outputs, change original controllers or alter exit barriers. Close result windows that have been hidden by clearing rather than showing empty snapshots.

The clear button belongs to interactive menu content, not the decorative background. Pointer, keyboard and native accessibility invoke the same clear intent. Leave 4 logical units on either side of the separator and use only shared menu padding below the button, without additional footer spacing. Task rows use equal horizontal and vertical padding; right-align status badges in available content and reserve scrollbar width only on actual overflow. Labels distinguish check, extract, create, add, move and export from snapshot kind rather than calling every non-creation task extraction. Activation retains full task identity and the original controller; checking tasks are not rerouted as extraction.

2026-10-15 revision: creation, extraction and shared task windows use width 491 logical pixels. Progress and results adapt height to content up to 600. Collapsed details reserve no expanded space; expanded lists are at most 168. Changing task ID clears detail expansion; updates to the same task preserve user choice. The file-exists window has the same width and maximum height 560 with normal density and shared footer. These dimensions do not change native standalone-window or cancellation semantics.

The status bar shows all tasks retained by the current controller, at most 64, with right-side badges distinguishing terminal and running states. Active task counts continue to govern asynchronous exit without history display changing scheduling or close barriers.

Task discovery retains entry identity by task ID. Progress and state update in place without rebuilding the list or interrupting hover, highlight or keyboard focus. New tasks and history eviction insert or remove only affected entries, preserving the identity and selection of others. Sort remains descending by task ID; mouse or keyboard activation always reopens the matching ID. The QML data model is only a UI projection of task history and changes no snapshot, cancellation, commit, terminal or exit-barrier semantics.

This update does not change existing window/menu layouts, logical units or visual states. The HTML design's task menu does not rebuild nodes on continuous progress and retains existing originals. Runtime verification still covers stationary hover, keyboard navigation, in-place state updates, task addition and history eviction.

## Native picker and drag activation

Opening archives, adding files/directories and changing extraction or creation destinations pass the actual calling Quick window to shared NativeDialogPolicy. The picker remains a standalone native application-modal dialog with transient ownership of the caller. After leaving the nested event loop, queue activation restoration only if the caller still exists and is visible; do not always restore the main window. Closing the caller must not revive it. System picker text continues to follow system language.

Only after a valid single local archive drop is accepted, the welcome page raises and activates the receiving main window in the next event-loop turn, after DropArea acceptance. Invalid drops do not change the foreground window; ordinary background task completion does not request activation. Automation uses owned windows and fixtures; real Finder drag-and-drop still requires desktop manual review.

## Exit and restart confirmation

QuitWindow and RestartWindow inherit OperationConfirmationWindow with application modality, normal density, adaptive height, scrollable body and fixed footer. Buttons retain their return, wait, cancel exit, later and restart intents; existing controllers handle file publication and task cleanup. While stopping, decision actions and Escape close are disabled, and changes to title or description do not restore old dimensions.

Task exit success was previously checked without confirmation-window visuals; functional and visual evidence are now recorded separately. See the [mandatory workflow](../visual/design-workflow.md) for window integrity, base-class and dimension checks, and [confirmation states](../../design/hifi/sources/confirmations.html) for designs.

Password extraction uses its own `waiting_password` state and request identity. TaskWindow shows waiting for password and offers to reopen; application-modal PasswordWindow handles input and cancellation. It does not use a conflict `promptId`; see [password extraction interaction](password-extraction.md) for lifecycle.
