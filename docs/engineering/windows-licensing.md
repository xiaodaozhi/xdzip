# Windows development tool and runtime licensing

This page defines applicable Windows build and redistribution paths and is used alongside [native runtime materials](native-runtime-materials.md), the [developer build entry](developer-build.md) and the [installation contract](installers-associations.md). Specific environments, verification commits, material hashes and acceptance conclusions belong in issues and local/CI artifacts; this page does not retain a machine's license proof.

## Free Community path and local choice

Original project content is published under Apache-2.0, an OSI-approved open-source license. Visual Studio Community 2022's individual terms allow individuals to develop their own applications; its organization terms also allow users to develop and test applications released under OSI-approved licenses. Assess an organization's open-source use separately from other commercial internal use; do not extend this project's eligibility to other projects.

When a maintainer needs their own Community development environment, obtain Community 2022 from the [official Microsoft installer](https://learn.microsoft.com/en-us/visualstudio/install/use-command-line-parameters-to-install-visual-studio?view=vs-2022), read and accept [that version's original terms](https://visualstudio.microsoft.com/license-terms/vs2022-ga-community/), and use it within their scope. Select `Microsoft.VisualStudio.Component.VC.Tools.x86.x64` and the Windows SDK for C++ builds; all workloads need not be installed. There is no requirement to purchase Professional/Enterprise or separately apply for a runtime distribution certificate per project.

Licensing review does not require a large IDE permanently installed locally. When building and publishing only on the standard GitHub-hosted environment below, the applicable basis is hosted Visual Studio authorization and its REDIST terms; there is no need to install local Community or purchase personal Enterprise for hosted CI. Community is a free choice when maintainers need their own environment, not an additional local-installation gate for hosted build legitimacy.

Community section 3 permits software files and Build Tools on qualifying build devices; section 4 grants distribution rights for listed Distributable Code subject to functionality, downstream terms and restrictions. Downloading VC_redist, installing Build Tools or including a license text alone does not establish eligibility to use development tools. The Build Tools exception without a Visual Studio license applies to building third-party open-source dependencies; it is not a general exception for developing all one's own C++ programs. Using VS Code does not automatically provide an MSVC license. See [Microsoft's licensing guidance](https://www.microsoft.com/licensing/guidance/Visual-Studio) and [Build Tools terms](https://visualstudio.microsoft.com/license-terms/vs2022-ga-diagnosticbuildtools/).

Locally verify product, full version, non-preview status and C++ components reported by `vswhere`, enter the actual instance's development environment, then check `cl`, `link` and the SDK. Installed 2019 Build Tools are not Community 2022 and do not replace verification of the current MSVC 2022 toolchain. Generic `desktop.py prepare` does not silently install a system IDE/SDK; use Microsoft's installer for first installation, retain existing tools and prohibit automatic restart.

Choosing 2022 is the current release-toolchain decision, not a claim that free Community licensing permits only 2022. The [Qt 6.8 support table](https://doc.qt.io/qt-6.8/supported-platforms.html) lists Windows MSVC 2022; this repository uses the corresponding `msvc2022_64` SDK. 2019 tools may remain for local development, but cross-version ABI compatibility alone cannot establish full support when mixed with the current SDK. [Microsoft compatibility rules](https://learn.microsoft.com/en-us/cpp/porting/binary-compat-2015-2017?view=msvc-170) also generally require the final linker to be no older than the tools used for input libraries and separately constrain runtime libraries and `/GL`/`/LTCG`. Alternative configurations need their own licensing and verification; this does not force local installation of the full 2022 IDE.

## GitHub-hosted builds

The project's Windows workflow uses standard GitHub-hosted `windows-2022` runners. The preinstalled product is Visual Studio Enterprise 2022, not Community. runner-images maintainers have explicitly [confirmed](https://github.com/actions/runner-images/issues/12945#issuecomment-3348002951) that preinstalled Enterprise is available for public and private GitHub Actions/Azure DevOps hosted-runner use under an agreement between GitHub and Microsoft, without users obtaining a separate personal Enterprise license. This project relies on that hosted build environment; the public explanation does not replace or claim to disclose the complete agreement.

According to [GitHub's hosted-runner documentation](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners), each Windows job receives an independent VM, and `Set up job` points to the image and software inventory for that run. Workflows only compile, test, deploy and release this repository, within the scope of the [Actions additional terms](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features#actions). Free public-repository compute allowance and Microsoft component redistribution rights are distinct.

CI records the actual VS product and version, relative compiler location, tool versions and SDK version in `windows-toolchain.json`, retained with same-commit packages and materials without product keys or private developer paths. It records tool identity, not automatic proof of license eligibility. Self-hosted runners, tools copied locally from images, other CI services and general shared servers do not inherit the hosted license; recheck Community/Build Tools terms and device conditions.

## Microsoft component redistribution

The [VS 2022 REDIST list](https://learn.microsoft.com/en-us/visualstudio/releases/2022/redistribution) explicitly includes validly licensed Community 2022. The current build uses the release VC_redist x64 pinned in [windows-runtime.json](../../scripts/windows-runtime.json), extracting it unchanged and individually checking eight CRT DLLs and the original runtime license. It does not package compilers, debuggers or `debug_nonredist`. Neither the free Community development path nor hosted CI Enterprise identity relicenses Microsoft DLLs under Apache-2.0.

New development packages do not include Windows SDK `d3dcompiler_47.dll`, `dxcompiler.dll` or `dxil.dll`, or a Mesa software OpenGL library. In historical packages these three files came from an explicit SDK's `Redist/D3D/x64`. The [SDK REDIST list](https://learn.microsoft.com/en-us/legal/windows-sdk/redist) permits unmodified distribution with Classic Windows applications under a valid SDK license and prohibits distribution with UWP applications; xdzip is a Classic Windows desktop app. Historical SDK licenses, notices and distribution conditions remain independently applicable even when future packages remove these files.

The bundled `share/notices/Windows-runtime-NOTICE.txt` explains each component's licensing boundaries in both languages. Original Microsoft CRT terms are at `Microsoft-VC-runtime/license.rtf`. The installer displays the original CRT agreement and requires acceptance, then displays component notices. Portable users must also read and comply with bundled Microsoft terms. Both packages retain original licenses and provenance. Downstream redistributors must independently satisfy eligibility and distribution conditions; the project's Apache-2.0 license alone does not authorize forwarding Microsoft components.

Displaying or bundling the SDK text alone does not establish that external distributors and end users agreed to SDK-required protective terms, or replace the publisher's valid licensing and responsibility assessment. The current installer acceptance page applies only to CRT. If SDK graphics DLLs are redistributed again, assess applicable terms and acceptance separately for installer and portable packages and retain actual evidence in the release record; see historical [#135](https://github.com/xiaodaozhi/xdzip/issues/135).

Before compiling the installer, check the pinned hash of the CRT agreement and bilingual notice; materials include the same original CRT text and source record. Historical SDK terms are at `Windows-SDK-graphics/sdk_license.rtf`. License corrections do not rewrite old public assets or historical build identity; issue corrected packages under a new version following the [immutable release protocol](release-protocol.md).
