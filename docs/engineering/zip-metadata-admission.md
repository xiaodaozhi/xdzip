# ZIP metadata dependency admission

This page retains the historical 2026-10-11 admission for the first read-only directory scan; it does not approve extraction, creation or third-party plugin execution. Current ZIP metadata has migrated to the [independent Rust record layer](independent-rust-codecs.md), with rawzip used only as a development-test reference. The historical selection below is not a current production dependency.

The choice was [rawzip 0.5.2](https://github.com/nickbabcock/rawzip), with exact version and checksum in the [pinned manifest](../../specs/engineering/zip-metadata-dependencies.json) and root Cargo.lock. Default features were disabled and std explicitly enabled; there were no runtime dependencies or build.rs. The full upstream MIT license is retained in [third_party/rawzip/LICENSE](../../third_party/rawzip/LICENSE) and accompanies releases using the dependency.

The historical review examined README, Cargo configuration and directory-reading source. The choice allowed central-directory records to be read one at a time from a borrowed Read + Seek input, preserving physical order and duplicate names while the host limited bytes read and cumulative name sizes. zip 9.0.1 was evaluated for read-only scanning but its name-indexed reading structure was unsuitable for retaining physical duplicate records. zip-rs 9.0.3 was later introduced separately for AES writing without replacing the read-only physical index. The current independent implementation retains these physical-index contracts.

No rawzip advisory was found in RustSec database snapshot `7eebec69c352c7191b1f13eb95dd510eeca5d1de`. cxx RUSTSEC-2026-0202 affects let_cxx_string! below 1.0.195; the pinned 1.0.205 includes the fix. This records a targeted advisory check, not a cargo-audit of all dependencies.

The metadata adapter enables no decoders and does not verify file content, CRC or consistency between local headers and the central directory. Unknown compression methods display only their numbers; listing does not imply extractability. Single-volume ZIP64 metadata was additionally admitted for M2, verifying 100,000 records and exact declared sizes beyond 2^53. The [multi-volume host](archive-opening.md) converts supported volume sets into a single-volume logical view; the adapter still rejects unconverted multi-disk records. Filename Unicode extensions and legacy encoding follow the [separate contract](filename-encoding.md). Actual content decoding is handled independently under [extraction dependency admission](zip-extraction-admission.md) and the [safe extraction contract](m3-extraction.md). Limits and failures are in the [implementation contract](readonly-browser.md).

Metadata regressions must include real ZIP64, malformed locator/end records, ZIP64 extension starting disks, name/display/read budgets, cancellation and source changes. The independent implementation additionally covers self-extracting offsets, ambiguous end records and bounded fixed-seed mutations. Production dependency-closure checks establish format-library removal; test dependencies remaining in the lockfile do not mean migration failed.

M3 payload decoding and host output are registered separately under [extraction dependency admission](zip-extraction-admission.md); this page retains the historical M2 read-only scope.
