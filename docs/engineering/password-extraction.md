# Archive passwords and encrypted-directory opening

This contract supplements [safe extraction](m3-extraction.md), defining passwords, authentication, and task interaction. Format and file-security logic remain independent of Qt; the password window submits user intent only. See [issue #11](https://github.com/xiaodaozhi/xdzip/issues/11) for actual progress and platform verification. Execution reports do not belong here.

## Capability and format boundaries

ZIP/ZIP64 WinZip AES-256 AE-1 and AE-2 are supported with Store or Deflate as actual compression methods. Plaintext, encrypted, and mixed entries can be selected; empty files must also verify authentication. Files may have different passwords. AES-128/192, traditional ZipCrypto, and other encryption remain unsupported. Supported split volumes use [unified logical input](archive-opening.md) with unchanged password/authentication rules. Filenames, directory structure, and ordinary ZIP metadata remain visible; password functionality does not encrypt or authenticate them.

AES fields follow the [WinZip format specification](https://www.winzip.com/en/support/aes-encryption/): marker method 99, encryption flag set, and one AES extra with AE vendor, known version, 256-bit strength, and supported actual method. Only seven defined data bytes are currently accepted; unknown extensions remain rejected. AE-1 additionally verifies decoded-content CRC; AE-2 stored CRC must be zero. Central directory, local headers, and data descriptor declarations are independently checked; authentication codes do not replace structural validation.

The adapter first compares the frozen snapshot's physical record identity, raw name, type, size, method, encryption flag, and password-support marker. It then records full flags and AES profile for this task and verifies consistency of local headers, central directory, descriptors, and payload ranges. The initial snapshot does not retain full flags/profile. Source changes still rely on best-effort identity/version detection, not an atomic input-content snapshot. ZIP64 size sentinels in either local or central headers determine descriptor width. The project independently implements the ZIP container and AES wrapping using [admitted cryptographic primitives](dependencies.md), without invoking a format library's unpack function.

The decryptor reads only the verified ciphertext range for one entry and receives no output path. Store or shared raw Deflate verifies exact compressed-byte consumption, decoded size, and AE-1 CRC. After fully consuming ciphertext, verify the HMAC authentication code; only complete success returns success. Empty files also complete authentication. Ciphertext and decoded data use bounded buffers rather than accumulating whole files in memory; no private archive view for a third-party ZIP library is constructed.

## 7z, RAR, and encrypted directories

7z and RAR retain the same host decode sink, secure output, actual quotas, and error classification. See the [isolated backend contract](native-codecs.md) and [independent implementation contract](independent-rust-codecs.md) for current product routes and in-house candidate boundaries. When 7z AES-CBC has no independent password verifier, decoding/parsing failure of recognized encrypted metadata or size/stream-termination/CRC failure of encrypted content uses `password_or_integrity`, indicating a password mismatch or encrypted-data corruption rather than pretending to know `wrong_password`. Outer plaintext-header verification failures remain container corruption. Source I/O, source changes, resource limits, cancellation, unsupported features, and output failures are not reclassified as password errors. RAR retains historical and current password boundaries; legacy/current formats, header encryption, solid archives, and split volumes are accepted by combination separately.

Encrypted filenames or directories require a secret before metadata scanning. OpenWithPassword is the only opening command carrying it; password containers are bounded before enqueue and zeroized on release, and events contain no secrets. No partial browsable index is published before a complete successful scan. On success, the session retains a zeroizing container; admitted tasks may clone a private copy to continue after page closure. Copies do not enter snapshots, logs, or settings. When task decoders reopen, they use the same password; subsequent entry passwords still use separate prompt-control responses.

7z creation supports content passwords and filename encryption together. Filename encryption requires a nonempty creation password and is 7z-only. ZIP retains content-only encryption; TAR/TAR.GZ reject encryption arguments. Encrypted 7z and all RAR archives reject modification.

## Secret and control protocol

`extraction::Password` is separate from creation passwords. Extraction accepts UTF-8 as entered, at most 1,024 bytes, including empty values, spaces, and control characters. It is not trimmed or subject to the 1–128-byte creation rule. The current text UI cannot express non-UTF-8 raw passwords. Input allocation capacity is also bounded. Rust-owned containers always redact Debug output and zeroize on rejection, replacement, cancellation, or scope exit.

`Client::respond_password(task, prompt, Password)` passes secrets through an independent control slot, not the ordinary command queue. Every prompt uses a task-local one-shot ID, distinguishing name-conflict and password prompts. Reject old IDs, cross-type responses, duplicates, and responses after terminal state or cancellation. Snapshots carry only `PasswordPrompt { id, name, retry }` and `waiting_password`, not passwords or digests. GUI mailbox byte limits still include prompt names.

The first password need pauses the task for an explicit response. A password used successfully within the task may be reused for later encrypted entries. A verifier mismatch or explicit `password_or_integrity` clears the old cache and prompts again, at most ten failures per physical entry. At the limit retain the actual terminal error category; an uncertain failure cannot be forced to `wrong_password`. Encrypted 7z directory opening likewise reuses the password window and open-request identity; users may cancel that open. When a format has an independent authenticator, authenticator mismatch remains an integrity failure and stops rather than entering password retry. A two-byte verifier cannot rule out every wrong password; final authentication remains required.

Cancellation and exit do not depend on ordinary queue capacity; they wake password waits and clear unconsumed secrets. Content passwords live only for the task; encrypted-directory passwords are limited to the open session and its admitted tasks. Neither enters settings, events, logs, command lines, recovery records, or test screenshots. Clear Qt input and controlled transport buffers on submit, close, cancel, prompt change, and exit. Qt, system input methods, and dependency internals cannot guarantee erasure of every historical copy; Rust container zeroization does not make that whole-process guarantee.

## Output, retries, and links

Every regular-file attempt uses a fresh private staging file. Wrong passwords, authentication failures, stream errors, and cancellation end that staging lifetime and attempt identity-checked deletion. If deletion fails, final workspace cleanup reports a warning and retains recovery materials; immediate deletion cannot be promised. Publish or replace under existing policy only after full verification, synchronization, source revalidation, and commit permission. Unauthenticated staging is never published as the destination. Existing targets remain unchanged on authentication failure. Actual decoded/written counts from retries remain and are subject to 8 GiB per file, 20 GiB per task, and source-read limits; retries cannot reset budgets.

ZIP tasks have a 64 MiB actual metadata-read budget while creating decoders, then switch to a shared 20 GiB input-read budget. Local headers, descriptors, ciphertext, and every password retry consume that same count. Input reads differ from source-file length and saved output; stop on overage without resetting during retries.

A task may already have committed earlier verified files before a later file fails; whole-archive rollback is not promised. Skipping a conflict need not read that file and cannot be counted as authenticated. Committed items, cleanup warnings, and uncertain counts after cancellation follow the safe extraction contract.

When encrypted symbolic links are selected, authenticate and verify all selected link payloads and their dependency graph during task Preparing, before obtaining output authorization or creating derived directories. Publish regular files first, links last. Path rules, 4,096 bytes per link/4 MiB total, 64 follows, closed dependencies, no link as write parent, and rejection of occupied leaves are not relaxed. POSIX execute permission restores only admitted safe bits; Windows ZIP links and TAR links remain unsupported.

## Interface and verification

See [password interaction](../ux/password-extraction.md) for password window, HTML, and high-fidelity sources. The application-modal window appears automatically when tasks wait and can be reopened from the task window. Error responses use new tokens and clear old input; accepted responses prevent duplicate submission. System close or Cancel cancels the current task. Escape retains the shared rule: first leave control focus, then close the window.

Creation and extraction password fields expose accessibility names through explicit UI labels independent of input. Qt 6.8.2 suppresses attached names in password state, so the desktop app installs a dedicated accessibility interface for these two fields, overriding only names while retaining Qt state, text/value, and actions. Password flags and masking remain unchanged. This interface subclasses a private Qt Quick class and requires matching Qt Quick build/runtime versions. On library upgrade or replacement, rebuild and reverify interfaces, password secrecy, and three-platform compatibility. Automated interface checks and manual system screen-reader acceptance are recorded separately.

Acceptance covers raw AES fields/CRC/descriptors/ZIP64, duplicate-name physical records, correct and wrong passwords, authentication corruption, mixed files, differing passwords, empty passwords/control characters, cumulative retry resources, full queues, cancellation/shutdown wakeups, source changes, old-target protection, links and executable permissions, and independent bidirectional 7-Zip byte checks. Interface checks separately cover the real controller flow, accessibility actions, bilingual multi-font-size layouts, light/dark themes, DPR, and native windows. Automation is not manual system screen-reader acceptance.

For RAR without a trusted password verifier, encrypted-header or content decode integrity failures likewise use `password_or_integrity`. A trusted verifier that has matched, plaintext-header checks, and non-password failures retain their own categories. See [RAR implementation basis](rar-format-sources.md) for historical per-entry passwords and platform character projection. Unknown sizes are rejected before decoding or password interaction; do not ask for secrets for non-outputtable entries.

Older RAR encrypted records lack a verifier that reliably distinguishes wrong passwords from corrupt content, so prompt separately before decoding each encrypted entry. Do not directly apply a preceding password to a later entry that may use a different secret. RAR5 and other supported formats continue task-local reuse. Legacy RAR CRC or header damage remains an integrity failure and is not a confirmed wrong password.
