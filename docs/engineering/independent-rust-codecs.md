# In-house Rust format and algorithm contract

This contract defines per-capability replacement rules for third-party format backends. Actual progress, test results, and incomplete items are tracked in [migration task #45](https://github.com/xiaodaozhi/xdzip/issues/45). Architecture decisions or the existence of code do not establish format acceptance.

<a id="实现边界"></a>

## Implementation boundaries

Container parsing, encoding, decoding, and compression algorithms use independent Rust implementations. Admitted general cryptography, character encoding, system, and bridge foundation libraries are permitted. Third-party format libraries, algorithm libraries, and command-line tools may be independent test references, but do not become product runtime dependencies for a migrated format. Removing only direct dependencies does not prove replacement: inspect transitive ordinary/build dependency closures and delivered files.

Replace a format only after all existing capabilities pass acceptance. An incomplete format retains its prior backend; there is no silent runtime-failure fallback. ZIP, TAR, TAR.GZ, and 7z retain existing read/write and modification limits. RAR, CAB, ISO, and UDF are read-only. A format name does not imply support for all historical and future extensions. RAR7 LZ requires a successful independent compressed-stream sample; Store success and rejecting an over-budget dictionary do not replace it.

The domain layer, Qt bridge, and public codec trait retain their ownership. Backends receive no destination paths and cannot publish files. Raw name bytes, physical EntryIds, duplicate entries, encoding resolution, source identity, volume authorization, path preflight, staging, verification, and commit remain governed by existing engineering contracts. Shared algorithms are implemented once; containers independently handle framing, block boundaries, dictionary resets, and verification semantics. Migration of native backends to Rust retains worker cancellation, termination, and resource governance.

## Sources and independent implementation

First define fields, state transitions, numeric ranges, error behavior, and test vectors from official technical documentation, then write code. Reference implementations supplement behavioral understanding only; no line-by-line language translation, renamed copying, transplanted structures, or copied comments. Record sections for specification identifiers/constants; prefer generating tables from explicit mathematical rules. Test-reference sources and licenses are managed separately from product dependencies.

Developers who have seen reference source do not claim strict clean-room development. For modules requiring source separation, an analyst supplies behavioral specifications without code expression to an implementer who has not seen the reference implementation. Licenses of reference source, documents, and test data do not disappear with a Rust rewrite. Historical deliveries and transition dependencies continue meeting their obligations.

Official RAR technical descriptions are incomplete. Decoder algorithm gaps must be recorded and receive dedicated licensing review. Do not develop a RAR encoder or interpret UnRAR restrictions as permission to reconstruct RAR compression algorithms. Review proprietary extensions, patent notices, and redistribution terms in public specifications separately; independent authorship does not eliminate legal risk.

## TAR record specification

The independent record layer is `xdzip-codec-tar/src/record.rs`. Layout follows [POSIX pax ustar and pax interchange formats](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/pax.html); GNU extensions follow the [GNU tar format description](https://www.gnu.org/software/tar/manual/html_node/Standard.html). Reference library internals and private APIs are not used.

- Records are 512 bytes. Header checksums use the unsigned-byte sum with the eight checksum-field bytes treated as spaces. Name, size, time, type, and ustar prefix are read at specified offsets. The prefix position in a GNU header is not a ustar path prefix.
- Ordinary numbers accept bounded octal and nonnegative GNU base-256. Reject negative values and u64 overflow. Invalid times remain unknown for display without changing payload location. Data is padded to 512 bytes; termination requires at least two all-zero records followed only by all-zero padding within budget.
- A PAX length includes its own decimal digits, space, key/value, and newline. Length must advance without exceeding bounds; keys are nonempty; records end in newline and contain no NUL. Local path, size, mtime, and hdrcharset retain existing interpretations. See the [TAR/GZIP contract](m4-tar-gzip.md) for GNU long-name and global-comment limits.
- Creation writes ustar; non-ASCII or overlong names use a local PAX UTF-8 path. Sizes and times outside octal range use PAX fields with representable placeholders in ordinary headers. Extension data is at most 64 KiB. Strictly read the frozen input size, then probe at most one byte; growth or shrinkage fails.
- Rewriting preserves ordinary header owner, mode, time, and other admitted metadata. Renaming updates path and charset declaration and recalculates checksums. PAX size controls data length; ordinary-header placeholders cannot truncate data. Bad headers/extensions, missing end records, and resource overages fail before host publication.

`tar` is an independent development-test read/write reference only. Foundation checks production dependency closure against [dependency policy](../../scripts/rust-codec-policy.json), forbidding tar, filetime, and retired compression libraries from returning to TAR implementation. The lockfile still records development-test references and alone does not establish product reachability.

## Shared Deflate and GZIP specification

`xdzip-compression` has no third-party production dependencies. Formats follow [RFC 1951 §3](https://www.rfc-editor.org/rfc/rfc1951) and [RFC 1952 §2.3](https://www.rfc-editor.org/rfc/rfc1952), without copying appendix example code. Length, distance, and extra-bit counts are specification wire-format tables; the CRC lookup table is generated at compile time from the IEEE polynomial.

The shared public interfaces are `DeflateReader`, `DeflateWriter`, `GzipReader`, `GzipWriter`, and incremental `Crc32`. ZIP and GZIP use the same Deflate codec. The raw-stream reader reads only admitted compressed ranges, distinguishes actual consumption from buffered read-ahead, and returns successful EOF only after BFINAL and when actual consumption exactly equals compressed size. Matching output size or CRC does not replace stream termination; a second stream or trailing garbage within the range is rejected.

`DeflateReader::with_dictionary` accepts at most 32 KiB of admitted history in chronological order, initializes only the match window, and does not emit history as new stream output. Ordinary ZIP/GZIP construction still begins with an empty window. CAB `MszipDecoder` reuses this interface under [MS-MCI](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-mci/27f0a9bf-9567-4e40-ad66-6ae9ab9d2786): each CK frame resets the Deflate bitstream while retaining the logical folder's last 32 KiB. Compressed frames are at most 32,780 bytes and output at most 32,768 bytes, requiring exact size and complete raw-stream EOF. Update history only after a complete frame passes; do not continue using a folder after failure or append frames after `finish`. Shared algorithms do not verify CAB physical-fragment checksums or volume chains; the independent container does. See [#48](https://github.com/xiaodaozhi/xdzip/issues/48) for CAB product switching and other method acceptance.

- Decoding handles Store, fixed and dynamic Huffman, retains a 32 KiB ring history across blocks, and permits overlapping matches. Reject reserved block types, LEN/NLEN mismatches, oversubscribed tables, impermissible incomplete tables, missing end markers, out-of-range repeat lengths, reserved symbols, and distances before history.
- Encoding uses bounded hash-chain LZ77, frequency-built canonical Huffman codes, and code-length run-length encoding. Use fixed trees when depth exceeds 15 rather than truncating lengths. Level 0 emits stored blocks of at most 65,535 bytes. Levels 1/6/9 encode blocks of at most 2 MiB with 4/32/128 candidate search limits; split into stored blocks when benefit is insufficient to avoid inflating incompressible data. Encoding history is rebuilt per block; compression ratio and bytes are not promised to match reference libraries.
- Decode intermediate state consists of a window and bounded code tables; encoding intermediate state is bounded by the single-block limit. Neither collects the entire archive. The host continues accounting input, decode work, and output quotas. Return control after bounded encoding blocks; shared algorithms add no threads or file authority.
- GZIP verifies magic, method, and reserved flags and handles extra, name, comment, and optional header CRC. Each member header is at most 64 KiB. Verify CRC-32 and ISIZE modulo 2^32 per member and concatenate all members into one TAR stream. Read to EOF; truncation, bad trailers, and non-member garbage cannot be successful termination.
- The writer produces the final block and trailer only on successful finish; Drop writes nothing. After output failure it cannot continue as a successful stream. Memory buffers grant no publication authority; the host commits only after full reverification.

A limited fixed-seed mutation test proves only its actual coverage, not long-term fuzzing. Record encoding performance, compression ratio, and three-platform results separately. Later optimization must not weaken integrity or quota checks.

## ZIP record and password-wrapping specification

ZIP EOCD, ZIP64, central/local headers, extra fields, and descriptors follow [PKWARE APPNOTE](https://www.pkware.com/documents/casestudies/APPNOTE.TXT); AES wrapping follows the [WinZip AE-1/AE-2 specification](https://www.winzip.com/en/support/aes-encryption/). Independently implement the container, name extensions, record location, codec composition, and authentication boundary. General cryptographic primitives are used under [dependency admission](dependencies.md); no RAR encoder or additional proprietary ZIP encryption extensions are implemented.

- Preserve physical central records individually; do not merge duplicate names. End records must be complete with consistent count/size/offset. Reject ambiguity if multiple end-record candidates exactly cover EOF, both before and after split-volume normalization; an embedded end record in a comment cannot hide the real directory. Interpret ZIP64 sentinels in the order fields actually appear. The two disk numbers and two counts in the classic end record may independently use 0xFFFF placeholders; determine single-volume status only after reading ZIP64 values. Every non-placeholder must match its corresponding actual value. Reject damaged or duplicate critical fields and multidisk metadata not normalized by the host. Scans display bounded metadata; large declared numbers remain exact u64 and payload ranges are rechecked at the payload phase.
- Each task has a 64 MiB metadata-read budget; subsequent local headers, descriptors, compressed data, ciphertext, and password retries share one cumulative 20 GiB input budget. Names and snapshot identity cannot be guessed again during payload handling. Actual output is staged first and host-committed only after full reading and successful verification.
- Check local/central names, critical flags, method, CRC, sizes, AES profile, and ZIP64 width per entry. Data and optional descriptors must end before the next local record and central directory, never crossing into other records. Store verifies exact size and CRC; Deflate additionally requires strict raw-stream EOF. Validate 32/64-bit descriptors with or without signatures by matching fields; a CRC equal to the signature must not be mistaken for one.
- AES-256 uses a 16-byte random salt, format-specified PBKDF2-HMAC-SHA1 parameters, two 32-byte keys, and a two-byte password verifier. CTR begins at 1 with little-endian block encoding. Compute HMAC-SHA1 over ciphertext only and verify the first 10 authentication bytes. AE-1 also verifies CRC; AE-2 requires declared CRC zero. Authentication failure is an integrity failure and must not masquerade as a definite wrong password.
- Passwords remain borrowed from the host; the format layer does not persist or print them. Derived keys and stream states have zeroizing lifetimes; AES/HMAC/SHA1 enable cleanup features from foundation libraries. Erasure of every historical Qt, input-method, or CPU copy is not guaranteed. Output before authentication completes has no publication eligibility.
- Creation uses streaming output, explicit descriptors, and ZIP64 boundaries. Directories are plaintext; regular files can select Store/Deflate and AES. The host splits and commits numbered volumes only after complete archive verification. Regular rewriting retains valid compressed payloads, comments, and admitted metadata while recalculating record offsets. Encrypted/split archives, self-extracting prefixes, and metadata that cannot be safely retained remain rejected for modification. Empty archives also check material before the central directory; absence of local records cannot discard prefixes. Truly empty archives can receive content and retain archive comments.
- Modification time is written to the DOS field with a precise-second extension. Nonnegative Unix seconds fitting signed 32-bit use the UT extra; other representable times use NTFS FILETIME mtime. NTFS atime/ctime are zero and do not have valid-time meaning under [Common ZIP conventions](https://commonzip.org/spec/#lastmodifiedtimestamp); APPNOTE itself does not define zero as missing. Negative Unix seconds do not use UT, avoiding interpretation as future dates by independent tools. Regular rewrites retain original time extensions and do not invent access or creation times.
- Renaming sets the UTF-8 flag and removes stale Unicode Path extras. The flag also declares entry comments UTF-8, so reject renaming and preserve the original archive if the original comment is not valid UTF-8; do not silently transcode or drop it. Unrenamed records may retain original flags and comments.

`rawzip`, `zip`, and `flate2` are test references only; ordinary and build dependency closures for migrated ZIP must not reintroduce these format or algorithm libraries. Test-reference licenses remain. A readable container does not imply every declared method is decodable.

## 7z read/write specification

`xdzip-codec-7z` is an in-house read/write backend running in the existing isolated worker, with no official handler or failure fallback. The container handles method graphs, compressed headers, external attributes, substreams, raw UTF-16LE names, and physical EntryIds. Its graph executor calls shared algorithms and independent AES wrapping without path or publication authority. Official 7-Zip source and container adapters are excluded from product builds; pinned official reference tools are tests only. See [7z sources](sevenzip-format-sources.md) for specifications, reference-analysis roles, and licensing distinctions.

Method graphs stream according to actual port relationships, retaining dictionaries, models, and bounded node buffers without materializing or caching the entire payload folder. Metadata terminal output remains limited to 64 MiB. Metadata, dictionaries, models, node buffers, and workspace are jointly admitted against the default 1 GiB before allocation. A file is at most 8 GiB; actual task input and terminal decode work are each at most 20 GiB. Reverse access and restarts are charged again. Sequential reads within one solid folder retain graph state. If a file has an independent substream CRC, exact size and that CRC suffice to complete that file; later files continue the same graph. Without an independent substream CRC, complete folder termination and any folder CRC before completing the file. At full completion, verify all connected packed ranges, node sizes, EOF, and supplied CRCs; unreferenced extra payload is not treated as ordinary file-check scope.

Header, Additional, and payload share the graph executor. Metadata reads and outputs are separately subject to scan budgets. Initialize payload input and terminal-work counters only once when entering payload; restarts do not reset them. Intermediate-node work and AES KDF accumulate across both phases. Only terminal output counts as actual host decode work, including unselected ranges. Intermediate nodes have a separate cumulative-work limit; AES, decompression, and filter output at every layer cannot each be charged as the same file's host work. Recursive reads reserve the current node's budget before calling upstream; failed operations release unperformed reservations, not completed work.

AES KDF admission uses actual cumulative rounds and hash-input bytes. Failure or retry does not refund credit, and output quotas cannot buy unbounded hashing. Cache at most 16 derived keys per task, matched by password, iteration parameters, and salt; IV is not part of derived identity. Password changes clear old caches; no reuse across sessions. Cache hits do not invent extra KDF work. Fixed caches and password copies count as 16 KiB in preflight; a node verifies the key matches its own KDF parameters before use. Passwords, keys, owned hash state, and candidate content buffers have zeroizing lifetimes without claiming that all historical Qt/system copies can be erased.

LZMA1/2, BZip2, PPMd7, and shared Deflate/Deflate64 live in `xdzip-compression`, whose production dependencies remain empty; no corresponding compression algorithm libraries are introduced. Deflate64 switches format differences within the same Deflate implementation; ZIP, GZIP, and MSZIP retain ordinary mode. PPMd7 explicitly distinguishes known-length and END profiles; format-model restarts cannot replace host memory admission. The LZMA2 writer supports bounded search levels 1/6/9 and uses format-permitted raw fallback when one chunk has no benefit. An implementation containing only raw chunks is not called a completed compressor. Shared readers explicitly bound packed ranges and return successful EOF only after a verified complete terminal state; they cannot continue after errors. A `Read` output-slice limit does not imply the same CPU bound for an individual block or model operation.

AES uses admitted general AES, SHA-256, randomness, and zeroize primitives. Format attributes, UTF-16LE password KDF, CBC composition, and block trimming are independent implementations; no 7z library is introduced. CBC itself provides no authentication; the container must complete CRC and size checks actually supplied. Arbitrary integrity failures cannot be reported as definite wrong passwords. Creation profiles, secret cleanup, and final publication still require host end-to-end acceptance.

Creation streams Copy or LZMA2 levels 1/6/9 to host random staging; solid affects file grouping only. Each encrypted folder and encrypted header uses a fresh random IV, with matching KDF identities reused within the task; header names remain inside the encrypted region. After reading the declared input length, check actual EOF and frozen source identity, including empty files; do not synthesize EOF. Host and worker both limit read/write blocks, offsets, cumulative work, and actual output. Progress messages grant no read/write permissions.

Rewriting supports only unencrypted, non-split archives whose records are safely preservable regular files or directories. Unknown required metadata, anti entries, links, and special objects are explicitly rejected. The worker retains at most 512 MiB of preserved and new content; dictionaries, models, metadata, and working set are preflighted together within the default 1 GiB. Rebuild preserved original attrs, ctime, atime, and mtime using understood fields; physical order and duplicate-name record identities are not merged. Rewrite follows selected FilesInfo entities and reorganizes compression graphs; folders referenced by no files and unreferenced attribute blobs are outside structural-preservation commitments. Source revalidation, whole-archive verification, and same-volume atomic publication remain host responsibilities.

## CAB read-only specification

`xdzip-codec-cab` is an in-house read-only backend for Store, MSZIP, LZX, Quantum, and same-directory volume chains already authorized by the host. The product uses Rust with no official handler or runtime failure fallback; official Cab containers and CAB-specific LZX/Quantum algorithms are excluded from compilation. CMake's internal `XDZIP_CAB_BACKEND=rust` records fixed build identity and is not a selectable product backend. Development, platform, and manual desktop acceptance are maintained separately in [task #48](https://github.com/xiaodaozhi/xdzip/issues/48) and related acceptance entries; they do not automatically approve release.

The container follows MS-CAB; MSZIP follows MS-MCI and reuses shared Deflate. LZX and Quantum call independent decoders in `xdzip-compression`. See [CAB sources and implementation basis](cab-format-sources.md) for official archive-document status, limits on authenticity of the mirrored 1997 LZX original, MS-PATCH versus CAB differences, and separation between the reference analyst and source-unread implementers. Rust implementation does not remove these source and role limitations.

- `ReadSource::volume_lengths()` and `volume_names()` supply frozen physical volume boundaries and original volume names. The host discovers, identifies, and authorizes same-directory volumes, at most 1,024. The format layer interprets offsets within each volume and checks addition of volume bases; it cannot read beyond one volume into the next. Volume names and disk labels grant no file access. Missing volumes or contradictory set/index/name/continuation data fail the entire scan without a partial index.
- Scanning checks container version, reserved fields, region bounds and non-overlap, file ranges, and CFDATA fragments. For an unfinished cross-volume frame, check each fragment checksum before concatenating a logical compressed frame. A folder is a compression/dictionary unit, not a filesystem directory. Only a new logical folder resets history; file and physical-volume boundaries do not. The last frame may be short; earlier complete logical frames each output 32,768 bytes. Unknown compression methods or parameters explicitly return unsupported; do not skip them and publish incomplete content.
- Merge only continued records explicitly defined by the specification into one logical file; names, offsets, sizes, times, and attributes must agree. Preserve ordinary duplicate names, duplicates, and overlapping output ranges separately. Allocate `EntryId` consecutively from 1 by physical appearance of the first CFFILE, not name order or source offset. Public `Entry.method` retains existing value 0; actual compression methods stay in private folder metadata. DOS times retain their original values without invented time zones.
- Resolve names archive-wide through `names::resolve_cab`. Preserve raw bytes and CFFILE UTF-8 declarations separately; `scan_with_encoding_flags` also returns original declarations. Do not infer a declaration from `NameEncoding` after resolving an ASCII name. Strictly decode legacy names before converting CAB separators to shared paths so Shift-JIS trail byte `0x5c` does not become a separator. Damaged declarations remain visibly warned and cannot be output; host code pages do not replace them. See the [filename encoding contract](filename-encoding.md).
- Read-only capabilities include metadata and regular-file contents, not creation, rewriting, execution, or link/special-object output. Empty files also verify required frames and history. On payload open, rescan and compare every frozen entry snapshot. Every reached CFDATA must fully verify its checksum, compressed-stream termination, and exact output length; do not truncate frame verification at the selected file's last byte. A zero CFDATA checksum means no checksum was supplied and does not establish content authentication. Preserve cancellation, quota, and source I/O failure categories; do not swallow them as success or retry unconditionally. A payload instance cannot continue from partially updated state after decoding fails.
- Default metadata reads are at most 64 MiB, physical CFFILE records at most 100,000 including continuation copies, logical folders at most 100,000, and physical CFDATA fragments at most 1,000,000. Shared scan budgets default to 4,096 bytes per name, 16 MiB total raw names, and 16 MiB decoded/display text; lower caller limits still apply. After payload-instance rescanning, actual input continues to accumulate. Input and decode work are each at most 20 GiB; the host's per-file limit is 8 GiB and does not expand CFFILE field ranges. Check all length arithmetic, allocations, and source ranges before use.
- Complete logical frames output at most 32,768 bytes. Store, MSZIP, and LZX compressed frames are limited to 32,768, 32,780, and 38,912 bytes respectively. Quantum complete compressed frames have a 1 MiB resource-admission limit, not a claimed official format maximum expansion. Cross-volume splitting does not expand one logical frame's limit. Decode state and one output frame are bounded and retained; sequential selected files in the same folder may reuse state and that frame instead of replaying the whole prefix for each file.

CAB and ISO/UDF share `xdzip-codec-bridge`, using synchronously borrowed CXX callbacks inside the existing isolated worker to read authorized streams and send metadata and bounded output. Volume arrays and byte slices are borrowed only during the call; exceptions and unwinds do not cross the boundary. The direct codec API is for the worker and independent probes and does not replace product process isolation. The host retains cancellation, forced termination, source revalidation, staging, and final commit.

Complete-frame accounting uses `DecodedSink::charge_skipped` and `write_precharged_chunk`. After completely decoding and validating a new frame, first charge its entire output byte count as actual work, including bytes before and after the selected interval, then deliver selected content. The container retains an equal unconsumed allowance for the cached frame. Output may use prepaid delivery only within remaining allowance; repeated or overlapping delivery after exhaustion uses ordinary `write_chunk` and is charged again. Switching frames discards unused old credit. Names, entries, or offsets do not automatically exempt repeated output. A sink without prepaid support defaults to ordinary writes; this may conservatively double-charge but preserves output and limit checks.

The worker protocol requests host admission using `WORK` (17, little-endian `u64` byte count) and sends already credited content using `PRECHARGED_DATA` (23), with at most 64 KiB per output block and host ACK. The Native receiver allows nonempty prepaid output only for CAB, 7z, and RAR within admitted credit for the same ongoing worker. Other formats or insufficient credit are rejected; exact declared size is still verified at entry completion. Worker restart, termination, or failure cannot reuse old worker credit. Runtime extraction and check sinks independently verify task-private allowances. Normal file changes may retain unconsumed allowance, but consumed credit cannot be reused. Prepayment only avoids re-adding already counted work: declared file size, 8 GiB per file, 20 GiB cumulative actual output, cancellation, and write-failure checks remain. Deduct credit before delivery; partial output failure does not refund it. Host rejection of `WORK` creates no credit. RAR auxiliary work has separate admission and grants no prepaid output credit; see the [auxiliary work contract](auxiliary-decoding-work.md).

## ISO and UDF read-only specification

`xdzip-codec-optical` receives only borrowed `ReadSource`; it does not access filesystems or mount images. ISO follows [ECMA-119 fifth edition](https://ecma-international.org/wp-content/uploads/ECMA-119_5th_edition_december_2024.pdf) volume descriptors, directories, extended attributes, and appendix C Joliet; [Rock Ridge 1.12](https://bitsavers.org/projects/cdrom/Rock_Ridge_Interchange_Protocol.pdf), SUSP 1.12, and [El Torito 1.0](https://bitsavers.org/projects/cdrom/El_Torito_CD-ROM_Spec.pdf). UDF follows structural limits, partitions, and character sets in [ECMA-167 third edition](https://ecma-international.org/publications-and-standards/standards/ecma-167/) parts 1, 3, and 4 and [OSTA UDF 2.60](https://www.osta.org/specs/pdf/udf260.pdf). The implementation does not translate third-party parser source; original specifications and third-party test tools are not relicensed as project-original material.

- ISO checks both-endian integers, volume ranges, directory records, and file extents. It supports multi-extent regular files, Joliet UCS-2, Rock Ridge name continuation, SUSP CE, CL/PL/RE directory relocation, and link/special-type identification. Non-Joliet raw names use shared bounded encoding resolution without system OEM conversion. Boot catalogs and images are represented only as readable records. Reject cross-volume ISO, interleaved files, record-oriented extended attributes, Rock Ridge SF sparse, and ZF compressed extensions; unknown mandatory features cannot be decoded as ordinary files.
- UDF distinguishes logical block numbers from physical offsets and validates descriptor-tag location, checksum, CRC, and size. It handles primary/backup anchors, VDS continuation chains, FSD, FE/EFE, FID, and ICB. Physical, sparable, VAT 1.50/2.x, and metadata/mirror partition mappings are admitted separately. The standard `*UDF Non-Allocatable Space` system record on a sparable partition is validated under OSTA 3.3.7.2 for name, type, Metadata/System/Stream flags, zero information length, and unrecorded tail allocation. It is system metadata only, not an output entry. Short, long, extended ADs, and continuations use actual recorded/information lengths, supporting inline, unrecorded zero extents, and noncontiguous content without assuming summed ranges are contiguous. Directory graphs, allocation chains, and mapping cycles are bounded; CS0 converts strictly to Unicode.
- Reject named streams of UDF regular files, unknown system streams, transformed data, unknown mapping/ICB policies, and uninterpretable extended-AD length combinations. Real-time and other special files are marked non-outputtable; symbolic links and multi-linked regular files are also rejected for output. Failure after identifying UDF does not switch to ISO. In-spec VDS/metadata redundancy recovery does not change the selected namespace.
- Allocate EntryId in original directory-record traversal order for the selected namespace, not decoded-name order or merged duplicate names. File-data sector offsets are not entry identities. Parse results retain separate extent lists for data, zero extents, and inline content. Rescan and compare frozen metadata on payload open, then validate entry identity, range, and exact output length while decoding. Formats without per-file CRC do not gain an invented integrity guarantee; same-size content changes may still be readable. Host source-identity checks remain independent.
- Metadata reads are at most 64 MiB, ordinary entries at most 100,000, names at most 4,096 bytes each, with total names/display text under shared scan budgets. Total output extents are at most 1,000,000; total inline data at most 64 MiB. ISO directory depth is at most 256, and CE per record at most 128 regions and 1 MiB; host output paths still use stricter shared limits. UDF permits at most 256 partition maps, 262,144 extents per allocation table, and 4,096 continuations. Check overflow for all additions, multiplications, and source ranges.
- Actual decoding retains limits of 8 GiB per file and 20 GiB each for cumulative work and input, using bounded read/output buffers. `xdzip-codec-bridge` passes authorized streams through synchronous borrowed CXX callbacks in the existing worker. Exceptions and unwinds do not cross the boundary; process termination fails unfinished output. The host retains memory governance, cancellation, forced termination, source revalidation, private staging, and final commit. Official 7-Zip Iso/Udf handlers are removed from builds and registry with no runtime fallback.

Independent samples must have verifiable generating tools or provenance and known contents; self-encoded specification vectors verify only internal state combinations. Independent real samples and three-platform acceptance for metadata, VAT, sparable, and other extensions are recorded separately in [migration task #47](https://github.com/xiaodaozhi/xdzip/issues/47). Code existence or a passing physical-partition sample does not establish acceptance of other mappings. Record test tools, reference workers, and product workers separately by identity; samples unsupported by reference tools are not marked verified.

## Capability and verification baseline

| Backend | Capabilities to retain | Independent implementation elements |
| --- | --- | --- |
| ZIP | Store/Deflate, ZIP64, AE-1/AE-2 AES-256, existing split volumes, creation and regular archive modification | Records, extra fields, data descriptors, encryption wrapping, shared Deflate |
| TAR, TAR.GZ | ustar, existing PAX/GNU, regular files/directories, creation and modification, multi-member GZIP | Record layer, extension state, streaming writes, GZIP framing and shared Deflate |
| 7z | Store, LZMA/LZMA2, PPMd, BZip2/Deflate decoding, BCJ/BCJ2, branch and Delta filters, solid archives, passwords/header encryption, numbered volumes, creation and limited rebuilding | Decode graphs, actually admitted method combinations, resource and encoding policies; a lower-level encoder does not expand product creation options |
| RAR | Existing read-only limits for legacy, RAR5, RAR7, passwords, solid archives, and split volumes | Version-specific decoders, filters, encryption wrapping, and state resets |
| CAB | Store, MSZIP, Quantum, LZX, same-directory volume chains | Records, file/folder mappings, cross-block dictionaries, and cross-volume files |
| ISO, UDF | ISO9660, Joliet, Rock Ridge, UDF, hybrid-image selection | Volume/partition mappings, namespaces, extents, directory graphs, and special-item restrictions |

Each switch requires bidirectional interoperability (independent sample reading for read-only formats), corruption/truncation, numeric overflow, resource limits, cancellation, and actual host business-path regression. An in-house encoder and decoder succeeding together does not prove compatibility. Fuzzing and benchmarks use pinned sources and record actual coverage and duration; limited random mutation tests are not called long-term fuzzing. Actual Windows, Linux, and Apple Silicon automated and desktop checks are recorded separately. Formal release still requires independent license review.
