# Built-in format declarations

The built-in declaration source is [archive-formats.json](../../specs/engineering/archive-formats.json). It records stable format identifiers, labels, container families, outer compression, existing private worker identifiers, supported method families, creation suffixes, checking strength and entry-point candidates. Method families summarize the corresponding format contracts; they do not promise every parameter, historical variant or combination. Actual records, host policy and platform capabilities narrow the declaration before an operation starts.

Checking strength describes the outcome of a successful [integrity check](archive-checking.md). `supported_content` verifies supported payloads. `structure_and_readability` verifies structure and readability without promising a payload checksum. `format_declared_checks` verifies the checks present in the stream, including profiles that carry none. Check eligibility is separate from strength. For example, the NSIS profile recognizes bounded installer metadata and has no check operation. Creation method identifiers resolve within each format's admitted write methods.

`creation_methods` assigns host transport identifiers to method names; `creation_levels` admits levels per format. Generated GUI choices and Rust descriptors carry both. The CLI, GUI and host resolve the same declaration rather than assuming every compression method is Deflate or LZMA2. Store and Copy retain identifier 0, Deflate 8 and LZMA2 32; Zstandard uses host identifier 93 and LZ4 uses 256, scoped to its container and never interpreted as a ZIP method. Read-only profiles have no creation levels. The generator rejects missing or ambiguous per-format identifiers and invalid levels.

| Operation | Built-in coverage |
| --- | --- |
| Create a new archive | ZIP, 7z, TAR, TAR.GZ (`.tar.gz`, `.tgz`), standalone GZIP, XZ/TAR.XZ, LZ4/TAR.LZ4, Zstandard/TAR.ZST, LHA (`.lha`, `.lzh`), ISO9660/Joliet and the Windows x64 ZIP SFX wrapper. A standalone stream takes one regular file. See [creation](zip-creation.md) and [single-file streams](single-file-streams.md). |
| Rewrite an existing archive | Eligible ZIP, 7z, TAR and TAR.GZ archives. Encrypted, split and other archives with unsupported records or storage are excluded, subject to the [modification contract](archive-transfers.md). |
| Browse, extract, open a member, export or check | Each operation has separate capability and record checks. For example, certain installers can be inspected as metadata only. See [read-only browsing](readonly-browser.md) and [checking](archive-checking.md). |

Run `python3 scripts/generate-format-registry.py` after changing the specification. It generates the Rust codec descriptors, C++ drag-and-drop/Shell candidates, JavaScript UI choices and Python installer icon mappings. `--check` rejects missing or stale output without changing files. `python3 scripts/test-format-registry.py` checks contradictory capabilities, duplicate identifiers/suffixes, invalid generated-language values and stale consumers. Routine CI runs both checks.

Opening first uses entry-point and source rules from [archive opening](archive-opening.md), then probes and validates authorized bytes. A suffix or MIME type offers an entry point. The host still checks source identity, operation parameters, output authorization and publication. `worker_id` selects a built-in worker route for reading and identifies no external plugin. In particular, ISO reading uses the worker, while new ISO images are written in the Rust host. The registry tracks creation and existing-archive modification separately.

Entry-point candidates distinguish drag-and-drop from Shell menus where required. Ordinary `.gz` now offers both entry points and single-file creation; `.tar.gz` and `.tgz` keep their TAR container semantics. XPI/APK/IPA/CBZ candidates retain ZIP validation and admitted profiles. See [single-file streams](single-file-streams.md). Split-volume spelling and source authorization remain governed by [archive opening](archive-opening.md); the registry does not reinterpret numbered files. Windows uses final-extension icon mappings, so `.tar.gz` uses the `gz` association.

Add only implemented declarations with matching automated acceptance. Source changes update the [in-house format contract](independent-rust-codecs.md), [format-worker contract](native-codecs.md), user capability documentation and [acceptance entries](../../developers/qa/acceptance.md) as applicable. Keep plans, progress and execution conclusions in issues, and generated test evidence under `build/` or CI artifacts.

`creation_wrappers` declares the Windows x64 ZIP SFX wrapper and its explicit `.sfx.exe` suffix. It reuses ZIP method identifiers and disables encryption and volumes. Generic EXE handling is excluded. ISO9660 creation uses host method identifier 260 and fixed level 0. See [ISO creation](iso-creation.md) and [owned SFX creation](sfx-creation.md).
