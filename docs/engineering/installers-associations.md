# Installers and file associations

Experimental Windows MSIX declares the same extensions as Open With candidates in its package manifest without taking the user's default choice. Packaged processes do not read ordinary installed-edition association registrations as their own management state; users manage defaults in Windows Settings. Actual file activation, icons, coexistence, and uninstall await target-system acceptance; see [MSIX builds](developer-build.md#windows-msix-实验构建).

See the [file-association icon specification](../visual/file-association-icons.md) for per-format artwork and platform mappings. Linux retains system MIME icons. Installation does not change defaults or existing registration scope.

Desktop packages from `v0.2.0` and current source builds place the CLI in a separate `cli/` directory, or `Contents/Helpers/cli/` on macOS, retaining existing GUI and file-association entry points. Earlier release assets do not acquire this feature retroactively. The Windows installer offers an opt-in per-user PATH option and detects same-name command conflicts; uninstall revokes only its installation directory. Mac/Linux explicitly run the private CLI's `setup`. Standalone CLI packages also use `setup` to install user-level version directories and a stable launcher, without changing shell configuration. `setup --remove` revokes registration while retaining version directories for inspection. See the [CLI installation contract](command-line.md#构建与命令安装).

This page describes local development and on-demand verification artifacts: a Windows x64 per-user installer, Ubuntu 24.04 amd64 X11 .deb, and [local macOS development DMG](macos-deployment.md) built on explicit request. These local artifacts remain experimental development delivery and do not replace official Releases. Formal `v0.1.0` platform packages were generated and verified by the dedicated Release workflow under the separate [release protocol](release-protocol.md). Personal open-source releases require no paid certificate, Developer ID, or notarization; macOS retains necessary ad-hoc integrity signing. Ordinary CI does not deploy or upload Mac apps. See the [support policy](support-policy.md).

Current source builds use `xiaodaozhi` as Windows installer publisher, Linux package maintainer, and update-policy vendor. These metadata fields do not replace publisher-certificate signing; existing releases retain original metadata.

For manual macOS updates, prefer the matching Release DMG. With app.zip, first extract and move xdzip.app out of Downloads, quit the running old version, then replace the copy in Applications. Downloading is not installation; an unnotarized package may trigger system warnings. See the [software update contract](software-update.md) for fallback conditions.

See the [file-manager actions contract](shell-actions.md) for context menus, the independent operation host, and owned registration lifecycle. Context actions do not open the browsing main window and do not open the destination folder on completion by default.

## Shared build entry point

See the [developer build guide](developer-build.md) for environment preparation and order. After a clean build and test for the same commit, use `python3 scripts/desktop.py prepare --packaging` to prepare pinned materials, then run package and verify. Do not use the full CI script directly for routine development.

Windows/Linux `package --kind runtime|installer|all` share one deployment and audit chain, defaulting to `all`. runtime first generates the deployed directory; installer builds from the verified runtime in the same output-dir, and Linux also creates tar.gz. macOS supports only local `all` development DMG. Artifacts and receipts are in the specified output-dir, default build/package. Preparation may download pinned packaging tools and materials but does not install xdzip or automatically install system compilers/SDKs. Windows prepares CRT/Inno Setup, Linux requires preinstalled patchelf and Debian tools, and Mac uses system deployment and ad-hoc integrity tools.

Ordinary `verify` checks existing runtimes/packages. Windows clears SDK search paths in an isolated copy, Linux uses an isolated runtime container, and Mac uses DMG relocation and Cocoa/Metal. It does not by default run installation, upgrade/rollback, or association lifecycles or write user defaults. Installation mechanisms and disposable CI checks below remain separate gates; runtime success cannot replace them.

## Windows

The installer presents the original Microsoft VC++ runtime agreement included with the package. Its license page identifies applicable components and requires acceptance, then displays bilingual Windows-runtime-NOTICE.txt. Portable packages include the same original text and explanation. Project-original code remains Apache-2.0; Qt and other components' original licenses and replacement rights are unaffected. Verify hashes and complete descriptions before compiling; material attachments retain the same text. See [Windows licensing](windows-licensing.md).

Portable packages and installers use the same deployed directory. [deploy_windows.py](../../scripts/deploy_windows.py) calls windeployqt, then follows the pinned Qt Quick Basic policy to remove FluentWinUI3, Fusion, Imagine, Material, Universal, Windows, NativeStyle/Effects referenced only by styles, qmltooling, and .qmltypes. Basic, Controls impl, Templates, runtime QML, and qmldir remain; Qt Widgets qmodernwindowsstyle still serves native controls. New deployment directories do not carry DXC, DXIL, or D3DCompiler; deployment fails if these names occur anywhere. `opengl32sw.dll` is not included in new deployments. An existing root copy is removed in controlled staging; same-name remnants elsewhere fail deployment. Adding a new style or Effects functionality requires updating deployment policy and reverification.

Qt Quick defaults to Direct3D 11 on Windows. With inadequate hardware or driver capabilities, Qt may fall back to Direct3D WARP; that is distinct from software OpenGL. New packages do not promise Mesa software fallback through `QT_OPENGL=software` or the OpenGL backend. Historical packages and their license materials remain unchanged. [Qt's Windows graphics documentation](https://doc.qt.io/qt-6.8/windows-graphics.html) describes default and explicitly requested software devices.

VC++ is deployed app-local using the official Microsoft x64 14.44.35211 runtime from [pinned sources and hashes](../../scripts/windows-runtime.json). The [preparation script](../../scripts/prepare-windows-runtime.py) extracts with pinned WiX tools and verifies every DLL and license text without executing EXE/MSI installers or copying from System32. Deliver required MSVCP/VCRUNTIME DLLs, licenses, and provenance; tools, CAB, MSI, and the unexecuted vc_redist installer do not enter the product. Windows 10/11 provides UCRT. App-local runtimes must be maintained with product updates; system-wide runtime updates cannot be relied on to replace them. See [Microsoft deployment methods](https://learn.microsoft.com/en-us/cpp/windows/choosing-a-deployment-method).

[Deployment regression](../../scripts/test-windows-deployment.py) checks trimming and missing-runtime boundaries. [Actual runtime verification](../../scripts/verify_windows_runtime.py) rejects software OpenGL DLLs, adds test DLLs to an isolated copy, clears SDK search paths, and checks system translations, settings restart, native title bar, and bilingual startup. After clearing render overrides it checks default D3D11 scene-graph initialization and explicitly requests WARP, verifying the actual selected Microsoft software device. Explicit requests do not establish automatic fallback under failure or replace manual visual acceptance. Test files do not enter the product directory; this does not replace clean-Windows install/upgrade/uninstall acceptance.

build-windows-installer.py accepts only a clean-build deployed audit and rechecks every file's SHA-256. See [toolchain configuration](../../scripts/installer-toolchain.json) for pinned Inno Setup 6.7.3, official installer hash, source commit, Simplified Chinese resources, and license text. The compiler does not enter the product; notices include the license text. The wizard supports Simplified Chinese and English according to system language.

The installer uses a fixed AppId and PrivilegesRequired=lowest, installing by default under the current user's LocalAppData/Programs/xdzip without administrator rights. The main executable is xdzip.exe at the installation root with Qt libraries alongside it; plugins, QML, translations, and notices retain necessary subdirectories. Shortcuts, associations, and uninstall display icons point to the root, without a versions/commit-hash product hierarchy. Commit and binary hashes remain in build and installer receipts rather than installation paths. Inno Setup's [cumulative uninstall log](https://jrsoftware.org/ishelp/topic_appendnotes.htm) records files owned by each installation without recursively deleting extras. Settings and recent items remain in existing user configuration directories and are not removed by the installer.

The new layout writes a bounded install-manifest.txt of audited relative paths and SHA-256. Before upgrade, validate old manifest paths, duplicates, and sizes; reject path escape, device aliases, and reparse points in cleanup paths. If files to be retired were modified or cannot be verified, stop installation before writing. After successful installation, clean only files listed in the old manifest that are no longer delivered and still hash-match; remove only empty directories and retain extras. Even repeated completion events in one installation trigger cleanup only once. Files changed or held during cleanup remain with a retry record and nonzero exit code 20. Failure to write a retry record requires manual repair; transactional recovery or power-loss safety is not claimed. This per-user installation assumes external processes do not concurrently modify the directory; path/hash rechecks are not handle-based malicious-race isolation.

Existing version-directory layouts upgrade directly. Launch commands and shortcuts move to the root while settings and recent-item locations remain. The old installer did not deliver a separate ownership manifest, so historical versions/ directories remain until normal uninstall; Inno's cumulative log cleans originally recorded files without recursive directory deletion. User-added files remain. Rollback can reinstall a chosen older version; older QA fixtures retain historical layouts and can later upgrade again to the root layout. Fresh installation does not create versions/. This does not include automatic full erasure of the old installation directory.

The product holds the `Local\xdzip.desktop.running` named mutex throughout its lifecycle. [AppMutex](https://jrsoftware.org/ishelp/topic_setup_appmutex.htm) blocks install/uninstall, with CloseApplications=no and no forced application termination. FFI handle creation failure prevents startup; process closure releases it. Task exit still uses the existing decision and Rust join barrier.

Associations write only HKCU: owned ProgIDs, two owned Applications entries, Capabilities, RegisteredApplications, and owned values in OpenWithProgids. They do not write HKLM, extension defaults, or protected UserChoice/UserChoiceLatest. Uninstall does not remove other applications' candidates. Nine extension categories use `xdzip.Archive.<format>`, with ZIP using `xdzip.Archive.ZIP`; document icons use format-specific ICOs. The legacy shared `xdzip.Archive` retains its direct open command and is marked `NoOpenWith` along with `Applications/xdzip.exe`. Upgrade removes only old shared recommendation values from each extension's OpenWithProgids and old SupportedTypes values from the main executable, not the compatibility command. Existing old defaults still open but may retain the ZIP document icon; users may reselect the format-specific xdzip candidate in system settings. When Windows recognizes only the final extension, `.tar.gz` uses the GZ icon.

The nine format-specific ProgID descriptions use application language, for example Chinese `ZIP 压缩包` or English `ZIP archive`, without an xdzip prefix. Installation or upgrade reads the local application's saved language and defaults to Simplified Chinese without a valid setting; wizard language does not change application language. Normal installed applications synchronize these descriptions and notify the Windows Shell at startup and after a successful language change. Before writing, check installation identity, current executable location, installation manifest, association launcher, and all nine existing open commands. If conditions do not match, do not write or create missing items. Registry writes can partially succeed; normal startup retries later. Portable, development, and test processes using temporary settings/language do not touch descriptions. The legacy shared ProgID remains compatible without per-format names. Explorer caching, system type identification, and the user's chosen default handler may affect display; native visuals need separate acceptance.

Disposable Windows CI checks installed-product startup synchronization in Chinese and English and uses a portable copy and isolated-settings process to verify no writes. It also checks that nine icons, commands, other candidates, and defaults are unchanged. This automatic check does not simulate changing language while running and does not replace manual Explorer or Settings display acceptance.

Quoted commands for all format ProgIDs launch `xdzip-association.exe -- "%1"`; its Applications registration carries complete SupportedTypes so “Open With” shows one xdzip application entry. The launcher embeds the same branded application ICO and distinct OriginalFilename and product-version resources. Verify application icons separately from per-format document icons; document DefaultIcon cannot replace executable application resources. The small GUI launcher accepts one file argument, initializes COM single-threaded apartment on its own thread, and delegates the existing open command through ShellExecuteEx with explicit `xdzip.Archive` class without a command interpreter; release COM after the call. Legacy rollback updates the shared entry, so per-format candidates still point to the rolled-back program. COM initialization failure, missing entry point, invalid arguments, or system rejection return nonzero without trying another application or changing defaults. This depends on rollback installation retaining the launcher in the current installation directory; install/rollback and cumulative uninstall require actual tests.

The legacy shared ProgID and nine individual ProgIDs set `AllowSilentDefaultTakeOver` as REG_NONE. Under [Windows ProgID conventions](https://learn.microsoft.com/en-us/windows/win32/shell/fa-progids), this directs the system to ignore the candidate during automatic default selection while retaining explicit Open With selection. Inno `ValueType: none` creates only a key, so the installer uses a bounded native registry call to write the exact type. Open only already-created owned ProgIDs; failure stops installation and releases handles on failure paths. On-demand installation checks also snapshot protected choices and verify native candidate counts and automatic fallback routing. Actual Settings and Explorer presentation is checked as needed and recorded honestly when unperformed.

ZIP, TAR, TGZ, GZ, 7Z, RAR, CAB, ISO, and UDF register as candidates. GZ is only for TAR.GZ; standalone GZIP remains unsupported, and associations do not expand format capabilities. CAB, ISO, and UDF are read-only. Generic `.img`, `.001`, or `.rNN` extensions are not registered to avoid claiming other file types; split volumes remain openable through the application's file chooser. Users choose defaults in system settings; the installer does not bypass confirmation.

## Ubuntu 24.04

build-linux-installer.py creates .deb from the same verified directory. Private staging directories are distinguished by output path, allowing the same package name to be rebuilt in different candidate directories without overwriting existing staging. Package name is xdzip, version binds product channel and commit, and architecture is amd64. System dependencies come from actual deployment manifests plus desktop-database and lock tools; glibc is at least 2.39. Qt/QML/plugins and notices reside under /opt/xdzip/versions/; /usr/bin/xdzip is a quoted fixed-target forwarding entry. dpkg replaces and removes old package files; rollback requires retaining the original .deb.

The desktop file registers ZIP, TAR, compressed TAR, 7z, RAR, CAB, ISO, and UDF under the [MimeType and Exec specification](https://specifications.freedesktop.org/desktop-entry/latest-single/), using %f for single-file launches and -- as the argument boundary. CAB and ISO use system MIME types; the package supplies a UDF MIME declaration matching only `*.udf`, not `*.img` or generic binaries. Refresh MIME and desktop databases after installation/removal. Do not run xdg-mime default or modify mimeapps.list or global MIME icons. Uninstall removes owned launchers, icons, and runtime files and refreshes caches, retaining user settings and extra files.

The installed product holds a shared flock on /run/xdzip/usage.lock. Maintenance scripts first obtain a nonblocking exclusive lock and fail if an active process exists. Scripts set an installing gate under root-owned /run/xdzip; the product checks again after acquiring its lock to avoid starting between dpkg hooks. Reject symlinks or incorrect owner/permissions; closing QFile releases the lock. tmpfiles.d prepares the runtime lock at system startup. This does not affect SDK development applications.

Successful and dpkg abort paths clean the gate. Interruption or power loss can leave an unfinished transaction; run sudo dpkg --configure -a and fix the actual error. Inability to start is not installation success. Scripts do not recursively clean user directories; artifacts are generated only under build/ or CI.

## macOS and file opening

The main application and delivered package declare documents and ICNS as Viewer/Alternate in Info.plist, [without claiming default ownership](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html). Development and test builds default to Viewer/None and do not enter system Open With candidates. Primary development packages or delivery builds must explicitly set `-DXDZIP_MACOS_HANDLER_RANK=Alternate`. Users and Launch Services determine defaults; the application does not actively change them. Clean up temporary registrations for development verification copies under the [Mac maintenance method](macos-deployment.md), preserving existing apps and user defaults.

CAB, ISO, and UDF join the same read-only Viewer declaration. Imported CAB and UDF types declare their respective extensions and MIME types; ISO uses `public.iso-image`. Do not add `.img` or a generic `public.disk-image` document handler. Actual content detection and the [format backend contract](native-codecs.md) still govern support.

Each type declaration uses its corresponding bundle ICNS. When the system recognizes `.tar.gz` and `.tgz` as one compressed-TAR type, they share the TAR.GZ icon. The GZ candidate still supports TAR.GZ content only. Finder caches, selected defaults, and system type identification affect actual display; native presentation and manual acceptance are recorded separately.

macOS RAR, CAB, and UDF imported types must conform to `public.data` so actual files can be identified. CAB declares both system `com.microsoft.cab` and compatibility `com.microsoft.cab-archive`; Settings queries and changes the actual preferred type when it is one of these, otherwise uses the compatibility identifier. The UDF Viewer declares the `.udf` extension without `LSItemContentTypes` so actual files can discover a candidate even if an older installation's invalid UTI declaration is still used. Apple has deprecated this [extension declaration key](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html); continue verifying it on supported macOS versions. Settings queries and changes the actual recognized `.udf` type, falling back to the existing identifier when unavailable. Installation or registration does not actively override existing defaults. When no handler existed, Launch Services may resolve a new candidate as the current handler through [implicit rules](https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/LaunchServicesConcepts/LSCGlossary/LSCGlossary.html). Removing temporary registration should restore the original state; this resolution is not the app writing user preferences.

FileOpenRouter receives [QFileOpenEvent](https://doc.qt.io/qt-6.8/qfileopenevent.html) before QML, accepts local files only, and reuses application open/activation routing. GUI command-line arguments after `--` are file paths, avoiding confusion with diagnostic flags. At most 128 pending intents are queued without preempting active tasks. Normal product processes in one login session share an instance; multi-file requests open in order and activate the last. See the [application sessions contract](application-sessions.md) for tab and window behavior.

Launch arguments are queued before QML loads. The main window starts hidden and submits the first available request immediately on controller attachment without requiring window visibility. The window is shown in the initial event queue so platform launch events use the same path. During external opening, hide the welcome entry before changing sessions to avoid a welcome-page flash on the first frame or session replacement. Cancellation/failure restores welcome; success shows the real list. See [loading state](../ux/welcome-opening.md).

Native macOS startup separately waits for AppKit's NSApplicationDidFinishLaunchingNotification, handles that batch of queued Qt file events while hidden, then shows the window. Notifications and queued callbacks are scoped to main-window lifetime; they do not replace Qt's application delegate or use fixed millisecond delays. A real Launch Services regression previously found one frame of welcome content; the corrected requirement is zero. check-macos-open.py runs argv and native open paths locally and in Mac CI, retaining JSON/logs only and not generating or uploading app packages.

## Automated verification and limits

Three-platform CTest checks pre-start file events, rejection of nonlocal URLs, and queuing while reading is busy. Explicit XDZIP_ASSOCIATION_PROBE plus isolated settings is CI-only: use the normal open flow to read a project-owned 100,000-entry ZIP, retain count/build identity, and exit normally without recording source paths or extracting.

The current association probe waits for at least one actual frame presentation and records welcome-content visibility per frame. Current product requirements for Windows ShellExecuteEx and Linux GIO are presented_frames greater than 0 and welcome_frames equal to 0. Pinned older products are tested according to historical probe capability; do not pretend old binaries have new first-frame counts.

Native Windows CI installs QA variant 1, upgrades to 2, rolls back to 1, then installs the real delivery package. ShellExecuteEx opens owned registration classes with Chinese, space, and ampersand paths, checking defaults and UserChoice remain unchanged, busy replacement is refused, and uninstall retains settings, extra files, and other candidates. Linux performs the same dpkg lifecycle in a no-network container without SDK, system Qt, or compiler. The UID 1000 product actually opens 100,000 entries through a GIO desktop launcher; check MIME, defaults, locks, uninstall, and purge.

Linux release verification also changes MIME defaults in an isolated container user profile and uses `gio open` for nine format samples. A separate handler verifies that switching actually takes effect, then original defaults are restored. This uses container GIO and a virtual display, does not change the maintainer's desktop configuration, and does not replace system-settings UI or other desktop-environment verification.

QA variants share the currently verified binaries and change only test package version/directory to test installation mechanisms. They are not release artifacts and do not masquerade as real data migration between different product versions. Settings schema is currently 1 and installation metadata records it on both platforms. Older installers refuse to overwrite an installation declaring a newer schema; future migration must update the contract.

Subsequent fault injection is allowed only in QA variant 2, failing once during postinst configure. Production must not contain this branch. The container actually verifies half-configured state, startup blocked by the gate, settings preserved, then runs dpkg --configure -a to recover and opens a real file through GIO. This is reproducible configuration failure, not device power loss. A separate settings-compatibility check compiles retained original and current settings components and round-trips same-schema configuration. Original inputs are pinned by per-file hashes, independent of old main history, and do not masquerade as complete installer data migration.

Full product compatibility is separately verified by prepare-previous-product.py building the complete product source from a pinned compatibility snapshot (originally from 4cf0f8c) on disposable Windows/Linux CI hosts. A detached worktree preserves actual clean identity; the current pinned SDK builds historical-product QA installers without downloading expiring old Actions binaries. Install the historical product and actually open it, then install the current product and check revision changes and configuration bytes are preserved, then roll back and reopen the historical product and check data. This proves same-schema compatibility between two complete source commits, not a historically signed original package, a nonexistent schema 2 migration, or device reboot. Historical installers are QA-only and are not uploaded as product assets; receipts bind both binaries and installer SHA-256 values.

windows-install-lifecycle.json, linux-install-lifecycle.json, and package hashes are actual evidence. Real Explorer/Finder double-click, default-selection UI, post-restart services/caches, warnings for lack of formal signing, GPU, and desktop checks follow the manual checklist. Automated scripts must not mark all INSTALL-01/ASSOC-01 passed themselves. Existing manual conclusions are in [WP-12 #5](https://github.com/xiaodaozhi/xdzip/issues/5); regenerating a pending template does not reopen acceptance. Future schema migrations need additional actual compatibility cases.

The Windows no-task probe for busy replacement protection uses isolated settings with the tray disabled so `CloseMainWindow` performs normal exit under that configuration. Other association-open probes retain default tray settings and end through the explicit shutdown barrier. Installation-protection probes must not mistake a hidden window for process exit failure or bypass exit verification by forcibly terminating the normal path.

Windows update-protocol fixtures and real Qt update fixtures both include the association launcher and all nine document ICOs; installers cannot pass checks with missing required payload. The protocol fixture's small C main program and association command verify update handoff only. Embedded application resources, native candidates, and real windows are separately checked through the complete Qt product; conclusions are not mixed.

## Long-term compatibility baseline inputs

Real upgrade/rollback uses pinned old complete product source rather than rewritten main history. `prepare-previous-product.py` pins a single-root source snapshot in the independent `codex/installer-compat-baseline` branch. That branch contains only original source and assets required for builds and regression, without old main parents, execution reports, or workflows. `COMPAT-BASELINE.json` in the snapshot records original source commit and tree identity. It must not be merged back into main or treated as a release package or current-product acceptance conclusion.

After building, CLI identity must match the snapshot's own pinned SHA; receipts separately record original source identity and must not impersonate the original released binary. Settings components also retain three small original source files as durable test inputs, pinned by per-file hash. Bidirectional reads/writes and rejection of future schemas do not depend on network or historical commits. Do not change these regression inputs with current implementation; review a new baseline separately and retain provenance when needed.

The frozen snapshot predates the independent update helper and contains no helper source or binary. Only `prepare-previous-product.py` passes it `--qa-historical-revision`. Deployment/packaging scripts require disposable CI, the complete pinned SHA, and actual clean product identity to match simultaneously. Linux additionally requires historical-version mode and forbids mixing with the current QA variant. Windows directly runs the old product's version command for identity; Linux uses the independent deployment audit's identity and complete file hashes. Receipts explicitly state that historical source lacks the helper, do not inject the current helper, and do not install polkit authorization for a nonexistent Linux helper. Ordinary products and current QA variants must still deliver and verify the independent helper; `--qa-legacy-version` alone does not allow it to be absent.

## Debian version migration

Starting with the first public prerelease, Debian epoch 1 is used: `1:<semantic-version mapping>+git<commit>`, for example `1:0.1.0~alpha.1+git...`. Historical `0.1.0~dev.9` sorts after alpha.1 without an epoch under dpkg rules, so the old mapping cannot simply be retained. The epoch is only for system package ordering; the product UI, version tags, and release.json continue using the original semantic version. Later Debian packages retain epoch 1, with alpha, beta, rc, and stable ordering still expressed by upstream versions. See [Debian Policy](https://www.debian.org/doc/debian-policy/ch-controlfields.html#version).

The real historical-product fixture uses CI-only `--qa-legacy-version` to retain its original no-epoch identity; do not alter the old package's ordering to hide upgrade problems. The current package must pass actual dpkg upgrade, rollback, and installation lifecycle acceptance. User configuration and external default associations retain their original contracts.

## Default applications in Settings

Settings queries the current OS and displays associations for nine categories. macOS uses the NSWorkspace content-type interface and lets the user choose a replacement when disabling; development copies disable association operations at None rank. Windows opens the system default-app page and rechecks on return, reading system associations without modifying UserChoice. Linux queries and changes user MIME defaults with xdg-mime; packages declare an xdg-utils dependency. Removing an association lets the user choose an installed replacement desktop entry. Composite extensions may share system types. Cancellation, system refusal, or query failure is not presented as false success. Real system UI and multiple desktop environments require separate acceptance.

In automatic language mode, Windows Setup resolves the current user's system UI language: Chinese variants use Chinese descriptions and others fall back to English. Explicit Chinese or English choices take precedence. Setup does not rewrite automatic detection as a fixed language; on startup, the application resolves its own system language and synchronizes owned descriptions.
