# Release runbook

Cross-platform stable releases and prereleases use [release protocol v1](release-protocol.md), freezing source by complete tag and assembling six platform package types, update materials, notices, licenses, SBOMs, and deployment/verification materials in a draft. Releases do not generate or attach corresponding-source archives. Routine releases and acceptance do not run the source-delivery collector; it may be used for local review only when the user separately and explicitly requests source collection. Formal release uses one manual Release workflow run: three-platform native artifacts are built once and assembly directly reuses those artifacts for publication. Do not run a validation round and then push a tag for a second build. Complete local verification and release preflight before creating the tag. After all checks pass, stable is a normal Release marked Latest; alpha/beta/rc are Pre-releases. Redownload retained attachments and verify hashes after publication. Explain unperformed manual acceptance within the candidate's actual scope; automation does not replace its conclusions.

Development acceptance, [release license review](../qa/release-review.md), and release execution are separately recorded in their issues. This runbook does not duplicate a review's open/closed status. License conclusions bind actual candidates and do not automatically approve later versions; unchecked items are not passes. Before a stable release, review the actual candidate's provenance, notices, source, and replacement materials under release review. Specific unfinished obligations must be resolved as blockers rather than merely disclosed.

On 2026-10-19, the user established personal GitHub open-source release policy: provide packages without formal publisher signatures through GitHub Releases without requiring paid developer accounts, purchased signing certificates, Developer ID, or macOS notarization. macOS retains only ad-hoc integrity signing necessary for Apple Silicon; Windows delivers an unsigned installer. Formal signing may be separately chosen later when feasible and is not mandatory for WP-12 or later stable releases. Version, commit, artifact hashes, source, licensing, and security requirements remain. This policy does not automatically authorize uploads or releases.

1. Update VERSION.json and derived versions under [versioning](versioning.md); confirm scope and capability matrix, disabling or labeling features that have not met gates. Prepare `release-notes/<full-version>.md` with consistent version/build metadata and Chinese/English notes citing actual platform/commit acceptance. Run `python3 scripts/publish-release.py --check-notes`; missing notes cannot inherit old content.
2. Build each platform's unsigned packages, debug symbols, SBOM, NOTICE, and dependency licenses from the specified commit. Do not generate or upload corresponding-source archives as release attachments.
3. Record toolchains, hashes, features, targets, and benchmark environments; verify source can rebuild unsigned portions.
4. Verify delivery without formal signatures: check macOS ad-hoc integrity, explicitly state the Windows installer is unsigned, and accurately describe potential system warnings and verified installation limits in notes. Do not require users to disable system protection or claim platform publisher trust.
5. Check installation, first open, associations, upgrade/uninstall, and dependency checks actually executed by the release workflow. Select additional desktop or clean-environment checks based on the change and record uncovered areas.
6. Review security, interoperability, and defect regression results, recording executed scope and known limitations.
7. Review version-specific notes, known limitations, complete installed/download sizes, and checksums, then upload after release-owner confirmation. Stop when draft and notes differ; explicitly align reviewed inputs first rather than automatically overwriting manual draft edits.
8. After release, confirm downloaded artifacts match verified hashes. If problems occur, withdraw the affected channel, explain impact, and retain diagnostic evidence.

In v0.1, users initiate updates from About. Installed builds meeting installation identity, version, and signature checks can download and hand off installation. Portable editions, older builds lacking update components, and builds without required installation identity/trust use the official release page for manual installation. When tasks are active, wait; users may cancel waiting without implicitly canceling tasks or forcibly overwriting the program. See the [user-initiated update contract](software-update.md). Before rollback, check settings-schema compatibility and retain an old runnable version; do not forcibly downgrade data. Bundle ID, GitHub Releases channels, and maintenance periods follow project support policy; do not request or invent formal signing identities or certificates.

When desktop checks are needed, select relevant scenarios under [desktop verification](../qa/private-test-manual.md) rather than refilling a fixed manual form for every candidate. The [deployment dependencies and SBOM](deployment-audit.md) source graph and actual-file inventory must match the same source/executable identity. Current completeness remains incomplete and actual deployed component attribution and license confirmation are still required. Existing clean-machine manual verification remains in the current WP-12 acceptance record. Experimental per-user Windows and Ubuntu 24.04 installers exist; see [installation and associations](installers-associations.md). A macOS development .app does not replace standalone installer verification; delivered DMGs still verify deployment dependencies and ad-hoc integrity.

A local Mac may create a [development DMG](macos-deployment.md) on explicit user request. Source and rebuilding materials may be reviewed locally with the [delivery collector](source-delivery.md), without uploading as Release or Actions downloads. Release review must still determine whether actual component obligations can be met under this policy; block affected binaries if not. Ad-hoc signing is not Developer ID or notarization but meets the project's current signing policy; image verification does not automatically approve release.
