# User-initiated update contract

Under Windows MSIX package identity, About does not show in-app updates and the update controller refuses the existing GitHub update check. Microsoft Store manages Store updates; sideloaded packages do not receive an in-app automatic-update commitment. Identity-query errors are treated as packaged identity to prevent misuse of installer updates. Ordinary installations and other platforms remain unchanged.

The standalone CLI and CLI within the desktop package update their own installations under the [command-line contract](command-line.md). Standalone CLI uses a separate signed manifest and managed version directory. Bundled CLI submits a candidate intent over same-user single-instance IPC, and the desktop controller independently verifies it. Accepted means handed_off only; actual success requires a receipt and running identity. Windows/Linux installation occupancy extends to CLI tasks; macOS protects CLI using a shared-use lock, commit gate and persistent state. Existing tasks are not implicitly cancelled. Headless CLI identity queries do not create QApplication or read and clear installation receipts.

The application-level `UpdateController` checks public releases from About. Closing About does not cancel checks or downloads; reopening shows the same state. Checks are user-initiated, without startup polling or automatic installation. Product windows continue to reuse About and shared operation controls.

## Selection, network and privacy

The client reads only the public [Releases API](https://docs.github.com/en/rest/releases/releases) of the fixed `xiaodaozhi/xdzip` repository, uses no credentials and uploads no filenames, archive contents, passwords, recent records or settings. GitHub and its download CDN receive connection information and a User-Agent containing the application version. Release pages and download folders open through the system interface.

Each page has at most 100 entries, at most 10 pages; each response is at most 8 MiB, manifests 256 KiB and signatures 4 KiB. Original requests allow only HTTPS and explicitly registered GitHub/CDN hosts. With a user-configured mirror, its HTTPS site is permitted as the transport address; at most five redirects are allowed. Metadata has a 15-second idle timeout and 30-second total limit; downloads have a 30-second idle timeout and one-hour total limit. The in-memory ETag cache holds at most 24 entries; 304 reuses only a prior successful response. Offline, TLS, timeout, rate limit, truncation, missing packages and manifest errors are failures, not “already up to date”. Repeated clicks do not start parallel updates.

Updates use configured system, direct or custom HTTP/SOCKS5 proxy settings without credentials. An optional mirror must use HTTPS and contain no credentials, query or fragment; its base is followed by the complete original GitHub HTTPS URL. Original URLs still pass the fixed host allowlist. Mirrors and redirects do not change signed manifest contents, verification, candidate identity or installation gates. Configuration changes apply to the next update after the current one ends. Native macOS Sparkle supports system, direct and credential-free custom HTTP CONNECT/SOCKS5 modes. Each native instance copies validated mode and proxy address before startup, using the same session policy for feed and archive. Custom proxy failure must not fall back to direct. Direct mode explicitly sets HTTP, HTTPS, SOCKS, FTP, PAC and discovery flags to numeric 0 in URLSession's proxy dictionary; nil dictionaries or empty modern proxy arrays still mean system default. TLS trust, release signatures and independent installation gates remain unchanged.

HTTP 429 is rate-limited. HTTP 403 is classified as rate-limited only when remaining quota is zero, a valid seconds-based Retry-After is present, or the GitHub JSON message explicitly identifies a rate limit. Other 403 responses remain network failures; do not infer quota exhaustion. The product neither automatically retries nor reads GitHub credentials. Anonymous quota is shared by source IP; CI repository permissions cannot increase it.

The Qt-free Rust core selects by semantic version, channel and monotonically increasing build and validates the fixed repository, complete six package classes, architecture, package type, minimum-system contract and identical candidate identity. Stable accepts stable only; alpha accepts alpha, beta, rc and stable; beta excludes alpha; rc accepts rc and stable; dev may check public releases. Both semantic version and build must increase; publication time is not used as a proxy. The client also checks current-system support and Releases asset byte counts.

## Trust and downloads

`release.json.sig` verifies the exact manifest bytes. Trust roots are compiled into client and installer helper and cannot be added from downloads or requests. Validate JSON metadata as UTF-8 before string FFI; invalid encoding explicitly fails instead of altering authenticated bytes through replacement characters. See the [release protocol](release-protocol.md) for signature formats, independent Sparkle keys, delivery order and immutable assets. Missing signatures or unknown public keys offer manual download from the official release page only; bad signatures fail explicitly. Automatic replacement is disabled until a production public key is configured.

Windows/Linux stream packages up to 2 GiB to a private update cache while checking length and SHA-256; only successful publication permits helper handoff. Cancellation or validation failure creates no installable state. Portable, dirty, development/source or unknown-identity builds offer checking and downloads only. Automatic replacement also requires Release configuration and valid commit identity; a source-archive build without Git identity is not treated as installed. Installation identity must match system installation record, running path and package marker.

macOS uses pinned Sparkle 2.10.0 and the restricted `xdzip-proxy.2` proxy extension, with a thin Objective-C++ user driver delivering state to unified About. The framework library and Ed25519 are built natively on Apple Silicon from pinned source and patches; resources, installer helper and signing tools retain pinned official SDK provenance. The derived framework is not claimed byte-identical to upstream SDK. Sparkle natively validates feed and archive; the feed contains only the same selected candidate. Do not claim Sparkle performs an additional SHA-256 check. Read-only DMG, App Translocation, unregistered .app or missing update public key offers manual installation. Ordinary CI does not deploy, sign or upload Mac app packages merely because Sparkle is used.

Manual fallback displays the first unmet condition among installation identity, session, missing automatic-update feed or invalid network configuration. An identity failure means only that the group of checks failed, without guessing which; multiple unmet conditions may need sequential resolution. About links to the matching release and DMG guidance and explains extracting app.zip, exiting the old version and replacing the app. A successful download is not successful installation.

## Installation handoff and recovery

Existing tasks continue during download. If tasks are active after choosing download and installation, wait; the user may cancel waiting and defer the update without implicitly cancelling tasks or password requests. After helper preparation, `prepareForUpdate` rejects active tasks, task starts and modal interactions. Once handoff begins, no new sessions or tasks are admitted; all Rust connections must clean up and join before sending the installation commit. Handoff does not use the “restart old program immediately” path.

Windows copies a standalone Qt-free helper to private cache only from the registered current-user installation root. The helper independently reverifies signature, size and hash, waits for the captured main process to exit, then invokes the existing Inno installer with interactive license acceptance. An installation gate blocks restart during replacement.

If the installation root fails safety checks, About identifies installation-folder permissions or manual installation from the release page, rather than classifying rejection as network failure. Existing directory and identity checks are not relaxed.

Ubuntu installations use fixed `/usr/libexec/xdzip-update-helper`; the ordinary-user coordinator invokes polkit with fixed arguments only. The root helper copies the package into private root staging, reverifies signature and xdzip package name, architecture and version, and permits fixed APT operations only. It accepts no commands, arbitrary package names or destination directories and uses no sudo shell. Authorization cancellation and missing authentication agent are separate states. An unconfigured dpkg is not reported as success; no automatic rollback or old-program restart occurs. Restarting the new version as the original user preserves bounded allowlisted XDG settings, data, cache and state directories and desktop language, but not dynamic loader, Qt SDK or test-environment overrides; these variables are not passed to root installation commands.

On macOS the Sparkle install callback is released only after all joins. The main program synchronously releases its quit interceptor only after the provider marks actual installation committed and before invoking the SDK install reply; the join barrier alone must not permit early last-window auto-exit. Following failed or cancelled handoff, ordinary exit continues to wait for the native helper observation gate. Sparkle performs actual archive replacement and restart. Cancellation leaves no plan to install on the next exit. Framework, XPC and helper retain their individually required signing parameters and entitlements; generic re-signing rules cannot be applied to all.

Sparkle cancellation replies are handled in an asynchronous update cycle; cycle completion does not mean the separate installer process has exited. For an uncommitted install, ordinary exit requests cancellation, waits for the cycle, then uses system `/bin/ps` read-only to observe Autoupdate processes matching this app's exact framework path and releases the quit interceptor only after they exit. Record the matching installer at readiness. Inspection failure is not exit permission; do not terminate the helper or log unrelated process information. Retries after preparation failure also wait for the old helper to exit before replacing the update driver. Committed installs use Sparkle's native exit and restart.

Windows/Linux transactions use random IDs and fixed ready/proceed/cancel/result filenames. Before exit, the client saves transaction, target identity and cache directory in a separate `update-state.ini` beside settings, not inside settings configuration. The helper atomically writes a success result before releasing the gate and restarting. At next startup, bound receipt paths and sizes and verify transaction and current version/build/installation identity. Failure, missing receipt or mismatch shows recovery without automatically retrying installation. A recovery record without valid candidate URL can still open the fixed official release list. Cache materials remain for user repair; public evidence must not contain full private paths.

Before releasing Sparkle installation, macOS saves a local attempt record for target version/build. On restart, actual running identity and reliable installation markers determine completion or recovery. This record grants no installation authority and does not replace Sparkle signature verification.

## Verification boundaries

A Mac-only diagnostic can run only the full product chain. All-platform verification always runs the six Sparkle scenarios and full product chain, ignoring the diagnostic option to skip the six scenarios.

Native downloader system-conflict checks temporarily enable owned static proxy and PAC only on explicitly isolated disposable hosted Apple Silicon runners. First require actual system-mode feed/archive hits on the proxy, then zero direct-mode hits. HTTPS controls verify connection destinations and retain untrusted-certificate rejection. A bounded helper saves, restores and verifies the service's complete proxy settings and fixed test-domain hosts contents, including on EOF and timeout. Local runs never modify proxy, DNS or certificate trust. A separate full product chain exercises direct installation under controlled PAC, ordinary restart and active update-configuration snapshots; downloader checks do not replace installation evidence.

Mac SDK-free HTTPS acceptance uses the same deployed probe and anonymous real update requests. Records contain only status code, Qt error and allowlisted rate-limit response headers, not raw error bodies, source IPs or credentials. After confirmed rate limiting, the acceptance driver starts at most three probes, waiting until the later of Retry-After and quota reset. Without a usable primary quota reset time it refuses early retry; other confirmed limits use increasing backoff of at least 60 seconds. Total waiting is capped at 3700 seconds; exceeding the budget fails explicitly, retaining each result and actual wait. Existing per-request timeouts, TLS, response bounds, success status and SDK isolation remain required; retries are not merged into a single pass. This backoff belongs only to the dedicated acceptance driver and neither adds product background retry nor permits skipping the final specialized checks.

Core fixtures cover channels, dev, out-of-order pagination, missing packages, bad signatures, minimum system and identity conflicts. Network fixtures cover cancellation, repeated clicks, rate limits, TLS, response limits, ETag and damaged downloads. Session regressions check task preservation and handoff after all joins. Real three-platform old-to-new upgrades, authorization cancellation, restart, installation failure/recovery, settings/association preservation and SDK-free HTTPS need isolated platform evidence; unit tests or CI compilation do not replace them. Full Mac updates require native Apple Silicon. Actual completion and evidence are tracked in issues.

The [dedicated native update regression](../../.github/workflows/update-regression.yml) is manually dispatched only, carries no production secrets and uploads no app packages. It defaults to all platforms and can select a single platform for diagnosis, each with an independent queue; final acceptance still requires same-commit all-platform results. Windows on disposable GitHub runners and Linux in a dedicated container first use an owned C protocol product and real Inno/APT to verify helper cancellation, failure and recovery. Another private Qt upgrade chain builds two real `browser_main`/QML versions, uses actual mouse input on About, validates manifests and packages, exit joins, Inno/APT, ordinary-user single-instance restart and receipt recovery, and verifies retention of settings, unknown settings keys, existing defaults and unrelated installation-directory files. Linux separates build SDK and runtime containers; runtime has no compiler or Qt SDK and uses custom XDG directories. Windows Server CI substitutes minimum-system detection only under a private macro and does not replace native Windows 11 acceptance. This chain substitutes network transport for public GitHub URLs; production HTTPS/TLS is separately verified without an SDK.

The separately authorized [production signing acceptance](../../.github/workflows/production-update-acceptance.yml) uses existing protected-environment keys while retaining committed production public roots and follows the real Qt upgrade and recovery chain. Preparation does not sign. An independent signing step first strictly matches public trust roots, then verifies this fixed candidate; execution rejects secret environments. It offers no arbitrary asset signing or publication interface. Signed candidates stay on disposable runners; public artifacts contain bounded diagnostics and summaries only.
