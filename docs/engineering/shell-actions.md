# File-manager actions and standalone task host

System entry points pass selections and actions to the desktop process in the same login session. Windows uses the classic `IContextMenu`, under “Show more options” on Windows 11. Ubuntu 24.04 Files uses a Nautilus 4.0 menu extension. macOS uses the Finder Sync “Open with xdzip” dynamic submenu, retaining “Services → Open with xdzip” and the standalone operation panel as fallbacks.

Actual platform verification and remaining work for this package are tracked in [#270](https://github.com/xiaodaozhi/xdzip/issues/270). Source capabilities are not retroactively added to existing release assets.

The no-paid-account Finder Sync implementation and local verification are tracked in [#273](https://github.com/xiaodaozhi/xdzip/issues/273). Apple positions Finder Sync for synchronization apps; this project accepts the applicability limitation for a general compression menu and does not claim App Store review acceptance. Local ad-hoc integrity signing requires no paid account, Developer ID, App Groups or notarization, and provides no Gatekeeper publisher trust. See [Apple's Finder Sync documentation](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Finder.html).

## macOS Finder Sync

`Contents/PlugIns/xdzip-finder-sync.appex` is a native extension that links neither Qt, Rust nor format libraries. It covers all local Finder directories with `/` as the observed root, handles only Finder's selection, never traverses directories, and adds no toolbar, badges or synchronization tasks. One ordinary item offers three creation actions; multiple selections add ZIP-per-item; four extraction actions are added when all items are archive candidates. No menu is created for an empty selection, nonlocal URL or more than 128 items. Native menus use system dimensions; standalone operations use the shared normal-density window.

The extension reads only its own JSON configuration at `xdzip/finder-sync.json` in the user's Application Support directory. It contains the current app location, toggle, language, registration revision and locally random handoff token. The file is limited to 8 KiB, owned by the current user, and a 0600 regular file; writes use atomic replacement and links or foreign configuration are rejected. It is not a CFPreferences file. The sandbox grants a read-only temporary exception only for this exact file, without sharing the user directory, App Groups or a network listener. Path entitlements must start with `/`; see [Apple's temporary exception specification](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/AppSandboxTemporaryExceptionEntitlements.html).

Finder does not retain menu-item `representedObject`, so the extension retains a bounded selection snapshot using monotonically increasing tags. An expired tag cannot refer to a new selection. Through an explicit `NSWorkspace` target the extension sends a base64url JSON event at `xdzip-shell://v1/` to `Contents/Helpers/xdzip-shell-relay.app`; sandboxed caller launch arguments cannot be relied upon. The relay is a separate native app that does not link Qt. It authenticates the random token in the current user's private configuration, validates the URL, UUID, action, paths and JSON bounds, preserves the UUID, and invokes the existing private request-file and single-instance entry points. Admission failures show a native error. The token is not included in request files, the desktop protocol or product logs; externally constructed URLs without the correct token do not perform file operations. The URL is only for local handoff.

The extension locates its containing app by fixed bundle layout without reading outer app metadata in the sandbox. The relay rereads the outer `Info.plist` on every invocation and requires the product identity, `XdzipShellProtocol=1`, `XdzipFinderSyncProtocol=1` and a valid executable filename. Rolled-back or incompatible targets are rejected. An old loaded extension may temporarily retain its menu, but the relay must reject clicks; the Service independently checks its existing protocol.

The installed app registers its own appex and Service on first launch; the user must still enable the Finder extension in system settings. The settings toggle manages both entry points; language switches only the extension menu, while the system Service title follows system language. Repeatedly saving settings does not re-add an unchanged appex and disconnect Finder; registration is repeated only when the content digest changes or registration is missing. Disabling removes only the registration at this app's exact path and retains disabled configuration; uninstalling an older copy does not disable the newer app's configuration. An explicitly registered development copy can be re-enabled in settings after disabling; an unregistered development copy is not enabled automatically.

An update can be affected by Finder holding an old extension instance. If necessary, disable and re-enable the owned extension in system settings; Finder is not forcibly terminated. Rollback and uninstall touch only owned registrations and files and do not change default file associations. Services placement is controlled by the system and may be promoted to the top-level context menu.

## Windows package boundary

Experimental MSIX builds register no context menu. They neither present classic `IContextMenu` as a modern menu nor enable a modern menu in sideloaded packages. The Windows 11 modern menu needs package identity, COM and Explorer extensions in the manifest, and a new `IExplorerCommand` implementation; the existing implementation cannot directly serve as the modern entry. A future implementation must require Store system signature type for the extension package and reliably identify installation origin to exclude sideloading. Query failure, Developer, Enterprise and None all disable it; test actual Explorer display, settings and existing request protocol separately. A Store signature alone does not establish installation channel: Store-signed packages can be copied and sideloaded. If they cannot reliably be distinguished, do not enable the modern menu. Windows 10 has no Windows 11 modern menu. Implementation and real Store-package verification are outside the current assessment.

[GetStagedPackageOrigin](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getstagedpackageorigin)'s `PackageOrigin_Store` is a candidate source interface. It reports staged package origin, not a verified per-user installation record. Multiple users of the same package, copied and sideloaded Store-signed packages and upgrades require real testing before deciding whether it satisfies the sideload exclusion. An extension in Explorer must identify its own package rather than query Explorer's process as xdzip. Hide the entry on failed or uncertain queries.

To collect origin comparisons, run the following read-only diagnostic in Windows where the target package is registered for the current user. The package name is an example; output must be a new JSON file under `build/`. The diagnostic records system signature type, staged origin and an anonymized digest of the full package name, rejecting results without a unique registered version. The scenario is an operator label and does not prove installation channel; query failures, unknown values or identical results cannot independently authorize the menu. No certificate, installation or system setting changes are needed.

```powershell
python scripts/msix-origin-probe.py --name xdzip.Example --scenario store-install --output build/store-origin-observation.json
```

## Selection and output

Shell creation confirmation directly checks the prefilled source directory or selected destination without first checking the default Downloads directory, avoiding unrelated macOS privacy access delays. Normal main-window creation retains its default destination.

Creation offers quick ZIP, 7z, creation confirmation and ZIP-per-item for multiple selections. A single regular file keeps its full name, such as `a.txt.zip`; a folder uses `foo.zip`; a combined selection in one directory uses that directory's name. A cross-directory combined selection opens the standalone creation window for destination confirmation. Quick creation uses the normal level without encryption or volumes; existing conflict prompts handle destination name collisions.

Extraction actions appear when every selected item is an archive candidate by supported suffix or volume naming. The menu does not scan file contents. On actual open, Rust discovers the complete volume group, identifies contents and validates source and format capability. Identical complete source groups execute once per extraction batch; the in-process opaque source-group marker holds file identities and is not write authorization.

- Current directory: extract each archive directly into its own containing directory.
- Smart directory: add no wrapper only if the complete validated output graph has one top-level directory, including implicit top-level directories. Root files or multiple top-level items require an archive-named wrapper. Internal directories are not stripped or renamed.
- Per-archive directory: always add an archive-named wrapper. Reserve it exclusively using the held destination capability; existing files, directories and links are never reused. Select a new numbered name such as `name (2)`, with up to ten thousand attempts.
- Selected directory: select a common destination in the standalone extraction window. Per-archive directories are the default, with smart or direct merge alternatives.

Directory derivation follows [safe extraction](m3-extraction.md) portable-name and `.app` suffix rules. Smart detection cannot authorize output; each task must revalidate destination, source, CRC/authentication, conflicts and publication permission. An individual archive failure follows the existing whole-archive stop policy; the batch coordinator then proceeds to the next archive.

## Processes, requests and windows

The private desktop entry is `--shell-request <request.json>`, not a script interface for the standalone CLI. Native extensions generate only a selection manifest and launch the desktop entry; they load neither Qt nor format libraries. The manifest resides in an exclusively created private `xdzip-shell-<32 random hexadecimal digits>` directory under the system temporary root, with fixed leaf `request.json`. Windows sets a protected DACL for the current user and SYSTEM before writing; POSIX uses a 0700 directory and 0600 file. The desktop uses shared Rust no-follow and directory capabilities to verify root, ownership and permissions, reads at most 256 KiB, and rejects links, relative paths, invalid Unicode, unknown actions and more than 128 selections.

Requests contain schema 1, UUID, action and absolute paths. Optional boolean `archive_candidates` conveys only MIME or UTI hints already available to the file manager. Together with shared suffix and volume rules, it determines menu visibility; it does not authorize I/O or bypass Rust content validation. Windows reads the extension's registered Content Type, Nautilus reads FileInfo MIME and the macOS helper reads URL Content Type; none parses archives in the file manager. The single-instance protocol keeps existing open and CLI operations and adds structured `shell_action`; admission and successful execution are judged separately. The application retains at most 128 admitted request identities. Identical identity and contents are admitted once; identical identity with different contents is rejected. After admission only the fixed file and empty directory are removed, without recursively cleaning external input.

A cold shell launch creates only `ShellHost`, not a hidden main window. Opening a file normally or explicitly showing the main window creates a browser window on demand. An existing instance receiving a shell action neither switches browser tabs nor restores a hidden main window. An operation session occupies an existing bounded session slot; the batch sequentially reuses a controller rather than creating a browser page per archive.

`OperationTasks` shares progress, result, password and conflict windows between browser and standalone entries. A top-level `OperationWindow` may have no owner; with an owner it follows the calling window, otherwise it is constrained to the selected screen. Modal prompts belong to the actual operation window; exit confirmation reuses `OperationConfirmationWindow`. Layout, shared controls, bilingual and accessibility requirements follow the [visual workflow](../visual/design-workflow.md).

On macOS single-instance identity uses the current user and actual Security framework login session ID; failed queries refuse election rather than relying on environment variables that helpers may lack. Normal startup, Finder relay and Services thus reach the same login-session instance; see [SessionGetInfo](https://developer.apple.com/documentation/security/sessions).

Shell creation and extraction reuse `TaskWindow` progress and result views. Batches show each actual status and error in the same layout; pre-submission failures without a task receipt create only a result view, not a fabricated task. Shell windows center in the current display's available area and prompts retain their actual calling window. The classic Windows menu precedes a recognizable Open With entry when available, otherwise retaining the system-provided insertion position; entries use application, format and system folder icons.

## Batch completion and exit

Each batch records actual success, failure, cancellation, unexecuted items and volume-group deduplication. An individual failure does not stop remaining items; cancellation stops subsequent items and sends the existing cancellation intent to the preparing or running task. Already committed output remains; the whole batch is not claimed to roll back. Preparation, password waits, conflicts, cancellation and cleanup count toward global activity and the exit barrier.

If a standalone creation window has not received a task receipt, rejected submission preserves input, parameters and errors for editing and retry, without creating a task terminal or consuming a batch index. Quick actions have no configuration window; submission failure is recorded and the batch continues.

Successful shell creation does not submit an in-app open intent; extraction's “open folder when finished” defaults off. Successful standalone results remain available for the user to open the destination. Completion does not steal focus. A window deliberately closed to the tray can reopen batch results from the task entry. If the tray disappears, standalone progress or retained results are restored to avoid losing the only operation entry. With an available tray, progress can be closed while work continues; without one, show a wait-or-cancel decision first. Once there is no main window, tray, active task or visible operation window, wait for all Rust connections to join before exiting.

## Installation and compatibility

Installed versions enable integration by default and can disable it in general settings. Registration manages only owned entries and does not change default file associations. Portable and development copies do not register automatically. Explicit desktop entries `--register-shell-integration` and `--remove-shell-integration` perform controlled registration and removal without showing the main window.

The installer uses exact single-argument synchronization or removal commands and updates only owned integration metadata before releasing the installation transaction startup lock. Normal files, shell tasks and main-window startup still require runtime admission. Windows installed identity checks the current user's registered product identity, installation location and file manifest; a portable directory does not automatically register even if it contains a deployment manifest.

Before handoff, verify desktop protocol 1 so that a still-loaded extension cannot pass requests to an old application after rollback. Windows reads GUI executable version resource `XdzipShellProtocol` and verifies the owned `Applications/xdzip.exe` registration command points to the same actual file; the association launcher does not claim protocol capability. After rollback to the legacy versioned layout, a retained newer root executable is no longer a shell target, and default file associations are neither read nor changed. The macOS helper rereads target Info.plist product identity, protocol and single executable filename each time instead of using cached NSBundle state. The Ubuntu package owns `/usr/share/xdzip/shell-protocol`; rollback to an old package and uninstall remove the marker. Missing, unknown, incompatible or no-longer-currently-registered targets refuse launch. Capability markers manage handoff compatibility only and do not replace request, Rust content or destination validation.

Windows stores its own CLSID and menu handler under HKCU. The runtime directory contains an extension DLL named by content digest and a verification manifest, avoiding overwriting a same-named DLL loaded by Explorer during upgrade. Old-file cleanup follows installer ownership and occupancy policy without forcibly terminating Explorer. On first normal launch the installed macOS app installs its own Service to the user's Library/Services. The helper only collects selections and hands them off; disabling integration removes only verified owned files, preserving and reporting extra content, links or mismatched ownership. Service visibility and enablement remain system-controlled.

The Ubuntu native extension is registered by the installation package in the Nautilus 4.0 extension directory and reads the same user's settings. Running Files may retain the old module; reopen Files to update without automatically terminating the file manager. A standalone runtime directory does not automatically write to the system extension directory; install its integration component explicitly.
