# Single-file streams and ZIP-derived packages

English | [简体中文](../zh-CN/engineering/single-file-streams.md)

The [built-in registry](format-registry.md) declares ordinary GZIP separately from TAR.GZ. `xdzip-codec-stream` adapts the independent `xdzip-compression` implementation of [RFC 1952](https://www.rfc-editor.org/rfc/rfc1952) to metadata, payload and creation contracts. No reference compression library enters the production dependency closure.

## Discovery and read boundaries

GZIP recognition checks at most 512 decoded prefix bytes with at most 256 KiB of compressed reads. A valid legacy TAR header or an explicit `ustar` marker selects TAR.GZ; a damaged recognized TAR fails without falling back to an ordinary file. Otherwise the complete GZIP stream is scanned before publishing its single regular-file entry. A fully zero decoded stream of at least 1024 bytes is ambiguous between an empty TAR and an ordinary zero-filled file. Only after complete stream validation, the longest registered suffix for the same outer filter resolves that view: an explicit ordinary suffix retains the file, a TAR suffix retains the container, and unknown/missing names keep empty-TAR precedence. An empty TAR.GZ produced by archive editing carries a fixed GZIP comment. It selects TAR.GZ even under an ordinary suffix, after validation of exactly two zero TAR end blocks. A zero prefix followed by nonzero ordinary data remains GZIP. The hint cannot override strong TAR identification, damaged compression, checks, quotas or source authority.

Scan admission limits both physical input length and actual decoded bytes to 24 GiB. `ControlledStream` checks cancellation before reads and retains the first typed error. At an exact decoded boundary, it may inspect one additional private decoded byte to distinguish EOF from overflow; that byte is never delivered. TAR uses the same controlled stream with either identity or GZIP filtering. Whole-stream EOF must validate every member's CRC32 and ISIZE, including empty members. Concatenated members form one logical file. Header flags, bounded optional fields, header checksum, truncation and trailing nonmember bytes retain the independent GZIP decoder's validation.

The row size is the observed complete decoded byte count, not the 32-bit ISIZE field. The host may provide a basename through `ReadSource::source_name_hint`; the codec removes a terminal `.gz` ignoring ASCII case, rejects separators, control characters and special names, and otherwise uses `content`. Header FNAME is ignored. Display text is escaped separately. All output names still pass the host's portable-path and destination checks. The hint grants no filesystem authority. Payload decoding binds to the immutable row, packed length and observed size, validates EOF again before success, and cannot resume after a failed or completed decode. Existing task limits remain 8 GiB per file and 20 GiB per task.

## Creation and publication

Ordinary `.gz` creation accepts exactly one regular input file, using Deflate levels 0/1/6/9. Directories, multiple files, passwords, volumes, solid mode and header encryption are rejected. The encoder reads the frozen input through EOF, checks its exact size and cancellation, and completes the GZIP trailer in host-owned staging. The host verifies the staged stream, source version and output transaction before publication. GZIP does not preserve the input filename; the reopened virtual name derives from the archive basename. Its verification therefore compares regular-file identity and size rather than requiring the original input name. Ordinary GZIP has no archive modification capability. TAR.GZ creation and rewriting retain their separate container contract.

Desktop creation choices, welcome labels and association candidates are generated from stable registry identifiers. The shared format selector derives its dimensions from existing control parameters. CLI creation uses the same suffix registry and prefers the longest matching suffix, preserving `.tar.gz` over `.gz`. Conflict renaming retains the actual registered suffix, including `.tgz`.

## ZIP-derived candidates

`.xpi`, `.apk`, `.ipa` and `.cbz` are entry-point candidates for the existing ZIP reader. Content validation, Store/Deflate, admitted WinZip AES-256 profiles, path handling and resource limits remain those of ZIP. A suffix alone never admits another method or encryption scheme. Package manifests, application installation and package signatures are not interpreted by these operations. These aliases do not add creation suffixes. Windows aliases reuse the ZIP icon; macOS declares their extensions and resolves the extension's assigned type without replacing every ZIP default. Linux uses the corresponding available MIME candidates, with IPA retaining the generic ZIP association.

## XZ admission and wire contract

An XZ profile must follow [Tukaani format 1.2.1](https://tukaani.org/xz/xz-file-format-1.2.1.txt). Validate stream flags and header CRC before allocating a decoder; reject reserved flags, noncanonical or overflowing nine-byte variable integers, unsupported filters and over-budget dictionaries. A block header has 8–1024 bytes, a verified CRC, optional nonzero compressed size and optional decoded size, a chain of at most three size-preserving Delta/BCJ filters followed by LZMA2, and zero header padding. LZMA2's end marker defines the exact compressed boundary; optional sizes assert observed work. Keep the strict 7z constructor separate from unknown-size member decoding, recovering the source only after validated termination.

Verify block padding, all declared content checks (None, CRC32, CRC64 or SHA-256), every index record against observed unpadded and decoded sizes, index padding/CRC, footer backward size/flags/CRC/magic, concatenated streams and four-byte zero stream padding. None provides no content checksum and must never be presented as a checksum guarantee. Limit streams and per-stream blocks to 100,000 each, account fixed parsing/filter buffers within 128 MiB working-memory admission, and retain cancellation plus independent input/output limits. Failure poisons the stream, and decoded data stays in host staging until complete validation and source checks succeed. Creation requires real LZMA2 compression, bounded independently reset blocks and a declared content checksum; independent decoding must verify emitted bytes before writer acceptance.

ZIPX uses existing ZIP records and physical identities. Method-specific admission follows [APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT), including BZip2 12, LZMA 14 and XZ 95. LZMA's properties header differs from LZMA Alone, and general-purpose bit 1 controls the EOS requirement. The admitted data-descriptor profile requires EOS; sized local records may omit it. Exact payload ranges, local/central consistency, descriptors, decoded sizes and ZIP CRC remain mandatory. Methods without verified implementations stay unsupported per record; an extension does not enable another algorithm or encryption profile.

XZ (`.xz`) and TAR.XZ (`.tar.xz`, `.txz`) implement this profile for reading, checking and extraction. Creation uses CRC64, independent blocks of at most 16 MiB, and LZMA2 levels 1/6/9; level 0, passwords and volumes are refused. Ordinary XZ accepts exactly one regular input and derives its virtual output name from the host basename. TAR.XZ accepts regular files/directories through the existing TAR writer. TAR.XZ supports archive edits. ZIPX adds `.zipx` as a ZIP candidate and reads unencrypted methods 9, 12, 14 and 95 alongside existing Store/Deflate. Eligible ZIP and ZIPX archives using these methods also support edits. Kept members retain their compressed data and method. AES-256 remains limited to the existing Store/Deflate profiles. PPMd I, JPEG and WavPack remain explicitly unsupported.

## Filtered stream profiles

BZip2 (`.bz2`, `.bz`), LZMA Alone (`.lzma`) and Lzip v1 (`.lz`) are read-only as standalone streams. TAR compositions accept `.tar.bz2`, `.tar.bz`, `.tbz`, `.tbz2`, `.tar.lzma`, `.tlz` and `.tar.lz`. Suffixes offer entry points; actual bytes resolve ambiguous shorthand. Their adapters reuse the independent algorithms. Admission must precede allocations, with a 128 MiB algorithm working-memory limit, the existing stream byte limits and at most 100,000 concatenated members. BZip2 validates each block and combined CRC and permits concatenated complete streams. LZMA Alone follows the [13-byte format](https://github.com/tukaani-project/xz/blob/master/doc/lzma-file-format.txt): five properties/dictionary bytes and eight little-endian size bytes; all-ones size requires EOS, known size permits a valid range ending or EOS, and trailing data is rejected. It provides structure/readability validation without a content checksum. Lzip v1 follows the [format specification](https://datatracker.ietf.org/doc/draft-diaz-lzip/02/), checks fixed LZMA properties, coded dictionary bounds, EOS and all three trailer fields: CRC32, decoded size and complete member size. Other versions fail explicitly. Concatenated Lzip members form one logical file.

An algorithm's member reader may return its remaining input only after validated EOF, without swallowing following container bytes. Its separate construction must preserve the strict full-span/known-size behavior of existing 7z readers. Prefix discovery and malformed-input tests must prove this separation. TAR reuses these filters for browsing and editing. compressed TAR parsing failures cannot become ordinary-file success. LZMA Alone has no strong magic, so it cannot supersede valid TAR headers, ZIP SFX or other strong container identification. Registry and entry-point declarations require matching implementation and automated acceptance. The registry records checking strength and unknown packed sizes, generating consistent CLI and interface presentation. Known LZMA sizes of 256 GiB or more are excluded from weak discovery, independently of the smaller actual-work budgets. Windows and macOS reuse the existing unlabelled generic archive artwork for these candidates.

## Automated acceptance

Use the stream crate's independent reference-reader/writer tests for member checksums, truncation, trailing bytes, input changes, cancellation, exact quotas and virtual names. Runtime tests cover classification, empty TAR precedence, single-file creation, checking, extraction and zero-publication rejection. The real CLI regression includes all four levels and ZIP aliases. Qt tests cover stable identifier selection, single-file admission, actual creation/reopening, native accessibility metadata, keyboard selection and bilingual layout at 100/125/150% text scales. Generated declarations, installer mappings and window/shared-control contracts have separate automated checks. Record actual execution results in the work issue; these checks do not establish unexecuted platform behavior or release permission.

LZ4 and TAR.LZ4 use the [standard-frame contract](lz4-streams.md). They read independent/linked blocks, declared checks and concatenated/skippable frames. Creation emits real LZ4 compression with 256 KiB independent blocks, block/content XXH32 and levels 1/6/9. Ordinary LZ4 accepts one regular input, while TAR.LZ4 uses the shared TAR writer for creation and editing. Passwords and volumes are unsupported. Checks validate only declared checksums. Legacy frames and external dictionaries are unsupported.

Zstandard (`.zst`) and TAR.ZST (`.tar.zst`, `.tzst`) follow the [Zstandard stream contract](zstandard-streams.md). Reading admits bounded standard-frame raw/RLE/compressed blocks, Huffman/FSE, repeat offsets, window history, declared checks, concatenation and skippable frames. Creation uses real LZ/FSE at levels 1/6/9, a 128 KiB window and mandatory XXH64; ordinary Zstandard accepts one regular input. TAR.ZST supports archive editing. Passwords and volumes are unsupported. Nonzero dictionary identifiers, unavailable external history and over-budget windows are refused. Checking verifies declared checks rather than promising checks absent from the format.

## Rewriting compressed TAR archives

Archive editing preserves supported TAR records and rebuilds the outer stream in the original format. TAR.XZ, TAR.LZ4 and TAR.ZST use their existing frame writers at normal compression. TAR.BZ2 emits BZh1 blocks with 64 KiB input chunks and block and stream CRCs. TAR.LZMA and TAR.LZ emit LZMA1 with an 8 MiB dictionary and an end marker. Lzip version 1 also emits its CRC and size trailer. TAR.Z uses block LZW with early CLEAR at nine bits. TAR.BR emits uncompressed meta-blocks as defined by [RFC 7932](https://www.rfc-editor.org/rfc/rfc7932). That output may be larger than the original Brotli stream.

After a rewrite, the host rescans and decodes the staged result before replacing the original. A compound TAR suffix preserves the empty archive view on reopening. An ambiguous bare stream suffix causes a failure before commit when deleting the final record. See the [archive modification contract](archive-transfers.md).
