# DEB container contract

English | [简体中文](../zh-CN/engineering/deb-containers.md)

The package envelope follows Debian's [deb(5)](https://manpages.debian.org/unstable/dpkg-dev/deb.5.en.html); common ar fields follow [ar(5)](https://man.netbsd.org/ar.5). Only the ordinary `!<arch>\n` layout is admitted. Each 60-byte header has bounded ASCII name/time/owner/mode/size fields and its required trailer. Validate decimal fields, octal mode, exact payload spans, newline padding of odd-length members and physical EOF. Thin archives, historical formats and long-name extensions are unsupported and grant no external file access.

`debian-binary` is first. Accept major version 2, bounded decimal minor versions and bounded additional version lines; refuse incompatible majors. Control and data members occur in that order. Underscore-prefixed extensions may intervene, and subsequent extra members are preserved. Control accepts TAR without compression, GZIP, XZ or Zstandard. Data additionally accepts BZip2 and LZMA Alone. The actual TAR/filter implementation, rather than a suffix alone, validates every selected member. Unsupported required member profiles fail explicitly. Deb822 fields, checksums listed inside metadata, signatures and installability are outside container validation.

## Views and physical identities

The existing directory model exposes three disjoint prefixes. `members/` contains every raw ar member, including the version and compressed TAR members. `control/` and `data/` contain the corresponding TAR records. These are export views: extracting all exports both raw members and expanded records. Selecting only `control/` or `data/` exports that view. No package installation or script execution is performed.

Raw records receive stable identifiers in ar order, followed by control and data identifiers in each TAR's physical record order. Preserve duplicates, raw and resolved names, warning/special flags and timestamp meaning; display names do not become source or output authority. Prefix both raw and resolved child names without normalizing away unsafe components, and mark unsafe original spellings before prefixing, so an absolute path cannot become an apparently safe relative child. The existing TAR parser omits benign empty `.` root markers. Directory nodes inferred from prefixes remain virtual, rather than invented physical entries. Links and special objects retain TAR's unsupported flags. Generic host path checks continue to reject unsafe outputs. Metadata opening completes both nested scans and their declared checks before publishing any rows.

## Source ownership, work and payload verification

Inner readers receive only bounded views of the existing authorized source. Relative seek/read operations cannot escape the member's physical span or open another file. Shared views serialize actual root access and retain independent logical cursors; no unsafe or self-referential pointers are introduced. Preserve typed cancellation/limit errors, while ordinary host read failures remain I/O failures. Reject borrow conflicts and impossible read counts rather than panicking or retrying terminal failures.

Extend the existing controlled stream and TAR reader with owned source input, preserving borrowed callers and the same initialization/admission rules. Keep each inner payload reader alive for its physical-order requests, so extracting many records does not rescan each TAR per file. Before payload use, reparse the outer envelope and both TAR indexes, retain those readers, project the complete fresh index and compare it with the immutable parent snapshot. Caller-supplied names, identifiers, types, methods and sizes cannot substitute other records. Padding and member spans are validated again. Readers cannot resume after failure. Parent host source checks, staging, per-file verification and final publication remain authoritative. The existing source identity checks detect changes on a best-effort basis; ar has no content checksum and these checks do not create an atomic or authenticated source snapshot. Parsed ar ownership/mode fields grant no permission restoration.

Apply common limits to the entire package's member/row counts, raw/resolved/display name bytes, physical source span and decoded metadata work. Control and data do not each gain a fresh aggregate decoded quota. Input I/O is counted across shared views within each preparation or delivery phase. Preparation is separate from delivery, as with existing TAR indexing and payload reopening; cached preparation bytes grant no additional source access. Delivery still accounts raw-member exports and actual inner decoding independently from delivered file bytes. Reject a limit before its next read/write/allocation, and check cancellation at record boundaries and source reads.

The profile is read-only, without passwords, volumes, package creation or rewriting. Raw ar members have known packed sizes; compressed TAR child records do not. Checking uses `format_declared_checks`: validate container structure, readability and checks actually declared by the admitted inner filters. This is not package authentication. Automated acceptance includes independent known-content references, every admitted filter family, nested bounds, duplicate identities, malformed envelopes/inner checks, exact budgets, source changes and cancellation, plus actual CLI/Qt browsing, checking and extraction. Generated evidence remains under `build/` or CI, separately from platform and release approval.
