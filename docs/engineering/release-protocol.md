# GitHub Release protocol v1

The dedicated [Release workflow](../../.github/workflows/release.yml) runs only by manual `workflow_dispatch` and requires an existing version tag. Creating or moving a tag does not trigger another release build, so three-platform native builds for one commit run once in that manual run and assembly reuses artifacts from the same run. The on-demand Qt workflow's macOS job performs SDK verification only. The dedicated release flow explicitly permits native Apple Silicon Qt deployment, necessary ad-hoc integrity signing, and ZIP/DMG packaging and verification from one app. Developer ID, Apple notarization, and Windows publisher certificates are not used.

The complete tag is `v` plus the semantic version derived from VERSION.json. `prerelease_number` is an optional positive integer; its absence remains compatible with historical build numbers. alpha.1 and build 14 are distinct identities. Windows numeric resources and macOS CFBundleVersion still use monotonically increasing build numbers. Public assets for the same version cannot be replaced; revisions require a new version. Drafts may be rerun.

Release notes are durable, reviewable version inputs, read by default from `release-notes/<full-version>.md`; the CLI may specify a reviewed file with `--notes-file`. The file contains one `<!-- xdzip-release {"version":"0.1.0-alpha.6","build":19} -->` metadata line and a matching version heading. Version and build must match VERSION.json. Run `python3 scripts/publish-release.py --check-notes` first; this check does not contact GitHub. The dedicated workflow performs the same preflight before building. New versions need new notes and do not automatically inherit older feature lists or acceptance status.

Notes document Chinese and English acceptance boundaries by platform, actual commit, and evidence, preserving existing manual acceptance separately from unperformed checks. Issues continue to track stage progress. Draft creation and publication use the same notes snapshot. On a draft rerun, if its body differs from the reviewed file, stop before uploading/deleting assets and require explicit alignment of inputs. Published versions continue to reject reruns that replace assets. `CHANGELOG.md` archives only actually published versions; local development delivery is not invented as public release history.

Before changing draft assets, the publisher reads back the GitHub tag, draft state, and channel marker. Stable must remain non-prerelease and become GitHub Latest; alpha, beta, and rc must remain prereleases and not replace Latest. Recheck appropriate state after publication and after public attachment verification; report success only when all match. If post-publication checks fail, the release may already be visible. The script stops for owner handling and does not automatically withdraw, edit, or replace the public release or assets.

Before formal release, complete local build, contract, and release-note preflight matching the commit. Use the version tag for one manual Release workflow run: create a draft, run three-platform native and contract checks in parallel, then reuse uploaded artifacts for assembly, signing, and publication through a protected environment. Do not run a validation workflow and then rerun formal release for the same commit, which would rebuild native artifacts. Formal release requires a version tag and production update signing; a commit SHA cannot impersonate a tag.

The release contract job first builds the same-commit isolated format worker and runs Rust workspace tests with `XDZIP_NATIVE_CODEC` and `XDZIP_NATIVE_CODEC_WORKER`. Cargo tests alone do not prove paths requiring a real worker executed. Native three-platform jobs separately verify actual applications, deployment, and installation lifecycles.

Each Windows deployment verification uses an independent temporary test copy and retains prior logs. Repeated verification neither reuses nor deletes existing directories; product runtime directories contain no test DLLs.

Releases always include `release.json` and `SHA256SUMS`. Manifest `schema_version=1` has root fields product, version, channel, build, tag, commit (full 40-character SHA), repository, and assets. Each asset includes filename, platform, architecture, package_type, minimum_system, bytes, sha256, and url pinned to the tag download path.

| Platform, architecture | Package types | Minimum system |
| --- | --- | --- |
| windows, x86_64 | zip, exe | Maintained Windows 11 |
| macos, arm64 | app.zip, dmg | macOS 14.0 |
| linux, x86_64 | tar.gz, deb | Ubuntu 24.04, glibc 2.39, X11 |

All six package types are required. Manifest validation rejects missing packages, duplicate targets, inconsistent channels, mutable download URLs, incorrect sizes, or hashes. Release attachments include platform notices, licenses, SBOMs, and deployment/verification materials, without corresponding-source archives. Windows uses app-local VC++ runtimes and does not distribute Windows SDK graphics compiler libraries.

Since 2026-11-05, the owner has directed removal of historical corresponding-source archives from GitHub Releases and Actions artifacts and stopped future release flows from generating or uploading them. `scripts/prepare-source-delivery.py` remains for local review. Release assembly and publication reject archive filenames containing `corresponding-source`. This policy does not change component licenses or establish fulfillment of corresponding-source, relinking, or other obligations. Release review must still resolve those obligations for actual delivery; if required conditions cannot otherwise be met, block affected binary distribution. GitHub automatically generated tag source snapshots in the public repository are not these Release attachments.

Routine releases must not independently run the source-delivery collector locally. Run it only when the user separately and explicitly requests source collection, while still respecting upload restrictions. Evaluate generic machine-review flags against actual components and specific obligations; flags alone do not establish new release defects.

macOS app ZIP, DMG, and notice materials must be exported while the same deployed and signed temporary app remains present, before staged `.app` and temporary registration cleanup. Do not redeploy another app after cleanup to fill in the ZIP.

Order: local preflight, freeze the version commit, create the tag, manually dispatch one Release workflow, perform three-platform builds and independent startup/installation-lifecycle verification, assemble the draft manifest, publish by channel after everything is complete, then redownload and verify all attachments. Stable is a normal Release explicitly marked Latest; alpha/beta/rc are Pre-releases. Any platform failure leaves the draft unpublished. Verify SHA256SUMS before and after publication. When provenance/license review or manual acceptance is incomplete, preserve limitations in notes; automation cannot impersonate those conclusions.

Update clients paginate GitHub Releases, skip drafts, validate manifest versions, and choose by semantic version, user-permitted channel, platform, architecture, and package type. Do not infer upgrades from publication dates or guess filenames. Prereleases do not use `/releases/latest`, which excludes them. Stable receives stable only; alpha allows alpha, beta, rc, and stable; beta does not return to alpha; rc receives only rc and stable; dev is supported in development-version comparison. Both semantic version and monotonic build must increase. After download verify size and SHA-256; reject missing or mismatched values.

## Trusted update attachments

New releases include `release.json.sig`, with schema_version=1, algorithm=ed25519, key_id, and a 128-character lowercase hexadecimal signature. The signature covers exact raw `release.json` bytes; do not parse and reserialize before verification. Clients and Qt-free installation helpers each use their embedded `resources/update-trust.json` public-key set; trust roots from downloaded manifests or user requests are not accepted. Reject unknown public keys, duplicate key_id, weak keys, and empty trust sets for installation.

After final app.zip naming, the macOS native phase uses `xdzip-update-tool sign-archive` to emit `macos-update.json` with schema_version, version, build, filename, bytes, sha256, and Sparkle base64 `ed_signature`. Assembly rechecks the archive and signature and creates `appcast.xml` containing the same immutable candidate only. Optional manifest field `macos_appcast_url` is pinned to that file under the same tag. The feed uses build as Sparkle version, full semantic version as shortVersionString, macOS 14.0 as minimum, and embeds only brief release notes. Full notes remain the GitHub Release body; clients do not fetch external release notes.

Archive and feed use a separate Sparkle key; the feed itself must also be signed. Cross-platform release tools follow [Sparkle's upstream signing format](https://github.com/sparkle-project/Sparkle/blob/2.x/common_cli/Signing.swift), signing complete raw XML and appending a sparkle-signatures comment block with base64 edSignature and raw-byte length. This is not merely signing the enclosure. Independently verify after generation; any byte change requires resigning. The Mac package SUPublicEDKey must match the public key in `resources/sparkle-update-key.json`.

The release environment supplies existing keys and public key ID through `XDZIP_UPDATE_SIGNING_KEY_HEX`, `XDZIP_UPDATE_KEY_ID`, and `XDZIP_SPARKLE_SIGNING_KEY_HEX`. The owner supplies two production public-key resources, versioned with clients and installation helpers; do not embed test public keys or generate private keys at build time. The owner first ships public trust roots in a client version, then configures matching private keys in a trusted release environment. Key rotation delivers new public keys before switching signing keys so old clients retain a verification path. Older clients without embedded public keys must first manually install a version containing them; downloaded manifests cannot add trust roots. Old public releases are not retroactively signed or replaced.

Release scripts build signing tools in a child process with both private-key environment variables removed; only the compiled tool process receives signing private keys. Cargo build scripts, compilers, and dependency resolution do not receive signing authority.

Formal native signing and assembly bind to the protected `release-signing` GitHub environment. The owner must configure matching secrets and environment protection. Mac private keys enter only a separate archive-signing step after native builds, not the build stage. Environment configuration and production trust roots are actual release prerequisites and are not created by ordinary CI.

[Production update acceptance](../../.github/workflows/production-update-acceptance.yml) is a separate manual entry point pinned to `main` and `contents: read`, using the same `release-signing` environment and owner approval. It does not invoke Release or create tags, drafts, or releases. First compile tools in a secret-free step, then independently derive public keys from existing private keys and strictly compare them with both public keys and public key ID in the current commit; entry existence does not establish a match. Private three-platform old build 200 and new build 201 retain production public keys and are built without secrets. Signing accepts only fixed candidates fully bound to this source commit, private product identity, and hashes. Native upgrade, failure recovery, and ordinary restart then run in secret-free processes. There are no arbitrary input manifests, assets, remote artifacts, or release parameters.

During secret-free macOS toolchain preparation, install `rustfmt` and `clippy` declared in `rust-toolchain.toml` once, then run archive admission tests. Test-key update regressions also cover preparation and admission without using or verifying production private keys.

Production acceptance packages, original manifests, signatures, appcast, and apps remain on disposable runners and are not uploaded. A bounded collector uploads only explicitly allowed logs, status, identity, and hash records, rejecting signed attachments in result slots. Record production-key matching, signature verification, actual installation, and manual desktop acceptance separately. macOS uses native Apple Silicon and actual `SUPublicEDKey` checks; Windows Server fixtures do not replace manual Windows 11 acceptance. This flow neither reads GitHub Secret values locally nor authorizes release.

`prepare-release.py --require-update-signature` stops if any key, signature, or native archive metadata is missing. `publish-release.py` independently reverifies the manifest, same-candidate feed, and archives before uploading. Signatures, appcast, and status attachments all enter complete SHA256SUMS. Do not add or replace these attachments on already public releases.

## Independent CLI attachments

Starting with v0.2.0, complete releases additionally provide `xdzip-cli-<version>-windows-x86_64.zip`, `xdzip-cli-<version>-macos-arm64.tar.gz`, and `xdzip-cli-<version>-linux-x86_64.tar.gz`. All three come from same-commit native CLI builds and verification, retaining workers, actual runtime dependencies, and notices; identity must be clean Release. Ordinary CI gains no permission to deploy or upload Mac app packages.

CLI uses `cli-release.json` and `cli-release.json.sig`. Manifest schema_version=1, product=xdzip, and component=cli. version, channel, build, tag, commit, and repository exactly match the desktop manifest. Assets contain only these three targets with the same fields as desktop assets. Mac package type is tar.gz; Linux minimum system omits display_server. Other system, architecture, size, and digest requirements remain. The fixed publisher remains xiaodaozhi/xdzip.

Desktop release.json continues to contain exactly six package types without component or CLI entries. Old clients ignore new independent attachments. CLI manifest signing reuses embedded Ed25519 trust roots; sign-cli/verify-cli sign and independently verify exact raw bytes. Full assembly and publication can go public only after signatures, identities, all three CLI packages, and all checksums are complete. Existing public releases do not receive retroactive additions, changes, or replacements.
