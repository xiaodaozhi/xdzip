# cxx bridge dependency rationale

Qt/Rust uses a typed ownership bridge generated by `cxx`; C++ retains Qt objects and Rust retains domain and runtime logic. `cxx` and `cxx-build` must have exactly matching versions, as governed by [Cargo.lock](../../Cargo.lock) and [toolchain policy](toolchain.md). cxx is not a stable ABI for third-party format extensions. A handwritten C ABI would reduce dependencies but increase maintenance of strings, free functions, and ownership invariants.

## Source and licensing

The source is crates.io, with [dtolnay/cxx](https://github.com/dtolnay/cxx) upstream. Dependency source hashes, versions, features, build scripts, and license declarations come from the lockfile and [bridge dependency inventory](../../specs/engineering/bridge-dependencies.json). Recheck and aggregate actually applicable notices for release. The lockfile includes dependencies whose target conditions may not hold; it is not the actual linked-binary inventory and does not cover compilers, Qt, or system libraries.

## Build and ownership boundaries

cxx-build generates sources and headers and invokes C++ compilation tools; cxx compiles the bundled bridge implementation, and link-cplusplus links the C++ standard library. Cargo verifies dependency acquisition against the lockfile. New build scripts or optional features require renewed review of network and execution behavior; historical checks are not a security conclusion for a new version.

Retain std/alloc and other features actually needed by the product. Trimming requires reverifying UTF-8, error propagation, unique handles, backpressure, shutdown, and draining. The [runtime contract](m1-runtime.md) and [bridge design](../design/05-qt-rust-bridge.md) define actual interfaces. Release licensing review follows the [release review process](../qa/release-review.md).

Specific probes, CI runs, and acceptance conclusions are recorded in the [WP-01 issue](https://github.com/xiaodaozhi/xdzip/issues/1) and its Actions artifacts; execution reports do not accumulate here.
