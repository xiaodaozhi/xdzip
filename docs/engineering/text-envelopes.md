# UU, UUE and XXE text envelopes

English | [简体中文](../zh-CN/engineering/text-envelopes.md) | [繁體中文（台灣）](../zh-TW/engineering/text-envelopes.md)

Traditional UU fields and bit order follow [NetBSD uuencode(5)](https://man.netbsd.org/uuencode.5). Base64 mode is described by [uuencode(1)](https://man.netbsd.org/uuencode.1) and [GNU Sharutils](https://www.gnu.org/software/sharutils/manual/sharutils.html). The XX alphabet is `+-0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz`, checked against the public encoder in [UUDeview](https://github.com/hannob/uudeview). The Rust reader is independently written from these field/bit rules. The reference C implementation is a test tool only, never a runtime dependency.

## Admitted profiles and boundaries

Accept `begin`, one space, one to four octal mode digits, one space and a nonempty raw filename. The header's mode is syntactically validated but never restored. UU and XX share this header; identify the actual alphabet through a fully valid counted body line, including an empty member's zero-count line. Each line's first sextet declares 0–63 decoded bytes and must have exactly `1 + 4 * ceil(count / 3)` characters. UU accepts space and backquote for zero. Decode high bits first, three bytes per four sextets, discarding unused bytes in a final group without requiring their historical padding bits to be zero. A zero-count line must be immediately followed by an exact `end` line. Do not repair shortened or damaged lines.

The `begin-base64` variant admits ordinary Base64 lines of 4–76 characters, each a multiple of four, with canonical zero padding bits. A padded line closes the data body; only the exact `====` trailer may follow. Empty bodies are allowed. Bare Base64, MIME assemblies, GNU `begin-encoded` filename extensions, multipart repairs, yEnc and BinHex are outside this profile. `.uu` and `.uue` are candidates for UU; `.xxe` is a candidate for XXE. Candidates do not determine the actual alphabet.

Accept LF or CRLF and a complete final trailer without a final newline. Bounded transport text may precede, separate or follow members. A header-looking malformed or unsupported line is an error, never ignored to hide a member. The first header must start within 64 KiB; individual transport/header lines are at most 8192 bytes. Strong container signatures, optical descriptors and valid TAR headers take precedence over text candidate discovery. Complete validation, not a suffix or the word `begin`, admits the format. An all-XX archive is labeled XXE; ordinary UU, Base64 and mixed-member envelopes are labeled UU. Each physical member keeps its serialization-order identity, original name and actual encoding, including duplicate names.

## Host authority, quotas and checking

The backend receives only an authorized seekable source and host-owned sink. Header filenames pass through shared archive-level filename resolution, display escaping and unsafe-path checks. They never open an input or grant an output path. The reader does not restore permissions, follow external files, execute commands or create directories. It provides no writer, rewriting, encryption or split-volume authority. Encoded body/trailer spans are known packed sizes; payload sizes are computed from validated lines.

Metadata validation reads the entire envelope under the common scan limits, normally 64 MiB of actual source reads, 100,000 entries, 4096 raw bytes per filename and 16 MiB aggregate raw/display name budgets. It retains bounded member spans rather than decoded content. Before payload delivery, rescan and compare the complete projected index with the immutable host snapshot, then retain these locators for arbitrary physical selection without rescanning every earlier member. Metadata and repeated body reads count toward a private 24 GiB cumulative input ceiling; delivered bytes have a separate 24 GiB ceiling, with stricter host task/file limits still applied. Reads, line work, sink delivery and separate cancellation tokens are checked cooperatively. Typed source failures are preserved without retrying terminal `Interrupted` failures. Any source, structure, quota, cancellation or sink error poisons the opened reader; no retry refunds work.

Checking validates structure and readability, with **no checksum or authentication**. Changing valid sextets can change output without causing a check failure. Staging and final publication remain host responsibilities; source identity checks are best-effort detection rather than an authenticated snapshot. Whole-envelope validation includes all members, even for selected extraction; unsupported header extensions or malformed later members cannot be silently skipped.

## Automated acceptance

Owned reference inputs cover all byte values, empty files, line tails, UU zero aliases, CRLF, XX and Base64, transport text and mixed members with duplicate names. Pin the independent source revision and call only its public encoder; verify UU through Python `binascii`, and Base64 through its independent standard decoder. Also exercise all counted lengths 0–63, unsafe/Unicode names, exact input/name/decoded limits, short reads, typed failures, snapshot mismatch, cancellation, terminal poisoning and unchanged existing outputs. Actual runtime, CLI and Qt tasks cover browse/check/extract, physical selection, read-only explanations, checking-strength notes and registered candidates. Affected bilingual/theme/font layouts and main/menu proportions use automation. Reference binaries and generated evidence stay under `build/`; progress and actual results belong in the delivery issue.
