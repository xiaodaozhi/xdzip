# Application sessions and shutdown contract

The tab context menu offers “Close,” “Close Others,” and “Close Tabs to the Right.” Shift+F10 or the menu key acts on the focused tab. Right-click does not switch the current page. Commands freeze the tab's stable identity and operate only on the current visual order in its owning window; they must not affect other windows. Close the menu on reorder, window resize, target disappearance, or entry into a modal operation. Disable bulk actions without applicable targets. Submit a bulk close once. Preserve the current page if it remains open; otherwise switch to the anchor tab, avoiding repeated page flashes. Closing the last page restores the welcome page; tasks and results remain in the global task entry point.

Within one user login session, ordinary installed and portable processes share a single instance, tray, and application menu. Windows packaged processes use a separate single-instance namespace and do not forward requests to an ordinary installation, preventing Store launches from reaching the ordinary version's update interface. When both processes coexist, each owns its tray. Existing installation/update gates conservatively constrain both; coexistence, settings, and associations require actual installation-environment verification. Version queries return before GUI creation. Smoke tests, desktop probes, and tests use isolated paths and do not connect to the real user instance.

`SingleInstance` uses QLockFile to elect an owner before creating the main window; only the lock owner may remove a crash-leftover local server. QLocalServer uses UserAccessOption. The structured JSON protocol is version 1, limited to 256 KiB per message, 128 absolute paths, and 32 connections. A later process waits for the primary to become ready and exits after receiving acknowledgement for its request ID. Communication failure within 15 seconds is reported explicitly; no second normal UI is created. On Windows, the launching process transfers foreground activation permission for this user action using the PID in the server handshake, without permanent always-on-top. IPC does not pass through a command interpreter or log user paths.

`ApplicationSessions` is a Qt application-layer coordinator; it does not interpret formats, authorize directories, or commit files. Each session owns an independent SessionPage, BrowserController, and Rust RuntimeConnection. Open pages retain query, selection, directory, and browsing state. Windows host pages; tabs do not create a hidden native main window for every archive. File associations, command line, native file-open events, Open, recent items, drag-and-drop, and creation results all submit open intents. Prefer reusing an idle welcome page without an archive or task. A duplicate path activates only a session that is still open. Multi-file requests are accepted in order and activate the last one. Path normalization is for UI deduplication only and grants no write authority.

`desktop/openMode=tabs|windows` defaults to tabs, keeps schema version 1, and preserves unknown fields. A successful setting change immediately affects future opens without migrating existing pages. The title-bar plus opens a page or window according to this setting.

Tab ordering submits a stable session identity and target index within its window. It changes only the display order of open sessions in that window, not the controller collection used for task admission. After drag release or keyboard reordering, preserve the active page, archive, controller, selection, and task identity; relative ordering in other windows and of closed background sessions is unchanged. Closing an inactive tab does not switch pages. Closing the active tab selects its visual right neighbor, or its left neighbor if there is no right neighbor. Ignore ordering requests with invalid identities, closed sessions, out-of-range indexes, or during shutdown; do not create or destroy Rust connections. Only within-window reorder is currently supported; cross-window dragging, window detachment, and restoring order across launches are not. Tab-bar overflow changes only the visible region and must not discard sessions. Menu and keyboard activation ensure the active tab is visible.

At most 32 live sessions are retained, with an explicit notice at the limit. If background tasks retain every slot, closing the last browsing page reuses its shell to display the welcome page and global task entry without creating an extra runtime. Closing a tab or main window clears that page's directory, search, sorting, selection, scroll, and view state but does not cancel background tasks. Pages with tasks or completed results retain their controller and task-required data. The unified task menu uses “session UUID/backend task ID”; the same numeric ID in another connection is not the same task. Password, conflict, and result windows remain handled by the original session controller. A closed page without tasks first requests asynchronous shutdown and is removed from the session collection only after its receiver thread joins.

After session closure, late start, preflight, password, and conflict events do not automatically open windows or steal focus. Task and request tokens remain. When the user explicitly opens the task from the global task entry, show the original session's progress and pending requests. Closing a page does not cancel a request.

The global task entry displays the original controller's task window by composite identity. It first closes the invoking menu; it does not switch the current archive tab, restore a closed archive page, or restore the main window. Password, conflict, and cancellation actions remain routed to the original controller. Ignore invalid or expired task identities. Closing a browsing page and explicitly viewing a task are separate user intents.

After task-menu content changes, a short list that fits in the viewport starts at the first item. A stale scroll position must not clip task rows. Lists exceeding the height limit remain scrollable; the clear area stays fixed.

Clearing task history is an application-layer display intent. Controllers retain authoritative backend snapshots and late acknowledgements, marking terminal items hidden only in bounded history. Duplicate updates for the same terminal state must not make them reappear. Active counts, preparation placeholders, passwords, conflicts, cancellation, and joins do not use hidden markers. Emit no change when there is no completed history. Eviction also removes hidden markers. Closed controllers with no visible tasks are reclaimed using the existing asynchronous shutdown flow. Cross-session clearing operates by controller identity and must not clear another session's active task because it shares a numeric ID.

Creation, extraction, and integrity checks use serial application-level admission, including preparation, password/conflict waits, commit, and cleanup. A controller waiting for admission retains only one bounded command; it is cancellable and does not occupy the GUI thread. Each Rust connection's task ordering and safety semantics still apply. Explicit exit first confirms across all sessions. Choosing wait exits after all tasks complete; choosing cancel waits for cancellation, cleanup, and joins across all connections. Check only shutdown completion state; do not trigger shutdown again from the state check.

Heavy-task snapshots carry the original task-creation request ID, even if they arrive before `TaskAccepted` or after that request's `Finished`. A controller binds its preparation placeholder to an actual task only when request, original session, and task identities match. Snapshots from other requests or sessions cannot consume the placeholder. Count the task and placeholder only once; terminal tasks are no longer active. Binding does not replace an actual acceptance receipt, open the task window early, or bypass serial admission, cancellation, or the all-connections join barrier.

Waiting for all tasks to exit converges only on the application-level task count and join barrier. When one page finishes first, do not run the former single-page auto-close behavior, hide the last window because that page ended, or show the exit confirmation again.

Set application-level `quitDecisionPending` before showing exit confirmation. Queued password prompts and explicit requests to redisplay them are paused across all sessions and windows during this decision and cannot cover the confirmation. Returning or choosing wait resumes only the still-valid task and prompt token. Presentation remains paused during cancellation, cleanup, and joins; do not reopen password windows. This state neither hides nor cancels existing requests and does not change explicit task access after session closure.

System Quit, the application menu, and tray explicit exit use the same desktop route. Password and conflict prompts owned by managed sessions may be superseded by global exit confirmation. Returning preserves the task and request tokens; cancel and exit still waits for every connection's cleanup and join. Native file selectors, other modal controls, and prompts outside managed windows continue to block exit and stay in front. A generic modal check must not swallow exit during password waiting or bypass confirmation to cancel tasks.

Tray Settings and About directly show the shared settings window. If the main window is hidden, minimized, or absent, use a standalone instance without creating or restoring the main window. Tray Exit goes directly to global quit and uses the shared confirmation while tasks are waiting. “Show main window” explicitly restores or creates a browsing window.

When the main window is visible, “Show and activate” only raises it and requests activation. When hidden or minimized, restore its prior normal, maximized, or fullscreen state without first restoring to normal and then maximizing. Prioritize activation of blocking modal windows. A popup's transientParent is its actual invoking window. Closing the final main window continues to follow the tray setting. Settings and About use a unified entry point: activate an existing window first, and switch it to the About page for the About action.

`showMinimized()` replaces the original state bits. During restoration, add the saved maximized or fullscreen flag while still minimized, then remove only the minimized flag; do not first show a normal window. Native regression waits for the window to be actually exposed and active and its final state confirmed, rather than treating a Qt request as a completed window-manager state.

The Cocoa path observes minimize and fullscreen transition notifications on the owning NSWindow. Keep restore requests pending during transitions and continue after native confirmation. If Qt reports minimized while the same native window remains visible and exposed and no transition is in progress, cancel the ineffective Qt state request and restore the saved state rather than waiting for a native confirmation that will not arrive. Remove observers when the native window is destroyed. If the window cannot be obtained, keep the request pending; do not use a fixed delay as proof of completion.

A minimize request during fullscreen entry or its completion callback may be overwritten by a later Qt state or recorded by Qt without AppKit accepting it. Record the request for the same native window. After entry, if it is still visible and no transition is in progress, align Qt state with native fullscreen on the next event-loop turn and retry minimization. Newer restore, normal, or maximized requests take priority. Do not retry if the window is destroyed or unavailable. A restore received during alignment also takes priority and cancels the older minimize request.

Password/quit ordering regressions use real AES waiting. They cover synchronous Quit after the task notification establishes the request but before deferred window presentation, from the same page, another session, and another window, including choosing wait. A genuinely posted Quit after the window is shown is a delivery control. Record actual notification and delivery states. Verify that the queued password window does not cover the exit decision, return/wait retains the same token, and cancellation completes all joins. Controlled synchronous notification order is not evidence of a historical platform event order.

Acceptance covers actual native window state changes, concurrent starts and crash leftovers, Unicode and batch routing, both opening modes, save/cancel and restart, cross-session ID conflicts, background tasks, passwords/conflicts, global exit, and receiver-thread reclamation. Offscreen tests establish state contracts only and do not replace native visual, accessibility, or manual desktop acceptance. Evidence stays in build/ or CI artifacts.

Once exit enters actual cancellation and joins, IPC explicitly rejects new intents. Release the election lock only after closing the channel; launch the restart process only after all connections finish. Repeated cleanup by the old instance must not remove the new endpoint. Windows restart also transfers foreground permission for the current user action.

For external opens received during a blocking dialog, retain the last activation intent, activate the blocking window first, and show the corresponding new window after it closes so that a hidden new window does not lose its entry point. The settings window retains its actual caller; another main window gaining focus does not change ownership.

The native regression entry point is `python3 scripts/check-native-sessions.py --tests <browser-tests> --output build/review/native-sessions.json`. Linux uses the real X11 window-management path with Xvfb and Openbox; Windows and macOS use system window managers. The script manages only validation processes it starts. The on-demand Qt workflow and Release share this entry point. Native logs and JSON remain in build/ or CI artifacts and cannot establish unperformed manual visual, GPU, IME, or screen-reader checks.

On Linux, create the Qt test process only after Openbox's `--startup` callback. `_NET_SUPPORTING_WM_CHECK` declares only window-manager identity and does not prove that theme and event handling are ready. `scripts/check-x11-startup.py` and `scripts/test-x11-startup-supervision.py` check cold-start readiness and timeout cleanup respectively, retaining their own process logs. Additional waiting or retries do not replace the original first-window assertion.

Closing a main window differs from minimizing it. Closing the last window with a tray clears all its browsing tabs, closes all owned dialogs including Settings and About, cancels unsaved appearance previews, retains applied settings, destroys native window resources, and then hides the main window. Restoration from the tray, Dock, or a second launch without file arguments shows only one welcome page and does not restore old tabs or owned dialogs. A non-final window still closes and cleans up its own browsing tabs and owned dialogs without affecting other windows. Background tasks and prompt tokens remain with their original controller; recreate the corresponding native window only when the user explicitly opens the task. If a modal window blocks, activate it first and do not accept main-window closure.

Closing a window does not cancel real background tasks; their owning sessions remain by composite identity. Normally a new blank session hosts the welcome page. At the 32-live-session limit, temporarily use the closed page's archive-free shell, hiding its old title, loading, and error feedback. Create a blank session after asynchronous join frees a slot, without exceeding the limit. This replacement does not reveal a hidden window or steal focus from another window. The global task entry displays only the task window. A file-open request does not restore a closed browsing page; it rereads using a new session. If a background task is still modifying the same file, the new page shows a cancellable wait and rereads after the task terminates. Canceling that wait does not affect the original task.

After an open fails or is canceled, a welcome page that is not reading and has no active task or password prompt can be reused for another open; the old path is not treated as a successfully opened archive identity. When reopening a closed archive retained by a task, prefer the current idle welcome page and read using a new session while keeping the original task's independent identity. Other pages explicitly created by the user and other windows are unaffected. Canceling a wait or closing the waiting page must not resurrect the open request after the task finishes.

If the user cancels while an open is still displayed as in progress, do not commit its result or show a password prompt even if a background completion receipt is already queued. The controller waits for the original request to finish, queries for any runtime archive session that may have been established, and closes it. Remain busy during cleanup; repeated cancellation does not stop cleanup. Report an actual cleanup failure rather than claiming cancellation cleanup succeeded. Other accepted background tasks retain their own lifecycles.

When accepting main-window closure, increment the activation generation and disconnect modal-wait connections. Already queued old wakeup callbacks must also check generation; they cannot redisplay the main window or restore old tabs immediately after a modal closes. This invalidation is shared with normal open entry points and does not cancel background tasks.

Update handoff uses a separate `prepareForUpdate` barrier rather than immediate restart. Reject handoff while tasks, task starts, or modal interactions exist; download may continue and waiting is cancellable. Once accepted, close new-intent entry points and clean up every Rust connection. Only after all joins complete emit `readyForUpdate`; do not exit early. The update provider signals the exit barrier before releasing the installation commit, and only then does the main application release its normal quit interception. If installation commit fails, retain a recovery entry on About, permit normal user exit, and do not automatically restart the old version. See [software updates](software-update.md).

## File-manager operation sessions

[File-manager context actions](shell-actions.md) use operation sessions without browsing pages or a main window. They share existing composite task identities, serial admission, and the exit join barrier. A cold start loads only the independent operation host; an already running instance does not switch tabs or restore the main window. Batch preparation and input waits count toward global activity; successful creation does not enter the browsing open queue. Create a browsing window only when the main window is explicitly shown.
