# AES Crypt read-only envelopes

English | [简体中文](../zh-CN/engineering/aescrypt-envelopes.md)

The independent Rust `xdzip-codec-aescrypt` backend reads AES Crypt stream versions 0, 1, 2 and 3. Application version numbers are separate. One regular virtual file is exposed; there is no creation, modification, volume or external-extension fetch capability. The format contains encrypted data without compression, so the row's method is Store and its encrypted flag is true. The packed size is the complete physical envelope. Content discovery, not `.aes`, selects the backend.

## Admission and authentication

All four versions require an opening password. The entire ciphertext is authenticated before exact-size metadata becomes visible, including empty files. The immutable archive session retains its bounded opening credential for checking, preview and extraction through the existing host secret slot; no new per-entry password mechanism is introduced. A second complete authentication admits the task reader. The export pass authenticates exactly the ciphertext it decrypts and succeeds only after its final MAC and size checks. The host publishes staged output only after codec success and source checks; unverified chunks never authorize final publication.

Versions 0–2 use the specified 8192-round SHA-256 ACKDF with UTF-16LE password bytes. Version 0 derives the data key directly and cannot distinguish an incorrect password from ciphertext corruption; it reports `password_or_integrity`. Versions 1–2 authenticate the wrapped session IV/key using HMAC-SHA-256 before CBC decryption. Their verifier failure reports `wrong_password`, which can also result from damaged wrapped data. Version 3 uses UTF-8 PBKDF2-HMAC-SHA-512, authenticates the wrapped session bytes plus version byte `03`, and uses AES-256-CBC with PKCS#7 padding for data. Actual ciphertext authentication precedes padding validation, both during metadata admission and after export; padding is not used as a password verifier. MAC comparisons have fixed width and use the admitted constant-time primitive.

Ciphertext HMAC-SHA-256 is verified in every version. However, versions 0–2 store the final plaintext length modulo 16 outside that authentication. A change to this field may alter the reported and exported length without invalidating the MAC. Extensions in versions 2–3 are also unencrypted and unauthenticated. Consequently `format_declared_checks` means that all checks declared by the format passed; it does not authenticate every envelope field, a sender identity or file provenance. Version 3's encrypted padding authenticates the plaintext length. Successful legacy checks must not be described as fully authenticated plaintext length.

## Names, limits and failures

The virtual basename comes only from the authorized host basename by removing a case-insensitive `.aes`; unsafe, empty, dot or dot-dot stems become `content`. Unauthenticated `FILENAME`, `URI`, `CREATED_BY` and container extension values provide no pathname, network, process or execution authority. No timestamps or executable permissions are restored. Ordinary TAR whose first member is literally named `AES` remains TAR after bounded framing disambiguation. A valid encrypted envelope containing a TAR marker in an extension remains AES Crypt. Once admitted as AES Crypt, authentication failure does not trigger TAR, ZIP or another format fallback.

Versions 1–3 require reserved byte zero; extension records require a NUL-delimited identifier. Admission limits are 256 extension records, a 1 MiB header and version-3 iteration counts from 1 through 2,000,000. Zero, malformed, truncated or non-block-aligned data is rejected before KDF work. Unknown versions are unsupported. Legacy modulo values must be 0–15; a zero-length cipher requires modulo zero. Version 3 requires at least one padded block. There is no damaged-data repair.

Reader-private cumulative quotas each have a hard 24 GiB maximum: actual input, actual hash compression-block work, actual AES-block work and delivered plaintext. They include metadata authentication, KDF and subsequent reads, with no refund after failure. Caller metadata input/name limits may only tighten admission. Hash work counts KDF, HMAC pads and finalization; CBC charges all actual blocks, including wrapped session material. Additional admission/KDF work is charged to the host sink before payload delivery. Ordinary decoding remains covered by existing host source/output/task budgets, including 8 GiB per-file and 20 GiB per-task plaintext ceilings. The general codec interface admits at most 4096 UTF-8 password bytes; the product's shared credential limit remains 1024 bytes. The iteration ceiling is an application resource policy, not a format maximum.

Cancellation is checked during KDF, each read and each bounded CBC batch. Password-derived hashes, intermediate KDF blocks, keys, IV chains and plaintext buffers use erasable state. The admitted AES primitive enables its zeroization feature. The codec retains derived keys, not an additional plaintext password. Cooperative cancellation cannot interrupt a blocked OS read. Source, cancellation, quota and output errors retain their typed identity; bare interrupted reads alone are retried. Reader errors are terminal. Host source identity/size/time checks remain best-effort mutation detection, not an atomic source snapshot.

## Sources and regression inputs

Primary framing and cryptographic rules are the author's [AES Crypt stream specification](https://www.aescrypt.com/aes_stream_format.html) and [engine stream description](https://github.com/terrapane/aescrypt_engine/blob/master/stream_format.md). The independent backend uses admitted general AES and SHA-2 primitives, not an AES Crypt runtime or official application. It neither executes encrypted files nor bypasses application licensing. Shared secret SHA-512/HMAC state follows RFC 2104 and [RFC 4231](https://www.rfc-editor.org/rfc/rfc4231).

The [owned fixture set](../../tests/fixtures/aescrypt/README.md) contains independently encoded versions 0–3 and is cross-checked by a separate Python cryptographic decoder. Fixed public test keys and IVs are deterministic fixture inputs only. Reference implementations remain under `build/toolchain/`; generated evidence remains under `build/` or CI. Acceptance is `FORMAT-AESCRYPT` in the [verification requirements](../qa/acceptance.md). See also [password handling](password-extraction.md), [checking](archive-checking.md) and [safe extraction](m3-extraction.md).
