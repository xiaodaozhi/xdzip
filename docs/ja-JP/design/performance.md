# 性能設計と測定

[English](../../design/performance.md) | [简体中文](../../zh-CN/design/performance.md) | [繁體中文](../../zh-TW/design/performance.md) | 日本語 | [한국어](../../ko-KR/design/performance.md) | [Français](../../fr-FR/design/performance.md) | [Deutsch](../../de-DE/design/performance.md) | [Español](../../es-ES/design/performance.md) | [Português (Brasil)](../../pt-BR/design/performance.md) | [Русский](../../ru-RU/design/performance.md)

XDZip は索引、転送、タスク実行、画像プレビューのメモリーと作業量を別々に制限します。以下のコード上の上限は実装規則です。時間、メモリー測定値、スループットはビルドと負荷に依存します。後述の参照目標はエンジニアリング上の目標です。

<a name="xdzip-limits-and-mechanisms-in-the-current-code"></a>

## 現在のコードの上限と仕組み

| 領域 | 現在の動作とコスト |
| --- | --- |
| 通常の単一ファイル ZIP/ZIP64 | ストリーミングスキャナーは名前、ディレクトリー、読み取りの予算の範囲で最大 100 万件の物理レコードを受け入れる。使用中のメタデータが 64 MiB を超えるか、新規レコードで常駐項目が 100,000 件を超える場合、レコードを非公開のディスク保存に移す。メタデータファイルは 512 MiB 以下で、別の位置表がある。参照では各ペイロードをデコードせずメタデータを走査する。 |
| メモリーとディスクのクエリー | ランタイムは現在の不変の結果順序を一度構築する。ディスク経路では最大 8 MiB のソートランを退避し、トークンの順序にマージする。名前とソートの保存は上限付き。キャッシュには現在のクエリーを保持し、完全に描画されたビューや無期限のクエリー履歴は保持しない。 |
| 移動と Qt 転送 | ディレクトリーツリーの予算は 32,768 ノード、64 階層、名前 4 MiB。超過してもルート参照と検索を保持できる。ブリッジはページごとに最大 128 行、名前 64 KiB を送る。大きなビューは最大 1,024 行を常駐させ、論理行数は結果全体をカバーする。 |
| コマンド、タスク、書き込み | メタデータとタスクのスレッドは別々の上限付きキューを使う。重いデスクトップタスクは一度に一つ受理する。デコード作業、出力バイト、ファイル確定、ワーカー資源は異なる方法で計上する。ソリッド形式やストリーミング形式は選択項目に到達する前に先行データを読み取るかデコードする場合がある。 |
| プレビューとネイティブワーカー | テキストとエンコード画像には別のバイト上限がある。画像寸法とピクセル数、ワーカー実行、サムネイルサイズは独立して制限する。形式ワーカーには独自のプロトコルとプロセスの上限がある。 |

[ディスク索引の実装](../../../crates/xdzip-runtime/src/disk_index.rs)、[大規模アーカイブの索引](../engineering/large-index.md)、[Qt/Rust ブリッジの上限](qt-rust-bridge.md)、[タスクの受理](task-scheduling.md)、[出力予算](file-security.md)、[プレビュー予算](../engineering/content-preview.md)

メモリーコストには Qt、フォント、描画とモデル、アーカイブメタデータ、位置表とクエリーバッファー、デコーダーの状態、子プロセス、I/O バッファーが含まれます。64 MiB の移行トリガーはメタデータのしきい値です。プロセスツリーのメモリーには索引以外も含まれます。メタデータの受理量を増やしても展開クォータは増えず、ディスク索引を使うセッションでアーカイブ全体の検査や編集が可能になるわけではありません。非公開索引の書き込みと展開の一時準備は別々のディスクコストです。

<a name="xdzip-measuring-the-current-implementation"></a>

## 現在の実装の測定

| 入口 | 測定または検証する内容 |
| --- | --- |
| `scripts/probe-large-index.py` と `xdzip-m2-probe` | 自作 ZIP64 を生成し、実際のスキャナー、並べ替え、ページ分割クエリーを実行して各段階と保存量を別々に報告する。重複、長い名前、ディレクトリー構造を含め、ディスク経路に到達したかを示す。 |
| `scripts/measure-desktop.py` と `xdzip-process-metrics` | デスクトップのプロセスツリー、起動、参照を測定する。展開オプションでは実際の展開を行い、出力バイトを独立して検証する。レンダラー、ビルド識別情報、正確な負荷を記録する。 |
| `scripts/run-performance-suite.py` | 起動、安定したアイドル、参照の Release 観測を収集し、自作テストデータで固定したコアプローブと展開を比較する。報告にはビルドとテストデータの識別情報を記録する。比較は観測であり、参照マシンの承認は別の条件として維持する。 |
| `scripts/check-runtime-resources.py` | プローブのランタイムリソースとフォントの記録を確認する。そのプローブのリソースの識別と網羅を示すが、操作遅延は測定しない。 |

[大規模索引プローブ](../../../scripts/probe-large-index.py)、[デスクトップ測定](../../../scripts/measure-desktop.py)、[性能スイート](../../../scripts/run-performance-suite.py)、[リソースプローブ](../../../scripts/check-runtime-resources.py)、[証拠の収集](../../../developers/engineering/candidate-verification.md#performance-and-resource-evidence)

比較にはコミットと設定、OS とアーキテクチャー、レンダラー、ハードウェア、実行回数、テストデータ、デバイスとキャッシュの条件を記録します。コールドスタートと繰り返し起動は分けます。測定可能な場合は、最初の操作、アーカイブの走査、クエリー順序付け、ページ転送、表示される描画を別々の段階として報告します。キャンセルの応答と実際の停止、クリーンアップを区別します。スループットでは入力、デコード済み、確定済みのバイトを別々に報告します。

プロセスツリーのツールは Linux PSS、macOS の物理フットプリント、Windows のプライベートコミットを区別し、利用できる場合は RSS またはワーキングセットも報告します。同じ指標を同等の条件で比較します。実際のパッケージのダウンロードサイズとインストール後サイズは別々に報告します。画面外の時間やプロトタイプの実行はそれぞれの条件だけを示します。

<a name="xdzip-workloads-for-comparative-tests"></a>

## 比較テストの負荷

| 負荷 | 測定内容 |
| --- | --- |
| B01/B08 空のウィンドウ、アイドル、テーマ変更 | 起動とフレーム時間、アイドル CPU、保持メモリー、レンダラー。 |
| B02 100,000 件と 100 万件の ZIP レコード | メタデータの走査、移行、並べ替え、ページ取得、別々のメモリーとディスクのコスト。 |
| B03/B04 大きな通常ファイル一つ、または多数の小さなファイル | スループット、キャンセル、出力先の作業、同期、クリーンアップ。小さなファイルではファイル操作が支配的になりうる。 |
| B05/B06 高圧縮またはストリームの深い位置にある項目 | クォータ処理と、選択項目に到達するまでの追加デコード作業。 |
| B07 重い作業が保留中の参照 | 一つの重い操作が実行中で別の操作が待機中の検索とページの遅延。 |
| B09 同梱ワーカーと完全なパッケージ | プロセスツリーの使用量、プロトコルコスト、ダウンロードサイズとインストール後サイズ。 |

これらは比較シナリオです。変更に合う負荷を選び、サイズとハッシュを記録したプロジェクト所有のテストデータを使います。

<a name="xdzip-reference-targets-and-planned-research"></a>

## 参照目標と今後の研究

既存の設計は、16 GiB メモリー、ローカル SSD、60 Hz ディスプレイ、システムフォント、実 GPU、Release ビルドを備えた Apple Silicon を参照とします。目標は比較可能な測定の候補であり、最新リリースや別のプラットフォームについての主張ではありません。

| シナリオ | 設計目標 |
| --- | --- |
| 空のウィンドウの繰り返し起動 | 少なくとも 30 回の実行で、操作可能なフレームまで P95 最大 500 ms |
| キャッシュされた ZIP レコード 100,000 件を開いて検索 | メタデータ準備 P95 最大 1 s、索引済みクエリーから表示まで最大 80 ms |
| ウォームページジャンプと GUI スケジューリング | 表示されるページジャンプ P95 最大 50 ms、GUI スレッドの連続ブロック最大 8 ms |
| メモリー | プロセスツリーは空で最大 150 MiB、プレビューとデコード辞書なしで 100,000 項目を参照時は最大 256 MiB |
| アイドル CPU | 安定後、論理コア一つの平均最大 0.5% |
| キャンセル | 応答 P95 最大 50 ms、ローカルの協調ストリーミング停止は最大 250 ms、別々に測定 |
| 展開と配布 | 同一の負荷と I/O 設定で GUI とコアを比較し、スループット損失の設計目標を最大 10% とする。単一アーキテクチャー Mac の目標はダウンロード最大 100 MiB、インストール後最大 250 MiB。 |

ブロック単位の並列展開、索引の永続的な再利用、共通 CPU トークンスケジューラーは設計案のままです。並行処理や保存方式を変える前に、現在の直列タスク経路とメモリー、ディスク経路をプロファイルします。比較では同等のバイト検証、キャンセル、安全な公開を維持します。[アーキテクチャーの変遷](architecture-evolution.md)、[ファイルの公開](file-security.md)
