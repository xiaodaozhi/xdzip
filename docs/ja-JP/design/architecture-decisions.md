初期の記録は 2026 年 10 月 11 日付です。後の記録にはそれぞれ日付を記載しています。「採用」はアーキテクチャ決定が採用されたことを示します。現在の実装に関する注記は、各決定を保守中の契約と機能の根拠に結び付けます。決定を置き換える場合は元の記録を残し、新しい記録を追加します。

## ADR-001: 製品の唯一のインターフェースに Qt Quick を採用

**状態: 採用。**

**現在の実装。** デスクトップは Qt Quick/QML と薄い C++ アダプターで構築されています。Windows SFX のシステムダイアログを使うホストは ADR-013 の限定的な例外です。[デスクトップインターフェース](qt-quick-ui.md)

背景: 製品には、現代的なデスクトップ UI、一貫した操作感、低いリソース使用量が必要です。同じコアを使う Slint、Tauri、Qt Quick の試作を完了しました。UI の機能、一貫性、既存の Linux ソフトウェアレンダリング測定を考慮し、製品段階には Qt Quick を選びました。他のプラットフォームは引き続き検証が必要です。

決定: Qt Quick/QML と Qt Quick Controls 2 を使い、C++ は薄い適応層とします。Slint と Tauri は過去の実験として残し、製品には同梱しません。

コスト: Qt ランタイム、QML モジュール、言語をまたぐビルド、ライセンス対応を保守します。Mac と Windows の入力、アクセシビリティ、GPU、配布には追加テストが必要です。0.80 MiB の試作実行ファイルは完全な Qt インストーラーではありません。

再評価の条件: 対象プラットフォームで必要な機能、ライセンス、セキュリティ保守を Qt が満たせず、実際に最適化しても主要な製品予算を満たさない場合。通常の性能変動だけでフレームワーク選定を繰り返しません。

## ADR-002: アーカイブの業務ロジックはすべて Rust が担う

**状態: 採用。**

**現在の実装。** Rust ランタイムがアーカイブの状態とタスクを管理します。ファイル選択はデスクトップからの意図であり、ファイルシステムへの権限はホストの I/O 層が与えます。[システムアーキテクチャ](../../design/system-architecture.md)

決定: ドメイン、インデックス、計画、タスク、割り当て、パス方針、形式レジストリーを Rust に置きます。Qt は状態を表し、システムのファイル選択を許可し、ユーザーの決定を伝えます。業務テストに Qt は不要です。

代替案: libarchive や 7zip を C++/QML に直接接続する、または UI ごとに制御ロジックを重複させる方法があります。これらはコアを各プラットフォームの UI に結び付け、安全性とキャンセルの一貫した検証を妨げます。Rust を使ってもネイティブライブラリーの安全上のリスクはなくなりません。関連ライブラリーはワーカープロセスで隔離できます。

再評価の条件: プラットフォーム API を Rust で確実に実装できない場合、業務ロジックの責任を変えずに、小規模なプラットフォーム固有の C++ 移植を許可します。

## ADR-003: ビルド時に生成する cxx ブリッジ

**状態: 採用。**

**現在の実装。** 製品はコマンドとイベントに別々のハンドルを持つ型付きブリッジをビルドして使用します。イベント受信側とシャットダウンのライフサイクルは[ブリッジ契約](qt-rust-bridge.md)で定義します。

決定: 製品内部には cxx が生成する型安全なブリッジを使い、同じコミットからビルドします。手書きの C ABI を長期保守せず、頻繁に通る経路で JSON をシリアライズしません。ブリッジに Qt の業務ロジックを入れません。

代替案: 実験的な C ABI の維持、CXX-Qt による QObject の生成、ローカル IPC による GUI とコア全体の接続があります。cxx は Qt のモデルとスレッドの境界を明示したまま、初期段階で別の QObject 生成フレームワークを導入せずに済みます。一方で、薄い QObject 層と CMake/Cargo の連携を保守する必要があります。

保証しないこと: cxx は任意の Rust/Qt バージョン間で動的なバイナリー互換性を提供せず、サードパーティー向け形式プロトコルも生成しません。

再評価の条件: サポート対象のデスクトップビルドまたはライフサイクルの検証が失敗する場合、またはアダプター層が大幅に増大する場合。黙って切り替えず、ADR で CXX-Qt または明示的にバージョン管理された C ABI を評価します。

## ADR-004: 組み込みソース SDK と外部プロセスプロトコルの分離

**状態: 設計上の境界を採用。外部プロトコルは実験段階。**

**現在の実装。** 製品の形式は明示的に登録された組み込み形式です。同梱の形式ワーカーは独自のプロトコルを使います。外部 CBOR 実装は独立した読み取り専用の試行です。[形式アダプターと試行](codec-extension-sdk.md)

決定: 組み込み形式には Rust のソースインターフェースを使い、外部拡張には別の有界なプロセスプロトコルを使います。I/O の権限はホストが保持します。

理由: Rust の動的ライブラリー ABI は安定しておらず、同一プロセス内の任意のネイティブプラグインはクラッシュの隔離とリソース管理を損ないます。既存のネイティブ codec に対する移行、スレッド、シーク、性能検証のコストから、Wasm は現在、汎用の形式ランタイムとして優先しません。将来の利用は否定しません。

コスト: プロトコル、仲介処理、サンドボックス、IPC のオーバーヘッドが必要です。二つの独立した実装が相互運用できてからプロトコルを固定します。

## ADR-005: 実際のファイル書き込みはホストが一元管理

**状態: 採用。**

**現在の実装。** ランタイムが操作を準備し、`xdzip-io` が権限、ステージング、確定を管理します。形式アダプターはリーダーと出力先を使います。[ファイルの権限](file-security.md)

決定: バックエンドは承認された `OutputSink` にのみ書き込みます。実際のパス、競合、ステージング、確定はホストが管理します。ライブラリーの汎用展開を任意のディレクトリーに直接呼び出すことは、その移植部分がホストの制約を受けると完全に検証されていない限り行いません。

理由: 形式ごとにパス保護を実装すると不整合が生じやすく、文字列検査だけではリンクや競合状態を防げません。三つのプラットフォームで安全なファイル層の実装と障害テストを行うコストがあります。

保証しないこと: ホストは悪意のあるプラグインの出力が意味的に正しいことを証明できず、同じユーザーを既に支配している悪意あるプロセスを止めることもできません。プラグインの信頼と権限は明示したままにします。

## ADR-006: 展開はファイル単位、新規アーカイブは全体で確定

**状態: 採用。**

**現在の実装。** 展開はファイルごとに公開します。作成と編集では、ステージングしたアーカイブを検証してから置換または公開します。分割作成は検証済みの一式を一部ずつ公開し、途中で失敗した場合は制限付きのロールバックを試みます。[公開の意味](file-security.md)

決定: 展開する各ファイルはステージングと検証の後に公開します。失敗したタスクでは完了済みの一部が残る場合があります。新規アーカイブは全体を書き終えてから公開し、既定では上書きしません。

理由: 既存ディレクトリーへの結合では、全プラットフォームでディレクトリー全体を真にアトミックな取引にすることは容易ではありません。タスク全体をロールバックしたふりをすると、後からユーザーが加えた変更を削除するおそれがあります。詳細な結果と復旧ログが必要で、キャンセルの意味も明確に説明します。

再評価の条件: 完全に新しいディレクトリーを一括公開するモードを、制限された条件で別途実装できます。既存ディレクトリーへの結合の意味は変えません。

## ADR-007: 有界なアクターとワーカープール、イベントのプッシュ

**状態: 採用。**

**現在の実装。** 接続ごとにコマンドとタスクのスレッドを分け、デスクトップでは重いタスクを直列に受け付けます。Rust のキューと Qt のメールボックスは有界です。汎用リソーストークンプールは設計上の選択肢として残ります。[タスクのスケジューリング](task-scheduling.md)、[Qt/Rust ブリッジ](qt-rust-bridge.md)

決定: 軽量スケジューラーが状態を決め、有界なプールが処理を実行し、Qt は独立したイベント受信スレッドを持ちます。進捗をまとめ、終端状態を届け、キャンセルとシャットダウンには独立した制御受付を用意します。

代替案: GUI の同期呼び出し、ファイルごとのスレッド、無制限の Tokio や `spawn_blocking`、継続的なポーリングがあります。アーカイブ処理は主に同期的な CPU/I/O 作業です。非同期と呼ぶだけで無制限のタスクを導入しません。将来の実際のネットワーク I/O には、局所的に非同期ランタイムを使えます。

コスト: バックプレッシャー、シャットダウン、リソースの貸与を明示する必要があります。利点は、待機中の負荷が低く、タスクで GUI が圧倒されないことです。

## ADR-008: 機能に基づき初版の形式を限定

**状態: 採用。**

**現在の実装。** 初期形式は過去の背景です。保守中のレジストリーと実行時の受付が現在のソースの機能を定め、拡張された読み取り・作成プロファイルと操作ごとの制約も含みます。[形式レジストリー](../engineering/format-registry.md)

決定: v0.1 では ZIP Store/Deflate と TAR/GZIP を使い、暗号化、分割、RAR、7z、追加アルゴリズムを個別に検証します。UI は拡張子から完全なサポートを推測しません。

理由: 形式名だけでは実際の機能すべてを表せません。初版の形式表は短くなりますが、ユーザーに対して正確で検証可能です。

## ADR-009: 小さな製品データとユーザーコンテンツを分離

**状態: 採用。**

**現在の実装。** 設定、インデックス、ジャーナルはそれぞれ異なる期間保持します。ディスク上のインデックスは非公開でセッション内に限定します。起動をまたぐインデックスの再利用と未完了ジョブの再実行は設計上の選択肢です。[ドメインモデル](domain-data.md)、[ファイル公開](file-security.md)

決定: 設定、一時インデックス、取引ログ、拡張マニフェストのライフサイクルを分けます。既定でテレメトリーを行わず、パスワードを永続化せず、起動をまたいでアーカイブインデックスをキャッシュしません。

コスト: 複数のスキーマとクリーンアップ規則が必要です。起動をまたぐインデックスを再検討するには、ソースの同一性、無効化、プライバシー、容量を新たに設計する必要があります。

## ADR-010: 配布全体とライセンスをアーキテクチャの条件にする

**状態: 採用。**

**現在の実装。** GitHub バイナリーと Microsoft Store の MSIX は、文書化された別々のパッケージ経路に従います。経路ごとに実際の配布依存関係、成果物の整合性、ライセンス資料を確認します。[ビルドとリリース](build-release.md)

決定: Qt は既定で動的に配布し、実際のモジュールのライセンスを確認します。インストールサイズにはランタイムを含めます。署名、SBOM、置換・ソース提供の義務をリリース確認に含めます。

代替案: 実行ファイルだけを比較する、または公開直前に `LICENSE` を追加する方法があります。どちらも製品が小さいことや合法的に配布できることを証明しません。

コスト: 配布とライセンスを継続的に保守します。静的な Qt ビルドやストア配布には別の ADR とライセンス審査が必要です。サイズ最適化の PR で付随的に変更してはいけません。

## ADR-011: 初期サポート範囲と個人プロジェクトの保守方針

**状態: 2026 年 10 月 19 日に採用。プロジェクト所有者が明示的に承認。**

**現在の実装。** 現在のサポートと更新は[サポート方針](../engineering/support-policy.md)と[更新契約](../../engineering/software-update.md)に従います。手動更新の条項は v0.1 を説明しています。

決定: 初期対象は Apple Silicon arm64 の macOS 14 以降、保守中の Windows 11 x86_64、X11 と glibc 2.39 以降を使う Ubuntu 24.04 LTS x86_64 です。最新の公開版だけを優先し、固定の応答期限を約束せず可能な範囲でフィードバックを処理します。v0.1 は手動更新とし、開発プレビューは実験版のままとします。[サポート方針](../engineering/support-policy.md)を参照してください。

理由: 既存のネイティブビルド、インストーラー、ランタイム依存関係が範囲を定めます。過去の設計にあった未検証の OS やアーキテクチャの約束を、個人のオープンソースプロジェクトの保守能力に合わせて絞ります。Intel Mac、Windows 10、ARM64 の Windows/Linux、その他のディストリビューション、Wayland のサポートは約束しません。範囲の拡大には先に実装と実際の検証が必要です。

境界: 個人の GitHub オープンソース配布には、有料の開発者アカウント、署名証明書、Developer ID、公証は必要ありません。macOS では整合性に必要な ad-hoc 署名を維持します。この方針はライセンスの出所やパッケージ検証の代わりではなく、将来のすべての OS バージョンとの互換性を意味しません。

## ADR-012: 各形式を独立した Rust の形式・圧縮アルゴリズムに移行

**状態: 2026 年 10 月 25 日に採用。所有者が実装を明示的に承認。サードパーティー製形式エンジンの長期選択に代わるもので、移行完了を意味しません。**

**現在の実装。** 製品のルーティングは Rust の形式実装を使います。該当する 7z、RAR、CAB、光学メディアの読み取りには同梱ワーカーを使います。現在の操作一覧にはプロセス内の ISO 書き込みも含みます。各操作は[形式レジストリー](../engineering/format-registry.md)と[アダプター設計](codec-extension-sdk.md)で確認してください。

決定: 形式の解析と圧縮・展開アルゴリズムには独立した Rust 実装を使います。汎用の暗号、文字エンコーディング、システム基盤ライブラリーは利用できます。まず公式仕様から動作仕様を定義し、その後独立して実装します。参照ソースを一行ずつ翻訳したり、名前を変えてコピーしたりしません。ソースを見た開発者は厳密なクリーンルーム開発を主張しません。資料不足やライセンス制限は別途審査し、特に RAR エンコーダーは開発しません。

移行計画は当時の機能に応じて ZIP、TAR、TAR.GZ、7z、RAR、CAB、ISO、UDF を個別に受け入れて置き換えるものでした。未合格の形式には現行実装を維持し、黙ってフォールバックしたり RAR/CAB/ISO/UDF の読み取り専用範囲を広げたりしません。共通圧縮アルゴリズムは再利用します。名前、同一性、許可された I/O、リソース、キャンセル、確定は引き続き Rust ホストが管理し、Rust 化によってワーカーの隔離を廃止しません。

コスト: 互換性、安全性、性能、ファジング、アルゴリズムを長期にわたり独立して保守します。サードパーティーの参照実装はテストに使えますが、移行済み形式では該当するエンジンを製品の依存関係と配布ファイルから除く必要があります。資料とインターフェースの規則は[独自バックエンド契約](../../engineering/independent-rust-codecs.md)、進捗と実際の受け入れは [#45](https://github.com/xiaodaozhi/xdzip/issues/45) を参照してください。

<a name="xdzip-adr-013-standalone-windows-sfx-host"></a>

## ADR-013: 独立した Windows SFX ホスト

**状態: 所有者が承認した初期 SFX プロファイルについて、2026 年 11 月 16 日に採用。**

**現在の実装。** [SFX 契約](../engineering/sfx-creation.md)は Windows プロファイルと、Rust およびシステムダイアログによる独立した入口を定義します。

背景: 生成された Windows x64 自己展開アーカイブは、xdzip や Qt をインストールせずに動作する必要があります。各アーカイブにもう一つ完全な Qt アプリを入れると、無関係な配布ランタイムが増えます。

決定: デスクトップは Qt Quick を維持し、既存の作成ウィンドウを再利用します。プロジェクト所有の独立 SFX 実行ファイルは Windows のシステムフォルダー・タスクダイアログだけを使い、フォント、DPI、サイズ、アクセシビリティはシステムが管理します。ZIP、検証、出力権限、競合、進捗、キャンセル、クリーンアップは既存の Rust コアを使います。これは ADR-001 に対する配布ホストの限定的な例外であり、別のデスクトップフレームワークや新しい独自ウィジェットライブラリーではありません。

コスト: 追加の Windows 実行ファイル、バージョン付きエンベロープ、静的 CRT リンク、Qt を含まない依存関係の監査、ネイティブダイアログホストを保守し、自動テストします。展開された内容を実行することはありません。生成された実行ファイルへの署名は、固定スタブへの署名とは別です。

再評価の条件: インストーラー、ペイロードの自動実行、追加の実行プラットフォーム、独自 SFX インターフェースの要求には、それぞれ別の範囲設定とアーキテクチャ審査が必要です。
