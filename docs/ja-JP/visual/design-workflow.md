# UI の設計と修正のワークフロー

[English](../../visual/design-workflow.md) | [简体中文](../../zh-CN/visual/design-workflow.md) | [繁體中文](../../zh-TW/visual/design-workflow.md) | 日本語 | [한국어](../../ko-KR/visual/design-workflow.md) | [Français](../../fr-FR/visual/design-workflow.md) | [Deutsch](../../de-DE/visual/design-workflow.md) | [Español](../../es-ES/visual/design-workflow.md) | [Português (Brasil)](../../pt-BR/visual/design-workflow.md) | [Русский](../../ru-RU/visual/design-workflow.md)

この手順は UI を作成する前に実施し、実装後に文書を補うためのものとはしません。仕様の入口は [UI 設計標準](../../visual/design-standard.md)です。

1. **目標と環境を定義する。** 機能、実データ、不足している能力を列挙します。プラットフォームと、論理ウィンドウ、アクセシビリティ用文字サイズ、メニュー、独立ウィンドウの寸法範囲を指定します。システム倍率、レビュー倍率、DPR を記録し、HTML プロトタイプではブラウザーのページ倍率も記録します。
2. **最初にパラメーターを定義する。** 寸法、タイポグラフィ、スロット、内側の余白、配置、状態には仕様 JSON を使用します。座標系とコンポーネント固有の密度を記録します。メインウィンドウとメニューの測定基準は独立しており、各独立ウィンドウはウィンドウ登録簿の式を使用します。操作本文の拡大率と共通フッターの寸法は別々に確認します。物理ピクセルは測定証拠を読むときだけ DPR で換算します。
3. **独立した参照を固定する。** 元画像のハッシュと測定座標を保存します。サイズ方針は明示的に改定できますが、チェックに合格させるために元画像や過去の証拠を差し替えてはいけません。追跡可能な改定記録を保持し、受け入れスクリプトが実行時パラメーターをそれ自身と比較するだけにならないようにします。
4. **先に構成を確認する。** ボタン、表、ツリー、メニューの設計では、文字、行高、アイコンの比率と操作状態を同時に確認し、少なくともドロップダウン、コンテキストメニュー、サブメニューを一緒に表示します。同じ操作ウィンドウをメインウィンドウと独立入口からそれぞれ開き、最終的なウィンドウ幅、本文、フッター、コントロールの寸法が等しいことを確認します。HTML プロトタイプは Qt 実装の基礎にする前に、原稿を基準にパラメーターを固定します。
5. **一貫して生成し実装する。** 仕様から HTML 表示契約、共有パラメーター、Qt Theme を生成します。Qt は論理レイアウトと実際の文字サイズを使用します。テーマの色や素材だけを交換しても寸法比較の代わりにはなりません。
6. **測定して修正する。** 同じ論理幅で、タイトルバー、タブ、ツールバー、パンくず、ディレクトリーツリー、表の見出し、ファイル行、プレビュー、下部バー、メニューを領域ごとに確認します。座標、フォント、アイコンの可視範囲、ベースライン、内側の余白、ホバーとフォーカスを確認し、修正後は影響する証拠を再収集します。
7. **拡大率と動作を検証する。** Qt の高 DPR、狭いウィンドウ、アクセシビリティ用文字サイズを確認します。任意の HTML レビューでは、ブラウザー倍率 100%/125% と DPR 1/1.25/2 も確認します。実際にクリックして展開と折りたたみを行い、キーボードでサブメニューに出入りします。無効項目、選択、端の位置、フォーカスの復帰を検証します。Qt の再利用プールにあり表示されないオブジェクトは除外します。
8. **納品して受け入れる。** 影響する仕様、機能の対応付け、生成ファイル、自動チェック、差分記録を更新します。コミットとプッシュ前に関連するローカル検証を完了します。必要に応じて 3 プラットフォームの完全なチェックを実行し、未検証のネイティブ装飾や未実装機能は明示したままにして、架空の状態を描きません。

実際に使用した仕様、パラメーター、倍率、メインウィンドウとメニューの測定、検証済みの操作、残る差分を記録します。固定の手動アンケートは必須ではありません。

<a name="xdzip-window-registration-and-mandatory-checks"></a>

## ウィンドウ登録と必須チェック

独立したすべての QML ウィンドウとインライン Window を[ウィンドウ登録簿](../../../specs/visual/window-registry.json)に登録します。抽象基底クラス、製品の操作ウィンドウ、独立したプロパティウィンドウ、開発プレビューも対象です。未登録の新規ウィンドウ、継承の変更、固定した式と異なる寸法、文字サイズや高さを上書きする確認ウィンドウ、スクロール可能な本文の欠落は `check-window-contracts.py --self-test` を失敗させます。チェックは手動管理の固定リストではなくソースからウィンドウを検出します。システム標準の選択画面の例外は登録簿に記載し、アプリケーションウィンドウの登録を回避するものではありません。

終了と再起動の確認には OperationConfirmationWindow を使用します。パラメーターは layout-scale.json の operation.confirmation から取得し、旧既定幅 612 や文字サイズで飛び変わる固定高さを使用しません。短い文言は内容に合わせてサイズを決め、本文が長い場合や画面が小さい場合はスクロールし、フッターは常に操作可能にします。フッターボタンの外観は引き続き共通コンポーネントが決めます。長い翻訳はボタン内で折り返してよく、操作ボタンは一列に保ちます。

静的な登録簿チェックは日常 CI で実行し、Qt 実行時の形状と操作のチェックはローカルまたは必要時の 3 プラットフォーム Qt ワークフローで実行します。Qt チェックは終了、停止、再起動、中国語と英語、ライトとダーク、100/125/150% の文字サイズ、小画面での本文スクロールを対象とします。必要時のワークフローは DPR 1/1.25/2 を対象とします。実際の HTML レイアウトは必要に応じてローカルで別途測定できますが、日常 CI の必須条件ではなく、未実施の Qt またはネイティブの視覚チェックの代わりにもなりません。静的チェックには、過去の過大寸法、漏れたウィンドウ、固定高さ、スクロール欠落に対する変異検証を含みます。

ウィンドウ変更では機能と実際に実施した視覚チェックを別々に記録し、可能な場合はスクリーンショットと寸法を収集します。実際の終了タスクが通過しても終了ウィンドウの外観が受け入れられたことにはなりません。ソース登録簿が完全でも、全プラットフォームの視覚検証が通過したことにはなりません。ネイティブメニュー、システム装飾、利用できないデバイスについて明確な制限を残し、保守担当者に固定の手動受け入れフォームを繰り返し記入させる必要はありません。
