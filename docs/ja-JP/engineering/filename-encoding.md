## 解決と識別

デコードは Qt に依存しない Rust の形式層で行います。ホストのシステムコードページ、UI 言語、ソースシステムの推測、ファイル内容、ネットワークサービスは使用しません。ZIP の raw_name は名前フィールドの元のバイトを保持します。TAR は PAX/GNU が選んだ生の名前から既存規則に従って先頭の `./` を除いて保持します。物理 EntryId は名前と独立しています。decoded_name はトランスコードまたは追加のエンコーディング宣言を要する UTF-8 表記を保存し、name_encoding は解決元を保持し、name_bytes は固定された実効名を提供します。display_name はエスケープ表示専用であり、出力パスにはできません。

ZIP は次の順序で名前を解決します。

1. UTF-8 フラグが設定されている場合、元のフィールドに有効な UTF-8 を要求し、破損した宣言を旧来のエンコーディングで修復しません。
2. それ以外では Info-ZIP Unicode Path 0x7075 を読み、バージョン 1 で元名の CRC32 が一致し、完全で有効な UTF-8 を受け入れます。未知のバージョンと CRC 不一致は仕様に従って無視します。一致しているが無効な UTF-8、重複する有効フィールド、破損したフィールド構造は要確認としてマークします。
3. 使用可能な拡張がなく、未宣言グループの名前がすべて有効な UTF-8 なら、未マーク UTF-8 を受け入れます。
4. それ以外では未宣言の非 ASCII 名にアーカイブ全体の統計的検出を適用し、GBK/GB18030、Big5、Shift-JIS、EUC-JP、韓国語、その他の検出器対応文字集合を対象とします。ZIP の西欧系の既定推測は歴史的既定値 CP437 にフォールバックします。GBK 検出時は互換性のある厳格な GB18030 デコーダーを使います。

通常の TAR ヘッダー、GNU 長名、明示的に hdrcharset=BINARY とされた PAX パスには同じ未宣言名の戦略を使います。通常の PAX パスは有効な UTF-8 を要求し、破損した宣言を検出で隠してはいけません。UTF-8 と BINARY 以外の明示的な hdrcharset は非対応です。TAR は ZIP の CP437 既定値を引き継ぎません。TAR.GZ は TAR と同じ名前解決を使います。

規則は [ZIP APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT)、[POSIX pax](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/pax.html)、[WHATWG Encoding Standard](https://encoding.spec.whatwg.org/) に従います。ローカルヘッダーには Unicode Path フィールドがなくても構いませんが、有効な値が提供された場合は固定された実効名と一致しなければなりません。ペイロードの検査では引き続き生の名前、ローカルと中央のヘッダー、CRC、サイズ、パスワード認証、ストリームの終了を検証します。

CAB は元の名前バイトと UTF-8 属性を保持します。明示された UTF-8 は厳格に検証し、その他の名前にはシステムコードページを使わずアーカイブ全体の上限付き検出を再利用します。CAB のバックスラッシュは形式上のディレクトリー区切りですが、完全にデコードした後だけスラッシュに正規化し、Shift-JIS のマルチバイト後続バイト 0x5C を分断しないようにします。生バイトは変更せず、実効パスには同じ安全性と衝突の検査を行います。Joliet 以外の ISO 名は生バイトを保持して同じ上限付き解決を使い、Rock Ridge 名のホスト OEM 変換を避けます。Joliet/UDF はプロセッサーが提供する Unicode 名を使って厳格に検証し、情報を失った置換文字を元の名前とは扱いません。

<a name="xdzip-detection-boundaries-and-resources"></a>

## 検出の境界とリソース

検出器は完全な未宣言の非 UTF-8 名を最大 1 MiB 読み、切れたマルチバイト列が名前をまたいで結合しないようレコードを改行で区切ります。明示的な Unicode 宣言と無効な拡張はサンプルにしません。サンプルに非 UTF-8 名が含まれる場合は未宣言名にアーカイブ全体の結果を一貫して適用し、GBK 内で偶然有効な UTF-8 断片によって一つのディレクトリーが二つの名前に分かれることを防ぎます。個々の名前の厳格なデコードが失敗した場合だけ、有効な UTF-8 またはその名前の局所的な結果を試せます。ISO-2022-JP の推測は無効で、名前内のエスケープ状態は解釈しません。厳格なデコードは置換文字を挿入せず、BOM を除去せず、スラッシュの変換、Unicode 正規化、パスの修復を行いません。

生の名前は合計最大 16 MiB です。生またはデコード済みの名前は一つ最大 4,096 バイト、デコード名とエスケープ表示の合計は最大 16 MiB です。ZIP Unicode 拡張の項目ごとと累積の割り当てはアーカイブ終了後ではなく走査中に検査します。解決、検出、項目ごとの変換ではキャンセルを確認します。ZIP ペイロードは実効名の検証表をさらに最大 16 MiB 保持し、後のデコードで固定名を変更できません。

統計的検出では任意の短い名前や混在する旧来のエンコーディングを一意に復元できず、他のソフトウェアが既に有効な Unicode として保存した文字化けも特定できません。明示的に宣言された Unicode と旧来のエンコーディングは一つのアーカイブ内で共存できますが、複数の未宣言エンコーディングの検出はベストエフォートです。現在、手動のエンコーディング選択はありません。厳格にデコードできない名前、宣言が破損した名前、異常なパスはエスケープ表示して要確認とし、展開、一時オープン、エクスポート、変更の権限を与えません。すべての過去のアーカイブを正しく識別する保証はありません。未解決名があると実際にどのディレクトリーに属するか不明な場合があるため、成功結果から項目を黙って漏らさないようディレクトリー展開による抽出を拒否します。明示的に選択された解決済みの通常ファイルは引き続き個別に展開できます。

<a name="xdzip-end-to-end-use-and-saving"></a>

## 一貫した利用と保存

ディレクトリーツリー、直下の子の索引、再帰検索、ディレクトリー選択の展開、事前確認、展開、一時オープン、外部エクスポート、アーカイブ変更は同じ実効名を使います。デコード後も PortablePath、Unicode NFD と大文字小文字の別名、重複名、出力許可の検査を行います。Shift-JIS マルチバイトの後続バイト 0x5C はディレクトリー区切りではありません。CAB と LHA の形式上の区切りを除き、実際にデコードされたバックスラッシュは引き続き拒否します。

計画後、通常の ZIP、TAR、TAR.GZ での追加と移動では、旧来のエンコーディング、Unicode 拡張、未マーク UTF-8 の名前を UTF-8 として再宣言し、論理的な移動計画内の元の位置とスキップの意味を保持します。ZIP は圧縮ペイロードを保持し、TAR は明示的な UTF-8 PAX パスを使います。書き込み後に再走査して各名前と内容を検証し、既存の同一ボリューム上の置換を実行します。TAR の書き換えで PAX パスの BINARY 宣言を除く際、他の非 UTF-8 PAX テキストの解釈が変わる場合は明示的に失敗し元のアーカイブを保持します。暗号化および分割アーカイブでも読み取りと展開には同じ名前を使い、追加と移動の制限は変わりません。

<a name="xdzip-reproducible-acceptance"></a>

## 再現可能な受け入れ

プロジェクト所有の生バイトテストデータと、Python 標準ライブラリーで独立してエンコードしたアーカイブを使い、未マーク UTF-8、GBK、4 バイト GB18030、Big5、0x5C を含む Shift-JIS、韓国語、ロシア語、ZIP CP437、Unicode Path を網羅します。完全な名前、元のバイト、ディレクトリー、検索、選択、事前確認、実際の出力バイト、一時オープン、エクスポート、通常アーカイブへの追加と移動、AES、分割ボリュームを検証します。破損した宣言、拡張の優先順位、パスの拒否、Unicode と大小文字の衝突、キャンセル、予算も確認します。

scripts/check-filename-encoding.py は Python が生成した ZIP/TAR/TAR.GZ を実際のサービスプローブで展開します。Python も Rust が書き換えたアーカイブを独立して読み、UTF-8 フラグ/PAX、名前、内容を検査します。テストデータはソースの定数だけから作り、ユーザーのアーカイブは使いません。実際の結果と残る手動受け入れは issue と build/CI 成果物に記録し、この契約内に合格状態として記載しません。

LHA は元の dirname/filename のフィールド境界と dirname の生の `0xff` 区切りを保持します。共通の上限付き検出は完全な各フィールドを個別にサンプリングします。各成分を厳格にデコードしてからデコードされたバックスラッシュを解釈し `/` を組み立てます。元のバイト境界によって、フィールドをまたぐマルチバイトの借用を防ぎます。ディレクトリーの展開と出力は同じ実効名を使います。[LHA 契約](lha-containers.md)を参照してください。
