# LHA ワイヤー形式とアルゴリズムの契約

[English](../../engineering/lha-containers.md) | [简体中文](../../zh-CN/engineering/lha-containers.md) | [繁體中文](../../zh-TW/engineering/lha-containers.md) | 日本語 | [한국어](../../ko-KR/engineering/lha-containers.md) | [Français](../../fr-FR/engineering/lha-containers.md) | [Deutsch](../../de-DE/engineering/lha-containers.md) | [Español](../../es-ES/engineering/lha-containers.md) | [Português (Brasil)](../../pt-BR/engineering/lha-containers.md)

LHA/LZH と歴史的な LArc は、メンバーを順に格納するコンテナーの一群です。ファイル拡張子、認識可能なメソッド文字列、または Store メンバーの成功は、別のメソッドのデコード対応を示しません。`xdzip-compression` の低水準プリミティブは、許容された圧縮範囲と独立に検証された展開後サイズを受け取り、ファイルシステム、プロセス、ファイル名、公開に関する権限を持ちません。製品への登録とコンテナーの受け入れには、以下の別個の検証が必要です。

## 出典と参照の境界

Masaru Oki の 1992 年 3 月 2 日の原著 [LHa for Unix ヘッダー文書](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/header.doc.md)は、吉崎氏の `lhx.doc` を引用し、レベル 0–2、メソッドマーカー、OS 識別子、拡張の分類を定義しています。固定された Git blob は `b09a87759e4cee9c99f69616b2e975493253d412`、リポジトリのコミットは `16619b066b189ef289bb8b07b37d1c38d550da99` です。

この文書は圧縮ビットストリームの完全な仕様ではありません。同じ原著者のソースを限定的に観察し、フィールド幅と歴史的な動作を補います。静的木のアルファベットについて [huf.c](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/huf.c)、blob `15f90e1bb3079f6c11d852b9cb8a86fc7f240c35`、空白で埋めた既定履歴と別個の壊れたアーカイブ修復モードについて [slide.c](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/slide.c)、blob `5dd5f9863993a6f4eda7398ecf4fe6f4ad7a711b`、LArc のフィールドと絶対参照の原点について [larc.c](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/larc.c)、blob `c6f8f1ca111705a11dd744ac01e458e95377366d`、および [lha_macro.h](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/lha_macro.h)、blob `5c207426d0450468857187f5d74a675d695e3cc2` を参照しています。厳密なクリーンルーム方式とは主張しません。Rust の状態、制限付きの共有プレフィックスデコード、エラー処理とリソース受け入れは独立して表現し、参照ソースを製品へコピー、翻訳、コンパイルしません。

[jLHA](https://github.com/umjammer/jlha/tree/0a6348d96e9bbb1ac5ee8b3f6ff1c2c75b17d0d9) 0.0.11、[Lhasa](https://github.com/fragglet/lhasa/releases/tag/v0.6.0) 0.6.0、7-Zip 26.06 は独立したテスト参照です。固定された識別情報と公開 API のハーネスは[自前のフィクスチャ](../../../tests/fixtures/lha/README.md)に記録しています。Java のアルゴリズムソースは製品コードとして使用しません。参照のメソッド対応範囲や既定履歴の相違は、バイト比較の成功とは別に扱います。参照ライブラリとツールは `build/toolchain/` に置き、製品の依存関係には含めません。

## コンテナーのフレーミング要件

`xdzip-codec-lha::inspect` は以下のレベル 0/1/2/3 のフレーミングを実装します。`LhaCodec` は物理項目を公開し、`Reader` は Qt と独立して制限付きのデータをデコードします。ランタイム、CLI、Qt は `LZH` 形式を公開し、`.lha` と `.lzh` をオープンと関連付けの候補とします。拡張子や形式群のマーカーは候補にすぎず、公開前に完全なメタデータの検証を通す必要があります。強い証拠のある有効な TAR、ZIP、光ディスク、SFX の検出は優先されます。生の TAR マーカーだけの場合は完全な LHA 検証によって判別できます。作成はレベル 2 ヘッダーと LH5 のレベル 1/6/9 を受け入れ、条件を満たすレベル 2 アーカイブは書き換え可能です。メタデータ読み取りは 64 MiB、物理レコードは 100,000、連鎖拡張はメンバーあたり 256、レベル 1 およびレベル 3 ヘッダーの累積は 1 MiB を上限とします。呼び出し元の名前と項目の制限も適用されます。レベル 0 の CRC 省略は明示的に表現します。不明な OS 固有ベース末尾、未対応の拡張種類、ヘッダーレベルを通常の対応データとして解釈しません。

各物理メンバーはヘッダーと正確な圧縮範囲で構成されます。ゼロの終端子でアーカイブが終わり、末尾データ、終端の欠落、不可能な範囲、後続メンバーの不正によって部分的なインデックスを公開することはできません。レベル 0 と 1 は 1 バイトのベースヘッダー合計と DOS 形式のタイムスタンプを保持します。レベル 1 のスキップサイズには連鎖拡張ヘッダーが含まれるため、データ範囲の受け入れ前に正確な合計を差し引く必要があります。レベル 2 のリトルエンディアンの総ヘッダー長は全拡張を制限し、Unix 秒を使用します。計算、割り当て、シークの前にフィールドと拡張リンクを確認します。宣言された拡張ヘッダー CRC は自身の CRC フィールドをゼロにして計算し、データ CRC とは別に扱います。ヘッダー拡張とコメントは隣接ファイル、権限、実行への権限を与えません。

レベル 3 はオフセット 0 の固定リトルエンディアンサイズフィールド幅 4、32 バイトのベース、オフセット 24 の総ヘッダーサイズ、オフセット 28 の最初の 32 ビット拡張サイズを使います。各拡張は 32 ビットの次サイズフィールドで終わります。圧縮後／元のサイズは 32 ビット、時刻は Unix 秒のままであり、ヘッダーが広いからといって 64 ビットのファイルサイズを自動的に許可しません。総ヘッダー長は割り当て前に 1 MiB 以下とし、拡張は最大 256 です。不正な最小サイズ、オーバーフローまたはヘッダー外のリンク、余分な末尾は失敗します。フィールドは原著者の[レベル 3 ヘッダーコメント](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/header.c)、Git blob `df8ae5e3f9dece45325d499cf63c34fc2bb0ec99` に基づきます。同 README は歴史的なレベル 3 仕様が固定されていなかったと注意しています。受け入れる共通拡張は jLHA と Lhasa により別途実証されており、歴史的な全拡張の対応は主張しません。

レベル 2 ヘッダーがちょうど 256 バイト境界に揃うと先頭がゼロになり、終端子と衝突します。原著者が文書化した回避策では、その場合に限りゼロのパディングをちょうど 1 バイト許可し、総サイズとヘッダー CRC に含めます。他のヘッダー末尾やゼロ以外のパディングは拒否します。参照ツールの旧来のパス制限に合わせて名前を切り詰めることなく、独立してエンコードした 222 バイトのファイル名で検証しています。

アーカイブ名の解決は出力認可と独立して行います。物理順序、重複、元の名前を保持します。複数バイト文字の後続バイトがディレクトリを作り出さないよう、バックスラッシュを区切りとして解釈する前に旧来のエンコードを解決します。拡張ファイル名とディレクトリ名フィールドには明示的な一意性と結合の規則があり、曖昧な重複宣言は都合のよい表記を選ばず失敗します。ディレクトリと特殊／リンクレコードを通常ファイルとして扱ってはなりません。元の Unix モードはメタデータであり、権限を復元しません。既存のソース固定、移植可能なパスの事前検査、選択項目の識別、プライベート準備領域と最終公開は引き続きホストの責任です。

元の名前はディレクトリ名のバイト、その `0xff` 区切り、ファイル名のバイトと両フィールドの正確な境界を保持します。共有の制限付き旧来エンコード検出器で完全なディレクトリ構成要素とファイル名を独立にサンプリングします。区切りバイトが検出を汚染したり、フィールドをまたいで複数バイト文字を完成させたりすることはできません。各フィールドを厳密にデコードしてから、実際にデコードされたバックスラッシュを正規化し、`/` 区切りで結合します。各構成要素と最終名に不審なパスの検査を適用します。元の名前、有効名、エスケープされた表示は共通の制限とキャンセルに従います。同じ固定された有効名をディレクトリ展開、選択展開、プレビュー、エクスポートに使用します。不明なメソッド、デコード不能または不審な名前、リンク、特殊種類、矛盾するディレクトリ宣言は警告付きで表示したままにし、データを出力できません。Unix モードは権限復元を許可しません。

製品は Store（`-lh0-`、`-lz4-`）、LH1–LH7、LZS、LZ5 を受け入れます。PMA メソッドは製品の受け入れ範囲外です。項目メソッド ID は LZH に限定され、ZIP のメソッド番号ではありません。検査は `format_declared_checks` を使用し、存在するヘッダー／データ CRC は通る必要がありますが、CRC のない古いレベル 0 メンバーは構造、サイズ、読み取り可能性だけを提供します。LH2 の有限バリアントの受け入れにはデータ CRC が必要です。パスワード、ボリューム、修復プロファイルは未対応です。ゼロ 1 バイトは空のアーカイブを表し、後続レコードの不正から成功した部分リストを作れません。オープン時は名前とフレーミングを走査し、検査または展開時に実際に内容をデコードして宣言された検査を検証します。

Store マーカー `-lh0-` と `-lz4-` は圧縮後と展開後のサイズが等しいことを要求します。歴史的な `-lz4-` は現代の LZ4 と関係ありません。`-lhd-` はディレクトリを宣言します。LH1–LH3、PMarc、拡張ヘッダー、パスワード、ボリュームはそれぞれ独自の検証済みプロファイルと独立サンプルを必要とします。拡張子や汎用 Huffman/LZW 実装だけでこれらの機能が自動的に提供されるわけではありません。不明なメソッドはデコード済みの通常ファイルと区別できる状態を維持します。フレーミングの検証はデータ内容を検証しません。

## 静的 LH4–LH7 プリミティブ

`LzhReader` は 1–65535 個のリテラル／一致コマンドからなる MSB 優先ブロックを実装します。LH4 と LH5 は位置アルファベット 14 と 4 ビットの木カウント、LH6 は 16 と 5 ビット、LH7 は 17 と 5 ビットを使用します。辞書のアドレスビットはそれぞれ 12、13、15、16 です。これは辞書容量と、より広い符号化位置アルファベットを区別するもので、辞書外の距離は失敗します。

19 シンボルのコード長木が 510 シンボルのリテラル／長さ木を記述します。それぞれのカウントフィールドは 5 ビットと 9 ビットです。短い木の長さは 3 ビットと制限付き単項拡張を使用し、長さ木は規定された三つのゼロ連続をサポートします。カウントゼロはシンボルビットを消費せず、明示的に制限された単一シンボルを選択します。通常の正準木は完全、非空、過剰割り当てなし、深さ最大 16 ビットでなければなりません。シンボル 0–255 はリテラル、256–509 は長さ 3–256 を意味します。位置ゼロは距離 1、それ以外は 2 のべき乗の先頭値と下位ビットを使います。重複コピーはブロック間で履歴を維持します。

初期辞書は通常の原版 LHa の動作に従い空白を含みます。ゼロ埋めによる壊れたアーカイブ修復へのフォールバックは試みません。既知の展開後サイズはコマンドとブロックの境界で正確に終わり、リーダーは許容されたバイト範囲全体を消費する必要があります。最終バイトの未使用ビットは無視しますが、余分な丸ごとのバイト、切り詰め、コマンド数ゼロ、出力超過は失敗します。空の展開後メンバーには空の圧縮範囲が必要です。CRC-16 の検証はコンテナーの責任です。

## LH1–LH3 プリミティブと LH2 バリアント

`LhDynamicReader` は LH1 の 314 シンボル適応モデル、4096 バイト辞書、長さ 3–60、距離から 1 を引いた値の固定正準上位ビットを実装し、下位 6 ビットは明示的です。LH2 は初期 286 シンボル、より長い長さにシンボル 285 と 8 ビット拡張、8192 バイト辞書、出力が 64 バイト境界を越えるたびに拡張する位置アルファベットを使います。範囲外の拡張長は失敗します。どちらも空白の履歴と正確なサイズ／範囲を保持します。`LzhReader` はさらに LH3 のブロックごとの 286 シンボル木、送信または固定の 128 シンボル位置木、三つの長さの単一シンボルセンチネル、同じ 8 ビット長拡張を受け入れます。ゼロブロック、不正なセンチネル、不完全または過剰割り当ての木は失敗します。

一般的な兄弟性の更新は安定したノード識別情報、明示的な順位、部分木の交換を使って独立に表現します。再構築は正の葉の重みを上方向に半減し、現在の順位を保持して二つのソート済みキューをマージします。再構築された根は、成長前の根の識別情報とは独立に完了したマージから取得します。実際の比較、交換、再構築、初期化を作業量に計上します。理論的根拠は [Vitter の FGK 分析](https://www.ittc.ku.edu/~jsv/Papers/Vit87.jacm.pdf)第 2 節です。ワイヤー固有のアルファベット、固定位置、しきい値の事実は固定された [dhuf.c](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/dhuf.c)、Git blob `bcb08bdccf6c6396938e3b2d9b6b032a991aa26e`、および [shuf.c](https://github.com/jca02266/lha/blob/16619b066b189ef289bb8b07b37d1c38d550da99/src/shuf.c)、blob `2c18ed6a909cfa7fd1d591af1e7f0bd90e269fd7` で観察しています。これは上記のソース観察の開示を拡張するもので、実装構造を翻訳していません。

原版 Unix LH2 は初期単一位置の重みを変えず、位置更新を別に数えます。jLHA は汎用モデルで単一位置を更新します。同じ `-lh2-` マーカーの下で互換性のない実際のビットストリームになります。低水準 API は明示的な `Lh2Variant` 選択を提供し、汎用メソッド 2 コンストラクターは jLHA のカウント規則を使います。コンテナーは LH2 に宣言された CRC を要求し、二つの有限バリアントを非出力シンクへ完全に検証します。不正な構造や CRC によりバリアントを除外できますが、ソース、キャンセル、クォータ、ホストの失敗は直ちに終了します。すべての検証で実際の入力、展開、補助作業を計上します。成功したバリアントは展開後サイズと SHA-256 ダイジェストが同じでなければならず、異なる場合は曖昧で未対応です。一つだけが有効な場合または結果が同一の場合は出力用に再度デコードし、選択したダイジェストと CRC に一致させます。これらのハッシュは検証と提供のバイトを結び付けるもので、アーカイブの真正性を示しません。候補バイトを公開したり、出力の作業量として再利用したりしません。

原版 C ファイルは変更せずハッシュを固定し、自前の制限付きホストハーネスとともに `build/toolchain/` でテスト用オラクルとしてのみコンパイルします。負荷生成はその参照ビルド内で原版のテスト専用エンコーダー／成長状態を呼び出し、製品に移植しません。距離を変えたサンプルは各バリアントの文字と位置の両方の再スケーリングしきい値を越えます。自前の LH2 ストリーム一つを、原版の単一シンボル規則を用いた公開汎用木 API で生成し、原著者のデコーダーで全体を独立に読み取ります。原版 Unix が jLHA の長い／空白プロファイルに失敗することなど、参照の相違は修復したり成功に数えたりせず、そのまま記録します。

## コンテナーの作成と公開

作成は `.lzh` または `.lha` にメソッド `lh5`、レベル 1/6/9、レベル 2 ヘッダーを使用し、デスクトップの既定拡張子は `.lzh` です。ホストの作成メソッド ID は 259 で、LZH 項目に限定されたメソッド ID 5 とは異なります。作成では Store、パスワード、ソリッドグループ、ボリュームをサポートしません。入力は固定した最大 100,000 レコード、名前 16 MiB、実読み取り 24 GiB で、ヘッダー合計は最大 64 MiB です。各メンバーの元と圧縮後の長さはそれぞれ符号なし 32 ビットに収まり、Unix 更新秒も切り詰めず符号なし 32 ビットに収まる必要があります。出力は 24 GiB に制限され、通常ファイルはメンバーをまたぐ累積低水準エンコーダー作業台帳を保持します。CRC 処理は受け入れた実ソースバイトを一度だけ対象とし、入力とヘッダーの制限内に収まります。読み取り予算を完全に使い切ると、最後の EOF 確認前に保守的に失敗する場合があります。

移植可能な通常ファイルとディレクトリだけを受け入れます。ディレクトリは `-lhd-`、サイズゼロ、データ CRC ゼロを使い、通常ファイルは小さい入力や圧縮できない入力でサイズが増えても LH5 を使います。名前は別々のファイル名拡張と `0xff` 区切りのディレクトリ名拡張に UTF-8 で格納します。共通ヘッダー CRC とファイルごとの CRC-16 は必ず出力します。ちょうど境界に揃ったレベル 2 ヘッダーは必要な 1 バイトのパディングを保持します。検証中に検証済みディレクトリを読み取っても、バイトを出力したりディレクトリや権限への権限を与えたりせず成功します。

ここでの UTF-8 は宣言されない命名規約であり、普遍的な Unicode フラグではありません。自前の jLHA 公開 API ハーネスは明示的に UTF-8 を選択し、データとは独立に完全なパスを確認します。旧来の Windows リーダーは代わりに OEM コードページを使用し、全バイトと CRC が通っても異なる名前を表示する場合があります。調査した原版 7-Zip の [LZH 名前投影](https://github.com/ip7z/7zip/blob/main/CPP/7zip/Archive/LzhHandler.cpp)、Git blob `1b6e3b9d9905abe28b53e39b1267465fe2fc7f03` は `CP_OEMCP` を選択します。このソース観察は参照の制限を説明するもので、実装を製品に追加しません。ファイル名の普遍的な相互運用性は主張しません。

コーデックは固定されたソースインデックスと空のプライベートなシーク可能準備出力を受け取ります。まず全レコードの境界を検証し、内容と CRC をストリーミングし、低水準エンコーダーを終了し、圧縮サイズと CRC を修正してから次のメンバーのために順次終端位置を復元します。ランダム書き込み未対応やソース／出力／制限／キャンセルの失敗は、成功を示す終端子を出さず中止します。最終パスやコミット権限はコーデックへ渡しません。ホスト検証は LHA の固定された有効名を入力名と比較し、他のコンテナーは元の生名比較を維持します。既存の固定ソース再確認と原子的公開の前に全内容を実際にデコードします。検証失敗、ソース変更、キャンセルは既存の対象を保持し、プライベート準備領域を整理します。

`scripts/check-lzh-creation.py` は生成されたレベル 2 フィールド、境界、UTF-8 名、タイムスタンプ、両 CRC を独立に解析・確認し、固定された jLHA、Lhasa、7-Zip を通して複数メンバーの全内容を比較します。ディレクトリ／名前とデータの結果は別々に記録します。ランタイム、CLI、Qt による作成、再オープン、検査、展開はそれぞれ別に自動化されており、低水準ライターの往復はそれらの入口の代わりにはなりません。

既存のレベル 2 LHA/LZH アーカイブは、全メンバーに宣言されたコンテンツ CRC があり、名前、レコード、データの受け入れを通る場合に編集可能です。保持するデータは圧縮済みのままコピーします。パス変更時は元のメソッド、サイズ、タイムスタンプ、属性、許容された名前以外の拡張を保持し、UTF-8 名拡張を再生成して共通ヘッダー CRC を更新します。新しいファイルは LH5 ライターを使います。レベル 0、1、3 のヘッダーは読み取りプロファイルの範囲で閲覧可能です。[アーカイブ変更契約](archive-transfers.md)を参照してください。

## 低水準 LH5 ライター

`LzhWriter` は製品の作成受け入れとは別の制限付き低水準エンコーダーです。32768 バイトの入力ブロックをまたいで 8192 バイトの履歴を保持し、共有の 4 バイトハッシュチェーンを通して長さ 4–256 の実際の一致を出力します。レベル 1/6/9 はそれぞれ 1/16/64 候補を探索し、距離は一致探索器のより広い容量ではなく LH5 辞書に制限します。完全な正準木を出力します。C シンボル 0/1 は長さ 8、残り 508 は長さ 9、使用する二つの長さシンボルは各長さ 1、位置シンボル 0/1 は長さ 3、残り 12 は長さ 4 です。この意図的に制限した固定木方式は最適なエントロピー符号化や Store へのフォールバックを主張しません。コマンド数は実数で、中間ブロックはバイト境界に揃えず、最後の部分バイトだけをゼロ埋めします。空入力は圧縮バイトを出力しません。

実際のハッシュチェーン、制限された入力／履歴、最大 32768 個の 4 バイトコマンド、出力バッファー、制御状態を含め、受け入れるメモリは 1 MiB です。実際のハッシュ初期化、シード／検索、候補比較、コピー、ビット、出力試行は累積 96 GiB の作業台帳を消費し、入力と圧縮バイトはそれぞれ 24 GiB を上限とします。コールバックは最大 8192 作業単位をカバーし、書き込みは最大 8192 入力バイトを受け付けます。`finish_with_work()` はメンバー間で残りの台帳を保持します。短い書き込みと型のない中断はバイトを重複させず再試行します。型付き中断、キャンセル、出力、リソースの失敗はインスタンスを終了します。出力先パスや公開権限は公開しません。最終でない `flush()` は連続した一つのビットストリームを維持し、成功には `finish()` が必要です。

明示的に呼び出す `scripts/check-lzh-writer.py` は、独立して構築したテスト専用レベル 0 フレーミングとともに自前の低水準ライター出力を書き出し、7-Zip の CRC テストを含め固定された jLHA、Lhasa、7-Zip ですべてのバイトを比較します。空、1 バイト、全バイト、空白、決定的な乱数、長い繰り返し、ちょうどウィンドウ長の繰り返しで各レベルをカバーします。これは低水準の相互運用性を示します。製品コンテナーの書き込み、名前メタデータ、ホストの原子的公開には別のテストが必要です。

## LArc プリミティブ

`LarcReader` は LZS または LZ5 を別々に選択します。LZS は空白で埋めた 2048 バイトのリング、初期書き込み位置 2031、MSB 優先のリテラルフラグ、8 ビットリテラルまたは 11 ビット絶対参照の後に 2 を引いた 4 ビット長を使います。一致長は 2–17 です。LZ5 は 4096 バイトのリング、初期書き込み位置 4078、1 バイトあたり LSB 優先の 8 フラグ、バイト境界に揃ったリテラルまたは長さ 3–18 の 2 バイト絶対参照を使います。絶対インデックスは相対距離ではなく、どちらのメソッドも Stac LZS フレーミングを再利用しません。

LZ5 の初期リングは各バイトの 13 回の繰り返し、昇順バイト、降順バイト、128 個のゼロ、110 個の空白を含みます。残る未書き込みの 18 スロットには互換性のない歴史的な既定値があり、実際に書き込まれる前に読み取ろうとすると拒否します。これにより修復バリアントを選ばず受け入れ結果を一意にします。ソースと送り先の重複やリングの折り返しは通常のバイト単位の意味を維持します。最後のフラグまたはバイト未満の埋めは、正確に最後に消費したバイト内でのみ無視し、余分な完全な 1 バイトは拒否します。既知の出力サイズと CRC の検査はコンテナーレベルで引き続き必須です。

## リソース、失敗と受け入れ

すべての低水準リーダーは圧縮後サイズと展開後サイズをそれぞれ 24 GiB、累積作業を 96 GiB 単位に制限します。LH4–LH7 は辞書サイズと 64 KiB、LArc は辞書サイズと 32 KiB を受け入れ、履歴初期化フラグ、入力バッファー、制御状態を含みます。呼び出し元のより小さい制限も適用されます。ビットフィールド、木の構築、繰り返し展開、辞書初期化、出力は使用前に作業量を消費します。`work_remaining()` によりコンテナーはメンバーや失敗をまたいで一つの実作業台帳を維持できます。メモリとフィールド数は割り当て前に受け入れを判断し、読み取りは最大 8192 バイトを返します。

LH3 は辞書と 64 KiB、動的 LH1/LH2 は保守的に 192 KiB を受け入れます。データインスタンスはメンバー、繰り返し要求、LH2 検証を通して、実入力と展開作業それぞれ 24 GiB の厳しい台帳と、アルゴリズム作業 96 GiB の台帳を共有します。メタデータの再走査は入力台帳に含まれます。LH2 はさらに最終パディングを含む実際の SHA 圧縮ブロックのバイトを最大 24 GiB 受け入れ、補助作業の受け入れを通じて報告します。破棄された候補は `charge_skipped` によって展開作業を消費します。最終提供は通常の書き込みを使い、前払いの作業量は得ません。データの前にソースと走査のスナップショットを比較し、最終エラーが発生したデータインスタンスは以後使用不能になります。

協調的なコールバックは新しいソース読み取りがなくても制限された作業をカバーします。型のない `Interrupted` I/O のみ再試行し、型付き中断はエラーオブジェクトを保持して終了します。ソース、作業量、キャンセル、不正データ、出力先の失敗は、フォールバックや部分更新された状態の再利用を許可しません。呼び出し元は EOF まで読み切り、宣言されたデータ CRC を検証し、成功まで出力を非公開に保持する必要があります。CRC-16 は偶発的な破損を検出するもので、真正性やパスワード検証には使えません。共有の反転多項式は `0xa001`、初期値はゼロ、最終 xor はありません。

[受け入れ要件](../../../developers/qa/acceptance.md)の `FORMAT-LHA` は低水準の相互運用性、コンテナー検証、実際のランタイム／CLI／Qt 統合を分けています。プリミティブのテストは製品入口、書き込み、パスワード、ボリューム、他のプラットフォーム、リリース承認を証明しません。参照結果と作業パッケージの進捗は issue、生成された証拠は `build/` または CI に記録します。
