# UU、UUE、XXE のテキスト封装

[English](../../engineering/text-envelopes.md) | [简体中文](../../zh-CN/engineering/text-envelopes.md) | [繁體中文](../../zh-TW/engineering/text-envelopes.md) | 日本語 | [한국어](../../ko-KR/engineering/text-envelopes.md) | [Français](../../fr-FR/engineering/text-envelopes.md) | [Deutsch](../../de-DE/engineering/text-envelopes.md) | [Español](../../es-ES/engineering/text-envelopes.md) | [Português (Brasil)](../../pt-BR/engineering/text-envelopes.md) | [Русский](../../ru-RU/engineering/text-envelopes.md)

従来の UU フィールドとビット順序は [NetBSD uuencode(5)](https://man.netbsd.org/uuencode.5) に従います。Base64 モードは [uuencode(1)](https://man.netbsd.org/uuencode.1) と [GNU Sharutils](https://www.gnu.org/software/sharutils/manual/sharutils.html) に記載されています。XX の文字集合は `+-0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz` で、[UUDeview](https://github.com/hannob/uudeview) の公開エンコーダーと照合しています。Rust リーダーはこれらのフィールドとビット規則から独立して記述されています。参照 C 実装はテストツールのみであり、ランタイム依存関係にはなりません。

<a name="xdzip-admitted-profiles-and-boundaries"></a>

## 受け入れるプロファイルと境界

`begin`、空白 1 つ、1～4 桁の 8 進モード、空白 1 つ、空でない生のファイル名を受け入れます。ヘッダーのモードは構文だけを検証し、復元しません。UU と XX は同じヘッダーを使用し、空メンバーのゼロカウント行を含む完全に有効なカウント付き本文行から実際の文字集合を識別します。各行の最初の 6 ビット値はデコード後の 0–63 バイトを宣言し、行の文字数は正確に `1 + 4 * ceil(count / 3)` でなければなりません。UU はゼロとして空白とバッククォートを受け入れます。上位ビットから先に、4 つの 6 ビット値を 3 バイトにデコードし、最後の組の未使用バイトを破棄します。過去のパディングビットがゼロであることは要求しません。ゼロカウント行の直後には正確に `end` の行が必要です。短縮または破損した行は修復しません。

`begin-base64` 変種は通常の Base64 行を 4–76 文字、各行 4 の倍数、標準のパディングビットがゼロという条件で受け入れます。パディングされた行で本文が終わり、その後は正確な `====` 終端だけが許されます。空の本文も可能です。裸の Base64、MIME の組み立て、GNU の `begin-encoded` ファイル名拡張、複数部分の修復、yEnc、BinHex は対象外です。`.uu` と `.uue` は UU 候補、`.xxe` は XXE 候補です。候補は実際の文字集合を決定しません。

LF または CRLF と、末尾に改行のない完全な終端を受け入れます。長さを制限した転送テキストはメンバーの前、間、後に置けます。ヘッダーに見えて不正または未対応の行はエラーであり、メンバーを隠すために無視しません。最初のヘッダーは 64 KiB 以内で始まり、転送行とヘッダー行はそれぞれ最大 8192 バイトです。強いコンテナーシグネチャー、光学メディア記述子、有効な TAR ヘッダーはテキスト候補の検出より優先します。拡張子や `begin` という語ではなく、完全な検証によって形式を受け入れます。すべて XX のアーカイブは XXE、通常の UU、Base64、混在メンバーの封装は UU と表示します。重複名を含め、各物理メンバーは直列化順の ID、元の名前、実際のエンコードを保持します。

<a name="xdzip-host-authority-quotas-and-checking"></a>

## ホストの権限、割り当て、検査

バックエンドは、承認されたシーク可能なソースとホスト所有の出力先だけを受け取ります。ヘッダーのファイル名は共有のアーカイブレベルの名前解決、表示用エスケープ、危険パスの検査を通ります。入力を開いたり出力パスの権限を与えたりすることはありません。リーダーは権限の復元、外部ファイルの追跡、コマンドの実行、ディレクトリーの作成を行いません。書き込み、書き換え、暗号化、分割ボリュームの権限も提供しません。エンコードされた本文と終端の範囲は既知の圧縮サイズであり、データサイズは検証済みの行から計算します。

メタデータ検証は共通走査制限の下で封装全体を読みます。通常は実際のソース読み取り 64 MiB、100,000 エントリー、ファイル名ごとに生の 4096 バイト、生と表示名の累積予算 16 MiB です。保持するのは制限されたメンバー範囲であり、デコード内容ではありません。データ配信前に再走査して完全な投影インデックスを不変のホストスナップショットと比較し、その後ロケーターを保持して、以前の各メンバーを再走査せず任意の物理選択を可能にします。メタデータと本文の繰り返し読み取りはプライベートな累積入力上限 24 GiB に計上し、配信バイトには別の 24 GiB 上限があります。ホストのより厳しいタスク、ファイル制限も適用します。読み取り、行処理、出力先への配信、独立したキャンセルトークンを協調的に確認します。型付きソース失敗を保持し、終端的な `Interrupted` 失敗は再試行しません。ソース、構造、割り当て、キャンセル、出力先のいずれかのエラーで開いたリーダーは無効になり、再試行しても作業量は返却されません。

検査は構造と読み取り可能性を確認し、**チェックサムも認証もありません**。有効な 6 ビット値を変更すると、検査が失敗せずに出力が変わる場合があります。一時準備と最終公開は引き続きホストの責任です。ソース ID の検査は変更をベストエフォートで検出し、認証済みスナップショットではありません。選択した項目だけの展開でも封装全体を検証し、未対応のヘッダー拡張や後続の不正なメンバーを黙って飛ばせません。

<a name="xdzip-automated-acceptance"></a>

## 自動受け入れ

プロジェクト所有の参照入力は、全バイト値、空ファイル、行末の余り、UU ゼロの別表記、CRLF、XX と Base64、転送テキスト、重複名を持つ混在メンバーを対象にします。独立したソースのリビジョンを固定し、その公開エンコーダーだけを呼び出します。UU は Python の `binascii`、Base64 は独立した標準デコーダーでも検証します。0–63 の全カウント長、危険名と Unicode 名、入力、名前、デコードの正確な上限、短い読み取り、型付き失敗、スナップショット不一致、キャンセル、終端後の無効化、既存出力の不変性もテストします。実際のランタイム、CLI、Qt タスクは閲覧、検査、展開、物理選択、読み取り専用の説明、検査強度の注意、登録された候補を対象とします。影響する二言語、テーマ、文字サイズのレイアウトとメインウィンドウ、メニューの比率は自動化します。参照バイナリーと生成証拠は `build/` に保管し、進捗と実際の結果は配布 issue に記録します。
