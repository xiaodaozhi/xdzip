# LZ4 ストリーム仕様

標準フレームのプロファイルは、作者による[フレーム形式 1.6.5](https://github.com/lz4/lz4/blob/v1.11.1/doc/lz4_Frame_format.md)、[ブロック形式、2026-10-26](https://github.com/lz4/lz4/blob/v1.11.1/doc/lz4_Block_format.md)、[XXH32 の仕様](https://github.com/Cyan4973/xxHash/blob/v0.8.3/doc/xxhash_spec.md)に従います。製品のアルゴリズムは Rust による独立実装です。参照ツールと生成した実行結果はローカルの `build/` に保存し、再現可能な自作の入力パターンのみをバージョン管理します。ホストの権限と出力の確定については[単一ファイルストリーム](single-file-streams.md)を参照してください。

<a name="xdzip-admission-and-framing"></a>

## 受け入れ条件とフレーム

バージョン 1 の標準フレームでは、予約ビット、BD の値 4〜7、ヘッダーの XXH32、省略可能なコンテンツサイズ、宣言されたすべてのブロックとコンテンツの XXH32、終端マーカーを検証します。ブロックデータの長さは 64 KiB から 4 MiB の範囲で宣言された上限を超えられません。独立ブロックでは履歴をリセットし、連結ブロックでは直前の 64 KiB だけを保持します。未圧縮ブロックは長さゼロの場合も同じ検証と計上の対象です。外部辞書プロファイルと旧フレームは対象外です。辞書の宣言で別のファイルの読み取りが許可されることはありません。

連結された標準フレームと途中のスキップ可能フレームには、物理入力、タスクの上限、キャンセル、および 100,000 フレームまたはブロックの上限が適用されます。有効な単独ファイルには少なくとも一つの標準データフレームが必要です。任意の末尾データや、スキップ可能フレームだけの入力は失敗します。検出では実際の圧縮入力を最大 8 MiB 調べてから、512 バイトの内容の接頭部を生成できます。形式が確実に識別された場合や識別済みの TAR が壊れている場合、失敗時にほかの形式へ切り替えません。完全なスキャンで全フレームを検証した後、実測サイズと仮想項目を公開します。

<a name="xdzip-block-processing-and-creation"></a>

## ブロックの処理と作成

長さの演算はオーバーフローを検査します。一致には履歴内に収まるゼロ以外のオフセットが必要です。重複するバイトは位置の昇順にコピーし、宣言された出力上限を守ります。最後のシーケンスはリテラルのみで、使わない一致ニブルは無視します。一致を含むストリームでは末尾に少なくとも五つのリテラルを残し、最後の一致はブロック末尾の少なくとも十二デコード済みバイト前で始まります。読み取りは上限内のチャンクを返し、失敗後は再開しません。履歴はブロックの正確な終端を検証した後にだけ引き継ぎます。ホスト I/O、キャンセル、上限超過、非対応プロファイルは異なるエラーに分類します。

許可される書き込み実装は実際の LZ4 一致を出力し、圧縮でサイズが減らないときだけ未圧縮ブロックを使い、ブロックと内容のチェックサムを含めます。選択できるレベルは一致探索の作業量を制限し、各レベルで、独立した実装による複数ブロックのデコードを確認します。フレームと一致用のバッファーは割り当て前に許可を得ます。作成では固定した正確な入力サイズ、ホストによる一時出力、完全な検証、ソースと出力の最終チェックを使用します。通常の LZ4 の入力は通常ファイル一つです。TAR との組み合わせは共有 TAR パーサー、書き込み実装、対応する自動検証がそろってから宣言できます。どちらも拡張子の登録だけで書き換え、暗号化、分割ボリュームに対応することはありません。

内容のチェックサムがないフレームもあるため、検証には `format_declared_checks` を使用します。チェックサムのないフレームを内容検証済みとは記載しません。リソース上限、実機でのプラットフォーム受け入れ、形式の妥当性、正式なリリース承認はそれぞれ別の基準です。
