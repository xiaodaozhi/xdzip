# アーカイブのパスワードと暗号化ディレクトリのオープン

[English](../../engineering/password-extraction.md) | [简体中文](../../zh-CN/engineering/password-extraction.md) | [繁體中文](../../zh-TW/engineering/password-extraction.md) | 日本語 | [한국어](../../ko-KR/engineering/password-extraction.md) | [Français](../../fr-FR/engineering/password-extraction.md) | [Deutsch](../../de-DE/engineering/password-extraction.md) | [Español](../../es-ES/engineering/password-extraction.md) | [Português (Brasil)](../../pt-BR/engineering/password-extraction.md) | [Русский](../../ru-RU/engineering/password-extraction.md)

この契約は[安全な展開](../../engineering/zip-safe-extraction.md)を補足し、パスワード、認証、タスク操作を定義します。形式とファイル安全性のロジックは Qt から独立し、パスワードウィンドウはユーザーの意図だけを送ります。実際の進捗とプラットフォーム検証は [issue #11](https://github.com/xiaodaozhi/xdzip/issues/11)を参照してください。実行レポートはここに置きません。

<a name="xdzip-capability-and-format-boundaries"></a>

## 機能と形式の境界

ZIP/ZIP64 の WinZip AES-256 AE-1 と AE-2 は、実際の圧縮方式が Store または Deflate の場合に対応します。平文、暗号化、混在した項目を選択でき、空ファイルも認証を検証する必要があります。ファイルごとに異なるパスワードを使えます。AES-128/192、従来の ZipCrypto、その他の暗号化は未対応です。対応する分割ボリュームは[統一された論理入力](archive-opening.md)を使い、パスワードと認証の規則は変わりません。ファイル名、ディレクトリ構造、通常の ZIP メタデータは見えたままであり、パスワード機能はこれらを暗号化または認証しません。

AES フィールドは [WinZip 形式仕様](https://www.winzip.com/en/support/aes-encryption/)に従います。マーカー方式 99、暗号化フラグの設定、AE ベンダー、既知のバージョン、256 ビット強度、対応する実際の方式を持つ単一 AES extra です。現在は定義済みデータ七バイトのみ受け入れ、未知の拡張は拒否します。AE-1 はデコード内容の CRC も検証し、AE-2 の保存 CRC はゼロでなければなりません。中央ディレクトリ、ローカルヘッダー、データデスクリプターの宣言は独立して検査し、認証コードは構造検証に代わりません。

アダプターはまず固定スナップショットの物理レコード ID、生の名前、種類、サイズ、方式、暗号化フラグ、パスワード対応マーカーを比較します。次にこのタスク用の完全なフラグと AES プロファイルを記録し、ローカルヘッダー、中央ディレクトリ、デスクリプター、ペイロード範囲の整合性を検証します。初期スナップショットは完全なフラグやプロファイルを保持しません。ソース変更は引き続き識別情報・バージョンによるベストエフォート検出に依存し、アトミックな入力内容スナップショットではありません。ローカルまたは中央ヘッダーの ZIP64 サイズセンチネルがデスクリプター幅を決めます。プロジェクトは[受理された暗号プリミティブ](../../engineering/dependencies.md)を使って ZIP コンテナーと AES ラッピングを独立して実装し、形式ライブラリの展開関数を呼び出しません。

復号器は一項目の検証済み暗号文範囲だけを読み、出力パスを受け取りません。Store または共有の生 Deflate は圧縮バイトの正確な消費、デコードサイズ、AE-1 CRC を検証します。暗号文を完全に消費した後に HMAC 認証コードを検証し、すべて成功した場合だけ成功を返します。空ファイルも認証を完了します。暗号文とデコードデータは上限付きバッファーを使い、ファイル全体をメモリーに蓄積せず、サードパーティー ZIP ライブラリ向けのプライベートなアーカイブビューも構築しません。

<a name="xdzip-7z-rar-and-encrypted-directories"></a>

## 7z、RAR、暗号化ディレクトリ

7z と RAR は同じホストのデコード先、安全な出力、実際のクォータ、エラー分類を維持します。現在の製品経路と自社候補の境界は[分離バックエンド契約](native-codecs.md)と[独立実装契約](../../engineering/independent-rust-codecs.md)を参照してください。7z AES-CBC に独立したパスワード検証値がない場合、認識済みの暗号化メタデータのデコード・解析失敗や暗号化内容のサイズ・ストリーム終端・CRC の失敗には `password_or_integrity` を使います。これはパスワード不一致または暗号化データの破損を示し、`wrong_password` と断定しません。外側の平文ヘッダー検証失敗はコンテナー破損のままです。ソース I/O、ソース変更、リソース上限、キャンセル、未対応機能、出力失敗はパスワードエラーに再分類しません。RAR は従来と現在のパスワード境界を維持し、旧・現行形式、ヘッダー暗号化、ソリッドアーカイブ、分割ボリュームの組み合わせを別々に受け入れます。

暗号化されたファイル名やディレクトリはメタデータ走査前に秘密情報を必要とします。OpenWithPassword はそれを運ぶ唯一のオープンコマンドです。パスワードコンテナーはキュー投入前に上限が設けられ、解放時にゼロ化され、イベントに秘密情報は含まれません。完全な走査が成功する前に部分的な閲覧可能インデックスを公開しません。成功後、セッションはゼロ化されるコンテナーを保持し、受理済みタスクはページを閉じた後も継続できるようプライベートなコピーを複製できます。コピーはスナップショット、ログ、設定に入りません。タスクデコーダーが再オープンする際は同じパスワードを使い、後続項目のパスワードは別のプロンプト制御応答を使います。

7z の作成は内容パスワードとファイル名暗号化を同時にサポートします。ファイル名暗号化には空でない作成パスワードが必要で、7z のみです。ZIP は内容だけの暗号化を維持し、TAR/TAR.GZ は暗号化引数を拒否します。暗号化された 7z とすべての RAR は変更を拒否します。

<a name="xdzip-secret-and-control-protocol"></a>

## 秘密情報と制御のプロトコル

`extraction::Password` は作成パスワードと別です。展開は入力されたままの UTF-8 を最大 1,024 バイト受け入れ、空文字、空白、制御文字を含められます。前後を切り詰めず、作成時の 1–128 バイト規則も適用しません。現在のテキスト UI は UTF-8 以外の生パスワードを表現できません。入力の割り当て容量にも上限があります。Rust が所有するコンテナーは Debug 出力を常に伏せ、拒否、置換、キャンセル、スコープ終了時にゼロ化します。

`Client::respond_password(task, prompt, Password)` は通常コマンドキューではなく独立した制御枠で秘密情報を渡します。各プロンプトはタスク内の一回限りの ID を使い、名前の競合とパスワードのプロンプトを区別します。古い ID、異なる種類への応答、重複応答、終端状態またはキャンセル後の応答を拒否します。スナップショットが持つのは `PasswordPrompt { id, name, retry }` と `waiting_password` だけで、パスワードやダイジェストは含みません。GUI メールボックスのバイト上限はプロンプト名も計上します。

最初にパスワードが必要になるとタスクは明示的な応答を待ちます。タスク内で成功したパスワードは後続の暗号化項目に再利用できます。検証値の不一致または明示的な `password_or_integrity` は古いキャッシュを消して再度要求し、物理項目ごとに最大十回の失敗までです。上限では実際の終端エラー分類を保持し、不確実な失敗を `wrong_password` に強制できません。暗号化 7z ディレクトリのオープンもパスワードウィンドウとオープン要求 ID を再利用し、ユーザーはオープンをキャンセルできます。形式に独立した認証子がある場合、その不一致は整合性エラーとして停止し、パスワード再試行に入りません。二バイトの検証値ですべての誤パスワードを排除できるわけではなく、最終認証が必要です。

キャンセルと終了は通常キューの容量に依存せず、パスワード待機を起こして未消費の秘密情報を消去します。内容パスワードはタスクの間だけ、暗号化ディレクトリのパスワードはオープンセッションとその受理済みタスクに限定されます。どちらも設定、イベント、ログ、コマンドライン、復旧記録、テストスクリーンショットに入りません。送信、クローズ、キャンセル、プロンプト変更、終了時に Qt 入力と制御された転送バッファーを消去します。Qt、システム入力メソッド、依存ライブラリ内部の過去のすべてのコピーは消去を保証できず、Rust コンテナーのゼロ化はプロセス全体の保証にはなりません。

<a name="xdzip-output-retries-and-links"></a>

## 出力、再試行、リンク

通常ファイルの各試行は新しいプライベートステージングファイルを使います。誤パスワード、認証失敗、ストリームエラー、キャンセルはそのステージングの寿命を終え、識別情報を検査して削除を試みます。削除に失敗した場合、最終的な作業領域のクリーンアップは警告を報告し復旧資料を保持するため、即時削除は保証できません。完全な検証、同期、ソース再検証、確定許可のすべてを終えてから、既存方針に従って公開または置き換えます。未認証のステージングを出力先として公開することはありません。認証失敗時は既存ターゲットを変更しません。再試行による実際のデコード・書き込み量は保持され、ファイルごと 8 GiB、タスクごと 20 GiB、ソース読み取り上限の対象です。再試行で予算はリセットされません。

ZIP タスクはデコーダー作成時に実際のメタデータ読み取り 64 MiB の予算を持ち、その後、共有の入力読み取り 20 GiB 予算に切り替えます。ローカルヘッダー、デスクリプター、暗号文、すべてのパスワード再試行が同じカウントを消費します。入力読み取り量はソースファイル長や保存出力とは異なり、超過時は停止し、再試行時もリセットしません。

後続ファイルの失敗前に、タスクが以前の検証済みファイルをすでに確定している場合があります。アーカイブ全体のロールバックは保証しません。競合のスキップではそのファイルを読まないことがあり、認証済みとは数えられません。確定済み項目、クリーンアップ警告、キャンセル後の不確実なカウントは安全な展開契約に従います。

暗号化シンボリックリンクを選択した場合、出力認可の取得や派生ディレクトリの作成より前に、タスクの Preparing 中ですべての選択リンクのペイロードと依存関係グラフを認証・検証します。通常ファイルを先、リンクを最後に公開します。パス規則、リンクごと 4,096 バイト・合計 4 MiB、64 回の追跡、閉じた依存関係、書き込みの親にリンクを使わないこと、占有された末端の拒否は緩和しません。POSIX が復元する実行権限は受理された安全なビットだけです。Windows の ZIP リンクと TAR リンクは未対応のままです。

## インターフェースと検証

パスワードウィンドウ、HTML、高忠実度ソースは[パスワード操作](../ux/password-extraction.md)を参照してください。アプリケーションモーダルウィンドウはタスクが待機すると自動表示され、タスクウィンドウから再表示できます。エラー応答では新しいトークンを使い古い入力を消去し、受理された応答は重複送信を防ぎます。システムのクローズまたはキャンセルで現在のタスクをキャンセルします。Escape は共通規則に従い、最初にコントロールのフォーカスを離れ、次にウィンドウを閉じます。

作成と展開のパスワード欄は、入力とは独立した明示的な UI ラベルでアクセシビリティ名を公開します。Qt 6.8.2 はパスワード状態で付与された名前を抑制するため、デスクトップアプリはこの二つの欄に専用のアクセシビリティインターフェースを導入し、名前のみを上書きして Qt の状態、テキスト・値、操作を維持します。パスワードフラグとマスキングは変えません。このインターフェースは Qt Quick のプライベートクラスを継承し、ビルド時と実行時の Qt Quick バージョンが一致する必要があります。ライブラリをアップグレードまたは置き換える際は再ビルドし、インターフェース、パスワードの秘匿性、三プラットフォームの互換性を再検証します。自動インターフェース検査とシステムスクリーンリーダーによる手動受け入れは別々に記録します。

受け入れは生の AES フィールド・CRC・デスクリプター・ZIP64、重複名の物理レコード、正しい・誤ったパスワード、認証破損、混在ファイル、異なるパスワード、空パスワード・制御文字、再試行の累積リソース、満杯キュー、キャンセル・終了時の起床、ソース変更、旧ターゲット保護、リンクと実行権限、独立した双方向 7-Zip バイト検査を対象とします。UI 検査は実際のコントローラーフロー、アクセシビリティ操作、二言語・複数字号レイアウト、ライト・ダーク、DPR、ネイティブウィンドウを別々に対象とします。自動化はシステムスクリーンリーダーによる手動受け入れではありません。

信頼できるパスワード検証値のない RAR では、暗号化ヘッダーまたは内容のデコード整合性失敗も `password_or_integrity` を使います。一致済みの信頼できる検証値、平文ヘッダーの検査、パスワード以外の失敗はそれぞれの分類を維持します。従来の項目別パスワードとプラットフォームごとの文字投影は [RAR 実装の根拠](../../engineering/rar-format-sources.md)を参照してください。サイズ不明はデコードやパスワード操作の前に拒否し、出力できない項目に秘密情報を要求しません。

旧 RAR の暗号化レコードには誤パスワードと破損を確実に区別する検証値がないため、各暗号化項目をデコードする前に個別にパスワードを要求します。別の秘密を使う可能性のある後続項目に前のパスワードを直接適用しません。RAR5 と他の対応形式はタスク内再利用を続けます。旧 RAR の CRC やヘッダー破損は整合性失敗のままで、確定した誤パスワードではありません。

AES Crypt v0–3 はファイル名が暗号化されていなくてもオープン認証情報が必要です。完全な暗号文認証によって、行を公開する前に正確なサイズのメタデータを受け入れます。検査・プレビュー・エクスポートは既存の秘密情報枠でセッション認証情報を保持し、項目ごとの再要求はしません。v0 の検証値の曖昧さ、v1–3 のラップされた鍵の検証、従来の未認証の長さ・拡張フィールドは [AES Crypt 契約](aescrypt-envelopes.md)に従います。
