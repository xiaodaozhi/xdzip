# GitHub Release プロトコル v1

[English](../../engineering/release-protocol.md) | [简体中文](../../zh-CN/engineering/release-protocol.md) | [繁體中文](../../zh-TW/engineering/release-protocol.md) | 日本語 | [한국어](../../ko-KR/engineering/release-protocol.md) | [Français](../../fr-FR/engineering/release-protocol.md) | [Deutsch](../../de-DE/engineering/release-protocol.md) | [Español](../../es-ES/engineering/release-protocol.md) | [Português (Brasil)](../../pt-BR/engineering/release-protocol.md) | [Русский](../../ru-RU/engineering/release-protocol.md)

このワークフローは GitHub のダウンロードを提供します。[Microsoft Store MSIX ワークフロー](../../../.github/workflows/windows-store-msix.yml)は同じバージョンのソースを Microsoft Partner Center 向けにパッケージ化し、Store の認定と公開は Partner Center が扱います。

専用の [Release ワークフロー](../../../.github/workflows/release.yml)は `workflow_dispatch` で手動実行します。正式な実行は `main` 上の既存バージョンタグから開始し、解決したコミットを固定します。4 つのネイティブジョブはそれぞれ設定、ビルド、テスト、パッケージ化を一度行います。macOS ジョブは初回ビルドから配布用の関連付け優先順位を使い、Qt をデプロイして ad-hoc の整合性署名を適用し、同じアプリから ZIP と DMG を作成します。通常の macOS Qt CI は SDK に対して検証します。Developer ID、Apple の公証、Windows 発行元証明書はこのリリース方針の対象外です。

Intel ビルドでは `macos-x86_64` のアプリ ZIP、DMG、CLI アーカイブを別途作成します。Intel デスクトップと CLI はそれぞれ `release-intel.json` と `cli-release-intel.json` を使い、署名と `appcast-intel.xml` を個別に検証します。旧クライアントとの互換性のため、既存の ARM64 マニフェストとフィードの形式は維持します。リリース前に両アーキテクチャのネイティブパッケージ検証が必要です。

製品のソースはタグが指すコミットから取得します。ドラフト作成、公開、公開後のダウンロード検証では、ワークフローを起動したときの `main` のコミットから同じレビュー済みのリリースノートを読み込みます。

完全なタグは VERSION.json から導いたセマンティックバージョンの先頭に `v` を付けます。`prerelease_number` は任意の正の整数で、省略時は過去のビルド番号との互換性を保ちます。alpha.1 と build 14 は異なる識別情報です。Windows の数値リソースと macOS の CFBundleVersion は引き続き単調増加するビルド番号を使います。同じバージョンの公開済みアセットは置換できず、修正には新しいバージョンが必要です。ドラフトは再実行できます。

リリースノートは保存され、レビュー可能なバージョン入力です。既定では `release-notes/<full-version>.md` を読み、CLI の `--notes-file` でレビュー済みファイルを指定できます。ファイルには `<!-- xdzip-release {"version":"0.1.0-alpha.6","build":19} -->` のメタデータ行を一つと、対応するバージョン見出しを含めます。バージョンとビルドは VERSION.json と一致しなければなりません。最初に `python3 scripts/publish-release.py --check-notes` を実行します。この検査は GitHub に接続しません。専用ワークフローもビルド前に同じ検査を行います。新バージョンには新しいノートが必要で、以前の機能一覧や受け入れ状態を自動で引き継ぎません。

ノートにはプラットフォームごとの受け入れ範囲、実際のコミットと証拠を中国語と英語で記録し、既存の手動受け入れと未実施の検査を分けて残します。段階の進捗は引き続き issue で管理します。ドラフト作成と公開には同じノートのスナップショットを使います。ドラフト再実行時に本文がレビュー済みファイルと異なる場合は、アセットのアップロードや削除の前に停止し、入力の明示的な一致を求めます。公開済みバージョンはアセットを置換する再実行を引き続き拒否します。未公開の変更は[変更履歴の未公開セクション](../../../CHANGELOG.ja-JP.md#unreleased)に記録し、公開後に対応するバージョンへ移します。変更履歴のすべての言語版を同期します。

ドラフトのアセットを変更する前に、公開ツールは GitHub のタグ、ドラフト状態、チャネル表示を読み直します。stable はプレリリースではなく GitHub Latest になる必要があり、alpha、beta、rc はプレリリースのままで Latest を置換してはなりません。公開後と公開添付の検証後にそれぞれ状態を再確認し、すべて一致した場合だけ成功を報告します。公開後の検査が失敗してもリリースはすでに見えている可能性があります。スクリプトは所有者による対応のため停止し、公開リリースやアセットを自動で撤回、編集、置換しません。

正式リリースの前にローカル事前検査と対応するノートのレビューを完了します。パッケージ検証は同じネイティブプラットフォームで独立して実行します。同一実行の受け渡しでも、リポジトリ、コミット、プラットフォーム、アーキテクチャ、アーカイブの SHA-256 を確認してから受け入れます。Windows と Linux はデプロイ済みランタイムを一度検証し、実際のインストーラーライフサイクルを実行します。macOS は実際の DMG とアプリ ZIP の両方を検証します。必要に応じた候補実行は同じジョブを実行し、組み立てた Actions アーティファクトをダウンロードしてチェックサムを検証します。候補経路はリポジトリの読み取り専用権限を使い、タグもリリース署名シークレットも必要としません。

リリース契約ジョブは最初に同一コミットの独立した形式ワーカーをビルドし、`XDZIP_NATIVE_CODEC` と `XDZIP_NATIVE_CODEC_WORKER` を使って Rust ワークスペーステストを実行します。3 プラットフォームのネイティブジョブはアプリ、デプロイ、インストールライフサイクルを別々に検証します。macOS の開発用関連付け優先順位テストには、開発用メタデータを指定したコンパイル済みバンドルの一時コピーを使います。配布バンドルはネイティブ起動とパッケージ化で実際の配布優先順位を維持します。

Windows のデプロイ検証は毎回独立した一時テストコピーを使い、過去のログを保持します。再検証で既存ディレクトリを再利用または削除せず、製品のランタイムディレクトリにテスト DLL を含めません。

リリースには必ず `release.json` と `SHA256SUMS` を含めます。`schema_version=1` のマニフェストのルートフィールドは product、version、channel、build、tag、commit（40 文字の完全な SHA）、repository、assets です。各アセットは filename、platform、architecture、package_type、minimum_system、bytes、sha256 と、タグのダウンロードパスに固定された url を含みます。

| プラットフォーム、アーキテクチャ | パッケージ形式 | 最低システム |
| --- | --- | --- |
| windows, x86_64 | zip, exe | 保守対象の Windows 11 |
| macos, arm64 | app.zip, dmg | macOS 14.0 |
| linux, x86_64 | tar.gz, deb | Ubuntu 24.04、glibc 2.39、X11 |

6 種類のパッケージがすべて必要です。マニフェスト検証はパッケージの欠落、対象の重複、チャネルの不一致、変更可能なダウンロード URL、不正なサイズやハッシュを拒否します。リリース添付にはプラットフォームの通知、ライセンス、SBOM、デプロイ／検証資料を含め、対応ソースのアーカイブは含めません。Windows はアプリローカルの VC++ ランタイムを使い、Windows SDK のグラフィックコンパイラーライブラリーを配布しません。

2026-11-05 以降、所有者の指示により GitHub Releases と Actions アーティファクトから過去の対応ソースアーカイブを削除し、今後のリリースフローでの生成とアップロードを停止しました。`scripts/prepare-source-delivery.py` はローカルレビュー用に残します。リリースの組み立てと公開は名前に `corresponding-source` を含むアーカイブを拒否します。この方針はコンポーネントのライセンスを変更せず、対応ソース、再リンクその他の義務が満たされたことを証明しません。リリースレビューでは実際の配布に対する義務を引き続き解決し、必要条件を他の方法で満たせない場合は対象バイナリの配布を止めます。GitHub が公開リポジトリのタグから自動生成するソーススナップショットは、これらの Release 添付とは別です。

通常のリリースでは、ソース配布収集器を独自にローカル実行してはなりません。ユーザーがソース収集を別途明示的に依頼した場合だけ実行し、アップロード制限も引き続き守ります。機械的な一般要確認フラグは実際のコンポーネントと具体的な義務に照らして評価し、フラグだけで新たなリリース欠陥と判断しません。

macOS アプリ ZIP、DMG、通知資料は、同じデプロイ済み署名付き一時アプリが存在する間に出力し、その後で準備した `.app` と一時登録を削除します。削除後に別のアプリを再デプロイして ZIP を補ってはなりません。

順序は、ローカル事前検査、バージョンコミットの固定、タグ作成、Release ワークフロー一回の手動起動、3 プラットフォームのビルドと独立した起動／インストールライフサイクル検証、ドラフトマニフェストの組み立て、すべて完了後のチャネル別公開、全添付の再ダウンロードと検証です。stable は明示的に Latest とした通常の Release、alpha／beta／rc は Pre-release です。いずれかのプラットフォームが失敗した場合、ドラフトは非公開のままにします。公開前後に SHA256SUMS を確認します。出所・ライセンスレビューや手動受け入れが未完了ならノートに制限を残し、自動化でその結論を代行しません。

更新クライアントは GitHub Releases をページごとに取得してドラフトを除外し、マニフェストのバージョンを検証して、セマンティックバージョン、ユーザーが許可したチャネル、プラットフォーム、アーキテクチャ、パッケージ形式で選択します。公開日から更新を推測したり、ファイル名を推測したりしません。プレリリースはプレリリースを除外する `/releases/latest` を使いません。stable は stable のみ、alpha は alpha・beta・rc・stable、beta は alpha に戻らず、rc は rc・stable のみを受け取ります。開発版の比較では dev をサポートします。セマンティックバージョンと単調増加するビルド番号の両方が上がる必要があります。ダウンロード後にサイズと SHA-256 を確認し、値の欠落や不一致を拒否します。

<a name="xdzip-trusted-update-attachments"></a>

## 信頼できる更新添付

新しいリリースには schema_version=1、algorithm=ed25519、key_id と 128 文字の小文字 16 進署名を持つ `release.json.sig` を含めます。署名は `release.json` の正確な生バイトを対象とするため、検証前に解析して再シリアライズしません。クライアントと Qt を使わないインストール補助プログラムは、それぞれに組み込まれた `resources/update-trust.json` 公開鍵セットを使い、ダウンロードしたマニフェストやユーザー要求からの信頼ルートを受け入れません。インストール時は未知の公開鍵、重複 key_id、弱い鍵、空の信頼セットを拒否します。

macOS ネイティブジョブはアプリの ZIP の作成と検証を行います。Linux の `sign` ジョブは検証済みのバイト列を受け取り、`scripts/sign-macos-update.py` から `xdzip-update-tool sign-archive` を呼び出して `macos-update.json` を出力します。このファイルには schema_version、version、build、filename、bytes、sha256 と Sparkle の base64 `ed_signature` が含まれます。組み立て時にアーカイブと署名を再確認し、同じ不変の候補だけを含む `appcast.xml` を作成します。任意のマニフェストフィールド `macos_appcast_url` は同じタグのこのファイルに固定されます。フィードは build を Sparkle バージョン、完全なセマンティックバージョンを shortVersionString、macOS 14.0 を最低バージョンとし、短いリリースノートだけを内包します。完全なノートは GitHub Release の本文に残り、クライアントは外部ノートを取得しません。

アーカイブとフィードは別の Sparkle 鍵を使い、フィード自体にも署名が必要です。クロスプラットフォームのリリースツールは [Sparkle の上流署名形式](https://github.com/sparkle-project/Sparkle/blob/2.x/common_cli/Signing.swift)に従い、完全な生 XML に署名し、base64 edSignature と生バイト長を含む sparkle-signatures コメントブロックを追加します。添付だけに署名する方法ではありません。生成後に独立して検証し、バイトが変われば再署名します。Mac パッケージの SUPublicEDKey は `resources/sparkle-update-key.json` の公開鍵と一致しなければなりません。

リリース環境は既存の鍵と公開鍵 ID を `XDZIP_UPDATE_SIGNING_KEY_HEX`、`XDZIP_UPDATE_KEY_ID`、`XDZIP_SPARKLE_SIGNING_KEY_HEX` で提供します。所有者はクライアントとインストール補助プログラムと共にバージョン管理する 2 つの本番公開鍵リソースを提供します。テスト公開鍵を組み込まず、ビルド時に秘密鍵を生成しません。所有者は先に公開信頼ルートをクライアント版で配布し、その後、信頼できるリリース環境に対応する秘密鍵を設定します。鍵のローテーションでは署名鍵の切り替え前に新しい公開鍵を配布し、旧クライアントの検証経路を維持します。公開鍵を組み込まない旧クライアントはまず公開鍵を含む版を手動インストールする必要があり、ダウンロードしたマニフェストでは信頼ルートを追加できません。過去の公開リリースに事後署名したり置換したりしません。

リリーススクリプトは 2 つの秘密鍵環境変数を除いた子プロセスで署名ツールをビルドし、コンパイル済みツールのプロセスだけが秘密署名鍵を受け取ります。Cargo のビルドスクリプト、コンパイラー、依存関係の解決には署名権限を渡しません。

最終署名ジョブは `release-signing` で検証済みアーカイブと更新マニフェストに署名します。別の公開ジョブもこの環境を必要とし、リリースを公開する前に署名とドラフトのダウンロードを検証します。最後の読み取り専用ジョブは公開リリースをダウンロードし、署名済みアセットと比較します。すべてのジョブは固定コミットと同一実行のアーティファクトを使います。

[本番更新の受け入れ](../../../.github/workflows/production-update-acceptance.yml)は `main` と `contents: read` に固定された別の手動入口で、同じ `release-signing` 環境と所有者の承認を使います。Release を呼び出さず、タグ、ドラフト、リリースも作成しません。最初にシークレットなしの段階でツールをコンパイルし、次に既存の秘密鍵から公開鍵を独立して導き、現行コミットの両公開鍵と公開鍵 ID に厳密に一致するか確認します。項目の存在だけでは一致を証明できません。3 プラットフォームの非公開旧ビルド 200 と新ビルド 201 は本番公開鍵を維持し、シークレットなしでビルドします。署名はこのソースコミット、非公開の製品識別情報、ハッシュに完全に結び付いた固定候補だけを受け入れます。その後、ネイティブ更新、失敗からの復旧、通常再起動をシークレットなしのプロセスで実行します。任意の入力マニフェスト、アセット、リモートアーティファクト、リリースパラメーターはありません。

シークレットなしの macOS ツールチェーン準備中に `rust-toolchain.toml` に宣言された `rustfmt` と `clippy` を一度インストールし、その後アーカイブ受け入れテストを実行します。テスト鍵による更新回帰も本番秘密鍵を使用または検証せずに準備と受け入れを検査します。

本番受け入れパッケージ、元のマニフェスト、署名、appcast、アプリは使い捨てランナー内に残り、アップロードしません。制限された収集器は明示的に許可したログ、状態、識別情報、ハッシュ記録だけをアップロードし、結果領域に署名付き添付がある場合は拒否します。本番鍵の一致、署名検証、実際のインストール、手動デスクトップ受け入れは別々に記録します。macOS はネイティブ Apple Silicon と実際の `SUPublicEDKey` 検査を使い、Windows Server のテストは Windows 11 の手動受け入れを代替しません。このフローは GitHub Secret 値をローカルで読み取らず、リリースを許可するものでもありません。

`prepare-release.py --require-update-signature` は鍵、署名、ネイティブアーカイブのメタデータが欠けると停止します。`publish-release.py` はアップロード前にマニフェスト、同じ候補のフィード、アーカイブを独立して再検証します。署名、appcast、状態添付はすべて SHA256SUMS に含めます。すでに公開されたリリースにこれらの添付を追加または置換しません。

<a name="xdzip-independent-cli-attachments"></a>

## 独立した CLI 添付

v0.2.0 以降、完全なリリースには `xdzip-cli-<version>-windows-x86_64.zip`、`xdzip-cli-<version>-macos-arm64.tar.gz`、`xdzip-cli-<version>-linux-x86_64.tar.gz` も提供します。3 つとも同じコミットのネイティブ CLI ビルドと検証から生成され、ワーカー、実際のランタイム依存関係、通知を保持します。識別情報は変更のない Release ビルドでなければなりません。通常の CI に Mac アプリパッケージをデプロイまたはアップロードする権限は追加されません。

CLI は `cli-release.json` と `cli-release.json.sig` を使います。マニフェストは schema_version=1、product=xdzip、component=cli です。version、channel、build、tag、commit、repository はデスクトップマニフェストと完全に一致します。アセットはこの 3 対象だけを含み、デスクトップアセットと同じフィールドを持ちます。Mac パッケージ形式は tar.gz、Linux の最低システムには display_server を含めません。その他のシステム、アーキテクチャ、サイズ、ダイジェストの要件は維持します。固定の発行元は xiaodaozhi/xdzip のままです。

デスクトップの release.json は component や CLI 項目を含めず、引き続き 6 種類のパッケージだけを含みます。旧クライアントは新しい独立添付を無視します。CLI マニフェストの署名は組み込み Ed25519 信頼ルートを再利用し、sign-cli／verify-cli が正確な生バイトに署名して独立に検証します。署名、識別情報、3 つの CLI パッケージ、すべてのチェックサムが完了してから完全な組み立てと公開を行えます。既存の公開リリースに後から追加、変更、置換はしません。
