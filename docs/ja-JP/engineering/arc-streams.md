# ARC コンテナーと圧縮ストリームのプロファイル

[English](../../engineering/arc-streams.md) | [简体中文](../../zh-CN/engineering/arc-streams.md) | [繁體中文（台灣）](../../zh-TW/engineering/arc-streams.md) | 日本語 | [한국어](../../ko-KR/engineering/arc-streams.md) | [Français](../../fr-FR/engineering/arc-streams.md) | [Deutsch](../../de-DE/engineering/arc-streams.md) | [Español](../../es-ES/engineering/arc-streams.md) | [Português (Brasil)](../../pt-BR/engineering/arc-streams.md) | [Русский](../../ru-RU/engineering/arc-streams.md)

`ArcReader` は ARC 方式 3–9 の上限付き生デコードを実装します。方式 1 と 2 はコンテナーの Store プロファイルです。`xdzip-codec-arc` と `ArcCodec` は完全な構造と必須 CRC-16 をランタイム、CLI、デスクトップの閲覧、検査、展開に接続します。[形式レジストリ](../../../specs/engineering/archive-formats.json)は読み取り専用の範囲を宣言し、作成、変更、パスワード、分割は利用できません。

<a name="xdzip-container-and-host-admission"></a>

## コンテナーとホストの受け入れ

受理されたプロファイルは通常の ARC 5.x 構造を使い、ARC 6.x の追加メタデータや Spark 拡張は対象として主張しません。各メンバーは `0x1a` と元の方式バイトで始まります。方式 1 は 25 バイト、他のゼロ以外の方式は通常の 29 バイトヘッダーを使います。13 バイトのファイル名フィールドには空でない NUL 終端の名前が必要です。整数はすべてリトルエンディアンで、15 に圧縮長、19/21 に DOS 日付・時刻、23 に必須 CRC-16、25 に通常のデコード長があります。旧 Store は圧縮長を引き継ぎ、両 Store 方式とも長さが等しい必要があります。圧縮範囲は収まり、次のマーカーは必須で、正確な 2 バイト終端 `1a00` は物理 EOF と一致しなければなりません。再同期、接頭辞走査、埋め草、隣接ファイルは受け入れません。

コンテナーはすべての物理的な重複と未知の方式を保持します。メタデータ読み取りの厳格な上限は 64 MiB、レコードは最大 100000、生の名前は呼び出し側の上限、物理入力の上限は 24 GiB です。SHA-256 は正確な `Index` を再オープンする際、無視された名前の埋め草を含むすべてのヘッダーバイトと終端を結び付けます。ヘッダーハッシュはペイロードを認証しません。各リーダーは実際の入力とデコードバイトそれぞれ 24 GiB、作業 96 GiB の累積台帳を持ち、デコード前にテーブル CRC のバイト作業を予約し、失敗時は予算返却や部分インデックス公開なしで終了します。

ホストは強いコンテナーと ZIP/SFX の優先順位を維持し、共有の探査台帳の下で弱い ARC 候補を完全に検証します。名前は共有の上限付きアーカイブエンコード判断を使い、DOS バックスラッシュを変換する前に完全なフィールドとしてデコードします。元のバイトと方式 ID は利用可能なままです。疑わしい・未解決の名前や未知方式はペイロード権限なしで表示されます。ARC にはディレクトリ、リンク、モード復元、外部オブジェクトの受理済みプロファイルがありません。従来の XOR には暗号化フラグがなく、パスワードを推測したりフォールバックしたりせず、ストリーム、サイズ、CRC の検証は必須です。このプロファイルは専用 Linux MIME 登録を主張しません。

ペイロードを開く際は固定された項目を再投影して比較します。選択 ID は物理行を識別し、正確に一致する必要があります。ランタイムの事前確認、固定されたホストソース ID、プライベートステージング、キャンセル、旧ファイル保護、最終公開は引き続き優先されます。全体の `supported_content` 検査は受理された通常メンバーをすべて実際にデコードし、正確なサイズと CRC-16 を検証し、未対応行で失敗します。未対応の隣接項目があっても、対応する物理選択は展開できます。

<a name="xdzip-method-scope"></a>

## 方式の範囲

| 方式 | ワイヤープロファイル | 後続ステージ |
| --- | --- | --- |
| 1 | 元の長さを暗黙に持つ旧 25 バイト構造 | Store |
| 2 | 通常の 29 バイト構造 | Store |
| 3 | DLE `0x90` の連続とエスケープされた DLE を持つバイト | なし |
| 4 | 符号付き子を明示する squeeze 木、下位ビット優先コード、EOF 記号 256 | 方式 3 の RLE |
| 5 | 固定 12 ビット上位優先コード、元のハッシュ辞書 | なし |
| 6 | 同じ元のハッシュ辞書 | 方式 3 の RLE |
| 7 | 固定 12 ビットコード、改良されたハッシュ | 方式 3 の RLE |
| 8 | 最大幅 12 の初期バイト、9–12 ビットのグループ化された下位優先 LZW | 方式 3 の RLE |
| 9 | 幅ヘッダーなし、9–13 ビットのグループ化された下位優先 LZW | なし |

未知の方式、Spark 拡張、パスワード、SFX 構造には別のコンテナー受け入れが必要です。アルゴリズム名が同じでも他の方式のビット順、辞書、アラインメント、リセット、RLE ステージを認可しません。

<a name="xdzip-rle-and-squeeze-trees"></a>

## RLE と squeeze 木

通常バイトは出力され、繰り返し履歴になります。ゼロが続く DLE は履歴を変えずリテラル DLE を出力します。ゼロ以外の回数は直前の通常バイトを `count - 1` 個出力し、履歴のない回数は無効です。エスケープは完全でなければならず、正確なデコードサイズが各繰り返しを制限します。RLE 状態は辞書文字列と呼び出し側の出力チャンクをまたいで維持されます。

Squeeze はリトルエンディアンのノード数、最大 256 で始まり、各ノードに二つの符号付き 16 ビット子が続きます。非負の子は内部ノードを示し、負の値は 0 から 256 までの記号 `-child - 1` を表します。ルートはゼロで、従来のノードゼロ形式には暗黙の EOF 子があります。全体グラフはサイクル、共有された内部子、到達不能な内部ノード、範囲外の辺のない根付き木で、EOF に到達できなければなりません。EOF まで下位ビットからたどります。圧縮入力はその終端と同じバイトで終了し、最後の未使用ビットは無視します。宣言サイズまでデコードすることは EOF 検査に代わりません。

<a name="xdzip-fixed-dictionaries"></a>

## 固定辞書

4096 スロットの辞書は最初に前駆 `0xffff` でバイト列 0–255 を挿入します。コードは物理ハッシュスロットを識別します。旧ハッシュは `((prefix + suffix) mod 65536) | 0x0800` の二乗の中央 12 ビットを使います。方式 7 は代わりに 16 ビットの合計に 15073 を掛け、下位 12 ビットを取ります。これらの定数は従来のワイヤー ID を定義します。

衝突時は既存スロットチェーンをたどり、最後の要素から 101 スロット先で探索を始め、その後折り返しながら線形探索します。各探査とプレフィックス展開は制限され、計上されます。新しい文字列は前の文字列に現在の文字列の先頭バイトを加えたものです。未登録コードは正確に新しく挿入された KwKwK スロットの場合だけ受理します。辞書が満杯になると増加を止めます。12 ビットコードはバイト間で上位ニブルが先で、後の下位ビット優先プロファイルとは異なります。最後の未使用ニブルは無視し、不足コードバイトや余分な完全バイトは無効です。

<a name="xdzip-dynamic-dictionaries"></a>

## 動的辞書

最初のコードはバイトでなければなりません。コード 256 は CLEAR、257 から辞書の逐次追加が始まります。幅は辞書のしきい値で方式の最大まで増えます。コードは八個ずつグループ化され、幅変更または CLEAR は旧グループを終え、未使用のアラインメントビットを消費して新しいグループを始めます。アラインメントビットは未規定です。CLEAR は次の辞書スロットと幅をリセットし、後続のリテラルを必要とし、リセット前の辞書文字列を借りられません。合成 EOF コードやバイトは供給しません。

辞書の増加、KwKwK、最大幅での動作、適応的なリセットは RLE ステージと別です。ネイティブの強制 LZW 参照入力はすべての幅と実際のリセットを示し、作成した CLEAR 入力は旧グループの八つの位置をそれぞれ独立にカバーします。

<a name="xdzip-budgets-and-failures"></a>

## 予算と失敗

圧縮長とデコード長にはそれぞれ厳格な 24 GiB、作業には 96 GiB の上限があります。呼び出し側のより小さい制限が優先されます。完全なプライベートメモリー受け入れは方式 3 に 16 KiB、方式 4 に 32 KiB、方式 5–7 に 64 KiB、方式 8–9 に 96 KiB です。これには 8192 バイトの入力バッファー、辞書、逆順展開、グラフ検証、状態が含まれます。

辞書初期化、消費ビット、木の辺、ハッシュ探査、プレフィックス展開、スタック配信、出力・繰り返し作業を計上します。`work_remaining()` はコンテナー所有の累積台帳のためにコンストラクター作業を含みます。協調ポーリングは入力依存・非依存の両作業を対象にします。出力読み取りは最大 8192 バイトです。入力不足、型付きホストエラー、クォータ枯渇、キャンセル、不正なコード・木、後続データ、デコードサイズの不一致はインスタンスを終了させます。最初のエラーはペイロードを保持し、後続の読み取りは再開できません。完了したリーダーは追加作業を消費せず安定した EOF を返します。

ARC の必須ペイロード CRC-16 と完全な物理構造はコンテナーに属します。生デコードの成功だけでは内容を認証せず、ファイルシステム、パス、プロセス、隣接ファイル、公開の権限を与えません。
