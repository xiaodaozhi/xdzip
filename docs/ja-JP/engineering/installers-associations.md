# インストーラーとファイルの関連付け

[English](../../engineering/installers-associations.md) | [简体中文](../../zh-CN/engineering/installers-associations.md) | [繁體中文](../../zh-TW/engineering/installers-associations.md) | 日本語 | [Español](../../es-ES/engineering/installers-associations.md) | [Português (Brasil)](../../pt-BR/engineering/installers-associations.md)

Windows 11 x64 では Microsoft Store で **XDZip** を検索して Store 版をインストールまたは更新できます。Windows EXE またはポータブル ZIP、macOS パッケージ、Linux パッケージは[最新の GitHub リリース](https://github.com/xiaodaozhi/xdzip/releases/latest)からダウンロードします。2 つのチャネルは独立して公開されます。インストールするバージョンの掲載内容またはリリースノートを確認してください。

Windows MSIX はパッケージマニフェストで同じ拡張子を「プログラムから開く」の候補として宣言し、ユーザーの既定選択を奪いません。関連付けページには対象となる全種類が無効なスイッチとともに表示されます。現在の既定値は Windows の設定に表示されます。「既定のアプリ設定を開く」は `registeredAUMID` で現在のパッケージを開きます。ID の取得に失敗した場合は一般の既定アプリ選択画面を開きます。パッケージは通常インストール版の登録をパッケージ状態として読み取らず、UserChoice 値を書き込みません。実際のファイル起動、アイコン、共存とアンインストールには対象システムでの受け入れが必要です。[MSIX ビルド](../../engineering/developer-build.md#windows-msix-实验构建)を参照してください。

形式別のデザインとプラットフォーム対応は[ファイル関連付けアイコン仕様](../visual/file-association-icons.md)を参照してください。Linux はシステムの MIME アイコンを維持します。インストールは既定値や既存の登録範囲を変更しません。

MSIX の関連付けは、通常の Windows インストーラーと同じ正規 ICO フレームから抽出された形式別 PNG リソースを参照します。ZIP、7z、RAR とその他の対応形式は、文書アイコン、サイズプロファイルと透明な余白を維持します。アプリアイコンにはプレートなしの別のターゲットサイズリソースがあります。両セットはパッケージの `resources.pri` に索引化され、Store 掲載画像を変更してもインストール済みアイコンは置き換わりません。アイコンキャッシュと既定ハンドラーの選択は Windows が管理し、インストールがその選択を自動変更することはありません。

`v0.2.0` 以降のデスクトップパッケージと現在のソースビルドは、CLI を別の `cli/` ディレクトリ、macOS では `Contents/Helpers/cli/` に配置し、既存の GUI とファイル関連付けの入口を維持します。以前のリリースアセットにこの機能が遡って追加されるわけではありません。Windows インストーラーは任意選択のユーザー単位 PATH オプションを提供し、同名コマンドの競合を検出します。アンインストールは自身のインストールディレクトリだけを登録解除します。Mac/Linux では非公開 CLI の `setup` を明示的に実行します。独立 CLI パッケージも `setup` でユーザー単位のバージョンディレクトリと安定ランチャーをインストールし、シェル設定を変更しません。`setup --remove` は登録を解除し、確認用にバージョンディレクトリを残します。[CLI インストール契約](command-line.md#xdzip-build-and-command-installation)を参照してください。

以下のパッケージングコマンドは実験的な開発アーティファクトを生成します。公式 GitHub パッケージは[リリースプロトコル](release-protocol.md)、Store パッケージは [MSIX ワークフロー](../../engineering/developer-build.md#microsoft-store-msix)に従います。macOS の直接ダウンロードは Developer ID と公証なしの ad-hoc 完全性署名を使用します。対応システムは[サポートポリシー](support-policy.md)を参照してください。

現在のソースビルドは Windows インストーラーの発行元、Linux パッケージのメンテナー、更新ポリシーのベンダーとして `xiaodaozhi` を使用します。これらのメタデータ欄は発行元証明書による署名を代替せず、既存リリースは元のメタデータを維持します。

macOS の手動更新には対応する Release DMG を推奨します。app.zip の場合は、まず xdzip.app を展開してダウンロードフォルダーから移動し、実行中の旧バージョンを終了してから Applications 内のコピーを置き換えます。ダウンロードはインストールではありません。公証されていないパッケージではシステム警告が表示される場合があります。フォールバック条件は[ソフトウェア更新契約](software-update.md)を参照してください。

コンテキストメニュー、独立した操作ホストと自前の登録ライフサイクルは[ファイルマネージャー操作契約](shell-actions.md)を参照してください。コンテキスト操作は閲覧用のメインウィンドウを開かず、完了時に出力先フォルダーを既定で開きません。

## 共通ビルド入口

環境準備と手順は[開発者向けビルドガイド](../../engineering/developer-build.md)を参照してください。同じコミットのクリーンビルドとテスト後、`python3 scripts/desktop.py prepare --packaging` で固定資料を準備し、package と verify を実行します。通常開発では完全な CI スクリプトを直接使用しません。

Windows/Linux の `package --kind runtime|installer|all` はデプロイと監査のチェーンを共有し、既定値は `all` です。runtime がまずデプロイ済みディレクトリを生成し、installer は同じ output-dir の検証済み runtime から作成され、Linux では tar.gz も作成します。macOS はローカルの `all` 開発 DMG のみをサポートします。アーティファクトと受領記録は指定 output-dir、既定では build/package にあります。準備は固定パッケージングツールや資料をダウンロードする場合がありますが、xdzip やシステムコンパイラー・SDK を自動インストールしません。Windows は CRT/Inno Setup を準備し、Linux は事前インストール済みの patchelf と Debian ツールを必要とし、Mac はシステムのデプロイと ad-hoc 完全性ツールを使用します。

通常の `verify` は既存の runtime とパッケージを検証します。Windows は分離コピーで SDK 検索パスを消去し、Linux は分離ランタイムコンテナーを使用し、Mac は DMG の移動と Cocoa/Metal を検証します。既定ではインストール、アップグレード・ロールバック、関連付けのライフサイクルやユーザー既定値の書き込みを行いません。以下のインストール機構と使い捨て CI の検査は別のゲートであり、ランタイムの成功はこれらを代替しません。

## Windows

インストーラーはパッケージに含まれる元の Microsoft VC++ ランタイム契約を表示します。ライセンスページは対象コンポーネントを示して同意を求め、その後中英二言語の Windows-runtime-NOTICE.txt を表示します。ポータブルパッケージにも同じ元文書と説明を含めます。プロジェクト独自コードは Apache-2.0 のままであり、Qt とその他のコンポーネントの元ライセンスおよび置換権は変わりません。コンパイル前にハッシュと完全な説明を確認し、添付資料は同じ文章を保持します。[Windows ライセンス](windows-licensing.md)を参照してください。

ポータブルパッケージとインストーラーは同じデプロイ済みディレクトリを使用します。[deploy_windows.py](../../../scripts/deploy_windows.py) は windeployqt を呼び出した後、固定された Qt Quick Basic ポリシーに従い、FluentWinUI3、Fusion、Imagine、Material、Universal、Windows、スタイルからのみ参照される NativeStyle/Effects、qmltooling と .qmltypes を削除します。Basic、Controls impl、Templates、ランタイム QML と qmldir は残ります。Qt Widgets の qmodernwindowsstyle は引き続きネイティブコントロールに使用します。新しいデプロイディレクトリには DXC、DXIL、D3DCompiler を含めず、これらの名前がどこかに存在するとデプロイは失敗します。新しいデプロイには `opengl32sw.dll` を含めません。既存ルートの同名コピーは管理された準備領域で削除し、他の場所に残存するとデプロイは失敗します。新しいスタイルや Effects 機能を追加する場合はデプロイポリシーの更新と再検証が必要です。

Qt Quick は Windows で既定で Direct3D 11 を使用します。ハードウェアやドライバーの機能が不足する場合、Qt は Direct3D WARP にフォールバックすることがあります。これはソフトウェア OpenGL とは別です。新しいパッケージは `QT_OPENGL=software` や OpenGL バックエンドによる Mesa ソフトウェアフォールバックを保証しません。過去のパッケージとライセンス資料は変更しません。[Qt の Windows グラフィックス文書](https://doc.qt.io/qt-6.8/windows-graphics.html)は既定のデバイスと明示的に要求するソフトウェアデバイスを説明しています。

VC++ は[固定された出所とハッシュ](../../../scripts/windows-runtime.json)に基づき、公式 Microsoft x64 14.44.35211 ランタイムをアプリローカルにデプロイします。[準備スクリプト](../../../scripts/prepare-windows-runtime.py)は固定 WiX ツールで抽出し、EXE/MSI インストーラーを実行したり System32 からコピーしたりせず、すべての DLL とライセンス文書を検証します。必要な MSVCP/VCRUNTIME DLL、ライセンスと出所を提供し、ツール、CAB、MSI、未実行の vc_redist インストーラーは製品に含めません。Windows 10/11 は UCRT を提供します。アプリローカルランタイムは製品更新とともに維持する必要があり、システム全体のランタイム更新による置換には依存できません。[Microsoft のデプロイ方法](https://learn.microsoft.com/en-us/cpp/windows/choosing-a-deployment-method)を参照してください。

[デプロイ回帰](../../../scripts/test-windows-deployment.py)は削減とランタイム欠如の境界を確認します。[実際のランタイム検証](../../../scripts/verify_windows_runtime.py)はソフトウェア OpenGL DLL を拒否し、分離コピーにテスト DLL を追加し、SDK 検索パスを消去して、システム翻訳、設定の再起動、ネイティブタイトルバーと中英二言語の起動を確認します。描画の上書き設定を消去した後、既定の D3D11 シーングラフ初期化を確認し、WARP を明示要求して、実際に選択された Microsoft ソフトウェアデバイスを検証します。明示要求は障害時の自動フォールバックを証明せず、手動の視覚受け入れも代替しません。テストファイルは製品ディレクトリに入りません。この検証はクリーンな Windows でのインストール・アップグレード・アンインストール受け入れを代替しません。

build-windows-installer.py はクリーンビルドの deployed 監査のみを受け付け、各ファイルの SHA-256 を再確認します。固定された Inno Setup 6.7.3、公式インストーラーのハッシュ、ソースコミット、簡体字・繁体字中国語リソースとライセンス文書は[ツールチェーン設定](../../../scripts/installer-toolchain.json)を参照してください。コンパイラーは製品に入らず、通知にはライセンス文書を含めます。ウィザードは共有言語一覧の 10 言語をサポートします。

インストーラーは固定 AppId と PrivilegesRequired=lowest を使用し、管理者権限なしで既定では現在のユーザーの LocalAppData/Programs/xdzip にインストールします。メイン実行ファイル xdzip.exe はインストールルートにあり、Qt ライブラリはその隣に置きます。プラグイン、QML、翻訳と通知は必要なサブディレクトリを維持します。ショートカット、関連付けとアンインストール表示アイコンはルートを指し、versions/コミットハッシュの製品階層は作りません。コミットとバイナリのハッシュはインストールパスでなくビルドとインストーラーの受領記録に残します。Inno Setup の[累積アンインストールログ](https://jrsoftware.org/ishelp/topic_appendnotes.htm)は各インストールが所有するファイルを記録し、追加ファイルを再帰的に削除しません。設定と最近の項目は既存のユーザー設定ディレクトリに残り、インストーラーは削除しません。

新しい構成は監査済み相対パスと SHA-256 を持つサイズ制限付き install-manifest.txt を書き込みます。アップグレード前に旧マニフェストのパス、重複とサイズを検証し、クリーンアップパスのパス逸脱、デバイス別名と再解析ポイントを拒否します。廃止するファイルが変更されている、または検証できない場合は書き込み前にインストールを停止します。インストール成功後、旧マニフェストに記載され、新たに提供されず、ハッシュがまだ一致するファイルだけを削除します。空のディレクトリだけを削除し、追加物は残します。1 回のインストール内で完了イベントが繰り返されてもクリーンアップは 1 回のみです。クリーンアップ中に変更または使用中のファイルは再試行記録と非ゼロ終了コード 20 を伴って残ります。再試行記録を書けない場合は手動修復が必要です。トランザクション復旧や停電安全性は保証しません。このユーザー単位インストールは外部プロセスが同時にディレクトリを変更しないことを前提とし、パス・ハッシュの再確認はハンドルベースの悪意ある競合分離ではありません。

既存のバージョンディレクトリ構成は直接アップグレードできます。起動コマンドとショートカットはルートへ移り、設定と最近の項目の場所は維持されます。旧インストーラーは別の所有マニフェストを提供していなかったため、過去の versions/ ディレクトリは通常アンインストールまで残ります。Inno の累積ログは元々記録されたファイルを削除しますが、ディレクトリを再帰削除しません。ユーザーが追加したファイルは残ります。選択した旧バージョンを再インストールしてロールバックでき、古い QA フィクスチャは過去の構成を維持し、後でルート構成へ再アップグレードできます。新規インストールは versions/ を作りません。旧インストールディレクトリを自動で完全消去するものではありません。

製品はライフサイクル全体で名前付きミューテックス `Local\xdzip.desktop.running` を保持します。[AppMutex](https://jrsoftware.org/ishelp/topic_setup_appmutex.htm) は CloseApplications=no でインストール・アンインストールを阻止し、アプリを強制終了しません。FFI ハンドルの作成に失敗すると起動できず、プロセス終了時に解放されます。タスクの終了には既存の判断と Rust の終了待ちバリアを使用します。

通常の Windows インストーラーは HKCU にアーカイブ候補を登録します。自分が所有する ProgID、Applications の 2 項目、Capabilities、RegisteredApplications と所有する OpenWithProgids 値を書き込みます。HKLM、拡張子の既定値、保護された UserChoice/UserChoiceLatest と他アプリの候補には触れません。登録される各拡張子には `xdzip.Archive.ZIP` のような ProgID と割り当てられた ICO があります。従来の `xdzip.Archive` は直接開くコマンドを保持し、`Applications/xdzip.exe` とともに「プログラムから開く」では非表示です。アップグレードは既存の既定値との互換性を保ちながら、それらの旧推奨項目を削除します。Windows は `.tar.gz` のような複合ファイル名のアイコンを最後の拡張子で選択します。

通常インストール版は起動時とアプリ言語の変更成功後に、ZIP、TAR、TGZ、GZ、7Z、RAR、CAB、ISO、UDF の 9 つの主要 ProgID の説明を同期します。インストーラーは保存されたアプリ言語、または自動モードではシステム表示言語で説明を選びます。ウィザード言語は独立しています。実行中の同期前に、インストール ID、実行ファイル位置、マニフェスト、関連付けランチャーと既存の 9 つのオープンコマンドを確認します。登録が欠落または不一致なら変更しません。一部書き込みの失敗は次回の通常起動時に再試行できます。ポータブル、開発、分離設定を使用するテストプロセスではこの同期を実行しません。その他の登録済み拡張子はインストーラーが提供した説明を保持します。Explorer のキャッシュと選択された既定値によって表示が変わる場合があります。

使い捨て Windows CI はインストール済み製品の起動時の説明同期と、実行中の簡体字中国語・英語間の切り替えを検証します。ポータブルコピーと分離設定プロセスで書き込みがないことを確認し、9 つのアイコン、コマンド、他の候補と既定値が変化しないことも確認します。この自動チェックは Explorer や設定の表示に対する手動受け入れを代替しません。

すべての形式 ProgID の引用符付きコマンドは `xdzip-association.exe -- "%1"` を起動します。その Applications 登録には完全な SupportedTypes があり、「プログラムから開く」に xdzip アプリ項目を 1 つ表示します。ランチャーは同じブランドのアプリ ICO と固有の OriginalFilename・製品バージョンリソースを内蔵します。アプリアイコンは形式別文書アイコンと別に検証してください。文書 DefaultIcon は実行ファイルのアプリリソースを代替できません。小さな GUI ランチャーは 1 つのファイル引数を受け取り、専用スレッドで COM シングルスレッドアパートメントを初期化し、コマンドインタープリターなしで明示的な `xdzip.Archive` クラスを指定した ShellExecuteEx を通じて既存のオープンコマンドに委譲します。呼び出し後に COM を解放します。旧バージョンへのロールバックは共有項目を更新するため、形式別候補もロールバック後のプログラムを指します。COM 初期化失敗、入口の欠如、不正な引数、システムの拒否は、別アプリを試したり既定値を変更したりせず非ゼロを返します。これはロールバック後も現在のインストールディレクトリにランチャーが残ることに依存し、インストール・ロールバックと累積アンインストールには実際のテストが必要です。

インストーラーは共有 ProgID と登録された形式別 ProgID に REG_NONE として `AllowSilentDefaultTakeOver` を設定します。Windows はこれらを明示的な「プログラムから開く」候補として引き続き提示できます。インストーラーは限定されたネイティブレジストリ呼び出しで、作成済みの所有キーに値を設定します。失敗した場合はインストールを停止してハンドルを解放します。[Windows ProgID の規約](https://learn.microsoft.com/en-us/windows/win32/shell/fa-progids)を参照してください。

通常インストーラーと MSIX は[形式レジストリ](format-registry.md)から Windows の「プログラムから開く」候補を生成します。この対応には主要な ZIP、TAR、TGZ、GZ、7z、RAR、CAB、ISO、UDF と追加の登録済み拡張子を含みます。`.gz` は内容によって独立 GZIP または TAR.GZ に振り分けられます。汎用の `.img`、`.001`、`.rNN` は明示的なオープンまたは対応する入口用です。関連付けはシステムから xdzip への経路を提供するもので、リーダーは引き続きファイルを調査し、操作の形式とソース要件を適用します。

## Ubuntu 24.04

build-linux-installer.py は同じ検証済みディレクトリから .deb を作成します。非公開ステージングディレクトリは出力パスで区別するため、同じパッケージ名を異なる候補ディレクトリで再ビルドしても既存のステージングを上書きしません。パッケージ名は xdzip、バージョンは製品チャネルとコミットに結び付き、アーキテクチャは amd64 です。システム依存関係は実際のデプロイマニフェストと desktop-database・ロックツールから決まり、glibc は 2.39 以上です。Qt/QML/プラグインと通知は /opt/xdzip/versions/ にあり、/usr/bin/xdzip は引用符付きの固定先転送入口です。dpkg が旧パッケージファイルを置換・削除し、ロールバックには元の .deb の保持が必要です。

インストールされた [xdzip.desktop](../../../apps/desktop/packaging/linux/xdzip.desktop) はパッケージの MIME 候補を宣言します。ZIP と選択された別名、TAR とフィルター付き TAR、独立圧縮ストリーム、7z、RAR、CAB などのアーカイブ形式、ISO/UDF イメージが含まれます。`%f` は単一ファイル起動を要求し、`--` は引数境界を示します。パッケージは `*.udf` の MIME 宣言を提供し、汎用イメージとバイナリ型には触れません。インストールと削除は MIME・デスクトップデータベースを更新しますが、`mimeapps.list` の書き換え、ユーザー既定値の変更、システム MIME アイコンの置換はしません。アンインストールは所有ランチャー、アイコンとランタイムファイルを削除し、ユーザー設定を保持します。

DEB は [AppStream カタログ項目](../../../apps/desktop/packaging/linux/xdzip-local.yml)を Ubuntu App Center から読み取れる `/var/lib/swcatalog/yaml/xdzip-local.yml` にインストールします。この項目はパッケージ名 `xdzip` と `xdzip.desktop` を関連付け、インストール済みパッケージがアプリ一覧に表示できるようにします。dpkg は XDZip のアンインストール時にカタログファイルを削除します。

インストール済み製品は /run/xdzip/usage.lock の共有 flock を保持します。メンテナンススクリプトは先に非ブロッキングの排他ロックを取得し、実行中プロセスがあれば失敗します。スクリプトは root 所有の /run/xdzip にインストール中ゲートを設定し、製品はロック取得後に再確認して dpkg フックの間に起動することを防ぎます。シンボリックリンクや不正な所有者・権限を拒否し、QFile を閉じるとロックを解放します。tmpfiles.d はシステム起動時にランタイムロックを準備します。SDK 開発アプリには影響しません。

成功時と dpkg 中止時の経路はゲートをクリーンアップします。中断や停電では未完了トランザクションが残る可能性があります。sudo dpkg --configure -a を実行し、実際のエラーを修正してください。起動できない状態はインストール成功ではありません。スクリプトはユーザーディレクトリを再帰的に削除せず、アーティファクトは build/ または CI にのみ生成します。

## macOS とファイルオープン

メインアプリと配布パッケージは Info.plist で文書と ICNS を Viewer/Alternate として宣言し、[既定の所有権を主張しません](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html)。開発・テストビルドは既定で Viewer/None であり、システムの「プログラムから開く」候補に入りません。主要な開発パッケージまたは配布ビルドでは `-DXDZIP_MACOS_HANDLER_RANK=Alternate` を明示的に設定する必要があります。既定値はユーザーと Launch Services が決定し、アプリは能動的に変更しません。開発検証用コピーの一時登録は[Mac メンテナンス方法](macos-deployment.md)に従ってクリーンアップし、既存アプリとユーザー既定値を保持します。

CAB、ISO、UDF も同じ Viewer ロールを使用します。ISO は `public.iso-image` を使用します。アプリは `.img` や汎用 `public.disk-image` を主張しません。Viewer は Launch Services の関連付けを示し、利用可能な操作は[形式バックエンド](native-codecs.md)が決定します。別の [ISO 作成プロファイル](iso-creation.md)は新規イメージを書き込めます。

文書宣言は[形式レジストリ](format-registry.md)のすべてのシェル候補の最後の拡張子を対象とし、対応するバンドル ICNS を使用します。複合拡張子は最後の拡張子の種類を共有します。たとえば `.tar.gz` と `.gz` は GZIP の既定値を共有し、`.tgz` はシステムの圧縮 TAR 種別を使用します。Finder のキャッシュ、選択された既定値とシステムの種類認識が実際の表示に影響します。

macOS の RAR、CAB、UDF の取り込み型は実際のファイルを識別できるよう `public.data` に準拠する必要があります。CAB はシステムの `com.microsoft.cab` と互換用の `com.microsoft.cab-archive` の両方を宣言します。設定は実際の優先型がこのいずれかならその型を照会・変更し、そうでなければ互換 ID を使います。UDF Viewer は `LSItemContentTypes` なしで `.udf` 拡張子を宣言し、古いインストールの無効な UTI 宣言がまだ使われていても実ファイルから候補を発見できるようにします。Apple はこの[拡張子宣言キー](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html)を非推奨にしているため、対応 macOS バージョンで引き続き検証します。設定は実際に認識された `.udf` 型を照会・変更し、取得できない場合は既存 ID にフォールバックします。インストールや登録は既存の既定値を能動的に上書きしません。ハンドラーが存在しなかった場合、Launch Services が[暗黙の規則](https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/LaunchServicesConcepts/LSCGlossary/LSCGlossary.html)により新しい候補を現在のハンドラーとして解決することがあります。一時登録の削除で元の状態を復元する必要があり、この解決はアプリがユーザー設定を書いたことを意味しません。

FileOpenRouter は QML より前に [QFileOpenEvent](https://doc.qt.io/qt-6.8/qfileopenevent.html) を受け取り、ローカルファイルのみを受け付け、既存のオープン・アクティブ化ルーティングを再利用します。GUI コマンドラインの `--` 以降の引数はファイルパスであり、診断フラグとの混同を避けます。保留意図は最大 128 件をキューに入れ、実行中タスクを先取りしません。1 つのログインセッションの通常製品プロセスはインスタンスを共有し、複数ファイル要求は順に開いて最後のものをアクティブにします。タブとウィンドウの動作は[アプリケーションセッション契約](application-sessions.md)を参照してください。

起動引数は QML 読み込み前にキューへ入ります。メインウィンドウは非表示で開始し、コントローラー接続時に最初の利用可能な要求を、ウィンドウの可視性を待たずに直ちに提出します。ウィンドウは初期イベントキューで表示され、プラットフォームの起動イベントも同じ経路を使用します。外部オープン中はセッション変更前にウェルカム項目を隠し、最初のフレームやセッション置換時にウェルカム画面が一瞬表示されるのを防ぎます。キャンセルまたは失敗時はウェルカム画面を復元し、成功時は実際の一覧を表示します。[読み込み状態](../ux/welcome-opening.md)を参照してください。

macOS ネイティブ起動では別途 AppKit の NSApplicationDidFinishLaunchingNotification を待ち、非表示の間にそのバッチのキュー済み Qt ファイルイベントを処理し、その後ウィンドウを表示します。通知とキュー済みコールバックはメインウィンドウの寿命に限定され、Qt のアプリケーションデリゲートを置換せず、固定ミリ秒の遅延も使用しません。実際の Launch Services 回帰で以前ウェルカム内容が 1 フレーム表示され、修正後の要件はゼロです。check-macos-open.py はローカルと Mac CI で argv とネイティブオープン経路を実行し、JSON・ログのみを保持し、アプリパッケージを生成またはアップロードしません。

## 自動検証と限界

3 プラットフォームの CTest は起動前のファイルイベント、非ローカル URL の拒否、読み込み中のキューを検査します。明示的な XDZIP_ASSOCIATION_PROBE と分離設定は CI 専用です。通常のオープンフローでプロジェクト所有の 100,000 項目 ZIP を読み取り、件数とビルド ID を記録し、ソースパスの記録や抽出をせず正常終了します。

現在の関連付けプローブは少なくとも 1 フレームが実際に表示されるのを待ち、フレームごとにウェルカム内容の可視性を記録します。現在の製品要件では Windows ShellExecuteEx と Linux GIO の presented_frames は 0 より大きく、welcome_frames は 0 です。固定された旧製品は過去のプローブ能力に従ってテストし、旧バイナリが新しい初回フレーム数を持つように装ってはいけません。

Windows ネイティブ CI は QA 変体 1 をインストールし、2 にアップグレードして 1 にロールバックした後、実際の配布パッケージをインストールします。ShellExecuteEx は自前の登録クラスで中国語、空白とアンパサンドを含むパスを開き、既定値と UserChoice の不変、使用中の置換拒否、アンインストール時の設定・追加ファイル・他候補の保持を確認します。Linux は SDK、システム Qt、コンパイラーのないネットワーク無効コンテナーで同じ dpkg ライフサイクルを実行します。UID 1000 の製品が GIO デスクトップランチャー経由で実際に 100,000 項目を開き、MIME、既定値、ロック、アンインストールと purge を確認します。

Linux リリース検証は分離コンテナーユーザープロファイルで MIME 既定値も変更し、GIO がサンプルのコンテンツ種別を xdzip に解決した場合に `gio open` を使用します。宣言されたすべての MIME 既定値を確認し、別のハンドラーも試して元の既定値を復元します。Linux と macOS の自動ファイルオープン検査は入力なしで開けるサンプルを使用します。AES Crypt のブラウザーテストはオープン時のパスワード要求と認証済み読み取りを検証します。システム設定と他のデスクトップ環境には別の検証が必要です。

QA 変体は現在検証済みのバイナリを共有し、インストール機構をテストするためにテスト用パッケージバージョンとディレクトリのみを変えます。リリースアーティファクトではなく、異なる製品バージョン間の実データ移行を装いません。設定スキーマは現在 1 で、インストールメタデータは両プラットフォームでその値を記録します。古いインストーラーは新しいスキーマを宣言するインストールの上書きを拒否し、今後の移行では契約の更新が必要です。

後続の故障注入は QA 変体 2 のみに許可され、postinst configure 中に一度失敗させます。本番にこの分岐を含めてはいけません。コンテナーは半設定状態、ゲートによる起動阻止、設定の保持を実際に検証し、その後 dpkg --configure -a で復旧して GIO から実ファイルを開きます。これは再現可能な設定障害であり、機器の停電ではありません。別の設定互換性チェックは保持した元の設定コンポーネントと現在のコンポーネントをコンパイルし、同一スキーマの設定を往復させます。元の入力は旧 main 履歴とは独立したファイルごとのハッシュで固定され、完全なインストーラーデータ移行を装いません。

完全な製品互換性は、prepare-previous-product.py が使い捨て Windows/Linux CI ホストで固定された互換スナップショット（元の 4cf0f8c 由来）から完全な製品ソースをビルドして別途検証します。detached worktree で実際のクリーンな ID を保持し、期限切れになりやすい旧 Actions バイナリをダウンロードせず、現在の固定 SDK で過去製品の QA インストーラーをビルドします。過去製品をインストールして実際に開き、現在の製品をインストールして revision の変更と設定バイトの保持を確認し、過去製品へロールバックして再度開き、データを確認します。これは 2 つの完全なソースコミット間の同一スキーマ互換性を証明し、過去の署名済み元パッケージ、存在しないスキーマ 2 の移行、機器の再起動を装うものではありません。過去インストーラーは QA 専用で製品アセットとしてアップロードせず、受領記録は両バイナリとインストーラーの SHA-256 を結び付けます。

windows-install-lifecycle.json、linux-install-lifecycle.json とパッケージハッシュが実際の証拠です。Explorer/Finder での実際のダブルクリック、既定選択 UI、再起動後のサービス・キャッシュ、正式署名がない場合の警告、GPU とデスクトップの検査は手動チェックリストに従います。自動スクリプト自身ですべての INSTALL-01/ASSOC-01 を合格にしてはいけません。既存の手動結論は [WP-12 #5](https://github.com/xiaodaozhi/xdzip/issues/5)にあり、保留テンプレートの再生成は受け入れを再開しません。今後のスキーマ移行には追加の実際の互換性ケースが必要です。

使用中の置換保護に関する Windows の非タスクプローブはトレイを無効にした分離設定を使用し、その構成で `CloseMainWindow` が通常終了を行うようにします。その他の関連付けオープンプローブは既定のトレイ設定を維持し、明示的なシャットダウンバリアで終了します。インストール保護プローブは非表示ウィンドウをプロセス終了失敗と誤認したり、通常経路を強制終了して終了検証を回避したりしてはいけません。

Windows 更新プロトコルフィクスチャと実際の Qt 更新フィクスチャには、関連付けランチャーと 9 個すべての文書 ICO が含まれます。必須ペイロードが不足したインストーラーは検査を通過できません。プロトコルフィクスチャの小さな C メインプログラムと関連付けコマンドは更新引き渡しのみを検証します。組み込みアプリリソース、ネイティブ候補と実ウィンドウは完全な Qt 製品で別途確認し、結論を混同しません。

## 長期互換性ベースラインの入力

実際のアップグレード・ロールバックは書き換えられた main 履歴ではなく、固定された旧製品の完全なソースを使用します。`prepare-previous-product.py` は独立した `codex/installer-compat-baseline` ブランチの単一ルートソーススナップショットを固定します。このブランチはビルドと回帰に必要な元のソースとアセットのみを含み、旧 main の親、実行報告、ワークフローを含みません。スナップショットの `COMPAT-BASELINE.json` は元のソースコミットとツリー ID を記録します。main へマージしたり、リリースパッケージや現行製品の受け入れ結論として扱ったりしてはいけません。

ビルド後の CLI ID はスナップショット自身の固定 SHA に一致する必要があり、受領記録は元のソース ID を別に記録し、元のリリースバイナリを装ってはいけません。設定コンポーネントも元の小さなソースファイル 3 件を永続的テスト入力として保持し、ファイルごとのハッシュで固定します。双方向の読み書きと将来スキーマの拒否はネットワークや過去コミットに依存しません。これらの回帰入力を現在の実装に合わせて変更せず、新しいベースラインは別途審査し、必要な出所を保持します。

固定スナップショットは独立更新ヘルパーより前のもので、そのソースもバイナリも含みません。`--qa-historical-revision` を渡すのは `prepare-previous-product.py` のみです。デプロイ・パッケージングスクリプトは、使い捨て CI、完全な固定 SHA と実際のクリーンな製品 ID が同時に一致することを要求します。Linux はさらに過去バージョンモードを要求し、現在の QA 変体との混在を禁止します。Windows は旧製品のバージョンコマンドを直接実行して ID を確認し、Linux は独立デプロイ監査の ID と全ファイルハッシュを使用します。受領記録は過去ソースにヘルパーがないことを明示し、現在のヘルパーを注入せず、存在しない Linux ヘルパーの polkit 認証をインストールしません。通常製品と現在の QA 変体は引き続き独立ヘルパーを提供・検証する必要があり、`--qa-legacy-version` だけでは欠如を許可しません。

## Debian バージョンの移行

最初の公開プレリリースから Debian epoch 1 を使用します。形式は `1:<semantic-version mapping>+git<commit>`、たとえば `1:0.1.0~alpha.1+git...` です。dpkg の規則では epoch がないと過去の `0.1.0~dev.9` が alpha.1 より後に並ぶため、旧マッピングをそのまま維持できません。epoch はシステムパッケージの順序付け専用であり、製品 UI、バージョンタグと release.json は元のセマンティックバージョンを使用し続けます。後続の Debian パッケージも epoch 1 を保持し、alpha、beta、rc、stable の順序は引き続き上流バージョンで表します。[Debian Policy](https://www.debian.org/doc/debian-policy/ch-controlfields.html#version)を参照してください。

実際の過去製品フィクスチャは CI 専用 `--qa-legacy-version` で epoch のない元の ID を維持します。アップグレード問題を隠すため旧パッケージの順序を変更してはいけません。現在のパッケージは実際の dpkg アップグレード、ロールバックとインストールライフサイクルの受け入れを通過する必要があります。ユーザー設定と外部の既定関連付けは元の契約を維持します。

## 設定の既定アプリ

設定は生成された形式データを使用して関連付け拡張子をグループ化します。編集可能なスイッチはプラットフォームサービスとインストール ID に依存します。Windows は変更をシステムの既定アプリに委ね、UserChoice を書き込みません。MSIX はスイッチを無効のままにし、パッケージのシステム設定項目を使用します。Linux は対応拡張子を MIME 型に対応付け、ユーザー既定値に `xdg-mime` を使用し、既定値を解除する際はインストール済みの代替を提供します。

macOS の設定は、インストール済みバンドルの Viewer/Alternate 宣言が対象とする各システム種別のスイッチを有効にします。有効なスイッチは以前の既定がない種別でも xdzip を既定として要求できます。macOS が確認を求める場合があります。コールバック成功後、設定は Launch Services が新しい既定値を報告するための短い時間を確保します。システム照会で xdzip を確認すると、アプリはシステムコンテンツ種別ごとに以前のアプリのバンドル ID をローカルに記録します。スイッチをオフにすると、macOS がその以前のアプリをまだ互換として一覧表示している場合はまずそれを要求します。保存された互換アプリがない場合や復元が失敗した場合、設定はインストール済みの互換代替アプリを提示します。代替がない場合はスイッチの横にその旨を説明します。キャンセルすると現在の選択を保持し、表示状態は新たなシステム照会に従います。Viewer/None ビルドでは変更を無効にします。

自動言語モードでは Windows Setup が現在のユーザーのシステム UI 言語を使用して関連付け説明を選択します。繁体字中国語が優先される場合は繁体字中国語、非対応言語では英語（米国）を使います。対応する手動選択は優先されます。Setup は自動モードを保持し、アプリが起動時にシステム言語を解決して所有する説明を同期できるようにします。
