# 自社 Rust フォーマットとアルゴリズムの契約

[English](../../engineering/independent-rust-codecs.md) | [简体中文](../../zh-CN/engineering/independent-rust-codecs.md) | [繁體中文](../../zh-TW/engineering/independent-rust-codecs.md) | 日本語 | [Français](../../fr-FR/engineering/independent-rust-codecs.md) | [Español](../../es-ES/engineering/independent-rust-codecs.md)

この契約は内蔵 Rust フォーマット実装、対応プロファイル、互換性の検証方法を説明します。許可された操作は[フォーマット登録表](format-registry.md)、プロセスのルーティングは[ワーカー契約](native-codecs.md)を参照してください。

<a id="实现边界"></a>

## 実装の境界

内蔵宣言と製品入口の対応付けには[フォーマット登録表](format-registry.md)を使用します。宣言は能力の候補であり、実際のコンテナーレコード、ホスト方針、プラットフォームのサポートによって絞り込まれます。コンテナー検証を代替せず、ファイルへの権限も与えません。

コンテナーの解析、エンコード、デコードと圧縮アルゴリズムには独立した Rust 実装を使用します。採用された汎用暗号、文字エンコーディング、システム、ブリッジの基盤ライブラリーは使用できます。第三者のフォーマットライブラリー、アルゴリズムライブラリー、コマンドラインツールは独立したテスト参照に使えますが、移行済みフォーマットの製品ランタイム依存関係にはなりません。直接依存関係を取り除くだけでは置換を証明できません。通常／ビルドの推移依存集合と提供ファイルを確認してください。

形式の識別後、アプリケーションは内蔵実装を選択します。デコード失敗時に別のバックエンドへ切り替えません。ZIP、TAR、TAR.GZ、7z は作成と、条件を満たす既存アーカイブの書き換えが可能です。RAR、CAB、UDF は読み取りのみです。ISO の読み取りはワーカーを使い、[ISO9660/Joliet ライター](iso-creation.md)は Rust ホストで新しいデータイメージを作成します。既存 ISO イメージは書き換えられません。各形式には明示的なプロファイルとリソース制限があります。例えば RAR7 LZ の相互運用には独立した圧縮ストリームのサンプルが必要です。

ドメイン層、Qt ブリッジ、公開 codec トレイトはそれぞれの所有権を維持します。バックエンドは出力先パスを受け取らず、ファイルを公開できません。生の名前バイト、物理 EntryId、重複エントリー、エンコーディング解決、ソース識別、ボリューム認可、パスの事前検査、一時配置、検証、コミットは既存の技術契約に従います。共通アルゴリズムは一度だけ実装し、各コンテナーがフレーミング、ブロック境界、辞書のリセット、検証セマンティクスを独立して処理します。ネイティブバックエンドの Rust 移行でも、ワーカーのキャンセル、終了、リソース管理を維持します。

読み取り専用 ASAR リーダーは[ASAR 契約](asar-containers.md)に従い、順序付きで上限のある JSON/Pickle メタデータ、共有保存範囲、任意の SHA-256 検査を扱います。汎用 JSON とハッシュの基本要素は外部ファイルへのアクセスやアプリケーション実行を許可しません。

読み取り専用 UU/UUE/XXE リーダーは[テキストエンベロープ契約](text-envelopes.md)に従います。カウント付き文字集合、Base64、メンバー識別、終端検証は独立した Rust コードであり、参照ストリームエンコーダーは実行依存集合の外に置きます。

Unix compress と TAR.Z は、[compress 契約](compress-streams.md)で規定した独立した制限付き LZW 基本要素と制御されたストリーム／TAR 構成を再利用します。コード、辞書の占有、グループ整列、作業量とメモリーの受理は第三者圧縮ランタイムなしで実装します。

## ソースと独立実装

共通 LH4–LH7 と LArc LZS/LZ5 の生デコーダーは [LHA ワイヤー形式とアルゴリズム契約](lha-containers.md)に従います。コンテナー方式、CRC と製品への受理は別々に評価し、生デコーダーだけでは登録済みアーカイブ機能を許可しません。共通の正準プレフィックス実装は各形式固有の最大深度と単一シンボル規則を維持します。

まず公式技術文書からフィールド、状態遷移、数値範囲、エラー動作、テストベクターを定義し、その後にコードを書きます。参照実装は動作理解の補足に限り、逐行の言語翻訳、名前を変えたコピー、構造の移植、コメントのコピーは行いません。仕様識別子と定数に対応する節を記録し、明示的な数学規則からの表生成を優先します。テスト参照のソースとライセンスは製品依存関係とは別に管理します。

参照ソースを見た開発者は厳密なクリーンルーム開発を主張しません。ソース分離が必要なモジュールでは、解析者がコード表現を含まない動作仕様を参照実装を見ていない実装者に渡します。参照ソース、文書、テストデータのライセンスは Rust で書き換えても消滅しません。過去の提供物と移行中の依存関係は引き続き義務を満たします。

公式 RAR 技術説明は不完全です。デコーダーアルゴリズムの不足を記録し、専用のライセンス審査を行う必要があります。RAR エンコーダーを開発したり、UnRAR の制限を RAR 圧縮アルゴリズムの再構築許可と解釈したりしません。公開仕様中の独自拡張、特許通知、再頒布条件は別途審査します。独立した著作であっても法的リスクはなくなりません。

## TAR レコード仕様

DEB の読み取り専用 common-ar エンベロープは、プロジェクト所有の制限付きサブソースを通じて同じ TAR と制御フィルター実装を構成します。生／control／data のエクスポートビュー、共有の入力クォータとデコードクォータ、スナップショット投影は [DEB 契約](deb-containers.md)に従います。パッケージインストーラー、スクリプト実行、第三者アーカイブランタイムは導入しません。

独立レコード層は `xdzip-codec-tar/src/record.rs` です。レイアウトは [POSIX pax ustar と pax 交換形式](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/pax.html)、GNU 拡張は [GNU tar 形式説明](https://www.gnu.org/software/tar/manual/html_node/Standard.html)に従います。参照ライブラリーの内部や非公開 API は使用しません。

- レコードは 512 バイトです。ヘッダーチェックサムは 8 バイトのチェックサムフィールドを空白として扱う符号なしバイトの合計です。名前、サイズ、時刻、種別、ustar プレフィックスを規定オフセットから読みます。GNU ヘッダーのプレフィックス位置は ustar パスプレフィックスではありません。
- 通常数値は範囲内の 8 進数と非負 GNU base-256 を受理します。負値と u64 オーバーフローは拒否します。不正な時刻はペイロード位置を変えず表示上は不明にします。データは 512 バイトにパディングし、終端には少なくとも 2 個の全ゼロレコードと、その後予算内の全ゼロパディングのみが必要です。
- PAX の長さには自身の 10 進桁、空白、キー／値、改行を含みます。長さは境界を越えず前進し、キーは空でなく、レコードは改行で終わり NUL を含みません。ローカル path、size、mtime、hdrcharset は既存の解釈を維持します。GNU 長名とグローバルコメントの制限は [TAR/GZIP 契約](tar-gzip.md)を参照してください。
- 作成では ustar を書き込み、非 ASCII または長すぎる名前はローカル PAX UTF-8 パスを使用します。8 進数範囲外のサイズと時刻は、通常ヘッダーに表現可能なプレースホルダーを置き PAX フィールドを使用します。拡張データは最大 64 KiB です。固定した入力サイズを厳密に読み、その後最大 1 バイトを調べます。増大または縮小は失敗です。
- 書き換えでは通常ヘッダーの所有者、モード、時刻などの許可されたメタデータを維持します。名前変更はパスと文字セット宣言を更新し、チェックサムを再計算します。PAX size がデータ長を制御し、通常ヘッダーのプレースホルダーでデータを切り詰めてはいけません。不正なヘッダー／拡張、終端レコードの欠落、リソース超過はホストの公開前に失敗します。

`tar` は独立した開発テストの読み書き参照専用です。Foundation は製品依存集合を[依存関係方針](../../../scripts/rust-codec-policy.json)に照らし、tar、filetime、廃止した圧縮ライブラリーの TAR 実装への再導入を禁止します。ロックファイルには開発テスト参照が残り、それだけでは製品からの到達可能性を示しません。

## 共通 Deflate と GZIP の仕様

通常 GZIP と制御された TAR フィルターは `xdzip-codec-stream` を共有します。ホストでの命名、クォータ、ストリーム全体の検証、作成制限は[単一ファイルストリーム契約](single-file-streams.md)に従います。

`xdzip-compression` は第三者の製品依存関係を持ちません。形式は付録のサンプルコードをコピーせず [RFC 1951 §3](https://www.rfc-editor.org/rfc/rfc1951) と [RFC 1952 §2.3](https://www.rfc-editor.org/rfc/rfc1952)に従います。長さ、距離、追加ビット数は仕様のワイヤーフォーマット表であり、CRC ルックアップ表は IEEE 多項式からコンパイル時に生成します。

共通公開インターフェースは `DeflateReader`、`DeflateWriter`、`GzipReader`、`GzipWriter`、増分 `Crc32` です。ZIP と GZIP は同じ Deflate codec を使います。生ストリームリーダーは許可された圧縮範囲のみを読み、実消費とバッファーの先読みを区別し、BFINAL の後かつ実消費が圧縮サイズと正確に等しい場合のみ成功 EOF を返します。出力サイズや CRC が一致してもストリーム終端の代わりになりません。範囲内の第 2 ストリームや末尾の不正データは拒否します。

`DeflateReader::with_dictionary` は許可された最大 32 KiB の履歴を時系列順に受け取り、一致ウィンドウのみを初期化し、履歴を新しいストリーム出力として出しません。通常の ZIP/GZIP 生成は引き続き空のウィンドウから始まります。CAB `MszipDecoder` は [MS-MCI](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-mci/27f0a9bf-9567-4e40-ad66-6ae9ab9d2786)に従ってこのインターフェースを再利用します。各 CK フレームは Deflate ビットストリームをリセットしつつ論理フォルダーの直近 32 KiB を保持します。圧縮フレームは最大 32,780 バイト、出力は最大 32,768 バイトで、正確なサイズと完全な生ストリーム EOF が必要です。完全なフレームの合格後にのみ履歴を更新し、失敗後のフォルダー使用や `finish` 後のフレーム追加は行いません。共通アルゴリズムは CAB の物理断片チェックサムやボリュームチェーンを検証せず、独立コンテナーが担当します。CAB 製品切替と他方式の受け入れは [#48](https://github.com/xiaodaozhi/xdzip/issues/48)を参照してください。

- デコードは Store、固定 Huffman と動的 Huffman を扱い、ブロック間で 32 KiB のリング履歴を保持し、重複する一致を許可します。予約ブロック種別、LEN/NLEN 不一致、過剰な表、許されない不完全表、終端マーカー欠落、範囲外の繰り返し長、予約シンボル、履歴前の距離を拒否します。
- エンコードは制限付きハッシュチェーン LZ77、頻度から構築する正準 Huffman コード、コード長ランレングス符号化を使用します。深さが 15 を超える場合は長さを切り詰めず固定ツリーを使用します。レベル 0 は最大 65,535 バイトの保存ブロックを出力します。レベル 1/6/9 は最大 2 MiB のブロックを候補探索上限 4/32/128 でエンコードし、効果が不十分なら保存ブロックに分割して非圧縮性データの膨張を避けます。エンコード履歴はブロックごとに再構築し、圧縮率やバイト列が参照ライブラリーと一致するとは保証しません。
- デコードの中間状態はウィンドウと制限付きコード表で構成し、エンコードの中間状態は単一ブロック上限で制限します。いずれもアーカイブ全体を収集しません。ホストは引き続き入力、デコード作業、出力のクォータを計上します。制限付きエンコードブロック後に制御を返し、共通アルゴリズムはスレッドやファイル権限を追加しません。
- GZIP はマジック、方式、予約フラグを検証し、extra、name、comment、任意のヘッダー CRC を扱います。各メンバーヘッダーは最大 64 KiB です。各メンバーの CRC-32 と ISIZE modulo 2^32 を検証し、すべてのメンバーを一つの TAR ストリームに連結します。EOF まで読み、切り詰め、不正トレーラー、メンバー以外の不正データを成功終端にしません。
- ライターは成功した finish の場合のみ最終ブロックとトレーラーを書き、Drop は何も書きません。出力失敗後は成功ストリームとして続行できません。メモリーバッファーは公開権限を与えず、ホストは完全な再検証後にのみコミットします。

固定シードによる限定的な変異テストが証明するのは実際のカバー範囲だけで、長期ファジングではありません。エンコード性能、圧縮率、3 プラットフォームの結果は別々に記録します。今後の最適化で整合性やクォータ検査を弱めてはいけません。

## ZIP レコードとパスワードラッピングの仕様

ZIP EOCD、ZIP64、中央／ローカルヘッダー、追加フィールド、デスクリプターは [PKWARE APPNOTE](https://www.pkware.com/documents/casestudies/APPNOTE.TXT)、AES ラッピングは [WinZip AE-1/AE-2 仕様](https://www.winzip.com/en/support/aes-encryption/)に従います。コンテナー、名前拡張、レコード位置、codec 構成、認証境界を独立して実装します。汎用暗号基本要素は[依存関係の採用](dependencies.md)に従って使用し、RAR エンコーダーや追加の独自 ZIP 暗号拡張は実装しません。

- 物理的な中央レコードを個別に保持し、重複名を統合しません。終端レコードは完全で、件数／サイズ／オフセットが整合している必要があります。分割ボリュームの正規化前後の両方で、EOF を正確に覆う終端レコード候補が複数ある場合は曖昧として拒否します。コメント内の埋め込み終端レコードで実際のディレクトリーを隠せません。ZIP64 センチネルはフィールドが実際に現れる順序で解釈します。従来終端レコードの 2 つのディスク番号と 2 つの件数はそれぞれ独立して 0xFFFF プレースホルダーを使用でき、単一ボリュームかどうかは ZIP64 値を読んでから判定します。プレースホルダーでない値は対応する実値とすべて一致する必要があります。破損または重複する重要フィールドと、ホストが正規化していないマルチディスクメタデータを拒否します。スキャンは上限付きメタデータを表示し、大きな宣言値は正確な u64 のまま保持し、ペイロード段階で範囲を再検査します。
- 各タスクのメタデータ読み取り予算は 64 MiB です。その後のローカルヘッダー、デスクリプター、圧縮データ、暗号文、パスワード再試行は一つの累積 20 GiB 入力予算を共有します。ペイロード処理時に名前やスナップショット識別を再推測してはいけません。実出力はまず一時配置し、完全な読み取りと検証の成功後にのみホストがコミットします。
- エントリーごとにローカル／中央の名前、重要フラグ、方式、CRC、サイズ、AES プロファイル、ZIP64 幅を確認します。データと任意のデスクリプターは次のローカルレコードと中央ディレクトリーより前に終わり、他のレコードに越境してはいけません。Store は正確なサイズと CRC、Deflate はさらに厳密な生ストリーム EOF を検証します。署名の有無を問わず 32/64 ビットデスクリプターのフィールドを照合します。CRC が署名と等しい場合に署名と誤認してはいけません。
- AES-256 は 16 バイトのランダムソルト、形式で指定された PBKDF2-HMAC-SHA1 パラメーター、2 つの 32 バイト鍵、2 バイトのパスワード検証値を使います。CTR はリトルエンディアンのブロックエンコードで 1 から始まります。暗号文のみの HMAC-SHA1 を計算し、先頭 10 認証バイトを検証します。AE-1 は CRC も検証し、AE-2 は宣言 CRC がゼロである必要があります。認証失敗は整合性エラーであり、確定的なパスワード誤りに見せかけてはいけません。
- パスワードはホストから借用したままで、フォーマット層は保存せず表示もしません。導出鍵とストリーム状態はゼロ化する寿命を持ち、AES/HMAC/SHA1 は基盤ライブラリーの消去機能を有効にします。過去の Qt、入力方式、CPU のすべてのコピーを消去できる保証はありません。認証完了前の出力に公開資格はありません。
- 作成はストリーミング出力、明示的なデスクリプター、ZIP64 境界を使用します。ディレクトリーは平文で、通常ファイルは Store/Deflate と AES を選択できます。ホストはアーカイブ全体の検証後にのみ番号付きボリュームを分割してコミットします。通常の書き換えは有効な圧縮ペイロード、コメント、許可されたメタデータを保持し、レコードオフセットを再計算します。暗号化／分割アーカイブ、自己解凍プレフィックス、安全に保持できないメタデータは引き続き変更を拒否します。空アーカイブでも中央ディレクトリー前の素材を確認し、ローカルレコードがないことを理由にプレフィックスを捨てません。真に空のアーカイブには内容を追加でき、アーカイブコメントを保持します。
- 更新時刻は DOS フィールドに書き、秒精度の拡張を付けます。符号付き 32 ビットに収まる非負 Unix 秒は UT 追加フィールド、それ以外の表現可能な時刻は NTFS FILETIME mtime を使います。NTFS atime/ctime はゼロで、[Common ZIP 規約](https://commonzip.org/spec/#lastmodifiedtimestamp)では有効な時刻を意味しません。APPNOTE 自体はゼロを欠落と定義していません。負の Unix 秒には UT を使わず、独立ツールで未来日時と解釈されることを避けます。通常の書き換えは元の時刻拡張を保持し、アクセス時刻や作成時刻を作りません。
- 名前変更は UTF-8 フラグを設定し、古い Unicode Path 追加フィールドを削除します。このフラグはエントリーコメントも UTF-8 と宣言するため、元コメントが有効な UTF-8 でなければ名前変更を拒否して元アーカイブを保持します。黙って変換したり削除したりしてはいけません。名前を変更しないレコードは元のフラグとコメントを保持できます。

`rawzip`、`zip`、`flate2` はテスト参照専用です。移行済み ZIP の通常依存集合とビルド依存集合にこれらのフォーマット／アルゴリズムライブラリーを再導入してはいけません。テスト参照のライセンスは残ります。コンテナーを読み取れることは、宣言された全方式をデコードできることを意味しません。

## 7z 読み書き仕様

`xdzip-codec-7z` は既存の分離ワーカーで動作する自社読み書きバックエンドで、公式ハンドラーや失敗時フォールバックはありません。コンテナーは方式グラフ、圧縮ヘッダー、外部属性、サブストリーム、生 UTF-16LE 名、物理 EntryId を扱います。グラフ実行器はパスや公開の権限なしに共通アルゴリズムと独立 AES ラッピングを呼びます。公式 7-Zip ソースとコンテナーアダプターは製品ビルドから除外し、固定した公式参照ツールはテスト専用です。仕様、参照解析の役割、ライセンスの違いは [7z ソース](sevenzip-format-sources.md)を参照してください。

方式グラフは実際のポート関係に従ってストリーミングし、ペイロードフォルダー全体を実体化したりキャッシュしたりせず辞書、モデル、上限付きノードバッファーを保持します。メタデータ終端出力は最大 64 MiB です。メタデータ、辞書、モデル、ノードバッファー、作業領域を割り当て前に既定 1 GiB に対して一括受理します。1 ファイル最大 8 GiB、実際のタスク入力と終端デコード作業はそれぞれ最大 20 GiB です。逆順アクセスと再開始は再度計上します。一つのソリッドフォルダー内の順次読み取りではグラフ状態を維持します。ファイルに独立サブストリーム CRC があれば、正確なサイズとその CRC でそのファイルを完了でき、後続ファイルは同じグラフを続行します。独立 CRC がなければ、ファイル完了前にフォルダー全体の終端と存在するフォルダー CRC を完了します。全体完了時には接続されたすべての圧縮範囲、ノードサイズ、EOF、提供された CRC を検証し、参照されない余分なペイロードを通常ファイル検査範囲に含めません。

Header、Additional、ペイロードはグラフ実行器を共有します。メタデータの読み取りと出力にはそれぞれスキャン予算が適用されます。ペイロード入力と終端作業カウンターはペイロードへ入るときに一度だけ初期化し、再開始でリセットしません。中間ノード作業と AES KDF は両段階にわたり累積します。ホストの実デコード作業として計上するのは未選択範囲を含む終端出力のみです。中間ノードには別の累積作業制限があり、AES、伸長、各層のフィルター出力を同一ファイルのホスト作業としてそれぞれ課金することはできません。再帰読み取りでは上流を呼ぶ前に現在ノードの予算を予約し、失敗した操作は未実行分の予約だけを解放し、完了した作業は解放しません。

AES KDF の受理には実際の累積ラウンド数とハッシュ入力バイト数を使用します。失敗や再試行でクレジットは返金せず、出力クォータで無制限のハッシュを購入することはできません。タスクごとに最大 16 個の導出鍵をキャッシュし、パスワード、反復パラメーター、ソルトで照合します。IV は導出識別に含みません。パスワード変更時に旧キャッシュを消去し、セッション間で再利用しません。キャッシュヒットで追加 KDF 作業を作りません。固定キャッシュとパスワードコピーは事前検査で 16 KiB と計上し、各ノードは使用前に鍵が自身の KDF パラメーターと一致するか検証します。パスワード、鍵、所有するハッシュ状態、候補内容バッファーはゼロ化する寿命を持ちますが、過去の Qt／システムコピーすべての消去は保証しません。

Zstandard/FSE/Huffman/XXH64、LZ4/XXH32、LZMA1/2、BZip2、PPMd7、共通 Deflate/Deflate64 は `xdzip-compression` にあり、製品依存関係は空のままです。対応する圧縮アルゴリズムライブラリーは導入しません。Deflate64 は同じ Deflate 実装内で形式差を切り替え、ZIP、GZIP、MSZIP は通常モードを維持します。PPMd7 は既知長と END プロファイルを明示的に区別し、形式モデルの再開始はホストのメモリー受理を代替できません。LZMA2 ライターは制限付き探索レベル 1/6/9 をサポートし、チャンクに効果がない場合は形式が許す生フォールバックを使用します。生チャンクのみの実装を完成したコンプレッサーとは呼びません。共通リーダーは圧縮範囲を明示的に制限し、検証済みの完全な終端状態の後にのみ成功 EOF を返します。エラー後は続行できません。`Read` の出力スライス上限は、個々のブロックやモデル操作に同じ CPU 上限があることを意味しません。

AES は採用済みの汎用 AES、SHA-256、乱数、zeroize 基本要素を使います。形式属性、UTF-16LE パスワード KDF、CBC 構成、ブロックのトリミングは独立実装で、7z ライブラリーを導入しません。CBC 自体は認証を提供しないため、コンテナーは実際に提供された CRC とサイズの検査を完了する必要があります。任意の整合性失敗を確定的なパスワード誤りとして報告してはいけません。作成プロファイル、秘密情報の消去、最終公開は引き続きホストの一連の受け入れ検証が必要です。

作成では Copy または LZMA2 レベル 1/6/9 をホストのランダム一時領域にストリーミングし、ソリッドはファイルのグループ化のみに影響します。暗号化された各フォルダーと暗号化ヘッダーには新しいランダム IV を使い、一致する KDF 識別はタスク内で再利用します。ヘッダー名は暗号化領域内に残ります。宣言された入力長を読んだ後、空ファイルを含め実 EOF と固定ソース識別を確認します。EOF を合成してはいけません。ホストとワーカーの両方が読み書きブロック、オフセット、累積作業と実出力を制限します。進捗メッセージは読み書き権限を与えません。

書き換えは、レコードを安全に保持できる通常ファイルまたはディレクトリーからなる、暗号化されておらず分割されていないアーカイブのみをサポートします。未知の必須メタデータ、anti エントリー、リンク、特殊オブジェクトは明示的に拒否します。ワーカーが保持する元内容と新規内容は最大 512 MiB です。辞書、モデル、メタデータ、作業セットを既定 1 GiB 内で一括事前検査します。理解したフィールドを使い、保持する元の attrs、ctime、atime、mtime を再構築します。物理順序と重複名レコードの識別は統合しません。書き換えは選択した FilesInfo エンティティーに従い圧縮グラフを再構成します。どのファイルからも参照されないフォルダーと未参照の属性 blob は構造保持の約束の対象外です。ソース再検証、アーカイブ全体検証、同一ボリュームでのアトミック公開は引き続きホストの責任です。

## CAB 読み取り専用仕様

`xdzip-codec-cab` は Store、MSZIP、LZX、Quantum と、ホストがすでに認可した同一ディレクトリーのボリュームチェーン向け自社読み取り専用バックエンドです。製品は Rust を使用し、公式ハンドラーやランタイム失敗時フォールバックはありません。公式 Cab コンテナーと CAB 専用 LZX/Quantum アルゴリズムはコンパイルから除外します。CMake 内部の `XDZIP_CAB_BACKEND=rust` は固定されたビルド識別を記録するもので、製品で選択可能なバックエンドではありません。開発、プラットフォーム、手動デスクトップ受け入れは [タスク #48](https://github.com/xiaodaozhi/xdzip/issues/48)と関連受け入れ項目で別々に管理し、リリースを自動承認しません。

コンテナーは MS-CAB、MSZIP は MS-MCI に従い共通 Deflate を再利用します。LZX と Quantum は `xdzip-compression` の独立デコーダーを呼びます。公式アーカイブ文書の状態、ミラーされた 1997 年 LZX 原文の真正性の制限、MS-PATCH と CAB の違い、参照解析者とソース未閲覧の実装者の分離は [CAB ソースと実装根拠](cab-format-sources.md)を参照してください。Rust 実装によってこれらのソースや役割の制限は消えません。

- `ReadSource::volume_lengths()` と `volume_names()` が固定された物理ボリューム境界と元のボリューム名を提供します。ホストが最大 1,024 個の同一ディレクトリーボリュームを発見、識別、認可します。フォーマット層は各ボリューム内オフセットを解釈してボリューム基点の加算を確認し、1 ボリュームを越えて次を読むことはできません。ボリューム名やディスクラベルはファイルアクセス権を与えません。ボリューム欠落やセット／インデックス／名前／継続データの矛盾は部分インデックスを出さずスキャン全体を失敗させます。
- スキャンではコンテナーバージョン、予約フィールド、領域境界と非重複、ファイル範囲、CFDATA 断片を確認します。未完了のボリューム横断フレームでは、論理圧縮フレームを連結する前に各断片のチェックサムを検証します。フォルダーは圧縮／辞書単位であり、ファイルシステムのディレクトリーではありません。履歴をリセットするのは新しい論理フォルダーのみで、ファイルや物理ボリューム境界ではリセットしません。最終フレームは短くてもよく、それ以前の完全な論理フレームはそれぞれ 32,768 バイトを出力します。未知の圧縮方式やパラメーターは明示的に unsupported を返し、スキップして不完全な内容を公開しません。
- 仕様で明示された継続レコードだけを 1 論理ファイルに統合し、名前、オフセット、サイズ、時刻、属性の一致を要求します。通常の重複名、重複と重なり合う出力範囲は別々に保持します。`EntryId` は名前順やソースオフセット順ではなく、最初の CFFILE の物理的な出現順に 1 から連続して割り当てます。公開 `Entry.method` は既存値 0 を維持し、実際の圧縮方式は非公開フォルダーメタデータに保持します。DOS 時刻はタイムゾーンを作らず元の値を維持します。
- 名前は `names::resolve_cab` でアーカイブ全体に対して解決します。生バイトと CFFILE の UTF-8 宣言を別々に保持し、`scan_with_encoding_flags` も元の宣言を返します。ASCII 名を解決した後の `NameEncoding` から宣言を推測しません。Shift-JIS の後続バイト `0x5c` が区切り文字にならないよう、CAB 区切りを共通パスに変換する前に旧名を厳密にデコードします。破損した宣言には見える警告を残し、出力できません。ホストのコードページで置き換えません。[ファイル名エンコーディング契約](filename-encoding.md)を参照してください。
- 読み取り専用の能力にはメタデータと通常ファイル内容が含まれ、作成、書き換え、実行、リンク／特殊オブジェクトの出力は含まれません。空ファイルでも必要なフレームと履歴を検証します。ペイロードを開くときに固定されたすべてのエントリースナップショットを再スキャンして比較します。到達した各 CFDATA はチェックサム、圧縮ストリーム終端、正確な出力長を完全に検証し、選択ファイルの最終バイトでフレーム検証を切り詰めません。CFDATA チェックサムがゼロの場合はチェックサムが提供されておらず、内容認証を意味しません。キャンセル、クォータ、ソース I/O 失敗の分類を保持し、成功として飲み込んだり無条件に再試行したりしません。デコード失敗後、部分更新された状態からペイロードインスタンスを続行できません。
- 既定のメタデータ読み取りは最大 64 MiB、物理 CFFILE レコードは継続コピーを含め最大 100,000、論理フォルダー最大 100,000、物理 CFDATA 断片最大 1,000,000 です。共通スキャン予算の既定値は名前ごと 4,096 バイト、生名前合計 16 MiB、デコード／表示テキスト合計 16 MiB で、呼び出し元のより低い制限が優先します。ペイロードインスタンスの再スキャン後も実入力は累積し続けます。入力とデコード作業はそれぞれ最大 20 GiB、ホストのファイルごとの上限は 8 GiB で、CFFILE フィールドの範囲を拡大しません。すべての長さ演算、割り当て、ソース範囲を使用前に確認します。
- 完全な論理フレームの出力は最大 32,768 バイトです。Store、MSZIP、LZX の圧縮フレーム上限はそれぞれ 32,768、32,780、38,912 バイトです。Quantum の完全圧縮フレームはリソース受理上限 1 MiB であり、公式形式の最大膨張を主張するものではありません。ボリュームをまたぐ分割は論理フレーム一つの上限を拡大しません。デコード状態と出力フレーム一つは制限付きで保持し、同じフォルダー内で順次選択されたファイルは各ファイルで全プレフィックスを再生せず、その状態とフレームを再利用できます。

CAB と ISO/UDF は `xdzip-codec-bridge` を共有し、既存の分離ワーカー内で同期的に借用した CXX コールバックを使って認可済みストリームを読み、メタデータと制限付き出力を送ります。ボリューム配列とバイトスライスは呼び出し中のみ借用し、例外や unwind は境界を越えません。直接 codec API はワーカーと独立プローブ用であり、製品のプロセス分離を代替しません。ホストはキャンセル、強制終了、ソース再検証、一時配置、最終コミットを保持します。

完全フレームの計上には `DecodedSink::charge_skipped` と `write_precharged_chunk` を使用します。新しいフレームを完全にデコードして検証した後、選択範囲の前後のバイトを含む全出力バイト数をまず実作業として計上し、その後に選択内容を渡します。コンテナーはキャッシュしたフレームについて同量の未消費許容量を保持します。前払い配送は残り許容量内でのみ使用でき、消費後の繰り返しや重複配送は通常の `write_chunk` を使用して再度計上します。フレーム切替時は旧クレジットの未使用分を破棄します。名前、エントリー、オフセットにより繰り返し出力が自動的に免除されることはありません。前払いをサポートしないシンクは通常書き込みにフォールバックします。保守的な二重計上になる場合がありますが、出力と制限検査は保持します。

ワーカープロトコルは `WORK`（17、リトルエンディアン `u64` バイト数）でホスト受理を要求し、計上済み内容を `PRECHARGED_DATA`（23）で送ります。出力ブロックは最大 64 KiB でホスト ACK を受けます。Native 受信側は同じ実行中ワーカーに受理されたクレジット内で、CAB、7z、RAR のみ非空の前払い出力を許可します。他の形式や不足クレジットは拒否し、エントリー完了時の正確な宣言サイズも検証します。ワーカーの再開始、終了、失敗後に旧クレジットは再利用できません。ランタイムの解凍シンクと検査シンクはタスク専用許容量をそれぞれ検証します。通常のファイル変更では未消費許容量を保持できますが、消費済みクレジットは再利用できません。前払いはすでに計上した作業の再加算を避けるだけです。宣言ファイルサイズ、ファイルごと 8 GiB、累積実出力 20 GiB、キャンセル、書き込み失敗の検査は引き続き適用します。配送前にクレジットを差し引き、部分出力失敗でも返金しません。ホストが `WORK` を拒否した場合はクレジットを作りません。RAR 補助作業は別に受理され、前払い出力クレジットを与えません。[補助作業契約](auxiliary-decoding-work.md)を参照してください。

## RAR 読み取り専用仕様

`xdzip-codec-rar` の最古形式、旧形式、現行形式のコンテナー、物理パート識別、認可ボリューム、名前、Store、13/15 と 20/26 の系列、RAR29 LZ/PPM／標準フィルター、現代 LZ／フィルター、旧／現代パスワード契約は [RAR 実装根拠](rar-format-sources.md)を参照してください。製品はこの Rust 経路を使い、UnRAR をコンパイルせず配置もせず、失敗時フォールバックもありません。未知サイズは明示され、出力できません。現代時刻は形式非依存のホストサービスで投影し、補助デコード作業は別に計上します。過去の組み合わせ、実際のフィルター、クロスプラットフォーム互換性は[完全移行タスク #51](https://github.com/xiaodaozhi/xdzip/issues/51)の下で個別に受け入れを続けます。一系列の成功で範囲を狭めることはできません。独立した健全な RAR7 アルゴリズム 1 サンプルは #43 で追跡します。

## ISO と UDF の読み取り専用仕様

`xdzip-codec-optical` は借用した `ReadSource` のみを受け取り、ファイルシステムにアクセスしたりイメージをマウントしたりしません。ISO は [ECMA-119 第 5 版](https://ecma-international.org/wp-content/uploads/ECMA-119_5th_edition_december_2024.pdf)のボリューム記述子、ディレクトリー、拡張属性と付録 C Joliet、[Rock Ridge 1.12](https://bitsavers.org/projects/cdrom/Rock_Ridge_Interchange_Protocol.pdf)、SUSP 1.12、[El Torito 1.0](https://bitsavers.org/projects/cdrom/El_Torito_CD-ROM_Spec.pdf)に従います。UDF は [ECMA-167 第 3 版](https://ecma-international.org/publications-and-standards/standards/ecma-167/)の第 1、3、4 部と [OSTA UDF 2.60（PDF ミラー）](https://www.13thmonkey.org/documentation/UDF/udf260.pdf)の構造制限、パーティション、文字セットに従います。実装は第三者パーサーソースを翻訳しません。元の仕様と第三者テストツールをプロジェクト独自の素材として再ライセンスしません。

- ISO は両エンディアン整数、ボリューム範囲、ディレクトリーレコード、ファイルエクステントを確認します。複数エクステントの通常ファイル、Joliet UCS-2、Rock Ridge 名前継続、SUSP CE、CL/PL/RE ディレクトリー移動、リンク／特殊種別識別をサポートします。Joliet 以外の生名前はシステム OEM 変換なしに共通の制限付きエンコーディング解決を使います。ブートカタログとイメージは読み取り可能なレコードとしてのみ表現します。ボリューム横断 ISO、インターリーブファイル、レコード指向拡張属性、Rock Ridge SF スパース、ZF 圧縮拡張を拒否します。未知の必須機能を通常ファイルとしてデコードできません。
- UDF は論理ブロック番号と物理オフセットを区別し、記述子タグの位置、チェックサム、CRC、サイズを検証します。主／バックアップアンカー、VDS 継続チェーン、FSD、FE/EFE、FID、ICB を扱います。物理、sparable、VAT 1.50/2.x、metadata/mirror パーティションマッピングは別々に受理します。sparable パーティションの標準 `*UDF Non-Allocatable Space` システムレコードは、OSTA 3.3.7.2 に基づき名前、種別、Metadata/System/Stream フラグ、ゼロ情報長、未記録末尾割り当てを検証します。これはシステムメタデータのみで出力エントリーではありません。short、long、extended AD と継続は実際の記録長／情報長を使い、範囲合計が連続すると仮定せず、インライン、未記録ゼロエクステント、非連続内容をサポートします。ディレクトリーグラフ、割り当てチェーン、マッピングサイクルには上限を設け、CS0 を Unicode に厳密変換します。
- UDF 通常ファイルの名前付きストリーム、未知のシステムストリーム、変換データ、未知のマッピング／ICB 方針、解釈不能な extended AD 長の組み合わせを拒否します。リアルタイムなどの特殊ファイルは出力不可とし、シンボリックリンクと複数リンクされた通常ファイルも出力を拒否します。UDF 識別後の失敗で ISO に切り替えません。仕様内の VDS／メタデータ冗長復旧は選択済み名前空間を変更しません。
- EntryId は選択した名前空間の元のディレクトリーレコード走査順に割り当て、デコード名順や重複名を統合した順にはしません。ファイルデータのセクターオフセットはエントリー識別ではありません。解析結果はデータ、ゼロエクステント、インライン内容のエクステント一覧を別々に保持します。ペイロードを開く際に固定メタデータを再スキャンして比較し、デコード中にエントリー識別、範囲、正確な出力長を検証します。ファイルごとの CRC がない形式に架空の整合性保証は与えず、同サイズの内容変更が読み取れる場合もあります。ホストのソース識別検査は独立して維持します。
- メタデータ読み取りは最大 64 MiB、通常エントリー最大 100,000、名前ごと最大 4,096 バイトで、名前／表示テキスト合計は共通スキャン予算内です。出力エクステント合計は最大 1,000,000、インラインデータ合計は最大 64 MiB です。ISO ディレクトリー深度は最大 256、レコードごとの CE は最大 128 領域かつ 1 MiB です。ホスト出力パスには引き続きより厳しい共通制限を使います。UDF は最大 256 パーティションマップ、割り当て表ごと最大 262,144 エクステント、最大 4,096 継続を許可します。すべての加算、乗算、ソース範囲のオーバーフローを確認します。
- 実際のデコードはファイルごと 8 GiB、累積作業と入力それぞれ 20 GiB の制限を保持し、制限付き読み取り／出力バッファーを使います。`xdzip-codec-bridge` は既存ワーカー内で同期的に借用した CXX コールバックを通じ認可ストリームを渡します。例外や unwind は境界を越えず、プロセス終了は未完了出力を失敗させます。ホストはメモリー管理、キャンセル、強制終了、ソース再検証、非公開の一時配置、最終コミットを保持します。公式 7-Zip Iso/Udf ハンドラーはビルドと登録表から除外し、ランタイムフォールバックはありません。

独立サンプルには検証可能な生成ツールまたは来歴と既知の内容が必要です。自己エンコードした仕様ベクターが検証するのは内部状態の組み合わせだけです。metadata、VAT、sparable などの拡張についての独立した実サンプルと 3 プラットフォーム受け入れは[移行タスク #47](https://github.com/xiaodaozhi/xdzip/issues/47)に別々に記録します。コードの存在や物理パーティションサンプルの合格は他のマッピングの受け入れを示しません。テストツール、参照ワーカー、製品ワーカーは識別情報を分けて記録し、参照ツールがサポートしないサンプルを検証済みとしません。

## 能力と検証の基準

| バックエンド | 維持する能力 | 独立実装の要素 |
| --- | --- | --- |
| ZIP | Store/Deflate、ZIP64、AE-1/AE-2 AES-256、既存の分割ボリューム、作成と通常アーカイブ変更 | レコード、追加フィールド、データデスクリプター、暗号ラッピング、共通 Deflate |
| TAR、TAR.GZ | ustar、既存 PAX/GNU、通常ファイル／ディレクトリー、作成と変更、複数メンバー GZIP | レコード層、拡張状態、ストリーミング書き込み、GZIP フレーミングと共通 Deflate |
| 7z | Store、LZMA/LZMA2、PPMd、BZip2/Deflate デコード、BCJ/BCJ2、分岐フィルターと Delta フィルター、ソリッド、パスワード／ヘッダー暗号化、番号付きボリューム、作成と限定再構築 | デコードグラフ、実際に受理された方式の組み合わせ、リソースとエンコーディング方針。下位エンコーダーは製品の作成オプションを拡大しない |
| RAR | 旧形式、RAR5、RAR7、パスワード、ソリッド、分割ボリュームの既存読み取り制限 | バージョン別デコーダー、フィルター、暗号ラッピング、状態リセット |
| CAB | Store、MSZIP、Quantum、LZX、同一ディレクトリーのボリュームチェーン | レコード、ファイル／フォルダー対応、ブロック横断辞書、ボリューム横断ファイル |
| ISO、UDF | ISO9660、Joliet、Rock Ridge、UDF、ハイブリッドイメージ選択 | ボリューム／パーティションマッピング、名前空間、エクステント、ディレクトリーグラフ、特殊項目の制限 |

各切替には双方向の相互運用（読み取り専用形式では独立サンプルの読み取り）、破損／切り詰め、数値オーバーフロー、リソース制限、キャンセル、実際のホスト業務経路の回帰が必要です。自社エンコーダーとデコーダーが互いに成功しても互換性は証明できません。ファジングとベンチマークは固定ソースを使用して実際の範囲と時間を記録し、限定的なランダム変異テストを長期ファジングとは呼びません。Windows、Linux、Apple Silicon の実際の自動検査とデスクトップ検査は別々に記録します。正式リリースには引き続き独立したライセンス審査が必要です。
