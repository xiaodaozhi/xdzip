# ローカル macOS 開発用 DMG

[English](../../engineering/macos-deployment.md) | [简体中文](../../zh-CN/engineering/macos-deployment.md) | [繁體中文](../../zh-TW/engineering/macos-deployment.md) | 日本語 | [Français](../../fr-FR/engineering/macos-deployment.md) | [Deutsch](../../de-DE/engineering/macos-deployment.md) | [Español](../../es-ES/engineering/macos-deployment.md) | [Português (Brasil)](../../pt-BR/engineering/macos-deployment.md)

専用 Release ワークフローでは、ネイティブ配置、必要な ad-hoc 署名、app.zip と DMG の作成とアップロードを許可します。オンデマンド Qt ワークフローの macOS ジョブでは SDK の検証を維持します。2 つのリリースパッケージには、配置、署名、検証済みの同一の .app を使用し、ZIP から展開したアプリは移動後の起動も検証します。[リリースプロトコル](release-protocol.md)を参照してください。

ローカルの開発用 DMG は、許可された開発成果物です。オンデマンド Qt ワークフローは Apple Silicon でのネイティブビルドと起動を検証しますが、Mac アプリのパッケージ化、署名、アップロードは行いません。ローカルスクリプトはアプリをインストールせず、既定の関連付けを変更せず、ファイルをアップロードせず、リリース認証情報も読みません。

## ビルドと検証

環境の事前確認と各段階のオプションは[開発者向けビルドガイド](../../engineering/developer-build.md)に従います。パッケージツールを準備し、クリーンなコミットから別の Release 主アプリをビルドした後、パッケージ化して検証します。

```sh
python3 scripts/desktop.py prepare --packaging
python3 scripts/desktop.py build --build-dir build/desktop-dmg --macos-handler-rank Alternate
python3 scripts/desktop.py test --build-dir build/desktop-dmg
python3 scripts/desktop.py doctor --for-stage package --build-dir build/desktop-dmg
python3 scripts/desktop.py package --build-dir build/desktop-dmg --output-dir build/package-macos --kind all
python3 scripts/desktop.py verify --build-dir build/desktop-dmg --output-dir build/package-macos --kind all
```

各段階は前の段階を暗黙に再実行しません。既定の Qt SDK は `build/toolchain/Qt/6.8.2/macos` です。別の場所を使う場合は各コマンドに `--qt-prefix` を渡します。通常の開発・テストビルドは既定で `None` を使用し、上記の主アプリはユーザーの既定設定を変更せずに `Alternate` を明示的に選択します。ローカル macOS パッケージは `all` のみをサポートします。オンデマンド Qt ワークフローは Mac アプリをパッケージ化またはアップロードしません。専用 Release の例外はリリースプロトコルを参照してください。

macdeployqt の前に、共通パッケージ検査はネイティブ arm64、システム SDK、配置ツール、Rust の PATH と固定メタデータ、Python 検証依存関係、および Qt のライセンス・スキーマ資料を確認します。build と test は未コミットのソースを許可しますが、package はクリーンなコミットと一致する実際の CLI 識別情報を要求し、ビルドキャッシュでこれらを回避できません。システムコンパイラ、SDK、lipo、codesign、hdiutil はシステムツールチェーンから提供され、prepare はインストールしません。

macdeployqt は画像ワーカーも移動します。Qt 6.8 の既定のプラットフォームプラグイン選択には Cocoa しか含まれないため、パッケージスクリプトはアプリのライブラリを走査する前に offscreen を明示的にコピーし、その Qt フレームワーク依存関係を処理します。プラグインやワーカーがない場合、パッケージ化を拒否します。完全性署名とインポート監査後、Qt/QML/DYLD の検索上書きを解除し、実際に同梱した画像ワーカーの対応形式と、プロジェクト所有の PNG のデコードを検証します。記録は `image-preview-deployed.json` です。スクリプトの単体テストは配置済みパッケージの受け入れを証明しません。

内部の [build-macos-dmg.py](../../../scripts/build-macos-dmg.py) と [verify-macos-dmg.py](../../../scripts/verify-macos-dmg.py) はイメージとネイティブ検証の詳細を保持します。日常手順を別途維持する代わりに、問題調査には `--help` を使用してください。内部スクリプトの出力先は build/ 内の新しいパスでなければなりません。DMG 入力のすべての文書タイプは `Viewer/Alternate` を宣言する必要があります。そうでなければ元のバンドルの plist や署名を書き換えず、再ビルドしてください。macdeployqt は実際の QML を走査して Qt フレームワーク、プラグイン、QML を配置します。Qt システムコントロールの翻訳、プロジェクトの通知、Rust 上流の通知、フォントライセンス、ソース SBOM、固定された Qt ライセンス資料を追加します。フレームワーク内部のシンボリックリンクを保持し、アプリ外へ出るリンクを拒否します。開発マシン固有の絶対 RPATH を削除し、すべてのネイティブインポートがアプリまたはシステム内にのみ解決されることを再帰的に確認します。ビルド識別情報は dirty または不明であってはならず、実際の通知を結び付けるため現在のクリーンなコミットと一致する必要があります。

Qt のオプション QML LocalStorage は QtSql を導入するため、配置時にはデータベースドライバもコピーします。プロジェクトにはサーバーデータベース機能がないため、PostgreSQL、ODBC、Mimer など SDK 外部のクライアントがイメージに入らないよう、組み込み SQLite 以外のドライバを削除します。削除を記録に残し、未解決のインポートを成功として隠さないでください。

## アーキテクチャとスタイルの削減

開発用 DMG は Apple Silicon の `arm64` のみを提供します。主プログラムの CMake アーキテクチャ設定は macdeployqt がコピーする Qt SDK ファイルを制限しないため、フレームワーク、動的ライブラリ、プラグイン、QML ネイティブプラグインを含むアプリ内のすべての Mach-O を再帰的に検査します。2 アーキテクチャのファイルを `arm64` のみに削減するのは、新しく作成したパッケージ用コピーに限ります。`arm64` の欠落、未知のアーキテクチャ、余分なスライスの残存はパッケージ化の失敗とし、主実行ファイルのアーキテクチャ確認で内部の検査を代用しません。RPATH の書き換えと再帰的 ad-hoc 署名より前に削減します。

製品は Qt Quick Controls の `Basic` を使用します。配置処理は明示的に列挙された非 Basic スタイルと専用のインポートまたは実装プラグインだけを削除し、Basic、共有コントロール、Templates、実際の QML 依存関係を保持します。未知のモジュールを削除してサイズを減らしてはいけません。想定外のスタイル配置、保持すべき依存関係の欠落、未使用スタイルの残存は監査の失敗です。製品スタイルまたは Qt SDK の変更時は削減規則とテストも同時に更新します。サイズ削減によって Qt ライセンス、対応ソース資料、システム翻訳、必要なランタイムプラグインを省略しません。

最適化するのは範囲を限定した `build/` 内に新たに準備したアプリだけで、入力の主アプリ、Qt SDK、ソースは変更しません。記録にはアーキテクチャとスタイルの検査、削減したバイナリと削除一覧、最適化前後の実際のアプリの論理バイト数を、フレームワーク、プラグイン、QML、その他に分けて残します。バイト数は実際のファイル内容から算出し、シンボリックリンクを二重計上しません。Finder のディスク使用量や UDZO イメージサイズではありません。最終 DMG サイズは別に記録します。バージョン別の比較、検証結論、残作業は issue に記録し、生の測定値はローカル成果物に残します。

`scripts/test-macos-bundle.py` はプラットフォーム共通 CI の小さなプロジェクト所有フィクスチャを使い、macOS 配置ツールなしでアーキテクチャ認識、コピーのみの操作、シンボリックリンクの境界、スタイルの保持・削除、失敗を検証します。最終パッケージの検証の代わりにはなりません。DMG 検査では、マウントしたイメージからコピー後、全ネイティブファイルに `arm64` だけが存在し、スタイルが契約に準拠することを再帰的に確認し、以下の SDK 検索分離と Cocoa/Metal のフローを実行します。

## イメージとランタイムの検証

UDZO 圧縮イメージには xdzip.app、Applications リンク、インストール手順が含まれます。hdiutil verify を実行してください。Applications にドラッグする前に旧バージョンを通常の手順で終了します。このフローではインストール中のアップデータやタスク移行はありません。設定と最近使った項目はユーザーディレクトリに残り、アプリを削除しても自動削除されません。

配置検証 JSON とファイル単位の CycloneDX SBOM をイメージの隣に保持し、同一コミットのソースインベントリ、最終ネイティブファイルの SHA-256、インポート関係に結び付けます。SBOM は不完全なままであり、ファイル列挙は正確なコンポーネント帰属やライセンス承認ではありません。再帰的な自己ハッシュを避けるため、インベントリはイメージ外に保持します。

新たに準備された `xdzip.app` は、配置、署名、イメージ作成、検証の間だけ存在し、成功・失敗のどちらでも自動的に回収されます。DMG、JSON、SBOM、手順書は残り、入力の主アプリは変更されません。システムが再発見できる準備済みバンドルは残りません。

変更された ARM64 Mach-O ファイルには有効なコードディレクトリが必要なため、コピーと書き換えの後にローカルの ad-hoc 署名を行い、内部のコードも検証します。**これは Developer ID 署名や公証ではなく、Gatekeeper の信頼を意味しません。** [個人のオープンソースリリース方針](../../../developers/engineering/release-runbook.md)では正式な署名と公証はリリースの必須条件ではありませんが、依存関係、ライセンス、セキュリティ、実際のパッケージの検証は引き続き必要です。SIP を無効にしたり、ユーザーのグローバルなセキュリティポリシーを削除したりしないでください。

検証スクリプトはイメージを読み取り専用でマウントし、Applications リンクを確認し、中国語文字と空白を含む分離パスにコピーし、すべてのネイティブファイルとバンドルについて arm64、Basic スタイル、厳格な署名を再帰的に確認します。SDK/QML/プラグイン検索変数を解除したうえで Cocoa/Metal で起動・終了します。イメージ内の実製品が自作 ZIP を開き、検索、ソート、展開、終了を行い、Unicode、空ファイルと空ディレクトリ、すべての出力バイトを独立に検証し、実際の最初のフレームでビルド識別情報、アーキテクチャ、Metal バックエンドを確認します。その後、検証用コピーだけで QtCore Mach-O ライブラリの識別情報を変更して ad-hoc で再署名し、アーキテクチャ、スタイル、署名、起動を再確認します。これは配置済みの変更・置換が可能なことを示しますが、対応ソースから Qt を再ビルドしたこと、任意の ABI 互換性、法的適合性の承認を証明するものではありません。

app.zip の検証でも製品の既定の同名フォルダ作成オプションでアプリ全体を展開し、ファイルのバイト、リンク先、安全な権限を `ditto` と項目ごとに比較した後、展開された実アプリに対して深い厳格な署名検査と Cocoa/Metal 起動を行います。外側のディレクトリは `.app` で終わってはいけません。検査中に新たに作られた一時アプリと登録はその後クリーンアップします。署名の信頼や公証の境界は変わりません。

ローカルマシンには引き続き SDK が存在します。インポート検査と環境変数の解除は、別のクリーンな Mac の代わりになりません。Finder へのドラッグ、システムの「このアプリケーションで開く」、既定選択、Gatekeeper、実際の再起動、署名・公証は[手動チェックリスト](../../../developers/qa/private-test-manual.md)に従います。

ネイティブメニューの編集コマンドと Qt 標準コントロールにはシステムロケールの qtbase 翻訳が必要です。パッケージ処理は `Contents/Resources/translations/qtbase_*.qm` のコピーに加え、`Contents/Resources/qt.conf` の `[Paths]` に `Translations = Resources/translations` を設定し、既存のプラグイン/QML パスを保持して、完全性署名より前に書き込みます。移動後の起動検査ではネイティブ編集レスポンダとアプリケーションメニューのロールの両方を確認します。SDK 開発ディレクトリ内だけの検査では不十分です。

## ローカル Finder Sync の署名と有効化

Finder Sync は同一アプリ内のネイティブ appex と独立したリレーを使用し、サービスヘルパーも残ります。署名の完全な順序は、ネイティブイメージ、フレームワークと専用ヘルパー、正確なサンドボックス権限を付けた appex、リレーバンドル、外側のアプリであり、その後に内部バンドルを厳格に検証します。署名済み appex を後から権限のない汎用署名で上書きしてはいけません。通常の CI ビルドは拡張機能を暗黙に署名または有効化しません。

ローカルで Finder を検証するには、既定のネイティブビルドを完了し、次を明示的に実行します。

```sh
python3 scripts/sign-macos-finder.py --app build/desktop/apps/desktop/xdzip.app --output build/review/finder-signing.json
build/desktop/apps/desktop/xdzip.app/Contents/MacOS/xdzip --register-shell-integration
```

署名スクリプトが受け付けるのはプロジェクト所有のアプリとリポジトリの `build/` 内への出力だけです。Qt の配置、DMG の作成、リリース認証情報の読み取りは行いません。記録が示すのは ad-hoc の完全性と内部の厳格な検証のみであり、Developer ID、公証、Gatekeeper の信頼、リリースライセンスの承認ではありません。アプリは元の場所に保持する必要があります。システム設定のログイン項目と機能拡張で xdzip の Finder 拡張を有効にします。設定パスやメニューは OS バージョンによって異なる場合があり、登録成功はメニューや操作の受け入れを証明しません。

一時的な検証を終了する前に、同じアプリの `--remove-shell-integration` で所有するサービスと拡張の登録を解除します。初期状態を確認した後、この作業が作成した設定と一時 LaunchServices 登録だけをクリーンアップします。他のアプリや既定の関連付けは変更しません。Finder がアプリを読み込んでいる場合、更新後は Finder を再起動せず、システム設定で所有する拡張を無効化してから再度有効化します。引き渡しとロールバックの境界は[ファイルマネージャー操作](shell-actions.md)を参照してください。

## 開発・検証用コピーの「このアプリケーションで開く」登録

LaunchServices は以前開いたアプリバンドルを記憶するため、ビルドツリー内の同じバンドル ID の複数コピーがシステムまたは Codex の「このアプリケーションで開く」メニューに表示されることがあります。そのためにシステムデータベースを削除したり、Finder を再起動したり、検証パッケージを削除したり、ユーザーの既定設定を変更したりしないでください。

新しい開発バンドルは生成 Info.plist で既定の `LSHandlerRank=None` を使用し、選択した主アプリと配布パッケージのみが `Alternate` を保持します。CMake オプション `XDZIP_MACOS_HANDLER_RANK` はこの 2 値のみを厳格に許可します。オフラインのソース再ビルド、ソース Qt 製品検証、Mac 製品 CI は明示的に `None` を渡し、将来既定値が変わってもテストコピーが候補として再導入されないようにします。[Apple による `None` の定義](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html)では、ファイルのドラッグを維持しつつ、そのタイプの開くアプリとしてバンドルを選びません。アプリ内のファイル選択やアプリの明示的な起動に影響せず、既定値を設定しません。

Mac 製品 CI は `scripts/check-macos-registration.py` を実行し、ネイティブ `NSWorkspace` を通じて新しいバンドルのファイル候補を問い合わせます。候補数とバンドル ID で列挙した登録は別々に評価し、後者で実際にユーザーに表示される「このアプリケーションで開く」の候補を代用しません。一時登録中も既存の既定ハンドラを維持する必要があります。以前のハンドラがないタイプは一時的に新しい候補に解決されることがありますが、登録解除後はテストしたすべてのタイプが元のハンドラと候補状態に戻る必要があります。現在のユーザーの `LSHandlers` 設定は登録前、登録中、登録後のメモリ内スナップショットとしてのみ比較し、内容は出力しません。他の設定やシステムレベルの規則はこの比較の対象外です。

`scripts/macos_launch_services.py` は `org.xdzip.desktop` だけを認識します。DMG の移動、オフラインソース再ビルド、ソース Qt 製品検証、QtCore の置換、システムファイルオープン検証は、範囲を限定した `build/` 内の実行前登録を記録し、完了時または失敗時には新たに追加したテストコピーだけの登録を解除します。既存の主アプリと他製品は保持します。クリーンアップの失敗は黙って成功とせず、検証を失敗とします。

DMG の移動と QtCore の置換は配布バンドルの元の文書宣言と検証を維持しますが、`build/` 内の新規で未存在の `.app` パスにだけコピーします。必要なハッシュをその範囲内で確定し、検証後または失敗後に新規バンドルを自動回収します。JSON、ログ、置換前の主バンドル、DMG、Qt ソースは残ります。クリーンアップは既存アプリやシンボリックリンクを受け付けず、過去の検証バンドルを遡って削除しません。登録解除しただけの古い `Alternate` バンドルはシステムや他アプリに再発見・再登録されることがあり、恒久的に再発しない保証はありません。古いバンドルの保持が必要なら、明示的な許可の下で単独コピーを処理する前に、検証・復元可能なバックアップに置くことができます。

次のツールで過去の残存物をプレビューし、その後明示的に適用します。`--keep` には正しく識別された既存の主アプリ、現在の開発ビルドまたは Applications 内のインストールを指定する必要があります。

```sh
python3 scripts/cleanup-macos-open-with.py --keep build/ui-release/apps/desktop/xdzip.app
python3 scripts/cleanup-macos-open-with.py --keep build/ui-release/apps/desktop/xdzip.app --apply
```

このツールは、このリポジトリの `build/` 内の他の xdzip コピーと、同じ識別情報を持つ無効パスだけを登録解除します。バンドルの削除、署名の変更、既定 ZIP アプリの設定は行いません。異なる製品、Applications の他のインストール、ビルドツリー外のパスは自動処理しません。シンボリックリンクにより範囲外へ解決されるパスはクリーンアップしません。その後登録を再確認し、指定した主開発バンドルだけを保持します。ビルドツリー外に複数のインストールがある場合は未処理として別に列挙し、全体の重複排除が完了したと主張しないでください。

クリーンアップの進捗、件数、実行結果は、[開発コピーのメンテナンス #7](https://github.com/xiaodaozhi/xdzip/issues/7) など該当 issue に記録します。生成 JSON とネイティブプローブの結果はローカルまたは CI の成果物にのみ保持します。
