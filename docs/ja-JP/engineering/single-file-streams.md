# 単一ファイルストリームと ZIP 派生パッケージ

[English](../../engineering/single-file-streams.md) | [简体中文](../../zh-CN/engineering/single-file-streams.md) | [繁體中文](../../zh-TW/engineering/single-file-streams.md) | 日本語 | [한국어](../../ko-KR/engineering/single-file-streams.md) | [Français](../../fr-FR/engineering/single-file-streams.md) | [Deutsch](../../de-DE/engineering/single-file-streams.md) | [Español](../../es-ES/engineering/single-file-streams.md) | [Português (Brasil)](../../pt-BR/engineering/single-file-streams.md) | [Русский](../../ru-RU/engineering/single-file-streams.md)

[組み込みレジストリ](format-registry.md)は通常の GZIP を TAR.GZ とは別に宣言します。`xdzip-codec-stream` は独立した `xdzip-compression` の [RFC 1952](https://www.rfc-editor.org/rfc/rfc1952) 実装をメタデータ、ペイロード、作成の契約に適合させます。参照用圧縮ライブラリーは製品の依存関係に入りません。

<a name="xdzip-discovery-and-read-boundaries"></a>

## 検出と読み取りの範囲

GZIP の認識は最大 256 KiB の圧縮読み取りで最大 512 バイトのデコード済みプレフィックスを確認します。有効な従来の TAR ヘッダーまたは明示的な `ustar` マーカーは TAR.GZ を選択します。認識された TAR が破損している場合、通常ファイルにフォールバックせず失敗します。それ以外は GZIP ストリーム全体を走査してから、単一の通常ファイル項目を公開します。少なくとも 1024 バイトのデコード済みストリームがすべてゼロの場合、空の TAR とゼロ埋めされた通常ファイルを区別できません。完全なストリーム検証後にのみ、同じ外側フィルターに登録された最長の拡張子で表示を決めます。明示的な通常拡張子はファイルを、TAR 拡張子はコンテナーを維持し、不明または名前がない場合は空 TAR を優先します。アーカイブ編集で生成された空の TAR.GZ は固定 GZIP コメントを持ちます。正確に 2 つのゼロ TAR 終端ブロックを検証した後、通常の拡張子でも TAR.GZ を選択します。ゼロのプレフィックスの後に非ゼロの通常データが続く場合は GZIP のままです。ヒントは強い TAR 識別、破損した圧縮、検査、クォータ、ソース権限を上書きできません。

走査の受理は物理入力長と実際のデコード済みバイト数をそれぞれ 24 GiB に制限します。`ControlledStream` は読み取り前にキャンセルを確認し、最初の型付きエラーを保持します。デコード量が境界に正確に達した場合、EOF と超過を区別するため非公開で追加のデコード済みバイトを一つ確認できますが、そのバイトは渡しません。TAR は同じ制御ストリームをそのまま、または GZIP フィルター付きで使用します。ストリーム全体の EOF では空メンバーを含む各メンバーの CRC32 と ISIZE を検証する必要があります。連結メンバーは一つの論理ファイルを構成します。ヘッダーフラグ、制限付きの任意フィールド、ヘッダーチェックサム、切り詰め、メンバーでない末尾バイトは独立した GZIP デコーダーが引き続き検証します。

行サイズは 32 ビットの ISIZE ではなく、完全にデコードして観察されたバイト数です。ホストは `ReadSource::source_name_hint` でベース名を提供でき、codec は ASCII の大文字小文字を区別せず末尾の `.gz` を除去し、区切り文字、制御文字、特殊な名前を拒否し、それ以外は `content` を使用します。ヘッダー FNAME は無視し、表示テキストは別途エスケープします。すべての出力名は引き続きホストの移植可能パスと保存先の検査を通過します。ヒントはファイルシステム権限を与えません。ペイロードのデコードは不変の行、圧縮長、観察サイズに結び付けられ、成功前に EOF を再検証し、失敗または完了後は再開できません。既存のタスク制限はファイルごとに 8 GiB、タスクごとに 20 GiB です。

<a name="xdzip-creation-and-publication"></a>

## 作成と公開

通常の `.gz` 作成は一つの通常入力ファイルのみを受け入れ、Deflate レベル 0/1/6/9 を使用します。ディレクトリ、複数ファイル、パスワード、分割、ソリッドモード、ヘッダー暗号化は拒否します。エンコーダーは固定された入力を EOF まで読み、正確なサイズとキャンセルを確認し、ホスト所有の一時領域で GZIP トレーラーを完成させます。ホストは公開前に一時ストリーム、ソースバージョン、出力トランザクションを検証します。GZIP は入力ファイル名を保存せず、再オープン時の仮想名はアーカイブのベース名に由来します。そのため検証は元の入力名を要求せず、通常ファイルの識別情報とサイズを比較します。通常の GZIP はアーカイブ変更に対応しません。TAR.GZ の作成と書き換えは別のコンテナー契約を維持します。

デスクトップの作成選択肢、ウェルカムラベル、関連付け候補は安定したレジストリ識別子から生成されます。共有形式セレクターの寸法は既存のコントロールパラメーターから導きます。CLI の作成は同じ拡張子レジストリを使い、最長一致を優先して `.gz` より `.tar.gz` を保持します。競合時の名前変更は `.tgz` を含む実際に登録された拡張子を保持します。

<a name="xdzip-zip-derived-candidates"></a>

## ZIP 派生候補

`.xpi`、`.apk`、`.ipa`、`.cbz` は既存 ZIP リーダーの入口候補です。内容検証、Store/Deflate、受理済み WinZip AES-256 プロファイル、パス処理、リソース上限は ZIP のものを維持します。拡張子だけで他の方式や暗号化方式を受理することはありません。これらの操作はパッケージマニフェスト、アプリケーションのインストール、パッケージ署名を解釈しません。別名による作成拡張子の追加はありません。Windows の別名は ZIP アイコンを再利用します。macOS は拡張子を宣言して割り当てられた型を解決し、すべての ZIP の既定を置き換えません。Linux は対応する利用可能な MIME 候補を使用し、IPA は汎用 ZIP 関連付けを維持します。

<a name="xdzip-xz-admission-and-wire-contract"></a>

## XZ の受理と形式契約

XZ プロファイルは [Tukaani 形式 1.2.1](https://tukaani.org/xz/xz-file-format-1.2.1.txt)に従う必要があります。デコーダーの割り当て前にストリームフラグとヘッダー CRC を検証し、予約フラグ、非正準またはオーバーフローする 9 バイトの可変整数、未対応フィルター、予算を超える辞書を拒否します。ブロックヘッダーは 8–1024 バイトで、検証済み CRC、任意の非ゼロ圧縮サイズと任意のデコードサイズ、最大 3 つのサイズを保持する Delta/BCJ フィルターに続く LZMA2、ゼロのヘッダーパディングを持ちます。LZMA2 の終端マーカーが正確な圧縮境界を決め、任意のサイズは観察された処理量を検証します。厳格な 7z コンストラクターとサイズ不明メンバーのデコードを分離し、終端検証後にのみソースを返します。

ブロックパディング、宣言されたすべての内容検査（None、CRC32、CRC64、SHA-256）、各インデックスレコードと観察された非パディングサイズおよびデコードサイズ、インデックスパディング/CRC、フッターの後方サイズ/フラグ/CRC/マジック、連結ストリーム、4 バイトのゼロストリームパディングを検証します。None は内容チェックサムを提供せず、チェックサム保証として表示してはなりません。ストリーム数とストリームごとのブロック数はそれぞれ 100,000 に制限し、固定の解析・フィルターバッファーを 128 MiB の作業メモリー受理に計上し、キャンセルと独立した入出力制限を維持します。失敗したストリームは使用不能となり、デコードデータは完全な検証とソース確認が成功するまでホストの一時領域に保持します。作成には実際の LZMA2 圧縮、独立してリセットされる制限付きブロック、宣言された内容チェックサムが必要です。ライターの受け入れ前に独立したデコードで出力バイトを検証する必要があります。

ZIPX は既存の ZIP レコードと物理識別情報を使用します。方式ごとの受理は BZip2 12、LZMA 14、XZ 95 を含め [APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) に従います。LZMA のプロパティヘッダーは LZMA Alone と異なり、汎用フラグのビット 1 が EOS の要件を制御します。受理されたデータディスクリプタープロファイルは EOS が必要で、サイズ付きローカルレコードでは省略できます。正確なペイロード範囲、ローカル/中央の整合性、ディスクリプター、デコードサイズ、ZIP CRC は引き続き必須です。検証済み実装のない方式はレコードごとに未対応のままで、拡張子によって他のアルゴリズムや暗号化プロファイルが有効になることはありません。

XZ（`.xz`）と TAR.XZ（`.tar.xz`、`.txz`）はこのプロファイルを読み取り、検査、展開に実装します。作成は CRC64、最大 16 MiB の独立ブロック、LZMA2 レベル 1/6/9 を使用し、レベル 0、パスワード、分割は拒否します。通常の XZ は一つの通常入力のみを受け入れ、ホストのベース名から仮想出力名を導きます。TAR.XZ は既存 TAR ライターを通じて通常ファイルとディレクトリを受け入れ、アーカイブ編集をサポートします。ZIPX は `.zipx` を ZIP 候補に追加し、既存の Store/Deflate に加えて非暗号化方式 9、12、14、95 を読み取ります。これらの方式を使う条件を満たした ZIP と ZIPX は編集にも対応します。保持されるメンバーは圧縮データと方式を維持します。AES-256 は既存の Store/Deflate プロファイルに限られます。PPMd I、JPEG、WavPack は明示的に未対応のままです。

<a name="xdzip-filtered-stream-profiles"></a>

## フィルター付きストリームのプロファイル

BZip2（`.bz2`、`.bz`）、LZMA Alone（`.lzma`）、Lzip v1（`.lz`）は単独ストリームでは読み取り専用です。TAR の組み合わせは `.tar.bz2`、`.tar.bz`、`.tbz`、`.tbz2`、`.tar.lzma`、`.tlz`、`.tar.lz` を受け入れます。拡張子は入口を提供し、曖昧な短縮形は実際のバイトで判断します。アダプターは独立アルゴリズムを再利用します。割り当て前に受理を行い、アルゴリズム作業メモリー 128 MiB、既存のストリームバイト制限、連結メンバー最大 100,000 を適用します。BZip2 は各ブロックと結合 CRC を検証し、完全なストリームの連結を許可します。LZMA Alone は[13 バイト形式](https://github.com/tukaani-project/xz/blob/master/doc/lzma-file-format.txt)に従います。最初の 5 バイトはプロパティ/辞書、次の 8 バイトはリトルエンディアンのサイズです。全ビット 1 のサイズは EOS が必須で、サイズ既知の場合は有効なレンジ終端または EOS を許可し、末尾データを拒否します。内容チェックサムなしで構造と読み取り可能性を検証します。Lzip v1 は[形式仕様](https://datatracker.ietf.org/doc/draft-diaz-lzip/02/)に従い、固定 LZMA プロパティ、符号化された辞書の範囲、EOS、トレーラーの CRC32、デコードサイズ、完全なメンバーサイズを検査します。他のバージョンは明示的に失敗します。連結された Lzip メンバーは一つの論理ファイルを構成します。

アルゴリズムのメンバーリーダーは EOF を検証した後にのみ残りの入力を返し、後続コンテナーのバイトを消費してはなりません。別の構築方法は既存 7z リーダーの全範囲/既知サイズの厳格な動作を維持する必要があります。プレフィックス検出と不正入力のテストで分離を証明します。TAR はこれらのフィルターを閲覧と編集に再利用します。圧縮 TAR の解析失敗を通常ファイルの成功に変えてはなりません。LZMA Alone は強いマジックを持たないため、有効な TAR ヘッダー、ZIP SFX、他の強いコンテナー識別より優先されてはなりません。レジストリと入口の宣言には対応する実装と自動受け入れが必要です。レジストリは検査の強さと不明な圧縮サイズを記録し、CLI と UI の一貫した表示を生成します。既知の LZMA サイズが 256 GiB 以上の場合、より小さい実作業予算とは独立に弱い検出から除外します。Windows と macOS はこれらの候補に既存の形式名のない汎用アーカイブ画像を再利用します。

<a name="xdzip-automated-acceptance"></a>

## 自動受け入れ

ストリーム crate の独立した参照リーダー/ライターテストで、メンバーチェックサム、切り詰め、末尾バイト、入力変更、キャンセル、正確なクォータ、仮想名を検証します。runtime テストは分類、空 TAR の優先、単一ファイル作成、検査、展開、公開せずに拒否する動作を対象とします。実際の CLI 回帰は 4 レベルすべてと ZIP 別名を含みます。Qt テストは安定識別子の選択、単一ファイル受理、実際の作成と再オープン、ネイティブアクセシビリティメタデータ、キーボード選択、文字サイズ 100/125/150% の二言語レイアウトを対象とします。生成された宣言、インストーラーの対応付け、ウィンドウと共有コントロールの契約は別々の自動検査を持ちます。実際の結果を作業 issue に記録し、これらの検査を未実行のプラットフォーム動作やリリース許可の証拠としません。

LZ4 と TAR.LZ4 は[標準フレーム契約](lz4-streams.md)を使用します。独立/連結ブロック、宣言された検査、連結/スキップ可能フレームを読み取ります。作成は 256 KiB の独立ブロック、ブロックと内容の XXH32、レベル 1/6/9 を用いた実際の LZ4 圧縮を出力します。通常の LZ4 は一つの通常入力を受け入れ、TAR.LZ4 は作成と編集に共有 TAR ライターを使用します。パスワードと分割は未対応です。検査は宣言されたチェックサムのみを検証し、旧フレームと外部辞書は未対応です。

Zstandard（`.zst`）と TAR.ZST（`.tar.zst`、`.tzst`）は [Zstandard ストリーム契約](zstandard-streams.md)に従います。読み取りは制限付き標準フレームの raw/RLE/圧縮ブロック、Huffman/FSE、反復オフセット、ウィンドウ履歴、宣言された検査、連結、スキップ可能フレームを受け入れます。作成はレベル 1/6/9、128 KiB ウィンドウ、必須 XXH64 を用いた実際の LZ/FSE を使用し、通常の Zstandard は一つの通常入力を受け入れます。TAR.ZST はアーカイブ編集に対応します。パスワードと分割は未対応です。非ゼロ辞書識別子、利用できない外部履歴、予算超過のウィンドウは拒否します。検査は宣言されたチェックのみを検証し、形式にないチェックを約束しません。

<a name="xdzip-rewriting-compressed-tar-archives"></a>

## 圧縮 TAR アーカイブの書き換え

アーカイブ編集は対応する TAR レコードを保持し、外側のストリームを元の形式で再構築します。TAR.XZ、TAR.LZ4、TAR.ZST は既存のフレームライターを通常圧縮で使用します。TAR.BZ2 は 64 KiB の入力チャンクとブロック・ストリーム CRC を持つ BZh1 ブロックを出力します。TAR.LZMA と TAR.LZ は 8 MiB 辞書と終端マーカーを持つ LZMA1 を出力します。Lzip バージョン 1 は CRC とサイズのトレーラーも出力します。TAR.Z は 9 ビットで早期 CLEAR を行うブロック LZW を使用します。TAR.BR は [RFC 7932](https://www.rfc-editor.org/rfc/rfc7932) で定義された非圧縮メタブロックを出力します。この出力は元の Brotli ストリームより大きくなることがあります。

書き換え後、ホストは元ファイルを置き換える前に一時結果を再走査してデコードします。複合 TAR 拡張子は再オープン時に空アーカイブの表示を維持します。曖昧な単独ストリーム拡張子では、最後のレコードの削除時にコミット前に失敗します。[アーカイブ変更契約](../../engineering/archive-transfers.md)を参照してください。
