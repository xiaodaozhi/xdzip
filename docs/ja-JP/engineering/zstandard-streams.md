# Zstandard ストリームの契約

[English](../../engineering/zstandard-streams.md) | [简体中文](../../zh-CN/engineering/zstandard-streams.md) | [繁體中文](../../zh-TW/engineering/zstandard-streams.md) | 日本語 | [한국어](../../ko-KR/engineering/zstandard-streams.md) | [Français](../../fr-FR/engineering/zstandard-streams.md) | [Deutsch](../../de-DE/engineering/zstandard-streams.md) | [Español](../../es-ES/engineering/zstandard-streams.md) | [Português (Brasil)](../../pt-BR/engineering/zstandard-streams.md) | [Русский](../../ru-RU/engineering/zstandard-streams.md)

バイナリプロファイルは [RFC 8878](https://www.rfc-editor.org/rfc/rfc8878.html)、作者の[形式仕様 0.4.3](https://github.com/facebook/zstd/blob/v1.5.7/doc/zstd_compression_format.md)、[XXH64 の仕様](https://github.com/Cyan4973/xxHash/blob/v0.8.3/doc/xxhash_spec.md)に従います。製品のアルゴリズムは Rust の独立実装です。独立した参照ライブラリーとプログラムは管理下の試験データの生成だけに使い、製品の依存関係には含めません。ホストの操作権限と出力確定は[単一ファイルストリーム](single-file-streams.md)の契約に従います。

<a name="xdzip-frame-and-resource-admission"></a>

## フレームとリソースの受け入れ

標準マジック値、予約ビット、ウィンドウの計算、任意の辞書 ID、任意の内容サイズ、ブロックの種類とサイズ、最終ブロック、シードがゼロの XXH64 の任意の下位 32 ビットを検証します。仕様で未使用とされるヘッダービットは読み取り時に無視し、書き込み時はゼロにします。辞書 ID がゼロの場合は辞書を要求しません。ゼロ以外の ID と外部履歴が必要な参照には対応しません。ヘッダーもアーカイブの内容も、他のパスへのアクセスや実行を許可しません。単一セグメントのフレームも割り当て前にウィンドウの上限を満たす必要があります。

ウィンドウ履歴は作業上限 128 MiB のうち 64 MiB までです。ブロックはウィンドウサイズと 128 KiB の小さい方までデコードします。割り当て、インデックスへのアクセス、コピーの前に算術を検査します。非圧縮、RLE、圧縮の各ブロックでデコード済みサイズの計上方法は同じです。物理入力とタスクのバイト上限およびキャンセル条件の範囲で、連結した標準フレームとスキップ可能フレームを扱います。標準フレームが少なくとも一つ必要です。フレーム当たりのブロック数と、標準フレームおよびスキップ可能フレームの合計には 100,000 の上限があります。検出には圧縮入力を最大 8 MiB、デコードした先頭を 512 バイトまで使用します。高い確度でフレームまたは TAR を識別したあとに破損を検出しても、別の判定へ格下げできません。全体走査で終端と宣言されたサイズおよび検査値をすべて確認した後に、実測結果の仮想行を公開します。

<a name="xdzip-entropy-and-sequence-processing"></a>

## エントロピー処理とシーケンス

逆順ビットストリームはゼロ以外の終端マーカーから読み、正確に消費したことを確認します。FSE の正規化頻度、連続するゼロ、テーブルサイズの対数、シンボル範囲、状態遷移、テーブル再利用を明示的に検証します。Huffman の重み、暗黙の最終重み、完全な接頭符号空間、一つまたは四つのリテラルストリームの範囲は実際の出力に一致する必要があります。再利用のエントロピーテーブルと繰り返しオフセットはフレーム境界で初期化し、ブロック間では仕様の状態だけを保持します。リテラル長、一致長、オフセットの追加ビット、リテラルがない場合の繰り返しオフセット調整、重なり、参照可能な履歴を出力前に検査します。不可能または不完全な状態は拒否し、失敗したリーダーを無効にします。ホストの終端 I/O エラー、キャンセル、上限、無効なデータ、非対応プロファイルの分類を維持します。

<a name="xdzip-creation-and-product-integration"></a>

## 作成と製品統合

採用するライターは、圧縮可能な通常の内容に対し、実際に圧縮したシーケンスブロックを使用します。各レベルは上限付きの一致検索量を選択し、空の入力、圧縮不能な入力、複数ブロックの入力を含めて独立にデコードできる必要があります。内容の XXH64 を出力し、形式に適合する非圧縮ブロックだけを代替として使います。フレーム当たりのブロック上限を超える前に次の標準フレームを開始し、履歴、オフセット、エントロピーテーブル、チェックサムを同時に初期化します。書き込み前に入出力バッファーを許可し、完了を明示します。

独立した Zstandard は一つの通常ファイルを受け付けます。TAR.ZST は共通の TAR リーダーとライターを使います。形式の登録ではホスト、実際の CLI、Qt の対応する自動検査を行います。固定した入力元の再確認、キャンセル、厳密なバイト上限、一時準備、失敗時の後処理、最終確定を含めます。作成方式とレベルは共通の形式レジストリに従います。どちらのプロファイルもパスワードや分割ボリュームには対応しません。独立ストリームは書き換えられません。条件を満たす TAR.ZST は[アーカイブ変更の契約](../../engineering/archive-transfers.md)に従い、外側の Zstandard ストリームを再エンコードして書き換えられます。入力フレームでは内容チェックサムを省略できるため、検査には `format_declared_checks` を使います。生成した検証資料は `build/` または CI に置きます。実際のプラットフォーム検証とリリース許可は別々に記録します。

上限付きライターは 128 KiB の独立した一致検索ブロック、非圧縮リテラル、規格で定義済みの FSE テーブル、繰り返しを使わない明示オフセットを使います。LZ4 と四バイトのハッシュチェーン検索を共用します。距離は最大 65535 バイト、レベル 1/6/9 の検索深さは 1/16/64 です。圧縮できないブロックは非圧縮とし、一様なブロックでは RLE を使えます。フレームは 128 KiB のウィンドウを宣言し、内容サイズを省略し、常に XXH64 を含めます。ホストは固定した入力長と一致することを検証します。一つのフレームは最大 65536 ブロックで閉じ、追加の入力がある場合だけ次を始めます。このライターの方針で、リーダーが受け付ける Huffman、FSE、繰り返し、ウィンドウのプロファイルを狭めることはありません。
