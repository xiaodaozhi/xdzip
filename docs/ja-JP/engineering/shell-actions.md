# ファイルマネージャーの操作と独立したタスクホスト

[English](../../engineering/shell-actions.md) | [简体中文](../../zh-CN/engineering/shell-actions.md) | [繁體中文](../../zh-TW/engineering/shell-actions.md) | 日本語 | [Français](../../fr-FR/engineering/shell-actions.md) | [Deutsch](../../de-DE/engineering/shell-actions.md) | [Español](../../es-ES/engineering/shell-actions.md) | [Português (Brasil)](../../pt-BR/engineering/shell-actions.md) | [Русский](../../ru-RU/engineering/shell-actions.md)

システムの入口は、選択内容と操作を同じログインセッションのデスクトッププロセスに渡します。Windows 11 の通常のインストール版では、拡張機能は「その他のオプションを表示」にあります。COM クラスは `IContextMenu` と `IExplorerCommand` の両方を公開します。MSIX は独立した従来メニューハンドラーを宣言し、Store ビルドは後述するモダンメニューハンドラーも追加します。Ubuntu 24.04 の「ファイル」は Nautilus 4.0 拡張機能を使います。macOS では Finder Sync のサブメニュー、サービスコマンド、独立した操作パネルを利用できます。

各プラットフォームの実際の検証と残作業は [#270](https://github.com/xiaodaozhi/xdzip/issues/270) で追跡します。ソースコードの機能は、既に公開されたリリースファイルへ遡って追加されません。

有料アカウント不要の Finder Sync 実装とローカル検証は [#273](https://github.com/xiaodaozhi/xdzip/issues/273) で追跡します。Apple は Finder Sync を同期アプリ向けとしています。本プロジェクトは汎用圧縮メニューへの適用上の制約を受け入れ、App Store の審査を通過したとは主張しません。ローカルの整合性用 ad-hoc 署名には有料アカウント、Developer ID、App Groups、公証は不要で、Gatekeeper による発行元への信頼は得られません。[Apple の Finder Sync ドキュメント](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Finder.html)を参照してください。

## macOS の Finder Sync

`Contents/PlugIns/xdzip-finder-sync.appex` は Qt、Rust、形式ライブラリーのいずれにもリンクしないネイティブ拡張機能です。監視ルートを `/` として Finder のすべてのローカルディレクトリーを対象にし、Finder の選択だけを処理し、ディレクトリーを走査せず、ツールバー、バッジ、同期タスクも追加しません。通常の項目が一つなら作成操作を三つ表示し、複数選択では項目ごとの ZIP 作成を追加します。すべてがアーカイブ候補なら四つの展開操作を追加します。空の選択、非ローカル URL、128 項目を超える選択にはメニューを作りません。ネイティブメニューの寸法はシステムが決め、独立操作には共通の通常密度ウィンドウを使います。

拡張機能が読むのは、ユーザーの Application Support 内の独自 JSON 設定 `xdzip/finder-sync.json` のみです。現在のアプリの場所、切り替え状態、言語、登録リビジョン、ローカルでランダムに生成した引き渡しトークンを含みます。ファイルは 8 KiB 以下、現在のユーザーが所有する 0600 の通常ファイルとし、書き込みはアトミックな置換で行います。リンクや他者の設定は拒否します。CFPreferences ファイルではありません。サンドボックスはこの正確なファイルだけに一時的な読み取り専用例外を与え、ユーザーディレクトリー、App Groups、ネットワークリスナーを共有しません。エンタイトルメントのパスは `/` で始めます。[Apple の一時的例外の仕様](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/AppSandboxTemporaryExceptionEntitlements.html)を参照してください。

Finder はメニュー項目の `representedObject` を保持しないため、拡張機能は単調増加するタグで、上限付きの選択スナップショットを保持します。期限切れのタグは新しい選択を参照できません。明示した `NSWorkspace` の宛先を通じて、拡張機能は `xdzip-shell://v1/` の base64url JSON イベントを `Contents/Helpers/xdzip-shell-relay.app` に送ります。サンドボックス内の呼び出し元が渡す起動引数には依存できません。relay は Qt にリンクしない独立したネイティブアプリです。現在のユーザーの非公開設定にあるランダムトークンを認証し、URL、UUID、操作、パス、JSON の上限を検証し、UUID を保持して既存の非公開リクエストファイルと単一インスタンスの入口を呼び出します。受け入れ失敗時にはネイティブエラーを表示します。トークンはリクエストファイル、デスクトッププロトコル、製品ログに含めません。正しいトークンのない外部構築 URL はファイル操作を実行しません。URL はローカル引き渡し専用です。

拡張機能は固定されたバンドル構造から自身を含むアプリを特定し、サンドボックス内で外側のアプリのメタデータを読みません。relay は呼び出しのたびに外側の `Info.plist` を再読込し、製品の識別情報、`XdzipShellProtocol=1`、`XdzipFinderSyncProtocol=1`、有効な実行ファイル名を要求します。ロールバックされた対象や互換性のない対象は拒否します。読み込み済みの古い拡張機能が一時的にメニューを保持しても、relay はクリックを拒否しなければなりません。サービスは既存のプロトコルを独立して検証します。

インストール済みアプリは初回起動時に自身の appex とサービスを登録します。ユーザーはシステム設定で Finder 拡張機能を有効にする必要があります。設定の切り替えは両方の入口を管理します。アプリの言語変更は拡張機能のメニューだけに適用され、サービス名はシステム言語に従います。設定を繰り返し保存しても、変更のない appex を再追加して Finder との接続を切りません。内容のダイジェストが変わるか、登録が存在しない場合だけ再登録します。無効化はそのアプリの正確なパスの登録だけを削除し、無効状態の設定を保持します。古いコピーのアンインストールは新しいアプリの設定を無効にしません。明示登録した開発版は無効化後に設定から再度有効化できます。未登録の開発版は自動的に有効化しません。

更新時に Finder が古い拡張機能インスタンスを保持する場合があります。必要ならシステム設定で自分の拡張機能を無効化し、再度有効化してください。Finder を強制終了しません。ロールバックとアンインストールは所有する登録とファイルだけに触れ、既定のファイル関連付けを変更しません。サービスの位置はシステムが管理し、コンテキストメニューの最上位に表示される場合があります。

## Windows パッケージの境界

MSIX ビルドは Windows 11 の「その他のオプションを表示」用に `desktop9:Extension` で従来の `IContextMenu` ハンドラーを宣言します。Store ビルドはさらにモダンメニュー用の独立した `IExplorerCommand` クラスと `windows.fileExplorerContextMenus` を宣言します。クラスは異なる識別情報を持ち、それぞれのメニューインターフェースだけを公開します。サイドロードビルドは従来クラスだけを宣言し、通常のインストーラーは既存の従来メニューを維持します。ファイル操作と非公開リクエストの検証は両メニューで共通です。

`--msix-channel store|sideload` は不変のパッケージマーカーと対応するマニフェスト宣言を選択し、既定は `sideload` です。モダンコマンドには、Windows 11 に登録された Store ビルドで、そのパッケージ自身のシステム署名種別が `Store` であることが必要です。署名照会失敗や Developer、Enterprise、None の署名ではモダン項目を表示しません。Store 署名済み Store ビルドのコピーは、サイドロードでインストールしても Store ビルドのままです。これはビルドチャネルの方針であり、同一の署名済みバイトのインストール経路を識別したとの主張ではありません。[Microsoft による制約の議論](https://github.com/microsoft/WindowsAppSDK/issues/4993)を参照してください。

拡張機能は Explorer プロセスの識別情報ではなく、自身の DLL のパッケージディレクトリーと現在のユーザーの登録を解決します。各呼び出し前に登録と実行ファイルのシェルプロトコルを再確認し、そのパッケージの AUMID を起動します。登録がない場合や置き換えられた場合は実行を拒否します。パッケージメニューの言語と有効状態は通常のインストールメタデータとは別のファミリー固有キーを使います。アプリはパッケージ識別情報で通常版の COM 登録を書きません。マニフェスト登録とアンインストールは Windows が管理します。実際の Store 署名、Explorer での表示、更新、共存の受け入れは自己署名フィクスチャーの確認と別です。Windows 10 には Windows 11 のモダンメニューがなく、現在のサポート範囲外です。

[GetStagedPackageOrigin](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getstagedpackageorigin) が示すのは準備済みパッケージの出所であり、ユーザーごとに検証されたインストール経路ではありません。診断用に保持し、モダンメニューの許可には使いません。

出所を比較するには、対象パッケージが現在のユーザーに登録された Windows で次の読み取り専用診断を実行します。パッケージ名は例です。出力は `build/` 内の新しい JSON ファイルにします。診断はシステム署名種別、準備済みパッケージの出所、完全なパッケージ名の匿名化ダイジェストを記録し、登録バージョンが一意でない結果を拒否します。シナリオは操作者のラベルで、インストールチャネルを証明しません。照会失敗、不明な値、同一の結果だけではメニューを許可できません。証明書、インストール、システム設定の変更は不要です。

```powershell
python scripts/msix-origin-probe.py --name xdzip.Example --scenario store-install --output build/store-origin-observation.json
```

## 選択と出力

シェルからの作成確認は、既定のダウンロードディレクトリーを先に確認せず、あらかじめ入力されたソースディレクトリーまたは選択された出力先を直接検証します。これにより無関係な macOS のプライバシーアクセスの遅延を避けます。通常のメインウィンドウからの作成では既定の出力先を維持します。

作成にはクイック ZIP、7z、確認付き作成、複数選択時の項目ごとの ZIP があります。単一の通常ファイルは `a.txt.zip` のように完全な名前を保持し、フォルダーは `foo.zip` を使い、同一ディレクトリー内の結合選択はそのディレクトリー名を使います。複数ディレクトリーにまたがる結合選択は出力先を確認するため独立した作成ウィンドウを開きます。クイック作成は通常のレベルを使い、暗号化や分割を行いません。出力名が衝突した場合は既存の競合確認を使います。

展開操作は、選択したすべての項目が対応する拡張子または分割ファイル名によるアーカイブ候補である場合に表示されます。メニューはファイル内容を走査しません。実際に開く際に Rust が完全な分割グループを検出し、内容、ソース、形式の機能を検証します。同一の完全なソースグループは展開バッチ内で一度だけ実行されます。プロセス内の不透明なソースグループマーカーはファイル識別情報を保持しますが、書き込み権限ではありません。

- 現在のディレクトリー: 各アーカイブをそれぞれの親ディレクトリーへ直接展開します。
- スマートディレクトリー: 完全に検証済みの出力グラフに、暗黙のディレクトリーも含めて最上位ディレクトリーが一つだけある場合に限り外側のフォルダーを追加しません。ルートのファイルや複数の最上位項目にはアーカイブ名のフォルダーが必要です。内部ディレクトリーは取り除かず、名前も変えません。
- アーカイブごとのディレクトリー: アーカイブ名の外側フォルダーを必ず追加します。保持する出力先の権限で排他的に予約し、既存のファイル、ディレクトリー、リンクは再利用しません。`name (2)` のような新しい番号付きの名前を最大一万回の試行で選びます。
- 選択したディレクトリー: 独立した展開ウィンドウで共通の出力先を選びます。既定はアーカイブごとのディレクトリーで、スマートまたは直接結合も選べます。

ディレクトリー名の導出は、[安全な展開](../../engineering/zip-safe-extraction.md)の移植可能な名前と `.app` 拡張子の規則に従います。スマート判定は出力を許可しません。各タスクで出力先、ソース、CRC または認証、競合、公開権限を再検証します。個別アーカイブの失敗は既存のアーカイブ全体の停止方針に従い、バッチの調整役は次のアーカイブに進みます。

## プロセス、リクエスト、ウィンドウ

非公開デスクトップ入口は `--shell-request <request.json>` で、独立 CLI のスクリプトインターフェースではありません。ネイティブ拡張機能は選択マニフェストだけを作成してデスクトップ入口を起動し、Qt や形式ライブラリーを読み込みません。マニフェストはシステム一時ルート内に排他的に作成した非公開ディレクトリー `xdzip-shell-<ランダムな16進数32桁>` に置き、ファイル名は `request.json` に固定します。Windows は書き込み前に現在のユーザーと SYSTEM 用の保護された DACL を設定し、POSIX は 0700 のディレクトリーと 0600 のファイルを使います。デスクトップはリンクを追跡しない共通の Rust 機能とディレクトリー権限でルート、所有者、権限を検証し、最大 256 KiB を読み、リンク、相対パス、不正な Unicode、未知の操作、128 件を超える選択を拒否します。

リクエストはスキーマ 1、UUID、操作、絶対パスを含みます。任意の真偽値 `archive_candidates` はファイルマネージャーが既に知っている MIME または UTI のヒントだけを渡します。共通の拡張子・分割規則とともにメニュー表示を決めますが、I/O を許可せず Rust の内容検証も回避しません。Windows は拡張機能に登録された Content Type、Nautilus は FileInfo の MIME、macOS ヘルパーは URL の Content Type を読みます。いずれもファイルマネージャー内でアーカイブを解析しません。単一インスタンスプロトコルは既存の開く操作と CLI 操作を維持し、構造化された `shell_action` を追加します。受け入れと実行成功は別に判定します。アプリは受け入れたリクエストの識別情報を最大 128 件保持します。同じ識別情報と内容は一度だけ受け入れ、同じ識別情報で内容が違えば拒否します。受け入れ後に削除するのは固定ファイルと空のディレクトリーだけで、外部入力を再帰的に消去しません。

シェルからのコールド起動は `ShellHost` だけを作り、非表示のメインウィンドウを作りません。通常のファイルオープンまたは明示的なメインウィンドウ表示で、必要に応じてブラウザーウィンドウを作ります。既存インスタンスがシェル操作を受け取っても、ブラウザーのタブを切り替えず、非表示のメインウィンドウを復元しません。操作セッションは既存の上限付きセッション枠を使い、バッチはコントローラーを順次再利用してアーカイブごとのブラウザーページを作りません。

`OperationTasks` はブラウザーと独立入口で進捗、結果、パスワード、競合のウィンドウを共有します。最上位の `OperationWindow` は所有者を持たない場合があります。所有者があれば呼び出し元に従い、なければ選択画面内に制限します。モーダル確認は実際の操作ウィンドウに属し、終了確認は `OperationConfirmationWindow` を再利用します。レイアウト、共通コントロール、二言語、アクセシビリティーの要件は[視覚ワークフロー](../visual/design-workflow.md)に従います。

macOS の単一インスタンス識別には現在のユーザーと Security framework の実際のログインセッション ID を使います。照会に失敗した場合は、ヘルパーに存在しない可能性のある環境変数に頼らず選出を拒否します。通常起動、Finder relay、サービスは同じログインセッションのインスタンスに到達します。[SessionGetInfo](https://developer.apple.com/documentation/security/sessions) を参照してください。

シェルからの作成と展開は `TaskWindow` の進捗・結果表示を再利用します。バッチは各実際の状態とエラーを同じレイアウトで表示します。タスク受領前の送信失敗は結果表示だけを作り、架空のタスクを作りません。シェルウィンドウは現在の画面の利用可能領域の中央に置き、確認は実際の呼び出し元ウィンドウを保持します。Windows の従来入口はシステムが対応する `Position=Top` を要求し、Explorer が動的メニュー照会後に「プログラムから開く」を追加してもその前に表示されるようにします。ルートと列挙された操作はアプリ、形式、システムフォルダーのアイコンを使い、Windows がネイティブ寸法を管理します。

## バッチ完了と終了

各バッチは実際の成功、失敗、キャンセル、未実行項目、分割グループの重複排除を記録します。個別の失敗は残りを停止しません。キャンセルは後続項目を停止し、準備中または実行中のタスクへ既存のキャンセル要求を送ります。既に確定した出力は残り、バッチ全体のロールバックは保証しません。準備、パスワード待ち、競合、キャンセル、クリーンアップは全体のアクティビティーと終了バリアに含まれます。

独立した作成ウィンドウがタスクの受領を得ていない場合、送信拒否後も入力、パラメーター、エラーを残して編集・再試行できます。タスクの終端状態を作らず、バッチのインデックスも消費しません。クイック操作には設定ウィンドウがなく、送信失敗を記録してバッチを続けます。

シェルからの作成成功はアプリ内で開く要求を送らず、展開の「完了時にフォルダーを開く」は既定でオフです。独立操作の成功結果は出力先を開くために利用できます。完了時にフォーカスを奪いません。意図的に閉じたウィンドウはタスク入口からバッチ結果を再度開けます。トレイを無効にするかホストを失うと、閉じた結果は非表示のままです。表示中または最小化されたメインウィンドウはタスク入口を提供し、それがなければ非表示のアクティブタスクだけを復元します。トレイかアクセス可能なメインウィンドウがあれば作業中に進捗を閉じられ、どちらもなければ先に待機またはキャンセルを選びます。アクセス可能なウィンドウ、トレイ、アクティブタスクがなくなったら、終了前にすべての Rust 接続の終了を待ちます。開いている設定ウィンドウはユーザーが閉じるまで利用できます。

## インストールと互換性

インストール版は既定で統合を有効にし、一般設定で無効にできます。登録は所有する項目だけを管理し、既定のファイル関連付けを変更しません。ポータブル版と開発版は自動登録しません。明示的なデスクトップ入口 `--register-shell-integration` と `--remove-shell-integration` は、メインウィンドウを表示せず制御された登録と削除を行います。

インストーラーは単一引数の正確な同期・削除コマンドを使い、インストールトランザクションの起動ロックを解放する前に所有する統合メタデータだけを更新します。通常のファイル、シェルタスク、メインウィンドウの起動には引き続きランタイムの受け入れが必要です。Windows のインストール済み識別は、現在のユーザーに登録された製品の識別情報、インストール先、ファイルマニフェストを確認します。ポータブルディレクトリーは配布マニフェストがあっても自動登録しません。

引き渡し前にデスクトッププロトコル 1 を検証し、読み込み済みの拡張機能がロールバック後に古いアプリへリクエストを送ることを防ぎます。Windows は GUI 実行ファイルのバージョンリソース `XdzipShellProtocol` を読み、所有する `Applications/xdzip.exe` の登録コマンドが同じ実ファイルを指すことを検証します。関連付けランチャーはプロトコル機能を主張しません。旧バージョン付き配置に戻した後、ルートに残った新しい実行ファイルはシェルの対象でなくなり、既定の関連付けは読まず変更しません。macOS ヘルパーはキャッシュされた NSBundle 状態ではなく、対象の Info.plist の製品識別情報、プロトコル、単一の実行ファイル名を毎回再読込します。Ubuntu パッケージは `/usr/share/xdzip/shell-protocol` を所有し、古いパッケージへのロールバックやアンインストールでマーカーを削除します。対象が存在しない、不明、非互換、または現在の登録先でない場合は起動を拒否します。機能マーカーは引き渡しの互換性だけを管理し、リクエスト、Rust の内容、出力先の検証を置き換えません。

Windows は独自の CLSID と従来コマンドを HKCU に保存します。コマンドは別のクラス識別情報を使い、Explorer がキャッシュした旧クラスファクトリーによって更新時に抑止されないようにします。統合の有効化・無効化で削除するのは対応する旧メニューハンドラーと所有する旧クラスだけです。旧ハンドラーを復元する履歴ロールバック後は、残った新コマンドが自身を隠して重複を防ぎます。インストーラーはロールバックをまたいでコマンドとクラスのアンインストール所有記録を保持します。ランタイムディレクトリーには内容のダイジェストで命名した拡張 DLL と検証マニフェストがあり、更新中に Explorer が読み込んでいる同名 DLL を上書きしません。古いファイルのクリーンアップはインストーラーの所有・使用中の方針に従い、Explorer を強制終了しません。macOS のインストール済みアプリは初回の通常起動時にユーザーの Library/Services に自身のサービスをインストールします。ヘルパーは選択の収集と引き渡しだけを行い、統合の無効化時には確認済みの所有ファイルだけを削除し、追加内容、リンク、所有者の不一致は保持して報告します。サービスの表示と有効化はシステムが管理します。

Ubuntu のネイティブ拡張機能はインストールパッケージによって Nautilus 4.0 の拡張ディレクトリーに登録され、同じユーザーの設定を読みます。実行中の「ファイル」は古いモジュールを保持する場合があります。更新するには、自動的にファイルマネージャーを終了せず「ファイル」を再度開きます。独立したランタイムディレクトリーはシステムの拡張ディレクトリーに自動的に書き込みません。統合コンポーネントを明示的にインストールしてください。
