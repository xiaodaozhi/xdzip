# 压缩包完整性检查

[English](../../engineering/archive-checking.md) | 简体中文

工具栏“测试”对符合条件的当前归档执行一次真实后台检查，覆盖全部物理记录，包含重复名称、目录和空文件，不受当前目录、搜索或选择影响。进入磁盘索引的归档暂不支持整包检查，见[大归档索引](large-index.md)。检查只持有冻结的输入来源与元数据，不取得目标目录授权、不创建暂存或输出文件，不使用解压路径映射和链接发布流程。

UU/UUE 和 XXE 检查文本封装中的每个物理成员，包括空文件与同名记录，验证计数行或已准入的 Base64 填充及精确结束标记。它们不提供校验和或认证，替换有效字母表字符可能改变内容而不报错。头部路径与权限不直接授予输出或执行能力，详见[文本封装契约](text-envelopes.md)。

Z 与 TAR.Z 验证 Unix compress LZW 码、字典边界、CLEAR/码宽对齐及物理 EOF，TAR.Z 另验证完整 TAR 记录与末尾。格式没有内容校验和、解码大小字段或认证，结构检查成功不能发现所有保持结构的替换或有效码尾部。继续使用相同受控源和任务限额，详见 [compress 契约](compress-streams.md)。
## 格式与结果

普通 GZIP、BZip2、LZMA Alone 和 Lzip v1 解码到同一有界丢弃接收器，验证精确终止和观察尺寸。GZIP 检查逐成员 CRC/ISIZE，BZip2 检查块与组合 CRC，Lzip 检查 CRC、数据尺寸和完整成员尺寸。LZMA Alone 无内容校验和，成功只表示结构与可读性成立。压缩 TAR 组合重新扫描完整容器及压缩 EOF，不再另解一次负载。检查强度由[内置能力表](format-registry.md)登记，边界及组合见[压缩流契约](single-file-streams.md)。

ZIP／ZIP64、Store／Deflate、受支持的编号分卷和 PKZIP 分卷逐条解码到有界丢弃接收器。检查包括中央目录与本地头、描述符、大小、压缩流准确终止、CRC，以及受支持 AES-256 的认证。安全名称的 ZIP 符号链接只检查负载，不解析目标或创建链接，因此不受写出链接的平台限制。未知方法、加密方式、危险名称与其他未准入记录仍失败，不跳过后宣称整包通过。

7z 和 RAR 使用隔离工作进程中的独立 Rust 后端，逐物理条目解码到同一个有界丢弃接收器，验证解码终止、声明大小和容器实际提供的校验。固实块内为到达当前选择而解码的其他数据只累计工作量，不增加当前文件的已验证计数。目录、空文件和加密条目均不能跳过后报告整包成功。RAR 旧版、RAR5 和 RAR 7 新算法分别使用独立已知内容样本验收，不能仅以相同魔数代表版本兼容。

CAB 使用隔离工作进程内的自研 Rust 容器与共享算法，验证卷集合、实际解码大小和完整数据帧提供的校验。ISO/UDF 检查描述符、目录、数据范围和声明大小，并实际读取所有受支持普通文件；它们没有普遍的逐文件内容校验和，不能发现任意保持结构的内容篡改。镜像链接、设备及其他不支持记录不能跳过后宣称整包通过。混合镜像检查冻结的 UDF 命名空间，不在失败后改查 ISO 命名空间。

TAR 与 TAR.GZ 在检查任务内重新顺序扫描完整流，对照冻结的物理记录元数据，检查头校验、长度、两个结束块及尾部。TAR.GZ 继续消费到 EOF，核对 GZIP CRC／ISIZE，不在完整扫描之后再次解压全部内容。TAR 没有文件内容校验和，只能确认格式结构与可读性，无法发现任意保持结构的内容篡改。TAR 链接、特殊对象和稀疏文件仍不支持。本功能不证明归档来源可信，也不检查恶意软件。

复合文件（MSI）检查容器结构及原始数据流的可读性，没有内容校验和。NSIS 仅提供静态安装器元数据。具体边界见 [MSI 与 NSIS 格式说明](wim-msi-installer-format-sources.md)。

首个结构、负载、来源、资源或不支持条目错误结束任务。结果区分成功、失败与取消，显示已验证及未检查文件数，保留失败条目和稳定错误码。所有物理记录均参与校验，`files`／`verified_files` 仍只统计非目录文件，空文件参与文件数。目录和纯目录包也必须完成结构校验后才能成功。检查中或此前已完成的读取不等于整包通过。

## 调度、来源与资源

`Check { session }` 冻结来源 `Source::fork()`、格式、元数据和原始会话身份，进入与创建、解压相同的有界重任务队列及应用级串行准入。开始、读取后及成功终态前复核来源句柄、全部卷路径的身份、大小和时间信息。来源变化返回 `source_changed`，只失效对应的原会话。此检测是尽力检查，不是输入内容的原子快照，不承诺检测保留身份和时间信息的并发原地修改。

实际解码受单文件 8 GiB、任务累计 20 GiB 限制，错误密码重试不重置累计工作量。ZIP 保留独立 64 MiB 定位元数据预算和共享 20 GiB 实际输入读取预算；TAR／GZIP 保留既有 24 GiB 整流读取上限。7z／RAR／CAB／ISO／UDF 额外使用原生进程 1 GiB 内存上限，输入读取与固实跳过同样有界，超限为资源限制而非完整性通过。任务与事件数量、快照明细和保留内存沿用既有队列上限。成功终态不设置写入、提交、保存目录或输出路径计数。

任务种类由 `kind=check` 明确传至 Qt。`read_bytes` 表示实际来源读取量，包含头部与重试；`decoded_bytes` 表示实际解码工作，`verified_bytes`／`verified_files` 只在要求的校验完成后增加。TAR／GZIP 完整扫描期间不编造文件级百分比，实际读取量与速度仍可见，成功后才将整流文件计为已验证。

AES 密码复用[密码协议](password-extraction.md)：独立控制槽、一次性提示身份、任务内缓存、最多每条十次错误验证值响应、认证破坏直接失败及秘密归零。取消和退出唤醒密码等待，不依赖普通命令队列容量。关闭浏览页或进度窗口不取消已接收任务，结果从全局任务入口重开；明确退出仍等待取消与异步 join。

## 验证边界

核心回归覆盖支持格式、空文件、目录、重复名称、ZIP 链接负载、密码重试／取消、损坏负载、来源变化、实际计数和无输出。桥接与 Qt 验证真实工具栏到后台任务和结果闭环，密码路由、历史任务、跨会话准入及退出独立检查。双语多字号、浅深色与原生桌面视觉验收分别登记在 issue，生成证据仅保存于 build/ 或 CI 工件。

旧式 RAR 加密条目缺少可可靠区分错误密码与损坏内容的验证值，因此每个加密条目解码前分别请求密码，不能把前一条密码直接套用到可能使用不同秘密的下一条。RAR5 和受支持的其他格式继续任务内复用。未取得可信密码验证值的加密解码或加密头完整性失败报告 `password_or_integrity`，保留错误密码或内容损坏的歧义；明文头校验、来源变化、取消、限额及输出 I/O 不误归类为密码问题。

包含未知原始大小的归档仍可浏览；整包检查的总量标为未知，并在打开 payload 或请求密码前以 `unsupported_feature` 失败，已验证和解码产量保持实际值。未知大小不按空文件验证，也不将内部 sentinel 用作进度分母。

XZ 和 TAR.XZ 使用 `format_declared_checks`，须验证声明的 CRC32、CRC64、SHA-256 和结构字段；声明 None 的流没有内容校验和。界面须说明此区别，不承诺每份输入都有内容校验和。新增未加密 ZIP 方法 9、12、14、95 仍须满足精确解码尺寸及外层 ZIP CRC，LZMA 数据描述符配置须有 EOS。未知方法可展示，但不能计为内容验证成功。

AES Crypt 使用 `format_declared_checks` 和保留的打开密码。元数据准入及实际任务解码都必须通过完整密文 HMAC。0–2 版不认证尾部长度模值，扩展字段也未认证。检查成功仅表示格式声明的检查通过，范围见 [AES Crypt 契约](aescrypt-envelopes.md)。

Brotli 与 TAR.BR 使用 `structure_and_readability`，必须通过完整流结束、声明的元块大小和全部准入词典/历史变换，Brotli 本身不提供内容校验和。详见 [Brotli 契约](brotli-streams.md)。

LHA/LZH 使用 `format_declared_checks`，实际解码全部受支持普通文件，验证准确长度和所有存在的头部、载荷 CRC-16。古老 0 级成员可缺少 CRC，此时仅检查结构、尺寸与可读性；LH2 必须按 CRC 约束执行有限变体准入。未知方法、异常名称、链接或特殊对象不能跳过后宣称整包成功，详见 [LHA 契约](lha-containers.md)。

PMA 使用 `format_declared_checks`，完整解码准入的 PM0/PM1/PM2，核对准确尺寸及存在的载荷 CRC-16；缺少 CRC 的成员仅检查结构、尺寸和可读性。未知方法和其他不支持条目阻止整包成功。CP/M 填充作为物理容器结构验证，位于成员压缩区间之外，详见 [PMA 契约](pma-streams.md)。

ARJ 使用 `supported_content`。完整元数据准入验证主头部、文件头部及扩展头部 CRC-32；检查通过 Store 或方法 1–4 完整解码所有准入普通成员，核对准确尺寸和必需载荷 CRC-32，旧文本保留 CRC 覆盖的原始字节，不转换换行。未知或不支持记录阻止整包成功，详见 [ARJ 契约](arj-streams.md)。

ARC 使用 `supported_content`，完整验证物理结构，通过旧/新 Store 或方法 3–9 实际解码，核对准确尺寸及必需 CRC-16/IBM。不跳过未知方法、可疑名称或不支持配置后宣称整包成功。头部 SHA 绑定用于冻结快照，不提供认证，详见 [ARC 契约](arc-streams.md)。

BH 使用 `supported_content`，完整验证 `BH 05 07` 成员结构、方法 8 raw Deflate 结束、准确解码长度和必需 CRC-32。未知方法、固定字段错误、可疑名称和不支持配置仍保持可见，但会阻止整包检查成功，详见 [BH 契约](bh-containers.md)。

ALZ 使用 `supported_content`，完整验证单卷结构、Store 或原始 Deflate 的载荷结束、准确解码长度和必需 CRC-32。加密、数据描述符、改造 BZip2、分卷和未知方法记录保持可见，但会阻止整包检查成功，详见 [ACE、ALZ 与 EGG 资料门槛](ace-alz-egg-format-sources.md)。

EGG 使用 `supported_content`，完整验证无加密、非固实普通单卷结构、Store 或原始 Deflate 块结束、准确块尺寸和必需 CRC-32。AZO、BZip2、LZMA、加密、分卷、固实和未知方法记录保持可见，但会阻止整包检查成功，详见 [ACE、ALZ 与 EGG 资料门槛](ace-alz-egg-format-sources.md)。
