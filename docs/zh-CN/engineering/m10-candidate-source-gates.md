# M10 候选格式资料和许可门槛

本记录收口 M9 之后的 Bandizip 清单候选格式。公开描述线格式，不等于允许发布解码器。参考实现，也不等于可以再分发的产品依赖。下面的资料均不链接进 xdzip。候选格式只有在源码版本、许可文本、完整样本、资源模型和失败行为冻结后，才能进入格式登记。

## DAA 1.0

- **公开规范**：没有找到厂商发布的 DAA 1.0 规范。公开资料把 DAA 描述为 PowerISO 的专有磁盘或归档镜像，通常包含头部、分块长度表和逐块压缩的 ISO 数据。公开记录涉及 zlib、LZMA 和后来的内部版本 110，但没有稳定的 1.0 契约。
- **参考实现**：`daa2iso` 0.1.7e，Debian 和 Fedora 的 GPL-2.0-or-later 软件包。它只能用于历史研究。当前无法从权威公开仓库固定上游 Git 提交，也没有厂商规范可固定。
- **许可和再分发**：实现使用 GPL-2.0-or-later。该许可没有授予 DAA 专有技术的产品权利，项目也没有可把解码器发布到 xdzip 的独立许可记录。
- **完整样本**：公开样本通常是来源和版本未固定的磁盘镜像或多卷归档。当前没有登记覆盖旧头部、版本 110、多卷顺序、zlib、LZMA、混淆、校验和畸形分块的可再分发语料库。
- **净室可行性**：在获得稳定线格式记录和法律结论后，有界 ISO 重建在技术上可能可行。仅依赖 GPL 解码器做逆向，不能作为产品实现依据。
- **能力边界**：未来切片可以把一个完成验证的镜像暴露为只读虚拟 ISO，并限制分块范围、解压大小和输出额度。密码、混淆和多卷变体需要各自的契约和样本。不能挂载、启动、写回或执行镜像。
- **结论**：**阻塞**。缺少公开的 1.0 规范、固定源码版本和完整可再分发语料库，暂不能作出可辩护的准入决定。

## ISZ

- **公开规范**：EZB Systems，《ISZ File Format Specification》1.00 版，修订日期为 2006 年 7 月 3 日，定义 `IsZ!` 签名、固定头部、可选分段定义表、块定义表和数据块。头部包含扇区尺寸、总扇区数、密码模式、分段尺寸、块数、块尺寸、指针长度、分段号、表偏移和数据偏移。块标志区分零块、存储块、zlib 块和 BZip2 块。可见 [ImgBurn 规范副本](https://forum.imgburn.com/topic/14260-isz-images-supporting/#comment-115553)，并由 [FileFormat.ArchiveTeam](http://fileformats.archiveteam.org/wiki/ISZ) 索引。
- **参考实现**：CDEmu `libmirage` 的 ISZ 过滤器，提交 `39fcffe09739e1dc40bef4781646f9ffb8b7dc4e`，以及 Play- 的 `IszImageStream`，提交 `5bb010f27d8e2309f37b1f8eba0f74ecd546b29b`。二者只用于参考分析。`Helias/isz-tool` 是 Python 读取器，但本环境未能取得权威不可变提交和许可记录。
- **许可和再分发**：EZB 规范第 8 节写明，把 ISZ 技术并入产品需要联系 EZB，取得带条件的免费许可。公开文本或宽松许可的独立读取器，都不能自动取消产品许可门槛。CDEmu 和 Play- 不作为 xdzip 依赖。
- **完整样本**：可以用公开工具生成有效的 Store、zlib 和 BZip2 块，但完整可再分发矩阵还需要单卷和分段镜像、零块、不同指针长度、精确尾块、密码模式、表混淆、截断、偏移越界和来源变化样本。仓库尚未登记这样的自有语料库。
- **净室可行性**：无加密、单卷、只读子集在技术上可以与 ISO 浏览分开。首个实现可以把四种有文档的块解码成一个虚拟 `image.iso` 文件，不挂载，也不执行启动镜像。但在编码前必须取得法律许可、固定不可变参考和完整夹具集。
- **能力边界**：门槛通过前，不登记 `.isz`，不因 `IsZ!` 自动宣称支持，也不开放密码、AES、分段、写入或直接光盘浏览。未来准入时必须验证头部和版本、指针表与分段表、XOR 或反混淆规则、块和数据范围、逻辑尺寸运算、完整块结束、取消以及输入、工作和输出额度。
- **结论**：**等待法律与语料门槛，当前阻塞**。线格式已有足够描述，技术上可设计有界读取器，但当前证据不足以授权产品实现。

## ZPAQ

- **公开规范**：Matt Mahoney，《The ZPAQ Open Standard Format for Highly Compressed Data》2.03 和 2.06 版。格式在块头中保存 ZPAQL 解压程序，支持固实块、日志更新、去重、SHA-1 记录，较新级别还涉及加密和分卷。
- **参考实现**：`zpaq/zpaq` 的 `6.22` 标签及对应 `libzpaq` 源码。本评估把该标签作为固定研究参考，但真正开始实现前仍需记录提交哈希和许可文本哈希。
- **许可和再分发**：参考实现和配置文件使用 GPLv3。按当前不引入第三方归档运行时的政策，不能链接进产品。公开标准支持净室分析，但解码虚拟机和配置语料仍需独立实现与复核。
- **完整样本**：有效语料库需要覆盖 1、2 级块、任意 ZPAQL 程序、日志更新、去重、加密和分卷记录、SHA-1 校验，以及畸形虚拟机和块边界。仓库没有这套自有语料库。
- **净室可行性**：理论上可行，但这是虚拟机和资源计量项目，不是小型容器解析器。必须分别计量字节码执行、模型内存、解压输出、历史窗口和去重状态。
- **能力边界**：未来第一切片只能是只读、无加密、非分卷、非日志更新，并声明支持的虚拟机子集。不自动获得创建、更新、密码或无界固实解压能力。
- **结论**：**阻塞**。虽然有公开规范，但 GPL 参考实现、缺少完整语料库和高风险解压虚拟机使其不能在 M10 准入。

## PEA

- **公开规范**：PeaZip，《Pack, Encrypt, Authenticate》规范，覆盖 PEA 1.x、仍处于提案状态的 PEA 2.0 流、多流和分卷控制、对象控制、结束标记以及 PCOMPRESS 级别。规范见 [`pea_help.pdf`](https://peazip.github.io/pea_help.pdf)，摘要见 [pea-file-format.html](https://peazip.github.io/pea-file-format.html)。当前官方页面明确说明 PEA 和 PCOMPRESS 规范属于公有领域。
- **参考实现**：`peazip/PeaZip` 11.4.0 源码发布包，以及其中的 `pea` 引擎。实现使用 LGPLv3，随附的 Wolfgang Ehrhardt 密码单元使用 zlib/libpng 许可。源码发布地址为 [peazip-11.4.0.src.zip](https://github.com/peazip/PeaZip/releases/download/11.4.0/peazip-11.4.0.src.zip)，在把它作为样本判定工具前仍需记录不可变提交和源码哈希。
- **许可和再分发**：格式规范本身没有产品许可阻塞，但 LGPLv3 引擎和密码依赖不能默认复制或链接进当前产品。净室 Rust 实现应依据公有领域格式记录并独立选择算法，参考程序只用于测试，不能成为运行时依赖。
- **完整样本**：完整语料库必须包含 PEA 1.x 和 2.0、多流、分卷边界、Store 和 PCOMP 级别、认证失败、加密头部、畸形结束标记和大尺寸声明。仓库尚未登记可再分发的自有语料库。
- **净室可行性**：无加密、单流、Store 或 Deflate 读取器在技术上可行，但认证和加密必须作为独立安全工作。由于该格式有完整性设计，仅做结构解析不能宣称内容验证完成。
- **能力边界**：未来应先只读，不开放密码、加密、多卷、创建或修改。每个流都要在发布前通过声明的摘要和终止认证。
- **结论**：**等待不可变参考版本和完整认证样本，当前阻塞**。公有领域规范已经清除格式文本许可门槛，但 PEA 仍需固定源码快照、独立完整样本和有界完整性模型后才能进入登记。

## BOND

- **公开规范**：没有找到 Bandizip BOND 归档的规范、签名、版本或压缩契约。Bandizip 近期更新说明提到“某些 BOND 文件”漏洞，但这不是线格式定义。公开 `.bond` 扩展数据库主要描述 Microsoft Bond 模式数据，与归档格式不同。
- **参考实现**：没有找到能够证明其为归档格式、拥有固定版本和可再分发许可的参考实现。
- **许可和再分发**：未知。在格式所有者、技术权利和参考条款明确前，不得准入产品或解码器。
- **完整样本**：没有可信、版本化来源的完整样本。仅凭文件名扩展不能确定夹具身份。
- **净室可行性**：在无法区分归档、Microsoft Bond 数据或其他二进制载荷前，无法评估。
- **能力边界**：不识别，不登记后缀，不浏览，不解压，不检查，不创建，不处理密码或分卷。
- **结论**：**阻塞，且尚未确认是 Bandizip 归档格式**。只有权威 Bandizip 来源或厂商披露格式身份和完整语料库后才能重开。

## J2J

- **公开规范**：没有找到 J2J 归档的规范、签名、版本或开发者记录。历史 Bandizip 功能列表曾把 J2J 列为只解压，现代官方格式页面没有技术定义。其他 J2J 搜索结果指向 job-to-job 数据集或 JPEG-to-JPEG 工具，与归档无关。
- **参考实现**：没有找到能与 Bandizip 归档读取器对应、具有固定版本和许可的参考实现。
- **许可和再分发**：未知。第三方扩展页面和旧软件列表不是许可授权。
- **完整样本**：仓库没有可信、可再分发的样本矩阵。`.j2j` 文件名不能建立容器身份。
- **净室可行性**：在签名、记录模型、压缩或加密行为和完整语料库明确前，无法评估。
- **能力边界**：不识别，不登记后缀，不浏览，不解压，不检查，不创建，不处理密码或分卷。
- **结论**：**阻塞，且尚未确认是 Bandizip 归档格式**。旧的第三方列表只能作为历史线索。

## M10 准入门槛

1. 记录权威规范或经过法律复核的净室协议。博客、扩展名数据库或单个解码器源码都不够。
2. 每个研究来源固定到不可变提交或内容哈希，并记录适用许可文本。
3. 为每个声称支持的方法、版本、分卷模式、加密状态和终止条件建立完整可再分发夹具矩阵。只有头部或 Store 样本不能证明互操作。
4. 为输入读取、元数据、解压工作、内存、逻辑输出、历史、密码状态和取消定义有界资源模型。在发布前拒绝畸形偏移、环、溢出和来源变化。
5. 所有解码器独立于 Qt、挂载、启动、安装器、脚本、注册表和任意进程执行 API。
6. 只有 codec、快照身份、准确载荷行为和失败分类通过定向自动化后，才能接入 runtime、CLI、关联入口和用户文档。
7. 阻塞候选继续在评估中标为阻塞。不能因为 Bandizip 或第三方列表出现名称，就获得后缀、MIME 或产品能力。

仓库回归命令 `python scripts/test-m10-source-gates.py` 会检查六项双语记录是否保留必要证据字段，每项结论是否仍明确为阻塞或未确认，以及阻塞候选是否误加入 `specs/engineering/archive-formats.json`。
