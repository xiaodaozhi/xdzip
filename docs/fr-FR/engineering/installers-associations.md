Sous Windows 11 x64, recherchez **XDZip** dans Microsoft Store pour installer ou mettre à jour l’édition Store. Téléchargez l’EXE ou le ZIP portable Windows, les paquets macOS et les paquets Linux depuis la [dernière publication GitHub](https://github.com/xiaodaozhi/xdzip/releases/latest). Les deux canaux publient indépendamment. Consultez la fiche ou les notes de la version que vous installez.

Windows MSIX déclare les mêmes extensions comme candidates à « Ouvrir avec » dans son manifeste de paquet sans prendre le choix par défaut de l’utilisateur. Sa page d’associations liste tous les types admissibles avec des interrupteurs désactivés. Les valeurs par défaut actuelles apparaissent dans les paramètres Windows. « Ouvrir les paramètres des applications par défaut » ouvre le paquet actuel à l’aide de son `registeredAUMID`. Si la recherche d’identité échoue, le sélecteur général des valeurs par défaut s’ouvre. Le paquet ne lit pas les enregistrements de l’édition installée ordinaire comme état de paquet et n’écrit pas de valeurs UserChoice. L’activation réelle des fichiers, les icônes, la coexistence et la désinstallation exigent une acceptation sur le système cible. Voir les [builds MSIX](../../engineering/developer-build.md#windows-msix-实验构建).

Voir la [spécification des icônes d’association](../visual/file-association-icons.md) pour les illustrations par format et leurs correspondances par plateforme. Linux conserve les icônes MIME du système. L’installation ne change ni les valeurs par défaut ni le périmètre d’enregistrement existant.

Les associations MSIX référencent des ressources PNG par format extraites des mêmes images ICO canoniques que l’installateur Windows ordinaire. ZIP, 7z, RAR et les autres formats associés conservent leurs illustrations de document, profils de taille et marges transparentes. L’icône d’application possède des ressources distinctes aux tailles cibles sans plaque. Les deux ensembles sont indexés dans `resources.pri` du paquet ; modifier l’illustration de la fiche Store ne remplace pas ces icônes installées. Windows gère le cache des icônes et le choix du gestionnaire par défaut ; l’installation ne modifie jamais automatiquement ce choix.

Les paquets de bureau depuis `v0.2.0` et les builds actuels depuis les sources placent la CLI dans un répertoire `cli/` distinct, ou `Contents/Helpers/cli/` sous macOS, en conservant les points d’entrée GUI et d’association existants. Les ressources des versions antérieures ne reçoivent pas rétroactivement cette fonction. L’installateur Windows propose une option PATH facultative par utilisateur et détecte les conflits de commandes homonymes ; la désinstallation ne révoque que son répertoire d’installation. Mac/Linux exécutent explicitement le `setup` de la CLI privée. Les paquets CLI autonomes utilisent aussi `setup` pour installer des répertoires de versions au niveau de l’utilisateur et un lanceur stable, sans modifier la configuration du shell. `setup --remove` révoque l’enregistrement tout en conservant les répertoires de versions pour inspection. Voir le [contrat d’installation CLI](command-line.md#xdzip-build-and-command-installation).

Les commandes d’empaquetage ci-dessous produisent des artefacts expérimentaux de développement. Les paquets officiels GitHub suivent le [protocole de publication](release-protocol.md) et les paquets Store le [workflow MSIX](../../engineering/developer-build.md#microsoft-store-msix). Les téléchargements directs macOS utilisent une signature ad-hoc d’intégrité sans Developer ID ni notarisation. Voir la [politique de support](support-policy.md) pour les systèmes pris en charge.

Les builds actuels depuis les sources utilisent `xiaodaozhi` comme éditeur de l’installateur Windows, mainteneur du paquet Linux et fournisseur de la politique de mise à jour. Ces métadonnées ne remplacent pas la signature par certificat d’éditeur ; les publications existantes conservent leurs métadonnées d’origine.

Pour les mises à jour manuelles macOS, privilégiez le DMG Release correspondant. Avec app.zip, extrayez d’abord xdzip.app et déplacez-le hors de Téléchargements, quittez l’ancienne version en cours d’exécution, puis remplacez la copie dans Applications. Télécharger n’est pas installer ; un paquet non notarisé peut déclencher des avertissements système. Voir le [contrat de mise à jour](software-update.md) pour les conditions de repli.

Voir le [contrat des actions du gestionnaire de fichiers](shell-actions.md) pour les menus contextuels, l’hôte d’opérations indépendant et le cycle de vie des enregistrements propres. Les actions contextuelles n’ouvrent pas la fenêtre principale de navigation et n’ouvrent pas par défaut le dossier de destination à la fin.

## Point d’entrée de build partagé

Voir le [guide de compilation développeur](../../engineering/developer-build.md) pour la préparation de l’environnement et l’ordre des étapes. Après une compilation propre et des tests pour le même commit, utilisez `python3 scripts/desktop.py prepare --packaging` pour préparer les éléments fixés, puis lancez package et verify. N’utilisez pas directement le script CI complet pour le développement courant.

Sous Windows/Linux, `package --kind runtime|installer|all` partage une chaîne de déploiement et d’audit, avec `all` par défaut. runtime génère d’abord le répertoire déployé ; installer est construit à partir du runtime vérifié dans le même output-dir, et Linux crée aussi un tar.gz. macOS ne prend en charge que le DMG local de développement `all`. Les artefacts et reçus se trouvent dans l’output-dir indiqué, par défaut build/package. La préparation peut télécharger des outils et éléments d’empaquetage fixés mais n’installe pas xdzip ni les compilateurs ou SDK système automatiquement. Windows prépare CRT/Inno Setup, Linux exige patchelf et les outils Debian préinstallés, et Mac utilise les outils système de déploiement et d’intégrité ad-hoc.

Le `verify` ordinaire vérifie les runtimes et paquets existants. Windows efface les chemins de recherche SDK dans une copie isolée, Linux utilise un conteneur de runtime isolé et Mac vérifie la relocalisation DMG et Cocoa/Metal. Par défaut, il n’exécute pas les cycles d’installation, mise à niveau/retour arrière ou association et n’écrit pas les valeurs par défaut de l’utilisateur. Les mécanismes d’installation et contrôles CI jetables ci-dessous restent des contrôles distincts ; le succès du runtime ne les remplace pas.

## Windows

L’installateur présente le contrat d’origine du runtime Microsoft VC++ inclus dans le paquet. Sa page de licence identifie les composants applicables et exige leur acceptation, puis affiche Windows-runtime-NOTICE.txt en chinois et en anglais. Les paquets portables incluent le même texte original et son explication. Le code original du projet reste sous Apache-2.0 ; les licences d’origine et droits de remplacement de Qt et des autres composants restent inchangés. Vérifiez les hashes et descriptions complètes avant compilation ; les documents joints conservent le même texte. Voir les [licences Windows](windows-licensing.md).

Les paquets portables et installateurs utilisent le même répertoire déployé. [deploy_windows.py](../../../scripts/deploy_windows.py) appelle windeployqt puis suit la politique Qt Quick Basic fixée pour retirer FluentWinUI3, Fusion, Imagine, Material, Universal, Windows, NativeStyle/Effects référencés uniquement par les styles, qmltooling et .qmltypes. Basic, Controls impl, Templates, QML de runtime et qmldir restent présents ; Qt Widgets qmodernwindowsstyle sert toujours les contrôles natifs. Les nouveaux répertoires de déploiement ne contiennent ni DXC, DXIL ou D3DCompiler ; le déploiement échoue si ces noms apparaissent où que ce soit. `opengl32sw.dll` n’est pas inclus dans les nouveaux déploiements. Une copie existante à la racine est supprimée dans une préparation contrôlée ; des éléments homonymes ailleurs font échouer le déploiement. L’ajout d’un nouveau style ou de fonctionnalités Effects exige une mise à jour de la politique et une nouvelle vérification.

Qt Quick utilise Direct3D 11 par défaut sous Windows. Si le matériel ou les pilotes sont insuffisants, Qt peut revenir à Direct3D WARP ; cela diffère d’OpenGL logiciel. Les nouveaux paquets ne garantissent pas de repli logiciel Mesa via `QT_OPENGL=software` ou le backend OpenGL. Les paquets historiques et leurs documents de licence restent inchangés. La [documentation graphique Windows de Qt](https://doc.qt.io/qt-6.8/windows-graphics.html) décrit les dispositifs par défaut et logiciels explicitement demandés.

VC++ est déployé localement à l’application avec le runtime officiel Microsoft x64 14.44.35211 provenant des [sources et hashes fixés](../../../scripts/windows-runtime.json). Le [script de préparation](../../../scripts/prepare-windows-runtime.py) extrait à l’aide d’outils WiX fixés et vérifie chaque DLL et texte de licence sans exécuter d’installateurs EXE/MSI ni copier depuis System32. Les DLL MSVCP/VCRUNTIME nécessaires, licences et provenance sont livrées ; outils, CAB, MSI et installateur vc_redist non exécuté n’entrent pas dans le produit. Windows 10/11 fournit UCRT. Les runtimes locaux à l’application doivent être entretenus avec les mises à jour du produit ; on ne peut pas compter sur les mises à jour du runtime système pour les remplacer. Voir les [méthodes de déploiement Microsoft](https://learn.microsoft.com/en-us/cpp/windows/choosing-a-deployment-method).

La [régression de déploiement](../../../scripts/test-windows-deployment.py) vérifie les limites de réduction et de runtime manquant. La [vérification réelle du runtime](../../../scripts/verify_windows_runtime.py) refuse les DLL OpenGL logiciel, ajoute des DLL de test à une copie isolée, efface les chemins de recherche SDK et vérifie les traductions système, le redémarrage des réglages, la barre de titre native et le démarrage bilingue. Après suppression des substitutions de rendu, elle vérifie l’initialisation par défaut du graphe de scène D3D11 et demande explicitement WARP, en vérifiant le dispositif logiciel Microsoft réellement sélectionné. Les demandes explicites ne prouvent pas le repli automatique en cas d’échec et ne remplacent pas l’acceptation visuelle manuelle. Les fichiers de test n’entrent pas dans le répertoire du produit ; cela ne remplace pas l’acceptation d’installation, mise à niveau et désinstallation sur Windows propre.

build-windows-installer.py n’accepte qu’un audit deployed de build propre et vérifie à nouveau le SHA-256 de chaque fichier. Voir la [configuration des outils](../../../scripts/installer-toolchain.json) pour Inno Setup 6.7.3 fixé, le hash de l’installateur officiel, le commit source, les ressources chinoises simplifiées et traditionnelles et les textes de licence. Le compilateur n’entre pas dans le produit ; les notices incluent le texte de licence. L’assistant prend en charge les dix langues du registre partagé.

L’installateur utilise un AppId fixe et PrivilegesRequired=lowest et installe par défaut sous LocalAppData/Programs/xdzip de l’utilisateur actuel sans droits administrateur. L’exécutable principal xdzip.exe est à la racine avec les bibliothèques Qt à côté ; plugins, QML, traductions et notices conservent les sous-répertoires nécessaires. Raccourcis, associations et icônes de désinstallation pointent vers la racine, sans hiérarchie produit versions/hash de commit. Les hashes du commit et des binaires restent dans les reçus de build et d’installation, pas dans les chemins d’installation. Le [journal cumulatif de désinstallation](https://jrsoftware.org/ishelp/topic_appendnotes.htm) d’Inno Setup enregistre les fichiers appartenant à chaque installation sans supprimer récursivement les éléments supplémentaires. Les réglages et éléments récents restent dans les répertoires de configuration existants de l’utilisateur et ne sont pas supprimés par l’installateur.

La nouvelle disposition écrit un install-manifest.txt borné contenant les chemins relatifs audités et SHA-256. Avant mise à niveau, validez chemins, doublons et tailles de l’ancien manifeste ; refusez les échappements de chemin, alias de périphérique et points de réanalyse dans les chemins de nettoyage. Si les fichiers à retirer ont été modifiés ou ne peuvent être vérifiés, l’installation s’arrête avant toute écriture. Après une installation réussie, seuls les fichiers listés dans l’ancien manifeste, qui ne sont plus livrés et dont le hash correspond encore, sont nettoyés ; seuls les répertoires vides sont supprimés et les éléments supplémentaires sont conservés. Même si les événements de fin se répètent pendant une installation, le nettoyage n’est déclenché qu’une fois. Les fichiers modifiés ou retenus pendant le nettoyage restent avec un enregistrement de nouvelle tentative et le code de sortie non nul 20. L’impossibilité d’écrire cet enregistrement exige une réparation manuelle ; aucune reprise transactionnelle ou sécurité en cas de coupure de courant n’est revendiquée. Cette installation par utilisateur suppose qu’aucun processus externe ne modifie simultanément le répertoire ; les nouvelles vérifications de chemin et de hash ne sont pas une isolation des courses malveillantes fondée sur des handles.

Les dispositions existantes à répertoires de versions sont mises à niveau directement. Commandes de lancement et raccourcis passent à la racine, les emplacements des réglages et éléments récents restent inchangés. L’ancien installateur ne livrait pas de manifeste de propriété distinct ; les anciens répertoires versions/ restent donc jusqu’à la désinstallation ordinaire. Le journal cumulatif Inno nettoie les fichiers initialement enregistrés sans supprimer récursivement les répertoires. Les fichiers ajoutés par l’utilisateur sont conservés. Le retour arrière peut réinstaller une ancienne version choisie ; les anciens fixtures QA conservent les dispositions historiques et peuvent ensuite être remis à niveau vers la disposition racine. Une installation neuve ne crée pas versions/. Cela ne comprend pas l’effacement complet automatique de l’ancien répertoire d’installation.

Le produit conserve le mutex nommé `Local\xdzip.desktop.running` pendant tout son cycle de vie. [AppMutex](https://jrsoftware.org/ishelp/topic_setup_appmutex.htm) bloque installation et désinstallation, avec CloseApplications=no et sans fermeture forcée de l’application. Un échec de création du handle FFI empêche le démarrage ; la fermeture du processus le libère. La sortie des tâches utilise toujours la décision existante et la barrière d’attente Rust.

L’installateur Windows ordinaire enregistre les candidats d’archives sous HKCU. Il écrit des ProgID propres, deux entrées Applications propres, Capabilities, RegisteredApplications et des valeurs OpenWithProgids propres. Il ne modifie pas HKLM, les valeurs par défaut d’extensions, UserChoice/UserChoiceLatest protégés ou les candidats d’autres applications. Chaque suffixe enregistré possède un ProgID comme `xdzip.Archive.ZIP` et un ICO attribué. L’ancien `xdzip.Archive` conserve sa commande d’ouverture directe et est masqué d’« Ouvrir avec » avec `Applications/xdzip.exe`. La mise à niveau retire leurs anciennes recommandations tout en préservant la compatibilité avec une valeur par défaut existante. Windows associe un nom composé comme `.tar.gz` par son extension finale pour le choix de l’icône.

Au démarrage et après un changement de langue réussi, l’application installée ordinaire synchronise les descriptions de neuf ProgID principaux : ZIP, TAR, TGZ, GZ, 7Z, RAR, CAB, ISO et UDF. L’installateur choisit les descriptions selon la langue enregistrée de l’application ou, en mode automatique, la langue d’affichage du système. La langue de l’assistant est indépendante. Avant la synchronisation en direct, l’application vérifie l’identité d’installation, l’emplacement de l’exécutable, le manifeste, le lanceur d’association et les neuf commandes d’ouverture existantes. Les enregistrements absents ou discordants restent inchangés. Les écritures partielles peuvent être retentées au prochain démarrage normal. Les processus portables, de développement et de test à réglages isolés n’exécutent pas cette synchronisation. Les autres suffixes enregistrés conservent les descriptions fournies par l’installateur. Le cache Explorer et la valeur par défaut choisie peuvent modifier l’affichage.

La CI Windows jetable vérifie la synchronisation des descriptions au démarrage du produit installé et le changement en direct entre chinois simplifié et anglais. Elle utilise une copie portable et un processus à réglages isolés pour vérifier l’absence d’écriture et contrôle que les neuf icônes, commandes, autres candidats et valeurs par défaut restent inchangés. Ce contrôle automatique ne remplace pas l’acceptation manuelle de l’affichage dans Explorer ou Paramètres.

Les commandes entre guillemets de tous les ProgID de format lancent `xdzip-association.exe -- "%1"` ; leur enregistrement Applications contient un SupportedTypes complet afin qu’« Ouvrir avec » affiche une seule entrée xdzip. Le lanceur intègre le même ICO de marque de l’application et des ressources OriginalFilename et version produit distinctes. Vérifiez les icônes d’application séparément des icônes de document par format ; le DefaultIcon du document ne remplace pas les ressources d’application de l’exécutable. Le petit lanceur GUI accepte un argument fichier, initialise COM dans un appartement monothread sur son propre thread et délègue la commande d’ouverture existante via ShellExecuteEx avec la classe explicite `xdzip.Archive`, sans interpréteur de commandes ; il libère COM après l’appel. Un retour arrière ancien met à jour l’entrée partagée ; les candidats par format continuent donc de pointer vers le programme restauré. Un échec d’initialisation COM, un point d’entrée manquant, des arguments invalides ou un refus du système renvoient une valeur non nulle sans essayer une autre application ni changer les valeurs par défaut. Cela dépend du maintien du lanceur dans le répertoire d’installation actuel lors du retour arrière ; installation/retour arrière et désinstallation cumulative exigent des tests réels.

L’installateur définit `AllowSilentDefaultTakeOver` en REG_NONE sur le ProgID partagé et les ProgID spécifiques de formats enregistrés. Windows peut toujours les proposer comme candidats explicites d’« Ouvrir avec ». L’installateur utilise un appel natif borné au registre pour définir la valeur sur les clés propres déjà créées. Un échec arrête l’installation et libère les handles. Voir les [conventions ProgID Windows](https://learn.microsoft.com/en-us/windows/win32/shell/fa-progids).

L’installateur ordinaire et MSIX génèrent leurs candidats Windows « Ouvrir avec » depuis le [registre des formats](format-registry.md). Ce mappage couvre les types principaux ZIP, TAR, TGZ, GZ, 7z, RAR, CAB, ISO et UDF ainsi que d’autres suffixes enregistrés. `.gz` peut être dirigé vers GZIP autonome ou TAR.GZ selon son contenu. Les suffixes génériques `.img`, `.001` et `.rNN` sont réservés à l’ouverture explicite ou aux points d’entrée pris en charge. L’association fournit au système un chemin vers xdzip. Le lecteur continue d’examiner le fichier et d’appliquer les exigences de format et de source de l’opération.

## Ubuntu 24.04

build-linux-installer.py crée un .deb depuis le même répertoire vérifié. Les répertoires de préparation privés sont distingués par leur chemin de sortie, permettant de reconstruire un même nom de paquet dans différents répertoires candidats sans écraser la préparation existante. Le paquet s’appelle xdzip, sa version lie le canal et le commit du produit, et son architecture est amd64. Les dépendances système proviennent des manifestes de déploiement réels ainsi que des outils desktop-database et de verrouillage ; glibc est au minimum 2.39. Qt/QML/plugins et notices se trouvent sous /opt/xdzip/versions/ ; /usr/bin/xdzip est une entrée de transfert entre guillemets à cible fixe. dpkg remplace et supprime les anciens fichiers de paquet ; un retour arrière exige de conserver le .deb d’origine.

Le [xdzip.desktop](../../../apps/desktop/packaging/linux/xdzip.desktop) installé déclare les candidats MIME du paquet. Ils comprennent ZIP et certains alias, TAR et TAR filtré, flux de compression autonomes, formats d’archives comme 7z, RAR et CAB et images ISO/UDF. `%f` demande le lancement d’un seul fichier et `--` marque la limite des arguments. Le paquet fournit une déclaration MIME pour `*.udf` et ne modifie pas les types génériques d’image et de binaire. Installation et suppression actualisent les bases MIME et de bureau sans réécrire `mimeapps.list`, changer les valeurs par défaut utilisateur ou remplacer les icônes MIME système. La désinstallation supprime les lanceurs, icônes et fichiers runtime propres et conserve les réglages utilisateur.

Le DEB installe son [entrée de catalogue AppStream](../../../apps/desktop/packaging/linux/xdzip-local.yml) dans `/var/lib/swcatalog/yaml/xdzip-local.yml`, chemin lisible par Ubuntu App Center. L’entrée associe le nom de paquet `xdzip` à `xdzip.desktop` afin que le paquet installé puisse apparaître dans la liste des applications. dpkg supprime le fichier de catalogue lors de la désinstallation de XDZip.

Le produit installé conserve un flock partagé sur /run/xdzip/usage.lock. Les scripts de maintenance obtiennent d’abord un verrou exclusif non bloquant et échouent si un processus est actif. Les scripts définissent une barrière d’installation sous /run/xdzip appartenant à root ; le produit vérifie à nouveau après acquisition de son verrou pour éviter un démarrage entre les hooks dpkg. Les liens symboliques ou propriétaire/permissions incorrects sont refusés ; fermer QFile libère le verrou. tmpfiles.d prépare le verrou de runtime au démarrage du système. Cela n’affecte pas les applications de développement SDK.

Les chemins de succès et d’abandon dpkg nettoient la barrière. Une interruption ou coupure de courant peut laisser une transaction inachevée ; exécutez sudo dpkg --configure -a et corrigez l’erreur réelle. L’impossibilité de démarrer n’est pas un succès d’installation. Les scripts ne nettoient pas récursivement les répertoires utilisateur ; les artefacts ne sont générés que sous build/ ou en CI.

## macOS et ouverture de fichiers

L’application principale et le paquet livré déclarent les documents et ICNS comme Viewer/Alternate dans Info.plist, [sans revendiquer la propriété par défaut](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html). Les builds de développement et test utilisent Viewer/None par défaut et n’entrent pas dans les candidats système « Ouvrir avec ». Les principaux paquets de développement ou builds de livraison doivent définir explicitement `-DXDZIP_MACOS_HANDLER_RANK=Alternate`. L’utilisateur et Launch Services déterminent les valeurs par défaut ; l’application ne les change pas activement. Nettoyez les enregistrements temporaires des copies de vérification de développement selon la [méthode de maintenance Mac](macos-deployment.md), en préservant les applications et choix par défaut existants.

CAB, ISO et UDF utilisent le même rôle Viewer. ISO utilise `public.iso-image`. L’application ne revendique ni `.img` ni le type générique `public.disk-image`. Viewer décrit l’association Launch Services, tandis que le [backend de formats](native-codecs.md) détermine les opérations disponibles. Le [profil distinct de création ISO](iso-creation.md) peut écrire de nouvelles images.

Les déclarations de documents couvrent les extensions finales de tous les candidats shell du [registre des formats](format-registry.md) et utilisent l’ICNS correspondant du bundle. Les suffixes composés partagent le type de leur extension finale. Par exemple, `.tar.gz` et `.gz` partagent le défaut GZIP, tandis que `.tgz` utilise le type TAR compressé du système. Le cache Finder, le défaut choisi et la reconnaissance de types du système affectent l’affichage réel.

Les types importés RAR, CAB et UDF de macOS doivent être conformes à `public.data` pour identifier les fichiers réels. CAB déclare à la fois le type système `com.microsoft.cab` et le type de compatibilité `com.microsoft.cab-archive` ; Paramètres interroge et modifie le type préféré réel lorsqu’il s’agit de l’un d’eux, sinon utilise l’identifiant de compatibilité. Le Viewer UDF déclare l’extension `.udf` sans `LSItemContentTypes` afin que les fichiers réels découvrent un candidat même si une déclaration UTI invalide d’une installation antérieure est encore utilisée. Apple a rendu obsolète cette [clé de déclaration d’extension](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html) ; continuez à la vérifier sur les versions macOS prises en charge. Paramètres interroge et modifie le type `.udf` réellement reconnu, en utilisant l’identifiant existant s’il est indisponible. L’installation ou l’enregistrement ne remplace pas activement les choix par défaut existants. Lorsqu’aucun gestionnaire n’existait, Launch Services peut résoudre un nouveau candidat comme gestionnaire actuel par des [règles implicites](https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/LaunchServicesConcepts/LSCGlossary/LSCGlossary.html). La suppression de l’enregistrement temporaire devrait restaurer l’état initial ; cette résolution ne signifie pas que l’application écrit les préférences utilisateur.

FileOpenRouter reçoit [QFileOpenEvent](https://doc.qt.io/qt-6.8/qfileopenevent.html) avant QML, n’accepte que les fichiers locaux et réutilise le routage existant d’ouverture et d’activation. Les arguments de ligne de commande GUI après `--` sont des chemins de fichiers, pour éviter toute confusion avec les options de diagnostic. Au plus 128 intentions en attente sont mises en file sans interrompre les tâches actives. Les processus produit ordinaires d’une session de connexion partagent une instance ; les demandes multifichiers s’ouvrent dans l’ordre et activent le dernier. Voir le [contrat des sessions](application-sessions.md) pour les onglets et fenêtres.

Les arguments de lancement sont mis en file avant le chargement QML. La fenêtre principale démarre masquée et soumet immédiatement la première demande disponible lors de l’attachement du contrôleur sans exiger que la fenêtre soit visible. La fenêtre est affichée dans la file initiale d’événements afin que les événements de lancement de la plateforme utilisent le même chemin. Pendant une ouverture externe, masquez l’entrée d’accueil avant de changer de session afin d’éviter un éclair de la page d’accueil à la première image ou au remplacement de session. L’annulation ou l’échec restaure l’accueil ; le succès affiche la liste réelle. Voir [l’état de chargement](../ux/welcome-opening.md).

Le démarrage natif macOS attend séparément NSApplicationDidFinishLaunchingNotification d’AppKit, traite ce lot d’événements de fichiers Qt en file pendant que la fenêtre est masquée, puis l’affiche. Notifications et callbacks en file sont limités à la durée de vie de la fenêtre principale ; ils ne remplacent pas le délégué d’application Qt et n’utilisent pas de délais fixes en millisecondes. Une régression Launch Services réelle a auparavant trouvé une image d’accueil ; l’exigence corrigée est zéro. check-macos-open.py exécute les chemins argv et d’ouverture native localement et en CI Mac, ne conservant que JSON et journaux sans générer ni téléverser de paquets d’application.

## Vérification automatisée et limites

CTest sur trois plateformes vérifie les événements de fichiers avant démarrage, le rejet des URL non locales et la mise en file lorsque la lecture est occupée. XDZIP_ASSOCIATION_PROBE explicite avec des réglages isolés est réservé à la CI : utilisez le flux normal d’ouverture pour lire un ZIP propre de 100 000 entrées, conserver le nombre et l’identité du build, puis quitter normalement sans enregistrer les chemins sources ni extraire.

La sonde d’association actuelle attend au moins une présentation réelle d’image et enregistre la visibilité du contenu d’accueil à chaque image. Les exigences actuelles pour Windows ShellExecuteEx et Linux GIO sont presented_frames supérieur à 0 et welcome_frames égal à 0. Les anciens produits fixés sont testés selon les capacités historiques de leur sonde ; ne prétendez pas que les anciens binaires possèdent les nouveaux comptages de première image.

La CI native Windows installe la variante QA 1, met à niveau vers 2, revient à 1, puis installe le véritable paquet de livraison. ShellExecuteEx ouvre des classes d’enregistrement propres avec des chemins contenant du chinois, des espaces et une esperluette, et vérifie que les défauts et UserChoice restent inchangés, que le remplacement pendant utilisation est refusé et que la désinstallation conserve réglages, fichiers supplémentaires et autres candidats. Linux effectue le même cycle dpkg dans un conteneur sans réseau, SDK, Qt système ou compilateur. Le produit sous UID 1000 ouvre réellement 100 000 entrées par un lanceur de bureau GIO ; MIME, valeurs par défaut, verrous, désinstallation et purge sont vérifiés.

La vérification de publication Linux modifie aussi les valeurs MIME par défaut dans un profil utilisateur isolé du conteneur et utilise `gio open` lorsque GIO résout le type de contenu d’un échantillon vers xdzip. Elle vérifie chaque MIME par défaut déclaré, exerce un gestionnaire distinct et restaure les valeurs initiales. Les contrôles automatiques d’ouverture Linux et macOS utilisent des échantillons ouvrables sans saisie. Le test de navigateur AES Crypt vérifie la demande du mot de passe d’ouverture et les lectures authentifiées. Les paramètres système et autres environnements de bureau nécessitent une vérification séparée.

Les variantes QA partagent les binaires actuellement vérifiés et ne changent que la version et le répertoire du paquet de test pour tester les mécanismes d’installation. Ce ne sont pas des artefacts de publication et elles ne se font pas passer pour une migration réelle de données entre versions différentes du produit. Le schéma des réglages est actuellement 1 et les métadonnées d’installation l’enregistrent sur les deux plateformes. Les anciens installateurs refusent d’écraser une installation déclarant un schéma plus récent ; une migration future doit mettre à jour le contrat.

L’injection ultérieure d’erreurs n’est autorisée que dans la variante QA 2, avec un échec unique pendant la configuration postinst. La production ne doit pas contenir cette branche. Le conteneur vérifie réellement l’état semi-configuré, le démarrage bloqué par la barrière et les réglages préservés, puis exécute dpkg --configure -a pour reprendre et ouvre un fichier réel par GIO. Il s’agit d’une erreur de configuration reproductible, pas d’une coupure de courant du matériel. Un contrôle distinct de compatibilité des réglages compile les composants de réglages originaux conservés et actuels et effectue un aller-retour de configuration au même schéma. Les entrées originales sont fixées par hashes de chaque fichier, indépendamment de l’ancien historique main, et ne prétendent pas représenter une migration complète des données de l’installateur.

La compatibilité complète du produit est vérifiée séparément par prepare-previous-product.py, qui compile les sources complètes depuis un instantané de compatibilité fixé (provenant initialement de 4cf0f8c) sur des hôtes CI Windows/Linux jetables. Un worktree détaché préserve l’identité réellement propre ; le SDK actuel fixé compile les installateurs QA du produit historique sans télécharger d’anciens binaires Actions périssables. Installez le produit historique et ouvrez-le réellement, installez ensuite le produit actuel et vérifiez le changement de révision et la conservation des octets de configuration, puis revenez en arrière, rouvrez le produit historique et vérifiez les données. Cela prouve la compatibilité au même schéma entre deux commits source complets, pas un paquet original historiquement signé, une migration inexistante de schéma 2 ou un redémarrage du matériel. Les installateurs historiques sont réservés à QA et ne sont pas téléversés comme ressources produit ; les reçus lient les SHA-256 des deux binaires et installateurs.

windows-install-lifecycle.json, linux-install-lifecycle.json et les hashes de paquets constituent des preuves réelles. Les doubles clics réels Explorer/Finder, l’interface de choix par défaut, les services et caches après redémarrage, les avertissements d’absence de signature formelle et les contrôles GPU et bureau suivent la liste manuelle. Les scripts automatisés ne doivent pas déclarer eux-mêmes tous les INSTALL-01/ASSOC-01 réussis. Les conclusions manuelles existantes figurent dans [WP-12 #5](https://github.com/xiaodaozhi/xdzip/issues/5) ; régénérer un modèle en attente ne rouvre pas l’acceptation. Les futures migrations de schéma exigent des cas réels supplémentaires de compatibilité.

La sonde Windows sans tâche pour la protection contre le remplacement occupé utilise des réglages isolés avec la zone de notification désactivée afin que `CloseMainWindow` effectue une sortie normale dans cette configuration. Les autres sondes d’ouverture par association conservent les réglages de zone de notification par défaut et se terminent par la barrière explicite d’arrêt. Les sondes de protection d’installation ne doivent pas confondre une fenêtre masquée avec un échec de sortie du processus ni contourner la vérification en terminant de force le chemin normal.

Les fixtures de protocole de mise à jour Windows et les fixtures de mise à jour Qt réelle comprennent le lanceur d’association et les neuf ICO de document ; les installateurs ne peuvent passer les contrôles s’il manque une charge utile requise. Le petit programme principal C et la commande d’association du fixture de protocole ne vérifient que la transmission de mise à jour. Les ressources d’application intégrées, candidats natifs et fenêtres réelles sont vérifiés séparément par le produit Qt complet ; les conclusions ne sont pas mélangées.

## Entrées de la base de compatibilité à long terme

La mise à niveau et le retour arrière réels utilisent les sources complètes anciennes fixées du produit au lieu de l’historique main réécrit. `prepare-previous-product.py` fixe un instantané source à racine unique dans la branche indépendante `codex/installer-compat-baseline`. Cette branche ne contient que les sources et ressources originales nécessaires aux builds et régressions, sans anciens parents main, rapports d’exécution ou workflows. `COMPAT-BASELINE.json` dans l’instantané enregistre le commit source et l’identité d’arbre d’origine. Il ne doit pas être fusionné de nouveau dans main ni traité comme un paquet de publication ou une conclusion d’acceptation du produit actuel.

Après compilation, l’identité CLI doit correspondre au SHA fixé propre à l’instantané ; les reçus enregistrent séparément l’identité source d’origine et ne doivent pas se faire passer pour le binaire original publié. Les composants de réglages conservent aussi trois petits fichiers source originaux comme entrées de test durables, fixées par hash individuel. Les lectures et écritures bidirectionnelles et le rejet des futurs schémas ne dépendent pas du réseau ni des commits historiques. Ne modifiez pas ces entrées de régression avec l’implémentation actuelle ; examinez séparément toute nouvelle base et conservez la provenance si nécessaire.

L’instantané figé est antérieur à l’assistant indépendant de mise à jour et ne contient ni source ni binaire de cet assistant. Seul `prepare-previous-product.py` lui transmet `--qa-historical-revision`. Les scripts de déploiement et d’empaquetage exigent simultanément une CI jetable, le SHA complet fixé et la correspondance de l’identité produit réellement propre. Linux exige en plus le mode de version historique et interdit de le mélanger à la variante QA actuelle. Windows exécute directement la commande de version de l’ancien produit pour l’identité ; Linux utilise l’identité de l’audit indépendant de déploiement et les hashes complets des fichiers. Les reçus indiquent explicitement que les sources historiques ne possèdent pas l’assistant, n’injectent pas l’assistant actuel et n’installent pas d’autorisation polkit pour un assistant Linux inexistant. Les produits ordinaires et variantes QA actuelles doivent toujours livrer et vérifier l’assistant indépendant ; `--qa-legacy-version` seul n’autorise pas son absence.

## Migration de version Debian

Depuis la première préversion publique, l’epoch Debian 1 est utilisé : `1:<semantic-version mapping>+git<commit>`, par exemple `1:0.1.0~alpha.1+git...`. Le `0.1.0~dev.9` historique est classé après alpha.1 sans epoch selon dpkg ; l’ancien mappage ne peut donc pas simplement être conservé. L’epoch sert uniquement à l’ordre des paquets système ; l’interface produit, les tags de version et release.json continuent d’utiliser la version sémantique d’origine. Les paquets Debian ultérieurs conservent l’epoch 1, l’ordre alpha, beta, rc et stable restant exprimé par les versions amont. Voir la [Debian Policy](https://www.debian.org/doc/debian-policy/ch-controlfields.html#version).

Le fixture réel du produit historique utilise `--qa-legacy-version` réservé à la CI pour conserver son identité d’origine sans epoch ; ne modifiez pas l’ordre de l’ancien paquet pour masquer des problèmes de mise à niveau. Le paquet actuel doit réussir l’acceptation réelle de mise à niveau, retour arrière et cycle d’installation dpkg. La configuration utilisateur et les associations externes par défaut conservent leurs contrats d’origine.

## Applications par défaut dans Paramètres

Paramètres regroupe les suffixes d’association à l’aide des données de formats générées. Les interrupteurs modifiables dépendent du service de plateforme et de l’identité d’installation. Windows délègue les changements aux applications par défaut du système et n’écrit jamais UserChoice. MSIX laisse les interrupteurs désactivés et utilise l’entrée système du paquet. Linux associe les suffixes pris en charge à des types MIME, utilise `xdg-mime` pour les valeurs utilisateur et propose un remplacement installé lors du retrait d’un défaut.

Sous macOS, Paramètres active chaque interrupteur dont le type système est couvert par les déclarations Viewer/Alternate du bundle installé. Un interrupteur activé peut demander xdzip comme défaut même si le type n’en avait pas auparavant. macOS peut demander confirmation. Après un callback réussi, Paramètres laisse un court délai à Launch Services pour signaler le nouveau défaut. Lorsque la requête système confirme xdzip, l’application enregistre localement l’identifiant de bundle de l’application précédente par type de contenu système. Désactiver l’interrupteur demande d’abord cette application précédente si macOS la liste toujours comme compatible. Si aucune application compatible n’est enregistrée ou si la restauration échoue, Paramètres propose des alternatives compatibles installées. Sans alternative, il l’explique à côté de l’interrupteur. Annuler conserve le choix actuel et l’état affiché suit une nouvelle requête système. Les builds Viewer/None désactivent les changements.

En mode de langue automatique, Windows Setup choisit une description d’association selon la langue actuelle de l’interface système de l’utilisateur. Il utilise le chinois traditionnel pour les préférences de chinois traditionnel et l’anglais américain pour les langues non prises en charge. Un choix manuel pris en charge est prioritaire. Setup préserve le mode automatique afin que l’application puisse résoudre la langue système et synchroniser ses descriptions propres au démarrage.
