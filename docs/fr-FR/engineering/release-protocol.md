# Protocole GitHub Release v1

[English](../../engineering/release-protocol.md) | [简体中文](../../zh-CN/engineering/release-protocol.md) | [繁體中文](../../zh-TW/engineering/release-protocol.md) | [日本語](../../ja-JP/engineering/release-protocol.md) | [한국어](../../ko-KR/engineering/release-protocol.md) | Français | [Deutsch](../../de-DE/engineering/release-protocol.md) | [Español](../../es-ES/engineering/release-protocol.md) | [Português (Brasil)](../../pt-BR/engineering/release-protocol.md) | [Русский](../../ru-RU/engineering/release-protocol.md)

Ce flux produit les téléchargements GitHub. Le [flux Microsoft Store MSIX](../../../.github/workflows/windows-store-msix.yml) empaquette le même code source versionné pour Microsoft Partner Center, qui assure la certification et la publication dans le Store.

Le [flux Release](../../../.github/workflows/release.yml) dédié est lancé manuellement par `workflow_dispatch`. Une exécution officielle part de `main` avec une étiquette de version existante et fige le commit résolu. Chacune des trois tâches natives configure, compile, teste et empaquette une fois. Dès la compilation initiale, la tâche macOS utilise le rang d'association de la distribution, puis déploie Qt et applique une signature d'intégrité ad-hoc pour créer le ZIP et le DMG à partir de la même application. Le CI Qt macOS ordinaire vérifie avec le SDK. Developer ID, la notarisation Apple et les certificats d'éditeur Windows sont hors de cette politique.

Le code source du produit provient du commit désigné par le tag. La préparation du brouillon, la publication et la vérification des téléchargements publics utilisent les mêmes notes de version relues, tirées du commit de `main` qui a déclenché le workflow.

L'étiquette complète est `v` suivi de la version sémantique issue de VERSION.json. `prerelease_number` est un entier positif facultatif ; son absence reste compatible avec les numéros de build historiques. alpha.1 et build 14 sont des identités distinctes. Les ressources numériques Windows et CFBundleVersion de macOS utilisent toujours des numéros de build strictement croissants. Les fichiers publics d'une même version ne peuvent pas être remplacés ; une révision exige une nouvelle version. Les brouillons peuvent être relancés.

Les notes de version constituent des entrées durables et vérifiables, lues par défaut dans `release-notes/<full-version>.md` ; l'interface CLI peut indiquer un fichier vérifié avec `--notes-file`. Le fichier contient une ligne de métadonnées `<!-- xdzip-release {"version":"0.1.0-alpha.6","build":19} -->` et un titre de version correspondant. La version et le build doivent correspondre à VERSION.json. Exécutez d'abord `python3 scripts/publish-release.py --check-notes` ; cette vérification ne contacte pas GitHub. Le flux dédié effectue le même contrôle avant compilation. Chaque nouvelle version nécessite ses propres notes et n'hérite pas automatiquement des fonctionnalités ou de l'état d'acceptation précédents.

Les notes décrivent en chinois et en anglais les limites de l'acceptation par plateforme, le commit réel et les preuves, en distinguant l'acceptation manuelle existante des vérifications non effectuées. Les issues continuent de suivre l'avancement des étapes. La création du brouillon et la publication utilisent le même instantané des notes. Lors d'une relance, si le corps du brouillon diffère du fichier vérifié, arrêtez-vous avant d'envoyer ou de supprimer des fichiers et exigez l'alignement explicite des entrées. Les versions publiées refusent toujours les relances qui remplaceraient des fichiers. Consignez les changements en attente dans [la rubrique Non publié du journal](../../../CHANGELOG.fr-FR.md#unreleased), puis déplacez-les vers la version correspondante après publication. Maintenez toutes les traductions du journal à jour.

Avant de modifier les fichiers d'un brouillon, l'outil de publication relit l'étiquette GitHub, l'état du brouillon et l'indicateur de canal. La version stable doit rester hors préversion et devenir GitHub Latest ; alpha, beta et rc doivent rester des préversions sans remplacer Latest. Revérifiez l'état après publication et après vérification des pièces jointes publiques ; n'annoncez la réussite que si tout concorde. Si la vérification échoue après publication, la version peut déjà être visible. Le script s'arrête pour intervention du propriétaire sans retirer, modifier ou remplacer automatiquement la version ou ses fichiers publics.

Avant une publication officielle, effectuez le contrôle local préalable et examinez les notes correspondantes. La vérification des paquets s'exécute indépendamment sur la même plateforme native. Elle accepte un transfert issu de la même exécution seulement après contrôle du dépôt, du commit, de la plateforme, de l'architecture et du SHA-256 de l'archive. Windows et Linux vérifient une fois l'environnement déployé et exercent le cycle de vie réel de l'installateur. macOS vérifie le DMG réel et le ZIP de l'application. Une exécution candidate à la demande utilise les mêmes tâches, puis télécharge l'artefact Actions assemblé pour vérifier ses sommes de contrôle. Le parcours candidat utilise des permissions de dépôt en lecture seule, ne nécessite pas d'étiquette et n'accède pas aux secrets de signature de publication.

La tâche de contrat de publication compile d'abord le processus isolé de format du même commit et exécute les tests de l'espace de travail Rust avec `XDZIP_NATIVE_CODEC` et `XDZIP_NATIVE_CODEC_WORKER`. Les tâches natives des trois plateformes vérifient séparément applications, déploiement et cycles d'installation. Le test macOS du rang d'association de la version de développement utilise une copie temporaire du paquet compilé avec ses métadonnées de développement. Le paquet de distribution conserve son rang réel pour les lancements natifs et l'empaquetage.

Chaque vérification de déploiement Windows utilise une copie temporaire indépendante et conserve les journaux antérieurs. Les répétitions ne réutilisent ni ne suppriment les répertoires existants ; les répertoires d'exécution du produit ne contiennent pas de DLL de test.

Les versions comprennent toujours `release.json` et `SHA256SUMS`. Le manifeste `schema_version=1` contient à la racine product, version, channel, build, tag, commit (SHA complet de 40 caractères), repository et assets. Chaque fichier indique filename, platform, architecture, package_type, minimum_system, bytes, sha256 et url fixé au chemin de téléchargement de l'étiquette.

| Plateforme, architecture | Types de paquet | Système minimal |
| --- | --- | --- |
| windows, x86_64 | zip, exe | Windows 11 maintenu |
| macos, arm64 | app.zip, dmg | macOS 14.0 |
| linux, x86_64 | tar.gz, deb | Ubuntu 24.04, glibc 2.39, X11 |

Les six types de paquet sont obligatoires. La validation du manifeste rejette les paquets manquants, cibles en double, canaux incohérents, URL de téléchargement modifiables, tailles ou hachages incorrects. Les pièces jointes contiennent les notices des plateformes, licences, SBOM et documents de déploiement et de vérification, sans archives des sources correspondantes. Windows utilise les environnements VC++ locaux à l'application et ne distribue pas les bibliothèques du compilateur graphique du SDK Windows.

Depuis le 2026-11-05, le propriétaire a demandé le retrait des anciennes archives des sources correspondantes de GitHub Releases et des artefacts Actions et l'arrêt de leur génération ou téléversement dans les futures publications. `scripts/prepare-source-delivery.py` reste disponible pour une vérification locale. L'assemblage et la publication refusent les noms d'archive contenant `corresponding-source`. Cette politique ne modifie pas les licences des composants et ne prouve pas que les obligations relatives aux sources correspondantes, à la réédition de liens ou autres sont remplies. La revue de publication doit traiter ces obligations pour la livraison réelle ; si les conditions requises ne peuvent être satisfaites autrement, bloquez la distribution des binaires concernés. Les instantanés de sources d'étiquettes générés automatiquement par GitHub dans le dépôt public ne sont pas ces pièces jointes Release.

Les publications habituelles ne doivent pas lancer de leur propre initiative le collecteur de livraison des sources en local. Ne l'exécutez que sur demande distincte et explicite de l'utilisateur visant la collecte des sources, en respectant toujours les restrictions de téléversement. Évaluez les alertes génériques de contrôle automatique selon les composants réels et leurs obligations précises ; elles ne prouvent pas à elles seules un nouveau défaut de publication.

Le ZIP de l'application macOS, le DMG et les notices doivent être exportés tant que la même application temporaire déployée et signée existe, avant le nettoyage du `.app` préparé et des enregistrements temporaires. Ne redéployez pas une autre application après nettoyage pour compléter le ZIP.

Ordre : contrôle local, gel du commit de version, création de l'étiquette, lancement manuel d'un flux Release, compilations sur trois plateformes et vérifications indépendantes du démarrage et du cycle d'installation, assemblage du manifeste brouillon, publication selon le canal après achèvement complet, puis téléchargement et vérification de toutes les pièces jointes. Une stable est une Release normale explicitement marquée Latest ; alpha/beta/rc sont des Pre-releases. Tout échec de plateforme laisse le brouillon non publié. Vérifiez SHA256SUMS avant et après publication. Si la revue de provenance ou de licence ou l'acceptation manuelle est incomplète, conservez ces limites dans les notes ; l'automatisation ne peut pas se substituer à leurs conclusions.

Les clients de mise à jour parcourent les pages GitHub Releases, ignorent les brouillons, valident les versions de manifeste et choisissent selon la version sémantique, le canal autorisé par l'utilisateur, la plateforme, l'architecture et le type de paquet. Ne déduisez pas une mise à niveau des dates de publication et ne devinez pas les noms de fichiers. Les préversions n'utilisent pas `/releases/latest`, qui les exclut. Stable ne reçoit que stable ; alpha accepte alpha, beta, rc et stable ; beta ne revient pas à alpha ; rc ne reçoit que rc et stable ; dev est pris en charge pour comparer les versions de développement. La version sémantique et le build croissant doivent tous deux augmenter. Après téléchargement, vérifiez la taille et SHA-256 ; rejetez toute valeur absente ou différente.

<a name="xdzip-trusted-update-attachments"></a>

## Pièces jointes de mise à jour de confiance

Les nouvelles versions comprennent `release.json.sig`, avec schema_version=1, algorithm=ed25519, key_id et une signature hexadécimale minuscule de 128 caractères. La signature couvre les octets bruts exacts de `release.json` ; ne l'analysez pas pour le sérialiser à nouveau avant vérification. Les clients et les assistants d'installation sans Qt utilisent chacun le jeu de clés publiques intégré `resources/update-trust.json` ; les racines de confiance fournies par un manifeste téléchargé ou une demande utilisateur sont refusées. Rejetez pour l'installation les clés inconnues, key_id en double, clés faibles et ensembles de confiance vides.

Les tâches natives macOS empaquettent et vérifient le ZIP de l’application. La tâche Linux `sign` récupère ensuite les octets vérifiés et exécute `scripts/sign-macos-update.py`, qui appelle `xdzip-update-tool sign-archive` pour produire `macos-update.json` avec schema_version, version, build, filename, bytes, sha256 et `ed_signature` Sparkle en base64. L'assemblage revérifie l'archive et sa signature et crée `appcast.xml` ne contenant que le même candidat immuable. Le champ facultatif du manifeste `macos_appcast_url` pointe vers ce fichier sous la même étiquette. Le flux utilise build comme version Sparkle, la version sémantique complète comme shortVersionString, macOS 14.0 comme minimum et n'intègre que de brèves notes. Les notes complètes restent dans le corps GitHub Release ; les clients ne récupèrent pas de notes externes.

L'archive et le flux utilisent une clé Sparkle distincte ; le flux lui-même doit aussi être signé. Les outils de publication multiplateformes suivent le [format de signature amont de Sparkle](https://github.com/sparkle-project/Sparkle/blob/2.x/common_cli/Signing.swift), signent le XML brut complet et ajoutent un bloc de commentaire sparkle-signatures avec edSignature en base64 et longueur en octets bruts. Signer uniquement la pièce jointe ne suffit pas. Vérifiez indépendamment après génération ; toute modification d'octet exige une nouvelle signature. SUPublicEDKey du paquet Mac doit correspondre à la clé publique de `resources/sparkle-update-key.json`.

L'environnement de publication fournit les clés existantes et l'identifiant de clé publique via `XDZIP_UPDATE_SIGNING_KEY_HEX`, `XDZIP_UPDATE_KEY_ID` et `XDZIP_SPARKLE_SIGNING_KEY_HEX`. Le propriétaire fournit deux ressources de clés publiques de production, versionnées avec les clients et assistants d'installation ; n'intégrez pas de clés publiques de test et ne générez pas de clés privées pendant la compilation. Le propriétaire livre d'abord les racines de confiance publiques dans une version du client, puis configure les clés privées correspondantes dans un environnement de publication fiable. La rotation livre les nouvelles clés publiques avant de changer les clés de signature afin de préserver la vérification par les anciens clients. Ceux qui n'ont pas de clés publiques intégrées doivent d'abord installer manuellement une version qui les contient ; un manifeste téléchargé ne peut pas ajouter de racine de confiance. Les anciennes publications ne sont pas signées ni remplacées rétroactivement.

Les scripts de publication compilent les outils de signature dans un processus enfant dont les deux variables d'environnement de clés privées ont été retirées ; seul le processus de l'outil compilé reçoit les clés privées de signature. Les scripts de build Cargo, compilateurs et résolveurs de dépendances ne reçoivent pas l'autorité de signature.

La tâche finale de signature signe l'archive et les manifestes de mise à jour vérifiés dans `release-signing`. La tâche distincte de publication exige également cet environnement et vérifie signatures et téléchargements du brouillon avant publication. La dernière tâche en lecture seule télécharge la publication publique et la compare aux fichiers signés. Toutes les tâches utilisent le commit figé et les artefacts de la même exécution.

[L'acceptation des mises à jour de production](../../../.github/workflows/production-update-acceptance.yml) est un point d'entrée manuel distinct, fixé à `main` et `contents: read`, utilisant le même environnement `release-signing` et l'approbation du propriétaire. Il ne lance pas Release et ne crée ni étiquette, ni brouillon, ni publication. Compilez d'abord les outils sans secret, puis dérivez indépendamment les clés publiques des clés privées existantes et comparez-les strictement aux deux clés publiques et à l'identifiant de clé publique du commit courant ; l'existence d'une entrée ne prouve pas sa correspondance. Les anciennes versions privées 200 et nouvelles 201 des trois plateformes conservent les clés publiques de production et sont compilées sans secret. La signature n'accepte que des candidats fixes entièrement liés à ce commit source, à l'identité privée du produit et aux hachages. Mise à niveau native, récupération après échec et redémarrage ordinaire s'exécutent ensuite dans des processus sans secret. Aucun manifeste, fichier, artefact distant ou paramètre de publication arbitraire n'est accepté.

Pendant la préparation sans secret de la chaîne d'outils macOS, installez une fois `rustfmt` et `clippy` déclarés dans `rust-toolchain.toml`, puis exécutez les tests d'admission des archives. Les régressions de mise à jour avec clés de test couvrent également préparation et admission sans utiliser ni vérifier les clés privées de production.

Les paquets, manifestes originaux, signatures, appcast et applications d'acceptation de production restent sur les runners jetables et ne sont pas téléversés. Un collecteur limité ne téléverse que les journaux, états, identités et relevés de hachage explicitement autorisés et refuse les pièces jointes signées dans les emplacements de résultats. Consignez séparément la correspondance des clés de production, la vérification des signatures, l'installation réelle et l'acceptation manuelle sur ordinateur. macOS utilise Apple Silicon natif et vérifie réellement `SUPublicEDKey` ; les fixtures Windows Server ne remplacent pas l'acceptation manuelle Windows 11. Ce flux ne lit pas les valeurs GitHub Secret localement et n'autorise pas une publication.

`prepare-release.py --require-update-signature` s'arrête si une clé, signature ou métadonnée d'archive native manque. `publish-release.py` revérifie indépendamment le manifeste, le flux du même candidat et les archives avant téléversement. Les signatures, appcast et pièces jointes d'état figurent tous dans le SHA256SUMS complet. N'ajoutez ni ne remplacez ces pièces jointes sur des versions déjà publiques.

<a name="xdzip-independent-cli-attachments"></a>

## Pièces jointes CLI indépendantes

À partir de v0.2.0, les publications complètes fournissent aussi `xdzip-cli-<version>-windows-x86_64.zip`, `xdzip-cli-<version>-macos-arm64.tar.gz` et `xdzip-cli-<version>-linux-x86_64.tar.gz`. Les trois proviennent de compilations et vérifications CLI natives du même commit, avec workers, dépendances d'exécution réelles et notices ; l'identité doit être une Release propre. Le CI ordinaire ne reçoit aucune autorisation supplémentaire pour déployer ou téléverser des paquets d'application Mac.

La CLI utilise `cli-release.json` et `cli-release.json.sig`. Le manifeste indique schema_version=1, product=xdzip et component=cli. version, channel, build, tag, commit et repository correspondent exactement au manifeste desktop. Assets ne contient que ces trois cibles avec les mêmes champs que les fichiers desktop. Le type de paquet Mac est tar.gz ; le système minimal Linux omet display_server. Les autres exigences de système, architecture, taille et empreinte restent inchangées. L'éditeur fixe reste xiaodaozhi/xdzip.

Le release.json desktop contient toujours exactement six types de paquet sans entrée component ou CLI. Les anciens clients ignorent les nouvelles pièces jointes indépendantes. La signature du manifeste CLI réutilise les racines de confiance Ed25519 intégrées ; sign-cli/verify-cli signent et vérifient indépendamment les octets bruts exacts. L'assemblage et la publication complets ne peuvent être rendus publics qu'après vérification des signatures, identités, trois paquets CLI et toutes les sommes de contrôle. Les versions publiques existantes ne reçoivent aucun ajout, modification ou remplacement rétroactif.
