# Sources correspondantes et documents de reconstruction

**Limite de publication, 2026-11-05 :** Sur décision du propriétaire, ce collecteur sert uniquement à la revue locale et à la vérification de reconstruction. Les archives de sources correspondantes ne sont plus fournies comme ressources GitHub Release ou artefacts Actions. Les ressources publiques historiques de Release et les artefacts Actions de publication encore téléchargeables qui contenaient ces archives ont été retirés ; les futurs workflows de publication refusent leur génération ou leur téléversement. Cette décision ne modifie pas les licences des composants et ne démontre pas que les obligations de sources correspondantes, de réédition de liens ou autres sont satisfaites. Les instantanés de sources que GitHub génère automatiquement pour les tags du dépôt public sont distincts de ces pièces jointes Release.

Une publication ou une acceptation de routine ne doit pas exécuter ce collecteur ni générer localement d’archives de sources correspondantes. Ne l’exécuter que si l’utilisateur demande explicitement la collecte des sources ; la restriction de téléversement reste applicable. La revue des licences doit identifier les composants et obligations réels, sans traiter les indicateurs génériques de revue générés par machine comme des défauts confirmés.

scripts/prepare-source-delivery.py collecte les sources du projet depuis un commit propre, les entrées Rust vendor complètes correspondant à Cargo.lock, les archives de sources fixées des modules Qt 6.8.2 et les instructions de reconstruction et de remplacement. Toutes les sorties sont sous build/. Une adresse de téléchargement n’est pas une source livrée, et le collecteur n’approuve pas automatiquement un choix de licence open source.

```sh
python3 scripts/prepare-source-delivery.py --output build/review/source-delivery \
  --qt-prefix build/toolchain/Qt/6.8.2/macos
python3 scripts/verify-source-delivery.py --delivery build/review/source-delivery \
  --qt-prefix build/toolchain/Qt/6.8.2/macos --output build/review/source-rebuild
```

Les archives des modules d’exécution Qt sont qtbase, qtdeclarative, qtsvg et qttranslations ; qtshadertools, qttools et les sources fixées de composants de la bibliothèque standard Rust nécessaires à la compilation sont également livrés depuis l’[archive officielle Qt 6.8.2](https://download.qt.io/archive/qt/6.8/6.8.2/submodules/). Les valeurs officielles .sha256 sont fixées dans scripts/corresponding-sources.json. Cache et téléchargements sont revérifiés ; les téléchargements sont d’abord écrits dans des fichiers partiels, puis validés avant leur finalisation. Seuls les répertoires des archives sont inspectés ; les chemins tiers ne sont pas extraits automatiquement. Cargo vendor utilise --locked, conserve les sommes du registre et les dépendances de compilation, et n’exécute pas les scripts de compilation tiers.

La livraison des sources inclut aussi la Public Suffix List éditable fixée et son texte MPL-2.0. La collecte vérifie l’identité des entrées, de l’archive Qt et du générateur, puis régénère et compare octet par octet les données C++ et les données binaires de test. Elle s’arrête en cas de différence et n’établit ni équivalence complète du SDK ni approbation de licence pour la publication.

La livraison conserve l’entrée Apache Tika fixée, le NOTICE d’origine et le texte OGL-UK-3.0 pour les données MIME de Qt Core. Elle vérifie l’attribution de l’archive Qt et régénère ses données MIME avec le script de conversion de l’archive fixée, en ne permettant que les différences de fins de ligne Windows natives. Le NOTICE Tika complet couvre la distribution amont plus large et n’implique pas que ses autres dépendances soient livrées par xdzip.

La livraison contient aussi les sources `common` de CLDR 46 et la licence amont utilisées pour la génération des locales Qt 6.8.2, mais pas le reste de l’arbre source CLDR. La collecte vérifie la version CLDR dans deux fichiers source Qt générés, le hash de l’archive amont fixée et les entrées sélectionnées. La seconde étape de génération de Qt exige en plus une table ISO 639-3 qui n’est pas incluse ; `qt-cldr-sources.json` enregistre la source, la version et le condensat du candidat testé, et sa [page de téléchargement et ses conditions amont](https://iso639-3.sil.org/code_tables/download_tables) nécessitent une revue distincte. Reproduire les données générées avec ce candidat n’établit ni l’entrée historique précise ni l’identité complète de compilation du SDK d’origine.

Omettre les tables ISO d’origine ne supprime pas tous les identifiants associés des autres données CLDR. Le fichier `common/validity/language.xml` de CLDR 46 conserve des codes de langue compacts et `common/supplemental/supplementalMetadata.xml` contient des alias. Dans la [comparaison locale](https://github.com/xiaodaozhi/xdzip/issues/138#issuecomment-6588994510), un ensemble candidat de trois lettres construit à partir de ces fichiers livrés couvrait 7 919 des 7 920 valeurs `Id` de la table ISO candidate CLDR 46 et comptait 338 valeurs supplémentaires. La même méthode appliquée au sous-ensemble CLDR 43.1 face à cette table ultérieure couvrait 7 896 valeurs et comptait 338 valeurs supplémentaires. L’ensemble candidat n’est pas la table d’origine et ne contient pas tous ses champs ; la seule correspondance des identifiants ne tranche ni la provenance, ni l’autorisation ou les conditions applicables. L’exclusion des cinq fichiers portant un nom ISO ne démontre pas l’absence d’autres données associées.

Le sous-ensemble CLDR 43.1 conserve aussi une entrée d’outil `language-subtag-registry` dont l’en-tête est daté du 2023-02-14. Parmi ses 8 049 sous-étiquettes de langue à trois lettres, 7 713 correspondent à des identifiants de la table ISO candidate ultérieure ; la cause de cet écart entre versions n’est pas attribuée ici. Les instructions de mise à jour Unicode identifient ce fichier comme le registre des sous-étiquettes de langue obtenu auprès de l’IANA. La déclaration CC0 de l’IANA ne couvre que les droits qu’elle possède ou peut sous-licencier et préserve les éventuels droits de tiers. Voir [#140](https://github.com/xiaodaozhi/xdzip/issues/140#issuecomment-6589292716) pour la comparaison et ses limites.

Le sous-ensemble CLDR 43.1 comprend aussi deux polices Noto, quatre fichiers Glyphicons, les scripts Bootstrap et Autosize et des images emoji utilisés par son outil web. `cldr43-webapp-notices/` fournit la provenance et les licences de ces polices et scripts et de 908 images correspondant à deux versions fixées de Noto Emoji, après vérification de chaque fichier fixé. Pour les 963 autres images originales dont la provenance et les conditions de redistribution n’ont pas été établies indépendamment, le collecteur vérifie chaque hash original et les remplace par 698 images Noto et 265 images Twemoji fixées. Le manifeste enregistre les deux hashes, les chemins et les sources ; aucune contrefaçon n’est alléguée. Ces fichiers ne font pas partie de l’interface xdzip. Les notices identifient aussi trois fichiers source de l’outil web portant des avis de copyright IBM et les traitent sous Unicode-DFS-2016 selon le README racine de cette version, en conservant copyright et licence. 27 autres images de la racine web correspondent octet pour octet à un commit CLDR fixé de 2026 et sont traitées sous la licence Unicode-3.0 de ce commit, avec la notice complète et les hashes individuels conservés. Cette évaluation ne s’étend pas aux marques, ressources non recensées ou dépendances externes.

Deux fichiers texte complets du sous-ensemble CLDR 43.1 `docs/rfc`, `draft-davis-t-langtag-ext.txt` et `draft-davis-u-langtag-ext-00.txt`, correspondent octet pour octet au [brouillon IETF d’extension T de 2011](https://www.ietf.org/archive/id/draft-davis-t-langtag-ext-07.txt) et au [brouillon d’extension U de 2010](https://www.ietf.org/archive/id/draft-davis-u-langtag-ext-00.txt). La collecte vérifie les hashes et conserve copyright et notices. Les deux font référence aux conditions en vigueur lors de leur publication ; la section 3.c de [TLP 4.0](https://trustee.ietf.org/wp-content/uploads/IETF-TLP-4.pdf) autorise leur distribution hors du processus de normalisation intégralement et sans modification, dans la mesure où le Trust peut accorder ces droits, avec conservation des notices requises. Cette évaluation ne couvre que ces deux textes, pas les autres HTML, XML, ressources ou droits de tiers.

Pour les langues déjà présentes dans les sources Qt, extraire une entrée limitée du générateur depuis le `qlocale_data_p.h` d’origine. Par exemple, après extraction de QtBase dans le répertoire courant, exécuter `python3 scripts/derive-qt-locale-code-input.py --qtbase qtbase-everywhere-src-6.8.2 --output build/qt-locale-codes.tsv`. Cela ne couvre que les clés de recherche existantes et ne constitue ni la table ISO 639-3 complète ni l’entrée amont historique. L’ajout de langues peut encore exiger des codes obtenus séparément et la revue de leurs conditions. La régénération de huit fichiers avec les sources Qt 6.8.2 fixées, les données CLDR 46 et cette entrée dérivée a été vérifiée en ne permettant que les différences de date de génération et de fins de ligne. Cela ne règle ni la licence de la table ISO ni les sources correspondantes complètes.

Pour une langue supplémentaire précise, extraire le sous-ensemble CLDR 43.1 livré et utiliser `tools/cldr-code/src/main/resources/org/unicode/cldr/util/data/language-subtag-registry` pour vérifier la sous-étiquette et fournir explicitement quatre champs de code. Les champs ISO 639-2 de l’exemple Choctaw peuvent être vérifiés dans la [liste de la Bibliothèque du Congrès](https://www.loc.gov/standards/iso639-2/php/code_list.php), et ISO 639-3 dans les [données de l’autorité d’enregistrement](https://iso639-3.sil.org/code_tables/download_tables). Le dernier champ vide indique l’absence de code à deux lettres :

```sh
python3 scripts/derive-qt-locale-code-input.py --qtbase path/to/qtbase \
  --iana path/to/cldr43/tools/cldr-code/src/main/resources/org/unicode/cldr/util/data/language-subtag-registry \
  --add-language 'cho,cho,cho,' --output build/qt-locale-codes-with-cho.tsv
```

`--add-language` peut être répété. Les champs sont le code à trois lettres, ISO 639-2/B, ISO 639-2/T et le code à deux lettres ; les champs manquants sont vides et les deux champs de la partie 2 doivent être fournis ensemble ou tous deux laissés vides. L’outil vérifie qu’au moins un code à trois ou deux lettres est une sous-étiquette IANA enregistrée, valide la syntaxe et refuse les conflits de clés Qt. Il ne déduit ni ne vérifie que les champs désignent la même langue et n’établit pas les correspondances ISO. Le destinataire doit examiner chaque correspondance et sa source. Ajouter une langue Qt exige aussi de mettre à jour `enumdata.py`, fournir des données de locale CLDR et régénérer et reconstruire Qt ; la ligne seule n’ajoute pas de langue. Cela reste une table dérivée limitée, et non la table ISO complète ni une preuve de l’identité de l’entrée historique ou de sources correspondantes complètes.

Dans un test isolé, l’ajout manuel d’un code de test à usage privé à l’enum de l’outil Qt et à la table dérivée a généré un nouvel enum et une entrée de code. Un QtCore Linux reconstruit a réussi les recherches directe et inverse, et une copie isolée de l’alpha.8 d’origine a effectué navigation, annulation et extraction hors écran. Aucun véritable langage ni donnée de format de locale CLDR n’a été ajouté ; cela ne remplace pas la revue des entrées et conditions réelles et n’établit pas toutes les obligations de sources correspondantes. Voir [#138](https://github.com/xiaodaozhi/xdzip/issues/138#issuecomment-6611169790) pour les étapes et l’échec initial de la sonde.

Une autre option consiste à obtenir indépendamment les données JSON ISO 639-2 et 639-3 de `iso-codes` et à les convertir en entrée Qt. Par exemple sous Linux avec le paquet de données installé :

```sh
python3 scripts/convert-iso-codes-for-qt.py \
  --iso-639-2 /usr/share/iso-codes/json/iso_639-2.json \
  --iso-639-3 /usr/share/iso-codes/json/iso_639-3.json \
  --output build/qt-iso-codes.tsv
```

Le convertisseur extrait les correspondances de codes sans noms ; une entrée complète produit toujours un ensemble complet de codes. Il refuse codes invalides, doublons et conflits de clés Qt, ignore la plage ISO 639-2 réservée à l’usage local et indique les SHA-256 d’entrée et de sortie. Voir [#138](https://github.com/xiaodaozhi/xdzip/issues/138) pour la comparaison Qt 6.8.2 avec Ubuntu `iso-codes` 4.16.0-1 ; les autres versions doivent être vérifiées séparément. Les données ne sont pas incluses. Examiner indépendamment leur licence déclarée, provenance et conditions de redistribution des tables générées ; une table alternative n’établit ni l’entrée historique Qt ni la conformité complète des sources.

Pour reproduire la comparaison, obtenir indépendamment le [paquet Ubuntu `iso-codes` 4.16.0-1](https://archive.ubuntu.com/ubuntu/pool/main/i/iso-codes/iso-codes_4.16.0-1_all.deb) fixé. L’exemple Linux suivant exige `curl`, `dpkg-deb` et Python 3 ; il vérifie le hash du paquet avant extraction et conversion locales sans modifier l’installation du système :

```sh
mkdir -p build && mkdir build/qt-iso-peer &&
curl --fail --location --silent --show-error --connect-timeout 15 --max-time 120 https://archive.ubuntu.com/ubuntu/pool/main/i/iso-codes/iso-codes_4.16.0-1_all.deb -o build/qt-iso-peer/iso-codes.deb &&
python3 -c "import hashlib,pathlib,sys; p=pathlib.Path('build/qt-iso-peer/iso-codes.deb'); h=hashlib.sha256(p.read_bytes()).hexdigest(); sys.exit(0 if h=='cafca0a3a1f07b44fbba53ab7a1f1d9755e6b80cc041173afe2b52e53bed97a7' else 'Package SHA-256 mismatch')" &&
dpkg-deb -x build/qt-iso-peer/iso-codes.deb build/qt-iso-peer/data &&
python3 scripts/convert-iso-codes-for-qt.py \
  --iso-639-2 build/qt-iso-peer/data/usr/share/iso-codes/json/iso_639-2.json \
  --iso-639-3 build/qt-iso-peer/data/usr/share/iso-codes/json/iso_639-3.json \
  --output build/qt-iso-peer/qt-locale-codes.tsv
```

Les SHA-256 des entrées vérifiées sont `fa83810fdb59f9d84b4d58486d5e5e48e807d82a98d6a39ef0ba4fc57c2a9327` et `9636ce5266053867627140ce5ada1f9aa897ca07a7501302c1b14b8d1147cdda` ; la sortie convertie est `85457a36e013e053b70dea19d500ebec2ae6bedf5dad9af0035b973c8db6a60a`. Le fichier Ubuntu `usr/share/doc/iso-codes/copyright` déclare LGPL-2.1-or-later, mais cette déclaration au niveau du paquet ne démontre pas à elle seule l’autorisation historique de la table SIL ni les droits de redistribution d’un ensemble complet de codes. Ni le paquet ni la table complète convertie ne sont inclus ici ; examiner séparément provenance, conditions et redistribution ultérieure.

Il est également possible d’obtenir indépendamment le [registre IANA des sous-étiquettes de langue](https://www.iana.org/assignments/language-subtag-registry/language-subtag-registry) et la [liste ISO 639-2 de la Bibliothèque du Congrès](https://loc.gov/standards/iso639-2/ISO-639-2_utf-8.txt), puis de générer une autre entrée. L’outil extrait les codes sans les noms, indique les codes sans correspondance et les hashes d’entrée et sortie, et refuse les enregistrements invalides ou ambigus. L’exemple shell Linux/macOS utilise un nouveau répertoire et vérifie les deux fichiers bruts de cette comparaison avant conversion :

```sh
(
  set -eu
  mkdir -p build
  mkdir build/qt-iana-loc-inputs
  curl --fail --location --output build/qt-iana-loc-inputs/iana.txt \
    https://www.iana.org/assignments/language-subtag-registry/language-subtag-registry
  curl --fail --location --output build/qt-iana-loc-inputs/loc.txt \
    https://loc.gov/standards/iso639-2/ISO-639-2_utf-8.txt
  python3 -c 'import hashlib,pathlib,sys; p=sys.argv[1:]; sys.exit(0 if all(hashlib.sha256(pathlib.Path(p[i]).read_bytes()).hexdigest()==p[i+1] for i in (0,2)) else "Input SHA-256 mismatch")' \
    build/qt-iana-loc-inputs/iana.txt 755fad43283be7b41ebe3c89ad054b6eaf928f404f9c0edb74799e0eab74beb1 \
    build/qt-iana-loc-inputs/loc.txt 42b71885e4dc885559fda5ad059fd81838cf4782cedb5fd08cc3431f7d067371
  python3 scripts/convert-iana-loc-for-qt.py \
    --iana build/qt-iana-loc-inputs/iana.txt \
    --loc build/qt-iana-loc-inputs/loc.txt \
    --output build/qt-iana-loc-inputs/qt-codes.tsv
)
```

La comparaison utilisait un fichier IANA daté du 2026-09-17, SHA-256 `755fad43283be7b41ebe3c89ad054b6eaf928f404f9c0edb74799e0eab74beb1`. Le fichier LoC UTF-8 obtenu directement le 2026-11-03 mesurait 16 010 octets, SHA-256 `42b71885e4dc885559fda5ad059fd81838cf4782cedb5fd08cc3431f7d067371`. Les trois premiers champs de code de ses 487 enregistrements correspondaient individuellement à la reconstruction web antérieure. Le SHA-256 de la sortie LF du convertisseur était `6a75bebfa694258a1a4125fc30512d8ae7994080701377b41306db665ad371c6`. Ensemble, ces entrées produisaient 8268 lignes correspondant aux 346 clés de recherche Qt distinctes existantes. Les huit fichiers régénérés correspondaient après normalisation des dates de génération et des fins de ligne ; un contrôle négatif modifiant une entrée correspondait à sept. Sept sous-étiquettes IANA à deux lettres `bh`, `in`, `iw`, `ji`, `jw`, `mo`, `sh` n’avaient pas d’enregistrement LoC et sont signalées par l’outil. Vérifier séparément les autres versions et langues ajoutées. Les adresses amont peuvent changer ; examiner une différence de hash au lieu de contourner les contrôles. Voir [#138](https://github.com/xiaodaozhi/xdzip/issues/138#issuecomment-6588040592).

La [déclaration IANA/IETF](https://www.iana.org/help/licensing-terms) applique CC0 aux droits de registres de protocoles qu’elles possèdent ou peuvent sous-licencier, tout en préservant les éventuels droits de tiers ; elle n’établit pas automatiquement tous les droits sur la table SIL d’origine. Ni l’instantané IANA du 2026-09-17, ni l’entrée LoC ou la table complète de comparaison convertie ne sont inclus ici. Le sous-ensemble CLDR 43.1 contient séparément le registre antérieur décrit ci-dessus. Les destinataires doivent examiner séparément provenance, conditions applicables et redistribution ultérieure. Cette alternative n’établit ni l’entrée historique Qt ni la conformité complète des sources correspondantes.

Ici, comparaison indépendante signifie obtenir et convertir les fichiers séparément, pas une provenance indépendante des normes. La [section 2.2.1 de la RFC 5646](https://www.rfc-editor.org/rfc/rfc5646#section-2.2.1) identifie ISO 639-2, 639-3 et 639-5 comme sources normatives des sous-étiquettes IANA de langue à trois lettres. La correspondance des valeurs n’établit ni paternité indépendante ni sous-licence complète.

La sortie comprend xdzip-source.tar pour le commit effectivement fixé, rust-vendor.tar.gz, la configuration Cargo hors ligne, les archives Qt d’origine, REBUILD.md et un manifeste SHA-256 et taille par fichier. Le manifeste indique explicitement une collecte sans vérification de conformité ; il ne remplace pas les contrôles des options et correctifs de compilation du SDK, runtimes de plateforme, ressources intégrées ou conformité des licences. Les sources reconfigurées du projet peuvent avoir une identité inconnue et doivent être reliées au commit d’origine par le manifeste externe de livraison, sans fabriquer une identité Git propre.

Le répertoire distinct `rar-wire-mappings/` conserve la provenance des références de correspondances finies bornées, des explications et la notice originale exacte d’UnRAR 7.30 beta1, tous inclus dans la livraison avec hash. Le nom de téléchargement fixé est `unrarsrc-7.3.1.tar.gz` ; son nom numérique n’établit pas une autre version amont. Par précaution pour la notice, la livraison exige le deuxième paragraphe complet de la licence d’origine dans les commentaires source Rust associés et s’arrête s’il manque ou a changé. Le crate RAR déclare par prudence `Apache-2.0 AND UnRAR` ; l’identifiant `UnRAR` non approuvé par l’OSI apparaît dans SPDX 3.28 et suivants et peut ne pas être reconnu par les anciens outils. Ces documents ne contiennent pas les sources du moteur officiel et ne placent pas sous Apache-2.0 les faits dérivés des références. Les conditions applicables et les obligations réelles de redistribution exigent une revue propre à chaque candidat.

Pour ICU sous Linux, la licence complète fixée ICU 73.2, l’archive officielle des sources ICU4C 73.2, les sources éditables ICU fixées, le sous-ensemble source CLDR 43.1 et les sources d’amorçage ICU 73.1 sont inclus et entrent dans le manifeste général. Le sous-ensemble CLDR exclut cinq fichiers ISO 639-3, le texte UTS #35 et les fichiers associés sous `docs/ldml`, ainsi que deux captures de documentation, et remplace 963 images de l’outil web. L’enregistrement de livraison conserve le hash de l’archive amont et chaque exclusion et remplacement. La [version 43.1 d’UTS #35 publiée par Unicode](https://www.unicode.org/reports/tr35/tr35-69/tr35.html) est disponible séparément selon les conditions de son propriétaire ; l’existence d’une autorisation transférable supplémentaire reste à établir. Le collecteur refuse aussi les fichiers d’archive d’amorçage dont le nom contient `iso-639-3` ; un contrôle de nom n’exclut pas des données sous une autre forme. La collecte vérifie hashes d’archives, versions, licences intégrées et fichiers source sélectionnés sans extraire de chemins tiers. Le [guide de reconstruction des données ICU](icu-cldr-rebuild.md) documente la compilation des outils et le périmètre de génération et d’édition. Des versions amont concordantes ne prouvent pas qu’un fournisseur a compilé ses binaires depuis ces entrées sans correctifs. Les paquets de développement Windows actuels omettent OpenGL logiciel et ne collectent plus de documents dédiés Mesa/LLVM ; les livraisons historiques conservent leurs documents et obligations d’origine. Voir [sources et notices du runtime natif](native-runtime-materials.md).

L’application lie Qt dynamiquement et fournit des instructions de reconstruction des sources et de remplacement par des bibliothèques compatibles. La [vérification du déploiement macOS](macos-deployment.md) couvre le chargement de bibliothèques modifiées dans une copie isolée sans prétendre à une reconstruction complète des sources Qt. Les véritables compilations des sources Qt et le chargement du produit suivent un processus distinct dans le [contrat de vérification automatisée](../../../developers/engineering/candidate-verification.md). L’équivalence octet par octet du build du SDK, l’attribution exacte des liens statiques et les choix de licence relèvent de la [revue des licences de publication](https://github.com/xiaodaozhi/xdzip/issues/4), et non d’une réouverture du développement WP-12 terminé.

verify-source-delivery.py revérifie d’abord les hashes des fichiers livrés, extrait de façon sûre les entrées propres du projet et vendor dans un nouveau répertoire build/, compile l’application réelle avec un cache Cargo vide, CARGO_NET_OFFLINE=true et le SDK Qt fixé existant, puis exécute un test rapide de démarrage et d’arrêt. Cela vérifie l’utilisation hors ligne des entrées du projet et Rust, pas la compilation des sources des modules Qt ni des builds reproductibles octet pour octet. Les répertoires source générés ont une identité Git inconnue, reliée extérieurement au commit fixé par le manifeste de livraison.

La livraison des sources invoque Cargo depuis le répertoire de sortie avec une destination `vendor` relative et un manifeste de projet explicite. Seuls le mappage de source crates.io actuellement pris en charge et la configuration relative `vendor` sont acceptés. Les répertoires absolus, échappements de chemin et mappages inattendus échouent plutôt que d’insérer les chemins de la machine de compilation dans une livraison déplaçable.

Pour les paquets vendor fixés dépourvus de fichiers autonomes de licence ou de notice aux noms conventionnels, `rust-vendor-notices/` indexe séparément les textes originaux amont fixés par paquet. Le collecteur vérifie le hash du manifeste Cargo du paquet, le commit et chemin Git amont, le SHA-256 du texte de licence et le blob Git ; lacunes inconnues ou différences d’identité arrêtent la livraison. Ce répertoire ne modifie ni les fichiers ni les sommes Cargo vendor. Les expressions de licence amont restent inchangées ; cela n’approuve ni un choix précis de licence ni la conformité d’une publication antérieure.

La [vérification de correspondance du SDK Qt](qt-sdk-correspondence.md) inclut toujours le manifeste de correspondance fixé et le correctif de consommateur AGL rejouable. Avec --qt-prefix, elle comprend aussi les vérifications par fichier des déclarations de sources, la configuration de compilation et les lacunes explicites de ce SDK. Le manifeste de livraison calcule récursivement les hashes des sous-répertoires de correctifs et la vérification de reconstruction contrôle à nouveau ces octets. Sans SDK, aucun enregistrement de vérification de configuration n’est fabriqué.

La livraison conserve un objet de commit Git Qt Declarative fixé pour vérifier hors ligne le lien du commit de publication avec l’objet d’arbre `.tag` de l’archive ; le manifeste de livraison en calcule le hash. Cette relation n’établit ni couverture complète de l’archive ni équivalence de compilation du SDK.

Voir le [contrat de finalisation automatisée](../../../developers/engineering/candidate-verification.md) pour les véritables compilations de Qt depuis les sources et le chargement ou remplacement compatible. Les reconstructions hors ligne de l’application avec un SDK existant ne doivent pas être décrites comme la reconstruction de Qt lui-même depuis les sources.
