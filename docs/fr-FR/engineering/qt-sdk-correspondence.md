# Vérification de la correspondance entre le SDK Qt et ses sources

[English](../../engineering/qt-sdk-correspondence.md) | [简体中文](../../zh-CN/engineering/qt-sdk-correspondence.md) | [繁體中文](../../zh-TW/engineering/qt-sdk-correspondence.md) | [日本語](../../ja-JP/engineering/qt-sdk-correspondence.md) | [한국어](../../ko-KR/engineering/qt-sdk-correspondence.md) | Français | [Deutsch](../../de-DE/engineering/qt-sdk-correspondence.md) | [Español](../../es-ES/engineering/qt-sdk-correspondence.md) | [Português (Brasil)](../../pt-BR/engineering/qt-sdk-correspondence.md) | [Русский](../../ru-RU/engineering/qt-sdk-correspondence.md)

La vérification de correspondance utilise les octets réels des archives officielles ; une version identique ne prouve pas l’équivalence de compilation du SDK. `scripts/qt_sdk_correspondence.py` associe les archives sources épinglées, les SPDX source fournis par le SDK, les déclarations de compilation, la configuration installée et les correctifs connus appliqués par les utilisateurs du SDK, puis écrit les résultats dans build/. Il ne modifie pas le SDK et n’approuve aucun choix de licence.

```sh
python3 scripts/qt_sdk_correspondence.py \
  --qt-prefix build/toolchain/Qt/6.8.2/macos \
  --output build/review/qt-sdk-correspondence.json
```

Par défaut, le programme lit build/source-cache hors ligne et échoue si les données manquent. Seul --fetch explicitement indiqué télécharge et vérifie les archives officielles du [manifeste épinglé](../../../scripts/corresponding-sources.json). Les workflows Qt à la demande sur les trois plateformes exécutent --fetch après installation du SDK épinglé et conservent le JSON avec les autres résultats. Sur Mac, ils ne téléversent toujours que les enregistrements, sans déployer, signer ni empaqueter d’application. Lorsque le collecteur de livraison des sources reçoit --qt-prefix, il inclut cet enregistrement, les correctifs et le manifeste épinglé dans les empreintes de la livraison ; voir la [livraison des sources](source-delivery.md).

<a name="xdzip-verification-layers"></a>

## Niveaux de vérification

1. Le SHA-256 de l’archive doit correspondre à la valeur épinglée ; la racine de l’archive, les chemins des membres et le marqueur `.tag` fixé doivent correspondre. Le type d’objet Git du marqueur est enregistré séparément. Pour un marqueur d’arbre, recalculez d’abord le hachage de l’objet commit d’origine épinglé et vérifiez son champ tree. Lisez les fichiers individuellement sans extraire les sources amont.
2. Si le SDK fournit le fichier .source.spdx d’un module, comparez chaque SHA-1 déclaré au contenu de l’archive. Enregistrez le nombre de correspondances, les deux hachages des différences, les fichiers déclarés par le SDK mais absents de l’archive et le nombre de fichiers de l’archive non couverts. SHA-1 ne vérifie que la déclaration d’origine en amont ; l’archive entière est liée séparément par le SHA-256 épinglé. Les déclarations manquantes, différences et fichiers non couverts ne sont pas marqués comme réussis.
3. Conservez les hachages SPDX de compilation des modules SDK, les déclarations de compilateur et les arguments configure. Lisez également les fichiers installés modules/*.json, qconfig*.pri et les en-têtes de configuration QT_FEATURE, en conservant contenu et hachages. Remplacez dans la sortie les répertoires absolus du constructeur amont par des espaces réservés ; les hachages lient les preuves d’origine. La configuration ne comprend pas tout le cache CMake, l’environnement de compilation ni les éléments de la chaîne d’outils. Les champs d’architecture par défaut du SDK ne représentent pas toutes les architectures des bibliothèques réelles et ne permettent pas de classer à tort des bibliothèques universelles comme x86_64.
4. Le [correctif AGL](../../../scripts/qt-patches/macos-no-agl.patch) ne modifie que lib/cmake/Qt6/FindWrapOpenGL.cmake dans le SDK pour éviter la liaison à l’ancien AGL lorsque ce projet utilise Qt. L’outil lit l’original dans l’archive QtBase épinglée, applique le diff unifié, vérifie les SHA-256 du correctif, de l’original et du résultat, puis contrôle le fichier SDK réel. Seules les versions originale ou corrigée connue sont acceptées. Pour le CRLF du SDK Windows, la comparaison n’a lieu qu’après normalisation des fins de ligne, en conservant le SHA-256 des octets réels, le SHA-256 LF et un marqueur de conversion. Toute autre modification inconnue échoue. Cela ne modifie pas le code machine d’exécution Qt et ne prouve pas que Qt a été recompilé. L’historique complet des modifications du SDK reste à vérifier.

Les enregistrements de correspondance utilisent le schéma 2 et conservent séparément archive_commit épinglé, archive_marker réel de l’archive, archive_marker_type et commit_tree_verified. Pour Qt Declarative 6.8.2, `.tag` est l’arbre Git `0a8139c574fe150aba92d5f2484a8f3fdb774977` ; le tag de publication correspond au commit `75534f3e7fff24ed7ccb364e2ed9950a73da879f`. Un objet commit d’origine en base64 épinglé dans le dépôt permet de recalculer hors ligne le hachage du commit et de valider son champ tree. Les autres marqueurs de modules actuellement épinglés sont des commits. La relation d’arbre n’établit que le lien entre ces deux objets Git ; elle ne prouve ni que l’archive contient l’arbre complet ni que le SDK est équivalent à sa compilation.

Les source_commits de qt-license-sources.json identifient uniquement les commits épinglés de récupération des textes de licence et sont stockés séparément des marqueurs d’archive et des commits de publication. Ils ne peuvent pas être présentés comme les commits de compilation du SDK. Les anciens documents du schéma 1 plaçaient le marqueur d’arbre Qt Declarative dans archive_commit ; les éléments publiés restent inchangés. Les explications ultérieures doivent corriger le type d’objet tout en continuant de vérifier les textes de licence avec le SHA-256 d’origine.

<a name="xdzip-interpreting-results-and-release-boundaries"></a>

## Interprétation des résultats et limites de publication

Le dérivé de sécurité QtNetwork enregistre séparément `network_security` avec des justificatifs liant les correctifs, le constructeur, les empreintes de QtCore d’origine et de QtNetwork réel, les fonctionnalités et la vérification réelle du transport. À la lecture des justificatifs, l’outil revérifie les octets réels du SDK. Cette preuve ne concerne que la bibliothèque modifiée ; elle ne transforme pas le SPDX amont en preuve du dérivé et ne change pas les faits non couverts des autres modules. Voir les [notes de correctifs Qt](../../../patches/qt/README.md) pour les entrées et la maintenance.

La présence d’un SPDX source par module, les nombres de fichiers correspondants, manquants ou non couverts, la configuration et les états de correctifs sont ceux du JSON généré pour l’exécution courante. Ne généralisez pas les observations d’un SDK à un autre. Sans déclaration fichier par fichier, ne concluez pas que la correspondance a réussi ; conservez les lacunes précises.

Le statut du rapport est toujours evidence-collected-not-build-equivalence. La [compilation réelle des sources Qt et leur chargement ou remplacement](../../../developers/engineering/candidate-verification.md#qt-source-and-compatible-replacement) suit un processus distinct, qui ne prouve pas la reproduction octet par octet du SDK d’origine. Tant que les éléments complets de la chaîne d’outils et du SDK système, les fichiers non couverts ou générés, la provenance à l’exécution et le respect des licences ne sont pas entièrement clarifiés, ne déclarez pas toutes les obligations relatives aux sources correspondantes satisfaites ni les compilations reproductibles octet par octet. Le statut incomplet de l’[attribution à l’exécution](runtime-attribution.md), les choix de licence et les revues d’exécution par plateforme restent applicables.
