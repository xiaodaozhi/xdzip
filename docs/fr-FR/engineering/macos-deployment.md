# DMG local de développement macOS

[English](../../engineering/macos-deployment.md) | [简体中文](../../zh-CN/engineering/macos-deployment.md) | [繁體中文](../../zh-TW/engineering/macos-deployment.md) | [日本語](../../ja-JP/engineering/macos-deployment.md) | Français | [Deutsch](../../de-DE/engineering/macos-deployment.md) | [Español](../../es-ES/engineering/macos-deployment.md) | [Português (Brasil)](../../pt-BR/engineering/macos-deployment.md)

Le workflow Release dédié autorise le déploiement natif, la signature ad hoc nécessaire, la création de app.zip et du DMG, ainsi que leur téléversement. Le job macOS du workflow Qt à la demande conserve la vérification du SDK. Une seule application .app déployée, signée et vérifiée sert aux deux paquets de publication ; l’application extraite du ZIP fait aussi l’objet d’une vérification de démarrage après déplacement. Voir le [protocole de publication](release-protocol.md).

Un DMG local de développement est un livrable de développement autorisé. Le workflow Qt à la demande vérifie la compilation et le démarrage natifs Apple Silicon sans empaqueter, signer ou téléverser une application Mac. Les scripts locaux n’installent pas l’application, ne changent pas les associations par défaut, ne téléversent aucun fichier et ne lisent aucun identifiant de publication.

## Compiler et vérifier

Les contrôles préalables de l’environnement et les options de chaque étape suivent le [guide de compilation pour développeurs](../../engineering/developer-build.md). Préparez les outils d’empaquetage, compilez une application principale Release distincte à partir d’un commit propre, puis empaquetez et vérifiez :

```sh
python3 scripts/desktop.py prepare --packaging
python3 scripts/desktop.py build --build-dir build/desktop-dmg --macos-handler-rank Alternate
python3 scripts/desktop.py test --build-dir build/desktop-dmg
python3 scripts/desktop.py doctor --for-stage package --build-dir build/desktop-dmg
python3 scripts/desktop.py package --build-dir build/desktop-dmg --output-dir build/package-macos --kind all
python3 scripts/desktop.py verify --build-dir build/desktop-dmg --output-dir build/package-macos --kind all
```

Les étapes ne relancent pas implicitement les précédentes. Le SDK Qt par défaut se trouve dans `build/toolchain/Qt/6.8.2/macos` ; pour un autre emplacement, passez `--qt-prefix` à chaque commande. Les compilations ordinaires de développement et de test utilisent `None` par défaut ; l’application principale ci-dessus choisit explicitement `Alternate` sans modifier les préférences par défaut de l’utilisateur. Le paquet macOS local n’accepte que `all`. Le workflow Qt à la demande n’empaquette ni ne téléverse d’application Mac ; l’exception Release dédiée est décrite dans le protocole de publication.

Avant macdeployqt, les contrôles communs du paquet vérifient arm64 natif, le SDK système, les outils d’empaquetage, le PATH et les métadonnées épinglées de Rust, les dépendances Python de validation ainsi que les documents de licence et schémas Qt. Les étapes build et test acceptent des sources non commises ; package exige un commit propre et une identité CLI réelle correspondante, sans pouvoir contourner ces conditions par les caches de compilation. Compilateur et SDK système, lipo, codesign et hdiutil proviennent de la chaîne système et ne sont pas installés par prepare.

macdeployqt déplace également le processus de prévisualisation d’images. La sélection par défaut des plugins de plateforme Qt 6.8 ne comprend que Cocoa ; le script d’empaquetage copie donc explicitement offscreen avant d’analyser les bibliothèques de l’application, afin de traiter ses dépendances aux frameworks Qt. Un plugin ou processus manquant fait échouer l’empaquetage. Après signature d’intégrité et audit des imports, effacez les surcharges de recherche Qt/QML/DYLD et vérifiez les formats du véritable processus d’image inclus ainsi que le décodage d’un PNG appartenant au projet ; le reçu est `image-preview-deployed.json`. Les tests unitaires des scripts ne prouvent pas l’acceptation du paquet déployé.

Les scripts sous-jacents [build-macos-dmg.py](../../../scripts/build-macos-dmg.py) et [verify-macos-dmg.py](../../../scripts/verify-macos-dmg.py) conservent les détails de l’image et des vérifications natives. Utilisez leur option `--help` pour le diagnostic plutôt que de maintenir une autre procédure courante. Leurs chemins de sortie doivent être nouveaux et situés dans build/. Chaque type de document de l’entrée DMG doit déclarer `Viewer/Alternate` ; sinon, recompilez au lieu de réécrire le plist ou les signatures du bundle d’origine. macdeployqt analyse le QML réel et déploie frameworks Qt, plugins et QML. Ajoutez les traductions des contrôles système Qt, les avis du projet, les avis amont Rust, les licences des polices, le SBOM source et les documents de licence Qt épinglés. Conservez les liens symboliques internes aux frameworks et rejetez ceux qui sortent de l’application. Supprimez les RPATH absolus propres à la machine du développeur et vérifiez récursivement que tous les imports natifs se résolvent uniquement dans l’application ou le système. L’identité de compilation ne doit être ni modifiée ni inconnue et doit correspondre au commit propre courant pour lier les avis réellement inclus.

Le module QML facultatif LocalStorage de Qt entraîne QtSql ; le déploiement copie donc aussi les pilotes de base de données. Le projet ne fournit pas de fonctionnalité de serveur de base de données : retirez les pilotes autres que SQLite intégré pour éviter PostgreSQL, ODBC, Mimer et les autres clients externes au SDK dans l’image. Enregistrez les suppressions dans le reçu et ne présentez pas des imports non résolus comme réussis.

## Réduction des architectures et styles

Les DMG de développement ne livrent que `arm64` Apple Silicon. Les paramètres d’architecture CMake du programme principal ne contraignent pas les fichiers du SDK Qt copiés par macdeployqt ; inspectez donc récursivement chaque Mach-O de l’application, y compris frameworks, bibliothèques dynamiques, plugins et plugins natifs QML. Ne retirez les autres architectures des fichiers universels que dans la copie nouvellement créée pour l’empaquetage. Une architecture `arm64` absente, une architecture non reconnue ou une tranche supplémentaire restante fait échouer l’empaquetage ; l’architecture de l’exécutable principal ne remplace pas les contrôles imbriqués. Effectuez la réduction avant la réécriture des RPATH et la signature ad hoc récursive.

Le produit utilise Qt Quick Controls `Basic`. Le déploiement ne supprime que les styles non Basic explicitement énumérés et leurs imports ou plugins d’implémentation dédiés ; il conserve Basic, les contrôles partagés, Templates et les dépendances QML réelles. Ne réduisez pas le paquet en supprimant des modules inconnus. Une disposition de styles inattendue, une dépendance conservée manquante ou un reste de style inutilisé fait échouer l’audit. Un changement de style du produit ou de SDK Qt exige une mise à jour coordonnée des règles de réduction et des tests. La réduction de taille ne dispense pas des licences Qt, des sources correspondantes, des traductions système ou des plugins d’exécution nécessaires.

Optimisez uniquement l’application préparée sous `build/`, et non l’application principale d’entrée, le SDK Qt ou les sources. Les reçus conservent les contrôles d’architecture et de style, les binaires réduits, les listes de suppression et les octets logiques réels de l’application avant et après optimisation, répartis entre frameworks, plugins, QML et autres catégories. Les octets correspondent au contenu réel des fichiers sans double comptage des liens symboliques ; ce ne sont ni l’espace disque indiqué par Finder ni la taille de l’image UDZO. La taille finale du DMG est enregistrée séparément. Les comparaisons propres à une version, conclusions de vérification et travaux restants vont dans les issues ; les mesures brutes restent dans les artefacts locaux.

`scripts/test-macos-bundle.py` utilise de petits échantillons appartenant au projet dans la CI multiplateforme pour vérifier la reconnaissance des architectures, l’opération sur copie uniquement, les limites des liens symboliques, la conservation et suppression des styles et les échecs, sans outils de déploiement macOS. Il ne remplace pas la vérification du paquet final. Les contrôles DMG doivent confirmer récursivement la présence exclusive de `arm64` dans tous les fichiers natifs et les styles conformes au contrat après copie depuis l’image montée, puis exécuter les vérifications d’isolation du SDK et les scénarios Cocoa/Metal ci-dessous.

## Vérification de l’image et de l’exécution

L’image compressée UDZO contient xdzip.app, un lien Applications et des instructions d’installation ; exécutez hdiutil verify. Quittez normalement les anciennes versions avant de glisser l’application dans Applications. Ce processus ne prévoit ni mise à jour automatique ni migration des tâches pendant l’installation. Les réglages et éléments récents restent dans les répertoires utilisateur et ne sont pas automatiquement supprimés avec l’application.

Conservez le JSON de vérification du déploiement et un SBOM CycloneDX au niveau des fichiers à côté de l’image, liés à l’inventaire source du même commit, aux SHA-256 finaux des fichiers natifs et aux relations d’import. Le SBOM reste incomplet : énumérer les fichiers ne constitue ni une attribution exacte des composants ni une approbation des licences. Conservez l’inventaire hors de l’image pour éviter son propre hachage récursif.

Le nouveau `xdzip.app` préparé n’existe que pendant le déploiement, la signature, la création de l’image et la vérification ; il est automatiquement supprimé en cas de réussite comme d’échec. DMG, JSON, SBOM et instructions restent ; l’application principale d’entrée est inchangée. Aucun bundle préparé isolé ne reste à redécouvrir par le système.

Les fichiers Mach-O ARM64 modifiés nécessitent des répertoires de code valides ; appliquez donc une signature ad hoc locale après copie et réécriture, puis vérifiez le code imbriqué. **Ce n’est ni une signature Developer ID ni une notarisation et cela n’implique aucune confiance Gatekeeper.** Selon la [politique personnelle de publication open source](../../../developers/engineering/release-runbook.md), la signature formelle et la notarisation ne sont pas des conditions obligatoires de publication ; la vérification des dépendances, licences, sécurité et du paquet réel reste nécessaire. Ne désactivez pas SIP et ne supprimez pas de règles globales de sécurité utilisateur.

Le script de vérification monte l’image en lecture seule, vérifie le lien Applications, copie l’application vers un chemin isolé contenant des caractères chinois et des espaces, puis contrôle récursivement arm64, les styles Basic et les signatures strictes de chaque fichier natif et du bundle. Après suppression des variables de recherche SDK/QML/plugins, il démarre et ferme l’application avec Cocoa/Metal. Le produit réel issu de l’image ouvre un ZIP généré par le projet, effectue recherche, tri, extraction et fermeture, vérifie indépendamment Unicode, fichiers et dossiers vides et chaque octet de sortie, puis contrôle l’identité de compilation, l’architecture et le moteur Metal dès la première image effective. Ensuite, uniquement dans la copie de vérification, il modifie l’identité de la bibliothèque Mach-O QtCore et la signe à nouveau ad hoc, puis revérifie architecture, styles, signatures et démarrage. Cela démontre que la modification ou le remplacement déployé est possible ; cela ne prouve ni une reconstruction de Qt depuis les sources correspondantes, ni une compatibilité ABI arbitraire, ni une approbation juridique.

La vérification de app.zip utilise également l’option par défaut du produit créant un dossier de même nom pour extraire l’application entière ; elle compare octet par octet les fichiers, cibles de liens et permissions sûres avec `ditto`, puis vérifie les signatures strictes en profondeur et le démarrage Cocoa/Metal de l’application réelle extraite. Le répertoire extérieur ne doit pas se terminer par `.app`. Les applications temporaires et enregistrements créés pendant le contrôle sont ensuite nettoyés. Cela ne modifie pas les limites de confiance de la signature ou de notarisation.

La machine locale conserve un SDK ; les contrôles d’import et la suppression des variables d’environnement ne remplacent pas un Mac distinct et vierge. Glisser-déposer dans Finder, Ouvrir avec du système, choix par défaut, Gatekeeper, redémarrage réel, signature et notarisation restent soumis à la [liste de vérification manuelle](../../../developers/qa/private-test-manual.md).

Les commandes d’édition des menus natifs et contrôles standard Qt nécessitent les traductions qtbase de la langue système. En plus de copier `Contents/Resources/translations/qtbase_*.qm`, l’empaquetage définit `Translations = Resources/translations` dans `[Paths]` de `Contents/Resources/qt.conf`, conserve les chemins existants des plugins et du QML, et écrit ce fichier avant la signature d’intégrité. Les contrôles de démarrage après déplacement vérifient à la fois les répondeurs natifs d’édition et les rôles du menu de l’application ; les contrôles dans le répertoire de développement du SDK ne suffisent pas.

## Signature et activation locales de Finder Sync

Finder Sync utilise une appex native et un relais indépendant dans la même application ; l’assistant de service reste présent. L’ordre complet de signature est : images natives, frameworks et assistants dédiés, appex avec les droits de sandbox exacts, bundle du relais, puis application extérieure, suivis d’une vérification stricte du bundle imbriqué. Ne remplacez pas ensuite une appex signée par une signature générique sans ses droits. Les compilations CI ordinaires ne signent ni n’activent implicitement l’extension.

Pour vérifier Finder localement, terminez la compilation native par défaut puis exécutez explicitement :

```sh
python3 scripts/sign-macos-finder.py --app build/desktop/apps/desktop/xdzip.app --output build/review/finder-signing.json
build/desktop/apps/desktop/xdzip.app/Contents/MacOS/xdzip --register-shell-integration
```

Le script de signature n’accepte que les applications appartenant au projet et une sortie sous `build/` du dépôt ; il ne déploie pas Qt, ne crée pas de DMG et ne lit pas les identifiants de publication. Son reçu établit seulement l’intégrité ad hoc et la vérification imbriquée stricte, sans Developer ID, notarisation, confiance Gatekeeper ou approbation des licences de publication. L’application doit rester à son emplacement initial. Activez l’extension Finder de xdzip dans les réglages système, sous les éléments d’ouverture et extensions. Chemins et menus peuvent varier selon la version du système ; un enregistrement réussi ne prouve pas l’acceptation du menu ou de ses actions.

Avant de terminer une vérification temporaire, utilisez `--remove-shell-integration` de la même application pour révoquer les enregistrements de service et d’extension appartenant au projet. Après avoir contrôlé l’état initial, nettoyez uniquement la configuration et les enregistrements LaunchServices temporaires créés par cette opération. Ne modifiez ni les autres applications ni les associations par défaut. Si Finder a chargé l’application, désactivez puis réactivez l’extension du projet dans les réglages système après les mises à jour au lieu de redémarrer Finder. Voir les [actions du gestionnaire de fichiers](shell-actions.md) pour les limites de transmission et de retour arrière.

## Enregistrement « Ouvrir avec » des copies de développement et de vérification

LaunchServices mémorise les bundles ouverts auparavant ; plusieurs copies du même identifiant de bundle dans un arbre de compilation peuvent apparaître dans les menus « Ouvrir avec » du système ou de Codex. Pour cette raison, ne supprimez pas la base système, ne redémarrez pas Finder, ne supprimez pas les paquets de vérification et ne changez pas les choix par défaut de l’utilisateur.

Les nouveaux bundles de développement utilisent par défaut `LSHandlerRank=None` dans Info.plist généré ; seules l’application principale choisie et celle du paquet livré conservent `Alternate`. L’option CMake `XDZIP_MACOS_HANDLER_RANK` n’accepte strictement que ces deux valeurs. Les reconstructions hors ligne, la vérification du produit Qt depuis les sources et la CI produit Mac passent explicitement `None` pour empêcher qu’un futur changement de valeur par défaut ne réintroduise les copies de test comme candidates. La [définition Apple de `None`](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html) conserve le glisser-déposer de fichiers sans sélectionner le bundle comme gestionnaire d’ouverture du type. Elle ne modifie pas la sélection de fichiers dans l’application ni son ouverture explicite et ne définit aucun choix par défaut.

La CI produit Mac exécute `scripts/check-macos-registration.py` pour interroger via `NSWorkspace` natif les applications candidates pour les fichiers du nouveau bundle. Le nombre de candidats et les enregistrements énumérés par identifiant de bundle sont évalués séparément ; ces derniers ne remplacent pas les candidats « Ouvrir avec » réellement présentés à l’utilisateur. Les gestionnaires par défaut existants doivent être conservés pendant l’enregistrement temporaire. Les types sans gestionnaire préalable peuvent temporairement résoudre vers un nouveau candidat ; tous les types testés doivent retrouver leurs gestionnaires et états de candidats initiaux après désenregistrement. Les préférences `LSHandlers` de l’utilisateur courant ne sont comparées qu’au moyen d’instantanés en mémoire avant, pendant et après l’enregistrement ; leur contenu n’est pas affiché. Les autres préférences et règles système sont hors de cette comparaison.

`scripts/macos_launch_services.py` ne reconnaît que `org.xdzip.desktop`. Le déplacement DMG, la reconstruction source hors ligne, la vérification du produit Qt depuis les sources, le remplacement de QtCore et la vérification d’ouverture système enregistrent les inscriptions préexistantes dans le périmètre `build/`, puis, à la fin ou en cas d’échec, ne désenregistrent que les copies de test nouvellement ajoutées. Les applications principales existantes et autres produits restent intacts. Un échec de nettoyage fait échouer la vérification au lieu d’être silencieusement signalé comme réussi.

Le déplacement DMG et le remplacement de QtCore conservent les déclarations de documents et la vérification des bundles livrés, mais ne copient que vers de nouveaux chemins `.app` inexistants sous `build/`. Récupérez automatiquement le bundle créé après vérification ou échec, en figeant les empreintes nécessaires dans son périmètre. JSON, journaux, bundle principal avant remplacement, DMG et sources Qt sont conservés. Le nettoyage n’accepte ni applications existantes ni liens symboliques et ne supprime pas rétroactivement les anciens bundles de vérification. Les anciens bundles `Alternate` simplement désenregistrés peuvent être redécouverts et enregistrés par le système ou d’autres applications ; leur non-réapparition permanente ne peut être garantie. Si ces anciens bundles doivent être conservés, ils peuvent être placés dans des sauvegardes vérifiables et restaurables avant le traitement des copies isolées sous autorisation explicite.

Prévisualisez les restes historiques avec l’outil suivant, puis appliquez explicitement. `--keep` doit désigner une application principale existante et correctement identifiée, soit la compilation actuelle de développement, soit une installation dans Applications :

```sh
python3 scripts/cleanup-macos-open-with.py --keep build/ui-release/apps/desktop/xdzip.app
python3 scripts/cleanup-macos-open-with.py --keep build/ui-release/apps/desktop/xdzip.app --apply
```

L’outil ne désenregistre que les autres copies xdzip dans `build/` de ce dépôt et les chemins invalides portant la même identité. Il ne supprime pas les bundles, ne modifie pas les signatures et ne définit pas l’application ZIP par défaut. Les produits différents, les autres installations Applications et les chemins hors de l’arbre de compilation ne sont pas traités automatiquement. Les chemins qui se résolvent hors périmètre par des liens symboliques ne sont pas nettoyés. Revérifiez ensuite les enregistrements en ne conservant que le bundle principal de développement indiqué. Si plusieurs installations existent hors de l’arbre de compilation, énumérez-les séparément comme non traitées ; ne prétendez pas avoir supprimé les doublons globalement.

Enregistrez la progression du nettoyage, les nombres et les conclusions dans l’issue concernée, par exemple [maintenance des copies de développement #7](https://github.com/xiaodaozhi/xdzip/issues/7). Les JSON générés et résultats de sondes natives restent uniquement dans les artefacts locaux ou CI.
