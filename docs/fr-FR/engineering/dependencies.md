## Essai du SDK externe

L'hôte d'essai indépendant réutilise les versions épinglées serde 1.0.229, serde_json 1.0.154, sha2 0.10.9, getrandom 0.4.2, libc 0.2.190 et tempfile 3.27.0, sans ajouter de versions tierces ni de bibliothèques de format ou CBOR. Le crate du protocole n'utilise que std ; le CBOR borné du projet interopère avec un pair indépendant utilisant la bibliothèque standard Python selon RFC 8949. L'hôte ne lie pas Qt, n'entre pas dans le périmètre d'exécution du bureau ou de la CLI et ne modifie pas les éléments d'une version officielle.

tempfile passe du fichier de verrouillage existant à une dépendance directe de l'essai pour conserver une copie exécutable privée vérifiée, sans maintenir une implémentation générale de répertoire temporaire. La sortie sécurisée utilise toujours xdzip-io ; tempfile n'autorise pas la validation. Sa source est [Stebalien/tempfile](https://github.com/Stebalien/tempfile), sous licence MIT ou Apache-2.0. Les fonctionnalités par défaut et le périmètre réel de la cible, dont fastrand, getrandom, once_cell et rustix/windows-sys, suivent Cargo.lock et ses métadonnées et réutilisent les versions épinglées, sans télécharger de scripts de compilation ni ajouter de bibliothèques C. L'utilisation, les sources et les licences des bibliothèques de base existantes restent applicables ; une consultation historique d'avis n'est pas présentée comme une nouvelle conclusion de sécurité. Voir l'[essai du SDK](sdk-trial.md) pour les tests et critères. Windows refuse explicitement l'exécution sans implémentation AppContainer.

L'accès aux membres de paquets réutilise les versions exactes admises de cap-std/cap-fs-ext 4.0.3 et leurs fonctionnalités existantes. Chaque composant est ouvert sans suivre les liens relativement à des répertoires détenus, pour éviter les courses entre la vérification des chaînes et la réouverture via des chemins d'environnement. Les deux conservent la provenance d'E/S sécurisée, les licences MIT ou Apache-2.0, les versions transitives et le comportement natif existants ; aucune version tierce n'est ajoutée.

## Interface CLI et HTTPS

La CLI promeut clap 4.6.7 verrouillé en dépendance réelle de l'interface produit, en activant uniquement std, help, usage, error-context, suggestions et string, sans derive ni couleurs de terminal. Elle ajoute ureq 3.5.1 avec les fonctionnalités par défaut désactivées, en activant seulement native-tls-no-default et socks-proxy et en sélectionnant explicitement NativeTls et les racines de confiance système. Elle n'introduit ni décodage GZIP par défaut, cookies, auxiliaires JSON, curl externe ou dépendances réseau Qt à l'exécution. serde, serde_json, zeroize, sha2, getrandom et les liaisons de plateforme réutilisent les versions épinglées.

ureq et ureq-proto proviennent de [algesten/ureq](https://github.com/algesten/ureq), avec la licence MIT sélectionnée. Les principales entrées transitives sont native-tls 0.2.18, ureq-proto 0.7.1, http 1.5.0 et httparse 1.10.1. Les versions complètes, fonctionnalités et périmètres par cible suivent Cargo.lock et les métadonnées Cargo filtrées par hôte. Windows utilise schannel 0.1.30 ; macOS utilise security-framework 3.7.0 et les frameworks système ; Linux utilise openssl 0.10.82/openssl-sys 0.9.118 et OpenSSL 3 système. Les types der/PKI de RustCrypto servent uniquement à l'encapsulation TLS générale et n'interprètent pas les formats d'archives.

Les compilations Native TLS Linux trouvent OpenSSL système par pkg-config sans intégrer, télécharger ou compiler une copie privée. Mac et Windows utilisent TLS système. Les scripts Cargo nécessaires, l'édition de liens native, les conditions de cible et les avis connus sont vérifiés pour les versions réelles épinglées ; les réponses restent dans les artefacts locaux ou CI et les résumés vont dans l'issue CLI. Une recherche sans résultat ne garantit pas une sécurité permanente. La FFI propre à la CLI pour terminal, signaux et requêtes système reste limitée aux adaptateurs de plateforme ; les échecs refusent les opérations et les conteneurs de mots de passe conservent les exigences d'effacement.

Les avis de paquet sont collectés séparément des dépendances ordinaires de la CLI et du processus de travail ; les dépendances de compilation, développement et proc-macro sont exclues comme preuves d'attribution à l'exécution. L'attribution du bureau ajoute la racine CLI. Seul le lanceur public Windows lie statiquement le CRT du compilateur afin de démarrer avant le chargement des DLL locales versionnées. Les charges et processus réels continuent d'inclure le runtime VC++ épinglé et les licences d'origine, sans bibliothèques graphiques du SDK. Les matériaux de publication réels examinent toujours la provenance, le code machine statique ou dynamique conservé et les obligations de licence.

Lors du premier ajout d'une dépendance, consignez sa finalité, les alternatives, la version, la source, la licence, les dépendances transitives, les fonctionnalités, le comportement de compilation native, les vulnérabilités connues et la maintenance. Le nom d'un crate ne suffit pas à son admission. Ne listez pas de versions auditées fictives.

| Orientation candidate | Vérification requise |
| --- | --- |
| Implémentation ZIP Rust | Store/Deflate, ZIP64, CRC, doublons, octets bruts des noms, annulation et destination de sortie de l'hôte |
| Implémentation TAR + GZIP Rust | Index en flux, métadonnées PAX/GNU, rejet des liens et périphériques, tailles inconnues et flux endommagés |
| cxx | Propriété, cohérence du générateur, liaison statique multiplateforme du noyau, absence d'exceptions traversant les frontières |
| Modules Qt | Dépendances réelles d'exécution et transitives, déploiement remplaçable, licence et canaux de mises à jour de sécurité |
| Jeu d'icônes | Licence explicite de redistribution, épaisseur cohérente des traits, accessibilité et inventaire des ressources |

Ordre de vérification : interopérabilité minimale → entrées malveillantes ou tronquées → annulation et limites de ressources → licences/SBOM → compilation propre → enregistrement de la décision. Ne contournez pas la protection des chemins de l'hôte avec une extraction générique de bibliothèque.

Un espace de travail Rust applicatif conserve Cargo.lock dans Git. Les nouvelles bibliothèques natives et les scripts de compilation qui téléchargent depuis le réseau exigent une revue spécifique ; désactivez les fonctionnalités inutilisées. Si une dépendance est abandonnée ou qu'une vulnérabilité n'a pas de correctif, décidez de mettre à jour, remplacer ou désactiver la capacité selon son accessibilité réelle et consignez la raison.

## Métadonnées de mise à jour et vérification de la signature de l'éditeur

`xdzip-update` est un noyau indépendant de Qt pour les manifestes, canaux et la vérification de signatures, appelé par le produit via une frontière cxx distincte. Les outils de publication et assistants d'installation suivent les mêmes règles. Utilisez `VerifyingKey::verify_strict` sûr de `ed25519-dalek = 2.2.0`, rejetez les clés publiques faibles et vérifiez les octets bruts exacts. N'implémentez pas l'arithmétique de signature et ne considérez pas TLS ou SHA-256 comme une signature de l'éditeur. Les fonctionnalités upstream fast, std et zeroize sont activées par défaut ; batch, hazmat, legacy_compatibility, rand_core et PKCS#8 sont désactivées. Les outils de publication importent uniquement une graine de 32 octets configurée par le propriétaire et ne génèrent pas de clés privées de production.

Les autres dépendances transitives suivent Cargo.lock et l'arbre réel de fonctionnalités, dont digest, block-buffer, crypto-common, generic-array, typenum, cpufeatures et les macros derive. Le script de curve25519-dalek détecte uniquement les capacités du compilateur local ; à l'exécution il peut sélectionner des implémentations upstream propres au processeur. Il ne télécharge pas de source externe et n'ajoute ni bibliothèque cryptographique C/C++ ni dépendance OpenSSL à l'exécution. La collecte existante d'avis et de fournisseurs inclut ces paquets via les métadonnées Cargo ; l'attribution et les licences du paquet réel restent soumises à la revue des matériaux de publication.

Les API cryptographiques système diviseraient les règles de vérification entre trois plateformes, tandis qu'une CLI OpenSSL externe augmenterait les dépendances et frontières d'arguments ; un seul noyau Rust est donc utilisé. L'ancienne API Keypair de l'avis historique [RUSTSEC-2022-0093](https://rustsec.org/advisories/RUSTSEC-2022-0093.html) n'est pas utilisée. La version corrigée de curve25519-dalek exigée par [RUSTSEC-2024-0344](https://rustsec.org/advisories/RUSTSEC-2024-0344.html) est 4.1.3, respectée par la version épinglée. Ces contrôles ne prouvent pas l'absence de vulnérabilités dans toutes les dépendances ; les mises à jour continuent d'examiner la maintenance et les avis.

La régression vérifie les changements d'octets exacts, les signatures invalides, les clés publiques inconnues, dupliquées ou faibles, un ensemble de confiance de production vide, le repli de canal, la liaison version/compilation, l'intégralité des six paquets et les flux signés. Les clés de test temporaires n'existent que dans le code de test et des artefacts isolés, jamais dans les ressources de confiance du produit. L'installation native et les résultats multiplateformes sont enregistrés séparément ; les tests du noyau sur une plateforme ne remplacent pas l'acceptation d'installation.

## Identité de source sous Windows

M2 utilise directement le wrapper sûr `file::information(&File)` de la version exacte `winapi-util = 0.1.11` à l'exécution sous Windows pour comparer les numéros de série de volume et les indices de fichier. La longueur et les dates de modification ou de création ne détectent pas de façon fiable un remplacement NTFS sous le même nom. L'API d'indice de fichier correspondante de la bibliothèque standard n'est pas encore stable et écrire du Win32 unsafe élargirait la revue. La bibliothèque déjà verrouillée est réutilisée sans ajouter de version de paquet.

La source est crates.io/[BurntSushi/winapi-util](https://github.com/BurntSushi/winapi-util), avec MIT choisi dans la double licence upstream MIT ou Unlicense. Les dépendances transitives Windows sont windows-sys 0.61.2 et windows-link 0.2.1 épinglés, tous deux MIT ou Apache-2.0. Seuls les modules Win32 déclarés upstream sont activés, les fonctionnalités par défaut sont désactivées et il n'y a ni script de compilation, compilation native externe ou téléchargement réseau. Les cibles non Windows ne compilent pas cette dépendance d'exécution. Le wrapper sûr upstream emprunte un handle File valide ; l'échec d'un appel système invalide l'ancienne source. Le handle ne traverse pas la FFI et les contrôles d'identité n'autorisent pas une écriture sécurisée.

La provenance des versions, les fonctionnalités et le comportement de compilation native ont été vérifiés ; la vérification de types pour Windows GNU a réussi. La régression Windows native doit couvrir le remplacement de même nom et taille conservant la date de modification. Upstream est un petit wrapper Win32 sûr ; les mises à jour sont contraintes par le fichier de verrouillage et les régressions natives. Une recherche OSV de versions exactes le 2026-10-13 n'a renvoyé aucun avis connu pour ces trois paquets. Les réponses historiques restent dans les artefacts d'exécution d'origine ; les nouvelles recherches enregistrent les réponses réelles selon la [vérification](../../../developers/qa/README.md). Cela ne prouve pas l'absence de vulnérabilités. Les paquets de développement continuent de collecter toutes les licences upstream.

## Moteurs Rust de formats et pont partagé du processus de travail

`xdzip-codec-7z` utilise l'API et le domaine du projet, des algorithmes de compression partagés sans dépendance de production tierce et des primitives cryptographiques générales. AES 0.9.3 active zeroize ; getrandom 0.4.2 et zeroize 1.9.1 réutilisent les versions ZIP. Le SHA-256 effaçable est extrait dans `xdzip-crypto`, indépendant des formats, qui gère l'état incrémental propre sur la primitive compress admise de sha2 0.10.9, sans dupliquer des wrappers par format. Le crate partagé implémente aussi HMAC-SHA256 et BLAKE2s/BLAKE2sp à partir de spécifications mathématiques publiques ; voir son [README](../../../crates/xdzip-crypto/README.md) pour les sources et limites. Il ne confère aucune autorité sur les archives ou leur publication et ne met pas à jour les versions cryptographiques tierces. Attributs de format, composition CBC, KDF, création et réécriture sont des implémentations indépendantes, non un traitement d'archives fourni par ces bibliothèques de base. Voir la [base de 7z](sevenzip-format-sources.md) pour les sources, rôles d'analyse et distinctions de licence.

La logique de format de `xdzip-codec-optical` utilise uniquement la bibliothèque standard et l'API et le domaine de codecs du projet, sans bibliothèques ISO/UDF ni d'archives générales. Voir le [contrat d'implémentation indépendante](independent-rust-codecs.md#iso与udf只读规格) pour spécifications, portée et erreurs. `xdzip-codec-bridge` réutilise les versions et la génération verrouillées de cxx/cxx-build, sans nouvelles versions externes, scripts qui téléchargent ou bibliothèques d'algorithmes de format. Le remplacer par un routage en processus ferait perdre la gestion de processus des tâches optiques existante ; le processus de travail et le protocole de flux contrôlé sont donc conservés.

`xdzip-codec-cab` dépend seulement de l'API, du domaine et de `xdzip-compression` du projet, sans dépendances de production tierces. MSZIP réutilise Deflate de ZIP/GZIP ; LZX et Quantum sont des modules indépendants sans autre bibliothèque Deflate ou d'archives générales. Les moteurs 7z, CAB et optique partagent `xdzip-codec-bridge` et les flux autorisés par l'hôte. La création n'ajoute que des callbacks d'entrée contrôlée et de préparation aléatoire sans dupliquer les frontières générales. Le produit utilise Rust ; Cab officiel et LZX/Quantum propres à CAB n'entrent pas dans les compilations. Voir le [contrat interne](independent-rust-codecs.md#cab只读规格) pour ressources et formats et les [sources CAB](cab-format-sources.md) pour portée de l'analyse de référence et licences.

`xdzip-codec-rar` réutilise la même API de codec, les algorithmes de compression partagés et les primitives cryptographiques sans introduire RAR ni d'autres bibliothèques d'archives. Le modèle statistique PPMd H est partagé par 7z et RAR ; chaque format définit son propre range, reset et termination. Les combinaisons spéciales de compatibilité avec les anciens mots de passe restent dans le module RAR. Le calendrier système et les encodages OEM/ANSI/locaux utilisent de légers callbacks du processus de travail ; Rust gère les champs de format, la troncature des mots de passe et la validation. Qt n'entre pas dans la logique de format.

La politique de dépendances de production vérifie les périmètres ordinaires et de compilation des crates de format et de pont. Les conteneurs, algorithmes et utilitaires généraux officiels 7-Zip et UnRAR ont quitté les manifestes CMake du produit ; la liste de préparation de sources produit est vide et aucun repli n'existe en cas d'échec. Les obligations de licence des livraisons historiques demeurent. pycdlib indépendant, Microsoft IMAPI, fixtures mkudffs/udfclient, processus de référence officiels et vecteurs de spécification servent uniquement aux tests ; leurs sources et licences sont gérées séparément et n'entrent pas dans les dépendances d'exécution. Les petites entrées et générateurs propres et fixés sont versionnés dans les répertoires de test ; images développées et preuves d'exécution restent dans build/.

## ZIP interne et primitives cryptographiques générales

Conteneurs ZIP, création en flux, réécriture ordinaire et encapsulation AES utilisent une [implémentation Rust indépendante](independent-rust-codecs.md) ; Deflate/CRC-32 réutilisent `xdzip-compression`. `rawzip = 0.5.2`, `zip = 9.0.5` et `flate2 = 1.1.10` sont uniquement des références de développement et de test et n'entrent pas dans les dépendances de production ou de compilation ZIP. Elles n'appellent pas d'extraction générique et n'autorisent pas de chemins arbitraires. Les livraisons historiques qui les utilisent conservent leurs obligations de licence.

Les primitives cryptographiques réutilisent les versions exactes de dépendances transitives existantes promues directes : RustCrypto `aes = 0.9.3`, `hmac = 0.13.0`, `sha1 = 0.11.0`, `pbkdf2 = 0.13.0`, ainsi que `getrandom = 0.4.2` et `constant_time_eq = 0.6.1`. PBKDF2 n'active que hmac. SHA1 désactive alloc/oid par défaut et n'active que zeroize ; AES/HMAC activent aussi zeroize. Aucun ajout de bibliothèque de format, bibliothèque native de compression ou téléchargement à l'exécution. CTR, encapsulation à sel aléatoire, découpage des résultats dérivés, valeurs de vérification du mot de passe et EOF authentifié sont implémentés par le projet ; les primitives générales ne doivent pas réintroduire un analyseur ZIP.

Ces paquets et les dépendances transitives cipher/digest sont verrouillés dans Cargo.lock et proviennent de crates.io et de leurs upstreams. AES/HMAC/SHA1/PBKDF2/zeroize/getrandom utilisent MIT ou Apache-2.0 ; constant_time_eq utilise CC0-1.0 ou MIT-0 ou Apache-2.0, selon les textes réels des paquets épinglés. Les paramètres SHA-1/PBKDF2 proviennent de WinZip AES et ne sont pas utilisés pour un schéma distinct de stockage des mots de passe utilisateurs. Les scripts de compilation ne font que configurer la plateforme, sans téléchargement réseau ni compilation de décodeur C.

`zeroize` est uniformément épinglé à 1.9.1 pour satisfaire le nettoyage des clés d'AES 0.9.3. Les conteneurs de mots de passe de l'hôte, de l'adaptateur natif, des mises à jour et des sondes conservent une version plutôt que deux du même major. Le Debug des secrets reste masqué ; les tampons dérivés et clés développées utilisent des durées de vie effaçables fournies par les bibliothèques, sans prétendre effacer toutes les copies historiques en mémoire. L'admission inclut le fichier de verrouillage, les licences, l'arbre réel de fonctionnalités, les tests d'échec et l'interopérabilité 7-Zip indépendante. Les réponses originales des recherches de vulnérabilités restent dans les artefacts ; une recherche réussie sans avis ne garantit pas l'absence de vulnérabilités.

## WP-11 TAR/GZIP

Épinglez exactement [tar 0.4.46](https://docs.rs/tar/0.4.46/tar/) (crates.io, [source upstream](https://github.com/alexcrichton/tar-rs), MIT ou Apache-2.0), avec la fonctionnalité xattr par défaut désactivée. Il sert uniquement de référence indépendante de lecture et écriture pour développement et tests. Les en-têtes TAR, PAX, création et réécriture du produit utilisent une [couche indépendante de registres Rust](independent-rust-codecs.md), non un analyseur ou Builder TAR tiers, une extraction générique ou la restauration des propriétaires et permissions. Les périmètres de production interdisent le retour de tar et filetime ; les licences de test et livraisons historiques demeurent. L'encodage écrit explicitement les chemins PAX UTF-8 et les nombres hors plage pour l'interopérabilité des noms entre plateformes.

GZIP utilise l'implémentation indépendante `xdzip-compression` sans dépendances de production tierces, dont Deflate RFC 1951, cadrage RFC 1952 et CRC-32. L'entrée compressée et la sortie décodée sont soumises à l'annulation et aux budgets d'octets de l'hôte. Un décodage complet vérifie CRC et ISIZE de chaque membre. `flate2` 1.1.10 est une référence de développement et test. ZIP et GZIP utilisent le même algorithme Deflate interne. Le routage d'exécution distingue [GZIP autonome](single-file-streams.md), qui expose un fichier logique, de [TAR.GZ](tar-gzip.md), qui expose une arborescence TAR.

Les dépendances transitives de test de tar incluent filetime 0.2.29 (MIT ou Apache-2.0), réutilisant cfg-if et libc ; filetime n'entre pas dans le périmètre produit du codec. Il n'y a ni nouveau script de compilation qui télécharge, requête réseau à l'exécution ou moteur de format en processus externe. Le collect-notices.py existant collecte les licences du fichier de verrouillage ; un paquet de test présent dans celui-ci ne signifie pas que le produit le lie. tar système et tarfile Python servent uniquement aux tests et n'entrent pas dans les dépendances d'exécution.

Une recherche OSV de versions exactes le 2026-10-15 pour tar 0.4.46, filetime 0.2.29 et flate2 1.1.10 n'a renvoyé aucun avis. Les réponses originales restent uniquement dans build/review/wp11. Cela ne garantit pas l'absence de vulnérabilités. L'interopérabilité bidirectionnelle, les entrées incorrectes, quotas, annulation et vérification sur trois plateformes doivent être réellement exécutés ; les preuves sont liées depuis le [contrat WP-11](tar-gzip.md).

## Dérivé QtNetwork corrigé pour la sécurité

La bibliothèque dynamique Network de Qt 6.8.2 du bureau utilise `6.8.2-xdzip-network.1`, appliquant cinq correctifs officiels non modifiés à une archive QtBase épinglée pour CVE-2026-116337 et CVE-2026-105946. Le périmètre couvre les limites de réception de ligne de statut et d'en-têtes HTTP/CONNECT et les frontières d'analyse de l'authentification ; QtCore, les autres modules et les plugins TLS ne sont pas remplacés. Les options existantes, symboles exportés et compatibilité d'importation avec QtCore du SDK d'origine sont conservés. Voir les [notes de maintenance](../../../patches/qt/README.md) pour sources, ordre, hashes, licence, remplacement et vérification sur entrées réelles. La production conserve la liaison dynamique LGPL-3.0. Les tests upstream exclusivement GPL ne sont pas distribués ; OpenSSL 3.5.9 ne génère que les déclarations de compilation et aucune nouvelle bibliothèque cryptographique n'est compilée ou distribuée. Provenance, avis et conditions de reliaison du paquet réel exigent toujours une revue séparée.

Linux ajoute aussi une unité originale épinglée par digest pour préserver l'ABI, instanciant explicitement des constantes existantes de types intégrés du SDK afin de maintenir les exportations d'origine sans ajouter de comportement réseau. Source et avis Apache-2.0 accompagnent les matériaux. Les cinq correctifs officiels ne sont pas modifiés et les bibliothèques produit des autres plateformes ne reçoivent pas cette unité.

## Fournisseur de mise à jour macOS

L'intégration des mises à jour Mac épingle Sparkle 2.10.0 et l'extension proxy `xdzip-proxy.2`. Les hashes du SDK, de l'archive source, du correctif et du texte complet de licence figurent dans la [configuration des dépendances](../../../scripts/sparkle-dependency.json). Elle ne gère que les mises à jour de l'application, pas le décodage d'archives. Les textes de licence originaux du SDK officiel incluent MIT, BSD-2-Clause et Zlib et sont conservés dans les avis Mac. Le collecteur local de code correspondant conserve les archives source épinglées et SDK originales pour la préparation hors ligne et la reliaison du framework dynamique ; selon le protocole de publication, cette archive n'est pas proposée en téléchargement Release ou Actions.

Les 67 unités Objective-C et 10 unités C Ed25519 upstream du framework principal sont compilées avec Clang natif Apple Silicon depuis la source épinglée et un [correctif restreint](../../../patches/sparkle/2.10.0-download-proxy.patch), en conservant les fonctionnalités de compilation et l'IPC d'installation upstream. Ressources, assistants d'installation et outils de signature restent issus du SDK officiel ; ils ne sont pas présentés comme reconstruits depuis les sources. Le framework dérivé enregistre une variante distincte, les hashes source/correctif/constructeur et les reçus de compilation par fichier. L'attribution de déploiement et le SBOM distinguent cette provenance des octets du SDK officiel. Voir les [notes de maintenance du correctif](../../../patches/sparkle/README.md).

L'extension utilise Network.framework système pour les proxies personnalisés sans repli vers une connexion directe et les options de proxy de session CFNetwork pour les connexions explicitement directes. Elle n'ajoute aucune bibliothèque d'exécution redistribuable et ne modifie pas les paramètres proxy du système.

Le job Mac du workflow Qt à la demande lie le SDK en externe et ne déploie pas le framework. Le paquet dédié l'intègre dans une copie temporaire, retire les services XPC non activés pour l'application hors bac à sable et conserve les assistants d'installation nécessaires. Après réduction et déplacement, effectuez la signature ad-hoc d'intégrité dans l'ordre assistants, framework, application. Les assistants conservent Hardened Runtime et les droits spécifiques requis ; n'appliquez pas une commande générique de nouvelle signature de bibliothèque native. Attribution de déploiement, SBOM, licences et matériaux source sont enregistrés avec la version.

## Outils expérimentaux d'installation

Les compilations Windows introduisent Inno Setup 6.7.3 uniquement pour compiler des installateurs par utilisateur du répertoire d'exécution du projet. Sa source est la [version officielle jrsoftware/issrc](https://github.com/jrsoftware/issrc/releases/tag/is-6_7_3) ; le commit source immuable et les SHA-256 des binaires officiels, ressources de langue chinoise et texte de licence sont épinglés dans [installer-toolchain.json](../../../scripts/installer-toolchain.json). Utilisez le mode par utilisateur et des journaux de désinstallation cumulatifs. NSIS et WiX/MSI sont des alternatives ; ce travail ne maintient pas de base de nettoyage personnalisée ou de règles de déploiement d'entreprise.

Utilisez l'Inno Setup License de cette source épinglée, en conservant droits d'auteur, provenance d'origine et interface du moteur sans modifier le compilateur. Livrez le texte dans les avis Windows. Le code transitif utilise Pascal Script, la compression et les composants de plateforme du compilateur et du stub officiels ; le moteur n'est pas reconstruit ici. Vérifiez les sources et licences des composants incorporés par rapport à la livraison réelle. Le compilateur est installé dans build/ de CI et n'entre pas dans le répertoire d'exécution Qt. Le stub entre dans l'installateur final ; les reçus enregistrent sa version et le hash de l'installateur. Le SBOM du répertoire d'exécution n'est pas présenté comme un SBOM complet du stub.

N'activez que la copie standard de fichiers, le registre par utilisateur, les raccourcis du projet et la protection par mutex. Désactivez la fermeture et le redémarrage automatiques de l'application. Il n'y a ni téléchargement réseau pendant l'installation, plugin natif personnalisé ou nouveau script Rust de compilation. Le .deb Linux utilise dpkg-deb d'Ubuntu et les outils de maintenance système sans ajouter de codecs à l'application. Les répertoires de travail du téléchargeur Qt sont fixés sous build/ pour éviter que aqtinstall.log contamine l'identité de la source.

L'API publique d'avis de sécurité du dépôt officiel a renvoyé une liste vide le 2026-10-16 ; la réponse originale reste dans build/review/installer-tool-advisories.json. Cela ne prouve pas l'absence de vulnérabilités et ne constitue pas une recherche NVD complète. L'[historique officiel des versions](https://jrsoftware.org/files/is6-whatsnew.htm) aide à examiner la maintenance de sécurité ultérieure ; épingler 6.7.3 ne signifie pas qu'elle soit la dernière version ou prise en charge à long terme. La vérification de hash ne remplace ni l'identité de signature ni l'admission complète de licence et sécurité du moteur. Compilation, installation, ouverture système, mise à jour, retour arrière, désinstallation et échecs réels sont enregistrés dans le [contrat d'installation](installers-associations.md) et la CI réelle.

## Détection et décodage des anciens noms de fichiers

Épinglez exactement [chardetng 1.0.0](https://docs.rs/chardetng/1.0.0/chardetng/) et [encoding_rs 0.8.42](https://docs.rs/encoding_rs/0.8.42/encoding_rs/), tous deux provenant de crates.io et du dépôt upstream hsivonen. Le premier utilise MIT ou Apache-2.0 ; le code du second utilise MIT ou Apache-2.0 et ses données de correspondance WHATWG utilisent aussi BSD-3-Clause. Conservez LICENSE-WHATWG et COPYRIGHT. Le collecteur d'avis inclut COPYRIGHT, pas seulement les textes complets de licence.

Désactivez les fonctionnalités par défaut des deux. encoding_rs n'active directement que alloc ; désactivez le multithreading/rayon du détecteur. Les nouveaux paquets transitifs épinglés sont core_detect 1.0.0, multiversion_no_op 1.0.0, scopeguard 1.2.0 et simdutf8 0.1.5, tous MIT ou Apache-2.0. cfg-if 1.0.5, memchr 2.8.3 et la macro de compilation rustversion 1.0.23 réutilisent les versions épinglées. core_detect détecte les capacités du processeur local, simdutf8 est la validation SIMD UTF-8 upstream et multiversion_no_op une macro sans effet à la compilation. Aucune nouvelle bibliothèque native C/C++, aucun script de compilation réseau ni téléchargement à l'exécution n'est ajouté. Le script encoding_rs ne sélectionne que la configuration locale selon la version du compilateur. L'unsafe propre au processeur reste dans le code upstream maintenu ; l'hôte n'ajoute pas d'unsafe/FFI.

Un détecteur Rust unique évite des règles divergentes entre Qt, iconv système et pages de codes Windows. Maintenir un modèle statistique CJK ou appeler des extracteurs externes élargirait les frontières d'implémentation et de déploiement. Le dépôt upstream chardetng est indiqué comme maintenu passivement ; les changements de version ou de modèle exigent de relancer des échantillons indépendants de noms. ZIP CP437 est une correspondance fixe sur un octet fondée sur la [table Unicode CP437](https://www.unicode.org/Public/MAPPINGS/VENDORS/MICSFT/PC/CP437.TXT), sans API de plateforme ; la bibliothèque standard Python génère séparément les octets bruts de test. La détection est heuristique et ne prouve ni l'autorisation d'un chemin ni la vérification du contenu.

Une recherche OSV de versions exactes pour six paquets nouvellement épinglés le 2026-10-24 n'a renvoyé aucun avis ; les réponses brutes restent uniquement dans les artefacts locaux. C'est un contrôle ciblé, pas une garantie d'absence de vulnérabilités. L'admission vérifie aussi les fonctionnalités Cargo réelles, les sources et les textes complets de licence. Voir le [contrat d'encodage des noms](filename-encoding.md) pour portée des régressions, ressources et règles d'échec. Les compilations sur trois plateformes, l'interopérabilité des contenus et les résultats réels sont suivis dans l'issue et la CI correspondantes.

## Modules Qt de prévisualisation d'images

Conservez Qt 6.8.2 épinglé et ajoutez qtimageformats officiel ; le commit source et les digests de l'archive figurent dans la [configuration des composants](../../../scripts/corresponding-sources.json). Utilisez qwebp, qtiff, qtga et qicns. macOS utilise aussi qmacheif avec ImageIO système. N'introduisez ni libheif/libavif ni moteurs d'images supplémentaires. GIF, BMP, ICO/CUR et JPEG réutilisent QtGui ; SVG réutilise QtSvg existant sans chargement illimité de ressources.

QtImageFormats inclut libwebp 1.5.0. XDZip recompile QtGui avec libpng 1.6.59 et le greffon TIFF avec libtiff 4.7.2. Les [sources épinglées](../../../scripts/qt-image-security.json) et le relevé d’attribution du SDK identifient les composants livrés. Les textes originaux COPYING/COPYRIGHT sont collectés par commit épinglé et SHA-256. Un marqueur générique NOASSERTION n'est pas en soi un défaut de licence confirmé. Les modules Qt dynamiques conservent la voie de licence existante, avec les avis tiers des composants réellement livrés. Les recherches de dépendances par version exacte et les résultats de décodage, entrées incorrectes et déploiement sur trois plateformes restent dans les issues et artefacts ; une recherche sans avis ne prétend pas à l'absence de vulnérabilités.

Les runtimes d'images utilisent un assistant fixé. Voir le [contrat de prévisualisation](content-preview.md) pour les limites d'image d'origine, pixels, processus de travail, entrée/sortie et échec. La préparation par défaut complète les outils existants, vérifie les plugins avant compilation et vérifie l'assistant réel lors du déploiement. Aucun second SDK Qt n'est ajouté.

## Adaptateurs de menu du gestionnaire de fichiers

L'extension Windows dépend uniquement des API système du SDK Windows et du runtime MSVC statique. L'assistant de service macOS dépend uniquement d'AppKit système et de la bibliothèque standard C++. Aucun ne charge Qt ou de bibliothèques de format dans le processus hôte du gestionnaire de fichiers. Ubuntu 24.04 utilise `libnautilus-extension4` et GLib/GObject/GIO de la distribution, avec `libnautilus-extension-dev` comme dépendance de compilation ; l'application Fichiers n'est pas un composant du produit.

L'[en-tête MenuProvider de Nautilus 46.0](https://github.com/GNOME/nautilus/blob/46.0/libnautilus-extension/nautilus-menu-provider.h) déclare GNU Library General Public License 2 ou ultérieure. La nouvelle extension utilise uniquement cette interface publique et lie dynamiquement la bibliothèque système, en choisissant les termes ultérieurs LGPL-3.0. Les audits de déploiement Linux enregistrent les versions et sources réelles des paquets système ; aucune copie séparée de Nautilus/GLib n'est incluse. Le code adaptateur du projet, l'utilisation de l'interface et l'application Nautilus complète ont des licences distinctes. Les candidats officiels exigent toujours l'examen des matériaux d'exécution réels ; compiler l'interface ne vaut pas approbation de licence de publication.
