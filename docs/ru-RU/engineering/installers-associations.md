# Установщики и ассоциации файлов

[English](../../engineering/installers-associations.md) | [简体中文](../../zh-CN/engineering/installers-associations.md) | [繁體中文](../../zh-TW/engineering/installers-associations.md) | [日本語](../../ja-JP/engineering/installers-associations.md) | [한국어](../../ko-KR/engineering/installers-associations.md) | [Français](../../fr-FR/engineering/installers-associations.md) | [Deutsch](../../de-DE/engineering/installers-associations.md) | [Español](../../es-ES/engineering/installers-associations.md) | [Português (Brasil)](../../pt-BR/engineering/installers-associations.md) | Русский

В Windows 11 x64 найдите **XDZip** в Microsoft Store, чтобы установить или обновить версию Store. Windows EXE или портативный ZIP, пакеты macOS и Linux доступны в [последнем выпуске GitHub](https://github.com/xiaodaozhi/xdzip/releases/latest). Два канала публикуются независимо. Проверяйте страницу или примечания устанавливаемой версии.

Windows MSIX объявляет те же расширения кандидатами «Открыть с помощью» в манифесте пакета, не забирая выбор пользователя по умолчанию. Страница ассоциаций перечисляет все подходящие типы с отключёнными переключателями. Текущие значения по умолчанию показаны в настройках Windows. «Открыть настройки приложений по умолчанию» переходит к текущему пакету через его `registeredAUMID`. При ошибке запроса идентичности открывается общий выбор приложений по умолчанию. Пакет не читает регистрации обычной установленной версии как состояние пакета и не записывает значения UserChoice. Фактическая активация файлов, значки, сосуществование и удаление требуют приёмки на целевой системе. См. [сборки MSIX](../../engineering/developer-build.md#windows-msix-实验构建).

Изображения по форматам и соответствия платформам описаны в [спецификации значков ассоциаций](../visual/file-association-icons.md). Linux сохраняет системные значки MIME. Установка не меняет значения по умолчанию или существующую область регистрации.

Ассоциации MSIX ссылаются на ресурсы PNG по форматам, извлечённые из тех же канонических кадров ICO, что использует обычный установщик Windows. ZIP, 7z, RAR и другие сопоставленные форматы сохраняют изображения документов, профили размеров и прозрачные поля. Значок приложения имеет отдельные ресурсы целевых размеров без подложки. Оба набора индексируются в `resources.pri` пакета; изменение изображения страницы Store не заменяет установленные значки. Кэшем значков и выбором обработчика по умолчанию управляет Windows, а установка никогда не меняет этот выбор автоматически.

Настольные пакеты начиная с `v0.2.0` и текущие сборки из исходников размещают CLI в отдельном каталоге `cli/`, а в macOS — `Contents/Helpers/cli/`, сохраняя существующие точки входа GUI и ассоциаций. Ресурсы прежних выпусков не получают эту функцию задним числом. Установщик Windows предлагает необязательный PATH для текущего пользователя и обнаруживает конфликты одноимённых команд; удаление отменяет регистрацию только своего каталога установки. Mac/Linux явно запускают `setup` приватной CLI. Автономные пакеты CLI также используют `setup` для установки пользовательских каталогов версий и стабильного средства запуска без изменения конфигурации оболочки. `setup --remove` отменяет регистрацию, сохраняя каталоги версий для проверки. См. [контракт установки CLI](command-line.md#xdzip-build-and-command-installation).

Приведённые ниже команды упаковки создают экспериментальные артефакты разработки. Официальные пакеты GitHub следуют [протоколу выпуска](release-protocol.md), а пакеты Store используют [процесс MSIX](../../engineering/developer-build.md#microsoft-store-msix). Прямые загрузки macOS используют ad-hoc-подпись целостности без Developer ID или нотариального подтверждения. Поддерживаемые системы описаны в [политике поддержки](support-policy.md).

Текущие сборки из исходников используют `xiaodaozhi` как издателя установщика Windows, сопровождающего пакета Linux и поставщика политики обновления. Эти метаданные не заменяют подпись сертификатом издателя; существующие выпуски сохраняют первоначальные метаданные.

Для ручного обновления macOS предпочтителен соответствующий DMG выпуска. При использовании app.zip сначала извлеките xdzip.app и переместите его из «Загрузок», завершите работающую старую версию, затем замените копию в Applications. Загрузка не является установкой; не прошедший нотариальное подтверждение пакет может вызвать предупреждения системы. Условия ручного варианта описаны в [контракте обновления](software-update.md).

Контекстные меню, независимый хост операций и жизненный цикл собственных регистраций описаны в [контракте действий файлового менеджера](shell-actions.md). Контекстные действия не открывают основное окно просмотра и по умолчанию не открывают целевую папку после завершения.

## Общая точка входа сборки

Подготовка среды и порядок описаны в [руководстве разработчика по сборке](../../engineering/developer-build.md). После чистой сборки и тестов того же коммита подготовьте фиксированные материалы командой `python3 scripts/desktop.py prepare --packaging`, затем выполните package и verify. Не используйте полный скрипт CI напрямую для обычной разработки.

Windows/Linux `package --kind runtime|installer|all` используют общую цепочку развёртывания и аудита, по умолчанию `all`. runtime сначала создаёт развёрнутый каталог; installer собирается из проверенной среды выполнения в том же output-dir, а Linux также создаёт tar.gz. macOS поддерживает только локальный DMG разработки `all`. Артефакты и квитанции находятся в заданном output-dir, по умолчанию build/package. Подготовка может скачать фиксированные инструменты и материалы упаковки, но не устанавливает xdzip или системные компиляторы и SDK автоматически. Windows подготавливает CRT/Inno Setup, Linux требует заранее установленные patchelf и инструменты Debian, а Mac использует системные инструменты развёртывания и ad-hoc-целостности.

Обычная `verify` проверяет существующие среды выполнения и пакеты. Windows очищает пути поиска SDK в изолированной копии, Linux использует изолированный контейнер среды выполнения, а Mac проверяет перемещение DMG и Cocoa/Metal. По умолчанию она не выполняет жизненные циклы установки, обновления/отката или ассоциаций и не записывает пользовательские значения по умолчанию. Механизмы установки и проверки одноразовой CI ниже остаются отдельными этапами; успех среды выполнения не заменяет их.

## Windows

Установщик показывает оригинальное соглашение Microsoft VC++ runtime, включённое в пакет. Страница лицензии указывает соответствующие компоненты и требует принятия, затем показывает Windows-runtime-NOTICE.txt на китайском и английском. Портативные пакеты содержат тот же исходный текст и объяснение. Оригинальный код проекта остаётся под Apache-2.0; исходные лицензии и права замены Qt и других компонентов не меняются. До компиляции проверьте хеши и полные описания; приложенные материалы сохраняют тот же текст. См. [лицензирование Windows](windows-licensing.md).

Портативные пакеты и установщики используют один развёрнутый каталог. [deploy_windows.py](../../../scripts/deploy_windows.py) вызывает windeployqt и затем по фиксированной политике Qt Quick Basic удаляет FluentWinUI3, Fusion, Imagine, Material, Universal, Windows, NativeStyle/Effects, используемые только стилями, qmltooling и .qmltypes. Basic, Controls impl, Templates, QML среды выполнения и qmldir остаются; Qt Widgets qmodernwindowsstyle по-прежнему обслуживает нативные элементы управления. Новые каталоги развёртывания не содержат DXC, DXIL или D3DCompiler; при появлении этих имён где-либо развёртывание завершается ошибкой. `opengl32sw.dll` не включается в новые развёртывания. Существующая копия в корне удаляется в контролируемой области подготовки; одноимённые остатки в других местах вызывают ошибку развёртывания. Добавление нового стиля или функций Effects требует изменения политики и повторной проверки.

Qt Quick по умолчанию использует Direct3D 11 в Windows. При недостаточных возможностях оборудования или драйверов Qt может перейти на Direct3D WARP; это отличается от программного OpenGL. Новые пакеты не обещают программный резерв Mesa через `QT_OPENGL=software` или backend OpenGL. Исторические пакеты и их лицензионные материалы не меняются. [Документация Qt по графике Windows](https://doc.qt.io/qt-6.8/windows-graphics.html) описывает устройства по умолчанию и явно запрошенные программные устройства.

VC++ развёртывается рядом с приложением из официальной Microsoft x64 14.44.35211 runtime по [фиксированным источникам и хешам](../../../scripts/windows-runtime.json). [Скрипт подготовки](../../../scripts/prepare-windows-runtime.py) извлекает данные фиксированными инструментами WiX и проверяет каждую DLL и текст лицензии без запуска установщиков EXE/MSI и копирования из System32. Поставляются необходимые MSVCP/VCRUNTIME DLL, лицензии и сведения о происхождении; инструменты, CAB, MSI и не запущенный установщик vc_redist не входят в продукт. Windows 10/11 предоставляет UCRT. Локальные для приложения runtime необходимо обслуживать с обновлениями продукта; нельзя рассчитывать на их замену системными обновлениями runtime. См. [методы развёртывания Microsoft](https://learn.microsoft.com/en-us/cpp/windows/choosing-a-deployment-method).

[Регрессия развёртывания](../../../scripts/test-windows-deployment.py) проверяет границы сокращения и отсутствия runtime. [Фактическая проверка runtime](../../../scripts/verify_windows_runtime.py) отклоняет DLL программного OpenGL, добавляет тестовые DLL в изолированную копию, очищает пути поиска SDK и проверяет системные переводы, перезапуск настроек, нативную строку заголовка и двуязычный запуск. После очистки переопределений рендеринга она проверяет стандартную инициализацию графа сцены D3D11 и явно запрашивает WARP, проверяя фактически выбранное программное устройство Microsoft. Явные запросы не доказывают автоматический переход при сбое и не заменяют ручную визуальную приёмку. Тестовые файлы не попадают в каталог продукта; это не заменяет приёмку установки, обновления и удаления на чистой Windows.

build-windows-installer.py принимает только аудит deployed чистой сборки и повторно проверяет SHA-256 каждого файла. [Конфигурация инструментов](../../../scripts/installer-toolchain.json) указывает фиксированный Inno Setup 6.7.3, хеш официального установщика, коммит исходников, ресурсы упрощённого и традиционного китайского и текст лицензии. Компилятор не входит в продукт; уведомления включают текст лицензии. Мастер поддерживает десять языков общего реестра.

Установщик использует фиксированный AppId и PrivilegesRequired=lowest и по умолчанию устанавливает программу в LocalAppData/Programs/xdzip текущего пользователя без прав администратора. Основной исполняемый файл xdzip.exe находится в корне установки рядом с библиотеками Qt; плагины, QML, переводы и уведомления сохраняют необходимые подкаталоги. Ярлыки, ассоциации и значки удаления указывают на корень без иерархии продукта versions/хеш коммита. Хеши коммита и двоичных файлов сохраняются в квитанциях сборки и установщика, а не в путях установки. [Накопительный журнал удаления](https://jrsoftware.org/ishelp/topic_appendnotes.htm) Inno Setup записывает файлы каждой установки, не удаляя дополнительные файлы рекурсивно. Настройки и последние элементы остаются в существующих каталогах пользователя и установщиком не удаляются.

Новая структура записывает ограниченный install-manifest.txt с проверенными относительными путями и SHA-256. До обновления проверяются пути, дубликаты и размеры старого манифеста; выход за пределы пути, псевдонимы устройств и точки повторной обработки в путях очистки отклоняются. Если удаляемые файлы изменены или их нельзя проверить, установка останавливается до записи. После успешной установки очищаются только файлы из старого манифеста, которые больше не поставляются и всё ещё совпадают по хешу; удаляются только пустые каталоги, дополнительные файлы сохраняются. Даже повторные события завершения одной установки запускают очистку только раз. Файлы, изменённые или занятые во время очистки, остаются вместе с записью повтора и ненулевым кодом выхода 20. Невозможность записать повтор требует ручного исправления; транзакционное восстановление и безопасность при отключении питания не заявляются. Эта пользовательская установка предполагает, что внешние процессы не изменяют каталог одновременно; повторные проверки пути и хеша не являются изоляцией от злонамеренной гонки на основе дескрипторов.

Существующие структуры с каталогами версий обновляются напрямую. Команды запуска и ярлыки переходят в корень, а расположение настроек и последних элементов сохраняется. Старый установщик не поставлял отдельный манифест владения, поэтому исторические каталоги versions/ остаются до обычного удаления; накопительный журнал Inno очищает первоначально записанные файлы без рекурсивного удаления каталогов. Файлы пользователя сохраняются. Откат может переустановить выбранную старую версию; старые QA-наборы сохраняют историческую структуру и позже могут снова обновиться до корневой. Новая установка не создаёт versions/. Автоматическое полное стирание старого каталога установки не предусмотрено.

Продукт удерживает именованный мьютекс `Local\xdzip.desktop.running` в течение всего жизненного цикла. [AppMutex](https://jrsoftware.org/ishelp/topic_setup_appmutex.htm) блокирует установку и удаление при CloseApplications=no без принудительного завершения приложения. Ошибка создания дескриптора FFI предотвращает запуск; завершение процесса освобождает его. Выход задач по-прежнему использует существующее решение и барьер завершения Rust.

Обычный установщик Windows регистрирует кандидатов архивов в HKCU. Он записывает собственные ProgID, две собственные записи Applications, Capabilities, RegisteredApplications и собственные значения OpenWithProgids. HKLM, расширения по умолчанию, защищённые UserChoice/UserChoiceLatest и кандидаты других приложений не меняются. Каждый зарегистрированный суффикс имеет ProgID, например `xdzip.Archive.ZIP`, и назначенный ICO. Старый `xdzip.Archive` сохраняет прямую команду открытия и скрыт из «Открыть с помощью» вместе с `Applications/xdzip.exe`. Обновление удаляет их прежние рекомендации, сохраняя совместимость с существующим значением по умолчанию. Для выбора значка Windows сопоставляет составное имя, например `.tar.gz`, по его последнему расширению.

При запуске и после успешного изменения языка обычное установленное приложение синхронизирует описания девяти основных ProgID: ZIP, TAR, TGZ, GZ, 7Z, RAR, CAB, ISO и UDF. Установщик выбирает описания по сохранённому языку приложения или в автоматическом режиме по языку интерфейса системы. Язык мастера независим. До синхронизации работающего приложения проверяются идентичность установки, расположение исполняемого файла, манифест, средство запуска ассоциации и девять существующих команд открытия. Отсутствующие или несовпадающие регистрации не изменяются. Частичную запись можно повторить при следующем обычном запуске. Портативные процессы, процессы разработки и тестовые процессы с изолированными настройками не выполняют синхронизацию. Другие зарегистрированные суффиксы сохраняют описания установщика. Кэш Explorer и выбранное приложение по умолчанию могут повлиять на отображение.

Одноразовая CI Windows проверяет синхронизацию описаний установленного продукта при запуске и переключение работающего приложения между упрощённым китайским и английским. Портативная копия и процесс с изолированными настройками проверяют отсутствие записи; также проверяется неизменность девяти значков, команд, других кандидатов и значений по умолчанию. Эта автоматическая проверка не заменяет ручную приёмку отображения в Explorer или настройках.

Команды в кавычках для всех ProgID форматов запускают `xdzip-association.exe -- "%1"`; их регистрация Applications содержит полный SupportedTypes, поэтому «Открыть с помощью» показывает одну запись приложения xdzip. Средство запуска содержит тот же фирменный ICO приложения и отдельные ресурсы OriginalFilename и версии продукта. Значки приложения проверяются отдельно от значков документов по форматам; DefaultIcon документа не заменяет ресурсы исполняемого приложения. Небольшое GUI-средство запуска принимает один аргумент файла, инициализирует однопоточный апартамент COM в собственном потоке и передаёт существующую команду открытия через ShellExecuteEx с явным классом `xdzip.Archive`, без интерпретатора команд; COM освобождается после вызова. Откат старой версии обновляет общую запись, поэтому кандидаты форматов продолжают указывать на восстановленную программу. Ошибка инициализации COM, отсутствие точки входа, неверные аргументы или отказ системы возвращают ненулевой код без попытки другого приложения или изменения значений по умолчанию. Это зависит от сохранения средства запуска в текущем каталоге при откате; установка/откат и накопительное удаление требуют фактических тестов.

Установщик задаёт `AllowSilentDefaultTakeOver` как REG_NONE в общем ProgID и зарегистрированных ProgID отдельных форматов. Windows всё ещё может предлагать их явными кандидатами «Открыть с помощью». Установщик ограниченным нативным вызовом реестра устанавливает значение в уже созданных собственных ключах. Ошибка останавливает установку и освобождает дескрипторы. См. [соглашения Windows о ProgID](https://learn.microsoft.com/en-us/windows/win32/shell/fa-progids).

Обычный установщик и MSIX создают кандидатов Windows «Открыть с помощью» из [реестра форматов](format-registry.md). Сопоставление охватывает основные типы ZIP, TAR, TGZ, GZ, 7z, RAR, CAB, ISO и UDF и дополнительные зарегистрированные суффиксы. `.gz` может направляться к автономному GZIP или TAR.GZ по содержимому. Общие `.img`, `.001` и `.rNN` зарезервированы для явного открытия или поддерживаемых точек входа. Ассоциация предоставляет системе путь к xdzip. Считыватель по-прежнему исследует файл и применяет требования операции к формату и источнику.

## Ubuntu 24.04

build-linux-installer.py создаёт .deb из того же проверенного каталога. Приватные каталоги подготовки различаются выходным путём, что позволяет пересобирать пакет с одним именем в разных каталогах кандидатов без перезаписи существующей подготовки. Имя пакета — xdzip, версия связывает канал продукта и коммит, архитектура — amd64. Системные зависимости берутся из фактических манифестов развёртывания и включают инструменты desktop-database и блокировки; glibc не ниже 2.39. Qt/QML/плагины и уведомления находятся в /opt/xdzip/versions/; /usr/bin/xdzip — заключённая в кавычки точка переадресации с фиксированной целью. dpkg заменяет и удаляет старые файлы пакета; откат требует сохранения исходного .deb.

Установленный [xdzip.desktop](../../../apps/desktop/packaging/linux/xdzip.desktop) объявляет MIME-кандидатов пакета. Они включают ZIP и выбранные псевдонимы, TAR и фильтрованный TAR, автономные потоки сжатия, архивные форматы вроде 7z, RAR и CAB и образы ISO/UDF. `%f` запрашивает запуск с одним файлом, `--` обозначает границу аргументов. Пакет предоставляет объявление MIME для `*.udf` и не изменяет общие типы изображений и двоичных файлов. Установка и удаление обновляют базы MIME и рабочего стола, не переписывая `mimeapps.list`, не изменяя пользовательские значения по умолчанию и не заменяя системные значки MIME. При удалении удаляются собственные средства запуска, значки и файлы runtime, настройки пользователя сохраняются.

DEB устанавливает свою [запись каталога AppStream](../../../apps/desktop/packaging/linux/xdzip-local.yml) в `/var/lib/swcatalog/yaml/xdzip-local.yml`, путь, доступный Ubuntu App Center. Запись связывает имя пакета `xdzip` с `xdzip.desktop`, чтобы установленный пакет мог появиться в списке приложений. При удалении XDZip dpkg удаляет файл каталога.

Установленный продукт удерживает общую блокировку flock на /run/xdzip/usage.lock. Скрипты обслуживания сначала получают неблокирующую исключительную блокировку и завершаются ошибкой при наличии активного процесса. Скрипты устанавливают барьер установки в принадлежащем root /run/xdzip; продукт повторно проверяет его после получения своей блокировки, предотвращая запуск между хуками dpkg. Символические ссылки или неправильный владелец/разрешения отклоняются; закрытие QFile освобождает блокировку. tmpfiles.d подготавливает блокировку среды выполнения при запуске системы. На приложения разработки SDK это не влияет.

Пути успешного завершения и отмены dpkg очищают барьер. Прерывание или отключение питания может оставить незавершённую транзакцию; выполните sudo dpkg --configure -a и исправьте фактическую ошибку. Невозможность запуска не является успехом установки. Скрипты не очищают пользовательские каталоги рекурсивно; артефакты создаются только в build/ или CI.

## macOS и открытие файлов

Основное приложение и поставляемый пакет объявляют документы и ICNS как Viewer/Alternate в Info.plist, [не заявляя владения по умолчанию](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html). Сборки разработки и тестов по умолчанию используют Viewer/None и не входят в системные кандидаты «Открыть с помощью». Основные пакеты разработки или сборки поставки должны явно задавать `-DXDZIP_MACOS_HANDLER_RANK=Alternate`. Значения по умолчанию определяют пользователь и Launch Services; приложение активно их не изменяет. Временные регистрации копий для проверки разработки очищаются по [методу обслуживания Mac](macos-deployment.md) с сохранением существующих приложений и пользовательских значений по умолчанию.

CAB, ISO и UDF используют ту же роль Viewer. ISO использует `public.iso-image`. Приложение не заявляет `.img` или общий `public.disk-image`. Viewer описывает ассоциацию Launch Services, а доступные операции определяет [backend форматов](native-codecs.md). Отдельный [профиль создания ISO](iso-creation.md) может записывать новые образы.

Объявления документов покрывают последние расширения всех кандидатов оболочки из [реестра форматов](format-registry.md) и используют соответствующий ICNS пакета. Составные суффиксы разделяют тип последнего расширения. Например, `.tar.gz` и `.gz` имеют общий GZIP по умолчанию, а `.tgz` использует системный тип сжатого TAR. Кэш Finder, выбранное значение по умолчанию и распознавание типа системой влияют на фактическое отображение.

Импортированные типы RAR, CAB и UDF в macOS должны соответствовать `public.data`, чтобы идентифицировать реальные файлы. CAB объявляет системный `com.microsoft.cab` и совместимый `com.microsoft.cab-archive`; настройки запрашивают и меняют фактический предпочтительный тип, если он один из них, иначе используют идентификатор совместимости. UDF Viewer объявляет расширение `.udf` без `LSItemContentTypes`, чтобы реальные файлы находили кандидата даже при использовании недействительного объявления UTI старой установки. Apple объявила этот [ключ объявления расширения](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html) устаревшим; продолжайте проверять его на поддерживаемых версиях macOS. Настройки запрашивают и меняют фактически распознанный тип `.udf`, при недоступности переходя к существующему идентификатору. Установка или регистрация не переопределяет активно существующие значения по умолчанию. Если обработчика не было, Launch Services может выбрать нового кандидата текущим обработчиком по [неявным правилам](https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/LaunchServicesConcepts/LSCGlossary/LSCGlossary.html). Удаление временной регистрации должно восстановить исходное состояние; это разрешение не является записью пользовательских предпочтений приложением.

FileOpenRouter получает [QFileOpenEvent](https://doc.qt.io/qt-6.8/qfileopenevent.html) до QML, принимает только локальные файлы и повторно использует существующую маршрутизацию открытия и активации. Аргументы GUI после `--` являются путями файлов, чтобы не путать их с диагностическими флагами. В очередь помещаются не более 128 ожидающих намерений без вытеснения активных задач. Обычные процессы продукта в одном сеансе входа используют один экземпляр; запросы нескольких файлов открываются по порядку и активируют последний. Поведение вкладок и окон описано в [контракте сеансов](application-sessions.md).

Аргументы запуска ставятся в очередь до загрузки QML. Главное окно начинает скрытым и немедленно отправляет первый доступный запрос при подключении контроллера без требования видимости окна. Окно показывается в начальной очереди событий, чтобы события запуска платформы использовали тот же путь. При внешнем открытии скрывайте элемент приветствия до смены сеансов, чтобы избежать вспышки страницы приветствия в первом кадре или при замене сеанса. Отмена или ошибка восстанавливает приветствие, успех показывает реальный список. См. [состояние загрузки](../ux/welcome-opening.md).

Нативный запуск macOS отдельно ожидает NSApplicationDidFinishLaunchingNotification AppKit, обрабатывает этот пакет ожидающих файловых событий Qt в скрытом состоянии, затем показывает окно. Уведомления и ожидающие обратные вызовы ограничены временем жизни главного окна; они не заменяют делегат приложения Qt и не используют фиксированные задержки в миллисекундах. Реальная регрессия Launch Services ранее обнаружила один кадр приветствия; исправленное требование — ноль. check-macos-open.py запускает пути argv и нативного открытия локально и в Mac CI, сохраняя только JSON и журналы без создания или загрузки пакетов приложения.

## Автоматическая проверка и ограничения

CTest на трёх платформах проверяет файловые события до запуска, отказ от нелокальных URL и постановку в очередь при занятом чтении. Явный XDZIP_ASSOCIATION_PROBE с изолированными настройками предназначен только для CI: через обычный процесс открытия прочитать собственный ZIP проекта со 100 000 записей, сохранить количество и идентичность сборки и нормально завершиться без записи исходных путей или извлечения.

Текущая проба ассоциаций ожидает хотя бы одного фактического представленного кадра и записывает видимость содержимого приветствия для каждого кадра. Текущие требования продукта для Windows ShellExecuteEx и Linux GIO — presented_frames больше 0 и welcome_frames равно 0. Фиксированные старые продукты тестируются по историческим возможностям их проб; не следует выдавать старые двоичные файлы за имеющие новые счётчики первого кадра.

Нативная CI Windows устанавливает QA-вариант 1, обновляет до 2, откатывает до 1, затем устанавливает реальный пакет поставки. ShellExecuteEx открывает собственные классы регистрации с путями, содержащими китайские символы, пробел и амперсанд, проверяя неизменность значений по умолчанию и UserChoice, отказ замены при занятости и сохранение настроек, дополнительных файлов и других кандидатов при удалении. Linux выполняет тот же цикл dpkg в контейнере без сети, SDK, системного Qt и компилятора. Продукт с UID 1000 действительно открывает 100 000 записей через средство запуска рабочего стола GIO; проверяются MIME, значения по умолчанию, блокировки, удаление и purge.

Проверка выпуска Linux также меняет значения MIME по умолчанию в изолированном пользовательском профиле контейнера и использует `gio open`, когда GIO разрешает тип содержимого образца в xdzip. Она проверяет каждый объявленный MIME по умолчанию, испытывает отдельный обработчик и восстанавливает исходные значения. Автоматические проверки открытия файлов Linux и macOS используют образцы, открывающиеся без ввода. Тест браузера AES Crypt проверяет запрос пароля открытия и аутентифицированное чтение. Системные настройки и другие среды рабочего стола требуют отдельной проверки.

Варианты QA используют общие проверенные двоичные файлы и меняют только версию и каталог тестового пакета для проверки механизмов установки. Они не являются артефактами выпуска и не выдают себя за реальную миграцию данных между разными версиями продукта. Текущая схема настроек — 1, и метаданные установки записывают её на обеих платформах. Старые установщики отказываются перезаписывать установку с более новой схемой; будущая миграция должна обновить контракт.

Последующее внедрение сбоя допускается только в QA-варианте 2 с однократной ошибкой во время настройки postinst. В production эта ветка отсутствует. Контейнер фактически проверяет наполовину настроенное состояние, запуск, заблокированный барьером, и сохранение настроек, затем выполняет dpkg --configure -a для восстановления и открывает реальный файл через GIO. Это воспроизводимый сбой конфигурации, а не отключение питания устройства. Отдельная проверка совместимости настроек компилирует сохранённые оригинальные и текущие компоненты настроек и выполняет двусторонний обмен конфигурацией той же схемы. Исходные входные файлы фиксируются пофайловыми хешами независимо от старой истории main и не выдаются за полную миграцию данных установщика.

Полная совместимость продукта отдельно проверяется prepare-previous-product.py, который собирает полные исходники из фиксированного снимка совместимости (первоначально из 4cf0f8c) на одноразовых CI-хостах Windows/Linux. Отсоединённый worktree сохраняет фактическую чистую идентичность; текущий фиксированный SDK собирает QA-установщики исторического продукта без загрузки старых двоичных файлов Actions с ограниченным сроком хранения. Установите исторический продукт и действительно откройте его, затем установите текущий продукт и проверьте изменение ревизии и сохранение байтов конфигурации, после чего откатите, снова откройте исторический продукт и проверьте данные. Это доказывает совместимость одной схемы между двумя полными коммитами исходников, а не исторически подписанный оригинальный пакет, несуществующую миграцию схемы 2 или перезагрузку устройства. Исторические установщики предназначены только для QA и не загружаются как ресурсы продукта; квитанции связывают SHA-256 обоих двоичных файлов и установщиков.

windows-install-lifecycle.json, linux-install-lifecycle.json и хеши пакетов являются фактическими свидетельствами. Реальный двойной щелчок Explorer/Finder, интерфейс выбора по умолчанию, службы и кэш после перезапуска, предупреждения об отсутствии формальной подписи, проверки GPU и рабочего стола выполняются по ручному контрольному списку. Автоматические скрипты не должны самостоятельно отмечать все INSTALL-01/ASSOC-01 как пройденные. Существующие ручные заключения находятся в [WP-12 #5](https://github.com/xiaodaozhi/xdzip/issues/5); повторное создание ожидающего шаблона не открывает приёмку заново. Будущим миграциям схемы нужны дополнительные фактические случаи совместимости.

Проба Windows без задач для защиты от замены занятого продукта использует изолированные настройки с отключённым треем, чтобы `CloseMainWindow` в этой конфигурации выполнял обычный выход. Другие пробы открытия по ассоциации сохраняют стандартные настройки трея и завершаются через явный барьер выключения. Пробы защиты установки не должны считать скрытое окно ошибкой завершения процесса или обходить проверку выхода принудительным завершением обычного пути.

Тестовые наборы протокола обновления Windows и реального обновления Qt содержат средство запуска ассоциации и все девять ICO документов; установщики не могут пройти проверки без необходимой нагрузки. Маленькая основная программа C и команда ассоциации в тесте протокола проверяют только передачу обновления. Встроенные ресурсы приложения, нативные кандидаты и реальные окна отдельно проверяются полным продуктом Qt; выводы не смешиваются.

## Долговременные входные данные базы совместимости

Реальные обновление и откат используют фиксированные полные исходники старого продукта, а не переписанную историю main. `prepare-previous-product.py` фиксирует снимок исходников с одним корнем в независимой ветке `codex/installer-compat-baseline`. Ветка содержит только оригинальные исходники и ресурсы, нужные для сборок и регрессии, без родителей старого main, отчётов исполнения или рабочих процессов. `COMPAT-BASELINE.json` в снимке записывает исходный коммит и идентичность дерева. Его нельзя сливать обратно в main или считать пакетом выпуска либо заключением о приёмке текущего продукта.

После сборки идентичность CLI должна совпадать с собственным фиксированным SHA снимка; квитанции отдельно записывают идентичность оригинальных исходников и не должны выдавать себя за первоначально выпущенный двоичный файл. Компоненты настроек также сохраняют три небольших оригинальных исходных файла как долговременные тестовые входы с пофайловой фиксацией хешей. Двусторонние чтение и запись и отказ от будущих схем не зависят от сети или исторических коммитов. Не изменяйте эти регрессионные входы вместе с текущей реализацией; новую базу проверяйте отдельно и при необходимости сохраняйте происхождение.

Зафиксированный снимок предшествует независимой вспомогательной программе обновления и не содержит её исходников или двоичного файла. Только `prepare-previous-product.py` передаёт ему `--qa-historical-revision`. Скрипты развёртывания и упаковки одновременно требуют одноразовую CI, полный фиксированный SHA и совпадение фактической чистой идентичности продукта. Linux дополнительно требует режим исторической версии и запрещает смешивание с текущим вариантом QA. Windows напрямую запускает команду версии старого продукта для проверки идентичности; Linux использует идентичность независимого аудита развёртывания и полные хеши файлов. Квитанции явно сообщают, что исторические исходники не содержат вспомогательную программу, не внедряют текущую программу и не устанавливают разрешение polkit для несуществующей программы Linux. Обычные продукты и текущие варианты QA по-прежнему должны поставлять и проверять независимую вспомогательную программу; один `--qa-legacy-version` не разрешает её отсутствие.

## Миграция версий Debian

Начиная с первого публичного предварительного выпуска используется Debian epoch 1: `1:<semantic-version mapping>+git<commit>`, например `1:0.1.0~alpha.1+git...`. Историческая `0.1.0~dev.9` без epoch сортируется после alpha.1 по правилам dpkg, поэтому старое сопоставление нельзя просто сохранить. Epoch используется только для порядка системных пакетов; интерфейс продукта, теги версий и release.json продолжают использовать исходную семантическую версию. Последующие пакеты Debian сохраняют epoch 1, порядок alpha, beta, rc и stable по-прежнему выражается версиями upstream. См. [Debian Policy](https://www.debian.org/doc/debian-policy/ch-controlfields.html#version).

Фактический тест исторического продукта использует `--qa-legacy-version` только в CI для сохранения исходной идентичности без epoch; не меняйте порядок старого пакета, чтобы скрыть проблемы обновления. Текущий пакет должен пройти фактическую приёмку обновления, отката и жизненного цикла установки dpkg. Пользовательская конфигурация и внешние ассоциации по умолчанию сохраняют исходные контракты.

## Приложения по умолчанию в настройках

Настройки группируют суффиксы ассоциаций с помощью созданных данных форматов. Доступность переключателей зависит от службы платформы и идентичности установки. Windows передаёт изменения системным приложениям по умолчанию и никогда не записывает UserChoice. MSIX оставляет переключатели отключёнными и использует системную запись пакета. Linux сопоставляет поддерживаемые суффиксы с MIME-типами, использует `xdg-mime` для пользовательских значений и предлагает установленную замену при удалении значения по умолчанию.

В macOS настройки включают каждый переключатель, системный тип которого покрыт объявлениями Viewer/Alternate установленного пакета. Включённый переключатель может запросить xdzip по умолчанию, даже если у типа раньше не было значения. macOS может запросить подтверждение. После успешного обратного вызова настройки дают Launch Services короткое время на сообщение нового значения. Когда системный запрос подтвердит xdzip, приложение локально сохраняет bundle ID предыдущего приложения по системному типу содержимого. При выключении переключателя сначала запрашивается предыдущее приложение, если macOS всё ещё считает его совместимым. Если сохранённого совместимого приложения нет или восстановление не удалось, настройки предлагают совместимые установленные альтернативы. Если альтернатив нет, это объясняется рядом с переключателем. Отмена сохраняет текущий выбор, а отображаемое состояние следует новому системному запросу. Сборки Viewer/None отключают изменения.

В автоматическом языковом режиме Windows Setup выбирает описание ассоциации по текущему языку системного интерфейса пользователя. Для предпочтения традиционного китайского используется традиционный китайский, для неподдерживаемых языков — английский США. Поддерживаемый ручной выбор имеет приоритет. Setup сохраняет автоматический режим, чтобы приложение при запуске определило язык системы и синхронизировало собственные описания.
