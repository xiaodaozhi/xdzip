# Фиксация инструментов и платформ

[English](../../engineering/toolchain.md) | [简体中文](../../zh-CN/engineering/toolchain.md) | [繁體中文（台灣）](../../zh-TW/engineering/toolchain.md) | [日本語](../../ja-JP/engineering/toolchain.md) | [한국어](../../ko-KR/engineering/toolchain.md) | [Français](../../fr-FR/engineering/toolchain.md) | [Deutsch](../../de-DE/engineering/toolchain.md) | [Español](../../es-ES/engineering/toolchain.md) | [Português (Brasil)](../../pt-BR/engineering/toolchain.md) | Русский

Версии инструментов разработки зафиксированы в rust-toolchain.toml, Cargo.lock, CMake и CI; область поддержки определяется [политикой поддержки](support-policy.md). Таблица задает проверки для обновлений и выпусков. Конкретные наблюдения остаются в issue или Actions; перечень инструментов одной машины не фиксирует зависимости выпуска.

| Элемент | Текущее направление | Доказательства для фиксации |
| --- | --- | --- |
| Rust | rust-toolchain.toml фиксирует 1.99.0, edition 2024, rust-version 1.99 | При обновлении проверить MSRV зависимостей, тесты трех целей и Clippy; согласовать инструменты и конфигурацию Cargo |
| Qt | Зафиксирован SDK 6.8.2; QtNetwork использует `6.8.2-xdzip-network.1`, полученный с официальными исправлениями безопасности. Локальный SDK в `build/toolchain/Qt/6.8.2/<platform-subdirectory>`; динамическое развертывание | Зафиксированные происхождение и хеши, лицензии модулей и базовые проверки трех платформ; перед каждым выпуском проверять поддержку безопасности, при обновлении повторно проверять исходники и замену |
| C++ | C++17 и компилятор, соответствующий Qt | Версии macOS clang, Windows MSVC и компилятора Linux |
| CMake | Корень требует 3.24 или новее и использует Ninja | Проверить фактическую версию сборки, зависимости сгенерированных заголовков и чистую конфигурацию; workflow фиксирует версии инструментов CI |
| Python | Общая точка входа desktop требует 3.10+; инструменты проверки пакета используют изолированные среды | Использовать тот же интерпретатор для последующих скриптов Python и проверять фиксированные зависимости по этапам; браузерные инструменты дизайна не являются зависимостями сборки продукта |
| cxx | 1.0.205; мост генерируется при сборке, стабильного бинарного ABI нет | Совпадение версий crate и генератора, регрессии гонок при завершении и границ исключений |
| Системы | macOS 14+ arm64, поддерживаемая Windows 11 x64, Ubuntu 24.04 X11 x64 | Проверить реальные среды по утвержденной политике; не распространять доказательства CI-хоста на все версии систем |

В Windows сборки desktop и исходников Qt и пересборки поставленных исходников временно используют консольную кодовую страницу UTF-8 для MSVC/Ninja и затем восстанавливают исходную. При отсутствии консоли создается временная скрытая консоль для процесса и потомков; внешние процессы не должны подключаться. Защищенные сборки в общей существующей консоли выполняются последовательно по списку подключенных процессов; независимые консоли могут собирать параллельно. Во время защиты процессы должны оставаться подключенными. Недействительный список останавливает сборку; после ожидания 30 секунд запрашивается повторная попытка. Старые скрипты без дескриптора окна используют несовместимые блокировки, а эта координация не препятствует изменению консоли другими программами. До и после сборки проверяются записи зависимостей Ninja для скомпилированных объектов. Если у исходника с прямым include в кавычках или include в угловых скобках из того же каталога нет записанных зависимостей, остановиться, сохранить старый каталог и запросить новый каталог сборки без автоматического удаления или повторного использования объектов. Ninja может намеренно опускать системные заголовки, поэтому исходники только с ними могут иметь ноль зависимостей. Проверка не охватывает include в угловых скобках из других путей поиска и все неявные входы компилятора, а также не вычисляет условия препроцессора; она может осторожно отклонять неактивные include. Прямой запуск CMake/Ninja обходит эту защиту: обеспечить соответствие вывода компилятора префиксу Ninja и после смены кодовой страницы или инструментов проверить, что реальное изменение заголовка вызывает перекомпиляцию.

Размещенные GitHub задания Apple Silicon используют исполнители macOS 15, тогда как цель развертывания продукта остается macOS 14.0. Обновление исполнителя не доказывает проверку на реальном устройстве с macOS 14; совместимость платформы и ручная приемка фиксируются отдельно.

Ежедневная подготовка, проверки и запуск описаны в [руководстве по сборке для разработчиков](developer-build.md). `scripts/desktop.py doctor` по умолчанию проверяет build; `doctor --for-stage package` заранее проверяет всю цепочку упаковки. Параметры prepare `--install-rust`, `--install-qt` и `--packaging` явно подготавливают соответствующие инструменты и зафиксированные материалы. Системные компиляторы и SDK по-прежнему устанавливают разработчики; предварительная проверка не является неявным установщиком.

Фиксированный локальный каталог инструментов — `build/toolchain/`. Qt SDK, `qmllint` и `qmake` используют `build/toolchain/Qt/6.8.2/<platform-subdirectory>`; `aqtinstall` и общие инструменты Python используют `build/toolchain/desktop-tools`; временное размещение загрузки Qt — `build/toolchain/qt-install-tool`. Общие точки входа используют эти каталоги вместо отдельных кешей для сборки, теста, пакета или отдельных проверок Qt. CI с временными каталогами исполнителя должна явно передавать параметры, не меняя локальную структуру по умолчанию.

Предварительная проверка запускает Rust/Cargo, фактически доступные в PATH, проверяет фиксированные версии и родной хост, CMake, Ninja, префикс Qt и инструменты платформы. Установленный, но недоступный текущей оболочке компилятор считается отсутствующим. Упаковка также проверяет метаданные зафиксированных зависимостей Rust, материалы SPDX и лицензий Qt и кеш схем. Все последующие процессы используют ту же проверенную среду, предотвращая отсутствие rustc/cargo при сборе лицензий после успешной сборки. Отсутствие Docker или Inno Setup влияет только на требующие их этапы и не блокирует обычные сборки разработки.

Каждая запись включает версию, источник загрузки, SHA-256, лицензию, цель, ответственного, проверочный коммит и дату. Обновления безопасности Rust/Qt вызывают повторную проверку; более не поддерживаемые исправления не сохраняются бессрочно. Кандидаты минимальных систем не являются формальным обязательством поддержки.

Обслуживание систем, каналы обновлений безопасности Qt и ответственность за проверку обновлений определяет [политика поддержки](support-policy.md). Выводы о происхождении и лицензиях записываются по [процессу проверки выпуска](../../../developers/qa/release-review.md).

В Windows расширение клиентской области главного окна реализует WindowsFrame через публичные оконные интерфейсы Qt и Win32 без связывания GuiPrivate. При первоначальной привязке к обычному окну рамка определяется по текущим логическим размерам клиентской области QWindow, DPR и системным метрикам границ; последующее повторное применение темы или DPI обновляет только границы. Для обычного окна PMv2 без локального переопределения масштаба и с округлением Qt PassThrough обработчик WM_GETDPISCALEDSIZE сохраняет поправку ожидающего SIZE до масштабирования, масштабирует клиентскую область и добавляет реальные границы целевого DPI. Недопустимые метрики, переполнение или другие состояния не изменяют SIZE и передают управление Qt. Заимствованные системные сообщения и доступные для записи структуры используются только в синхронном обратном вызове. При обновлении Qt или замене SDK повторно проверить затронутые клиентские области, границы и состояния окон. Физическое перетаскивание между двумя экранами и внешний вид проверяются по необходимости; программные результаты не заменяют невыполненную физическую проверку.

Ежедневная CI независимо устанавливает закрепленную в rust-toolchain.toml версию Rust, rustfmt и clippy во временный каталог исполнителя и перед проверкой форматирования Rust убеждается, что фактический компилятор находится там, избегая неполного набора rustup хоста. Полные тесты Rust и инструментов подписи выполняются локально или в соответствующем workflow по запросу согласно изменению.
