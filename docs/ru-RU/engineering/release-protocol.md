# Протокол GitHub Release v1

[English](../../engineering/release-protocol.md) | [简体中文](../../zh-CN/engineering/release-protocol.md) | [繁體中文](../../zh-TW/engineering/release-protocol.md) | [日本語](../../ja-JP/engineering/release-protocol.md) | [한국어](../../ko-KR/engineering/release-protocol.md) | [Français](../../fr-FR/engineering/release-protocol.md) | [Deutsch](../../de-DE/engineering/release-protocol.md) | [Español](../../es-ES/engineering/release-protocol.md) | [Português (Brasil)](../../pt-BR/engineering/release-protocol.md) | Русский

Этот процесс обеспечивает загрузки с GitHub. [Процесс MSIX для Microsoft Store](../../../.github/workflows/windows-store-msix.yml) упаковывает тот же версионированный исходный код для Microsoft Partner Center, где выполняются сертификация и публикация в Store.

Отдельный [рабочий процесс Release](../../../.github/workflows/release.yml) запускается вручную через `workflow_dispatch`. Официальный запуск начинается из `main` с существующим тегом версии и фиксирует соответствующий коммит. Каждая из четырех нативных задач один раз выполняет настройку, сборку, тесты и упаковку. Задача macOS с начальной сборки использует ранг ассоциации дистрибутива, затем развертывает Qt и применяет ad-hoc подпись целостности, создавая ZIP и DMG из одного приложения. Обычный CI Qt для macOS проверяет сборку с SDK. Developer ID, нотариальное заверение Apple и сертификаты издателя Windows не входят в эту политику выпуска.

Сборка Intel отдельно создает архивы приложения ZIP, DMG и CLI `macos-x86_64`. Настольное приложение и CLI Intel используют соответственно `release-intel.json` и `cli-release-intel.json`; их подписи и `appcast-intel.xml` проверяются отдельно. Формат существующих манифестов и ленты ARM64 сохраняется для старых клиентов. Перед выпуском необходимо проверить нативные пакеты обеих архитектур.

Исходный код продукта берётся из коммита, на который указывает тег. Подготовка черновика, публикация и проверка общедоступных загрузок используют одни и те же проверенные примечания из коммита `main`, запустившего рабочий процесс.

Полный тег состоит из `v` и семантической версии, полученной из VERSION.json. `prerelease_number` — необязательное положительное целое число; его отсутствие сохраняет совместимость с историческими номерами сборок. alpha.1 и build 14 — разные идентификаторы. Числовые ресурсы Windows и CFBundleVersion macOS по-прежнему используют монотонно возрастающие номера сборок. Публичные активы одной версии заменять нельзя; для исправления нужна новая версия. Черновики можно запускать повторно.

Примечания к выпуску — сохраняемый и доступный для проверки вход версии. По умолчанию они читаются из `release-notes/<full-version>.md`; CLI может указать проверенный файл через `--notes-file`. Файл содержит одну строку метаданных `<!-- xdzip-release {"version":"0.1.0-alpha.6","build":19} -->` и соответствующий заголовок версии. Версия и build должны совпадать с VERSION.json. Сначала выполните `python3 scripts/publish-release.py --check-notes`; эта проверка не обращается к GitHub. Отдельный рабочий процесс выполняет ту же предварительную проверку перед сборкой. Новым версиям нужны новые примечания; списки функций и статусы приемки прежних версий автоматически не наследуются.

Примечания на китайском и английском фиксируют границы приемки по платформам, фактический коммит и доказательства, отдельно сохраняя прежнюю ручную приемку и невыполненные проверки. Ход этапов по-прежнему отслеживается в issue. Для создания черновика и публикации используется один снимок примечаний. Если при повторном запуске черновика его текст отличается от проверенного файла, остановитесь до загрузки или удаления активов и явно согласуйте входные данные. Опубликованные версии продолжают отклонять повторные запуски с заменой активов. Записывайте ожидающие выпуска изменения в [разделе «Не выпущено» журнала](../../../CHANGELOG.ru-RU.md#unreleased) и переносите их в раздел версии после публикации. Синхронизируйте изменения во всех переводах журнала.

Перед изменением активов черновика инструмент публикации повторно считывает тег GitHub, состояние черновика и маркер канала. Stable должен оставаться не предварительным выпуском и стать GitHub Latest; alpha, beta и rc должны оставаться предварительными и не заменять Latest. Повторно проверяйте соответствующее состояние после публикации и после проверки публичных вложений; сообщайте об успехе, только если все совпадает. При ошибке после публикации выпуск уже может быть виден. Скрипт останавливается для действий владельца и не отзывает, не изменяет и не заменяет публичный выпуск или активы автоматически.

Перед официальным выпуском завершите локальную предварительную проверку и просмотр соответствующих примечаний. Проверка пакета независимо выполняется на той же нативной платформе. Передача из одного запуска допускается только после проверки репозитория, коммита, платформы, архитектуры и SHA-256 архива. Windows и Linux один раз проверяют развернутую среду и выполняют реальный жизненный цикл установщика. macOS проверяет и фактический DMG, и ZIP приложения. Запуск кандидата по запросу выполняет те же задачи и загружает собранный артефакт Actions для проверки контрольной суммы. Для кандидата используются права репозитория только на чтение, тег не нужен, секреты подписи выпуска недоступны.

Задача контракта выпуска сначала собирает из того же коммита изолированный процесс обработки форматов и выполняет тесты рабочего пространства Rust с `XDZIP_NATIVE_CODEC` и `XDZIP_NATIVE_CODEC_WORKER`. Нативные задачи трех платформ отдельно проверяют приложения, развертывание и жизненные циклы установки. Тест ранга ассоциации разработческой версии macOS использует временную копию скомпилированного пакета с метаданными разработчика. Пакет дистрибутива сохраняет свой действительный ранг для нативного запуска и упаковки.

Каждая проверка развертывания Windows использует отдельную временную тестовую копию и сохраняет предыдущие журналы. Повторные проверки не используют и не удаляют существующие каталоги; каталоги среды выполнения продукта не содержат тестовых DLL.

Выпуски всегда включают `release.json` и `SHA256SUMS`. Корневые поля манифеста `schema_version=1`: product, version, channel, build, tag, commit (полный SHA из 40 символов), repository и assets. Каждый актив содержит filename, platform, architecture, package_type, minimum_system, bytes, sha256 и url, закрепленный за путем загрузки тега.

| Платформа, архитектура | Типы пакетов | Минимальная система |
| --- | --- | --- |
| windows, x86_64 | zip, exe | Поддерживаемая Windows 11 |
| macos, arm64 | app.zip, dmg | macOS 14.0 |
| linux, x86_64 | tar.gz, deb | Ubuntu 24.04, glibc 2.39, X11 |

Необходимы все шесть типов пакетов. Проверка манифеста отклоняет отсутствующие пакеты, повторяющиеся цели, несогласованные каналы, изменяемые URL загрузки, неверные размеры или хеши. Вложения выпуска включают уведомления платформ, лицензии, SBOM и материалы развертывания и проверки, но не архивы соответствующего исходного кода. Windows использует локальные для приложения среды VC++ и не распространяет библиотеки графического компилятора Windows SDK.

С 2026-11-05 владелец распорядился удалить исторические архивы соответствующего исходного кода из GitHub Releases и артефактов Actions и прекратить их создание и загрузку в последующих процессах выпуска. `scripts/prepare-source-delivery.py` сохранен для локальной проверки. Сборка и публикация выпуска отклоняют имена архивов с `corresponding-source`. Эта политика не меняет лицензии компонентов и не подтверждает выполнение обязательств по соответствующему исходному коду, повторному связыванию или иных обязательств. При проверке выпуска необходимо решить эти вопросы для фактической поставки; если обязательные условия нельзя выполнить иначе, заблокируйте распространение затронутых бинарных файлов. Автоматические снимки исходного кода тегов GitHub в публичном репозитории не являются этими вложениями Release.

При обычном выпуске нельзя самостоятельно запускать локальный сборщик исходной поставки. Запускайте его только по отдельному явному запросу пользователя на сбор исходного кода, соблюдая ограничения на загрузку. Общие отметки машинной проверки оцениваются по фактическим компонентам и конкретным обязательствам; сами по себе они не подтверждают новый дефект выпуска.

ZIP приложения macOS, DMG и уведомления необходимо экспортировать, пока существует то же развернутое и подписанное временное приложение, до очистки подготовленного `.app` и временных регистраций. Не развертывайте другое приложение после очистки, чтобы дополнить ZIP.

Порядок: локальная предварительная проверка, фиксация коммита версии, создание тега, один ручной запуск Release, сборки на трех платформах и независимая проверка запуска и жизненного цикла установки, сборка манифеста черновика, публикация по каналу после выполнения всех условий, затем повторная загрузка и проверка всех вложений. Stable — обычный Release, явно отмеченный Latest; alpha, beta и rc — Pre-release. При ошибке любой платформы черновик остается неопубликованным. Проверяйте SHA256SUMS до и после публикации. Если проверка происхождения и лицензий или ручная приемка не завершены, сохраните ограничения в примечаниях; автоматизация не может подменять эти выводы.

Клиенты обновления постранично читают GitHub Releases, пропускают черновики, проверяют версии манифестов и выбирают пакет по семантической версии, разрешенному пользователем каналу, платформе, архитектуре и типу пакета. Не определяйте обновления по датам публикации и не угадывайте имена файлов. Предварительные выпуски не используют `/releases/latest`, поскольку он их исключает. Stable получает только stable; alpha допускает alpha, beta, rc и stable; beta не возвращается к alpha; rc получает только rc и stable; dev поддерживается при сравнении версий разработки. Должны увеличиться и семантическая версия, и монотонный номер сборки. После загрузки проверьте размер и SHA-256; отсутствующие или несовпадающие значения отклоняются.

<a name="xdzip-trusted-update-attachments"></a>

## Доверенные вложения обновления

Новые выпуски включают `release.json.sig` с schema_version=1, algorithm=ed25519, key_id и подписью из 128 строчных шестнадцатеричных символов. Подпись покрывает точные исходные байты `release.json`; перед проверкой нельзя разбирать их и сериализовать заново. Клиенты и помощники установки без Qt используют каждый свой встроенный набор открытых ключей `resources/update-trust.json`; корни доверия из загруженных манифестов или запросов пользователя не принимаются. При установке отклоняются неизвестные открытые ключи, повторные key_id, слабые ключи и пустые наборы доверия.

Задания macOS упаковывают и проверяют ZIP с приложением. Затем задание `sign` на Linux получает проверенные байты и запускает `scripts/sign-macos-update.py`, который вызывает `xdzip-update-tool sign-archive` для создания `macos-update.json` с полями schema_version, version, build, filename, bytes, sha256 и `ed_signature` Sparkle в base64. Сборка снова проверяет архив и подпись и создает `appcast.xml` только с тем же неизменяемым кандидатом. Необязательное поле `macos_appcast_url` закрепляется за этим файлом в том же теге. Лента использует build как версию Sparkle, полную семантическую версию как shortVersionString и macOS 14.0 как минимум, включая только краткие примечания. Полные примечания остаются в тексте GitHub Release; клиенты не загружают внешние примечания.

Архив и лента используют отдельный ключ Sparkle; сама лента также должна быть подписана. Кроссплатформенные инструменты выпуска следуют [формату подписи Sparkle](https://github.com/sparkle-project/Sparkle/blob/2.x/common_cli/Signing.swift): подписывают полный исходный XML и добавляют блок комментария sparkle-signatures с edSignature в base64 и длиной исходных байтов. Недостаточно подписать только вложение. После создания выполните независимую проверку; любое изменение байтов требует повторной подписи. SUPublicEDKey пакета Mac должен совпадать с открытым ключом в `resources/sparkle-update-key.json`.

Среда выпуска предоставляет существующие ключи и ID открытого ключа через `XDZIP_UPDATE_SIGNING_KEY_HEX`, `XDZIP_UPDATE_KEY_ID` и `XDZIP_SPARKLE_SIGNING_KEY_HEX`. Владелец предоставляет два ресурса открытых производственных ключей, версионируемых вместе с клиентами и помощниками установки; не встраивайте тестовые открытые ключи и не создавайте закрытые ключи во время сборки. Сначала владелец поставляет публичные корни доверия в клиентской версии, затем настраивает соответствующие закрытые ключи в доверенной среде выпуска. При ротации новые открытые ключи поставляются до смены ключей подписи, чтобы старые клиенты сохраняли возможность проверки. Старые клиенты без встроенных открытых ключей должны сначала вручную установить версию с ними; загруженные манифесты не могут добавлять корни доверия. Старые публичные выпуски задним числом не подписываются и не заменяются.

Скрипты выпуска собирают инструменты подписи в дочернем процессе, из которого удалены обе переменные среды с закрытыми ключами; только процесс скомпилированного инструмента получает закрытые ключи подписи. Скрипты сборки Cargo, компиляторы и разрешение зависимостей не получают полномочий на подпись.

Финальная задача подписи подписывает проверенный архив и манифесты обновления в `release-signing`. Отдельная задача публикации также требует эту среду и до публичного выпуска проверяет подписи и загрузки черновика. Последняя задача с правом только чтения загружает публичный выпуск и сверяет его с подписанными активами. Все задачи используют зафиксированный коммит и артефакты одного запуска.

[Приемка обновления production](../../../.github/workflows/production-update-acceptance.yml) — отдельная ручная точка входа, закрепленная за `main` и `contents: read`, с той же средой `release-signing` и одобрением владельца. Она не запускает Release и не создает теги, черновики или выпуски. Сначала инструменты компилируются на этапе без секретов; затем открытые ключи независимо выводятся из существующих закрытых ключей и строго сравниваются с обоими открытыми ключами и ID открытого ключа текущего коммита. Само наличие записи не доказывает совпадение. Приватные старые сборки 200 и новые сборки 201 трех платформ сохраняют производственные открытые ключи и собираются без секретов. Подпись принимает только фиксированные кандидаты, полностью связанные с этим коммитом, приватной идентичностью продукта и хешами. Нативное обновление, восстановление после ошибки и обычный перезапуск затем выполняются в процессах без секретов. Произвольных входных манифестов, активов, удаленных артефактов и параметров выпуска нет.

При подготовке инструментов macOS без секретов один раз установите `rustfmt` и `clippy`, объявленные в `rust-toolchain.toml`, затем выполните тесты допуска архива. Регрессионные тесты обновления с тестовыми ключами также проверяют подготовку и допуск без использования или проверки закрытых производственных ключей.

Пакеты производственной приемки, исходные манифесты, подписи, appcast и приложения остаются на одноразовых runner и не загружаются. Ограниченный сборщик загружает только явно разрешенные журналы, записи статуса, идентичности и хешей и отклоняет подписанные вложения в областях результатов. Совпадение производственных ключей, проверку подписи, фактическую установку и ручную приемку рабочего стола фиксируйте отдельно. macOS использует нативный Apple Silicon и фактические проверки `SUPublicEDKey`; тесты Windows Server не заменяют ручную приемку Windows 11. Этот процесс не читает значения GitHub Secrets локально и не разрешает выпуск.

`prepare-release.py --require-update-signature` останавливается при отсутствии любого ключа, подписи или метаданных нативного архива. `publish-release.py` независимо повторно проверяет манифест, ленту того же кандидата и архивы перед загрузкой. Подписи, appcast и вложения статуса полностью входят в SHA256SUMS. Не добавляйте и не заменяйте эти вложения в уже опубликованных выпусках.

<a name="xdzip-independent-cli-attachments"></a>

## Независимые вложения CLI

Начиная с v0.2.0 полные выпуски дополнительно содержат `xdzip-cli-<version>-windows-x86_64.zip`, `xdzip-cli-<version>-macos-arm64.tar.gz` и `xdzip-cli-<version>-linux-x86_64.tar.gz`. Все три получены из нативных сборок и проверок CLI одного коммита и сохраняют рабочие процессы, фактические зависимости среды выполнения и уведомления; идентичность должна соответствовать чистой сборке Release. Обычный CI не получает разрешения развертывать или загружать пакеты приложений Mac.

CLI использует `cli-release.json` и `cli-release.json.sig`. Манифест имеет schema_version=1, product=xdzip и component=cli. version, channel, build, tag, commit и repository точно совпадают с манифестом настольного приложения. Активы содержат только эти три цели с теми же полями, что и активы приложения. Тип пакета Mac — tar.gz; минимальная система Linux не включает display_server. Остальные требования к системе, архитектуре, размеру и дайджесту сохраняются. Фиксированный издатель по-прежнему xiaodaozhi/xdzip.

Настольный release.json по-прежнему содержит ровно шесть типов пакетов без component и записей CLI. Старые клиенты игнорируют новые независимые вложения.
