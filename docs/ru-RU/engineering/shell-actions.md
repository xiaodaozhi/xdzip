# Действия файлового менеджера и автономное окно задач

[English](../../engineering/shell-actions.md) | [简体中文](../../zh-CN/engineering/shell-actions.md) | [繁體中文](../../zh-TW/engineering/shell-actions.md) | [Français](../../fr-FR/engineering/shell-actions.md) | [Deutsch](../../de-DE/engineering/shell-actions.md) | [Español](../../es-ES/engineering/shell-actions.md) | [Português (Brasil)](../../pt-BR/engineering/shell-actions.md) | Русский

Системные точки входа передают выбранные объекты и действия настольному процессу в том же сеансе входа. В Windows 11 обычное установленное расширение находится в меню «Показать дополнительные параметры». Его класс COM предоставляет `IContextMenu` и `IExplorerCommand`. MSIX объявляет отдельный класс классического меню, а сборка Store также добавляет обработчик современного меню, как описано ниже. Файловый менеджер Ubuntu 24.04 использует расширение Nautilus 4.0. В macOS доступны подменю Finder Sync, команда «Службы» и автономное окно операции.

Фактическая проверка платформ и оставшаяся работа отслеживаются в [#270](https://github.com/xiaodaozhi/xdzip/issues/270). Возможности текущего исходного кода не добавляются задним числом к уже опубликованным файлам.

Реализация Finder Sync без платной учётной записи и её локальная проверка отслеживаются в [#273](https://github.com/xiaodaozhi/xdzip/issues/273). Apple предназначает Finder Sync для приложений синхронизации; проект принимает ограничение применимости к общему меню сжатия и не утверждает, что прошёл проверку App Store. Локальная подпись ad-hoc для целостности не требует платной учётной записи, Developer ID, App Groups или нотариального заверения и не предоставляет доверие издателя Gatekeeper. См. [документацию Apple по Finder Sync](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Finder.html).

## macOS Finder Sync

`Contents/PlugIns/xdzip-finder-sync.appex` — нативное расширение без связей с Qt, Rust и библиотеками форматов. Оно охватывает локальные каталоги Finder с наблюдаемым корнем `/`, обрабатывает только выбор Finder, никогда не обходит каталоги и не добавляет панели инструментов, значков состояния или задач синхронизации. Для одного обычного объекта доступны три действия создания, для нескольких — дополнительное создание ZIP для каждого. Четыре действия извлечения появляются, когда все объекты являются возможными архивами. Меню не создаётся при пустом выборе, нелокальном URL или более чем 128 объектах. Размеры нативного меню задаёт система; автономные операции используют общее окно обычной плотности.

Расширение читает только собственную конфигурацию JSON `xdzip/finder-sync.json` в каталоге Application Support пользователя. Она содержит расположение текущего приложения, переключатель, язык, версию регистрации и локально случайно созданный токен передачи. Размер ограничен 8 KiB, файл должен быть обычным, принадлежать текущему пользователю и иметь права 0600. Запись выполняется атомарной заменой; ссылки и чужая конфигурация отклоняются. Это не файл CFPreferences. Песочница разрешает временное исключение только на чтение этого конкретного файла, без общего доступа к каталогу пользователя, App Groups или сетевого слушателя. Пути разрешений должны начинаться с `/`; см. [спецификацию временных исключений Apple](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/AppSandboxTemporaryExceptionEntitlements.html).

Finder не сохраняет `representedObject` пунктов меню, поэтому расширение хранит ограниченный снимок выбора с монотонно возрастающими метками. Устаревшая метка не может ссылаться на новый выбор. Через явно указанную цель `NSWorkspace` расширение отправляет событие JSON в base64url по `xdzip-shell://v1/` приложению `Contents/Helpers/xdzip-shell-relay.app`; полагаться на аргументы запуска из песочницы нельзя. Relay — отдельное нативное приложение без Qt. Оно проверяет случайный токен в частной конфигурации текущего пользователя, URL, UUID, действие, пути и пределы JSON, сохраняет UUID и вызывает существующие частные точки входа файла запроса и единственного экземпляра. Ошибка допуска отображается системным сообщением. Токен не включается в файлы запросов, протокол настольного приложения или журналы продукта; внешние URL без правильного токена не выполняют файловые операции. URL служит только для локальной передачи.

Расширение находит содержащее его приложение по фиксированной структуре пакета, не читая внешние метаданные в песочнице. При каждом вызове relay повторно читает внешний `Info.plist` и проверяет идентичность продукта, `XdzipShellProtocol=1`, `XdzipFinderSyncProtocol=1` и допустимое имя исполняемого файла. Цели после отката или с несовместимым протоколом отклоняются. Загруженное старое расширение может временно сохранять меню, но relay должен отклонять нажатия; служба независимо проверяет собственный протокол.

Установленное приложение при первом запуске регистрирует свои appex и службу; пользователь должен отдельно включить расширение Finder в системных настройках. Переключатель настроек управляет обеими точками входа; язык приложения меняет только меню расширения, а название службы следует языку системы. Повторное сохранение настроек не регистрирует неизменённый appex заново и не отключает его от Finder: регистрация повторяется только при изменении хэша содержимого или её отсутствии. Отключение удаляет только регистрацию по точному пути этого приложения и сохраняет отключённую конфигурацию. Удаление старой копии не отключает конфигурацию более новой. Явно зарегистрированную сборку для разработки можно снова включить в настройках после отключения; незарегистрированная сборка автоматически не включается.

При обновлении Finder может удерживать старый экземпляр расширения. При необходимости отключите и снова включите принадлежащее приложению расширение в системных настройках; принудительно завершать Finder не требуется. Откат и удаление затрагивают только собственные регистрации и файлы и не меняют ассоциации по умолчанию. Положение службы определяет система; она может вывести команду на верхний уровень контекстного меню.

## Граница пакета Windows

Сборки MSIX объявляют обработчик классического `IContextMenu` через `desktop9:Extension` для пункта Windows 11 «Показать дополнительные параметры». Сборки Store дополнительно объявляют отдельный класс `IExplorerCommand` и `windows.fileExplorerContextMenus` для современного меню. Классы имеют разные идентификаторы и предоставляют только соответствующие интерфейсы меню. Сборки для сторонней установки объявляют только класс классического меню. Обычные установщики сохраняют существующее классическое меню. Файловые действия и проверка частного запроса общие для обоих вариантов меню.

`--msix-channel store|sideload` выбирает неизменяемый маркер канала и соответствующие объявления манифеста; по умолчанию используется `sideload`. Современные команды требуют зарегистрированной сборки Store в Windows 11, системный тип подписи собственного пакета которой равен `Store`. Ошибка определения подписи и подписи Developer, Enterprise или None скрывают современный пункт. Копия сборки Store с подписью Store остаётся сборкой Store даже при сторонней установке. Это политика канала сборки, а не утверждение о способе установки одинаковых подписанных байтов. См. [обсуждение ограничения Microsoft](https://github.com/microsoft/WindowsAppSDK/issues/4993).

Расширение определяет каталог пакета собственной DLL и регистрацию текущего пользователя, а не использует идентичность процесса Explorer. Перед каждым вызовом оно повторно проверяет регистрацию и shell-протокол исполняемого файла, затем активирует AUMID этого пакета. Отсутствующая или заменённая регистрация приводит к отказу. Язык и включение меню пакета хранятся в ключе семейства пакетов отдельно от метаданных обычной установки; приложение не записывает обычные COM-регистрации под идентичностью пакета. Регистрацией по манифесту и удалением управляет Windows. Фактические подпись Store, отображение в Explorer, обновление и сосуществование проверяются отдельно от самоподписанного тестового пакета. В Windows 10 нет современного меню Windows 11, и она не входит в текущую область поддержки.

[GetStagedPackageOrigin](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getstagedpackageorigin) сообщает происхождение подготовленного пакета, а не проверенный способ установки конкретным пользователем. Значение сохраняется для диагностики и не разрешает современное меню.

Для сравнения происхождения запустите следующую диагностику только для чтения в Windows, где целевой пакет зарегистрирован для текущего пользователя. Имя пакета приведено как пример; результатом должен быть новый файл JSON в `build/`. Диагностика записывает системный тип подписи, происхождение подготовленного пакета и анонимизированный хэш полного имени, отклоняя результат без единственной зарегистрированной версии. Сценарий — метка оператора и не доказывает канал установки. Ошибки запроса, неизвестные или одинаковые значения сами по себе не разрешают меню. Сертификаты, установка и системные настройки не меняются.

```powershell
python scripts/msix-origin-probe.py --name xdzip.Example --scenario store-install --output build/store-origin-observation.json
```

## Выбор и вывод

Подтверждение создания из файлового менеджера проверяет непосредственно подставленный исходный каталог или выбранное место назначения, не обращаясь сначала к каталогу загрузок по умолчанию. Это исключает несвязанные задержки разрешений macOS. При обычном создании из главного окна сохраняется место назначения по умолчанию.

Для создания доступны быстрые ZIP и 7z, создание с подтверждением и отдельный ZIP для каждого из нескольких выбранных объектов. Полное имя одного обычного файла сохраняется, например `a.txt.zip`; для папки используется `foo.zip`, а общий выбор в одном каталоге получает имя этого каталога. Общий выбор из разных каталогов открывает автономное окно создания для подтверждения назначения. Быстрое создание использует обычный уровень без шифрования и томов; коллизии обрабатывают обычные запросы о конфликте.

Действия извлечения показываются, когда каждый выбранный объект может быть архивом по поддерживаемому суффиксу или имени тома. Меню не анализирует содержимое. При фактическом открытии Rust определяет полную группу томов, содержимое и возможности формата. Идентичные полные группы источников выполняются один раз за пакет извлечения; непрозрачная внутрипроцессная метка группы содержит идентичности файлов и не является разрешением записи.

- Текущий каталог: каждый архив извлекается непосредственно в содержащий его каталог.
- Умный каталог: дополнительная папка не создаётся только если полный проверенный граф вывода имеет один каталог верхнего уровня, включая неявные каталоги. Файлы в корне или несколько объектов верхнего уровня требуют папку с именем архива. Внутренние каталоги не удаляются и не переименовываются.
- Каталог для каждого архива: всегда создаётся папка с именем архива. Она резервируется исключительно через удерживаемое разрешение назначения; существующие файлы, каталоги и ссылки не используются повторно. Выбирается новое нумерованное имя, например `name (2)`, максимум за десять тысяч попыток.
- Выбранный каталог: общее назначение выбирается в автономном окне извлечения. По умолчанию создаются каталоги для каждого архива, также доступны умное или прямое объединение.

Имена каталогов следуют правилам переносимых имён и суффикса `.app` из [контракта безопасного извлечения](../../engineering/zip-safe-extraction.md). Умное определение не разрешает вывод: каждая задача повторно проверяет назначение, источник, CRC или аутентификацию, конфликты и право публикации. Сбой отдельного архива следует существующей политике остановки этого архива, после чего координатор переходит к следующему.

## Процессы, запросы и окна

Частная точка входа настольного приложения — `--shell-request <request.json>`; она не является интерфейсом сценариев автономного CLI. Нативные расширения создают только манифест выбора и запускают настольную точку входа, не загружая Qt или библиотеки форматов. Манифест находится в частном каталоге `xdzip-shell-<32 случайные шестнадцатеричные цифры>`, созданном с исключительным доступом в системном временном каталоге; фиксированное имя файла — `request.json`. Windows перед записью устанавливает защищённый DACL для текущего пользователя и SYSTEM, POSIX использует каталог 0700 и файл 0600. Настольное приложение применяет общие средства Rust для отказа от перехода по ссылкам и проверки корневого каталога, владельца и прав, читает не более 256 KiB и отклоняет ссылки, относительные пути, недопустимый Unicode, неизвестные действия и выбор более 128 объектов.

Запрос содержит схему 1, UUID, действие и абсолютные пути. Необязательный логический `archive_candidates` передаёт только уже доступные файловому менеджеру признаки MIME или UTI. Вместе с общими правилами суффиксов и томов он определяет видимость меню, но не разрешает ввод-вывод и не обходит проверку содержимого Rust. Windows читает зарегистрированный Content Type расширения, Nautilus — MIME FileInfo, помощник macOS — Content Type URL; архивы в файловом менеджере не разбираются. Протокол единственного экземпляра сохраняет существующие операции открытия и CLI и добавляет структурированный `shell_action`; допуск и успешное выполнение оцениваются отдельно. Приложение хранит не более 128 идентичностей допущенных запросов. Одинаковые идентичность и содержимое принимаются один раз; одинаковая идентичность с другим содержимым отклоняется. После допуска удаляются только фиксированный файл и пустой каталог, без рекурсивной очистки внешних входных данных.

Холодный запуск из файлового менеджера создаёт только `ShellHost`, а не скрытое главное окно. Обычное открытие файла или явный показ главного окна создаёт окно просмотра по требованию. Получив shell-действие, существующий экземпляр не переключает вкладки и не восстанавливает скрытое главное окно. Сеанс операции занимает существующую ограниченную позицию сеанса; пакет последовательно повторно использует контроллер, не создавая страницу просмотра для каждого архива.

`OperationTasks` использует общие окна прогресса, результата, пароля и конфликта для просмотра и автономных операций. Окно верхнего уровня `OperationWindow` может не иметь владельца; при наличии владельца оно следует вызывающему окну, иначе ограничивается выбранным экраном. Модальные запросы принадлежат фактическому окну операции; подтверждение выхода повторно использует `OperationConfirmationWindow`. Требования к компоновке, общим элементам, двуязычности и доступности определены в [процессе визуального проектирования](../visual/design-workflow.md).

В macOS идентичность единственного экземпляра использует текущего пользователя и фактический идентификатор сеанса входа Security framework. При ошибке запроса выбор экземпляра отклоняется, а не полагается на переменные окружения, которые могут отсутствовать у помощников. Поэтому обычный запуск, Finder relay и службы обращаются к экземпляру того же сеанса входа; см. [SessionGetInfo](https://developer.apple.com/documentation/security/sessions).

Создание и извлечение из файлового менеджера повторно используют представления прогресса и результата `TaskWindow`. Пакет показывает фактический статус и ошибку каждого элемента в общей компоновке; ошибка до отправки без квитанции задачи создаёт только представление результата, а не вымышленную задачу. Окна shell центрируются в доступной области текущего экрана, запросы сохраняют фактическое вызывающее окно. Классический вход Windows запрашивает поддерживаемое системой размещение `Position=Top`, чтобы находиться перед «Открыть с помощью», даже если Explorer добавляет этот пункт после динамического запроса меню. Корень и перечисленные действия используют значки приложения, форматов и системных папок; их размеры контролирует Windows.

## Завершение пакета и выход

Каждый пакет записывает фактические успехи, ошибки, отменённые и невыполненные элементы и устранение повторных групп томов. Ошибка отдельного элемента не останавливает остальные; отмена останавливает последующие элементы и передаёт существующий запрос отмены подготавливаемой или выполняемой задаче. Уже опубликованный вывод сохраняется; полный откат пакета не обещается. Подготовка, ожидание пароля, конфликты, отмена и очистка учитываются в глобальной активности и барьере выхода.

Если автономное окно создания не получило квитанцию задачи, отклонение отправки сохраняет входные данные, параметры и ошибки для исправления и повтора, не создавая конечное состояние задачи и не расходуя индекс пакета. Быстрые действия не имеют окна настроек; ошибка отправки записывается, после чего пакет продолжается.

Успешное создание из файлового менеджера не отправляет запрос открытия в приложении; для извлечения «открыть папку после завершения» по умолчанию выключено. Успешные автономные результаты остаются доступны для открытия назначения пользователем. Завершение не перехватывает фокус. Намеренно закрытое окно может снова открыть результаты пакета через вход задач. При отключённом трее или потере его хоста закрытые результаты остаются скрытыми. Видимое или свёрнутое главное окно предоставляет вход задач; без него восстанавливаются только скрытые активные задачи. При доступном трее или главном окне прогресс можно закрыть без остановки работы; без обоих сначала предлагается выбор ожидания или отмены. Когда доступных окон, трея и активных задач нет, перед выходом приложение ожидает завершения всех соединений Rust. Открытое окно настроек остаётся доступным, пока пользователь его не закроет.

## Установка и совместимость

Установленные версии включают интеграцию по умолчанию и позволяют отключить её в общих настройках. Регистрация управляет только собственными записями и не меняет ассоциации файлов по умолчанию. Переносные копии и сборки для разработки не регистрируются автоматически. Явные точки входа `--register-shell-integration` и `--remove-shell-integration` выполняют контролируемую регистрацию и удаление без показа главного окна.

Установщик использует точные команды синхронизации или удаления с одним аргументом и обновляет только собственные метаданные интеграции до освобождения стартовой блокировки транзакции установки. Для обычных файлов, shell-задач и запуска главного окна по-прежнему требуется допуск среды выполнения. Установленная идентичность Windows проверяет зарегистрированную идентичность продукта текущего пользователя, расположение установки и манифест файлов; переносной каталог не регистрируется автоматически даже при наличии манифеста развёртывания.

Перед передачей проверяется настольный протокол 1, чтобы всё ещё загруженное расширение не передало запросы старому приложению после отката. Windows читает ресурс версии GUI `XdzipShellProtocol` и проверяет, что собственная команда регистрации `Applications/xdzip.exe` указывает на тот же фактический файл; средство запуска ассоциации не заявляет поддержку протокола. После отката к старой версионированной структуре сохранённый новый исполняемый файл в корне больше не является shell-целью, а ассоциации по умолчанию не читаются и не меняются. Помощник macOS каждый раз повторно читает идентичность продукта, протокол и одно имя исполняемого файла из Info.plist цели вместо кэшированного состояния NSBundle. Пакет Ubuntu владеет `/usr/share/xdzip/shell-protocol`; откат к старому пакету и удаление убирают маркер. Отсутствующая, неизвестная, несовместимая или больше не зарегистрированная цель отклоняет запуск. Маркеры управляют только совместимостью передачи и не заменяют проверку запроса, содержимого Rust или назначения.

Windows хранит собственный CLSID и классическую команду в HKCU. Команда использует отдельную идентичность класса, чтобы старая фабрика классов в кэше Explorer не скрывала её при обновлении. Включение и отключение интеграции удаляет только соответствующий старый обработчик меню и собственный старый класс. После исторического отката, восстановившего этот обработчик, сохранённая новая команда скрывает себя, чтобы избежать дубликатов. Установщик сохраняет записи владения для удаления команды и её класса при откате. Каталог среды выполнения содержит DLL расширения с именем по хэшу содержимого и манифест проверки, чтобы не перезаписывать одноимённую DLL, загруженную Explorer при обновлении. Очистка старых файлов следует политике владения установщика и занятости без принудительного завершения Explorer. При первом обычном запуске установленное приложение macOS устанавливает собственную службу в Library/Services пользователя. Помощник только собирает выбор и передаёт его; отключение интеграции удаляет только проверенные собственные файлы, сохраняя дополнительное содержимое, ссылки и объекты с несоответствующим владельцем и сообщая о них. Видимость и включение службы контролирует система.

Нативное расширение Ubuntu регистрируется установочным пакетом в каталоге расширений Nautilus 4.0 и читает настройки того же пользователя. Запущенный файловый менеджер может удерживать старый модуль; для обновления откройте его заново без автоматического завершения. Автономный каталог среды выполнения не записывает данные в системный каталог расширений автоматически; установите компонент интеграции отдельно.
