# Сборки разработки и проверка платформ

[English](../../engineering/developer-build.md) | [简体中文](../../zh-CN/engineering/developer-build.md) | [繁體中文](../../zh-TW/engineering/developer-build.md) | [日本語](../../ja-JP/engineering/developer-build.md) | [한국어](../../ko-KR/engineering/developer-build.md) | [Français](../../fr-FR/engineering/developer-build.md) | [Deutsch](../../de-DE/engineering/developer-build.md) | [Español](../../es-ES/engineering/developer-build.md) | [Português (Brasil)](../../pt-BR/engineering/developer-build.md) | Русский

Это единая точка входа для подготовки, сборки, тестирования, пакетирования и проверки сред на трех платформах. Общая координация реализована в [scripts/desktop.py](../../../scripts/desktop.py). Документы платформ дополняют устройство развертывания, поведение инструментов и ограничения системы, не поддерживая отдельные обычные команды.

Автономная CLI использует `python3 scripts/cli.py build`, `test` и `package` без Qt, X11 или графического сеанса. Для компиляции Linux также нужны `libssl-dev pkg-config`; при выполнении используются системные OpenSSL и сертификаты. Сборки приложения автоматически создают приватный каталог CLI. Команды, установка и границы доверенных обновлений описаны в [контракте CLI](command-line.md).

Сборки разработки остаются экспериментальными и не являются официальными установщиками Release. Возможности и ограничения приведены в корневом [README](../../../README.ru-RU.md), поддерживаемая область — в [политике поддержки](support-policy.md). Историческая проверка выпуска `v0.1.0` находится в [#4](https://github.com/xiaodaozhi/xdzip/issues/4) и [#53](https://github.com/xiaodaozhi/xdzip/issues/53); будущие версии требуют новых записей проверки конкретных кандидатов.

## Среда и точки входа

Сначала установите Python 3.10 или новее, Git, CMake 3.24 или новее, Ninja, rustup и компилятор/SDK платформы. Версия Rust берется из корневого rust-toolchain.toml; Qt зафиксирован на 6.8.2. Правила зависимостей и обновлений см. в [политике инструментов](toolchain.md). Выполняйте команды из корня репозитория. В Windows замените `python3` в примерах доступным `python` и используйте среду разработки MSVC x64.

## Локальные каталоги инструментов

При загрузке среды PowerShell Visual Studio сохраняйте значения Unicode переменных `USERPROFILE`, `LOCALAPPDATA` и `APPDATA` и восстанавливайте их, если загрузчик изменил кодировку. Qt использует эти расположения для стандартных путей кэша и настроек, поэтому поврежденные значения могут вызвать ошибки файловой системы даже при работающем компиляторе.

`prepare` собирает и проверяет в существующем SDK QtNetwork с исправлениями безопасности для CVE-2026-116337 и CVE-2026-105946; перестроенная библиотека не заменяет другие модули выполнения. Также нужны Perl, make (nmake в Windows) и консольный инструмент OpenSSL. Ubuntu требует `zlib1g-dev libpcre2-dev libicu-dev libglib2.0-dev libzstd-dev libkrb5-dev`. Исходный код, созданные объявления и кэш сборки остаются в `build/`, по умолчанию повторно используется `build/toolchain/qt-network-security/<platform>`. При несовпадении digest входов и фактической библиотеки сборка продукта и пакетирование немедленно завершаются ошибкой; повторите `prepare`. Происхождение, ABI, работу TLS и восстановление см. в [примечаниях сопровождения исправления](../../../patches/qt/README.md).

Локальные зависимости единой точки входа используют только `build/toolchain/`, игнорируемый Git и не включаемый в коммиты:

| Содержимое | Фиксированный каталог | Примечания |
| --- | --- | --- |
| Qt SDK 6.8.2 | `build/toolchain/Qt/6.8.2/<platform-subdirectory>` | `<platform-subdirectory>` — `macos`, `msvc2022_64` или `gcc_64`; qmllint, qmake, конфигурация CMake и runtime Qt берутся отсюда |
| Среда инструментов Python | `build/toolchain/desktop-tools` | Фиксированное виртуальное окружение для aqtinstall и сценариев пакетирования и проверки |
| Подготовка загрузок Qt | `build/toolchain/qt-install-tool` | Только загрузки и временные входы установщика Qt |

`scripts/desktop.py prepare --install-qt`, `doctor`, `build` и `test` по умолчанию используют эти общие расположения. Не создавайте отдельные `.cache/Qt`, `.cache/desktop-tools` или подобные копии для каждого конвейера разработки. Явно задавайте `--qt-prefix`, `--qt-root` и `--tools-dir` только для изоляции разных версий Qt, платформ или экспериментальных сборок. CI может явно направлять их во временные каталоги runner, но резервные пути CI не меняют локальные значения по умолчанию. CMake, Ninja, rustup, Rust и компилятор C++ платформы принадлежат инструментам хоста и устанавливаются или вызываются согласно предварительной проверке среды, а не копируются каталогом инструментов Qt.

После цикла разработки и очистки веток и worktree удалите временные каталоги и файлы, созданные этим циклом в `build/`. Сохраните пригодные для повторного использования общие инструменты вроде `build/toolchain/`; удалите сборки, диагностику и подготовленные загрузки конкретного цикла. Правила и ручной резервный способ см. в [управлении содержимым и историей репозитория](../../../developers/engineering/repository-hygiene.md#研发周期工件收尾).

| Платформа | Системная среда, которую нужно подготовить сначала | Подкаталог Qt SDK |
| --- | --- | --- |
| macOS | Нативный терминал Apple Silicon, Xcode Command Line Tools и действительный macOS SDK | macos |
| Windows | Инструменты C++ MSVC 2022 x64 и Windows SDK, x64 Developer PowerShell/командная строка | msvc2022_64 |
| Ubuntu 24.04 | Компилятор C++ x86_64, пакеты разработки OpenGL/EGL/xkbcommon и библиотеки выполнения X11 | gcc_64 |

В macOS `xcode-select --install` подготавливает инструменты командной строки. Базовые пакеты разработки Ubuntu включают `libgl1-mesa-dev libegl1-mesa-dev libxkbcommon-dev libx11-dev libxext-dev libnautilus-extension-dev pkg-config`; для пакетирования также нужны patchelf, binutils (readelf и strip) и инструменты пакетов Debian, а для изолированной проверки выполнения — доступный Docker. Установка Visual Studio в Windows без входа в среду разработки может оставить cl, link, rc или dumpbin недоступными; предварительная проверка выявляет фактически отсутствующие инструменты. Общая точка входа не устанавливает автоматически системные компиляторы, SDK или системные пакеты, требующие прав администратора.

Разработчики Windows могут подготовить инструменты по [бесплатному пути лицензии Community](windows-licensing.md), прочитав и приняв условия данной версии. Только Build Tools или VC_redist не подтверждают право использования. Корпоративное использование и связанное перераспространение на стандартных runner GitHub имеют отдельное публичное разрешение; сопровождающим не нужно покупать Enterprise для размещенных сборок или устанавливать локально Community IDE, и это разрешение не распространяется на собственные машины. Для проверки лицензии необязательно удалять существующие инструменты 2019; совместимость локальных альтернатив с текущим SDK выпуска 2022 проверяется отдельно.

Все команды используют общие параметры:

| Параметр | Значение по умолчанию и назначение |
| --- | --- |
| `--qt-prefix` | Сначала `XDZIP_QT_PREFIX`, иначе `build/toolchain/Qt/6.8.2/<platform-subdirectory>`; указывает префикс SDK, не bin |
| `--build-dir` | `build/desktop`, каталог сборки и тестов CMake |
| `--output-dir` | `build/package`, каталог поставляемых артефактов и результатов проверки |
| `--tools-dir` | `build/toolchain/desktop-tools`, изолированные инструменты Python и материалы подготовки |
| `--configuration` | `Release`; можно явно выбрать другую конфигурацию разработки |

build-dir и output-dir должны быть независимыми подкаталогами внутри build/ репозитория согласно границам вывода пакетирования и проверки. Сохраняйте одни параметры на этапах одного запуска. Явный `--qt-prefix` имеет приоритет над переменной окружения; глобальное изменение CMAKE_PREFIX_PATH не требуется. Точка входа подготавливает среду поиска Qt и инструментов для подпроцессов. Обычные запуски приложения не должны наследовать переменные внеэкранных тестов. Созданные данные находятся только в игнорируемых build/, target/, dist/ или кэшах инструментов и не коммитятся.

## Выполнение по этапам

Этапы выполняются независимо и не повторяют неявно предыдущую подготовку, сборку или тестирование. Отсутствующие предварительные условия вызывают ошибку; выполните соответствующий этап и повторите попытку. Каждый этап заранее проверяет нужную среду; `doctor` показывает проблемы без сборки или пакетирования.

Защищенные сборки Windows координируют процессы в своей существующей консоли. Разные консоли могут работать параллельно; сборки в одной существующей консоли выполняются последовательно. Во время сборки другой код не должен отсоединять защищенные процессы от этой консоли или присоединять их обратно. Временная консоль, созданная процессом без консоли, предназначена ему и его дочерним процессам; внешние процессы не должны подключаться. Старые сценарии используют общую резервную блокировку для консолей без дескриптора окна и не могут координироваться с новыми; не запускайте новую сборку в той же консоли без окна до завершения старой. Если списки процессов определить невозможно, остановитесь без изменения кодовой страницы.

Для неинтерактивной сборки можно явно использовать обертку независимой консоли с полностью перенаправленными stdin, stdout и stderr. Пример PowerShell:

```powershell
New-Item -ItemType Directory -Force build\isolated-logs | Out-Null
cmd /c "python scripts\windows_detached_console.py --timeout 7200 -- python scripts\desktop.py build <NUL >build\isolated-logs\desktop.log 2>&1"
$LASTEXITCODE
```

Обертка создает отдельную скрытую консоль для каждой команды и завершает дочерние процессы при тайм-ауте или выходе супервизора; отсутствие сигнала завершения вызывает ошибку. Параллельным сборкам по-прежнему нужны отдельные значения `--build-dir`; обертка не блокирует каталоги сборки. Существующие проверки зависимостей desktop-build и `windows_ninja_safety.py` продолжаются, но обертывание других команд не добавляет их автоматически. Эта точка входа предназначена только для неинтерактивных команд; запросы ввода, пароли и взаимодействие с псевдоконсолью не поддерживаются.

`prepare` проверяет текущий перечень источников форматов продукта. ZIP, TAR/GZIP, 7z, RAR, CAB и оптические контейнеры используют независимый Rust; официальный список исходных кодов продукта пуст, официальные движки UnRAR/7-Zip не загружаются и не компилируются. Независимые эталоны тестов подготавливаются из собственных зафиксированных источников и отделяются от зависимостей выполнения продукта. Исходные уведомления для ограниченных сопоставлений RAR остаются в пакетировании и материалах соответствующего исходного кода; см. [лицензионный контракт](licensing.md). `build` использует только подготовленные данные и не загружает плавающие версии. Для тестов только Rust сначала соберите `xdzip-native-codec`, направьте `XDZIP_NATIVE_CODEC` на этот рабочий процесс и выполните тесты рабочей области. Поток нативного обработчика дополнительно выполняет `cargo test -p xdzip-runtime --locked native_backend_tests -- --ignored`; оба единый `test` и Foundation CI требуют его. Статус ignored не означает успешной проверки формата. Источники, разрешение потоков и лицензионные границы описаны в [контракте нативного обработчика](native-codecs.md).

| Команда | Назначение и предварительные условия |
| --- | --- |
| `doctor --for-stage build` | Проверка PATH, зафиксированного Rust, Qt, компилятора, SDK и версий; по умолчанию проверяется среда сборки |
| `prepare` | Подготовка общих инструментов и зависимостей; загрузка и установка Qt, Rust и материалов пакетирования требуют явных переключателей ниже |
| `build` | Настройка и сборка реального продукта, тестов и диагностики; нужна подготовленная среда, незафиксированные изменения допустимы |
| `test` | По умолчанию запускает тесты рабочей области Rust, qmllint и CTest; нужна завершенная сборка той же конфигурации, незафиксированные изменения допустимы |
| `package` | Развертывает runtime, собирает материалы лицензий и происхождения, проверяет развертывание и создает выбранные артефакты; нужны чистый исходный код, квитанции сборки и тестов одного коммита и инструменты пакетирования |
| `verify` | Проверяет существующий runtime или пакет без пересборки, установки продукта и изменения стандартных ассоциаций; нужны артефакт и среда проверки платформы |

Предварительная проверка различает отсутствующие необходимые инструменты, несовпадение версий и инструменты, ненужные текущему этапу; отсутствие Docker или Inno Setup не блокирует обычную сборку разработки. Проверка пакетирования действительно проверяет вызов Rust/Cargo и метаданные заблокированных зависимостей, чтобы проблемы PATH или кэша не обнаруживались только при сборе лицензий. Неудачные команды и пределы проверки остаются в локальном или CI-выводе; частичное завершение не объявляется успехом.

Сначала подготовьте зафиксированные инструменты Qt и Rust:

```sh
python3 scripts/desktop.py prepare --install-rust --install-qt --qt-root build/toolchain/Qt
python3 scripts/desktop.py doctor --for-stage build
python3 scripts/desktop.py build
```

`--install-rust` использует установленный rustup для подготовки инструментария, закрепленного репозиторием; сам rustup не устанавливается. `--install-qt` явно загружает зафиксированный Qt SDK по умолчанию в `build/toolchain/Qt`. Существующий SDK не нужно загружать снова; передавайте его путь каждому этапу:

```sh
python3 scripts/desktop.py doctor --qt-prefix build/toolchain/Qt/6.8.2/gcc_64
python3 scripts/desktop.py build --qt-prefix build/toolchain/Qt/6.8.2/gcc_64
```

После сборки явно подготовьте публичные тестовые данные для полного набора `native_backend_tests`. Фикстуры CAB, ISO/UDF и базового RAR хранятся в исходном коде проекта в `tests/fixtures/cab-iso/` и `tests/fixtures/native-archives/`. Тесты 7z создают свои архивы новым рабочим процессом Rust. Этому набору выполнения не нужны официальные инструменты 7-Zip/UnRAR или смонтированные образы; другие эталоны совместимости Foundation следуют [контракту нативного обработчика](native-codecs.md).

Для первого получения зафиксированных публичных входов RAR PPM, старых паролей и других явно выполните:

```sh
python3 scripts/prepare-rar-rust-fixtures.py --output build/native-test-inputs
```

При наличии зафиксированного кэша, проверенного по размеру и SHA-256, явно используйте автономный режим, заменив путь к кэшу и сохранив структуру подкаталога `junrar/` манифеста:

```sh
python3 scripts/prepare-rar-rust-fixtures.py --output build/native-test-inputs --archives /path/to/fixed-rar-cache --offline
```

Зафиксированные источники и уведомления находятся в `scripts/rar-rust-fixtures.json` и его публичном перечне совместимости. Вывод `sources.json.environment` использует пути относительно корня исходного кода. Текущая поставка соответствующего исходного кода не содержит эти семь публичных файлов кэша; Cargo `--offline` их не предоставляет. Подготовитель не экспортирует переменные окружения оболочки. Перед полным `test` запустите дочерний процесс со следующей явной передачей:

```sh
python3 -c "
import json, os, pathlib, subprocess, sys
root = pathlib.Path.cwd()
worker = pathlib.Path(sys.argv[1]).resolve(strict=True)
prepared = json.loads((root/'build/native-test-inputs/sources.json').read_text(encoding='utf-8'))
environment = os.environ.copy()
environment.update({name: str(root/value) for name, value in prepared['environment'].items()})
environment.update(XDZIP_NATIVE_CODEC=str(worker), XDZIP_NATIVE_CODEC_WORKER=str(worker), XDZIP_CAB_BACKEND='rust')
environment['XDZIP_RAR_FIXTURE_PASSWORD'] = 'password'
subprocess.run([sys.executable, 'scripts/desktop.py', 'test', *sys.argv[2:]], env=environment, check=True)
" build/desktop/tools/native-codec/xdzip-native-codec
```

В Windows добавьте `.exe` к пути рабочего процесса. При собственном SDK, build-dir или tools-dir добавьте те же параметры после пути, например `--qt-prefix /path/to/Qt/6.8.2/gcc_64`, и измените путь на фактический каталог сборки. `XDZIP_CAB_BACKEND=rust` выбирает фиксированную проверку Rust CAB; `password` — существующее публичное тестовое значение фикстуры, передаваемое только тестовому потомку. Эта передача сохраняет стандартные тесты рабочей области и полный ignored-набор; она не загружает данные и не собирает процесс неявно.

`test` включает внеэкранный и программный режимы только для потомков и не загрязняет последующие команды приложения. При обычных изменениях пересобирайте и проверяйте по влиянию. Для проверки только ядра Rust можно выполнить `cargo test --locked` затронутого крейта без Qt. `test --skip-rust` запускает qmllint и Qt CTest, но пропускает рабочую область Rust и полный набор тестов нативного обработчика; квитанции отмечают Rust как `not-run`. Если нужен вывод о Rust, выполните его отдельно и запишите фактические результаты.

Тесты браузера можно запускать непосредственно или группами через существующую точку входа набора. Каждый процесс создает уникальный короткий временный корень в `build/test-tmp/` проекта. При выходе после уничтожения тестовых объектов и до уничтожения приложения Qt он восстанавливает TEMP, TMP и TMPDIR и выполняет очистку. Стандартные файлы настроек также изолированы. Unix проверяет длину в байтах временного корня и существующего имени IPC относительно фактической емкости sun_path. Слишком длинный путь явно нарушает предварительное условие фикстуры; сократите путь checkout, а не выходите за пределы проекта и не меняйте IPC продукта. Вспомогательные процессы группы наследуют временный корень родителя для сохранения идентичности каталога IPC единственного экземпляра, используют приватные предварительные проверки и завершаются до очистки родителя. Разные группы не разделяют корни. Потомки перезапуска языка и режима открытия, которым явно передана тестовая конфигурация, продолжают ее разделять вместо новой пустой. Перед запуском действительно проверьте создание дочерних файлов, блокировки, временное размещение, атомарные фиксации и чтение настроек. Ошибка сообщает `Fixture precondition` и ненулевой код выхода; не пропускайте тесты и не ослабляйте проверки скрытия окон. Наличие каталога и QTemporaryDir::isValid сами по себе не доказывают возможность записи, а системные права не меняются для прохождения фикстур.

Пути тестовой конфигурации используют ограниченное сохранение/восстановление `tests/test_environment`. Windows сохраняет значения широких символов и различает неустановленные и явно пустые записи в системном блоке окружения; Unix сохраняет исходные байты окружения. Установщик CRT MSVC удаляет пустые значения, поэтому нативный блок восстанавливается отдельно. Проверяйте наличие пустого значения через processValue помощника или QProcessEnvironment, не обещая различие пустого/null в CRT Qt. Этот помощник ограничен главным потоком последовательного теста: устанавливайте до создания соответствующих движков/рабочих процессов и восстанавливайте после их уничтожения/соединения. Он не предназначен для кода продукта или одновременных изменений окружения. ASCII, китайские и непредставимые в ANSI символы требуют проверки реальных файлов по исходному пути, потомков восстановления языка и сохранения окна/черновика при ошибке. Автоматические результаты остаются отдельно от реальных действий человека в настройках.

Реальный продукт называется `xdzip` на всех платформах. Стандартные точки входа сборки:

| Платформа | Точка входа |
| --- | --- |
| macOS | `build/desktop/apps/desktop/xdzip.app/Contents/MacOS/xdzip` |
| Windows | `build/desktop/apps/desktop/xdzip.exe` |
| Linux | `build/desktop/apps/desktop/xdzip` |

Пример компонентов `xdzip-ui-preview` не предназначен для приемки реальных файлов. При изменении build-dir измените пути. Идентичность фактической сборки записывает версию, канал, коммит и наличие изменений. Модули и низкоуровневая диагностика CMake описаны в [приложении Qt для разработки](../../../apps/desktop/README.md).

## Генерация шрифтов интерфейса

`prepare` устанавливает зафиксированные FontTools/Brotli в общую среду инструментов и кэширует upstream-шрифты интерфейса, проверенные по хэшу. Каждая сборка приложения автоматически собирает каталоги поддерживаемых языков и постоянный текст QML/C++ и создает подмножества шрифтов в `<build-directory>/generated/fonts/`. Добавление символов не требует коммита двоичных шрифтов. После подготовки сборки работают без сети; отсутствие или повреждение кэша явно вызывает ошибку. Прямые сборки CMake должны выбрать эту среду через `Python3_EXECUTABLE`.

Предпросмотр только HTML, автономный экспорт, ручной импорт исходных материалов и проверка шрифтов описаны в [общем руководстве по шрифтам](../../../design/assets/fonts/README.en.md). Пакетирование проверяет манифест шрифтов соответствующей сборки продукта без повторной генерации. Постоянный текст интерфейса и выбор системного шрифта для пользовательских данных сохраняют свои роли.

## Пакетирование и проверка

`test` и `package` проверяют квитанции сборки, отпечатки исходного кода, конфигурацию, идентичность SDK и реальные файлы продукта. После изменений исходного кода или конфигурации сначала пересоберите. Перед пакетированием зафиксируйте поставляемый код, затем соберите и протестируйте чистый коммит. package не должен обходить проверки, игнорируя изменения, меняя идентичность артефакта или повторно используя старые отчеты. Лицензионные материалы, метаданные Rust и фактическая версия CLI должны соответствовать этому коду. Инструменты платформы проверяют ограничения использования и перезаписи существующих каталогов пакетов. Для пересобранных кандидатов предпочитайте новый output-dir, чтобы не смешивать старые файлы.

В Windows/Linux подготовьте инструменты пакетирования и выполните единые этапы:

```sh
python3 scripts/desktop.py prepare --packaging
python3 scripts/desktop.py doctor --for-stage package
python3 scripts/desktop.py build
python3 scripts/desktop.py test
python3 scripts/desktop.py package --kind all
python3 scripts/desktop.py verify --kind all
```

`prepare --packaging` подготавливает изолированные зависимости проверки Python, зафиксированные тексты лицензий и кэш схем, а также материалы пакетирования платформы; Windows включает зафиксированные CRT и Inno Setup. Разработчики по-прежнему сначала устанавливают системные инструменты. `package --kind runtime` подготавливает только развернутый каталог выполнения и материалы аудита. Затем в том же output-dir можно выполнить `package --kind installer` для создания установщика из проверенного runtime; Linux также создает tar.gz с сохранением прав исполнения. `--kind all` — стандартное значение, выполняющее оба действия одной командой. Пакетирование Windows использует Release или RelWithDebInfo без развертывания библиотек Qt Debug. Windows предоставляет развернутый каталог и пользовательский установщик; Linux — каталог выполнения, tar.gz и .deb. Проверке Windows нужны исполняемый тест браузера той же конфигурации и данные Qt Test/внеэкранных тестов. Проверке Linux нужен m2-flat.zip, созданный тестами сборки. Тестовые файлы не входят в каталог продукта. verify `--kind runtime` проверяет runtime; стандартный `--kind all` проверяет выбранные результаты. Обычная проверка не устанавливает, не обновляет, не откатывает продукт и не меняет пользовательские ассоциации файлов.

Для DMG macOS требуется отдельно выбранная основная сборка с разрешением регистрации кандидатом обработчика документов, чтобы обычные копии разработки и тестов не попадали в «Открыть с помощью»:

```sh
python3 scripts/desktop.py prepare --packaging
python3 scripts/desktop.py build --build-dir build/desktop-dmg --macos-handler-rank Alternate
python3 scripts/desktop.py test --build-dir build/desktop-dmg
python3 scripts/desktop.py doctor --for-stage package --build-dir build/desktop-dmg
python3 scripts/desktop.py package --build-dir build/desktop-dmg --output-dir build/package-macos --kind all
python3 scripts/desktop.py verify --build-dir build/desktop-dmg --output-dir build/package-macos --kind all
```

Ранг обработчика обычной сборки macOS по умолчанию — `None`, пользовательские значения по умолчанию не меняются; `Alternate` выбирайте только для долговременного основного приложения или входа DMG. Локальный пакет macOS поддерживает только `all`, создавая DMG разработки arm64 с необходимой ad-hoc подписью целостности. verify проверяет перемещенные Cocoa/Metal и реальное извлечение. Обычная CI не должна запускать пакетирование Mac или развертывать, подписывать, сжимать или загружать пакет приложения; исключение выделенного Release описано в [протоколе выпуска](release-protocol.md). Полные ограничения и сопровождение регистрации копий см. в [руководстве развертывания Mac](macos-deployment.md).

Устройство и базовые инструменты описаны в [развертывании Linux](linux-deployment.md), [DMG Mac](macos-deployment.md) и [установке и ассоциациях](installers-associations.md). Установщики Windows/Linux не подписаны официально; macOS не имеет подписи Developer ID и нотариального заверения. Диагностируйте проблемы установки и выполнения на реальном продукте с соответствующей проверкой платформы; работа под SDK не доказывает проверку автономного пакета.

## Связь с CI

Перед коммитом или push выполните локальные сборки или проверки, соответствующие изменению. Для документации запустите `python3 scripts/check-docs.py` и проверьте затронутые созданные результаты. Для Rust проверьте форматирование и как минимум соберите или протестируйте затронутые крейты. Тесты изолированных обработчиков форматов подготавливают фактический рабочий процесс и необходимые фикстуры, как описано выше. Изменения C++, моста и QML требуют сборки затронутого продукта через `python3 scripts/desktop.py build` и соответствующих тестов. Не каждое изменение требует всей проверки совместимости форматов или десяти повторов полного набора браузера.

При добавлении или изменении окна QML запустите `python3 scripts/check-window-contracts.py --self-test`, `python3 scripts/check-operation-components.py` и затронутые регрессии компоновки на двух языках и с несколькими размерами шрифта. После сборки `python3 scripts/desktop.py test --skip-rust` запускает полные проверки компонентов Qt и CTest. Либо после настройки путей SDK Qt и внеэкранной среды выполните соответствующие случаи через существующие точки входа, например `ctest --test-dir build/desktop -R qt_task_components --output-on-failure`. Изменения радиокнопок и флажков также запускают соответствующие регрессии QAccessibleActionInterface, например `accessibleRadioActionsCommitSelection` и `accessibleCheckboxActionsCommitIntent`.

[Обычная CI](../../../.github/workflows/docs.yml) выполняет только легкие статические проверки и не заменяет локальные сборки продукта. [Foundation](../../../.github/workflows/foundation.yml) и [workflow Qt](../../../.github/workflows/qt-components.yml) запускаются вручную по запросу. Qt использует тот же desktop.py для сборок, тестов Qt и пакетирования и проверки выполнения Windows/Linux. [ci-desktop.ps1](../../../scripts/ci-desktop.ps1) сохраняет проверки повторений, визуальные, совместимости и совместимости установки по запросу и не обязателен для обычной локальной проверки.

Исторические полные циклы продукта, реальной установки с обновлением/откатом и ассоциаций выполняются только на одноразовых хостах CI Windows/Linux или в изолированных контейнерах; единая точка входа не делает их стандартным поведением обычного локального verify. Задача macOS в workflow Qt по запросу использует аудит развертывания в режиме SDK и проверки запуска Cocoa и открытия файлов, сохраняя только журналы и JSON. Все проверки и границы свидетельств приведены в [политике CI](../../../developers/engineering/ci-policy.md).

## Границы файлов и задач

Открытие позволяет только просматривать и не извлекает автоматически. Для обычных одноименных файлов доступны вопрос, пропуск, переименование и явная замена. Публикуйте файл целиком только после проверки содержимого и синхронизации. Отмена до фиксации или ошибка записи сохраняет старый файл; уже зафиксированные извлеченные элементы остаются. Закрытие окна задачи только скрывает сведения. При выходе используются решение по активным задачам и асинхронный барьер завершения.

ZIP может восстанавливать относительные символические ссылки и биты исполнения при ограниченных условиях POSIX, но не биты привилегий, расширенные атрибуты или исходное время изменения. Это не подтверждает установку пакета приложения или проверку подписи. Источник и назначение должны удовлетворять [контракту безопасного извлечения](zip-safe-extraction.md). Временные данные после сбоя только сообщаются и сохраняются для проверки; неизвестное содержимое не восстанавливается и не удаляется автоматически.

## Экспериментальная сборка Windows MSIX

MSIX повторно использует сборку приложения Windows Release, тесты и проверенный каталог выполнения одного коммита. Завершите `prepare --packaging`, `build` и `test` как выше, затем выполните с теми же параметрами:

```powershell
python scripts/desktop.py package --kind runtime
python scripts/desktop.py package --kind msix --msix-name xdzip.Development --msix-publisher 'CN=xdzip development' --msix-publisher-display-name xdzip
python scripts/desktop.py verify --kind msix
```

Пример идентичности предназначен только для локальной разработки. Имя пакета, издатель и отображаемое имя официальной идентичности Store должны совпадать с Partner Center. Вывод `build/package/xdzip-windows-x64.msix` — неподписанный экспериментальный пакет, не являющийся автоматически пригодным для распространения через sideload или сертифицированным Store. Обычный sideload требует подписи, доверенной устройством и соответствующей издателю. Ограниченный режим неподписанной разработки Windows 11 дополнительно требует определенного OID издателя и для исполняемого содержимого обычно прав администратора; пример идентичности этим требованиям не соответствует. Сценарии не создают сертификаты, не подписывают, не устанавливают и не отправляют в Store. Технический минимум — Windows 10 22H2 x64, что не расширяет обязательства поддержки платформ. Версия `1.0.<product build>.0` отделена от отображаемой; политику версий Store нужно пересмотреть до исчерпания номеров сборки.

Для сборки необходимы чистый исходный код, соответствующие квитанции сборки/тестов, полностью проверенный каталог выполнения и MakeAppx и MakePRI Windows SDK. Сценарии повторно проверяют runtime и маркеры возможностей обновления, ассоциаций и меню, создают манифест и ресурсы значков в отдельной временной области, сравнивают каждый файл пакета и записывают хэши. Существующие пакеты и временные области не перезаписываются. Манифест объявляет существующие расширения из реестра форматов, точку входа приложения с полным доверием и классы меню по каналам.

Значки приложения включают варианты масштаба и точные целевые размеры в стандартной форме и без подложки для темного и светлого фона. MakePRI индексирует ресурсы в `resources.pri`, чтобы Windows выбирала нужный размер без системной подложки. Ассоциации файлов объявляют отдельный логотип формата и повторно используют PNG-кадры 16–256 пикселей существующих Windows ICO без изменения изображения, видимого размера, полей и положения. Политика ресурсов — [msix-icons.json](../../../specs/visual/msix-icons.json). Это ресурсы установленного пакета; логотипы страницы Partner Center отдельны. `verify --kind msix` сверяет новые квитанции значков с реальным пакетом, включая размеры, полный набор вариантов, канонические изображения форматов и наличие индекса ресурсов. Установленные пользователи получат изменения только после сборки и доставки обновленного пакета.

Пример использует стандартный `--msix-channel sideload`, регистрирующий только классическое меню Windows 11. Для загрузки в Store используйте `package --kind msix --msix-channel store` с точной идентичностью Partner Center. Объявляются современное и классическое меню; современный пункт скрыт до появления фактической системной подписи Store у пакета. Маркеры канала добавляются при пакетировании и не требуют пересборки проверенного runtime. Держите результаты в отдельных каталогах. См. [политику каналов меню](shell-actions.md#граница-пакета-windows). Лицензирование, реальная установка, ассоциации, удаление, подпись Store и фактическая приемка на целевой системе отделены от успеха пакетирования.

Манифест MSIX объявляет десять языков общего реестра в соответствии со встроенными каталогами; квитанции записывают и проверяют список. Этот процесс MakeAppx не превращает автоматически ресурсы переводов Qt в объявления языков пакета. «Языки, поддерживаемые пакетом» Partner Center отражают загруженный пакет; после исправления исходного кода нужно пересобрать и заменить пакет черновика. «Дополнительные языки страницы Store» настраиваются отдельно и не заменяют объявления манифеста. См. [документацию Microsoft о языках манифеста](https://learn.microsoft.com/windows/apps/design/globalizing/manage-language-and-region).

## Свидетельства и повторная проверка

Выбирайте затронутые проверки по [общей проверке](../../../developers/qa/README.md) и [проверке приложения по запросу](../../../developers/qa/private-test-manual.md); обычная работа не требует формы ручной приемки. Квитанции сборки и тестов — `desktop-build.json` и `desktop-test.json` в build-dir. Квитанции подготовки, пакетирования и проверки — `<stage>.json` в output-dir со ссылками на исходные свидетельства. Автоматические квитанции записывают реальные этапы и источники. Внеэкранный и программный рендеринг, нативные проверки Cocoa и выполненные ручные проверки записываются отдельно и не заменяют друг друга. Существующая приемка остается в [#5](https://github.com/xiaodaozhi/xdzip/issues/5) и не повторяется только из-за повторного создания перечня кандидатов.

Поставка артефактов Windows/Linux включает исходный код и уведомления лицензий одного коммита; Actions хранит артефакты 14 дней. После истечения срока пересоберите их по идентичностям и зафиксированным входам. deployment-audit.json и перечни CycloneDX по источникам/файлам помогают проверке происхождения, но могут быть неполными и не подтверждают одобрение лицензий. О пересборке исходного кода и замене Qt см. [поставку исходного кода](source-delivery.md) и [контракт автоматической проверки](../../../developers/engineering/candidate-verification.md).

Сборки, снимки экрана, измерения, отчеты и пакеты остаются только игнорируемыми локальными или CI-артефактами. Не описывайте созданные ожидающие формы, внеэкранные проверки или частичные SBOM как успешную проверку чистой среды и полного условия выпуска.

## Фреймворк обновлений macOS

Нативные сборки используют `prepare-sparkle.py` для подготовки `build/toolchain/Sparkle/2.10.0-xdzip-proxy.2`. Основная библиотека фреймворка компилируется из зафиксированного upstream-кода и исправления прокси; помощники установки, ресурсы и инструменты подписания сохраняют происхождение официального SDK. См. [контракт зависимостей](dependencies.md#macos-更新提供者). Действительные квитанции сборки можно использовать повторно; старый официальный SDK не заменяет производный фреймворк с интерфейсами прокси. CI может явно выбрать временный каталог SDK.

`python3 scripts/prepare-sparkle.py --output build/toolchain/Sparkle/2.10.0-xdzip-proxy.2` использует нативный Clang существующих Xcode Command Line Tools или Xcode и не требует отдельного SDK Qt. Оригинальные архивы SDK и исходного кода кэшируются в `build/source-cache/`; для автономной работы можно отдельно передать `--archive` и `--source-archive`. Сборка не выполняет сценарии загруженного кода, не изменяет системные прокси, не обращается к производственным ключам подписи и не собирает архивы поставки исходного кода проекта.

`check-macos-proxy.py` по умолчанию проверяет только собственный загрузчик по loopback. `--system-conflicts` ограничен одноразовыми размещенными runner Apple Silicon в выделенном workflow. Ограниченный помощник подготавливает, восстанавливает и проверяет настройки системного прокси и hosts фиксированных тестовых доменов. Не добавляйте этот флаг локально.
