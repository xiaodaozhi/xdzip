## Пробное использование внешнего SDK

Независимый пробный хост повторно использует зафиксированные serde 1.0.229, serde_json 1.0.154, sha2 0.10.9, getrandom 0.4.2, libc 0.2.190 и tempfile 3.27.0 без добавления сторонних версий или библиотек форматов и CBOR. Крейту протокола нужен только std; ограниченный CBOR проекта взаимодействует с независимым участником на стандартной библиотеке Python согласно RFC 8949. Хост не связывается с Qt, не входит в состав зависимостей выполнения приложения или CLI и не меняет материалы официального выпуска.

tempfile переводится из существующего lockfile в прямую зависимость испытания для хранения проверенной приватной копии исполняемого файла вместо поддержки общей реализации временного каталога. Безопасный вывод по-прежнему использует xdzip-io; tempfile не дает разрешения на фиксацию. Источник — [Stebalien/tempfile](https://github.com/Stebalien/tempfile), лицензия MIT или Apache-2.0. Стандартные функции и фактический состав зависимостей цели, включая fastrand, getrandom, once_cell и rustix/windows-sys, следуют Cargo.lock и метаданным и повторно используют зафиксированные версии без загрузки сценариев сборки и добавления библиотек C. Сохраняются существующие использование, источники и лицензии базовых библиотек; исторический запрос уведомлений не считается новым выводом о безопасности. Тесты и условия описаны в [испытании SDK](sdk-trial.md). Windows явно отказывает в выполнении без реализации AppContainer.

Доступ к элементам пакета повторно использует точно допущенные версии cap-std/cap-fs-ext 4.0.3 и существующие функции, открывая каждый компонент без перехода по ссылкам относительно удерживаемых каталогов. Это предотвращает гонки между проверкой строк и повторным открытием по путям окружения. Оба сохраняют существующие происхождение безопасного ввода-вывода, лицензии MIT или Apache-2.0, транзитивные версии и нативное поведение; новая сторонняя версия не добавляется.

## Интерфейс CLI и HTTPS

CLI повышает заблокированный clap 4.6.7 до реальной зависимости интерфейса продукта, включая только std, help, usage, error-context, suggestions и string, без derive и цвета терминала. Добавляется ureq 3.5.1 с отключенными стандартными функциями, только с native-tls-no-default и socks-proxy и явным выбором NativeTls и системных корней доверия. Стандартное декодирование GZIP, cookies, помощники JSON, внешний curl и сетевые зависимости выполнения Qt не вводятся. serde, serde_json, zeroize, sha2, getrandom и привязки платформы повторно используют зафиксированные версии.

ureq и ureq-proto происходят из [algesten/ureq](https://github.com/algesten/ureq), выбрана лицензия MIT. Основные транзитивные входы — native-tls 0.2.18, ureq-proto 0.7.1, http 1.5.0 и httparse 1.10.1. Полный состав версий, функций и зависимостей целей определяется Cargo.lock и метаданными Cargo с фильтрацией по хосту. Windows использует schannel 0.1.30; macOS — security-framework 3.7.0 и системные фреймворки; Linux — openssl 0.10.82/openssl-sys 0.9.118 и системный OpenSSL 3. Типы der/PKI RustCrypto поддерживают только общую оболочку TLS и не интерпретируют форматы архивов.

Сборки Linux Native TLS находят системный OpenSSL через pkg-config без включения, загрузки или компиляции частной копии. Mac и Windows используют системный TLS. Необходимые сценарии сборки Cargo, нативное связывание, условия целей и известные уведомления проверяются для фактических зафиксированных версий; записи запросов остаются локальными или CI-артефактами, сводки помещаются в issue CLI. Один запрос без совпадений не дает постоянной гарантии безопасности. Собственная FFI CLI для терминала, сигналов и запросов к ОС ограничена адаптерами платформ; ошибки приводят к отказу операции, контейнеры паролей сохраняют требования обнуления.

Уведомления пакетов собираются отдельно из обычных зависимостей CLI и рабочего процесса; зависимости сборки, разработки и proc-macro исключены из доказательств атрибуции выполнения. Атрибуция выполнения приложения добавляет корень CLI. Только публичный загрузчик Windows статически связывает CRT компилятора, чтобы точка входа запускалась до загрузки версионированных локальных DLL приложения. Фактические полезные данные и рабочие процессы продолжают включать зафиксированный runtime VC++ и исходные лицензии без графических библиотек SDK. Материалы реального выпуска по-прежнему требуют проверки происхождения зависимостей, сохраненного статического и динамического машинного кода и лицензионных обязательств.

При первом добавлении зависимости запишите назначение, альтернативы, версию, источник, лицензию, транзитивные зависимости, функции, поведение нативной сборки, известные уязвимости и поддержку. Имя крейта само по себе не завершает допуск. Не указывайте вымышленные проверенные версии.

| Возможное направление | Необходимая проверка |
| --- | --- |
| Реализация ZIP на Rust | Store/Deflate, ZIP64, CRC, дубликаты, исходные байты имен, отмена, приемник вывода хоста |
| Реализация TAR + GZIP на Rust | Потоковый индекс, метаданные PAX/GNU, отказ ссылок и устройств, неизвестные размеры, поврежденные потоки |
| cxx | Владение, согласованность генератора, кроссплатформенная статическая связка ядра, отсутствие исключений через границы |
| Модули Qt | Фактические зависимости выполнения и транзитивные зависимости, заменяемое развертывание, лицензии и каналы обновлений безопасности |
| Набор значков | Явная лицензия на перераспространение, согласованная толщина линий, доступность и учет ресурсов |

Порядок проверки: минимальная совместимость → вредоносные или усеченные данные → отмена и ограничения ресурсов → лицензии/SBOM → чистая сборка → запись решения. Не обходите защиту путей хоста общим распаковыванием библиотеки.

Рабочая область приложения Rust включает Cargo.lock в Git. Новые нативные библиотеки и сценарии сборки с загрузкой по сети требуют отдельной проверки; неиспользуемые функции отключаются. Если поддержка зависимости прекращена или уязвимость не исправлена, решение об обновлении, замене или отключении функции принимается по фактической достижимости с записью причины.

## Метаданные обновления и проверка подписи издателя

`xdzip-update` — независимое от Qt ядро для манифестов, каналов и проверки подписей; продукт вызывает его через отдельную границу cxx. Инструменты выпуска и помощники установки применяют те же правила. Используйте безопасный `VerifyingKey::verify_strict` из `ed25519-dalek = 2.2.0`, отклоняйте слабые открытые ключи и проверяйте точные исходные байты. Не реализуйте арифметику подписей самостоятельно и не считайте TLS или SHA-256 подписью издателя. Upstream-функции fast, std и zeroize включены по умолчанию; batch, hazmat, legacy_compatibility, rand_core и PKCS#8 отключены. Инструменты выпуска импортируют только заданное владельцем начальное значение длиной 32 байта и не создают производственные закрытые ключи.

| Прямая или основная транзитивная зависимость | Точная версия | Источник, лицензия и назначение |
| --- | --- | --- |
| ed25519-dalek, curve25519-dalek | 2.2.0, 4.1.3 | [dalek-cryptography](https://github.com/dalek-cryptography/curve25519-dalek), BSD-3-Clause, операции Ed25519 и кривых |
| base64ct | 1.8.3, alloc | [RustCrypto/formats](https://github.com/RustCrypto/formats), Apache-2.0 или MIT, кодирование подписи, совместимое со Sparkle |
| sha2 | 0.10.9 | [RustCrypto/hashes](https://github.com/RustCrypto/hashes), MIT или Apache-2.0, хэши пакетов |
| semver | 1.0.28 | [dtolnay/semver](https://github.com/dtolnay/semver), MIT или Apache-2.0, ограниченный разбор версий продукта |
| subtle | 2.6.1 | [dalek-cryptography/subtle](https://github.com/dalek-cryptography/subtle), BSD-3-Clause, upstream-поддержка операций постоянного времени |
| zeroize | 1.9.1 | [RustCrypto/utils](https://github.com/RustCrypto/utils), Apache-2.0 или MIT, обнуление временных контейнеров закрытых ключей при выпуске |

serde 1.0.229 и serde_json 1.0.154 повторно используют заблокированные версии. Другие транзитивные зависимости следуют Cargo.lock и фактическому дереву функций, включая digest, block-buffer, crypto-common, generic-array, typenum, cpufeatures и макросы derive. Сценарий сборки curve25519-dalek обнаруживает только возможности локального компилятора; во время выполнения могут выбираться upstream-реализации для конкретного процессора. Он не загружает внешний код и не добавляет криптографическую библиотеку C/C++ или зависимость выполнения OpenSSL. Существующая сборка уведомлений и поставщиков включает эти пакеты по метаданным Cargo; фактическая атрибуция и лицензии пакета остаются предметом проверки материалов выпуска.

Системные криптографические API разделили бы правила проверки между тремя платформами, а внешняя CLI OpenSSL увеличила бы зависимости выполнения и границы аргументов, поэтому используется одно ядро Rust. Старый API Keypair из исторического [RUSTSEC-2022-0093](https://rustsec.org/advisories/RUSTSEC-2022-0093.html) не используется. Исправленная граница curve25519-dalek по [RUSTSEC-2024-0344](https://rustsec.org/advisories/RUSTSEC-2024-0344.html) — 4.1.3; зафиксированная версия ей соответствует. Эти проверки не доказывают отсутствие уязвимостей во всех зависимостях; обновления продолжают проверять поддержку и уведомления.

Регрессии проверяют точные изменения байтов, недействительные подписи, неизвестные, повторные или слабые открытые ключи, пустой производственный набор доверия, резервный канал, привязку версии и сборки, комплектность шести пакетов и подписанные ленты. Временные ключи тестов существуют только в тестовом коде и изолированных артефактах, никогда в ресурсах доверия продукта. Нативная установка и результаты разных платформ записываются отдельно; тесты ядра на одной платформе не заменяют приемку установки.

## Идентичность источника Windows

M2 непосредственно использует безопасную обертку `file::information(&File)` точной версии `winapi-util = 0.1.11` во время выполнения Windows для сравнения серийных номеров тома и индексов файла. Длина и время изменения или создания не позволяют надежно обнаружить замену NTFS под тем же именем. Соответствующий API индекса файла стандартной библиотеки еще нестабилен, а написанный вручную Win32 unsafe расширил бы проверку. Уже заблокированная библиотека используется повторно без добавления версии пакета.

Источник — crates.io/[BurntSushi/winapi-util](https://github.com/BurntSushi/winapi-util), из двойной upstream-лицензии MIT или Unlicense выбирается MIT. Транзитивные зависимости Windows — зафиксированные windows-sys 0.61.2 и windows-link 0.2.1, обе MIT или Apache-2.0. Включены только объявленные upstream модули Win32, стандартные функции отключены, сценариев сборки, внешних нативных сборок и сетевых загрузок нет. Цели вне Windows не компилируют эту зависимость выполнения. Безопасная upstream-обертка заимствует действительный дескриптор File; ошибка системного вызова делает старый источник недействительным. Дескриптор не пересекает FFI, а проверка идентичности не разрешает безопасную запись.

Проверены происхождение версии, функции и поведение нативной компиляции; проверка типов цели Windows GNU прошла. Нативная регрессия Windows должна охватывать замену с тем же именем и размером при сохранении времени изменения. Upstream — небольшая безопасная обертка Win32; обновления ограничены lockfile и нативными регрессиями. Запрос OSV точных версий 2026-10-13 не обнаружил известных уведомлений для этих трех пакетов. Исторические ответы остаются в исходных артефактах выполнения; новые запросы фиксируют фактические ответы согласно [проверке](../../../developers/qa/README.md). Это не доказывает отсутствие уязвимостей. Пакеты разработки продолжают собирать все upstream-лицензии.

## Обработчики форматов Rust и общий мост рабочего процесса

`xdzip-codec-7z` использует API и домен проекта, общие алгоритмы сжатия без сторонних производственных зависимостей и общие криптографические примитивы. AES 0.9.3 включает zeroize; getrandom 0.4.2 и zeroize 1.9.1 повторно используют версии ZIP. SHA-256 с возможностью обнуления вынесен в независимый от форматов `xdzip-crypto`, который управляет собственным инкрементным состоянием на допущенном примитиве compress sha2 0.10.9 вместо дублирования оберток по форматам. Общий крейт также реализует HMAC-SHA256 и BLAKE2s/BLAKE2sp по публичным математическим спецификациям; источники и границы см. в его [README](../../../crates/xdzip-crypto/README.md). Он не дает полномочий на работу с архивами или публикацию и не обновляет сторонние криптографические версии. Атрибуты формата, композиция CBC, KDF, создание и перезапись реализованы независимо, а не предоставлены как обработка архивов базовыми библиотеками. Источники, роли анализа и различия лицензий см. в [основе 7z](sevenzip-format-sources.md).

Логика формата `xdzip-codec-optical` использует только стандартную библиотеку и API/домен кодеков проекта, без библиотек ISO/UDF или общих архивов. Спецификации, область и ошибки приведены в [контракте независимой реализации](independent-rust-codecs.md#iso与udf只读规格). `xdzip-codec-bridge` повторно использует заблокированные версии и генерацию cxx/cxx-build без новых внешних версий, скачивающих сценариев сборки или библиотек алгоритмов форматов. Замена маршрутизацией внутри процесса лишила бы существующего управления процессами оптических задач, поэтому рабочий процесс и протокол управляемых потоков сохраняются.

`xdzip-codec-cab` зависит только от API, домена и `xdzip-compression` проекта без сторонних производственных зависимостей. MSZIP повторно использует Deflate ZIP/GZIP; LZX и Quantum — независимые модули алгоритмов без дополнительной библиотеки Deflate или общих архивов. Обработчики 7z, CAB и оптических форматов разделяют `xdzip-codec-bridge` и потоки, разрешенные хостом. Создание добавляет только обратные вызовы управляемого ввода и случайного временного размещения без дублирования общих границ. Продукт использует Rust; официальный Cab и специфичные для CAB LZX/Quantum в сборки не входят. Ресурсы и форматы см. во [внутреннем контракте](independent-rust-codecs.md#cab只读规格), область анализа и лицензии — в [источниках CAB](cab-format-sources.md).

`xdzip-codec-rar` повторно использует тот же API кодеков, общие алгоритмы сжатия и криптографические примитивы, не вводя RAR или другие библиотеки архивов. Статистическая модель PPMd H общая для 7z и RAR; каждый формат определяет собственные диапазон, сброс и завершение. Особые сочетания совместимости со старыми паролями остаются в модуле RAR. Системный календарь и кодировки OEM/ANSI/локальная используют тонкие обратные вызовы рабочего процесса; Rust обрабатывает поля формата, усечение паролей и проверку. Qt не входит в логику форматов.

Политика производственных зависимостей проверяет обычные зависимости и зависимости сборки крейтов форматов и моста. Официальные контейнеры, алгоритмы и общие утилиты 7-Zip и UnRAR удалены из манифестов CMake продукта; список подготовки источников продукта пуст, резервного перехода при ошибке нет. Лицензионные обязательства прошлых поставок сохраняются. Независимый pycdlib, Microsoft IMAPI, фикстуры mkudffs/udfclient, официальные эталонные рабочие процессы и векторы спецификаций используются только в тестах; их источники и лицензии управляются отдельно и не входят в зависимости выполнения. Небольшие фиксированные собственные входы и генераторы версионируются в тестовых каталогах; развернутые образы и свидетельства выполнения остаются в build/.

## Шрифты и инструменты интерфейса

Используйте автономное переменное подмножество официального Noto Sans SC 2.004-H2 вместо резервных системных шрифтов устройства проверки. В [инвентаре материалов](../../../specs/dependencies/ui-font.json) указаны зафиксированный коммит Google Fonts, исходный хэш и рецепт генерации, авторские права и лицензия OFL-1.1. Сборки генерируют WOFF2 с насыщенностью 400–750 и нативный TTF из того же источника в каталоге сборки; репозиторий не хранит сгенерированные двоичные шрифты, внешние службы, транзитивные зависимости выполнения и нативная компиляция не требуются. Системные шрифты дают разные метрики текста на разных платформах, поэтому дизайн проверки включает шрифт. Каждая сборка проверяет покрытие текущего текста; нельзя предполагать совпадение неизвестных шрифтов сгенерированного дизайна. Upstream продолжает поддерживаться; пересматривайте зафиксированную версию при изменениях поддержки.

Статические проверки ресурсов приложения используют Pillow (HPND), FontTools (MIT), Brotli (MIT) и PyYAML (MIT) для проверки workflows; версии закреплены в [требованиях инструментов ресурсов приложения](../../../scripts/desktop-asset-requirements.txt) и устанавливаются в отдельный venv. Playwright (Apache-2.0) и Chromium применяются для локальной визуализации ресурсов по необходимости и не входят в исполняемый код продукта.

## Собственный ZIP и общие криптографические примитивы

Контейнеры ZIP, потоковое создание, обычная перезапись и оболочка AES используют [независимую реализацию Rust](independent-rust-codecs.md); Deflate/CRC-32 повторно используют `xdzip-compression`. `rawzip = 0.5.2`, `zip = 9.0.3` и `flate2 = 1.1.10` служат только эталонами разработки и тестов и не входят в производственные зависимости или зависимости сборки ZIP. Они не вызывают общее распаковывание и не разрешают произвольные пути. Лицензионные обязательства прошлых поставок с ними сохраняются.

Криптографические примитивы повторно используют точные версии существующих транзитивных зависимостей, повышенных до прямых: RustCrypto `aes = 0.9.3`, `hmac = 0.13.0`, `sha1 = 0.11.0`, `pbkdf2 = 0.13.0`, а также `getrandom = 0.4.2` и `constant_time_eq = 0.6.1`. PBKDF2 включает только hmac. SHA1 отключает стандартные alloc/oid и включает только zeroize; AES/HMAC также включают zeroize. Библиотеки форматов, нативные библиотеки сжатия и загрузки во время выполнения не добавляются. CTR, оболочка со случайной солью, разделение результатов вывода ключа, значения проверки пароля и аутентифицированный EOF реализованы проектом; общие примитивы не должны возвращать парсер ZIP.

Эти пакеты и транзитивные зависимости cipher/digest заблокированы в Cargo.lock и получаются из crates.io и upstream. AES/HMAC/SHA1/PBKDF2/zeroize/getrandom используют MIT или Apache-2.0; constant_time_eq использует CC0-1.0 или MIT-0 или Apache-2.0 согласно фактическим текстам закрепленных пакетов. Параметры SHA-1/PBKDF2 происходят из WinZip AES и не применяются к отдельно выбранной схеме хранения пользовательских паролей. Сценарии сборки выполняют только настройку платформы, без сетевых загрузок и компиляции C-декодера.

`zeroize` единообразно зафиксирован на 1.9.1 для функций очистки ключей AES 0.9.3. Контейнеры паролей хоста, нативного адаптера, обновления и проб используют одну версию вместо двух одной основной версии. Debug секретов остается скрытым; производные буферы и развернутые ключи используют поддерживаемое библиотеками обнуление по времени жизни без обещания стереть все исторические копии в памяти. Допуск включает lockfile, лицензии, фактическое дерево функций, тесты отказов и независимую совместимость с 7-Zip. Исходные ответы запросов уязвимостей остаются в артефактах сборки; успешный запрос без уведомлений не гарантирует отсутствие уязвимостей.

## WP-11 TAR/GZIP

Точно зафиксируйте [tar 0.4.46](https://docs.rs/tar/0.4.46/tar/) (crates.io, [upstream-источник](https://github.com/alexcrichton/tar-rs), MIT или Apache-2.0), отключив стандартную функцию xattr. Это только независимый эталон чтения и записи для разработки и тестов. Заголовки TAR, PAX, создание и перезапись продукта используют [независимый слой записей Rust](independent-rust-codecs.md), а не сторонний парсер или Builder TAR, общее распаковывание или восстановление владельца и прав. Производственные зависимости запрещают возвращение tar и filetime; лицензии тестов и прошлых поставок остаются. Кодирование явно записывает пути PAX UTF-8 и числа вне диапазона для совместимости имен между платформами.

GZIP использует независимую реализацию `xdzip-compression` без сторонних производственных зависимостей, включая Deflate RFC 1951, кадрирование RFC 1952 и CRC-32. Сжатый ввод и декодированный вывод подчиняются отмене и бюджетам байтов хоста. Полное декодирование проверяет CRC и ISIZE каждого элемента. `flate2` 1.1.10 — эталон разработки и тестов. ZIP и GZIP используют один собственный алгоритм Deflate. Маршрутизация выполнения различает [отдельный GZIP](single-file-streams.md), представляющий один логический файл, и [TAR.GZ](tar-gzip.md), представляющий дерево каталогов TAR.

Транзитивные зависимости тестов tar включают filetime 0.2.29 (MIT или Apache-2.0) с повторным использованием cfg-if и libc; filetime не входит в производственные зависимости кодека. Новых сценариев сборки с загрузкой, сетевых запросов во время выполнения и обработчиков форматов во внешних процессах нет. Существующий collect-notices.py собирает лицензии из lockfile; тестовый пакет в lockfile не означает, что продукт его связывает. Системный tar и tarfile Python используются только в тестах и не входят в зависимости выполнения.

Запрос OSV точных версий 2026-10-15 для tar 0.4.46, filetime 0.2.29 и flate2 1.1.10 не вернул уведомлений. Исходные ответы остаются только в build/review/wp11. Это не гарантия отсутствия уязвимостей. Двусторонняя совместимость, некорректные данные, квоты, отмена и проверка трех платформ должны быть действительно выполнены; свидетельства связаны из [контракта WP-11](tar-gzip.md).

## Производная QtNetwork с исправлениями безопасности

Динамическая библиотека Network приложения Qt 6.8.2 использует `6.8.2-xdzip-network.1`, применяя пять неизмененных официальных исправлений к зафиксированному архиву QtBase для CVE-2026-116337 и CVE-2026-105946. Область охватывает пределы приема строки состояния и заголовков HTTP/CONNECT и границы разбора аутентификации; QtCore, другие модули и плагины TLS не заменяются. Сохраняются существующие переключатели функций, экспортируемые символы и совместимость импорта с QtCore исходного SDK. Источники, порядок, хэши, лицензии, замена и проверка на реальных данных описаны в [примечаниях сопровождения](../../../patches/qt/README.md). В продукте сохраняется динамическое связывание LGPL-3.0. Исключительно GPL-тесты upstream не распространяются; OpenSSL 3.5.9 создает только объявления компиляции, новая криптографическая библиотека не собирается и не распространяется. Фактические происхождение пакета, уведомления и условия повторного связывания требуют отдельной проверки.

Linux также добавляет собственный модуль сохранения ABI с фиксированным digest, явно создающий экземпляры существующих констант встроенных типов SDK и сохраняющий исходный экспорт без нового сетевого поведения. Исходный код и уведомления Apache-2.0 сопровождают материалы. Пять официальных исправлений не изменены; библиотеки продукта других платформ не получают этот модуль.

## Определение и декодирование старых имен файлов
