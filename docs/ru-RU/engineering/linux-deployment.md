# Автономный каталог среды выполнения Linux и проверка

[English](../../engineering/linux-deployment.md) | [简体中文](../../zh-CN/engineering/linux-deployment.md) | [繁體中文](../../zh-TW/engineering/linux-deployment.md) | [日本語](../../ja-JP/engineering/linux-deployment.md) | [한국어](../../ko-KR/engineering/linux-deployment.md) | [Français](../../fr-FR/engineering/linux-deployment.md) | [Deutsch](../../de-DE/engineering/linux-deployment.md) | [Español](../../es-ES/engineering/linux-deployment.md) | [Português (Brasil)](../../pt-BR/engineering/linux-deployment.md) | Русский

Текущая база развертывания для разработки — Ubuntu 24.04, x86_64 и X11. Цель — запуск текущего продукта без SDK Qt для разработки; это не обещает поддержку других дистрибутивов, старых версий glibc, Wayland или полноценного установщика. CI macOS сохраняет нативные сборку, тесты и проверку запуска. Локальные DMG для разработки следуют [руководству по развертыванию Mac](macos-deployment.md) и не затрагиваются этим процессом.

<a name="xdzip-layout-and-generation"></a>

## Структура и создание

`scripts/deploy_linux.py` принимает только доверенные ELF-файлы проекта и явно указанный SDK Qt 6.8.2 и создает новый каталог build/ или dist/:

- `xdzip` — программа запуска, использующая локальные библиотеки, плагины и QML без наследования путей поиска SDK разработки.
- `bin/xdzip` — продукт; соседний `qt.conf` использует относительные пути Qt.
- `lib/` содержит фактически импортированные общие библиотеки Qt/SDK; `qml/` сохраняет стиль Basic Controls и необходимые подмодули реализации. Другие стили Controls, NativeStyle, Effects, варианты диалогов для отдельных стилей, файлы дизайнера и метаданные типов QML удаляются до сбора нативных зависимостей, поэтому их исключительные библиотеки не развертываются.
- `plugins/` содержит xcb, внеэкранную проверку, изображения, значки, ввод платформы, графическую интеграцию xcb и обязательный `tls/libqopensslbackend.so`; без OpenSSL backend развертывание завершается ошибкой. Плагины платформ EGLFS, framebuffer и Wayland не описываются как проверенная поставка.
- `translations/` сохраняет переводы стандартных элементов Qt; `share/notices/` поставляет текущие уведомления и материалы об исходных зависимостях.
- `share/deployment.json` записывает QML, системные зависимости среды выполнения, скопированные библиотеки SDK и границы; README.md содержит инструкции по использованию.

Сканер использует [qmlimportscanner](https://doc.qt.io/qt-6.8/qtqml-tooling-qmlimportscanner.html) зафиксированной версии Qt. Xdzip.Settings и Xdzip.Native — встроенные зарегистрированные модули; статические библиотеки разработки не копируются. Отсутствующие обычные зависимости, пути QML за пределами SDK, конфликты одноименных библиотек и неизвестные внешние библиотеки вызывают ошибку. Рекурсивный сбор нативных импортов копирует только библиотеки SDK, но не glibc или графические драйверы хоста; системные зависимости перечисляются по фактической принадлежности пакетам Debian.

Перед удалением сокращение проверяет скопированное дерево QML, необходимые плагины Basic, сохраненные сильные импорты и известные структуры стилей. Неожиданные ссылки, неизвестные стили или селекторы диалогов и сильные зависимости от исключенных модулей вызывают ошибку. Стандартные диалоги, методы ввода, доступность, плагины изображений, TLS и системные переводы сохраняют прежние правила. `share/deployment.json` записывает удаленные файлы QML и число байтов. Внутренний `cli/` использует общий `bin/xdzip-native-codec` через фиксированный контекстный путь; автономные пакеты CLI остаются самостоятельными.

Для HTTPS дополнительно необходимы Ubuntu `libssl3t64` и `ca-certificates`. Проверить принадлежность `libssl.so.3` и `libcrypto.so.3` системным пакетам и непустое системное хранилище доверенных CA. Qt OpenSSL backend может загрузить эти библиотеки во время выполнения, поэтому одного ldd недостаточно для подтверждения полноты зависимостей. Манифест развертывания записывает версии установленных бинарных пакетов, исходные пакеты и их версии. Установщики объявляют обе зависимости; SBOM фактических файлов записывает их как обязательные пакеты ОС, не включая системные библиотеки в приложение.

patchelf устанавливает относительный RPATH `$ORIGIN` в каждом ELF, вычисляя относительное расстояние каждого плагина до lib/. Перенаправление путей Qt следует [официальным правилам qt.conf](https://doc.qt.io/qt-6.8/qt-conf.html), позволяя перемещать весь каталог. Библиотеки остаются динамически связанными и заменяемыми; совместимая замена Qt не ограничивается. Общие границы приведены в [развертывании Qt в Linux](https://doc.qt.io/qt-6.8/linux-deployment.html).

После перезаписи относительного RPATH развертывание удаляет ненужные нативные таблицы символов и проверяет неизменность каждой записи DT_NEEDED и RPATH/RUNPATH. В `symbol_stripping` для каждого ELF записываются версия инструмента, хеши и число байтов до и после; входы SDK и исходные бинарные файлы сборки не изменяются. Для диагностической копии базовый скрипт развертывания принимает `--keep-symbols`. Окончательная атрибуция SDK и хеши приложения описывают преобразованные файлы. Это уменьшает размер пакета, но не подтверждает измеренное улучшение памяти или пропускной способности.

Для обычного создания и проверки используйте поэтапно [единый вход сборки](developer-build.md). Сначала завершите сборку, тесты и подготовку упаковки с одинаковой конфигурацией, затем выполните:

```sh
python3 scripts/desktop.py doctor --for-stage package
python3 scripts/desktop.py package --kind all
python3 scripts/desktop.py verify --kind all
```

Каталог сборки по умолчанию — build/desktop, вывод поставки — build/package, SDK Qt — `build/toolchain/Qt/6.8.2/gcc_64`; для других расположений передавайте общие параметры на каждом этапе. `package --kind runtime` создает каталог среды выполнения и материалы аудита; затем `package --kind installer` с тем же output-dir создает tar.gz и .deb. Значение `all` по умолчанию выполняет оба этапа по порядку. Нижележащие [deploy_linux.py](../../../scripts/deploy_linux.py), [package_linux.py](../../../scripts/package_linux.py) и [verify_linux_runtime.py](../../../scripts/verify_linux_runtime.py) сохраняют логику платформы; для устранения неполадок используйте их `--help`.

Развертывание выполняется только в нативном Linux x86_64 и не перезаписывает существующие каталоги. Предварительная проверка упаковки проверяет qmlimportscanner, ldd, patchelf, dpkg-query и необходимый установщику dpkg-deb; эти инструменты сборки не входят в продукт. Проверка среды выполнения в контейнере также требует Docker и доступный демон; сборки ограничены зафиксированным образом Ubuntu и записанными пакетами ОС. Отсутствие Docker не блокирует обычные сборку и тесты, но verify явно завершается ошибкой; невыполненная проверка изоляции не отмечается пройденной. Обычный verify не устанавливает .deb на хосте и не меняет ассоциации файлов; жизненный цикл установки проверяется в одноразовой среде CI.

<a name="xdzip-experimental-strict-snap"></a>

## Экспериментальный строгий Snap

Строгий Snap `core24` — отдельная экспериментальная поставка. Ограниченное приложение не наследует конфигурацию XKB хоста по пути `$SNAP/usr/share/X11/xkb`. Если программа запуска задаёт этот путь в `QT_XKB_CONFIG_ROOT`, Snap должен включать полное дерево XKB из зафиксированной среды сборки Ubuntu. Без него плагин Qt Wayland может загрузиться и подключиться к композитору, но при создании контекста клавиатуры возникнет ошибка пути включения `xkbcommon`. Сохраните уведомление об авторских правах `xkb-data` в пакете и запишите в отчёт кандидата версию пакета, детерминированный хеш каталога, число файлов и хеш уведомления. Проверьте готовый Snap после распаковки, затем отдельно выполните проверки запуска вне экрана и в Wayland. Они не заменяют проверку установки и взаимодействия в реальном сеансе рабочего стола строгого Snap.

<a name="xdzip-automated-evidence-without-the-sdk"></a>

## Автоматизированные свидетельства без SDK

Контейнер использует Ubuntu 24.04, зафиксированный по дайджесту, и устанавливает фактические зависимости ОС и поддержку тестирования Xvfb, шрифтов и локалей, но не Qt, Rust или компилятор, повторно проверяя их отсутствие. Он не монтирует SDK разработки или полное дерево исходников, а только каталог продукта только для чтения, отдельный принадлежащий проекту ZIP на 100 000 записей и скрипты проверки. Проверка выполнения архивов отключает сеть и повышение привилегий; запись разрешена только во временном каталоге конфигурации.

Смонтируйте приложение по новому пути с пробелами. После очистки переменных поиска разработки проверьте через программу запуска:

1. Фактическое выполнение `--version`.
2. Запуск и безопасное закрытие настоящего окна QML в X11.
3. Нативная проба продукта завершает первый кадр, чтение 100 000 записей, отмену активного запроса и выход; количества и результаты отмены соответствуют контракту.
4. После очистки переменных разработки хоста проверить все упакованные ELF в режиме развертывания без обращения к SDK. SBOM фактических файлов сохраняет ту же идентичность версии и коммита и проходит официальную схему.
5. Включить сеть в новом процессе того же образа без SDK, запустить `--update-probe` продукта с изолированным `XDZIP_SETTINGS_PATH` и действительно обратиться к GitHub по HTTPS. Он должен сообщить о доступном OpenSSL backend и завершить проверку обновления; отдельно сохранить `.https.json` и `.https.log`. Ошибки сети, сертификата или TLS блокируют проверку.

HTTPS-проба отдельно записывает OpenSSL backend, системный файл CA и фактические результаты запроса GitHub. Успешный реальный запрос сам по себе не доказывает проверку подписи или нативную установку обновления. Разбор подписи и процессы обновления без SDK проверяются [отдельным процессом регрессии обновлений](../../../.github/workflows/update-regression.yml); эти виды свидетельств не заменяют друг друга.

Сохранять исходные журналы и структурированные отчеты каждой попытки пробы как `.https.attempt-N.log` и `.https.attempt-N.json`, а также `.https.log` последней попытки. Отсутствующие или неверные отчеты, тайм-ауты и завершения процесса сохраняют статус ошибки. Повторять только тогда, когда контроллер продукта подтвердил ограничение частоты анонимного списка релизов GitHub и статус, этап запроса, заголовки ответа и диагностика полны. Дождаться срока сервера или применить ограниченную задержку с увеличением, не более трех попыток и 3 700 секунд общего ожидания, как в приемочной пробе macOS. Срок сверх оставшегося бюджета, прерванное ожидание или ошибка TLS, сети либо другая ошибка немедленно приводят к сбою. Для успеха проба должна завершить настоящий запрос обновления. Каждое решение об ожидании и фактическую длительность записывать в `.https-waits.json`.

Перед повторным использованием пути вывода переместить предыдущий отчет и журналы в каталог `.history` с именем отчета в том же родительском каталоге, выделив подкаталог для каждого запуска. Если новый запуск прервется ошибкой, старый успешный отчет не останется по текущему пути вывода и не вызовет путаницы; исторические артефакты можно проверять отдельно.

linux-runtime.json записывает фактические события и SHA-256 исполняемого файла. Программная отрисовка Xvfb/Qt Quick подтверждает только процесс выполнения, но не физический GPU, китайские окна кандидатов, настоящие программы чтения с экрана или полную установку рабочего стола.

<a name="xdzip-download-delivery-and-remaining-gates"></a>

## Поставка для загрузки и оставшиеся условия

CI создает xdzip-linux-x86_64.tar.gz и записывает SHA-256 и хеши исполняемого файла. tar.gz сохраняет права исполнения и предотвращает их потерю при распаковке ZIP в Actions. Пути архива, UID/GID и временные метки нормализуются без личных каталогов. После загрузки распаковать и выполнить `./xdzip` внутри каталога; нельзя переносить только bin/xdzip. Неупакованный каталог linux/ повторно не загружается.

Созданные здесь каталог среды выполнения `build/package`, tar.gz и .deb — экспериментальные материалы разработки, которые автоматически ничего не устанавливают и не меняют ассоциации по умолчанию. Официальные Ubuntu tar.gz и .deb для Release создает отдельный процесс Release и предоставляет согласно [протоколу выпуска](release-protocol.md). Область платформ определена [политикой поддержки](support-policy.md); другие дистрибутивы и рабочие столы, Wayland и связанные расширения требуют отдельных issue. Существующая приемка рабочего стола остается в [WP-12 #5](https://github.com/xiaodaozhi/xdzip/issues/5). Для последующих изменений повторно проверить затронутые реальные IME и программы чтения с экрана, а также чистую установку, обновление и удаление; одна лишь пересборка каталога не требует повторять существующую приемку. Историческая проверка компонентов `v0.1.0` приведена в [#4](https://github.com/xiaodaozhi/xdzip/issues/4) и [#53](https://github.com/xiaodaozhi/xdzip/issues/53); успешное выполнение из каталога не выполняет автоматически будущие условия выпуска.

Установка, обновление, откат и удаление Ubuntu .deb, блокировки выполнения и автоматизация MIME рабочего стола описаны в [установке и ассоциациях](installers-associations.md). Успех контейнера среды выполнения не заменяет реальные проверки рабочего стола или проверку лицензий для выпуска.
