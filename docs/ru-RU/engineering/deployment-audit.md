# Проверка зависимостей развёртывания и SBOM

[English](../../engineering/deployment-audit.md) | [简体中文](../../zh-CN/engineering/deployment-audit.md) | [繁體中文（台灣）](../../zh-TW/engineering/deployment-audit.md) | [日本語](../../ja-JP/engineering/deployment-audit.md) | [한국어](../../ko-KR/engineering/deployment-audit.md) | [Français](../../fr-FR/engineering/deployment-audit.md) | [Deutsch](../../de-DE/engineering/deployment-audit.md) | [Español](../../es-ES/engineering/deployment-audit.md) | [Português (Brasil)](../../pt-BR/engineering/deployment-audit.md) | Русский

По умолчанию проверка развёртывания создаёт материалы для проверки разработки с явной отметкой `incomplete`; она не доказывает автоматически готовность к выпуску. Официальный Release отдельно собирает материалы того же кандидата и предоставляет их с пакетом после проверки процесса выпуска. Формат использует [официальную схему CycloneDX 1.6](https://github.com/CycloneDX/specification/blob/55343ba19dee1785acf1ce9191540d5fd7b590db/schema/bom-1.6.schema.json). Исходный коммит и SHA-256 трёх файлов схемы зафиксированы в [конфигурации](../../../scripts/sbom-schemas.json). Проверка загружает и разбирает только эти ресурсы, кешируя их в build/; схемы по произвольным URL из SBOM не загружаются.

| Артефакт | Источник данных и назначение | Что не может доказать |
| --- | --- | --- |
| source-build.cdx.json | Граф зависимостей рабочего пространства Cargo для хоста, включая инструменты разработки и сборки; объявленные модули Qt; хеши исходников шрифтов и бренда | Что пакет Rust обязательно статически скомпонован с продуктом или все плагины Qt и встроенные сторонние компоненты идентифицированы |
| deployment-audit.json | SHA-256 файлов под указанным фактическим корнем артефакта, импорты нативных бинарных файлов, зависимости SDK, системы и неразрешённые зависимости, фактическая идентичность сборки CLI | Все динамические загрузки QML или плагинов по имени, чистую установку, системный ABI, подписи или соблюдение лицензий |
| artifact-files.cdx.json | Фактические артефакты и обнаруженные внешние файлы SDK, известные связи нативных импортов, привязанные к перечню исходников и версии, коммиту и состоянию dirty фактического исполняемого файла | Полную идентичность развёрнутых компонентов, атрибуцию статической компоновки, лицензии встроенных библиотек Qt или завершённый формальный SBOM продукта |
| Необязательные записи рабочего стола | Выполненные проверки рабочего стола и ограничения с учётом изменения и доступной среды | Невыполненные действия, другие платформы или одобрение выпуска |

Записи исходников не включают непрозрачные идентификаторы Cargo на основе путей и не выдумывают crates.io purl для пакетов рабочего пространства. Пути артефактов указываются относительно заданного корня или Qt SDK. Другие внешние зависимости определяются по хешу содержимого и имени файла без частных абсолютных путей SDK. Шрифты используют OFL-1.1; исходные материалы бренда сохраняют Apache-2.0 библиотеки ресурсов. Объявление модулей Qt не позволяет выводить лицензии всех фактически развёрнутых компонентов.

## Автоматизированная проверка

`deployment_audit.py` проверяет только явно указанные доверенные сборки проекта, а не архивы пользователей. macOS использует otool для импортов и RPATH; Windows использует MSVC dumpbin для обычных и отложенных импортов DLL; Linux использует ldd, который нельзя применять к исполняемым файлам неизвестного происхождения. Символическая ссылка файла, выходящая за указанный корень артефакта, приводит к ошибке проверки. Отчёты должны записываться вне корня, чтобы не включать собственный вывод в перечень.

- `--mode sdk` разрешает поиск во внешнем Qt SDK и явно показывает, что сборка не автономна. Неразрешённые импорты по-прежнему приводят к ошибке. Рекурсия охватывает артефакт и объявленный Qt SDK; другие внешние библиотеки записываются только по хешу и числу непросмотренных и не считаются проверенными как полное замыкание.
- `--mode deployed` запрещает внешние несистемные зависимости и неразрешённые импорты. В Windows импорты VC++, например MSVCP и VCRUNTIME, должны поступать из пакета; System32 компьютера разработчика не может скрывать отсутствие файлов. Системные UCRT и контракты API по-прежнему предоставляет система. Продолжайте нативные проверки запуска с очищенными путями поиска разработки Qt.
- Неразрешённые импорты, несоответствие версии, коммита или состояния dirty исходников и фактического бинарного файла, несовпадение хеша или формата официальной схемы и дублирующие или несуществующие ссылки на компоненты блокируют соответствующую проверку.
- Замыкание нативных импортов не заменяет покрытие плагинов, загружаемых по имени, или проверки на чистой машине. Успешные импорты из развёрнутого каталога Windows не являются приёмкой установщика.

Qt-процесс по требованию для трёх платформ сохраняет два файла cdx.json в корне и deployment-audit.json без автоматического создания пустых ручных форм. macOS читает только локально собранный .app и SDK; обычные проверки не запускают macdeployqt, не подписывают, не сжимают и не загружают пакеты приложений. Linux предоставляет Qt/QML/плагины через [независимый каталог среды выполнения](linux-deployment.md), используя проверку deployed и контейнер без SDK; загруженный tar.gz сохраняет исполняемые биты. Сейчас заявлена только база Ubuntu 24.04, x86_64, X11, а не универсальный установщик Linux.

Для доверенных собственных артефактов Windows отдельно извлеките установщик и сравните его каталог приложения с переносимым ZIP того же кандидата с помощью `python scripts/check-windows-package-payload.py --installer-app <extracted-app-directory> --portable <portable-package.zip> --output build/review/payload-comparison.json`. Проверяются хеши каждого файла, манифест установки и графические DLL SDK, которые нельзя включать. Путь вывода должен быть новым. Это статическое сравнение не запускает установщик или обновление и не заменяет фактическую проверку установки.

Локальный пример macOS после пересборки из согласованных исходников:

```sh
python3 scripts/collect-notices.py build/review/wp12/notices
python3 scripts/deployment_audit.py \
  --root build/ui/apps/desktop/xdzip.app \
  --app build/ui/apps/desktop/xdzip.app/Contents/MacOS/xdzip \
  --qt-prefix build/toolchain/Qt/6.8.2/macos --mode sdk \
  --output build/review/wp12/deployment-audit.json
python3 scripts/sbom.py \
  --audit build/review/wp12/deployment-audit.json \
  --source build/review/wp12/notices/source-build.cdx.json \
  --output build/review/wp12/artifact-files.cdx.json
```

После установки jsonschema==4.23.0 в изолированной среде проверки используйте её Python для запуска `scripts/validate-sbom.py` с двумя указанными файлами cdx.json. Использование реестра описано в [документации jsonschema 4.23](https://python-jsonschema.readthedocs.io/en/v4.23.0/referencing/). Инструменты проверки не развёртываются в продукте.

<a name="xdzip-attribution-results-and-verification-limits"></a>

## Результаты атрибуции и ограничения проверки

[Атрибуция фактических компонентов](runtime-attribution.md) интегрирована: SPDX SDK связывает фактические файлы, модули Qt и встроенные сторонние компоненты; поставляются официальные тексты лицензий с зафиксированными хешами; записываются различия хешей SDK и исходников и неподтверждённая атрибуция. Обычные кандидаты Rust для выполнения отделены от инструментов сборки, разработки и proc-macro. Новые связи компонентов привязаны к фактическому аудиту и объединены в SBOM артефакта, который по-прежнему явно неполон.

В установленном дереве свяжите каждую поставленную DLL, framework и плагин с исходным компонентом, версией, лицензией и соответствующим исходным кодом. Отдельно проверяйте встроенные компоненты Qt, атрибуцию статической компоновки Rust и происхождение инструментальной цепочки. Для решений по кандидатам используйте [руководство по проверке выпуска](../../../developers/qa/release-review.md).
