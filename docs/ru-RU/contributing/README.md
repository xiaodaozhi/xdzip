Прочитайте [правила участия](../../../CONTRIBUTING.md) и найдите или заведите задачу для изменения. Опишите ожидаемое поведение, затронутые платформы и небольшой проверяемый пример. Используйте тестовые файлы проекта или материалы, разрешённые к распространению. [Структура репозитория](../engineering/repository-layout.md) показывает, где находится каждая часть реализации.

<a name="xdzip-build-the-part-you-need"></a>

## Сборка нужной части

Выполняйте команды из корня репозитория. В Windows используйте `python` в среде разработки MSVC x64. В macOS используйте нативный терминал Apple Silicon и Xcode Command Line Tools. В Ubuntu следуйте списку зависимостей платформы. В [руководстве по сборке](../../engineering/developer-build.md#environment-and-entry-points) указаны необходимые компоненты и версии Rust и Qt, зафиксированные в репозитории.

Для первой сборки настольного приложения выполните следующие команды.

```sh
python3 scripts/desktop.py prepare --install-rust --install-qt
python3 scripts/desktop.py doctor --for-stage build
python3 scripts/desktop.py build
```

Параметры подготовки устанавливают зафиксированный набор инструментов через имеющийся rustup и при необходимости загружают требуемую версию Qt SDK. Если общие зависимости в `build/toolchain/` уже подготовлены, используйте их повторно. Если совместимый Qt SDK находится в другом каталоге, передавайте одинаковый `--qt-prefix` на нужных этапах. Когда изменение требует настольных тестов, запустите `python3 scripts/desktop.py test` для готовой сборки той же конфигурации. Для полного набора тестов рабочего процесса см. [подготовку входных данных](../../engineering/developer-build.md).

При работе с автономной CLI соберите и проверьте саму CLI и вспомогательный процесс.

```sh
python3 scripts/cli.py build
python3 scripts/cli.py test
```

Результат по умолчанию сохраняется в `build/cli`. Для сборки нужны зафиксированный набор Rust, CMake и инструменты C++ платформы. В Ubuntu также требуются `libssl-dev` и `pkg-config`. Сведения о платформах приведены в [спецификации сборки CLI](../engineering/command-line.md#xdzip-build-and-command-installation).

## Проверка затронутого поведения

Повторно используйте подходящую сборку, если она доступна. При изменении только документации начните с проверок ниже и проверьте вывод затронутых генераторов. Полная сборка настольного приложения нужна, когда её требует изменение или обязательная проверка.

```sh
python3 scripts/check-docs.py
git diff --check
```

| Изменение | Код и спецификация | Что запустить или проверить |
| --- | --- | --- |
| Документация и примеры | Обновите соответствующие переводы, ссылки и якоря. README в корне и `docs/` доступны на десяти языках. Руководства в `developers/` используют американский английский и упрощённый китайский. Сверьтесь со спецификацией и проверьте изменённые команды на небольшом собственном тестовом файле. | Запустите проверку документации выше. Откройте изменённые ссылки на разделы. Если страница служит входом генератора, проверьте результат генерации. |
| CLI | Начните с `crates/xdzip-cli` и проследите путь через общую среду Rust. [Спецификация CLI](../engineering/command-line.md) | Запустите проверки автономной CLI для своей сборки. Если изменились команды или вывод, проверьте stdout, stderr, код завершения и записанные файлы. Включите подходящий сценарий сбоя. |
| Предметная логика Rust, форматы или архивные задачи | Начните с `xdzip-domain`, нужного кодека, `xdzip-runtime` или `xdzip-io`. Для настольной команды проследите `BrowserController` и `RuntimeConnection`. [Реестр форматов](../engineering/format-registry.md), [среда выполнения](../engineering/product-runtime.md), [безопасность файлов](../design/file-security.md) | Запустите `cargo fmt --all -- --check` и тесты затронутых crate. Проверьте реальный путь выполнения и относящиеся к нему сбои, отмену и окончательную запись. Если используется нативный рабочий процесс формата, обратитесь к [точкам входа для его тестирования](../../../developers/qa/runtime-worker-tests.md). При изменении реестра запустите `python3 scripts/generate-format-registry.py`, затем ту же команду с `--check` и `python3 scripts/test-format-registry.py`. |
| Окна QML, элементы управления или локализация | Начните с `apps/desktop/ui`, `resources/i18n` и `specs/visual`. Перед редактированием окна прочитайте [визуальную спецификацию](../../visual/design-standard.md) и [порядок проектирования](../visual/design-workflow.md) и укажите контракт окна в [реестре окон](../../../specs/visual/window-registry.json). | Для изменений окон запустите `python3 scripts/check-window-contracts.py --self-test`, `python3 scripts/check-operation-components.py` и относящиеся к изменению тесты компоновки на двух языках и с несколькими размерами текста. Для локализации запустите `python3 scripts/check-ui-i18n.py`. Когда требуется, проверьте взаимодействие или отображение в нативной среде нужной платформы. |
| Установка, интеграция с оболочкой или обновления | См. [руководство по сборке и развёртыванию](../../engineering/developer-build.md), [спецификацию ассоциаций](../../engineering/installers-associations.md) и [спецификацию обновлений](../engineering/software-update.md). | Проверьте затронутый путь установки или регистрации, идентичность фактического пакета, ошибки и восстановление. По [правилам CI](../../../developers/engineering/ci-policy.md) выберите подходящий процесс для платформы. |

## Описание проверок

В PR укажите изменённое поведение, проверенные команды и платформы и оставшиеся проверки. Явно укажите результаты вне экрана, на нативном рабочем столе и при установке. В [руководстве по проверке](../../../developers/qa/README.md) описана область каждого результата. Спецификации подсистем находятся в [техническом справочнике](../reference/README.md), процедуры выпусков — в [руководстве сопровождающего](../../../developers/README.md).
