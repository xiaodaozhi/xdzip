# Fuentes correspondientes y materiales de recompilación

[English](../../engineering/source-delivery.md) | [简体中文](../../zh-CN/engineering/source-delivery.md) | [繁體中文](../../zh-TW/engineering/source-delivery.md) | [日本語](../../ja-JP/engineering/source-delivery.md) | Español | [Português (Brasil)](../../pt-BR/engineering/source-delivery.md)

**Límite de publicación, 2026-11-05:** Por decisión del propietario, este recopilador se usa solo para revisión local y verificación de recompilación. Los archivos de fuentes correspondientes ya no se ofrecen como recursos de GitHub Release ni como artefactos de Actions. Se retiraron los recursos históricos públicos de Release y los artefactos descargables de Actions de publicación que contenían esos archivos, y los futuros flujos de publicación rechazan su generación o subida. Esta decisión no modifica las licencias de los componentes ni demuestra que se cumplan las obligaciones de fuentes correspondientes, reenlace u otras. Las instantáneas de fuentes que GitHub genera automáticamente para etiquetas del repositorio público son distintas de esos adjuntos de Release.

La publicación y aceptación rutinarias no deben ejecutar este recopilador ni generar localmente archivos de fuentes correspondientes. Ejecútelo únicamente cuando el usuario solicite expresamente la recopilación de fuentes; la restricción de subida sigue vigente. La revisión de licencias debe identificar los componentes y obligaciones reales, sin considerar defectos confirmados las marcas genéricas de revisión generadas por máquinas.

scripts/prepare-source-delivery.py recopila las fuentes del proyecto desde un commit limpio, las entradas completas de Rust vendor correspondientes a Cargo.lock, archivos de fuentes fijados de módulos Qt 6.8.2 e instrucciones de recompilación y sustitución. Todas las salidas se encuentran en build/. Una dirección de descarga no es una fuente entregada y el recopilador no aprueba automáticamente una opción de licencia de código abierto.

```sh
python3 scripts/prepare-source-delivery.py --output build/review/source-delivery \
  --qt-prefix build/toolchain/Qt/6.8.2/macos
python3 scripts/verify-source-delivery.py --delivery build/review/source-delivery \
  --qt-prefix build/toolchain/Qt/6.8.2/macos --output build/review/source-rebuild
```

Los archivos de módulos de ejecución Qt son qtbase, qtdeclarative, qtsvg y qttranslations; también se entregan qtshadertools, qttools y los componentes fijados de fuentes de la biblioteca estándar de Rust necesarios para compilar, desde el [archivo oficial de Qt 6.8.2](https://download.qt.io/archive/qt/6.8/6.8.2/submodules/). Los valores oficiales .sha256 están fijados en scripts/corresponding-sources.json. Se vuelven a verificar la caché y las descargas; estas se escriben primero en archivos parciales y se confirman después de validarlas. Solo se inspeccionan los directorios de los archivos comprimidos; no se extraen automáticamente rutas de terceros. Cargo vendor usa --locked, conserva sumas del registro y dependencias de compilación, y no ejecuta scripts de compilación de terceros.

La entrega de fuentes incluye también la Public Suffix List editable fijada y su texto MPL-2.0. La recopilación verifica las identidades de entrada, archivo Qt y generador; después regenera y compara byte a byte los datos C++ y los datos binarios de prueba. Se detiene ante cualquier diferencia y no establece equivalencia completa del SDK ni aprueba la licencia de una publicación.

La entrega conserva la entrada fijada de Apache Tika, el NOTICE original y el texto OGL-UK-3.0 para los datos MIME de Qt Core. Verifica la atribución del archivo Qt y regenera sus datos MIME mediante el script de conversión del archivo fijado, permitiendo únicamente finales de línea nativos de Windows. El NOTICE completo de Tika cubre la distribución original más amplia y no implica que xdzip incluya sus demás dependencias.

La entrega contiene también las fuentes `common` de CLDR 46 y la licencia original usadas para generar configuraciones regionales de Qt 6.8.2, pero no el resto del árbol CLDR. La recopilación verifica la versión CLDR en dos archivos fuente generados de Qt, el hash del archivo original fijado y las entradas seleccionadas. El segundo paso de generación de Qt requiere además una tabla ISO 639-3 no incluida; `qt-cldr-sources.json` registra fuente, versión y resumen del candidato probado, y su [página de descarga y condiciones originales](https://iso639-3.sil.org/code_tables/download_tables) requiere revisión separada. Reproducir los datos generados con este candidato no establece la entrada histórica exacta ni la identidad completa de compilación del SDK original.

Excluir las tablas ISO originales no elimina todos los identificadores relacionados de otros datos CLDR. `common/validity/language.xml` de CLDR 46 conserva códigos de idioma compactos y `common/supplemental/supplementalMetadata.xml` contiene alias. En la [comparación local](https://github.com/xiaodaozhi/xdzip/issues/138#issuecomment-6588994510), un conjunto candidato de tres letras construido con estos archivos entregados cubrió 7.919 de los 7.920 valores `Id` de la tabla ISO candidata de CLDR 46 y tenía 338 valores adicionales. El mismo método aplicado al subconjunto CLDR 43.1 frente a esa tabla posterior cubrió 7.896 valores y tenía 338 adicionales. El conjunto candidato no es la tabla original ni contiene todos sus campos; la coincidencia de identificadores por sí sola no resuelve procedencia, autorización o condiciones aplicables. Excluir los cinco archivos con nombre ISO no demuestra la ausencia de otros datos relacionados.

El subconjunto CLDR 43.1 conserva también una entrada de herramienta `language-subtag-registry` cuya cabecera lleva fecha 2023-02-14. De sus 8.049 subetiquetas de idioma de tres letras, 7.713 coinciden con identificadores de la tabla ISO candidata posterior; aquí no se atribuye la causa de esa diferencia entre versiones. Las instrucciones de actualización de Unicode identifican el archivo como el registro de subetiquetas de idioma obtenido de IANA. La declaración CC0 de IANA cubre solo los derechos que posee o puede sublicenciar y mantiene la posibilidad de derechos de terceros. Véase [#140](https://github.com/xiaodaozhi/xdzip/issues/140#issuecomment-6589292716) para la comparación y sus límites.

El subconjunto CLDR 43.1 incluye también dos fuentes Noto, cuatro archivos Glyphicons, scripts Bootstrap y Autosize e imágenes emoji usadas por su herramienta web. `cldr43-webapp-notices/` proporciona procedencia y licencias de esas fuentes y scripts y de 908 imágenes que coinciden con dos versiones fijadas de Noto Emoji, después de verificar cada archivo fijado. Para las otras 963 imágenes originales cuya procedencia y condiciones de redistribución no se han establecido de forma independiente, el recopilador verifica cada hash original y las sustituye por 698 imágenes Noto y 265 Twemoji fijadas. El manifiesto registra ambos hashes, rutas y fuentes; no se afirma una infracción. Estos archivos no forman parte de la interfaz de xdzip. Las notificaciones también identifican tres archivos fuente de la herramienta web con avisos de copyright de IBM y los tratan bajo Unicode-DFS-2016 a partir del README raíz de esa versión, conservando avisos de copyright y licencia. Otras 27 imágenes de la raíz web coinciden byte a byte con un commit CLDR fijado de 2026 y se tratan bajo su licencia Unicode-3.0, conservando el aviso completo y hashes individuales. Esta evaluación no se extiende a marcas, recursos no enumerados ni dependencias externas.

Dos archivos de texto completos del subconjunto CLDR 43.1 `docs/rfc`, `draft-davis-t-langtag-ext.txt` y `draft-davis-u-langtag-ext-00.txt`, coinciden byte a byte con el [borrador IETF de extensión T de 2011](https://www.ietf.org/archive/id/draft-davis-t-langtag-ext-07.txt) y el [borrador de extensión U de 2010](https://www.ietf.org/archive/id/draft-davis-u-langtag-ext-00.txt). La recopilación verifica hashes y conserva copyright y avisos. Ambos remiten a condiciones vigentes en su publicación; la sección 3.c de [TLP 4.0](https://trustee.ietf.org/wp-content/uploads/IETF-TLP-4.pdf) permite su distribución fuera del proceso de estandarización íntegramente y sin modificaciones, en la medida en que el Trust pueda conceder esos derechos, conservando los avisos exigidos. Esta evaluación solo cubre esos dos textos, no otros HTML, XML, recursos o derechos de terceros.

Para idiomas ya presentes en las fuentes Qt, extraiga una entrada limitada para el generador del `qlocale_data_p.h` original. Por ejemplo, después de extraer QtBase en el directorio actual, ejecute `python3 scripts/derive-qt-locale-code-input.py --qtbase qtbase-everywhere-src-6.8.2 --output build/qt-locale-codes.tsv`. Esto solo cubre claves de búsqueda existentes y no es la tabla ISO 639-3 completa ni la entrada histórica original. Añadir idiomas puede requerir códigos obtenidos por separado y revisión de sus condiciones. Se verificó la regeneración de ocho archivos con fuentes Qt 6.8.2 fijadas, datos CLDR 46 y esta entrada derivada, permitiendo solo diferencias de fecha de generación y finales de línea. Esto no resuelve la licencia de la tabla ISO ni establece la totalidad de las fuentes correspondientes.

Para un idioma adicional específico, extraiga el subconjunto CLDR 43.1 entregado y use `tools/cldr-code/src/main/resources/org/unicode/cldr/util/data/language-subtag-registry` para comprobar la subetiqueta e indicar expresamente cuatro campos de código. Los campos ISO 639-2 del ejemplo Choctaw pueden comprobarse con la [lista de la Biblioteca del Congreso](https://www.loc.gov/standards/iso639-2/php/code_list.php) y el ISO 639-3 con los [datos de la autoridad de registro](https://iso639-3.sil.org/code_tables/download_tables). El último campo vacío indica que no hay código de dos letras:

```sh
python3 scripts/derive-qt-locale-code-input.py --qtbase path/to/qtbase \
  --iana path/to/cldr43/tools/cldr-code/src/main/resources/org/unicode/cldr/util/data/language-subtag-registry \
  --add-language 'cho,cho,cho,' --output build/qt-locale-codes-with-cho.tsv
```

`--add-language` puede repetirse. Los campos son código de tres letras, ISO 639-2/B, ISO 639-2/T y código de dos letras; los campos ausentes quedan vacíos y los dos campos de la parte 2 deben suministrarse juntos o dejarse ambos vacíos. La herramienta comprueba que al menos un código de tres o dos letras sea una subetiqueta IANA registrada, valida la sintaxis y rechaza conflictos con claves Qt. **No** deduce ni verifica que los campos se refieran al mismo idioma ni establece las correspondencias ISO. El destinatario debe revisar cada correspondencia y fuente. Añadir un idioma a Qt exige además actualizar `enumdata.py`, proporcionar datos regionales CLDR y regenerar y recompilar Qt; la fila por sí sola no añade un idioma. Sigue siendo una tabla derivada limitada, no la tabla ISO completa ni una prueba de la identidad de la entrada histórica o de todas las fuentes correspondientes.

En una prueba aislada, añadir manualmente un código de prueba de uso privado al enum de la herramienta Qt y a la tabla derivada generó un nuevo enum y entrada de código. Un QtCore Linux recompilado superó las búsquedas directa e inversa, y una copia aislada del alpha.8 original completó exploración, cancelación y extracción fuera de pantalla. Esto no añadió un idioma real ni datos de formatos regionales CLDR, no sustituye la revisión de entradas y condiciones reales y no establece todas las obligaciones de fuentes correspondientes. Véase [#138](https://github.com/xiaodaozhi/xdzip/issues/138#issuecomment-6611169790) para los pasos y el fallo inicial de la prueba.

Otra opción es obtener independientemente los datos JSON ISO 639-2 y 639-3 de `iso-codes` y convertirlos en una entrada Qt. Por ejemplo, en Linux con el paquete de datos instalado:

```sh
python3 scripts/convert-iso-codes-for-qt.py \
  --iso-639-2 /usr/share/iso-codes/json/iso_639-2.json \
  --iso-639-3 /usr/share/iso-codes/json/iso_639-3.json \
  --output build/qt-iso-codes.tsv
```

El conversor extrae correspondencias de códigos sin nombres; una entrada completa sigue produciendo un conjunto completo de códigos. Rechaza códigos inválidos, duplicados y conflictos con claves Qt, omite el intervalo reservado para uso local ISO 639-2 e informa los SHA-256 de entrada y salida. Véase [#138](https://github.com/xiaodaozhi/xdzip/issues/138) para la comparación de Qt 6.8.2 con Ubuntu `iso-codes` 4.16.0-1; otras versiones deben comprobarse por separado. Los datos no están incluidos. Revise independientemente su licencia declarada, procedencia y condiciones de redistribución de las tablas generadas; una tabla alternativa no establece la entrada histórica de Qt ni la conformidad completa de fuentes.

Para reproducir la comparación, obtenga independientemente el [paquete Ubuntu `iso-codes` 4.16.0-1](https://archive.ubuntu.com/ubuntu/pool/main/i/iso-codes/iso-codes_4.16.0-1_all.deb) fijado. El siguiente ejemplo de Linux requiere `curl`, `dpkg-deb` y Python 3; verifica el hash del paquete antes de extraerlo y convertirlo localmente sin cambiar la instalación del sistema:

```sh
mkdir -p build && mkdir build/qt-iso-peer &&
curl --fail --location --silent --show-error --connect-timeout 15 --max-time 120 https://archive.ubuntu.com/ubuntu/pool/main/i/iso-codes/iso-codes_4.16.0-1_all.deb -o build/qt-iso-peer/iso-codes.deb &&
python3 -c "import hashlib,pathlib,sys; p=pathlib.Path('build/qt-iso-peer/iso-codes.deb'); h=hashlib.sha256(p.read_bytes()).hexdigest(); sys.exit(0 if h=='cafca0a3a1f07b44fbba53ab7a1f1d9755e6b80cc041173afe2b52e53bed97a7' else 'Package SHA-256 mismatch')" &&
dpkg-deb -x build/qt-iso-peer/iso-codes.deb build/qt-iso-peer/data &&
python3 scripts/convert-iso-codes-for-qt.py \
  --iso-639-2 build/qt-iso-peer/data/usr/share/iso-codes/json/iso_639-2.json \
  --iso-639-3 build/qt-iso-peer/data/usr/share/iso-codes/json/iso_639-3.json \
  --output build/qt-iso-peer/qt-locale-codes.tsv
```

Los SHA-256 de entrada verificados son `fa83810fdb59f9d84b4d58486d5e5e48e807d82a98d6a39ef0ba4fc57c2a9327` y `9636ce5266053867627140ce5ada1f9aa897ca07a7501302c1b14b8d1147cdda`; la salida convertida es `85457a36e013e053b70dea19d500ebec2ae6bedf5dad9af0035b973c8db6a60a`. El archivo Ubuntu `usr/share/doc/iso-codes/copyright` declara LGPL-2.1-or-later, pero esa declaración a nivel de paquete por sí sola no establece la concesión histórica de la tabla SIL ni los derechos de redistribución de un conjunto completo de códigos. Aquí no se incluye ni el paquete ni la tabla completa convertida; revise por separado la procedencia, las condiciones y la redistribución posterior.

Como alternativa, obtenga independientemente el [registro de subetiquetas de idioma IANA](https://www.iana.org/assignments/language-subtag-registry/language-subtag-registry) y la [lista ISO 639-2 de la Biblioteca del Congreso](https://loc.gov/standards/iso639-2/ISO-639-2_utf-8.txt) y genere otra entrada. La herramienta extrae códigos sin nombres, informa códigos sin coincidencia y hashes de entrada y salida, y rechaza registros inválidos o ambiguos. El ejemplo de shell Linux/macOS usa un directorio nuevo y verifica ambos archivos originales de esta comparación antes de convertir:

```sh
(

  mkdir -p build
  mkdir build/qt-iana-loc-inputs

    build/qt-iana-loc-inputs/iana.txt 755fad43283be7b41ebe3c89ad054b6eaf928f404f9c0edb74799e0eab74beb1 \

El archivo LoC UTF-8 obtenido directamente el 2026-11-03 tenía 16.010 bytes y SHA-256 `42b71885e4dc885559fda5ad059fd81838cf4782cedb5fd08cc3431f7d067371`. Los primeros tres campos de código de sus 487 registros coincidían individualmente con la reconstrucción web anterior. El SHA-256 de salida LF del conversor era `6a75bebfa694258a1a4125fc30512d8ae7994080701377b41306db665ad371c6`. Juntas, estas entradas produjeron 8268 filas que coincidían con las 346 claves de búsqueda Qt distintas existentes. Los ocho archivos regenerados coincidieron tras normalizar fechas de generación y finales de línea; un control negativo que modificó una entrada coincidió en siete. Siete subetiquetas IANA de dos letras `bh`, `in`, `iw`, `ji`, `jw`, `mo`, `sh` no tenían registro LoC y la herramienta las informa. Verifique por separado otras versiones e idiomas añadidos. Las direcciones originales pueden cambiar; investigue una discrepancia de hash en lugar de omitir la comprobación. Véase [#138](https://github.com/xiaodaozhi/xdzip/issues/138#issuecomment-6588040592).

La [declaración de IANA/IETF](https://www.iana.org/help/licensing-terms) aplica CC0 a los derechos de registros de protocolo que poseen o pueden sublicenciar, preservando posibles derechos de terceros; no establece automáticamente todos los derechos de la tabla SIL original. Aquí no se incluye la instantánea IANA 2026-09-17, la entrada LoC ni la tabla completa convertida de comparación. El subconjunto CLDR 43.1 contiene por separado el registro anterior descrito arriba. Los destinatarios deben revisar por separado procedencia, condiciones aplicables y redistribución posterior. Esta alternativa no establece ni la entrada histórica de Qt ni la conformidad completa de fuentes correspondientes.

Aquí, comparación independiente significa obtener y convertir archivos por separado, no una procedencia independiente de los estándares. La [sección 2.2.1 de RFC 5646](https://www.rfc-editor.org/rfc/rfc5646#section-2.2.1) identifica ISO 639-2, 639-3 y 639-5 como fuentes de estándares para las subetiquetas de idioma IANA de tres letras. La coincidencia de valores no establece autoría independiente ni una sublicencia completa.

La salida incluye xdzip-source.tar del commit fijado real, rust-vendor.tar.gz, configuración Cargo sin conexión, archivos Qt originales, REBUILD.md y un manifiesto de SHA-256 y tamaño por archivo. El manifiesto se declara recopilado y no verificado para conformidad; no sustituye las comprobaciones de funciones y parches de compilación del SDK, runtimes de plataforma, recursos integrados o cumplimiento de licencias. Las fuentes de proyecto reconfiguradas pueden tener identidad desconocida y deben vincularse al commit original mediante el manifiesto externo de entrega, sin fabricar una identidad Git limpia.

El directorio separado `rar-wire-mappings/` conserva la procedencia de referencia de asignaciones finitas acotadas, explicaciones y el aviso original exacto de UnRAR 7.30 beta1, todo incluido en la entrega con hash. El nombre de descarga fijado es `unrarsrc-7.3.1.tar.gz`; su nombre numérico no establece una versión de lanzamiento original distinta. Como medida conservadora de aviso, la entrega exige el segundo párrafo completo de la licencia original en los comentarios de las fuentes Rust relacionadas y se detiene si falta o cambia. El crate RAR declara conservadoramente `Apache-2.0 AND UnRAR`; el identificador `UnRAR`, no aprobado por OSI, aparece en SPDX 3.28 y posteriores y puede no ser reconocido por herramientas antiguas. Estos materiales no incluyen fuentes del motor oficial ni vuelven a licenciar como Apache-2.0 los hechos derivados de referencias. Las condiciones aplicables y obligaciones reales de redistribución requieren revisión específica de cada candidato.

Para ICU en Linux se incluyen la licencia completa fijada de ICU 73.2, el archivo oficial de fuentes de ICU4C 73.2, las fuentes editables fijadas de ICU, el subconjunto de fuentes CLDR 43.1 y las fuentes de arranque ICU 73.1, todos en el manifiesto general. El subconjunto CLDR excluye cinco archivos ISO 639-3, el texto UTS #35 y archivos asociados bajo `docs/ldml`, y dos capturas de documentación, y sustituye 963 imágenes de la herramienta web. El registro de entrega conserva el hash del archivo original y cada exclusión y sustitución. [UTS #35 versión 43.1 publicada por Unicode](https://www.unicode.org/reports/tr35/tr35-69/tr35.html) está disponible por separado bajo las condiciones de su propietario; aún debe establecerse si existe algún permiso transferible adicional. El recopilador también rechaza archivos del paquete de arranque con `iso-639-3` en el nombre; una comprobación de nombres no descarta datos en otra forma. La recopilación verifica hashes, versiones, licencias integradas y archivos fuente seleccionados sin extraer rutas de terceros. La [guía de recompilación de datos ICU](icu-cldr-rebuild.md) registra la compilación de herramientas y el alcance de generación y edición. La coincidencia de versiones originales no demuestra que un proveedor compilara sus binarios a partir de estas entradas sin parches. Los paquetes actuales de desarrollo Windows omiten OpenGL por software y ya no recopilan materiales dedicados de Mesa/LLVM; las entregas históricas conservan sus materiales y obligaciones originales. Véanse [fuentes y avisos del runtime nativo](native-runtime-materials.md).

La aplicación enlaza dinámicamente Qt y proporciona instrucciones para recompilar desde fuentes y sustituir bibliotecas compatibles. La [verificación de despliegue macOS](macos-deployment.md) cubre la carga de bibliotecas modificadas en una copia aislada sin afirmar una recompilación completa de Qt desde fuentes. Las compilaciones reales de fuentes Qt y la carga en el producto siguen un proceso separado en el [contrato de verificación automática](../../../developers/engineering/candidate-verification.md). La equivalencia de compilación byte a byte del SDK, la atribución exacta de enlaces estáticos y las elecciones de licencia forman parte de la [revisión de licencias de publicación](https://github.com/xiaodaozhi/xdzip/issues/4), no de una reapertura del trabajo de desarrollo WP-12 completado.

verify-source-delivery.py primero vuelve a verificar los hashes de los archivos entregados, extrae de forma segura las entradas propias del proyecto y vendor en un nuevo directorio build/, compila la aplicación real con una caché Cargo vacía, CARGO_NET_OFFLINE=true y el SDK Qt fijado existente, y ejecuta una prueba rápida de inicio y cierre. Esto verifica el uso sin conexión de las entradas del proyecto y Rust, no una compilación de fuentes de módulos Qt ni compilaciones reproducibles byte a byte. Los directorios fuente generados tienen identidad Git desconocida, vinculada externamente por el commit fijado y el manifiesto de entrega.

La entrega de fuentes invoca Cargo desde el directorio de salida con un destino `vendor` relativo y un manifiesto de proyecto explícito. Solo se aceptan el mapeo de fuentes crates.io actualmente admitido y la configuración relativa de `vendor`. Los directorios absolutos, escapes de ruta o mapeos inesperados fallan en lugar de incrustar rutas de la máquina de compilación en una entrega reubicable.

Para paquetes vendor fijados sin archivos independientes de licencia o aviso con nombres convencionales, `rust-vendor-notices/` indexa por separado los textos originales fijados por paquete. El recopilador verifica hash del manifiesto Cargo del paquete, commit y ruta Git originales, SHA-256 del texto de licencia y blob Git; las lagunas desconocidas o discrepancias de identidad detienen la entrega. Este directorio no modifica archivos ni sumas de Cargo vendor. Las expresiones de licencia originales permanecen sin cambios; esto no aprueba una elección concreta de licencia ni la conformidad de una publicación anterior.

La [comprobación de correspondencia del SDK Qt](qt-sdk-correspondence.md) incluye siempre el manifiesto de correspondencia fijado y el parche de consumidor AGL reproducible. Con --qt-prefix también incluye comprobaciones por archivo de declaraciones de fuentes, configuración de compilación y lagunas explícitas de ese SDK. El manifiesto de entrega calcula hashes recursivos de los subdirectorios de parches y la verificación de recompilación vuelve a comprobar esos bytes. Sin SDK no se fabrica ningún registro de verificación de configuración.

La entrega conserva un objeto de commit Git Qt Declarative fijado para verificar sin conexión la relación del commit de publicación con el objeto de árbol `.tag` del archivo; el manifiesto calcula su hash. Esa relación no establece cobertura completa del archivo ni equivalencia de compilación del SDK.

Véase el [contrato de finalización automática](../../../developers/engineering/candidate-verification.md) para compilaciones reales de Qt desde fuentes y carga o sustitución compatible. Las recompilaciones sin conexión de la aplicación con un SDK existente no deben describirse como recompilación del propio Qt desde fuentes.
