# Contenedores BH y perfil BlakHole admitido

[English](../../engineering/bh-containers.md) | [简体中文](../../zh-CN/engineering/bh-containers.md) | [繁體中文](../../zh-TW/engineering/bh-containers.md) | [日本語](../../ja-JP/engineering/bh-containers.md) | [한국어](../../ko-KR/engineering/bh-containers.md) | [Français](../../fr-FR/engineering/bh-containers.md) | [Deutsch](../../de-DE/engineering/bh-containers.md) | Español | [Português (Brasil)](../../pt-BR/engineering/bh-containers.md) | [Русский](../../ru-RU/engineering/bh-containers.md)

`xdzip-codec-bh` lee entradas BlakHole (`.bh`) en secuencia desde el origen gestionado por el host. El perfil exige el prefijo `BH 05 07`, las constantes de cabecera observadas, metadatos de archivo normal, tamaños comprimido y descodificado exactos y el CRC-32 de IEEE declarado para cada entrada. Se conserva el orden físico. Los nombres duplicados siguen siendo distintos y la identidad fija de cada fila es independiente de la descodificación del nombre visible.

El único método admitido para el contenido es el 8, Deflate en bruto según RFC 1951. El lector Deflate compartido y limitado requiere un flujo completo y consumir exactamente el tramo comprimido. Los bytes sobrantes, flujos truncados y discrepancias de tamaño descodificado o CRC provocan un fallo. Los métodos desconocidos siguen visibles con un aviso. Sus entradas no se pueden extraer ni contar como contenido verificado.

La cabecera admitida consta del prefijo fijo de cinco bytes, una longitud de cabecera de 16 bits en orden de menor a mayor peso, los bytes constantes `25 d8 0c 00`, el método, una marca de tiempo de cuatro bytes al estilo DOS, los tamaños comprimido y descodificado, el CRC-32, los atributos `0x20`, cinco bytes reservados a cero, una longitud de nombre de cuatro bytes y los bytes del nombre. La longitud de cabecera debe ser `37 + filename_length`. Las entradas son contiguas y el último contenido termina exactamente al final físico del archivo. No se aceptan datos finales del contenedor, entradas de directorio, prefijos SFX, resincronización, relleno ni búsquedas en archivos vecinos.

BH carece de una especificación pública mantenida. Las observaciones se fijan en `support/formats/BLAKHOLE.TXT` de `ashang/libxad` (revisión `dbe67a865207e49cd917ad9170a11b9eaa83998a`, SHA-256 `fdb2b4d2fffa7760eef4b3ccbabdcd6b2d43df33949a1b793f9efb7e4c2c0f2d`) y `docs/BLAKHOLE-ON-DISK.md` de Hawkynt/CompressionWorkbench (commit `ab61c59f789d82c628d3c5b4bac264afbdc0c7a7`, SHA-256 `f79f66d98d6c922ea4b64bde3ff5540a4d894de6632375513f3db89876e27bca`). Este último documenta una sola muestra de procedencia conocida con cinco entradas. La muestra no permite determinar el comportamiento de Store, cifrado, directorios, bloques sólidos o volúmenes.

IZArc Command Line Add-On v1.1 se conserva como referencia exclusiva de compilación. La descarga oficial publica el MD5 `9002c7634768e5336244f9accb2223b0`. El SHA-256 del `IZArcCL.exe` local es `959050AFC513C64FD61F9EE15837054D0FAEE5EFB98C9107B4DC5D9A528A62D4`. En este entorno, los ejecutables extraídos `IZARCC.exe` y `IZARCE.exe` terminan con el código Windows `0xC0000005` antes de generar resultados. La herramienta no acredita compatibilidad con Store, niveles de compresión, contraseñas o extracción. La referencia permanece en `build/toolchain` y no es una dependencia del producto.

BH es de solo lectura. Se excluyen la creación, modificación, cifrado, archivos comprimidos multivolumen y un tipo MIME dedicado en Linux. El registro de formatos y el [contrato de comprobación](archive-checking.md) describen estos límites. La extensión `.bh` permite iniciar la detección. El resultado depende de la validación completa del contenido.
