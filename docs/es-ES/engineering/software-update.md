Cuando una versión incluye paquetes Intel, el cliente macOS Intel selecciona `release-intel.json` y `appcast-intel.xml`, firmados por separado; la CLI independiente usa `cli-release-intel.json`. Apple Silicon sigue usando los manifiestos y el feed existentes. Las actualizaciones Intel estarán disponibles cuando se publique una versión que incluya estos archivos.



Con identidad de paquete MSIX en Windows, Acerca de no muestra actualizaciones internas y el controlador rechaza la comprobación de actualización de GitHub existente. Microsoft Store gestiona las actualizaciones de la edición Store; los paquetes instalados por carga lateral no tienen garantía de actualización automática en la aplicación. Los errores al consultar la identidad se tratan como identidad de paquete para evitar el uso indebido de actualizaciones del instalador. Las instalaciones ordinarias y las demás plataformas no cambian.

La CLI independiente y la CLI incluida en el paquete de escritorio actualizan sus propias instalaciones conforme al [contrato de línea de comandos](command-line.md). La CLI independiente usa un manifiesto firmado separado y un directorio de versiones gestionado. La CLI incluida envía la intención de candidato mediante IPC de instancia única para el mismo usuario y el controlador de escritorio la verifica independientemente. La aceptación solo significa handed_off; el éxito real requiere un recibo y la identidad en ejecución. La protección por instalación ocupada en Windows/Linux también cubre tareas de la CLI; macOS protege la CLI mediante un bloqueo de uso compartido, una barrera de confirmación y estado persistente. Las tareas existentes no se cancelan implícitamente. Las consultas de identidad de la CLI sin interfaz no crean QApplication ni leen o eliminan recibos de instalación.

El `UpdateController` de la aplicación comprueba las versiones públicas desde Acerca de. Cerrar esa ventana no cancela las comprobaciones ni descargas; al volver a abrirla se muestra el mismo estado. Las comprobaciones las inicia el usuario, sin sondeo al inicio ni instalación automática. Las ventanas del producto siguen utilizando Acerca de y los controles de operación compartidos.

## Selección, red y privacidad

El cliente Qt de actualización usa HTTP/1.1 para metadatos, sumas de comprobación y descargas de paquetes. Así aplica la mitigación publicada para la versión fijada de Qt. El transporte de actualización Sparkle en macOS es independiente. [Aviso de seguridad de Qt](https://www.qt.io/blog/security-advisory-cve-2026-96432)

El cliente solo lee la [API pública de Releases](https://docs.github.com/en/rest/releases/releases) del repositorio fijo `xiaodaozhi/xdzip`, no usa credenciales y no envía nombres de archivo, contenido de archivos comprimidos, contraseñas, registros recientes ni ajustes. GitHub y su CDN de descarga reciben información de conexión y un User-Agent que contiene la versión de la aplicación. Las páginas de publicación y las carpetas de descarga se abren mediante la interfaz del sistema.

Cada página contiene como máximo 100 entradas, con un máximo de 10 páginas; cada respuesta se limita a 8 MiB, los manifiestos a 256 KiB y las firmas a 4 KiB. Las solicitudes originales solo permiten HTTPS y hosts GitHub/CDN registrados explícitamente. Con un espejo configurado por el usuario, se permite su sitio HTTPS como dirección de transporte y se admiten hasta cinco redirecciones. Los metadatos tienen un límite de inactividad de 15 segundos y total de 30 segundos; las descargas, 30 segundos de inactividad y una hora total. La caché ETag en memoria contiene hasta 24 entradas; un 304 solo reutiliza una respuesta anterior satisfactoria. La desconexión, TLS, tiempos de espera, límites de frecuencia, truncamientos, paquetes ausentes y errores de manifiesto son fallos, no «ya está actualizado». Los clics repetidos no inician actualizaciones paralelas.

Las actualizaciones usan la configuración de proxy del sistema, conexión directa o un proxy HTTP/SOCKS5 personalizado sin credenciales. Un espejo opcional debe usar HTTPS y no contener credenciales, consulta ni fragmento; a su base se añade la URL HTTPS completa original de GitHub. Las URL originales siguen pasando por la lista fija de hosts permitidos. Espejos y redirecciones no cambian el contenido del manifiesto firmado, la verificación, la identidad del candidato ni las barreras de instalación. Los cambios de configuración se aplican a la siguiente actualización cuando termina la actual. Sparkle nativo de macOS admite modos de sistema, directo y HTTP CONNECT/SOCKS5 personalizado sin credenciales. Cada instancia nativa copia el modo y la dirección de proxy validados antes de iniciarse y usa la misma política de sesión para fuente y archivo. Si falla el proxy personalizado, no debe recurrirse a conexión directa. El modo directo establece explícitamente las banderas HTTP, HTTPS, SOCKS, FTP, PAC y detección en el valor numérico 0 del diccionario de proxy de URLSession; un diccionario nil o arreglos modernos de proxy vacíos siguen significando el valor predeterminado del sistema. La confianza TLS, las firmas de publicación y las barreras independientes de instalación no cambian.

HTTP 429 indica límite de frecuencia. HTTP 403 solo se clasifica como límite de frecuencia si la cuota restante es cero, existe un Retry-After válido en segundos o el mensaje JSON de GitHub identifica explícitamente el límite. Los demás 403 siguen siendo fallos de red; no se infiere agotamiento de cuota. El producto no reintenta automáticamente ni lee credenciales de GitHub. La cuota anónima se comparte por IP de origen; los permisos de repositorio de CI no pueden aumentarla.

El núcleo Rust sin Qt selecciona por versión semántica, canal y número de compilación monótonamente creciente, y valida el repositorio fijo, las seis clases completas de paquete, la arquitectura, el tipo de paquete, el contrato de sistema mínimo y una identidad de candidato idéntica. stable acepta solo stable; alpha acepta alpha, beta, rc y stable; beta excluye alpha; rc acepta rc y stable; dev puede consultar publicaciones públicas. Tanto la versión semántica como la compilación deben aumentar; no se usa la fecha de publicación como sustituto. El cliente también comprueba la compatibilidad del sistema actual y el número de bytes de los recursos de Releases.

## Confianza y descargas

`release.json.sig` verifica los bytes exactos del manifiesto. Las raíces de confianza están compiladas en el cliente y el ayudante del instalador y no pueden añadirse desde descargas ni solicitudes. Los metadatos JSON se validan como UTF-8 antes de pasar cadenas por FFI; una codificación inválida falla explícitamente en vez de alterar bytes autenticados con caracteres de reemplazo. Véase el [protocolo de publicación](release-protocol.md) para formatos de firma, claves independientes de Sparkle, orden de entrega y recursos inmutables. Si faltan firmas o las claves públicas son desconocidas, solo se ofrece la descarga manual desde la página oficial; las firmas incorrectas fallan explícitamente. La sustitución automática permanece desactivada hasta configurar una clave pública de producción.

Windows/Linux transmiten paquetes de hasta 2 GiB a una caché privada de actualización mientras comprueban longitud y SHA-256; solo una publicación satisfactoria permite la entrega al ayudante. Una cancelación o fallo de validación no crea un estado instalable. Las compilaciones portátiles, modificadas, de desarrollo o fuente, o de identidad desconocida, solo ofrecen comprobación y descarga. La sustitución automática también exige configuración Release e identidad de commit válida; una compilación desde un archivo fuente sin identidad Git no se considera instalada. La identidad de instalación debe coincidir con el registro del sistema, la ruta en ejecución y el marcador del paquete.

macOS usa Sparkle 2.10.0 fijado y la extensión de proxy restringida `xdzip-proxy.2`, con un controlador de usuario Objective-C++ ligero que comunica el estado a Acerca de unificada. La biblioteca del framework y Ed25519 se compilan de forma nativa en Apple Silicon o Intel a partir de fuentes y parches fijados; los recursos, el ayudante de instalación y las herramientas de firma conservan la procedencia del SDK oficial fijado. No se afirma que el framework derivado sea idéntico byte a byte al SDK original. Sparkle valida de forma nativa la fuente y el archivo; la fuente solo contiene el mismo candidato seleccionado. No se afirma que Sparkle realice una comprobación SHA-256 adicional. Un DMG de solo lectura, App Translocation, una .app no registrada o la ausencia de clave pública de actualización conducen a instalación manual. La CI ordinaria no despliega, firma ni sube paquetes de aplicaciones Mac solo por usar Sparkle.

El recurso manual muestra la primera condición incumplida entre identidad de instalación, sesión, ausencia de fuente de actualización automática o configuración de red inválida. Un fallo de identidad solo indica que falló el grupo de comprobaciones, sin adivinar cuál; varias condiciones pueden requerir resolución sucesiva. Acerca de enlaza a la publicación correspondiente y a las instrucciones del DMG, y explica cómo extraer app.zip, salir de la versión anterior y reemplazar la aplicación. Una descarga exitosa no equivale a instalación exitosa.

## Entrega de instalación y recuperación

Las tareas existentes continúan durante la descarga. Si hay tareas activas después de elegir descargar e instalar, se espera; el usuario puede cancelar la espera y aplazar la actualización sin cancelar implícitamente tareas ni solicitudes de contraseña. Tras preparar el ayudante, `prepareForUpdate` rechaza tareas activas, inicio de tareas e interacciones modales. Una vez iniciada la entrega, no se admiten nuevas sesiones ni tareas; todas las conexiones Rust deben limpiarse y finalizar antes de enviar la confirmación de instalación. La entrega no usa la vía de «reiniciar inmediatamente el programa anterior».

Windows copia un ayudante independiente sin Qt a una caché privada únicamente desde la raíz de instalación registrada para el usuario actual. El ayudante vuelve a verificar por separado firma, tamaño y hash, espera a que termine el proceso principal capturado y ejecuta el instalador Inno existente con aceptación interactiva de la licencia. Una barrera de instalación impide reinicios durante la sustitución.

Si la raíz de instalación no supera las comprobaciones de seguridad, Acerca de indica los permisos de la carpeta de instalación o la instalación manual desde la página de publicación, sin clasificar el rechazo como fallo de red. No se relajan las comprobaciones existentes de directorio e identidad.

Las instalaciones Ubuntu usan la ruta fija `/usr/libexec/xdzip-update-helper`; el coordinador del usuario ordinario llama a polkit solo con argumentos fijos. El ayudante root copia el paquete a un área privada de preparación root, verifica de nuevo la firma, el nombre de paquete xdzip, la arquitectura y la versión, y solo permite operaciones APT fijas. No acepta órdenes, nombres arbitrarios de paquetes ni directorios de destino, y no usa una shell sudo. La cancelación de autorización y la ausencia del agente de autenticación son estados diferentes. Un dpkg sin configurar no se comunica como éxito; no hay reversión automática ni reinicio del programa anterior. Al reiniciar la nueva versión como el usuario original se conservan los directorios XDG de configuración, datos, caché y estado permitidos y acotados, y el idioma del escritorio, pero no las sustituciones del cargador dinámico, SDK Qt o entorno de pruebas; esas variables no se pasan a las órdenes de instalación root.

En macOS, la devolución de llamada de instalación de Sparkle solo se libera después de esperar a que todo termine. El programa principal libera de forma síncrona su interceptor de salida solo después de que el proveedor marque la instalación real como confirmada y antes de invocar la respuesta de instalación del SDK; la barrera de espera por sí sola no debe permitir la salida automática prematura al cerrar la última ventana. Tras una entrega fallida o cancelada, la salida ordinaria sigue esperando la barrera de observación del ayudante nativo. Sparkle realiza la sustitución real del archivo y el reinicio. La cancelación no deja un plan de instalación para la siguiente salida. El framework, XPC y el ayudante conservan sus propios parámetros de firma y permisos requeridos; no se pueden aplicar reglas genéricas de refirma a todos.

Las respuestas de cancelación de Sparkle se procesan en un ciclo asíncrono de actualización; completar el ciclo no significa que haya terminado el proceso separado del instalador. En una instalación no confirmada, la salida ordinaria solicita la cancelación, espera el ciclo y usa `/bin/ps` del sistema en modo de solo lectura para observar procesos Autoupdate que coincidan con la ruta exacta del framework de esta aplicación. El interceptor de salida solo se libera después de que esos procesos terminen. Se registra el instalador coincidente cuando está preparado. Un fallo de inspección no autoriza la salida; no se termina el ayudante ni se registran datos de procesos ajenos. Tras un fallo de preparación, los reintentos también esperan a que termine el ayudante anterior antes de reemplazar el controlador de actualización. Las instalaciones confirmadas usan la salida y el reinicio nativos de Sparkle.

Las transacciones Windows/Linux usan ID aleatorios y nombres de archivo fijos ready/proceed/cancel/result. Antes de salir, el cliente guarda la transacción, la identidad del destino y el directorio de caché en un `update-state.ini` independiente junto a los ajustes, no dentro de la configuración. El ayudante escribe atómicamente un resultado de éxito antes de liberar la barrera y reiniciar. En el siguiente inicio se acotan rutas y tamaños del recibo y se verifica la transacción y la identidad actual de versión, compilación e instalación. Un fallo, recibo ausente o discrepancia muestra recuperación sin reintentar automáticamente. Un registro de recuperación sin URL de candidato válida todavía puede abrir la lista oficial fija de publicaciones. Los materiales de caché se conservan para que el usuario pueda reparar; las pruebas públicas no deben contener rutas privadas completas.

Antes de liberar la instalación Sparkle, macOS guarda un registro local del intento con la versión y compilación de destino. Al reiniciar, la identidad realmente en ejecución y marcadores de instalación fiables determinan si se completó o necesita recuperación. El registro no concede autoridad de instalación ni sustituye la verificación de firma Sparkle.

## Límites de verificación

Un diagnóstico exclusivo de Mac solo puede ejecutar la cadena completa del producto. La verificación de todas las plataformas ejecuta siempre los seis escenarios de Sparkle y la cadena completa, ignorando la opción de diagnóstico que omite los seis escenarios.

Las comprobaciones de conflicto de sistema del descargador nativo habilitan temporalmente un proxy estático y PAC propios solo en runners Apple Silicon o Intel alojados, desechables y explícitamente aislados. Primero se exige que las solicitudes reales de fuente y archivo en modo sistema lleguen al proxy y que las del modo directo produzcan cero accesos. Los controles HTTPS verifican los destinos de conexión y mantienen el rechazo de certificados no fiables. Un ayudante acotado guarda, restaura y verifica todos los ajustes de proxy del servicio y el contenido de hosts para dominios de prueba fijos, incluso ante EOF o tiempo de espera. Las ejecuciones locales nunca modifican proxy, DNS ni confianza de certificados. Una cadena completa separada del producto prueba instalación directa bajo PAC controlado, reinicio ordinario e instantáneas activas de configuración de actualización; las comprobaciones del descargador no reemplazan la prueba de instalación.

La aceptación HTTPS sin SDK en Mac usa la misma sonda desplegada y solicitudes reales anónimas de actualización. Los registros solo contienen código de estado, error Qt y cabeceras de límite de frecuencia permitidas, no cuerpos de error sin procesar, IP de origen ni credenciales. Tras confirmar el límite de frecuencia, el controlador de aceptación inicia como máximo tres sondas, esperando hasta el momento posterior entre Retry-After y el restablecimiento de cuota. Sin una hora utilizable de restablecimiento de cuota principal rechaza el reintento temprano; otros límites confirmados usan espera creciente de al menos 60 segundos. La espera total se limita a 3700 segundos; superar el límite falla explícitamente y conserva cada resultado y espera real. Siguen siendo obligatorios los tiempos de espera por solicitud, TLS, límites de respuesta, estado satisfactorio y aislamiento del SDK; los reintentos no se combinan en una sola aprobación. Esta espera pertenece solo al controlador de aceptación dedicado y no añade reintentos de fondo al producto ni permite omitir las comprobaciones especializadas finales.

Los fixtures del núcleo cubren canales, dev, paginación fuera de orden, paquetes ausentes, firmas incorrectas, sistema mínimo y conflictos de identidad. Los fixtures de red cubren cancelación, clics repetidos, límites de frecuencia, TLS, límites de respuesta, ETag y descargas dañadas. Las regresiones de sesión comprueban la conservación de tareas y la entrega después de que todas terminen. Las actualizaciones reales de versión anterior a nueva en las tres plataformas, la cancelación de autorización, el reinicio, el fallo y recuperación de instalación, la conservación de ajustes y asociaciones y HTTPS sin SDK requieren pruebas de plataforma aislada; las pruebas unitarias y la compilación CI no las sustituyen. Las actualizaciones completas de Mac requieren ejecución nativa en la arquitectura de destino. La finalización y las pruebas reales se siguen en las issues.

La [regresión nativa de actualización dedicada](../../../.github/workflows/update-regression.yml) solo se ejecuta manualmente, no lleva secretos de producción y no sube paquetes de aplicaciones. Por defecto cubre todas las plataformas y permite seleccionar una para diagnóstico, cada una con su propia cola; la aceptación final sigue exigiendo resultados de todas las plataformas del mismo commit. Windows en runners GitHub desechables y Linux en un contenedor dedicado usan primero un producto propio de protocolo en C e Inno/APT reales para verificar cancelación, fallo y recuperación del ayudante. Otra cadena privada de actualización Qt compila dos versiones reales de `browser_main`/QML, usa entrada real de ratón en Acerca de y valida manifiestos y paquetes, espera de salida, Inno/APT, reinicio de instancia única como usuario ordinario y recuperación de recibos. También verifica conservación de ajustes, claves de ajustes desconocidas, valores predeterminados existentes y archivos ajenos en el directorio de instalación. Linux separa los contenedores del SDK de compilación y del entorno de ejecución; este último no tiene compilador ni SDK Qt y usa directorios XDG personalizados. La CI Windows Server sustituye la detección de sistema mínimo solo bajo una macro privada y no reemplaza la aceptación nativa de Windows 11. Esta cadena sustituye el transporte de red de las URL públicas de GitHub; HTTPS/TLS de producción se verifica por separado sin SDK.

La [aceptación de firma de producción](../../../.github/workflows/production-update-acceptance.yml), autorizada por separado, usa las claves existentes del entorno protegido y conserva las raíces públicas de producción confirmadas en el repositorio, siguiendo la cadena real de actualización y recuperación Qt. La preparación no firma. Un paso de firma independiente comprueba primero que las raíces públicas de confianza coincidan estrictamente y luego verifica este candidato fijo; la ejecución rechaza entornos con secretos. No ofrece una interfaz para firmar o publicar recursos arbitrarios. Los candidatos firmados permanecen en runners desechables; los artefactos públicos solo contienen diagnósticos y resúmenes acotados. Debe registrarse por separado de las regresiones con claves de prueba; solo la ejecución real se considera aprobación y la coincidencia de claves no es éxito de instalación. Véase el [protocolo de publicación](release-protocol.md).

Un escenario ampliado retrasa la finalización de la descarga e inicia una comprobación AES real hasta que espera una contraseña; después verifica que la actualización espera a esa tarea. El diálogo de contraseña sigue siendo modal nativo de aplicación; el fixture cancela la espera de actualización mediante el controlador y registra expresamente que no se usó el ratón en Acerca de para ese paso. Tras cancelar permanecen la misma tarea y el mismo token de contraseña; un evento de confirmación del método de entrada y el botón de confirmación de contraseña completan la comprobación, y luego se reinicia la instalación desde Acerca de. Otra ejecución envía la salida del sistema al programa principal real mientras coexisten la actualización y la espera de contraseña, pulsa los controles reales Volver y Cancelar y salir y comprueba la misma tarea y token, todas las esperas de finalización, cero entregas de instalación y el reinicio ordinario en la misma instalación anterior antes de actualizar. El escritorio físico y la entrada humana se comprueban según necesidad y se registran por separado; la revisión de licencias y la autorización de publicación también son independientes.

Una regresión de componentes con dos sesiones entra en la misma ventana de salida mediante AppQuitGuard, DesktopIntegration y el enrutamiento de todas las sesiones, comprobando Volver/cancelar y la espera de finalización de una tarea AES en espera. Solo un diálogo modal de contraseña o conflicto propio de una sesión gestionada puede quedar cubierto por la confirmación de salida; los modales QWidget nativos siguen bloqueando la salida. Esta comprobación de componentes se registra por separado de la salida del sistema del programa principal completo durante la espera de actualización y de la regresión nativa de instalación.

Antes de su primera salida del sistema, el fixture completo del producto Mac debe observar realmente que la ventana de contraseña de la misma sesión de trabajo está visible y expuesta, pertenece a esa ventana principal y es el modal actual de la aplicación, con tarea y tokens de contraseña sin cambios. Una solicitud de contraseña Rust no demuestra que la presentación diferida esté lista. Se envía la salida una sola vez después de estas condiciones y se verifican el control Volver real, la restauración del modal, la cancelación y todas las esperas de finalización. Si se agota el tiempo, se congela el progreso antes de limpiar; los resultados de salida posteriores obtenidos durante la limpieza no pueden sobrescribir el fallo.

La regresión privada de instalación en Windows pausa Inno real después de copiar el nuevo `xdzip.exe` y antes de otros archivos, comprueba la nueva identidad y vuelve a iniciar el programa Qt real. Se exige la salida 11 de la barrera de inicio sin ventana visible ni sesión nueva; después se reanuda la copia y se completa la aceptación de actualización existente. Los identificadores de observación se cierran inmediatamente para que la prueba no prolongue la barrera del instalador. La versión anterior y la nueva usan Qt 6.8.2; esto no demuestra sustitución atómica de paquetes de aplicación ni migración entre versiones de Qt. La plantilla del instalador de producción no contiene la pausa.

Una aplicación Qt privada de Mac con otro nombre usa Acerca de real, espera de finalización de dos sesiones, Sparkle, un app.zip firmado y reinicio en la nueva compilación, cubriendo manipulación de fuente o archivo y cancelación. Solo el descubrimiento de candidatos usa un sustituto de bucle local; los manifiestos y canales públicos de GitHub se comprueban por separado mediante regresiones del núcleo de actualización y red. Las claves de prueba solo se inyectan en una copia privada; los recursos de producción no cambian. Solo puede registrarse como aprobada la evidencia de una ejecución real.

La prueba especializada del ayudante Windows también acciona el botón Cancelar de la página de licencia real de Inno y una inyección privada de fallo en InitializeSetup. Los registros del instalador deben demostrar esa ruta, conservar la identidad anterior, no reiniciar y liberar la barrera de instalación. Linux usa pkexec real para verificar por separado la denegación de la política, la ausencia de agente de autenticación y un agente D-Bus estándar que devuelve Cancelled. El agente de cancelación solo atiende el UID, la acción y la solicitud de prueba fijos; no recibe contraseñas ni concede autoridad. Una actualización satisfactoria comprueba por separado las asociaciones predeterminadas existentes de ZIP, TAR y GZip. El accionamiento automático del botón de licencia y un agente de prueba no constituyen confirmación manual de licencia ni aceptación del agente de autenticación del escritorio del sistema.

Las regresiones Qt completas de Windows/Linux envían un paquete real con inicialización Inno fallida o un postinst que falla una vez, registran la solicitud real, la transacción, el recibo de fallo y la liberación de la barrera, y prohíben el reinicio automático tras el fallo. La recuperación inicia el programa principal ordinario. Una fábrica de red privada devuelve null para que el constructor predeterminado del controlador consuma el recibo de la caché predeterminada real. Se exige estado de recuperación, la misma identidad de instalación real, ausencia de nuevas tareas, entrega de instalación o reintento automático, y conservación de ajustes y valores predeterminados ZIP/TAR/GZip. Un postinst de Linux fallido puede haber instalado ya archivos nuevos; se verifica la versión realmente nueva y el estado semiconfigurado de dpkg en lugar de afirmar que se conservó la versión anterior. Solo el fixture repara explícitamente la configuración APT y restablece un escenario satisfactorio separado; esa acción de prueba no debe describirse como reversión del producto.

Las regresiones completas del producto Mac distinguen la cancelación en el límite de espera y confirmación de un rechazo del sistema de archivos posterior a la confirmación real, aplicando UF_IMMUTABLE reversible a la raíz antigua de la aplicación propiedad de esta prueba. En el segundo caso se deben registrar la confirmación real de instalación, el PID exacto del ayudante que termina por sí solo y el registro de fallo de permisos de ese ayudante; la cancelación de la entrega no sustituye al fallo de instalación. Los indicadores solo se restauran después de comprobar el alcance propio, UID, dev/inode y valores originales. No se usa sudo, no se termina el instalador ni se fabrican resultados. Ambos casos de recuperación arrancan normalmente la versión anterior y leen registros persistentes de intento. Los artefactos reales de Apple Silicon establecen si se aprobaron.

Otra cadena completa del producto Mac compila programas principales reales a partir de dos identidades limpias de fuente Release, conserva el ID formal del paquete, marcadores de instalación y tipos de documento Alternate, y los instala en una ruta Applications propia de un runner desechable. La versión anterior usa Acerca de y UpdateController reales para autenticar el manifiesto, instalar con Sparkle y entregar después de esperar la finalización. El inicio ordinario de la nueva versión verifica la identidad de instalación, el recibo de actualización, el directorio de configuración predeterminado, ajustes y claves desconocidas, comportamiento de instancia única y controlador ZIP predeterminado de LaunchServices. El transporte privado solo asigna las URL fijas de metadatos, la URL autenticada de la fuente y la URL exacta del archivo; las firmas se verifican realmente y HTTPS sin SDK se comprueba por separado. La regresión usa HOME y rutas de configuración predeterminadas del usuario original, sin sustituir la recuperación tras reinicio por inyección de rutas de prueba.
