# Fijación de herramientas y plataformas

[English](../../engineering/toolchain.md) | [简体中文](../../zh-CN/engineering/toolchain.md) | [繁體中文](../../zh-TW/engineering/toolchain.md) | [日本語](../../ja-JP/engineering/toolchain.md) | [한국어](../../ko-KR/engineering/toolchain.md) | [Français](../../fr-FR/engineering/toolchain.md) | [Deutsch](../../de-DE/engineering/toolchain.md) | Español | [Português (Brasil)](../../pt-BR/engineering/toolchain.md) | [Русский](../../ru-RU/engineering/toolchain.md)

Las versiones de herramientas de desarrollo están fijadas por rust-toolchain.toml, Cargo.lock, CMake y CI; el alcance sigue la [política de soporte](support-policy.md). Esta tabla define las verificaciones para actualizaciones y entregas. Las observaciones concretas quedan en incidencias o Actions; el inventario de una sola máquina no bloquea las dependencias de una entrega.

| Elemento | Dirección actual | Evidencia necesaria para fijar |
| --- | --- | --- |
| Rust | rust-toolchain.toml fija 1.99.0, edición 2024, rust-version 1.99 | Al actualizar comprobar el MSRV de dependencias, pruebas en tres destinos y Clippy; mantener alineadas herramientas y configuración Cargo |
| Qt | SDK 6.8.2 fijado; QtNetwork usa `6.8.2-xdzip-network.1`, derivado con parches oficiales de seguridad. SDK local en `build/toolchain/Qt/6.8.2/<platform-subdirectory>`; despliegue dinámico | Origen y hashes fijados, licencias de módulos y pruebas básicas en tres plataformas; comprobar mantenimiento de seguridad antes de cada entrega y volver a verificar origen y sustitución al actualizar |
| C++ | C++17 y compilador compatible con Qt | Versiones de clang en macOS, MSVC en Windows y compilador de Linux |
| CMake | La raíz exige 3.24 o posterior con Ninja | Comprobar versión real de compilación, dependencias de cabeceras generadas y configuración limpia; el flujo fija herramientas de CI |
| Python | La entrada de escritorio compartida exige 3.10+; las herramientas de validación del paquete usan entornos aislados | Usar el mismo intérprete para scripts Python posteriores y comprobar dependencias fijadas por etapa; las herramientas de diseño en navegador no son dependencias de compilación del producto |
| cxx | 1.0.205; puente generado al compilar, sin ABI binaria estable | Versiones coincidentes de crate y generador, regresiones de carreras al cerrar y límites de excepciones |
| Sistemas | macOS 14+ arm64, Windows 11 x64 mantenido, Ubuntu 24.04 X11 x64 | Verificar entornos reales según la política aprobada; no extender la evidencia del anfitrión CI a todas las versiones del sistema |

En Windows, las compilaciones de escritorio, de código Qt y las reconstrucciones del código entregado usan temporalmente una página de códigos UTF-8 de consola para MSVC/Ninja y después restauran la original. Sin consola crean una consola oculta temporal para el proceso y sus hijos; los procesos externos no deben adjuntarse. Las compilaciones protegidas que comparten una consola existente se serializan mediante la lista de procesos adjuntos; consolas independientes pueden compilar en paralelo. Los procesos deben permanecer adjuntos durante la protección. Una lista inválida detiene la compilación; tras esperar 30 segundos se solicita reintentar. Los scripts antiguos sin identificador de ventana usan bloqueos incompatibles y esta coordinación no impide que otros programas cambien la configuración de consola. Antes y después de compilar se revisan los registros de dependencias Ninja de los objetos compilados. Si un archivo fuente con inclusión directa entre comillas o inclusión entre ángulos del mismo directorio no tiene dependencias registradas, detenerse, conservar el directorio anterior y solicitar uno nuevo sin borrar ni reutilizar objetos automáticamente. Ninja puede omitir cabeceras del sistema intencionadamente, por lo que una fuente que solo las use puede tener cero dependencias. La comprobación no cubre inclusiones entre ángulos resueltas por otras rutas ni todas las entradas implícitas del compilador, y no evalúa condiciones del preprocesador; puede rechazar por precaución inclusiones inactivas. CMake/Ninja ejecutados directamente omiten estas protecciones: asegurar que la salida del compilador coincida con el prefijo de Ninja y verificar que un cambio real de cabecera provoque recompilación tras cambiar página de códigos o herramientas.

Los trabajos Apple Silicon alojados por GitHub usan ejecutores macOS 15, mientras el destino de despliegue sigue siendo macOS 14.0. Actualizar el ejecutor no demuestra verificación en un dispositivo real con macOS 14; la compatibilidad y la aceptación manual se registran por separado.

Consulta la [guía de compilación para desarrolladores](../../engineering/developer-build.md) para preparación diaria, comprobaciones y ejecución. `scripts/desktop.py doctor` comprueba build por defecto; `doctor --for-stage package` verifica de antemano toda la cadena de empaquetado. Las opciones de prepare `--install-rust`, `--install-qt` y `--packaging` preparan explícitamente las herramientas y materiales fijados correspondientes. Los desarrolladores siguen instalando compiladores y SDK del sistema; la comprobación previa no es un instalador implícito.

El directorio local fijo de herramientas es `build/toolchain/`. El SDK de Qt, `qmllint` y `qmake` usan `build/toolchain/Qt/6.8.2/<platform-subdirectory>`; `aqtinstall` y las herramientas Python compartidas usan `build/toolchain/desktop-tools`; la preparación de descargas Qt usa `build/toolchain/qt-install-tool`. Las entradas compartidas usan estos directorios en vez de cachés separados para compilación, pruebas, paquete o comprobaciones Qt individuales. CI con directorios temporales del ejecutor debe pasar parámetros explícitos sin cambiar la estructura local predeterminada.

La comprobación previa ejecuta Rust/Cargo disponibles realmente en PATH, verifica versiones fijadas y anfitrión nativo y comprueba CMake, Ninja, prefijo Qt y herramientas de plataforma. Un compilador instalado pero inaccesible desde el shell actual se considera ausente. El empaquetado también comprueba metadatos de dependencias Rust bloqueadas, materiales SPDX/licencia de Qt y caché de esquemas. Todos los procesos posteriores usan el mismo entorno comprobado para evitar que una compilación correcta termine sin rustc/cargo durante la recopilación de licencias. La ausencia de Docker o Inno Setup afecta solo a etapas que los requieren y no bloquea compilaciones ordinarias de desarrollo.

Cada registro incluye versión, origen de descarga, SHA-256, licencia, destino, responsable, commit de verificación y fecha. Las actualizaciones de seguridad Rust/Qt provocan una nueva validación; los parches sin mantenimiento no se conservan indefinidamente. Los candidatos de sistema mínimo no son compromisos formales de soporte.

El mantenimiento del sistema, los canales de seguridad Qt y la responsabilidad de verificar actualizaciones siguen la [política de soporte](support-policy.md). Registrar las conclusiones de origen y licencia según el [proceso de revisión de entrega](../../../developers/qa/release-review.md).

En Windows, WindowsFrame implementa la extensión del área cliente de la ventana principal con interfaces públicas de ventanas Qt y Win32, sin enlazar GuiPrivate. Al vincularse inicialmente a una ventana normal determina el marco a partir de dimensiones lógicas actuales del área cliente QWindow, DPR y métricas nativas de borde; las aplicaciones posteriores de tema o DPI solo actualizan el borde. Para una ventana PMv2 normal sin sustitución local de escala y con redondeo Qt PassThrough, WM_GETDPISCALEDSIZE conserva el ajuste previo al escalado del SIZE pendiente, escala el área cliente y añade los bordes reales del DPI de destino. Métricas inválidas, desbordamiento u otros estados no modifican SIZE y devuelven el control a Qt. Los mensajes nativos prestados y estructuras modificables se usan solo durante la devolución síncrona. Volver a verificar áreas cliente, bordes y estados afectados al actualizar Qt o sustituir el SDK. El arrastre físico entre dos pantallas y la apariencia se comprueban cuando sea necesario; los resultados programáticos no sustituyen una verificación física no realizada.

La CI diaria instala por separado en un directorio temporal del ejecutor la versión Rust fijada por rust-toolchain.toml, rustfmt y clippy, y comprueba que el compilador real esté allí antes de verificar el formato Rust, evitando una instalación rustup incompleta del anfitrión. Las pruebas completas de Rust y herramientas de firma se ejecutan localmente o en el flujo bajo demanda pertinente según el cambio.
