# DMG local de desarrollo para macOS

[English](../../engineering/macos-deployment.md) | [简体中文](../../zh-CN/engineering/macos-deployment.md) | [繁體中文](../../zh-TW/engineering/macos-deployment.md) | [Français](../../fr-FR/engineering/macos-deployment.md) | Español

El flujo Release dedicado permite el despliegue nativo, la firma ad hoc necesaria, el empaquetado de app.zip y DMG y su subida. El trabajo de macOS del flujo Qt bajo demanda conserva la verificación del SDK. Una misma aplicación .app desplegada, firmada y verificada sirve para ambos paquetes de publicación; la aplicación extraída del ZIP también se comprueba tras cambiarla de ubicación. Consulte el [protocolo de publicación](release-protocol.md).

Un DMG local de desarrollo es un entregable de desarrollo permitido. El flujo Qt bajo demanda verifica la compilación y el arranque nativos en Apple Silicon sin empaquetar, firmar ni subir una aplicación Mac. Los scripts locales no instalan la aplicación, no cambian las asociaciones predeterminadas, no suben archivos y no leen credenciales de publicación.

## Compilar y verificar

La comprobación previa del entorno y las opciones de cada etapa siguen la [guía de compilación para desarrolladores](../../engineering/developer-build.md). Prepare las herramientas de empaquetado, compile una aplicación principal Release separada desde un commit limpio y después empaquete y verifique:

```sh
python3 scripts/desktop.py prepare --packaging
python3 scripts/desktop.py build --build-dir build/desktop-dmg --macos-handler-rank Alternate
python3 scripts/desktop.py test --build-dir build/desktop-dmg
python3 scripts/desktop.py doctor --for-stage package --build-dir build/desktop-dmg
python3 scripts/desktop.py package --build-dir build/desktop-dmg --output-dir build/package-macos --kind all
python3 scripts/desktop.py verify --build-dir build/desktop-dmg --output-dir build/package-macos --kind all
```

Las etapas no vuelven a ejecutar implícitamente las anteriores. El SDK Qt predeterminado está en `build/toolchain/Qt/6.8.2/macos`; para otra ubicación, pase `--qt-prefix` a cada comando. Las compilaciones ordinarias de desarrollo y pruebas usan `None` por defecto; la aplicación principal anterior selecciona explícitamente `Alternate` sin cambiar los valores predeterminados del usuario. El paquete local de macOS solo admite `all`. El flujo Qt bajo demanda no empaqueta ni sube aplicaciones Mac; consulte el protocolo de publicación para la excepción Release dedicada.

Antes de macdeployqt, las comprobaciones comunes del paquete verifican arm64 nativo, el SDK del sistema, las herramientas de despliegue, el PATH y los metadatos fijados de Rust, las dependencias Python de validación y los materiales de licencia y esquemas Qt. build y test permiten fuentes sin confirmar; package exige un commit limpio y una identidad CLI real coincidente, y no permite eludir estas condiciones mediante cachés de compilación. El compilador y SDK del sistema, lipo, codesign y hdiutil los proporciona la cadena del sistema; prepare no los instala.

macdeployqt también reubica el proceso de vista previa de imágenes. La selección predeterminada de plugins de plataforma de Qt 6.8 solo incluye Cocoa, por lo que el script de empaquetado copia explícitamente offscreen antes de analizar las bibliotecas de la aplicación para procesar sus dependencias de frameworks Qt. Un plugin o proceso auxiliar ausente impide empaquetar. Tras la firma de integridad y la auditoría de importaciones, elimine las variables que alteran la búsqueda Qt/QML/DYLD y verifique los formatos del proceso de imagen realmente incluido y la decodificación de un PNG propio; el comprobante es `image-preview-deployed.json`. Las pruebas unitarias de los scripts no acreditan la aceptación del paquete desplegado.

Los scripts subyacentes [build-macos-dmg.py](../../../scripts/build-macos-dmg.py) y [verify-macos-dmg.py](../../../scripts/verify-macos-dmg.py) conservan los detalles de la imagen y de la verificación nativa. Para diagnosticar problemas, use su opción `--help` en lugar de mantener pasos rutinarios separados. Sus rutas de salida deben ser nuevas y estar dentro de build/. Cada tipo de documento de la entrada DMG debe declarar `Viewer/Alternate`; de lo contrario, vuelva a compilar en vez de reescribir el plist o las firmas del paquete original. macdeployqt analiza el QML real y despliega frameworks Qt, plugins y QML. Añada las traducciones de controles de sistema Qt, avisos del proyecto, avisos originales de Rust, licencias de fuentes, SBOM de fuentes y materiales fijados de licencia Qt. Conserve los enlaces simbólicos internos de los frameworks y rechace los que salen de la aplicación. Elimine los RPATH absolutos de la máquina de desarrollo y compruebe recursivamente que todas las importaciones nativas se resuelven solo en la aplicación o el sistema. La identidad de compilación no puede estar modificada ni ser desconocida y debe coincidir con el commit limpio actual para vincular los avisos reales.

El módulo QML opcional LocalStorage de Qt incorpora QtSql, por lo que el despliegue también copia controladores de bases de datos. El proyecto no ofrece capacidades de servidor de bases de datos; elimine los controladores distintos del SQLite integrado para evitar clientes PostgreSQL, ODBC, Mimer y otros externos al SDK en la imagen. Registre las eliminaciones en el comprobante y no presente importaciones sin resolver como verificaciones satisfactorias.

## Reducción de arquitecturas y estilos

Los DMG de desarrollo solo entregan `arm64` de Apple Silicon. La configuración de arquitectura CMake del programa principal no limita los archivos del SDK Qt copiados por macdeployqt; inspeccione recursivamente cada Mach-O de la aplicación, incluidos frameworks, bibliotecas dinámicas, plugins y plugins nativos QML. Reduzca los archivos de dos arquitecturas a `arm64` únicamente en la copia nueva de empaquetado. La ausencia de `arm64`, una arquitectura desconocida o una sección adicional restante hacen fallar el empaquetado; la arquitectura del ejecutable principal no sustituye las comprobaciones de elementos anidados. Reduzca antes de reescribir RPATH y de firmar recursivamente ad hoc.

El producto usa Qt Quick Controls `Basic`. El despliegue elimina únicamente los estilos no Basic indicados explícitamente y sus imports o plugins de implementación dedicados; conserva Basic, los controles compartidos, Templates y las dependencias QML reales. No reduzca el paquete eliminando módulos desconocidos. Una disposición de estilos inesperada, dependencias conservadas ausentes o restos de estilos no utilizados hacen fallar la auditoría. Los cambios de estilo del producto o del SDK Qt requieren actualizar conjuntamente las reglas de reducción y las pruebas. Reducir el tamaño no elimina licencias Qt, materiales de fuentes correspondientes, traducciones del sistema ni plugins de ejecución necesarios.

Optimice solo la aplicación recién preparada bajo `build/`, no la aplicación principal de entrada, el SDK Qt ni las fuentes. Los comprobantes conservan las comprobaciones de arquitectura y estilo, los binarios reducidos, las listas de eliminaciones y los bytes lógicos reales de la aplicación antes y después de la optimización, con categorías de frameworks, plugins, QML y otros. Los bytes se cuentan a partir del contenido real sin contar dos veces los enlaces simbólicos; no son el uso de disco de Finder ni el tamaño de la imagen UDZO. El tamaño final del DMG se registra aparte. Las comparaciones por versión, las conclusiones y el trabajo pendiente se registran en issues; las mediciones brutas permanecen en artefactos locales.

`scripts/test-macos-bundle.py` usa pequeños datos de prueba propios en CI multiplataforma para verificar el reconocimiento de arquitecturas, la operación solo sobre copias, los límites de enlaces simbólicos, la conservación y eliminación de estilos y los fallos, sin herramientas de despliegue macOS. No sustituye la verificación del paquete final. Las comprobaciones del DMG deben confirmar recursivamente que todos los archivos nativos solo contienen `arm64` y que los estilos cumplen el contrato tras copiar desde la imagen montada, y ejecutar los flujos de aislamiento de búsqueda del SDK y Cocoa/Metal indicados a continuación.

## Verificación de imagen y ejecución

La imagen comprimida UDZO contiene xdzip.app, un enlace a Applications e instrucciones de instalación; ejecute hdiutil verify. Cierre normalmente las versiones anteriores antes de arrastrar a Applications. Este proceso no incluye actualizador ni migración de tareas durante la instalación. Los ajustes y elementos recientes permanecen en directorios del usuario y no se borran automáticamente al eliminar la aplicación.

Conserve junto a la imagen el JSON de verificación de despliegue y un SBOM CycloneDX a nivel de archivo, vinculados al inventario de fuentes del mismo commit, los SHA-256 finales de archivos nativos y las relaciones de importación. El SBOM sigue incompleto: enumerar archivos no equivale a una atribución exacta de componentes ni a una aprobación de licencias. Mantenga el inventario fuera de la imagen para evitar su propio hash recursivo.

El nuevo `xdzip.app` preparado existe solo durante el despliegue, la firma, la creación de la imagen y la verificación, y se elimina automáticamente tanto si hay éxito como si hay fallo. Permanecen el DMG, JSON, SBOM e instrucciones; la aplicación principal de entrada no cambia. No queda ningún paquete preparado suelto que el sistema pueda volver a descubrir.

Los Mach-O ARM64 modificados necesitan directorios de código válidos; use una firma ad hoc local tras copiar y reescribir, y verifique el código anidado. **Esto no es una firma Developer ID ni una notarización y no implica confianza de Gatekeeper.** Según la [política personal de publicación de código abierto](../../../developers/engineering/release-runbook.md), la firma formal y la notarización no son condiciones obligatorias para publicar; siguen siendo necesarias las verificaciones de dependencias, licencias, seguridad y del paquete real. No desactive SIP ni elimine políticas globales de seguridad del usuario.

El script de verificación monta la imagen en solo lectura, comprueba el enlace Applications, copia la aplicación a una ruta aislada con caracteres chinos y espacios y comprueba recursivamente arm64, estilos Basic y firmas estrictas de cada archivo nativo y del paquete. La inicia y cierra con Cocoa/Metal tras eliminar las variables de búsqueda de SDK/QML/plugins. El producto real de la imagen abre un ZIP generado por el proyecto, realiza búsqueda, ordenación, extracción y salida, verifica independientemente Unicode, archivos y directorios vacíos y cada byte de salida, y comprueba identidad de compilación, arquitectura y motor Metal en el primer fotograma real. Después, solo en la copia de verificación, modifica la identidad de la biblioteca Mach-O QtCore y vuelve a firmar ad hoc, y comprueba de nuevo arquitectura, estilos, firmas y arranque. Esto demuestra que se permite la modificación o sustitución desplegada; no demuestra que Qt se haya recompilado desde las fuentes correspondientes, compatibilidad ABI arbitraria ni aprobación de cumplimiento legal.

La verificación de app.zip también usa la opción predeterminada del producto de crear una carpeta del mismo nombre para extraer toda la aplicación, compara archivo por archivo los bytes, destinos de enlaces y permisos seguros con `ditto`, y después realiza comprobaciones de firma estrictas y profundas y arranque Cocoa/Metal de la aplicación real extraída. El directorio exterior no debe terminar en `.app`. Las aplicaciones temporales y registros creados durante la prueba se limpian después. Esto no cambia los límites de confianza de firma ni de notarización.

La máquina local aún tiene un SDK; las comprobaciones de imports y la limpieza del entorno no sustituyen un Mac limpio independiente. El arrastre desde Finder, Abrir con del sistema, la selección predeterminada, Gatekeeper, el reinicio real y la firma/notarización siguen sujetos a la [lista manual](../../../developers/qa/private-test-manual.md).

Los comandos de edición de menús nativos y los controles estándar Qt necesitan traducciones qtbase de la configuración regional del sistema. Además de copiar `Contents/Resources/translations/qtbase_*.qm`, el empaquetado establece `Translations = Resources/translations` en `[Paths]` de `Contents/Resources/qt.conf`, conserva las rutas existentes de plugins y QML y lo escribe antes de la firma de integridad. Los controles de arranque reubicado verifican tanto los respondedores nativos de edición como los roles del menú de la aplicación; no bastan las comprobaciones en el directorio de desarrollo del SDK.

## Firma y activación locales de Finder Sync

Finder Sync usa una appex nativa y un relay independiente dentro de la misma aplicación; se conserva el auxiliar de servicio. El orden completo de firma es: imágenes nativas, frameworks y auxiliares dedicados, appex con los permisos de sandbox exactos, paquete relay y aplicación externa, seguido de la verificación estricta del paquete anidado. No sobrescriba después una appex firmada con una firma genérica sin permisos. Las compilaciones CI ordinarias no firman ni activan implícitamente la extensión.

Para verificar Finder localmente, complete la compilación nativa predeterminada y ejecute explícitamente:

```sh
python3 scripts/sign-macos-finder.py --app build/desktop/apps/desktop/xdzip.app --output build/review/finder-signing.json
build/desktop/apps/desktop/xdzip.app/Contents/MacOS/xdzip --register-shell-integration
```

El script de firma solo acepta aplicaciones propias del proyecto y salidas bajo `build/` del repositorio; no despliega Qt, no crea un DMG y no lee credenciales de publicación. Su comprobante acredita únicamente integridad ad hoc y verificación estricta anidada, no Developer ID, notarización, confianza de Gatekeeper ni aprobación de licencias de publicación. La aplicación debe permanecer en su ubicación original. Active la extensión Finder de xdzip en Ajustes del sistema, en ítems de inicio y extensiones. Las rutas de ajustes y los menús pueden variar según la versión del sistema; registrar correctamente no acredita la aceptación del menú ni de sus acciones.

Antes de terminar una verificación temporal, use `--remove-shell-integration` de la misma aplicación para revocar los registros propios de servicio y extensión. Tras comprobar el estado inicial, limpie únicamente la configuración y los registros temporales LaunchServices creados por este trabajo. No modifique otras aplicaciones ni las asociaciones predeterminadas. Si Finder ha cargado la aplicación, desactive y vuelva a activar la extensión propia en los ajustes del sistema después de actualizar, en lugar de reiniciar Finder. Consulte [acciones del gestor de archivos](shell-actions.md) para los límites de transferencia y reversión.

## Registro «Abrir con» de copias de desarrollo y verificación

LaunchServices recuerda los paquetes de aplicación abiertos anteriormente; varias copias del mismo identificador de paquete en un árbol de compilación pueden aparecer en los menús «Abrir con» del sistema o de Codex. Por ese motivo no borre la base de datos del sistema, no reinicie Finder, no borre paquetes de verificación ni cambie los valores predeterminados del usuario.

Los paquetes de desarrollo nuevos usan `LSHandlerRank=None` por defecto en el Info.plist generado; solo la aplicación principal elegida y el paquete entregado conservan `Alternate`. La opción CMake `XDZIP_MACOS_HANDLER_RANK` solo permite estrictamente esos dos valores. Las reconstrucciones de fuentes sin conexión, la verificación del producto Qt desde fuentes y la CI de producto Mac pasan explícitamente `None` para evitar que futuros cambios del valor predeterminado reintroduzcan copias de prueba como candidatas. La [definición de Apple de `None`](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html) mantiene el arrastre de archivos sin seleccionar el paquete como gestor de apertura del tipo. No afecta a la selección de archivos dentro de la aplicación ni a su apertura explícita y no establece valores predeterminados.

La CI del producto Mac ejecuta `scripts/check-macos-registration.py` para consultar mediante `NSWorkspace` nativo las aplicaciones candidatas para los archivos del paquete nuevo. El número de candidatos y los registros enumerados por identificador de paquete se evalúan por separado; estos últimos no sustituyen los candidatos «Abrir con» realmente visibles para el usuario. Los gestores predeterminados existentes deben mantenerse durante el registro temporal. Los tipos sin gestor previo pueden resolverse temporalmente a un candidato nuevo; todos los tipos probados deben recuperar los gestores y estados de candidatos originales tras cancelar el registro. Las preferencias `LSHandlers` del usuario actual solo se comparan como instantáneas en memoria antes, durante y después del registro; su contenido no se imprime. Otras preferencias y reglas del sistema quedan fuera de esta comparación.

`scripts/macos_launch_services.py` solo reconoce `org.xdzip.desktop`. La reubicación del DMG, reconstrucción de fuentes sin conexión, verificación del producto Qt desde fuentes, sustitución de QtCore y verificación de apertura de archivos del sistema registran las inscripciones previas dentro del ámbito de `build/` y, al terminar o fallar, cancelan únicamente los registros de copias de prueba añadidos durante la ejecución. Las aplicaciones principales existentes y otros productos se conservan. Si falla la limpieza, falla la verificación en lugar de declararse silenciosamente satisfactoria.

La reubicación del DMG y la sustitución de QtCore conservan las declaraciones originales de documentos y la verificación de los paquetes entregados, pero solo copian a rutas `.app` nuevas e inexistentes bajo `build/`. El paquete nuevo se elimina automáticamente tras verificar o fallar, conservando en su ámbito los hashes necesarios. Permanecen JSON, registros, paquete principal anterior a la sustitución, DMG y fuentes Qt. La limpieza no acepta aplicaciones existentes ni enlaces simbólicos y no elimina retrospectivamente paquetes de verificación históricos. El sistema u otras aplicaciones pueden volver a descubrir y registrar paquetes `Alternate` antiguos que solo se desregistraron; no puede garantizarse que no reaparezcan. Si deben conservarse, pueden guardarse en copias verificables y restaurables antes de tratar las copias sueltas con autorización explícita.

Previsualice los restos históricos con la herramienta siguiente y después aplique explícitamente. `--keep` debe indicar una aplicación principal existente y correctamente identificada, ya sea la compilación actual de desarrollo o una instalación en Applications:

```sh
python3 scripts/cleanup-macos-open-with.py --keep build/ui-release/apps/desktop/xdzip.app
python3 scripts/cleanup-macos-open-with.py --keep build/ui-release/apps/desktop/xdzip.app --apply
```

La herramienta solo desregistra otras copias xdzip dentro de `build/` de este repositorio y rutas inválidas con la misma identidad. No elimina paquetes, no cambia firmas y no establece la aplicación ZIP predeterminada. No trata automáticamente otros productos, otras instalaciones en Applications ni rutas fuera del árbol de compilación. No limpia rutas que se resuelven fuera del ámbito mediante enlaces simbólicos. Vuelva a comprobar los registros, conservando solo el paquete principal de desarrollo indicado. Si hay varias instalaciones fuera del árbol de compilación, enumérelas por separado como no tratadas; no afirme haber eliminado duplicados globalmente.

Registre el progreso de limpieza, los recuentos y las conclusiones en la issue correspondiente, por ejemplo [mantenimiento de copias de desarrollo #7](https://github.com/xiaodaozhi/xdzip/issues/7). Los JSON generados y resultados de sondas nativas permanecen únicamente en artefactos locales o CI.
