# Instaladores y asociaciones de archivos

En Windows 11 x64, busque **XDZip** en Microsoft Store para instalar o actualizar la edición Store. Descargue el EXE o ZIP portátil de Windows, los paquetes macOS y los paquetes Linux desde la [última publicación de GitHub](https://github.com/xiaodaozhi/xdzip/releases/latest). Los dos canales publican independientemente. Consulte la ficha o las notas de la versión que va a instalar.

Windows MSIX declara las mismas extensiones como candidatas de Abrir con en su manifiesto de paquete sin apoderarse de la elección predeterminada del usuario. Su página de asociaciones muestra todos los tipos elegibles con interruptores deshabilitados. Los valores predeterminados actuales aparecen en la configuración de Windows. «Abrir la configuración de aplicaciones predeterminadas» navega al paquete actual mediante su `registeredAUMID`. Si falla la consulta de identidad, abre el selector general de valores predeterminados. El paquete no lee los registros de la edición instalada ordinaria como estado del paquete ni escribe valores UserChoice. La activación real de archivos, los iconos, la coexistencia y la desinstalación requieren aceptación en el sistema de destino. Véanse las [compilaciones MSIX](../engineering/developer-build.md#windows-msix-实验构建).

Véase la [especificación de iconos de asociación](../visual/file-association-icons.md) para las imágenes de cada formato y su correspondencia por plataforma. Linux conserva los iconos MIME del sistema. La instalación no modifica los valores predeterminados ni el ámbito de registro existente.

Las asociaciones MSIX hacen referencia a recursos PNG por formato extraídos de los mismos fotogramas ICO canónicos que usa el instalador ordinario de Windows. ZIP, 7z, RAR y los demás formatos asignados conservan sus imágenes de documento, perfiles de tamaño y márgenes transparentes. El icono de la aplicación tiene recursos de tamaño de destino separados sin placa. Ambos conjuntos se indexan en `resources.pri` del paquete; cambiar la imagen de la ficha Store no sustituye los iconos instalados. Windows gestiona la caché de iconos y la selección del controlador predeterminado, y la instalación nunca cambia esa selección automáticamente.

Los paquetes de escritorio desde `v0.2.0` y las compilaciones actuales de fuentes sitúan la CLI en un directorio `cli/` separado, o `Contents/Helpers/cli/` en macOS, conservando los puntos de entrada existentes de GUI y asociación. Los recursos de versiones anteriores no adquieren esta función retroactivamente. El instalador Windows ofrece una opción PATH por usuario de inclusión voluntaria y detecta conflictos de comandos con el mismo nombre; la desinstalación solo revoca su directorio de instalación. Mac/Linux ejecutan explícitamente `setup` de la CLI privada. Los paquetes CLI independientes también usan `setup` para instalar directorios de versiones a nivel de usuario y un lanzador estable, sin modificar la configuración de la shell. `setup --remove` revoca el registro pero conserva los directorios de versiones para inspección. Véase el [contrato de instalación de CLI](command-line.md#xdzip-build-and-command-installation).

Los comandos de empaquetado siguientes producen artefactos experimentales de desarrollo. Los paquetes oficiales de GitHub siguen el [protocolo de publicación](release-protocol.md), y los de Store usan el [flujo MSIX](../engineering/developer-build.md#microsoft-store-msix). Las descargas directas macOS usan firma ad-hoc de integridad sin Developer ID ni notarización. Véase la [política de soporte](support-policy.md) para los sistemas compatibles.

Las compilaciones actuales de fuentes usan `xiaodaozhi` como editor del instalador Windows, mantenedor del paquete Linux y proveedor de la política de actualización. Estos metadatos no sustituyen la firma con certificado de editor; las publicaciones existentes conservan sus metadatos originales.

Para actualizaciones manuales en macOS, prefiera el DMG de Release correspondiente. Con app.zip, primero extraiga y saque xdzip.app de Descargas, cierre la versión anterior en ejecución y luego sustituya la copia en Aplicaciones. Descargar no es instalar; un paquete sin notarizar puede provocar avisos del sistema. Véase el [contrato de actualización](software-update.md) para las condiciones de alternativa manual.

Véase el [contrato de acciones del gestor de archivos](shell-actions.md) para menús contextuales, el host de operaciones independiente y el ciclo de vida de registros propios. Las acciones contextuales no abren la ventana principal de exploración y no abren por defecto la carpeta de destino al terminar.

## Punto de entrada de compilación compartido

Consulte la [guía de compilación para desarrolladores](../engineering/developer-build.md) para preparar el entorno y seguir el orden. Después de una compilación limpia y pruebas para el mismo commit, use `python3 scripts/desktop.py prepare --packaging` para preparar materiales fijados y ejecute package y verify. No use directamente el script completo de CI para el desarrollo rutinario.

`package --kind runtime|installer|all` de Windows/Linux comparte una cadena de despliegue y auditoría; el valor predeterminado es `all`. runtime primero genera el directorio desplegado; installer se construye desde el runtime verificado en el mismo output-dir y Linux también crea un tar.gz. macOS solo admite el DMG de desarrollo local `all`. Los artefactos y recibos están en el output-dir indicado, por defecto build/package. La preparación puede descargar herramientas y materiales de empaquetado fijados, pero no instala xdzip ni instala automáticamente compiladores o SDK del sistema. Windows prepara CRT/Inno Setup, Linux requiere patchelf y herramientas Debian preinstaladas y Mac usa herramientas de despliegue del sistema e integridad ad-hoc.

El `verify` ordinario comprueba los runtimes y paquetes existentes. Windows elimina las rutas de búsqueda del SDK en una copia aislada, Linux usa un contenedor de runtime aislado y Mac comprueba reubicación DMG y Cocoa/Metal. Por defecto no ejecuta los ciclos de instalación, actualización/reversión o asociación ni escribe valores predeterminados del usuario. Los mecanismos de instalación y controles de CI desechable siguientes son barreras separadas; el éxito del runtime no los sustituye.

## Windows

El instalador presenta el contrato original de runtime Microsoft VC++ incluido en el paquete. La página de licencia identifica los componentes aplicables y requiere aceptación, y luego muestra Windows-runtime-NOTICE.txt en chino e inglés. Los paquetes portátiles incluyen el mismo texto original y explicación. El código original del proyecto sigue bajo Apache-2.0; las licencias originales y los derechos de sustitución de Qt y otros componentes no cambian. Verifique hashes y descripciones completas antes de compilar; los adjuntos conservan el mismo texto. Véase [licencias Windows](windows-licensing.md).

Los paquetes portátiles y los instaladores usan el mismo directorio desplegado. [deploy_windows.py](../../../scripts/deploy_windows.py) llama a windeployqt y luego sigue la política fijada de Qt Quick Basic para eliminar FluentWinUI3, Fusion, Imagine, Material, Universal, Windows, NativeStyle/Effects referenciados solo por estilos, qmltooling y .qmltypes. Se conservan Basic, Controls impl, Templates, QML de runtime y qmldir; Qt Widgets qmodernwindowsstyle sigue prestando servicio a los controles nativos. Los directorios nuevos de despliegue no contienen DXC, DXIL ni D3DCompiler; el despliegue falla si esos nombres aparecen en cualquier lugar. `opengl32sw.dll` no se incluye en despliegues nuevos. Una copia existente en la raíz se elimina en una preparación controlada; restos homónimos en otros lugares hacen fallar el despliegue. Añadir un estilo nuevo o funcionalidad Effects exige actualizar la política y volver a verificar.

Qt Quick usa por defecto Direct3D 11 en Windows. Si el hardware o los controladores son insuficientes, Qt puede recurrir a Direct3D WARP; esto es distinto de OpenGL por software. Los paquetes nuevos no prometen un recurso alternativo Mesa por software mediante `QT_OPENGL=software` o el backend OpenGL. Los paquetes históricos y sus materiales de licencia no cambian. La [documentación de gráficos Windows de Qt](https://doc.qt.io/qt-6.8/windows-graphics.html) describe los dispositivos predeterminados y los de software solicitados explícitamente.

VC++ se despliega junto a la aplicación usando el runtime oficial Microsoft x64 14.44.35211 de las [fuentes y hashes fijados](../../../scripts/windows-runtime.json). El [script de preparación](../../../scripts/prepare-windows-runtime.py) extrae con herramientas WiX fijadas y verifica cada DLL y texto de licencia sin ejecutar instaladores EXE/MSI ni copiar de System32. Se entregan las DLL MSVCP/VCRUNTIME necesarias, licencias y procedencia; herramientas, CAB, MSI y el instalador vc_redist no ejecutado no entran en el producto. Windows 10/11 proporciona UCRT. Los runtimes locales a la aplicación deben mantenerse con sus actualizaciones; no puede dependerse de que las actualizaciones de runtime de todo el sistema los sustituyan. Véanse los [métodos de despliegue de Microsoft](https://learn.microsoft.com/en-us/cpp/windows/choosing-a-deployment-method).

La [regresión de despliegue](../../../scripts/test-windows-deployment.py) comprueba el recorte y los límites ante runtimes ausentes. La [verificación real del runtime](../../../scripts/verify_windows_runtime.py) rechaza DLL de OpenGL por software, añade DLL de prueba a una copia aislada, elimina las rutas de búsqueda del SDK y comprueba traducciones del sistema, reinicio de ajustes, barra de título nativa e inicio bilingüe. Tras eliminar las sustituciones de renderizado comprueba la inicialización predeterminada del grafo de escena D3D11 y solicita explícitamente WARP, verificando el dispositivo de software Microsoft realmente seleccionado. Las solicitudes explícitas no establecen el recurso automático ante fallos ni sustituyen la aceptación visual manual. Los archivos de prueba no entran en el directorio del producto; esto no reemplaza la aceptación de instalación, actualización y desinstalación en Windows limpio.

build-windows-installer.py solo acepta una auditoría deployed de compilación limpia y vuelve a comprobar el SHA-256 de cada archivo. Véase la [configuración de herramientas](../../../scripts/installer-toolchain.json) para Inno Setup 6.7.3 fijado, hash del instalador oficial, commit fuente, recursos de chino simplificado y tradicional y textos de licencia. El compilador no entra en el producto; los avisos incluyen el texto de licencia. El asistente admite los diez idiomas del registro compartido.

El instalador usa un AppId fijo y PrivilegesRequired=lowest e instala por defecto bajo LocalAppData/Programs/xdzip del usuario actual sin derechos de administrador. El ejecutable principal es xdzip.exe en la raíz de instalación, con las bibliotecas Qt a su lado; complementos, QML, traducciones y avisos conservan los subdirectorios necesarios. Los accesos directos, asociaciones e iconos de desinstalación apuntan a la raíz, sin jerarquía de producto versions/hash de commit. Los hashes de commit y binarios permanecen en los recibos de compilación e instalador, no en las rutas de instalación. El [registro acumulativo de desinstalación](https://jrsoftware.org/ishelp/topic_appendnotes.htm) de Inno Setup registra los archivos propiedad de cada instalación sin borrar recursivamente extras. Los ajustes y elementos recientes permanecen en los directorios existentes de configuración del usuario y el instalador no los elimina.

La nueva disposición escribe un install-manifest.txt acotado con rutas relativas auditadas y SHA-256. Antes de actualizar se validan rutas, duplicados y tamaños del manifiesto anterior; se rechazan escapes de ruta, alias de dispositivo y puntos de reanálisis en las rutas de limpieza. Si los archivos que deben retirarse fueron modificados o no pueden verificarse, la instalación se detiene antes de escribir. Tras una instalación satisfactoria solo se limpian los archivos del manifiesto anterior que ya no se entregan y aún coinciden por hash; solo se eliminan directorios vacíos y se conservan extras. Incluso si se repiten eventos de finalización en una instalación, la limpieza se ejecuta una sola vez. Los archivos modificados o retenidos durante la limpieza permanecen con un registro de reintento y código de salida no cero 20. Si no se puede escribir el registro de reintento, se requiere reparación manual; no se afirma recuperación transaccional ni seguridad ante pérdida de energía. Esta instalación por usuario supone que procesos externos no modifican el directorio simultáneamente; las comprobaciones repetidas de ruta y hash no son aislamiento contra carreras maliciosas basado en identificadores.

Las disposiciones existentes con directorios de versión se actualizan directamente. Los comandos de inicio y accesos directos pasan a la raíz, mientras las ubicaciones de ajustes y elementos recientes permanecen. El instalador antiguo no entregaba un manifiesto de propiedad independiente, por lo que los directorios históricos versions/ permanecen hasta la desinstalación normal; el registro acumulativo de Inno limpia los archivos registrados originalmente sin borrar directorios recursivamente. Se conservan los archivos añadidos por el usuario. La reversión puede reinstalar una versión anterior elegida; los fixtures QA antiguos mantienen las disposiciones históricas y pueden actualizarse de nuevo a la disposición de raíz. Una instalación nueva no crea versions/. Esto no incluye el borrado completo automático del antiguo directorio de instalación.

El producto mantiene el mutex con nombre `Local\xdzip.desktop.running` durante todo su ciclo de vida. [AppMutex](https://jrsoftware.org/ishelp/topic_setup_appmutex.htm) bloquea instalación y desinstalación, con CloseApplications=no y sin forzar el cierre de la aplicación. Si falla la creación del identificador FFI se impide el inicio; el cierre del proceso lo libera. La salida de tareas sigue usando la decisión existente y la barrera de finalización Rust.

El instalador ordinario Windows registra candidatos de archivo en HKCU. Escribe ProgID propios, dos entradas Applications propias, Capabilities, RegisteredApplications y valores OpenWithProgids propios. No toca HKLM, valores predeterminados de extensión, UserChoice/UserChoiceLatest protegidos ni candidatos de otras aplicaciones. Cada sufijo registrado tiene un ProgID como `xdzip.Archive.ZIP` y un ICO asignado. El antiguo `xdzip.Archive` conserva su comando de apertura directa y queda oculto de Abrir con junto con `Applications/xdzip.exe`. La actualización elimina sus antiguas recomendaciones preservando compatibilidad con una opción predeterminada existente. Windows asigna un nombre compuesto como `.tar.gz` por su extensión final para elegir icono.

Al iniciar y después de un cambio satisfactorio de idioma, la aplicación instalada ordinaria sincroniza las descripciones de nueve ProgID principales: ZIP, TAR, TGZ, GZ, 7Z, RAR, CAB, ISO y UDF. El instalador elige descripciones usando el idioma guardado de la aplicación o, en modo automático, el idioma de pantalla del sistema. El idioma del asistente es independiente. Antes de sincronizar en vivo, la aplicación comprueba identidad de instalación, ubicación del ejecutable, manifiesto, lanzador de asociación y los nueve comandos de apertura existentes. Si faltan registros o no coinciden, los deja intactos. Las escrituras parciales pueden reintentarse en el siguiente inicio normal. Los procesos portátiles, de desarrollo y de prueba con ajustes aislados no ejecutan esta sincronización. Los demás sufijos registrados conservan sus descripciones proporcionadas por el instalador. La caché de Explorer y el valor predeterminado elegido pueden afectar a lo mostrado.

La CI Windows desechable comprueba la sincronización de descripciones al iniciar el producto instalado y el cambio en vivo entre chino simplificado e inglés. Usa una copia portátil y un proceso con ajustes aislados para verificar que no escriben y comprueba que los nueve iconos, comandos, otros candidatos y valores predeterminados no cambian. Esta comprobación automática no sustituye la aceptación manual de la visualización en Explorer o Configuración.

Los comandos entrecomillados de todos los ProgID de formato ejecutan `xdzip-association.exe -- "%1"`; su registro Applications contiene SupportedTypes completo para que Abrir con muestre una sola entrada de la aplicación xdzip. El lanzador incorpora el mismo ICO de aplicación de marca y recursos OriginalFilename y versión de producto diferenciados. Verifique por separado los iconos de aplicación y los iconos de documento por formato; DefaultIcon de documento no puede sustituir los recursos de aplicación del ejecutable. El pequeño lanzador GUI acepta un argumento de archivo, inicializa COM en un apartamento de un solo subproceso propio y delega el comando de apertura existente mediante ShellExecuteEx con la clase explícita `xdzip.Archive` sin intérprete de comandos; libera COM después de la llamada. La reversión antigua actualiza la entrada compartida, por lo que los candidatos por formato siguen apuntando al programa revertido. Un fallo de inicialización COM, punto de entrada ausente, argumentos inválidos o rechazo del sistema devuelve un valor distinto de cero sin probar otra aplicación ni cambiar valores predeterminados. Esto depende de que la instalación de reversión conserve el lanzador en el directorio actual; la instalación/reversión y la desinstalación acumulativa requieren pruebas reales.

El instalador establece `AllowSilentDefaultTakeOver` como REG_NONE en el ProgID compartido y los ProgID específicos de formato registrados. Windows puede seguir ofreciéndolos como candidatos explícitos de Abrir con. El instalador usa una llamada nativa acotada al registro para establecer el valor en claves propias ya creadas. Si falla, detiene la instalación y libera los identificadores. Véanse las [convenciones ProgID de Windows](https://learn.microsoft.com/en-us/windows/win32/shell/fa-progids).

El instalador ordinario y MSIX generan sus candidatos Windows de Abrir con a partir del [registro de formatos](format-registry.md). El mapeo cubre los tipos principales ZIP, TAR, TGZ, GZ, 7z, RAR, CAB, ISO y UDF y sufijos registrados adicionales. `.gz` puede dirigirse a GZIP independiente o TAR.GZ según el contenido. Los genéricos `.img`, `.001` y `.rNN` están reservados para apertura explícita o puntos de entrada compatibles. La asociación proporciona al sistema una ruta hacia xdzip. El lector sigue examinando el archivo y aplicando los requisitos de formato y fuente de la operación.

## Ubuntu 24.04

build-linux-installer.py crea .deb desde el mismo directorio verificado. Los directorios de preparación privados se distinguen por la ruta de salida, lo que permite recompilar el mismo nombre de paquete en distintos directorios candidatos sin sobrescribir la preparación existente. El paquete se llama xdzip, su versión vincula canal y commit del producto y la arquitectura es amd64. Las dependencias del sistema proceden de manifiestos reales de despliegue más herramientas de base de datos de escritorio y bloqueo; glibc es al menos 2.39. Qt/QML/complementos y avisos están bajo /opt/xdzip/versions/; /usr/bin/xdzip es una entrada de reenvío entrecomillada a destino fijo. dpkg sustituye y elimina archivos de paquetes antiguos; para revertir hay que conservar el .deb original.

El [xdzip.desktop](../../../apps/desktop/packaging/linux/xdzip.desktop) instalado declara los candidatos MIME del paquete. Incluyen ZIP y alias seleccionados, TAR y TAR filtrado, flujos de compresión independientes, formatos como 7z, RAR y CAB e imágenes ISO/UDF. `%f` solicita el inicio de un solo archivo y `--` marca el límite de argumentos. El paquete proporciona una declaración MIME para `*.udf` y no modifica los tipos genéricos de imagen y binario. La instalación y eliminación actualizan bases MIME y de escritorio sin reescribir `mimeapps.list`, cambiar valores predeterminados del usuario ni sustituir iconos MIME del sistema. La desinstalación elimina lanzadores, iconos y archivos de runtime propios y conserva los ajustes del usuario.

El DEB instala su [entrada de catálogo AppStream](../../../apps/desktop/packaging/linux/xdzip-local.yml) en `/var/lib/swcatalog/yaml/xdzip-local.yml`, ruta legible por Ubuntu App Center. La entrada asocia el nombre de paquete `xdzip` con `xdzip.desktop` para que el paquete instalado pueda aparecer en la lista de aplicaciones. dpkg elimina el archivo de catálogo al desinstalar XDZip.

El producto instalado mantiene un flock compartido en /run/xdzip/usage.lock. Los scripts de mantenimiento primero obtienen un bloqueo exclusivo sin espera y fallan si existe un proceso activo. Los scripts establecen una barrera de instalación bajo /run/xdzip propiedad de root; el producto vuelve a comprobar después de adquirir su bloqueo para evitar iniciarse entre hooks de dpkg. Se rechazan enlaces simbólicos o propietario/permisos incorrectos; al cerrar QFile se libera el bloqueo. tmpfiles.d prepara el bloqueo de runtime al iniciar el sistema. Esto no afecta a las aplicaciones de desarrollo SDK.

Las rutas de éxito y aborto de dpkg limpian la barrera. Una interrupción o pérdida de energía puede dejar una transacción incompleta; ejecute sudo dpkg --configure -a y corrija el error real. No poder iniciar no es una instalación satisfactoria. Los scripts no limpian recursivamente directorios de usuario; los artefactos se generan solo en build/ o CI.

## macOS y apertura de archivos

La aplicación principal y el paquete entregado declaran documentos e ICNS como Viewer/Alternate en Info.plist, [sin reclamar la propiedad predeterminada](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html). Las compilaciones de desarrollo y prueba usan por defecto Viewer/None y no entran en los candidatos del sistema Abrir con. Los paquetes principales de desarrollo o compilaciones de entrega deben establecer explícitamente `-DXDZIP_MACOS_HANDLER_RANK=Alternate`. El usuario y Launch Services determinan los valores predeterminados; la aplicación no los cambia activamente. Limpie los registros temporales de copias de verificación de desarrollo según el [método de mantenimiento Mac](macos-deployment.md), conservando aplicaciones y valores predeterminados existentes.

CAB, ISO y UDF usan el mismo rol Viewer. ISO usa `public.iso-image`. La aplicación no reclama `.img` ni el genérico `public.disk-image`. Viewer describe la asociación de Launch Services, mientras que el [backend de formatos](native-codecs.md) determina las operaciones disponibles. El [perfil de creación ISO](iso-creation.md) independiente puede escribir imágenes nuevas.

Las declaraciones de documentos cubren las extensiones finales de todos los candidatos de shell del [registro de formatos](format-registry.md) y usan el ICNS correspondiente del paquete. Los sufijos compuestos comparten el tipo de su extensión final. Por ejemplo, `.tar.gz` y `.gz` comparten el valor predeterminado GZIP, mientras que `.tgz` usa el tipo TAR comprimido del sistema. La caché de Finder, el predeterminado elegido y el reconocimiento de tipos del sistema afectan a la visualización real.

Los tipos importados RAR, CAB y UDF de macOS deben ajustarse a `public.data` para identificar archivos reales. CAB declara tanto el tipo del sistema `com.microsoft.cab` como el de compatibilidad `com.microsoft.cab-archive`; Configuración consulta y cambia el tipo preferido real cuando es uno de ellos y, en otro caso, usa el identificador de compatibilidad. El Viewer UDF declara la extensión `.udf` sin `LSItemContentTypes` para que los archivos reales descubran un candidato aunque siga usándose una declaración UTI inválida de una instalación antigua. Apple ha dejado obsoleta esta [clave de declaración de extensión](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html); siga verificándola en las versiones macOS compatibles. Configuración consulta y cambia el tipo `.udf` realmente reconocido y recurre al identificador existente cuando no está disponible. La instalación o registro no sustituye activamente valores predeterminados. Si no existía controlador, Launch Services puede resolver un candidato nuevo como controlador actual mediante [reglas implícitas](https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/LaunchServicesConcepts/LSCGlossary/LSCGlossary.html). Eliminar el registro temporal debería restaurar el estado original; esta resolución no significa que la aplicación escriba preferencias del usuario.

FileOpenRouter recibe [QFileOpenEvent](https://doc.qt.io/qt-6.8/qfileopenevent.html) antes de QML, acepta solo archivos locales y reutiliza el enrutamiento existente de apertura y activación. Los argumentos GUI de línea de comandos después de `--` son rutas de archivo, evitando confusión con banderas de diagnóstico. Se ponen en cola hasta 128 intenciones pendientes sin interrumpir tareas activas. Los procesos ordinarios del producto en una sesión de inicio comparten instancia; las solicitudes de varios archivos se abren en orden y activan la última. Véase el [contrato de sesiones](application-sessions.md) para pestañas y ventanas.

Los argumentos de inicio se ponen en cola antes de cargar QML. La ventana principal comienza oculta y presenta la primera solicitud disponible inmediatamente al conectar el controlador, sin exigir visibilidad. La ventana se muestra en la cola inicial de eventos para que los eventos de inicio de plataforma usen la misma ruta. Durante una apertura externa, oculte la entrada de bienvenida antes de cambiar sesiones para evitar un destello de la página de bienvenida en el primer fotograma o al sustituir sesiones. La cancelación o fallo restaura la bienvenida; el éxito muestra la lista real. Véase [estado de carga](../ux/welcome-opening.md).

El inicio nativo de macOS espera por separado NSApplicationDidFinishLaunchingNotification de AppKit, procesa ese lote de eventos de archivo Qt en cola mientras permanece oculto y después muestra la ventana. Las notificaciones y llamadas en cola se limitan a la vida de la ventana principal; no sustituyen el delegado de aplicación Qt ni usan retardos fijos en milisegundos. Una regresión real de Launch Services encontró antes un fotograma de bienvenida; el requisito corregido es cero. check-macos-open.py ejecuta rutas argv y de apertura nativa localmente y en CI Mac, conservando solo JSON y registros sin generar o subir paquetes de aplicaciones.

## Verificación automática y límites

CTest en tres plataformas comprueba eventos de archivo previos al inicio, rechazo de URL no locales y puesta en cola mientras la lectura está ocupada. XDZIP_ASSOCIATION_PROBE explícito con ajustes aislados es solo para CI: use el flujo normal de apertura para leer un ZIP propio de 100.000 entradas, conserve el recuento y la identidad de compilación y salga normalmente sin registrar rutas de origen ni extraer.

La sonda actual de asociación espera al menos una presentación real de fotograma y registra por fotograma la visibilidad del contenido de bienvenida. Los requisitos actuales para Windows ShellExecuteEx y Linux GIO son presented_frames mayor que 0 y welcome_frames igual a 0. Los productos antiguos fijados se prueban según sus capacidades históricas de sonda; no se finge que los binarios antiguos tengan nuevos recuentos del primer fotograma.

La CI nativa Windows instala la variante QA 1, actualiza a 2, revierte a 1 y después instala el paquete real de entrega. ShellExecuteEx abre clases de registro propias con rutas que contienen chino, espacios y ampersand, comprobando que valores predeterminados y UserChoice no cambien, que se rechace la sustitución mientras está ocupado y que la desinstalación conserve ajustes, archivos extra y otros candidatos. Linux realiza el mismo ciclo dpkg en un contenedor sin red, SDK, Qt del sistema ni compilador. El producto con UID 1000 abre realmente 100.000 entradas mediante un lanzador de escritorio GIO; se comprueban MIME, valores predeterminados, bloqueos, desinstalación y purge.

La verificación de publicación Linux también cambia valores MIME predeterminados en un perfil de usuario aislado del contenedor y usa `gio open` cuando GIO resuelve el tipo de contenido de una muestra hacia xdzip. Comprueba cada MIME predeterminado declarado, prueba un controlador independiente y restaura los valores originales. Las comprobaciones automáticas de apertura Linux y macOS usan muestras que pueden abrirse sin entrada. La prueba de navegador AES Crypt verifica la solicitud de contraseña de apertura y las lecturas autenticadas. La configuración del sistema y otros entornos de escritorio necesitan verificación separada.

Las variantes QA comparten los binarios verificados actualmente y cambian solo la versión y el directorio del paquete de prueba para comprobar mecanismos de instalación. No son artefactos de publicación ni se hacen pasar por migración real de datos entre versiones diferentes del producto. El esquema de ajustes es actualmente 1 y los metadatos de instalación lo registran en ambas plataformas. Los instaladores antiguos rechazan sobrescribir una instalación que declare un esquema más nuevo; una migración futura debe actualizar el contrato.

La inyección posterior de fallos solo se permite en la variante QA 2, con un fallo único durante la configuración de postinst. La producción no debe contener esta rama. El contenedor verifica realmente el estado semiconfigurado, el inicio bloqueado por la barrera y la conservación de ajustes, después ejecuta dpkg --configure -a para recuperar y abre un archivo real mediante GIO. Es un fallo de configuración reproducible, no una pérdida de energía del dispositivo. Una comprobación separada de compatibilidad de ajustes compila componentes originales conservados y actuales y hace un recorrido de ida y vuelta de la configuración con el mismo esquema. Las entradas originales se fijan por hashes de cada archivo, independientemente del antiguo historial de main, y no se hacen pasar por una migración completa de datos del instalador.

La compatibilidad completa del producto se verifica por separado mediante prepare-previous-product.py, que compila el código fuente completo desde una instantánea de compatibilidad fijada (originalmente de 4cf0f8c) en hosts CI Windows/Linux desechables. Un worktree separado conserva la identidad limpia real; el SDK fijado actual compila instaladores QA del producto histórico sin descargar binarios antiguos de Actions que caducan. Instale el producto histórico y ábralo realmente, instale después el producto actual y compruebe el cambio de revisión y la conservación de bytes de configuración, luego revierta, vuelva a abrir el producto histórico y compruebe los datos. Esto demuestra compatibilidad del mismo esquema entre dos commits completos de fuentes, no un paquete original firmado históricamente, una migración inexistente de esquema 2 ni un reinicio del dispositivo. Los instaladores históricos son solo para QA y no se suben como recursos del producto; los recibos vinculan los SHA-256 de ambos binarios e instaladores.

windows-install-lifecycle.json, linux-install-lifecycle.json y los hashes de paquetes son evidencia real. El doble clic real en Explorer/Finder, la interfaz de selección predeterminada, servicios y cachés tras reinicio, avisos por falta de firma formal y comprobaciones de GPU y escritorio siguen la lista manual. Los scripts automáticos no deben marcar por sí mismos todos los INSTALL-01/ASSOC-01 como aprobados. Las conclusiones manuales existentes están en [WP-12 #5](https://github.com/xiaodaozhi/xdzip/issues/5); regenerar una plantilla pendiente no reabre la aceptación. Las migraciones de esquema futuras requieren casos reales adicionales de compatibilidad.

La sonda Windows sin tareas para protección contra sustitución ocupada usa ajustes aislados con la bandeja desactivada para que `CloseMainWindow` realice una salida normal en esa configuración. Otras sondas de apertura de asociación conservan ajustes de bandeja predeterminados y terminan mediante la barrera explícita de cierre. Las sondas de protección de instalación no deben confundir una ventana oculta con un fallo de salida del proceso ni evitar la verificación forzando la terminación de la ruta normal.

Los fixtures de protocolo de actualización Windows y los fixtures de actualización Qt real incluyen el lanzador de asociación y los nueve ICO de documento; los instaladores no pueden superar las comprobaciones si falta una carga útil requerida. El pequeño programa principal C y el comando de asociación del fixture de protocolo solo verifican la entrega de actualización. Los recursos integrados de aplicación, los candidatos nativos y las ventanas reales se comprueban por separado mediante el producto Qt completo; no se mezclan las conclusiones.

## Entradas de la base de compatibilidad a largo plazo

La actualización y reversión reales usan fuentes completas fijadas del producto antiguo en lugar del historial reescrito de main. `prepare-previous-product.py` fija una instantánea de fuente de raíz única en la rama independiente `codex/installer-compat-baseline`. Esa rama solo contiene fuentes y recursos originales necesarios para compilaciones y regresión, sin padres del antiguo main, informes de ejecución o flujos de trabajo. `COMPAT-BASELINE.json` de la instantánea registra el commit fuente y la identidad de árbol originales. No debe fusionarse de vuelta a main ni tratarse como paquete de publicación o conclusión de aceptación del producto actual.

Después de compilar, la identidad de la CLI debe coincidir con el SHA fijado propio de la instantánea; los recibos registran por separado la identidad original de fuentes y no deben hacerse pasar por el binario publicado original. Los componentes de ajustes también conservan tres pequeños archivos fuente originales como entradas de prueba duraderas, fijadas por hash de cada archivo. Las lecturas y escrituras bidireccionales y el rechazo de esquemas futuros no dependen de la red ni de commits históricos. No cambie estas entradas de regresión con la implementación actual; revise una nueva base por separado y conserve la procedencia cuando sea necesario.

La instantánea congelada es anterior al ayudante independiente de actualización y no contiene sus fuentes ni binario. Solo `prepare-previous-product.py` le pasa `--qa-historical-revision`. Los scripts de despliegue y empaquetado exigen simultáneamente CI desechable, el SHA fijado completo y coincidencia con la identidad real limpia del producto. Linux también requiere el modo de versión histórica y prohíbe mezclarlo con la variante QA actual. Windows ejecuta directamente el comando de versión del producto antiguo para la identidad; Linux usa la identidad de la auditoría independiente de despliegue y los hashes completos de archivos. Los recibos indican expresamente que las fuentes históricas carecen del ayudante, no inyectan el ayudante actual y no instalan autorización polkit para un ayudante Linux inexistente. Los productos ordinarios y variantes QA actuales siguen obligados a entregar y verificar el ayudante independiente; `--qa-legacy-version` por sí solo no permite que falte.

## Migración de versión Debian

Desde la primera versión preliminar pública se usa el epoch Debian 1: `1:<semantic-version mapping>+git<commit>`, por ejemplo `1:0.1.0~alpha.1+git...`. El histórico `0.1.0~dev.9` se ordena después de alpha.1 sin epoch según dpkg, por lo que no puede conservarse simplemente el mapeo anterior. El epoch solo sirve para el orden de paquetes del sistema; la interfaz, etiquetas de versión y release.json siguen usando la versión semántica original. Los paquetes Debian posteriores mantienen epoch 1, con el orden alpha, beta, rc y stable expresado por las versiones originales. Véase [Debian Policy](https://www.debian.org/doc/debian-policy/ch-controlfields.html#version).

El fixture real del producto histórico usa `--qa-legacy-version` solo en CI para conservar su identidad original sin epoch; no cambie el orden del paquete antiguo para ocultar problemas de actualización. El paquete actual debe superar la aceptación real de actualización, reversión y ciclo de instalación dpkg. La configuración del usuario y las asociaciones externas predeterminadas conservan sus contratos originales.

## Aplicaciones predeterminadas en Configuración

Configuración agrupa los sufijos de asociación mediante datos de formato generados. Los interruptores editables dependen del servicio de plataforma y de la identidad de instalación. Windows delega cambios en Aplicaciones predeterminadas del sistema y nunca escribe UserChoice. MSIX deja los interruptores deshabilitados y usa la entrada del paquete en la configuración del sistema. Linux asigna sufijos compatibles a tipos MIME, usa `xdg-mime` para los valores del usuario y ofrece un sustituto instalado al quitar un valor predeterminado.

En macOS, Configuración habilita cada interruptor cuyo tipo de sistema esté cubierto por las declaraciones Viewer/Alternate del paquete instalado. Un interruptor habilitado puede solicitar xdzip como predeterminado incluso si el tipo no tenía uno anterior. macOS puede pedir confirmación. Tras una devolución de llamada satisfactoria, Configuración permite un breve intervalo para que Launch Services informe el nuevo valor. Cuando la consulta del sistema confirma xdzip, la aplicación registra localmente el ID del paquete de la aplicación anterior por tipo de contenido del sistema. Al apagar el interruptor, primero solicita la aplicación anterior si macOS aún la enumera como compatible. Si no hay una aplicación compatible guardada o falla la restauración, Configuración ofrece alternativas compatibles instaladas. Si no hay alternativa, lo explica junto al interruptor. Cancelar conserva la selección actual y el estado mostrado sigue una nueva consulta del sistema. Las compilaciones Viewer/None deshabilitan cambios.

En modo de idioma automático, Windows Setup elige la descripción de asociación según el idioma actual de la interfaz del sistema del usuario. Usa chino tradicional para preferencias de chino tradicional e inglés de EE. UU. para idiomas no compatibles. Una elección manual compatible tiene prioridad. Setup conserva el modo automático para que la aplicación resuelva el idioma del sistema y sincronice sus descripciones propias al iniciar.
