# Protocolo de GitHub Release v1

[English](../../engineering/release-protocol.md) | [简体中文](../../zh-CN/engineering/release-protocol.md) | [繁體中文](../../zh-TW/engineering/release-protocol.md) | [日本語](../../ja-JP/engineering/release-protocol.md) | [한국어](../../ko-KR/engineering/release-protocol.md) | [Français](../../fr-FR/engineering/release-protocol.md) | [Deutsch](../../de-DE/engineering/release-protocol.md) | Español | [Português (Brasil)](../../pt-BR/engineering/release-protocol.md) | [Русский](../../ru-RU/engineering/release-protocol.md)

Este flujo proporciona las descargas de GitHub. El [flujo MSIX de Microsoft Store](../../../.github/workflows/windows-store-msix.yml) empaqueta el mismo código fuente versionado para Microsoft Partner Center, que gestiona la certificación y publicación en la tienda.

El [flujo Release](../../../.github/workflows/release.yml) dedicado se ejecuta manualmente mediante `workflow_dispatch`. Una ejecución formal parte de `main` con una etiqueta de versión existente y congela el commit resuelto. Cada uno de los tres trabajos nativos configura, compila, prueba y empaqueta una vez. El trabajo de macOS usa desde la compilación inicial el rango de asociación de la distribución; después despliega Qt y aplica una firma ad hoc de integridad para crear el ZIP y el DMG a partir de la misma aplicación. El CI habitual de Qt en macOS verifica frente al SDK. Developer ID, la notarización de Apple y los certificados de editor de Windows quedan fuera de esta política de publicación.

La etiqueta completa es `v` seguido de la versión semántica derivada de VERSION.json. `prerelease_number` es un entero positivo opcional; su ausencia conserva la compatibilidad con números de compilación históricos. alpha.1 y build 14 son identidades distintas. Los recursos numéricos de Windows y CFBundleVersion de macOS siguen usando números de compilación crecientes. Los activos públicos de una misma versión no se pueden reemplazar; una revisión requiere otra versión. Los borradores sí se pueden ejecutar de nuevo.

Las notas de publicación son entradas de versión permanentes y revisables, leídas por defecto de `release-notes/<full-version>.md`; la CLI puede indicar un archivo revisado con `--notes-file`. El archivo contiene una línea de metadatos `<!-- xdzip-release {"version":"0.1.0-alpha.6","build":19} -->` y un encabezado de versión correspondiente. La versión y el número de compilación deben coincidir con VERSION.json. Ejecute primero `python3 scripts/publish-release.py --check-notes`; esta comprobación no contacta con GitHub. El flujo dedicado realiza la misma comprobación antes de compilar. Cada versión nueva necesita notas propias y no hereda automáticamente listas de funciones ni estados de aceptación anteriores.

Las notas documentan en chino e inglés los límites de aceptación por plataforma, el commit real y las pruebas, conservando las aceptaciones manuales anteriores por separado de las comprobaciones no realizadas. Los issues siguen registrando el progreso de las etapas. La creación del borrador y la publicación usan la misma instantánea de notas. Si al repetir un borrador su texto difiere del archivo revisado, se detiene antes de subir o eliminar activos y exige alinear explícitamente las entradas. Las versiones publicadas siguen rechazando repeticiones que sustituyan activos. `CHANGELOG.md` archiva solo versiones realmente publicadas; una entrega local de desarrollo no se presenta como historial público.

Antes de modificar activos de un borrador, el publicador vuelve a leer la etiqueta de GitHub, el estado del borrador y la marca de canal. Stable debe seguir sin ser una versión preliminar y convertirse en GitHub Latest; alpha, beta y rc deben seguir siendo preliminares y no reemplazar Latest. Vuelva a comprobar el estado correspondiente después de publicar y después de verificar los adjuntos públicos; informe del éxito solo si todo coincide. Si una comprobación posterior falla, la versión puede estar ya visible. El script se detiene para que el propietario actúe y no retira, modifica ni reemplaza automáticamente la versión o sus activos públicos.

Antes de una publicación formal, complete la comprobación local y revise las notas correspondientes. La verificación de paquetes se ejecuta de forma independiente en la misma plataforma nativa. Solo acepta una entrega del mismo ciclo tras comprobar repositorio, commit, plataforma, arquitectura y SHA-256 del archivo. Windows y Linux verifican una vez el entorno desplegado y ejercitan el ciclo de vida real del instalador. macOS verifica tanto el DMG real como el ZIP de la aplicación. Una ejecución de candidato bajo demanda usa los mismos trabajos y descarga el artefacto ensamblado de Actions para comprobar sus sumas. La ruta de candidato usa permisos de solo lectura del repositorio, no necesita etiqueta y no accede a secretos de firma de publicación.

El trabajo de contrato de publicación primero compila el proceso aislado de formatos del mismo commit y ejecuta las pruebas del espacio de trabajo Rust con `XDZIP_NATIVE_CODEC` y `XDZIP_NATIVE_CODEC_WORKER`. Los trabajos nativos de las tres plataformas verifican por separado las aplicaciones, el despliegue y los ciclos de instalación. La prueba de rango de asociación de desarrollo de macOS usa una copia temporal del paquete compilado con metadatos de desarrollo. El paquete de distribución mantiene su rango real para los arranques nativos y el empaquetado.

Cada verificación de despliegue de Windows usa una copia temporal independiente y conserva los registros anteriores. Las repeticiones no reutilizan ni eliminan directorios existentes; los directorios de ejecución del producto no contienen DLL de prueba.

Las publicaciones incluyen siempre `release.json` y `SHA256SUMS`. El manifiesto `schema_version=1` contiene en la raíz product, version, channel, build, tag, commit (SHA completo de 40 caracteres), repository y assets. Cada activo incluye filename, platform, architecture, package_type, minimum_system, bytes, sha256 y una url fijada a la ruta de descarga de la etiqueta.

| Plataforma, arquitectura | Tipos de paquete | Sistema mínimo |
| --- | --- | --- |
| windows, x86_64 | zip, exe | Windows 11 con mantenimiento |
| macos, arm64 | app.zip, dmg | macOS 14.0 |
| linux, x86_64 | tar.gz, deb | Ubuntu 24.04, glibc 2.39, X11 |

Se requieren los seis tipos de paquete. La validación del manifiesto rechaza paquetes ausentes, destinos duplicados, canales incoherentes, URL de descarga mutables y tamaños o hashes incorrectos. Los adjuntos de la publicación incluyen avisos de plataforma, licencias, SBOM y materiales de despliegue y verificación, sin archivos comprimidos de código fuente correspondiente. Windows usa runtimes VC++ locales a la aplicación y no distribuye bibliotecas del compilador gráfico del SDK de Windows.

Desde el 2026-11-05, el propietario ordenó retirar los archivos históricos de código fuente correspondiente de GitHub Releases y de los artefactos de Actions, y detener su generación y subida en futuras publicaciones. `scripts/prepare-source-delivery.py` se conserva para revisión local. El ensamblado y la publicación rechazan nombres de archivo comprimido que contengan `corresponding-source`. Esta política no cambia las licencias de los componentes ni demuestra el cumplimiento de obligaciones relativas al código fuente correspondiente, el reenlace u otras condiciones. La revisión de publicación debe resolver esas obligaciones para la entrega real; si las condiciones obligatorias no pueden cumplirse de otra forma, se debe bloquear la distribución binaria afectada. Las instantáneas de código de etiqueta que GitHub genera automáticamente en el repositorio público no son estos adjuntos de Release.

Las publicaciones habituales no deben ejecutar por iniciativa propia el recolector de entrega de código fuente en local. Ejecútelo solo cuando el usuario solicite la recopilación de código fuente de forma separada y explícita, respetando también las restricciones de subida. Evalúe las marcas genéricas de revisión automática según los componentes reales y sus obligaciones concretas; por sí solas no prueban nuevos defectos de publicación.

El ZIP de la aplicación macOS, el DMG y los avisos se deben exportar mientras sigue presente la misma aplicación temporal desplegada y firmada, antes de limpiar la `.app` preparada y las registraciones temporales. No despliegue otra aplicación después de la limpieza para completar el ZIP.

Orden: comprobación local, congelar el commit de versión, crear la etiqueta, iniciar manualmente un flujo Release, compilar en tres plataformas y verificar de forma independiente el arranque y el ciclo de instalación, ensamblar el manifiesto del borrador, publicar por canal cuando todo esté completo y volver a descargar y verificar todos los adjuntos. Stable es un Release normal marcado explícitamente como Latest; alpha, beta y rc son Pre-releases. Cualquier fallo de plataforma deja el borrador sin publicar. Verifique SHA256SUMS antes y después de publicar. Si la revisión de procedencia o licencias, o la aceptación manual, está incompleta, conserve sus límites en las notas; la automatización no puede suplantar esos resultados.

Los clientes de actualización recorren las páginas de GitHub Releases, omiten borradores, validan las versiones del manifiesto y seleccionan por versión semántica, canal permitido por el usuario, plataforma, arquitectura y tipo de paquete. No deduzca actualizaciones por fecha de publicación ni adivine nombres de archivo. Las versiones preliminares no usan `/releases/latest`, que las excluye. Stable recibe solo stable; alpha permite alpha, beta, rc y stable; beta no vuelve a alpha; rc solo recibe rc y stable; dev se admite al comparar versiones de desarrollo. Deben aumentar tanto la versión semántica como el número de compilación. Tras la descarga verifique tamaño y SHA-256; rechace valores ausentes o distintos.

<a name="xdzip-trusted-update-attachments"></a>

## Adjuntos de actualización de confianza

Las nuevas publicaciones incluyen `release.json.sig`, con schema_version=1, algorithm=ed25519, key_id y una firma hexadecimal en minúsculas de 128 caracteres. La firma cubre los bytes originales exactos de `release.json`; no los analice y vuelva a serializar antes de verificarlos. Tanto los clientes como los asistentes de instalación sin Qt usan su propio conjunto de claves públicas integrado en `resources/update-trust.json`; no aceptan raíces de confianza de manifiestos descargados ni de solicitudes del usuario. Para la instalación se rechazan claves públicas desconocidas, key_id duplicados, claves débiles y conjuntos de confianza vacíos.

Tras fijar el nombre final de app.zip, la fase nativa de macOS usa `xdzip-update-tool sign-archive` para emitir `macos-update.json` con schema_version, version, build, filename, bytes, sha256 y la `ed_signature` de Sparkle en base64. El ensamblado vuelve a comprobar el archivo y la firma y crea `appcast.xml` con solo ese mismo candidato inmutable. El campo opcional `macos_appcast_url` del manifiesto queda fijado a ese archivo bajo la misma etiqueta. El feed usa build como versión de Sparkle, la versión semántica completa como shortVersionString y macOS 14.0 como mínimo, y solo incorpora notas breves. Las notas completas permanecen en el cuerpo de GitHub Release; los clientes no descargan notas externas.

El archivo y el feed usan una clave Sparkle independiente; el propio feed también debe firmarse. Las herramientas de publicación multiplataforma siguen el [formato de firma de Sparkle](https://github.com/sparkle-project/Sparkle/blob/2.x/common_cli/Signing.swift): firman todo el XML original y añaden un bloque de comentario sparkle-signatures con edSignature en base64 y longitud en bytes originales. No basta con firmar el archivo adjunto. Verifique independientemente después de generarlo; cualquier cambio de bytes exige firmar de nuevo. El SUPublicEDKey del paquete Mac debe coincidir con la clave pública de `resources/sparkle-update-key.json`.

El entorno de publicación aporta las claves existentes y el identificador de clave pública mediante `XDZIP_UPDATE_SIGNING_KEY_HEX`, `XDZIP_UPDATE_KEY_ID` y `XDZIP_SPARKLE_SIGNING_KEY_HEX`. El propietario proporciona dos recursos de claves públicas de producción versionados con los clientes y asistentes de instalación; no incorpore claves públicas de prueba ni genere claves privadas al compilar. Primero se distribuyen las raíces públicas de confianza en una versión del cliente y después se configuran las claves privadas correspondientes en un entorno de publicación de confianza. La rotación entrega las nuevas claves públicas antes de cambiar las claves de firma, para que los clientes antiguos mantengan una vía de verificación. Los clientes anteriores sin claves públicas integradas deben instalar primero manualmente una versión que las incluya; los manifiestos descargados no pueden añadir raíces de confianza. Las publicaciones públicas antiguas no se firman ni reemplazan retroactivamente.

Los scripts de publicación compilan las herramientas de firma en un proceso hijo del que se han eliminado ambas variables de entorno de claves privadas; solo el proceso de la herramienta compilada recibe esas claves. Los scripts de compilación de Cargo, los compiladores y la resolución de dependencias no reciben autoridad de firma.

El trabajo final de firma firma el archivo verificado y los manifiestos de actualización en `release-signing`. El trabajo de publicación separado también requiere ese entorno y verifica las firmas y las descargas del borrador antes de hacer público el Release. El último trabajo, de solo lectura, descarga la publicación pública y la coteja con los activos firmados. Todos los trabajos usan el commit congelado y artefactos de la misma ejecución.

La [aceptación de actualización de producción](../../../.github/workflows/production-update-acceptance.yml) es una entrada manual separada, fijada a `main` y `contents: read`, que usa el mismo entorno `release-signing` y la aprobación del propietario. No invoca Release ni crea etiquetas, borradores o publicaciones. Primero compila herramientas en un paso sin secretos; después deriva independientemente las claves públicas de las privadas existentes y las compara estrictamente con ambas claves públicas y el ID de clave pública del commit actual. La existencia de una entrada no demuestra que coincida. Las compilaciones privadas antiguas 200 y nuevas 201 de las tres plataformas conservan las claves públicas de producción y se compilan sin secretos. La firma solo admite candidatos fijos vinculados por completo a este commit de código, la identidad privada del producto y los hashes. La actualización nativa, la recuperación ante fallos y el reinicio normal se ejecutan después en procesos sin secretos. No hay manifiestos, activos, artefactos remotos ni parámetros de publicación arbitrarios como entrada.

Durante la preparación de la cadena de herramientas macOS sin secretos, instale una vez `rustfmt` y `clippy`, declarados en `rust-toolchain.toml`, y ejecute las pruebas de admisión del archivo. Las regresiones de actualización con claves de prueba también cubren preparación y admisión sin usar ni verificar claves privadas de producción.

Los paquetes de aceptación de producción, manifiestos originales, firmas, appcast y aplicaciones permanecen en los runners desechables y no se suben. Un recolector limitado sube solo registros, estados, identidades y hashes explícitamente permitidos y rechaza adjuntos firmados en los espacios de resultados. Registre por separado la coincidencia de claves de producción, la verificación de firmas, la instalación real y la aceptación manual del escritorio. macOS usa Apple Silicon nativo y comprobaciones reales de `SUPublicEDKey`; las pruebas en Windows Server no sustituyen la aceptación manual de Windows 11. Este flujo no lee localmente valores de GitHub Secrets ni autoriza una publicación.

`prepare-release.py --require-update-signature` se detiene si faltan una clave, una firma o metadatos del archivo nativo. `publish-release.py` vuelve a verificar independientemente el manifiesto, el feed del mismo candidato y los archivos antes de subirlos. Firmas, appcast y adjuntos de estado se incluyen íntegramente en SHA256SUMS. No añada ni reemplace estos adjuntos en publicaciones ya públicas.

<a name="xdzip-independent-cli-attachments"></a>

## Adjuntos independientes de la CLI

Desde v0.2.0, las publicaciones completas también proporcionan `xdzip-cli-<version>-windows-x86_64.zip`, `xdzip-cli-<version>-macos-arm64.tar.gz` y `xdzip-cli-<version>-linux-x86_64.tar.gz`. Los tres proceden de compilaciones y verificaciones nativas de la CLI del mismo commit, con sus procesos auxiliares, dependencias reales de ejecución y avisos; la identidad debe corresponder a una compilación Release sin cambios. El CI habitual no adquiere permiso para desplegar o subir paquetes de aplicaciones Mac.

La CLI usa `cli-release.json` y `cli-release.json.sig`. Su manifiesto tiene schema_version=1, product=xdzip y component=cli. version, channel, build, tag, commit y repository coinciden exactamente con el manifiesto de escritorio. Los activos contienen solo esos tres destinos con los mismos campos que los activos de escritorio. El tipo de paquete Mac es tar.gz; el sistema mínimo de Linux omite display_server. Se mantienen los demás requisitos de sistema, arquitectura, tamaño y resumen. El publicador fijo sigue siendo xiaodaozhi/xdzip.

El release.json de escritorio sigue conteniendo exactamente seis tipos de paquete, sin component ni entradas de la CLI. Los clientes antiguos ignoran los nuevos adjuntos independientes. La firma del manifiesto de CLI reutiliza las raíces Ed25519 integradas; sign-cli y verify-cli firman y verifican por separado los bytes originales exactos. El ensamblado y la publicación completos solo pueden hacerse públicos cuando estén completas las firmas, identidades, los tres paquetes CLI y todas las sumas. Las publicaciones públicas existentes no reciben incorporaciones, cambios ni sustituciones retroactivas.
