## Prueba de SDK externo

El host de prueba independiente reutiliza serde 1.0.229, serde_json 1.0.154, sha2 0.10.9, getrandom 0.4.2, libc 0.2.190 y tempfile 3.27.0 fijados, sin añadir versiones de terceros ni bibliotecas de formatos o CBOR. El crate de protocolo usa solo std; el CBOR acotado del proyecto interopera con un par independiente de la biblioteca estándar de Python según RFC 8949. El host no enlaza Qt, no entra en el conjunto de ejecución de escritorio o CLI ni modifica los materiales de una versión oficial.

tempfile pasa del archivo de bloqueo existente a dependencia directa de la prueba para conservar una copia ejecutable privada y verificada, sin mantener una implementación general de directorios temporales. La salida segura sigue usando xdzip-io; tempfile no autoriza la confirmación. Su origen es [Stebalien/tempfile](https://github.com/Stebalien/tempfile), con licencia MIT o Apache-2.0. Las funciones predeterminadas y el conjunto real del destino, incluidos fastrand, getrandom, once_cell y rustix/windows-sys, siguen Cargo.lock y sus metadatos y reutilizan versiones fijadas, sin descargar scripts de compilación ni añadir bibliotecas C. Se mantienen el uso, origen y licencias de las bibliotecas de base existentes; una consulta histórica de avisos no se presenta como una nueva conclusión de seguridad. Véase la [prueba del SDK](sdk-trial.md) para las pruebas y condiciones. Windows rechaza explícitamente la ejecución sin una implementación de AppContainer.

El acceso a miembros de paquetes reutiliza las versiones exactas ya admitidas de cap-std/cap-fs-ext 4.0.3 y sus funciones existentes. Abre cada componente sin seguir enlaces, relativo a directorios retenidos, para evitar carreras entre comprobar cadenas y reabrir mediante rutas del entorno. Ambos mantienen el origen de E/S segura, las licencias MIT o Apache-2.0, las versiones transitivas y el comportamiento nativo existentes; no se añade ninguna versión de terceros.

## Frontend CLI y HTTPS

La CLI promueve clap 4.6.7 bloqueado a dependencia real del frontend del producto, con solo std, help, usage, error-context, suggestions y string, sin derive ni color de terminal. Añade ureq 3.5.1 con las funciones predeterminadas desactivadas, habilitando solo native-tls-no-default y socks-proxy y seleccionando explícitamente NativeTls y las raíces de confianza del sistema. No introduce decodificación GZIP predeterminada, cookies, utilidades JSON, curl externo ni dependencias de ejecución de red de Qt. serde, serde_json, zeroize, sha2, getrandom y las vinculaciones de plataforma reutilizan versiones fijadas.

ureq y ureq-proto proceden de [algesten/ureq](https://github.com/algesten/ureq), seleccionando la licencia MIT. Las principales entradas transitivas son native-tls 0.2.18, ureq-proto 0.7.1, http 1.5.0 y httparse 1.10.1. Las versiones completas, funciones y conjuntos por destino siguen Cargo.lock y los metadatos de Cargo filtrados por host. Windows usa schannel 0.1.30; macOS usa security-framework 3.7.0 y marcos del sistema; Linux usa openssl 0.10.82/openssl-sys 0.9.118 y OpenSSL 3 del sistema. Los tipos der/PKI de RustCrypto solo ayudan al envoltorio TLS general y no interpretan formatos de archivo.

Las compilaciones Native TLS de Linux encuentran OpenSSL del sistema mediante pkg-config, sin incluir, descargar ni compilar una copia privada. Mac y Windows usan TLS del sistema. Los scripts necesarios de Cargo, el enlace nativo, las condiciones de destino y los avisos conocidos se comprueban para las versiones fijadas reales; los registros de consulta quedan en artefactos locales o de CI y los resúmenes se registran en el issue de CLI. Una consulta sin coincidencias no garantiza seguridad permanente. La FFI propia de terminal, señales y consultas al sistema de la CLI queda limitada a adaptadores de plataforma; los fallos rechazan las operaciones y los contenedores de contraseñas conservan los requisitos de borrado a cero.

Los avisos de los paquetes se recopilan por separado de los conjuntos ordinarios de dependencias de CLI y del proceso de trabajo; las dependencias de compilación, desarrollo y proc-macro se excluyen de la atribución de ejecución. La atribución de escritorio añade la raíz CLI. Solo el lanzador público de Windows enlaza estáticamente el CRT del compilador para que el punto de entrada arranque antes de cargar DLL locales con versión. Las cargas y procesos de trabajo reales siguen incluyendo el runtime VC++ fijado y las licencias originales, sin bibliotecas gráficas del SDK. Los materiales reales de publicación aún deben revisar el origen de dependencias, el código máquina estático o dinámico conservado y las obligaciones de licencia.

Al añadir una dependencia por primera vez, registre propósito, alternativas, versión, origen, licencia, dependencias transitivas, funciones, comportamiento de compilación nativa, vulnerabilidades conocidas y mantenimiento. El nombre de un crate no completa la admisión. No enumere versiones auditadas ficticias.

| Candidato | Verificación necesaria |
| --- | --- |
| Implementación ZIP en Rust | Store/Deflate, ZIP64, CRC, duplicados, bytes originales de nombres, cancelación y destino de salida del host |
| Implementación TAR + GZIP en Rust | Índice en flujo, metadatos PAX/GNU, rechazo de enlaces y dispositivos, tamaños desconocidos y flujos dañados |
| cxx | Propiedad, coherencia del generador, enlace estático multiplataforma del núcleo y que las excepciones no crucen fronteras |
| Módulos Qt | Dependencias reales de ejecución y transitivas, despliegue reemplazable, licencias y canales de actualización de seguridad |
| Conjunto de iconos | Licencia explícita de redistribución, anchura uniforme de trazos, accesibilidad e inventario de recursos |

Orden de verificación: interoperabilidad mínima → entradas maliciosas o truncadas → cancelación y límites de recursos → licencias/SBOM → compilación limpia → registro de la decisión. No eluda la protección de rutas del host mediante un desempaquetado genérico de una biblioteca.

Un espacio de trabajo de aplicación Rust incluye Cargo.lock en Git. Las nuevas bibliotecas nativas y los scripts de compilación que descargan desde la red necesitan una revisión específica; desactive las funciones no utilizadas. Si una dependencia se abandona o una vulnerabilidad no tiene solución, decida si actualizar, sustituir o desactivar la capacidad según su accesibilidad real y registre el motivo.

## Metadatos de actualización y verificación de la firma del editor

`xdzip-update` es un núcleo independiente de Qt para manifiestos, canales y verificación de firmas, al que el producto llama por una frontera cxx separada. Las herramientas de publicación y los asistentes de instalación usan las mismas reglas. Utilice `VerifyingKey::verify_strict` seguro de `ed25519-dalek = 2.2.0`, rechace claves públicas débiles y verifique los bytes originales exactos. No implemente operaciones aritméticas de firma ni considere TLS o SHA-256 como firmas del editor. Las funciones upstream fast, std y zeroize están habilitadas por defecto; batch, hazmat, legacy_compatibility, rand_core y PKCS#8 están desactivadas. Las herramientas de publicación solo importan una semilla de 32 bytes configurada por el propietario y no generan claves privadas de producción.

serde 1.0.229 y serde_json 1.0.154 reutilizan versiones bloqueadas. Las demás dependencias transitivas siguen Cargo.lock y el árbol real de funciones, incluidos digest, block-buffer, crypto-common, generic-array, typenum, cpufeatures y macros derive. El script de curve25519-dalek solo detecta capacidades del compilador local; en ejecución puede seleccionar implementaciones upstream específicas de CPU. No descarga código externo ni añade una biblioteca criptográfica C/C++ o una dependencia de ejecución de OpenSSL. La recopilación existente de avisos y proveedores incluye estos paquetes mediante metadatos de Cargo; la atribución y las licencias reales del paquete siguen sujetas a la revisión de los materiales de publicación.

Usar API criptográficas del sistema dividiría las reglas de verificación entre tres plataformas y una CLI externa de OpenSSL ampliaría las dependencias y fronteras de argumentos, por lo que se usa un único núcleo Rust. No se usa la antigua API Keypair del aviso histórico [RUSTSEC-2022-0093](https://rustsec.org/advisories/RUSTSEC-2022-0093.html). La versión corregida de curve25519-dalek exigida por [RUSTSEC-2024-0344](https://rustsec.org/advisories/RUSTSEC-2024-0344.html) es 4.1.3, que cumple la versión fijada. Estas comprobaciones no demuestran que todas las dependencias estén libres de vulnerabilidades; las actualizaciones seguirán revisando mantenimiento y avisos.

La regresión verifica cambios de bytes exactos, firmas inválidas, claves públicas desconocidas, duplicadas o débiles, conjunto de confianza de producción vacío, alternativa de canal, vinculación de versión y compilación, integridad de seis paquetes y feeds firmados. Las claves de prueba temporales solo existen en código de prueba y artefactos aislados, nunca en recursos de confianza del producto. La instalación nativa y los resultados multiplataforma se registran por separado; las pruebas del núcleo en una plataforma no sustituyen la aceptación de instalación.

## Identidad de origen en Windows

M2 usa directamente el envoltorio seguro `file::information(&File)` de la versión exacta `winapi-util = 0.1.11` en Windows para comparar números de serie de volumen e índices de archivo. La longitud y las fechas de modificación o creación no detectan de forma fiable la sustitución NTFS bajo el mismo nombre. La API correspondiente del índice de archivo de la biblioteca estándar aún no es estable y escribir Win32 unsafe ampliaría la revisión. Se reutiliza la biblioteca ya bloqueada sin añadir otra versión.

El origen es crates.io/[BurntSushi/winapi-util](https://github.com/BurntSushi/winapi-util), seleccionando MIT de la licencia dual MIT o Unlicense upstream. Las dependencias transitivas de Windows son windows-sys 0.61.2 y windows-link 0.2.1 fijadas, ambas MIT o Apache-2.0. Solo se habilitan módulos Win32 declarados upstream, se desactivan las funciones predeterminadas y no hay scripts de compilación, compilaciones nativas externas ni descargas de red. Los destinos ajenos a Windows no compilan esta dependencia de ejecución. El envoltorio seguro upstream toma prestado un manejador File válido; si falla la llamada al sistema, la fuente anterior deja de ser válida. El manejador no cruza FFI y las comprobaciones de identidad no autorizan escritura segura.

Se comprobaron el origen de las versiones, las funciones y el comportamiento de compilación nativa; pasó la comprobación de tipos del destino Windows GNU. La regresión nativa de Windows debe cubrir una sustitución de igual nombre y tamaño que conserve la fecha de modificación. Upstream es un pequeño envoltorio Win32 seguro; las actualizaciones quedan sujetas al archivo de bloqueo y las regresiones nativas. Una consulta OSV de versiones exactas del 2026-10-13 no encontró avisos conocidos para estos tres paquetes. Las respuestas históricas permanecen en los artefactos originales y las consultas nuevas registran respuestas reales según la [verificación](../../../developers/qa/README.md). Esto no prueba ausencia de vulnerabilidades. Los paquetes de desarrollo siguen recopilando todas las licencias upstream.

## Backends de formatos Rust y puente compartido del proceso de trabajo

`xdzip-codec-7z` usa la API y el dominio del proyecto, algoritmos de compresión compartidos sin dependencias de producción de terceros y primitivas criptográficas generales. AES 0.9.3 habilita zeroize; getrandom 0.4.2 y zeroize 1.9.1 reutilizan las versiones de ZIP. El SHA-256 que puede borrarse a cero se extrae a `xdzip-crypto`, independiente de formatos, que gestiona el estado incremental propio sobre la primitiva compress admitida de sha2 0.10.9, sin duplicar envoltorios por formato. El crate compartido también implementa HMAC-SHA256 y BLAKE2s/BLAKE2sp a partir de especificaciones matemáticas públicas; véase su [README](../../../crates/xdzip-crypto/README.md) para fuentes y límites. No otorga autoridad sobre archivos ni publicación y no actualiza versiones criptográficas de terceros. Los atributos de formato, composición CBC, KDF, creación y reescritura son implementaciones independientes, no procesamiento de archivos proporcionado por esas bibliotecas de base. Véase la [base de 7z](sevenzip-format-sources.md) para las fuentes, sus funciones en el análisis y las diferencias de licencia.

La lógica de formato de `xdzip-codec-optical` usa solo la biblioteca estándar y la API y dominio de códecs del proyecto, sin bibliotecas ISO/UDF ni de archivos generales. Véase el [contrato de implementación independiente](../../engineering/independent-rust-codecs.md#iso与udf只读规格) para especificaciones, alcance y errores. `xdzip-codec-bridge` reutiliza las versiones y generación bloqueadas de cxx/cxx-build, sin nuevas versiones externas, scripts de compilación que descarguen ni bibliotecas de algoritmos de formato. Sustituirlo por rutas dentro del proceso perdería la gestión de procesos de tareas ópticas existente, por lo que se mantienen el proceso de trabajo y el protocolo de flujo controlado.

`xdzip-codec-cab` depende solo de la API, dominio y `xdzip-compression` del proyecto, que no tiene dependencias de producción de terceros. MSZIP reutiliza Deflate de ZIP/GZIP; LZX y Quantum son módulos de algoritmo independientes sin biblioteca adicional de Deflate ni de archivos generales. Los backends 7z, CAB y óptico comparten `xdzip-codec-bridge` y flujos autorizados por el host. La creación solo añade callbacks de entrada controlada y preparación aleatoria sin duplicar fronteras generales. El producto usa Rust; Cab oficial y LZX/Quantum específicos de CAB no entran en las compilaciones. Véase el [contrato propio](../../engineering/independent-rust-codecs.md#cab只读规格) para recursos y formatos y las [fuentes CAB](cab-format-sources.md) para alcance de análisis y licencias.

`xdzip-codec-rar` reutiliza la misma API de códecs, algoritmos de compresión compartidos y primitivas criptográficas sin introducir RAR ni otras bibliotecas de archivos. El modelo estadístico PPMd H se comparte entre 7z y RAR; cada formato define su propio rango, reinicio y terminación. Las combinaciones especiales de compatibilidad con contraseñas antiguas permanecen en el módulo RAR. El calendario del sistema y la codificación OEM/ANSI/local usan callbacks ligeros del proceso de trabajo; Rust maneja los campos de formato, truncamiento de contraseñas y validación. Qt no entra en la lógica de formato.

La política de dependencias de producción comprueba los conjuntos de dependencias ordinarias y de compilación de los crates de formato y puente. Los contenedores, algoritmos y utilidades generales oficiales de 7-Zip y UnRAR han salido de los manifiestos CMake del producto; la lista de preparación de fuentes del producto está vacía y no hay alternativa en caso de fallo. Las obligaciones de licencia de entregas históricas siguen vigentes. pycdlib independiente, Microsoft IMAPI, fixtures mkudffs/udfclient, procesos de referencia oficiales y vectores de especificación son solo para pruebas; sus fuentes y licencias se gestionan por separado y no entran en las dependencias de ejecución. Las entradas y generadores pequeños y fijados del proyecto se versionan en los directorios de prueba; las imágenes expandidas y la evidencia de ejecución permanecen en build/.

## ZIP propio y primitivas criptográficas generales

Los contenedores ZIP, la creación en flujo, la reescritura ordinaria y el envoltorio AES usan una [implementación Rust independiente](../../engineering/independent-rust-codecs.md); Deflate/CRC-32 reutilizan `xdzip-compression`. `rawzip = 0.5.2`, `zip = 9.0.3` y `flate2 = 1.1.10` son solo referencias de desarrollo y prueba y no entran en los conjuntos de dependencias de producción o compilación de ZIP. No llaman a un desempaquetado genérico ni autorizan rutas arbitrarias. Las entregas históricas que los usaron conservan sus obligaciones de licencia.

Las primitivas criptográficas reutilizan versiones exactas de dependencias transitivas existentes promovidas a directas: RustCrypto `aes = 0.9.3`, `hmac = 0.13.0`, `sha1 = 0.11.0`, `pbkdf2 = 0.13.0`, además de `getrandom = 0.4.2` y `constant_time_eq = 0.6.1`. PBKDF2 solo habilita hmac. SHA1 desactiva alloc/oid predeterminados y habilita solo zeroize; AES/HMAC también habilitan zeroize. No se añade biblioteca de formato, biblioteca nativa de compresión ni descarga en ejecución. El proyecto implementa CTR, el envoltorio con sal aleatoria, la división del resultado derivado, los valores de verificación de contraseña y EOF autenticado; las primitivas generales no deben reintroducir un analizador ZIP.

Estos paquetes y las dependencias transitivas cipher/digest se bloquean en Cargo.lock y proceden de crates.io y sus upstreams. AES/HMAC/SHA1/PBKDF2/zeroize/getrandom usan MIT o Apache-2.0; constant_time_eq usa CC0-1.0 o MIT-0 o Apache-2.0, según los textos del paquete fijado real. Los parámetros SHA-1/PBKDF2 proceden de WinZip AES y no se usan para otro esquema elegido de almacenamiento de contraseñas de usuario. Los scripts de compilación solo configuran la plataforma, sin descargas de red ni compilación de decodificadores C.

`zeroize` se fija de forma uniforme en 1.9.1 para satisfacer las funciones de limpieza de claves de AES 0.9.3. Los contenedores de contraseñas del host, adaptador nativo, actualización y sondas mantienen una versión en vez de dos del mismo major. Debug de secretos sigue oculto; los búferes derivados y claves expandidas usan ciclos de vida con borrado a cero soportados por las bibliotecas, sin afirmar que puedan borrarse todas las copias históricas de memoria. La admisión incluye el archivo de bloqueo, licencias, árbol real de funciones, pruebas de fallo e interoperabilidad con 7-Zip independiente. Las respuestas originales de consultas de vulnerabilidades permanecen en artefactos de compilación; una consulta exitosa sin avisos no garantiza ausencia de vulnerabilidades.

## WP-11 TAR/GZIP

Fije exactamente [tar 0.4.46](https://docs.rs/tar/0.4.46/tar/) (crates.io, [origen upstream](https://github.com/alexcrichton/tar-rs), MIT o Apache-2.0) desactivando la función xattr predeterminada. Solo es una referencia independiente de lectura y escritura para desarrollo y pruebas. Las cabeceras TAR, PAX, creación y reescritura del producto usan una [capa independiente de registros Rust](../../engineering/independent-rust-codecs.md), no un analizador o Builder TAR de terceros, desempaquetado genérico ni restauración de propietario o permisos. Los conjuntos de producción prohíben que tar y filetime regresen; se mantienen las licencias de prueba y entregas históricas. La codificación escribe explícitamente rutas PAX UTF-8 y números fuera de rango para interoperabilidad de nombres entre plataformas.

GZIP usa la implementación independiente `xdzip-compression` sin dependencias de producción de terceros, incluidos Deflate RFC 1951, tramas RFC 1952 y CRC-32. La entrada comprimida y la salida decodificada están sujetas a la cancelación y los presupuestos de bytes del host. Una decodificación completa verifica CRC e ISIZE de cada miembro. `flate2` 1.1.10 es una referencia de desarrollo y prueba. ZIP y GZIP usan el mismo algoritmo Deflate propio. Las rutas de ejecución distinguen [GZIP independiente](single-file-streams.md), que expone un archivo lógico, de [TAR.GZ](tar-gzip.md), que expone un árbol de directorios TAR.

Las dependencias transitivas de prueba de tar incluyen filetime 0.2.29 (MIT o Apache-2.0), reutilizando cfg-if y libc; filetime no entra en el conjunto del códec del producto. No hay nuevos scripts de compilación que descarguen, solicitudes de red en ejecución ni backends de formato en procesos externos. El collect-notices.py existente recopila licencias del archivo de bloqueo; que un paquete de prueba figure en él no significa que el producto lo enlace. tar del sistema y tarfile de Python son solo para pruebas y no entran en las dependencias de ejecución.

Una consulta OSV de versión exacta el 2026-10-15 para tar 0.4.46, filetime 0.2.29 y flate2 1.1.10 no devolvió avisos. Las respuestas originales solo permanecen en build/review/wp11. Esto no garantiza ausencia de vulnerabilidades. La interoperabilidad bidireccional, las entradas incorrectas, cuotas, cancelación y verificación en tres plataformas deben ejecutarse realmente; la evidencia se enlaza desde el [contrato WP-11](tar-gzip.md).

## Derivado QtNetwork con parches de seguridad

La biblioteca dinámica Network de Qt 6.8.2 de escritorio usa `6.8.2-xdzip-network.1`, aplicando cinco parches oficiales sin modificar a un archivo QtBase fijado para CVE-2026-116337 y CVE-2026-105946. El alcance comprende límites de recepción de la línea de estado y cabeceras HTTP/CONNECT y fronteras del análisis de autenticación; no se reemplazan QtCore, otros módulos ni plugins TLS. Se conservan los conmutadores de funciones, símbolos exportados y compatibilidad de importación con QtCore del SDK original. Véanse las [notas de mantenimiento](../../../patches/qt/README.md) para fuentes, orden, hashes, licencias, sustitución y verificación con entradas reales. Producción mantiene el enlace dinámico LGPL-3.0. Las pruebas upstream exclusivas GPL no se distribuyen; OpenSSL 3.5.9 solo genera declaraciones de compilación y no se compila ni distribuye una nueva biblioteca criptográfica. El origen, avisos y condiciones de reenlace del paquete real aún requieren revisión separada.

Linux también añade una unidad original fijada por digest para conservar ABI, que instancia explícitamente constantes de tipos integrados del SDK existente y mantiene las exportaciones originales sin añadir comportamiento de red. El código y los avisos Apache-2.0 acompañan los materiales. Los cinco parches oficiales no se modifican y las bibliotecas de producto de otras plataformas no reciben esta unidad.

## Proveedor de actualización macOS

La integración de actualización de Mac fija Sparkle 2.10.0 y la extensión de proxy `xdzip-proxy.2`. Los hashes del SDK, archivo de código, parche y texto completo de licencia están en la [configuración de dependencias](../../../scripts/sparkle-dependency.json). Solo maneja actualizaciones de la aplicación, no decodificación de archivos. Los textos originales de licencia del SDK oficial incluyen MIT, BSD-2-Clause y Zlib y se conservan en los avisos de Mac. El recopilador local de código correspondiente conserva el código fijado y los archivos originales del SDK para preparación sin conexión y reenlace del marco dinámico; según el protocolo de publicación, este archivo no se ofrece como recurso descargable de Release ni Actions.

Las 67 unidades Objective-C y 10 unidades C Ed25519 upstream de la biblioteca principal se compilan con Clang nativo de Apple Silicon a partir del código fijado y un [parche restringido](../../../patches/sparkle/2.10.0-download-proxy.patch), conservando las funciones de compilación y la IPC de instalación upstream. Los recursos, asistentes de instalación y herramientas de firma siguen procediendo del SDK oficial; no se afirma que se hayan reconstruido desde el código. El marco derivado registra una variante separada, hashes del código, parche y compilador, y recibos de compilación por archivo. La atribución del despliegue y el SBOM distinguen este origen de los bytes del SDK oficial. Véanse las [notas de mantenimiento del parche](../../../patches/sparkle/README.md).

La extensión usa Network.framework del sistema para proxies personalizados sin alternativa de conexión directa y conmutadores de proxy de sesión CFNetwork para conexiones explícitamente directas. No añade una biblioteca de ejecución redistribuible ni modifica los ajustes de proxy del sistema.

El trabajo de Mac del flujo Qt bajo demanda enlaza el SDK externamente y no despliega el marco. El empaquetado dedicado lo incorpora en una copia temporal, elimina los servicios XPC no habilitados para la aplicación sin sandbox y conserva los asistentes necesarios de instalación. Tras reducir y reubicar, realice la firma ad-hoc de integridad en orden: asistentes, marco y aplicación. Los asistentes conservan Hardened Runtime y los entitlements específicos requeridos; no aplique un comando genérico de nueva firma para bibliotecas nativas. Se registran junto con la versión la atribución del despliegue, SBOM, licencias y materiales de código.

## Herramientas experimentales de instalación

Las compilaciones de Windows introducen Inno Setup 6.7.3 solo para compilar instaladores por usuario del directorio de ejecución del proyecto. Su origen es la [versión oficial de jrsoftware/issrc](https://github.com/jrsoftware/issrc/releases/tag/is-6_7_3); el commit inmutable y los SHA-256 de binarios oficiales, recursos de idioma chino y texto de licencia se fijan en [installer-toolchain.json](../../../scripts/installer-toolchain.json). Use el modo por usuario y registros acumulativos de desinstalación. NSIS y WiX/MSI son alternativas; este trabajo no mantiene una base de datos propia de limpieza ni reglas de despliegue empresarial.

Use la licencia Inno Setup License de ese código fijado, conservando derechos, origen e interfaz del motor sin modificar el compilador. Incluya el texto en los avisos de Windows. El código transitivo usa Pascal Script, compresión y componentes de plataforma del compilador oficial y del stub del instalador; aquí no se reconstruye el motor. Compruebe las fuentes y licencias de los componentes incorporados frente a la entrega real. El compilador se instala en build/ de CI y no entra en el directorio de ejecución Qt. El stub entra en el instalador final; los recibos registran su versión y el hash del instalador. El SBOM del directorio de ejecución no se presenta como un SBOM completo del stub.

Habilite solo copia estándar de archivos, registro por usuario, accesos directos del proyecto y protección por mutex. Desactive el cierre y reinicio automáticos de la aplicación. No hay descargas de red durante la instalación, plugins nativos personalizados ni nuevos scripts Rust de compilación. El .deb de Linux usa dpkg-deb de Ubuntu y herramientas de mantenimiento del sistema sin añadir códecs a la aplicación. Los directorios de trabajo de la herramienta de descarga Qt se fijan bajo build/ para que aqtinstall.log no contamine la identidad del código.

La API pública de avisos de seguridad del repositorio oficial devolvió una lista vacía el 2026-10-16; la respuesta original permanece en build/review/installer-tool-advisories.json. Esto no prueba ausencia de vulnerabilidades ni constituye una búsqueda NVD completa. El [historial oficial de versiones](https://jrsoftware.org/files/is6-whatsnew.htm) sirve para revisar el mantenimiento de seguridad posterior; fijar 6.7.3 no afirma que sea la versión más reciente ni que tenga soporte a largo plazo. La compilación, instalación, apertura del sistema, actualización, reversión, desinstalación y fallos reales se registran en el [contrato de instalación](installers-associations.md) y la CI real.

## Detección y decodificación de nombres antiguos

Fije exactamente [chardetng 1.0.0](https://docs.rs/chardetng/1.0.0/chardetng/) y [encoding_rs 0.8.42](https://docs.rs/encoding_rs/0.8.42/encoding_rs/), ambos procedentes de crates.io y del upstream de hsivonen. El primero usa MIT o Apache-2.0; el código del segundo usa MIT o Apache-2.0 y sus datos de mapeo WHATWG también usan BSD-3-Clause. Conserve LICENSE-WHATWG y COPYRIGHT. El recopilador de avisos incluye COPYRIGHT, no solo textos completos de licencia.

Desactive las funciones predeterminadas de ambos. encoding_rs habilita directamente solo alloc; desactive multihilo/rayon del detector. Los paquetes transitivos recién fijados son core_detect 1.0.0, multiversion_no_op 1.0.0, scopeguard 1.2.0 y simdutf8 0.1.5, todos MIT o Apache-2.0. cfg-if 1.0.5, memchr 2.8.3 y la macro de compilación rustversion 1.0.23 reutilizan versiones fijadas. core_detect detecta capacidades de CPU local, simdutf8 es la validación SIMD UTF-8 upstream y multiversion_no_op es una macro sin efecto en compilación. No se añaden bibliotecas nativas C/C++, scripts de compilación de red ni descargas en ejecución. El script de encoding_rs selecciona solo configuración local según la versión del compilador. El unsafe específico de CPU permanece en código upstream mantenido; el host no añade unsafe/FFI.

Un solo detector Rust evita reglas divergentes entre Qt, iconv del sistema y páginas de códigos Windows. Mantener un modelo estadístico CJK o invocar extractores externos ampliaría las fronteras de implementación y despliegue. El upstream de chardetng se declara mantenido de forma pasiva; los cambios de versión o modelo requieren repetir muestras independientes de nombres. ZIP CP437 es un mapeo fijo de un byte basado en la [tabla Unicode CP437](https://www.unicode.org/Public/MAPPINGS/VENDORS/MICSFT/PC/CP437.TXT), sin API de plataforma; la biblioteca estándar de Python genera por separado los bytes originales de prueba. La detección es heurística, no evidencia de autorización de rutas ni verificación de contenido.

Una consulta OSV de versión exacta para seis paquetes recién fijados el 2026-10-24 no devolvió avisos; las respuestas originales solo permanecen en artefactos locales. Es una comprobación dirigida, no una garantía de ausencia de vulnerabilidades. La admisión también comprueba las funciones reales de Cargo, fuentes y textos completos de licencia. Véase el [contrato de codificación de nombres](filename-encoding.md) para alcance de regresión, recursos y reglas de fallo. Las compilaciones en tres plataformas, interoperabilidad de contenido y resultados reales se siguen en el issue y CI correspondientes.

Mantenga Qt 6.8.2 fijado y añada qtimageformats oficial; el commit y los digests del archivo de código están en la [configuración de componentes](../../../scripts/corresponding-sources.json). ## Adaptadores de menú del gestor de archivos

La extensión Windows depende solo de API del sistema del SDK Windows y del runtime MSVC estático. El asistente de servicio macOS depende solo de AppKit del sistema y de la biblioteca estándar C++. Las auditorías de despliegue Linux registran las versiones y fuentes reales de los paquetes del sistema; no se incluye otra copia de Nautilus/GLib. El código adaptador del proyecto, el uso de la interfaz y la aplicación Nautilus completa tienen licencias separadas.
